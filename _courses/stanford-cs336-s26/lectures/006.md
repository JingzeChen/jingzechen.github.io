## 学习目标

- 理解本讲如何把上一讲的 GPU 高层性能图景，推进到 benchmarking、profiling 与 Triton kernel 编写。
- 建立统一的 GPU 编程心智模型：grid -> thread block -> thread，以及 HBM / shared memory / registers 的层级关系。
- 能说明 kernel 性能为什么受 warp、occupancy、bank conflicts、memory coalescing、block occupancy 等硬件细节左右。
- 能按老师的顺序讲清四个 Triton 例子：GeLU、softmax、row-sum、matmul+ReLU。
- 能把 benchmark/profile 看成 kernel 开发流程中的入口，而不是收尾动作。

## 需要的先修知识

- GPU 的基本部件与上一讲对性能层级的高层介绍。
- element-wise 运算、softmax、矩阵乘法的基本数学含义。
- 行列式样的内存访问、stride、以及矩阵维度规则。
- PyTorch 的张量表达式与基本自动并行直觉。

## 老师的教学主线

- 先复习 GPU 硬件与编程模型，明确 correctness 的抽象层和 performance 的硬件层并不相同。
- 再给出 benchmark/profile 的方法论，要求在真正动手写 kernel 前先测量瓶颈。
- 用 GeLU 对比 naive、built-in、compiled 三种实现，借 profiler 说明 kernel fusion 与 HBM 读写次数才是性能差异来源。
- 然后切到 Triton，把思考单位从 CUDA 的单 thread 提升到 thread block。
- 最后沿“element-wise -> row-wise reduction -> row 不 fit in block -> matmul tiling”的顺序递增复杂度，完成从模板到大例子的闭环。

## 核心概念与依赖关系

- 硬件层级：HBM 全局且慢，shared memory 与 registers 更局部更快。
- 编程层级：grid 管 blocks，block 管 threads；Triton 原生按 block 思考，PTX 则是更底层的 thread 执行层。
- 性能概念：warp / control divergence、warp occupancy、thread coarsening、bank conflicts、memory coalescing、block occupancy。
- 工具链：benchmark 回答“多久”，profile 回答“花在哪、底层跑了什么”。
- Kernel 设计依赖链：GeLU 先给出基本模板；softmax 引入 block 内归约；row-sum 引入 tile 循环；matmul 则把 tile 复用推广到二维输出块与 shared-memory tiling。

## 关键推导、例子与结论边界

- occupancy 例子给出可计算的资源约束：128 threads、160 registers/thread 时，一个 SM 大约只能并发 3 个 blocks、12 个 warps，occupancy 约 18.75%。
- benchmark 例子说明 GPU 对小矩阵并不高效，小到一定规模前 matmul 时间近似常数，之后才显出近似立方增长。
- GeLU 例子证明“语义相同不代表性能相同”：naive 多 kernel 往返 HBM，built-in 与 compiled 借单 kernel 融合显著加速。
- softmax 例子划出边界：一行 fit in block 时几乎可以像普通 PyTorch 一样写；不 fit 时就必须引入 tiles 和显式循环。
- matmul 例子说明 tiling 的必要性：整体装入 shared memory 只是理想状态，真实实现只能局部复用，性能收益受 tile 大小与硬件约束共同限制。
- 结论边界：老师多次强调课堂实现主要用于传递思路，不宣称是最优内核；不同硬件下相对快慢可能变化。

## 易错点与待核对项

- 不要把 Triton 误解为 GPU 上逐句执行的 Python；它会被编译成 PTX，再映射到真实硬件执行。
- 不要把 occupancy 当成单一优化目标；thread coarsening 可能以更低 occupancy 换来更高吞吐。
- 不要混淆 shared memory 的 bank conflicts 与 HBM 的 memory coalescing。
- 不要混淆 blocks 与 tiles：有时一片数据是独立 block，有时只是同一 block 反复处理的 tile。

## 概念、符号与推导

- GPU 存储层级：HBM 是全局、大而慢；L2 是整芯片共享；L1 cache / shared memory 与 registers 位于 SM 上，本地、快但小。
- SM：Streaming Multiprocessor。老师用它作为 GPU 上承载 block 执行与本地存储层级的基本硬件单位。
- Thread：对一小块数据执行代码的最小编程单位。
- Thread block / CTA：一组 threads，能围绕同一片 shared memory 协作。
- Grid：一组 thread blocks；启动 kernel 时实际启动的是一个 grid。
- element-wise 视角：老师口头用“$f(i)$，$i=0,\ldots,N-1$”说明一个 thread 处理一个元素的模式。[需回听]
- 为什么需要 block：非 element-wise 操作需要线程通信，而 HBM 慢，因此要把会共享 shared memory 的线程放在同一 block，并让该 block 落在单个 SM 上运行。
- Warp：一个 block 内部按 32 个线程一组再分组；warp 内线程必须同步执行同一指令。
- Control divergence：若 warp 内不同线程分到不同分支，则两条分支都会串行执行，降低吞吐。
- 本段无公式推导。

## 例子与课堂提示

- [00:04:45-00:04:58] GeLU 被用作“只做 element-wise 时 thread 很自然”的正例，服务于说明“不是所有操作都需要 block 级协作”。
- [00:05:05-00:06:37] Softmax 与 matmul 被用作反例，说明一旦需要线程通信，只靠 thread 独立读写 HBM 会非常慢，因此必须引入 shared memory 和 thread block。
- [00:06:22-00:06:37] 老师把一个 block 的标准动作概括为“从 HBM 读、在本地处理、写回 HBM”，这是后面理解 Triton kernel 模板的课堂提示。
- [00:09:45-00:10:04] if A else B 的分支例子用于提醒：warp 级分歧会把本来并行的事情变成顺序执行，是 kernel 设计时应尽量避免的模式。

## 本段在整讲中的作用

本段承接前一段对 warp 的引入，集中展示“编程模型之外，硬件细节如何决定性能”。老师依次用 warp latency hiding、warp occupancy、bank conflicts、memory coalescing、block occupancy 五类例子，把后面 profiling 与 kernel 优化所需的性能语言补齐。

## 教学展开

- [00:10:04-00:11:10] 老师先补完 warp 的另一个重要性质：SM 同时驻留多个 warps，并可零成本切换。这样当某个 warp 因 HBM 访问而等待时，SM 可以切到别的 warp 执行，用来隐藏延迟。
- [00:11:14-00:12:47] 接着引出 occupancy，尤其是 warp occupancy。约束是每个 thread 最多 255 个 registers；每个 thread 用的 registers 越多，同一个 SM 能并发的 threads / warps 越少，但 occupancy 低并不自动等于坏，因为每个 thread 也可能做更多工作。
- [00:12:07-00:12:47] 老师用 thread coarsening 说明这个 tradeoff：原本一个 thread 处理一个元素，也可以改成一个 thread 处理多个元素，线程数更少但每个线程更“胖”。
- [00:12:49-00:14:05] 随后给出一个具体 occupancy 例子：block 有 128 个线程，每个线程用 160 个 registers，B200 每个 SM 有约 65,000 registers、最多 64 warps。由此算出每个 block 约用 20,000 registers，每个 SM 最多并发 3 个 blocks，也就是 12 个 warps，occupancy 约 18%。
- [00:14:21-00:16:37] 然后切到 shared memory 的 bank conflicts。shared memory 被划成 32 个 banks，每个 bank 宽 4 bytes；若多个 threads 同时访问同一 bank，不得不串行化。老师用“32 个线程都访问矩阵第一列”举出最坏的 32-way bank conflict，并说明 matmul 中行/列访问常常使这类冲突难以完全避免。
- [00:16:24-00:16:37] 对 bank conflict 的缓解只点到一个关键词：swizzling，通过重新排布 shared memory，减少冲突。
- [00:16:50-00:18:14] 再回顾 HBM 上的 memory coalescing：warp 中 32 个线程访问 HBM 时，请求会尽量合并成 128-byte cache line 事务。最佳情况是 32 个线程正好落在同一 cache line；若按列访问，则会带回很多根本用不到的数据。
- [00:18:15-00:19:14] 最后讲 block occupancy：block 是按“波次”调度到有限个 SM 上的。若 B200 有 148 个 SM，却发出 160 个 blocks，那么第一波 148 个、第二波只剩 12 个，第二波会让大量 SM 闲置。
- [00:19:18-00:20:04] 老师收束本段：抽象上 memory 是 HBM -> shared memory -> registers，但性能由 warps、bank conflicts、memory coalescing、occupancy 等硬件细节共同决定，而且这些细节并不总像编程模型那样干净。

## 概念、符号与推导

- Latency hiding：一个 warp 因 HBM 读写停住时，SM 切换到别的 resident warp 执行，以隐藏等待开销。
- 每线程寄存器上限：255 registers。
- Warp occupancy：在硬件允许的最大 warps 数量中，当前真正驻留并可运行的 warps 比例。
- Thread coarsening：让单个 thread 处理多个元素，以减少线程数量、提升每线程工作量。
- Occupancy 例子推导：
  - 线程数/块：128
  - 每线程寄存器数：160
  - 每块寄存器数：$128 \times 160 = 20480$
  - 每个 SM 的寄存器总量：约 65536
  - 可并发 blocks 数：$\lfloor 65536 / 20480 \rfloor = 3$
  - 每块 warps 数：$128 / 32 = 4$
  - 可并发 warps 数：$3 \times 4 = 12$
  - 最大 warps 数：64
  - Occupancy：$12 / 64 = 18.75\%$，老师口头近似为 18%。
- Bank conflict：shared memory 的 32 个 banks 中，若同一时钟周期多个线程访问同一 bank 的不同地址，这些访问会被串行化。
- Memory coalescing：warp 对 HBM 的多个访问尽量合并成 128-byte cache line 事务；最佳情况是 32 个线程刚好共同覆盖一个 cache line。
- Block occupancy：由于 SM 数有限，blocks 只能分波调度；最后一波 blocks 太少时会造成 SM 闲置。

## 例子与课堂提示

- [00:10:49-00:11:10] “一个 warp 在读 HBM，另一个 warp 去做 tensor core 运算”这个例子服务于解释为什么 GPU 能靠多 warp 驻留隐藏高延迟访问。
- [00:12:07-00:12:47] thread coarsening 的例子提醒：不要把 occupancy 当作“越高越好”的单指标，关键是吞吐与资源占用的整体平衡。
- [00:15:26-00:15:46] 32 个线程同时访问矩阵第一列的最坏例子，服务于说明 bank conflict 为什么会把看似高并行的访问彻底串行化。
- [00:15:54-00:16:18] matmul 必须同时访问一边的行、一边的列，这个例子说明某些冲突并非简单换访问顺序就能消失。
- [00:17:35-00:18:01] “按行访问 vs 按列访问”的 cache line 例子用于区分 coalescing 与 bank conflicts：前者关心 HBM 事务是否浪费带宽，后者关心 shared memory 是否发生同 bank 串行化。
- [00:18:36-00:19:14] 148 个 SM 上发 160 个 blocks 的波次例子，是理解 wave quantization / tail inefficiency 的直接课堂提示。

## 本段掌握检查

1. 为什么说 warp 切换能隐藏 HBM 延迟？
参考答案：因为 SM 同时驻留多个 warps；某个 warp 因 HBM 访问阻塞时，SM 可零成本切换到另一个可执行 warp。

2. occupancy 低一定差吗？
参考答案：不一定。若每个线程做更多工作，例如 thread coarsening，较低 occupancy 也可能换来更高整体效率。

3. 128 个线程、每线程 160 个寄存器、SM 有 65536 个寄存器且上限 64 warps 时，occupancy 大约是多少？
参考答案：每块 20480 寄存器，最多 3 块并发，共 12 warps，occupancy 约为 $12/64 \approx 18.75\%$。

4. bank conflict 与 memory coalescing 分别对应哪层存储？
参考答案：bank conflict 对应 shared memory；memory coalescing 对应 HBM 访问事务。

5. 为什么 160 个 blocks 落在 148 个 SM 上会有 block occupancy 问题？

## 本段在整讲中的作用

## 教学展开

- [00:59:55-01:00:21] 老师先把 naive softmax 的性能问题明确量化：多个逐步操作分别从 HBM 读写，导致每个矩阵整体约有 $5MN$ 次读、$3MN$ 次写，而原则上应远少于此。

- [01:00:42-01:01:11] 核心设计决策是“每一行是一个 block”。原因是 softmax 不是 element-wise，但它是 row-wise；不同行之间无需通信，因此自然可以用 block 为单位独立处理。
- [01:01:20-01:01:58] 在 Python 侧，先分配输出矩阵；随后把 block size 取为列数并上调到 next power of 2；block 数就是行数，每行一个 block。

- [01:03:33-01:03:44] 读入整行后，核心计算与 naive softmax 一样：求 max、减 max、取 exp、求和、再除法归一化，最后把结果写回。

- [01:04:30-01:05:22] 问答阶段，老师说明若想按列做 softmax，主要修改的是 stride / pointer 的走法；本质上仍是通过地址计算决定访问模式。
- [01:05:24-01:06:18] 然后转向更难情况：如果一整行放不进一个 block，例如 4000 列但 block size 只有 1024，就必须把一行拆成多个 tiles，让每个 thread 迭代这些 tiles 并累加部分结果，最后再做一次归约。
- [01:06:20-01:09:54] 为了降低概念负担，老师把示例从 softmax 换成 row sum。思路是：一个 block 仍负责一整行，但行内按 tile 0、tile 1、tile 2 切开；每个 thread 带一个 accumulator，遍历各 tile，把自己负责位置上的值不断累加，所有 tile 走完后再把整个 accumulator 向量求和，得到这一行的标量和。

## 概念、符号与推导

- naive softmax 的读写统计：$5MN$ reads、$3MN$ writes；老师用它说明不融合时 HBM 往返过多。
- Softmax 的 block 设计：一行对应一个 block，因为 softmax 是 row-wise reduction，不同行彼此独立。
- block size 选择：取列数并上调到 2 的幂，确保一个 block 能覆盖该行全部列。
- row stride：告诉 kernel 从一行起点跳到下一行起点需要跨过多远的地址。
- mask 的 softmax 语义：masked-out 位置填 `-inf`，使其 exponentiate 后等效于 0 贡献。
- 行内计算顺序：先求 max（数值稳定），再减 max、取 exp、求分母、再做归一化。
- 行放不进 block 时的策略：把一行切成多个 tiles；每个 thread 在循环中跨 tile 累积局部值，最后再做一次 reduction。

## 教学展开

- [01:09:54-01:10:11] 老师先结束 row-sum kernel：每个 thread 遍历完所有 tiles 后，手里有自己的 accumulator；把这些 accumulator 再求和，就得到这一整行的标量结果并写出。
- [01:10:06-01:10:48] 他强调这比前面更复杂，因为 thread 内部真的出现了 `for` 循环；只要数据放不进一个 block，这类循环就不可避免。关于 accumulator 放在哪里，老师说 Triton 程序里不显式指定，由编译器决定；若 block 太大，通常不得不落到 shared memory。
- [01:10:57-01:11:38] 老师再次校准概念：GeLU 时也把行切成许多片段，但那些片段本身就是 blocks、彼此独立；这里切出来的是 tiles，不是 blocks。一个 block 负责整行，必须自己把所有 tiles 都扫完。
- [01:11:53-01:12:38] 然后进入压轴 matmul。老师把它称为深度学习的 bread and butter，并故意在 matmul 后再接一个 ReLU，目的是顺手展示 kernel fusion。
- [01:12:41-01:13:48] 先从 naive matmul 开始：设 $A$ 是 $M \times K$，$B$ 是 $K \times N$，输出 $C$ 是 $M \times N$。若固定一个输出元素 $C[m,n]$，就对每个 $k$ 去 HBM 读取 $A[m,k]$ 与 $B[k,n]$，相乘并累加，最后写回这个元素。这当然正确。
- [01:13:49-01:14:44] 但老师立刻指出问题：这种写法需要数量级为 $MKN$ 的 HBM 读取，而 operations 也是 $MKN$ 量级，所以 arithmetic intensity 只是常数阶，不理想。
- [01:14:44-01:15:10] 他用“算 $C4$ 和 $C5$ 都要重复读取 $A4,A5,A6$”的例子暴露出根因：有大量冗余读。
- [01:15:10-01:15:56] 于是提出理想化方案：把整个 $A$ 和 $B$ 都装进 shared memory，再在本地完成乘法。这样 reads 就从立方级降到二次级，arithmetic intensity 升到 $O(N)$，接近上一讲说的理想状态。
- [01:16:03-01:16:14] 但理想方案立刻遇到现实约束：$A$ 和 $B$ 通常大到放不进 shared memory。
- [01:16:14-01:18:31] 于是引出经典 tiling：全局上看仍像 naive matmul，要扫描整个 $K$ 维；但局部上，每次只把一个 $A$ 的 row tile 与一个 $B$ 的 column tile 装进 shared memory，在 block 内做一次“小 matmul”，把结果积累到输出 tile 的 partial sum 上，扫完整个 $K$ 维后再一次性把输出 tile 写回 HBM。老师指出这会把 arithmetic intensity 提升到 $O(\text{tile size})$，虽然不及整体装入 shared memory 的理想 $O(N)$，但已显著更好。
- [01:18:37-01:18:54] 顺手还能把 ReLU 这类 element-wise 激活放在写回前直接做掉，这就是 kernel fusion。
- [01:19:04-01:19:47] 进入具体实现前，老师补充 stride 概念：张量虽然是多维数组，但内存中是线性化的；row / column 的多维下标需要通过各自 stride 映射到真实地址。例子里向下换一行前进 4 个位置，向右一列前进 1 个位置；若转置，stride 就会翻转。

## 概念、符号与推导

- Tile vs block：
  - GeLU 中切片后每片就是独立 block。
  - row sum 中切片后得到的是 tiles；一个 block 必须循环处理同一行的所有 tiles。
- Accumulator：每个 thread 在跨 tile 循环中保留的局部累计值；最终再做一次 reduction 得到整行和。
- 矩阵乘法维度：$A \in \mathbb{R}^{M \times K}$，$B \in \mathbb{R}^{K \times N}$，$C \in \mathbb{R}^{M \times N}$。
- naive matmul 的逐元素思路：固定 $(m,n)$，沿 $k$ 扫描，累计 $A[m,k] \times B[k,n]$。
- naive matmul 的复杂度口径：
  - 计算量：$O(MKN)$
  - HBM 读：$O(MKN)$
  - 因此 arithmetic intensity 为常数阶 $O(1)$。
- 理想化 shared-memory 方案：
  - 读入量降到 $O(MK + KN)$
  - 写出量约为 $O(MN)$
  - arithmetic intensity 可升到 $O(N)$。
- Tiling 方案：
  - 把输出矩阵 $C$ 切成多个 output tiles，每个 tile 对应一个 thread block。
  - 对固定输出 tile，循环遍历 $K$ 方向的 tile 对；每次把对应的 $A$ 子块和 $B$ 子块读入 shared memory，做局部乘法并累积。
  - arithmetic intensity 提升到 $O(\text{tile size})$。
- Stride 映射：多维下标通过“行索引乘行 stride，再加列索引乘列 stride”映射到线性地址。

## 概念、符号与推导

- matmul kernel 的二维 tile 视角：二维 grid 中的一个程序实例负责输出矩阵 $C$ 的一个 output tile。[代码: lecture_06.py p.24]
- 索引集合：

- 内层循环逻辑：
  - 载入当前 $A$ tile 与 $B$ tile
  - 做局部 `dot`
  - 推进到下一对 tiles
  - 循环直至覆盖完整 $K$ 维。[代码: lecture_06.py p.25]
- Kernel fusion：在 accumulator 还没写回 HBM 前，顺手施加 ReLU 等 element-wise 操作。[代码: lecture_06.py p.22] [代码: lecture_06.py p.25]

1. matmul Triton kernel 中，一个程序实例负责什么？
