### 00:10:05-00:20:00

#### 本段在整讲中的作用
这一段开始真正展开“a lifetime of a token”。老师先说明真实生产流量长什么样，再把一个请求拆成 tokenize、schedule、prefill、decode、continuous batching、KV cache、模型并行等子问题，为后面关于系统优化和研究机会的讨论建立共同术语。

#### 教学展开
- 00:10:05-00:11:18：他先提醒真实 serving workload 既不像训练流量，也不像你凭空想象出来的平均请求。以 coding agent 为例，往往是超长输入、再加不同长度的 thinking/output token；而 summarization、书籍对话、普通聊天又会呈现完全不同的输入输出分布。
- 00:11:21-00:12:33：他强调现在大量应用是 turn-based、agentic workflow。人和 coding agent 会反复来回，agent 本身也会发起 grep、网络搜索、工具调用，再把结果送回模型，所以一次“会话”其实是多轮、带工具反馈的复合流量。
- 00:12:00-00:13:39：不同应用还会有不同的时间尺度和 SLA。语音/交互式 chat 追求很快看到首 token；放任 agent 自主执行的 workflow 则允许更长间隔；有些长期对话甚至会隔周才继续一次。
- 00:13:46-00:14:21：请求一进来，先 tokenize，再进入更复杂的 scheduling：有没有缓存命中、能不能直接复用 activations。
- 00:14:25-00:16:10：然后他把核心 ML 计算分为 prefill 与 decode。prefill 是“很多新 token 进、一个 token/logit 出”，算力密集，接近训练前向；decode 是“每次只生成一个 token，再把它重新过模型”，计算量轻但极度吃 memory bandwidth。
- 00:16:21-00:17:57：接着他讲 continuous batching。系统会同时处理多条不同长短、不同阶段的请求；有的请求很长，有的很短，有的会因为 GPU memory 尤其是 KV cache 满了而被排队。
- 00:18:02-00:19:01：之后引入 KV cache。它让系统在多用户常见前缀、同一会话前缀或大文档后续追问中复用先前算过的 activations，而不是每次从头 prefill。
- 00:19:01-00:20:00：最后回到模型放不下单卡的问题，引入 tensor parallelism 与 mixture-of-experts 的分布方式，并指出这些切分选择会决定瓶颈、GPU 数量和可并发 session 数量。

#### 概念、符号与推导
- `workload shape`：输入 token 数、输出 token 数、会话轮数、轮间停顿时间、延迟目标等共同决定的流量形状。
- `prefill`：对“此前没见过”的整段 prompt 做前向计算，典型是 `10000 tokens in -> 1 token/logit out`，更 compute-bound。
- `decode`：每次新生成一个 token，就把该 token 继续送入模型，逐步生成后续 token，更 memory-bandwidth-bound。
- `continuous batching`：随着时间向下推进，系统动态把不同请求编到同一批次，同时受算力和 KV cache 容量约束。
- `KV cache`：保存前缀相关 activations；老师说可用树等经典数据结构做 prefix sharing 和 lookup。
- `tensor parallelism`：把单个 tensor 切到多张 GPU 上。
- `mixture of experts`：不同 expert 按 token 条件选择性激活，并可分散在不同 GPU 上。
- 本段无公式推导。

### 00:49:52-00:59:50

#### 本段在整讲中的作用
这一段完成 Parcae 的核心理论与实验叙事：先用谱半径解释为什么旧 looped model 会爆炸，再给出对 `A`、`B` 的稳定化重参数化，接着用训练曲线、质量表和 scaling law 展示“循环不仅能稳，还可能更优”。它是全讲第二个研究项目的主干。

#### 教学展开
- 00:49:52-00:50:49：老师接着上一段的动态系统分析，指出 residual 演化被 `A` 矩阵强烈主导，尤其是 `A` 被反复乘幂后的放大效应。
- 00:50:15-00:50:47：他引入 spectral radius，把它近似解释成 norm 一类的量，并用标量例子说明：如果 `A` 像数字 2，而循环次数 `T` 很大，那么激活会被放大成 `2^T` 量级，于是 loss spike 就不难理解。
- 00:50:52-00:51:27：他总结旧工作里 `A`、`B` 的常见设计不是 marginally stable，就是直接 unstable，因此 recurrence 稍微放大就会把系统推到爆炸区间。
- 00:51:11-00:51:51：Parcae 的应对是直接约束 `A`、`B`：把 `A` 参数化成负对角矩阵，使其多次乘幂后自然衰减；对 `B` 只施加简单线性 norm，因为它只作用一次，不会像 `A^T` 那样累积爆炸。
- 00:51:55-00:53:23：实验上，Parcae 在高学习率下仍能稳定训练。老师还解释了“单纯靠 norm 压激活”为什么不够：模型一边试图拉大状态空间以表达更多概念，一边又被 norm 强制压回，二者对冲反而造成 loss spike。
- 00:53:27-00:54:09：因此，稳定化不仅带来平滑训练曲线，也带来更高质量。Parcae 相比旧 loop transformer 和强 transformer baseline 都取得更好 perplexity/端到端质量。
- 00:54:13-00:58:09：接着他把问题推进到 scaling law：当数据量增加时，recurrence 应不应该一起增加？他的实验固定参数或 FLOP 条件后发现，最佳曲线仍然是“向右下”，表示数据变多时，适当增加 recurrence 会更优；若再结合经典参数-数据 scaling law，则可能需要把数据、参数、recurrence 三者一起放大。
- 00:58:36-00:59:50：最后用固定模型大小、固定 FLOP budget 的实验再说明一次：与其只是多喂数据，不如在一定条件下同时提高 recurrence，这会得到更低验证损失。

#### 概念、符号与推导
- `spectral radius`：老师把它口语化解释成类似 norm 的量，用来判断 `A` 反复乘幂时是否会放大状态。
- `A^T` 主导效应：若 `A` 的谱半径大于 1，随着循环次数 `T` 增加，状态会指数放大，导致训练不稳定。
- `marginally stable / unstable`：前人对 `A`、`B` 的设定要么处在边界稳定、稍有扰动就炸，要么本身就是不稳定系统。
- `negative diagonal A`：Parcae 对 `A` 的约束方式，使多次乘幂后趋于衰减而不是爆炸。
- `B` 的线性 norm：因为 `B` 只施加一次，不需要像 `A` 一样严苛，但仍做简单约束以控制初始注入幅度。
- `state norm`：循环状态向量的幅度；Parcae 通过重参数化而不是事后强压 norm 的方式控制它。
- `ISO-param / ISO-FLOP`：比较时固定参数量或固定 FLOPs，再考察不同 recurrence 与数据量的性能曲线。
- 近似推导链条：把复杂非线性藏进 `R` -> 聚焦 `A`、`B` -> 观察 `A^T` 放大主导训练行为 -> 约束 `A`、`B` 以获得稳定系统。

#### 例子与课堂提示
- 00:50:38-00:50:47：把矩阵退化成标量 2，再看 `2^16`，是让学生直观看懂谱半径为何会制造爆炸的课堂技巧。
- 00:52:24-00:53:06：老师用“模型想把概念拉得更开，norm 又强迫压回去”的对抗来解释为什么单纯加 norm 也会出现 gnarly loss spikes。
- 00:55:00-00:55:33：他回顾经典参数-数据 scaling law 的“右下倾斜”形状，帮助听众把 recurrence scaling 放进更熟悉的优化框架里。
- 00:57:59-00:58:07：他直说“如果可以，三者都增大”，提醒学生 scaling law 给的是方向判断，不是脱离资源约束的绝对命令。

#### 本段掌握检查
1. 为什么 `A` 的谱半径会决定 looped model 是否容易爆炸？
答案：因为 `A` 会被多次乘幂，若其放大效应大于 1，状态幅度会随循环次数指数增长。
2. Parcae 如何稳定循环系统？
答案：把 `A` 约束为负对角矩阵、把 `B` 做简单线性 norm，从参数化层面保证系统不爆炸。
3. 为什么“直接在状态上加 norm”不是最好的解决方法？
答案：因为模型会试图扩展状态空间表达能力，而 norm 又强压回去，这种拉扯本身会制造训练不稳定。
4. 本段 scaling law 的结论是什么？
答案：在固定参数或 FLOP 的比较里，随着数据量增加，增加 recurrence 往往也会更优，提示数据、参数、recurrence 可能要协同扩展。

### 00:59:50-01:09:48

#### 教学展开
- 00:59:50-01:00:24：Dan Fu 先做总收束：理解 inference、GPU kernels 和系统全栈，可以带来 routing、kernel、architecture 三个层面的创新。
- 01:00:46-01:01:58：第一个问题问 Parcae 是否必须从头训练。Dan Fu 回答说，他们主要是从 scratch 训练，但有人曾在预训练 Quinn/Qwen [需回听 01:01:14] 模型里直接 loop 两三层，在某些数学榜单上出现质量提升；他觉得这件事“很怪”，但团队也在继续研究。
- 01:02:00-01:03:20：第二个问题问 loop model 对 inference/memory 的好处。他的回答是：更小参数量会释放 GPU memory，允许容纳更多 KV cache、减少多 GPU 通信；如果 recurrent block 足够小，甚至可能塞进更小 memory footprint 的高速芯片或专门写成极快的 Megakernel 循环。
- 01:03:26-01:04:37：接着有人问 Megakernel 的 trade-off。Dan Fu 直言最大的代价就是“工程血汗”：一个强 kernel engineer 花一年也许只能为一种硬件、两三个模型、batch size 1-16 写出可用 Megakernel；batch size 一变，往往就要重来。因此 Together 正在尝试用 compiler 自动化一部分过程。
- 01:04:46-01:06:14：Percy 追问 co-design：既然 decode/prefill 在新硬件上分化，设计模型时应怎样针对服务平台改 architecture。Dan Fu 的答案是先看 memory 限制，再决定模型尺寸和 KV cache 余量；之后再根据目标硬件的数值格式做量化/训练格式选择，例如面向 NVIDIA 的 NVFP4、面向 AMD 的 MXFP4。
- 01:06:17-01:07:37：又有人问 compute-optimal 条件下，为何不直接增大参数而要 loop。Dan Fu 回答比较务实：如果只追求质量，增加 FLOP budget 通常还是有效；但真正的选择取决于模型大小限制、数据是否足够、是否要开源到可在 laptop 上运行、以及后续怎么服务等设计点。
- 01:07:55-01:09:48：最后一个较长问题问不同 use case 会不会对应不同最优 architecture。Dan Fu 认为，agentic loop workflow 尤其在乎让 KV cache 保持 hot；大批量一次性处理则不一定。像 DeepSeek MLA attention 这类显著压缩 KV cache 的设计，更适合重视长会话与多轮 agent 的场景；而纯 batch processing 可能更像 BERT/T5 这类以编码/双向处理为主的范式。

#### 概念、符号与推导
- `from scratch vs looping pretrained layers`：Parcae 当前主体是从头训练，但讲者承认“直接对现成模型做少量 loop”可能也有奇特收益。
- `memory as the first constraint`：做 inference co-design 时，先看目标芯片可容纳多少权重与 KV cache，再谈其他结构选择。
- `NVFP4 / MXFP4`：针对不同硬件生态的低比特数值格式；老师用它们说明 architecture 与部署硬件并非解耦。
- `compute-optimal`：在给定 FLOP budget 下决定参数、数据、recurrence 等如何分配，而不是抽象地问“哪个永远更好”。
- `hot KV cache`：对 agentic workflow 来说，多轮往返请求会反复命中同一会话缓存，因此缓存压缩与驻留极其关键。
- 本段无公式推导。

#### 本段掌握检查
1. 为什么更小参数量的 loop model 可能有 inference 优势？
答案：因为它占用更少 GPU memory，可容纳更多 KV cache、减少跨 GPU 通信，并可能适配更小片上存储的芯片。

### 01:09:48-01:11:36

#### 本段在整讲中的作用
这一段是问答收尾，补上一个非常具体的系统问题：Megakernel 在多 GPU/多机通信场景下还能不能成立。它把整场讲座最后落点重新拉回 inference system 的现实边界，即单机内核融合很强，但跨设备通信延迟仍然会成为新的硬约束。

#### 教学展开
- 01:09:48-01:10:00：老师先补完上一题里对 T5 的例子，说明曾有人选择“先做双向处理，再做生成”的折中范式。
- 01:10:04-01:10:26：最后一个问题聚焦 Megakernel 在“多计算机/多 GPU 通信”中的表现，实质是在问：一旦通信进入环路，融合还剩多少价值。
- 01:10:27-01:10:53：Dan Fu 回答说，他们有过很初步的尝试，理论上可以把 NCCL 通信调用也 fuse 进 Megakernel，但实际收益未必稳定，因为很多时候瓶颈就是 NCCL 本身的调用/通信延迟。
- 01:10:57-01:11:14：他举 DeepSeek 4/4s [需回听 01:10:57] 的 mixture-of-experts inference layer 为例，说对局部计算块做小型 Megakernel，并把部分通信一起融合，是已经开始出现的方向。
- 01:11:08-01:11:25：因此他给出的现实判断不是“整个模型一定做成一个超大 Megakernel”，而是未来更可能出现大量“局部小 Megakernel”，只覆盖计算图中的某些部分；除非你愿意支付极高工程成本，才可能把整模型都做成 Megakernel。
- 01:11:29-01:11:36：全场在感谢和掌声中结束。

#### 概念、符号与推导
- `NCCL`：多 GPU 通信库；这里代表跨 GPU collective communication 的开销来源。
- `fuse communication into Megakernel`：不仅融合计算，还尝试把通信调用与计算调度一起编排。
- `partial/local Megakernel`：只对某个高价值子层或子路径做融合，而非整模型端到端融合。
- `communication latency bound`：即使计算融合成功，系统也可能被跨设备通信延迟卡住。
- 本段无公式推导。

#### 例子与课堂提示
- 01:10:38-01:10:53：老师明确说“有时就是被 NCCL call 自身 latency 卡住”，提醒学生不要把单机 kernel 优化想当然地外推到分布式场景。
- 01:10:57-01:11:14：DeepSeek 的 mixture-of-experts inference layer 例子说明，现实落地更可能先从局部融合而不是整模型巨型融合开始。
- 01:11:13-01:11:25：再次出现“blood, sweat, and tears price”，延续前面对 Megakernel 工程成本的警告。

#### 本段掌握检查
1. Megakernel 在多 GPU 通信场景下还能做什么融合？
答案：可以尝试把 NCCL 等通信调用与计算一起融合调度。
2. 为什么这种融合不一定总有巨大收益？
答案：因为分布式场景下瓶颈可能直接来自通信调用自身的延迟，而不是单机计算空隙。
3. 老师认为更现实的演进方向是什么？
答案：先在高价值局部子层上做小型 Megakernel，而不是一开始就追求整模型完全融合。
