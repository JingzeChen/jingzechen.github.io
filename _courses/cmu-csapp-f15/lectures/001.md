## 老师的教学主线

### 1. 先回答“这是什么课，为什么值得学”（`00:00:00-00:07:29`）

Randy 先说明 15-213、18-213、15-513 是同一课程的不同注册入口，介绍自己与 David R. O'Hallaron，并把 CS:APP3e 定位为由课程发展而来的 required text。随后从学生过去把机器当作“盒子”的经验出发，提出课程要打开这个盒子，从 programmer's perspective 理解 code 为什么正确、失败、快或慢。课程有双重收益：立即改善编程；为更深的 systems 课程建立 foundation。[课件: 01-overview.pptx p.1] [课件: 01-overview.pptx p.3]

### 2. 再用 five realities 逐层打破过度理想化的模型（`00:07:29-00:28:55`）

1. **Ints are not integers; floats are not reals。** 有限表示导致 integer overflow 与 floating-point roundoff；computer arithmetic 有确定性质，却不能照搬全部数学性质。[课件: 01-overview.pptx p.4] [课件: 01-overview.pptx p.5]
2. **You've got to know assembly。** 高级语言模型在 bug、optimization、system software 和 security 场景会失效，程序员必须理解 compiler-generated x86-64 code。[课件: 01-overview.pptx p.6]
3. **Memory matters。** Random-access、unbounded、uniform memory 都是抽象；实际 memory 要管理、性能分层，错误 reference 还可能跨时间和空间破坏无关对象。[课件: 01-overview.pptx p.7] [课件: 01-overview.pptx p.10]
4. **Performance 不只由 asymptotic complexity 决定。** Algorithm 仍重要，但 representation、procedure、loop 与 access pattern 的 constant factors 也可造成数量级差异。[课件: 01-overview.pptx p.11]
5. **Computer 不只执行孤立程序。** I/O、network、concurrent autonomous processes、不可靠介质与 cross-platform compatibility 都属于现实 system。[课件: 01-overview.pptx p.14]

### 3. 把 realities 放回 curriculum 与课程视角（`00:28:55-00:35:38`）

Randy 说明多个 CS/ECE 后续课程依赖 213/513 的共同基础；15-410 曾需要在开头补 machine programming，正是创建本课的动因之一。传统 systems course 多从“怎样 build component”出发，本课先问“程序员为了有效使用 system 必须知道什么”。Programmer-centric 并不降低深度，而是先从使用者看到 feature 的价值，日后也能成为更好的 builder。[课件: 01-overview.pptx p.15] [课件: 01-overview.pptx p.16] [课件: 01-overview.pptx p.17]

## 核心概念与依赖关系

```text
Abstraction 有边界
├─ finite representation
│  ├─ integer overflow
│  └─ floating-point roundoff / evaluation-order sensitivity
├─ high-level program model
│  └─ compiler-generated assembly -> machine execution -> debug/performance/security
├─ flat random-access memory model
│  ├─ layout + unchecked reference -> corruption/action at a distance
│  └─ hierarchy + access pattern -> cache locality/performance
└─ isolated-program model
   └─ ECF/process -> I/O/sockets -> networking/concurrency
```

课程能力按如下顺序依赖：

`C/bit representation` -> `x86-64 execution` -> `memory layout/cache` -> `ECF/process` -> `virtual memory/allocation` -> `I/O/networking/concurrency`

课程活动与能力形成的依赖：

`CS:APP + lecture` -> `recitation/tool practice` -> `individual lab implementation/measurement` -> `Autolab feedback` -> `exam/mastery check`

## 易错点与政策陷阱

### 概念易错点

- 把 mathematical integer/reals 与 `int`/floating-point value 等同。
- 看到 overflow 就认为 computer arithmetic “随机”，忽视仍保留的 properties。
- 为了代数化简随意重排 floating-point expression，忽略 intermediate rounding。
- 认为 out-of-bounds 必然立刻 segmentation fault；silent corruption 同样可能发生。
- 把 Big-O 或 operation count 当作完整 performance predictor。
- 把 assembly 课理解成“与 compiler 竞争手写代码”；本课重点是读 compiler output。
- 把 Virtual Memory 简化为 DRAM 或“只是扩大容量”，忽略 abstraction、translation、performance 与 allocation。
- 把 exception 只理解为 error；ECF 横跨 interrupt、process、signal 与 nonlocal jump。

### 行政与学习陷阱

- “没有传文件”不代表没有 share code；观看、重打、逐行描述/coaching 都可能违规。[课件: 01-overview.pptx p.19]
- Public GitHub/搜索结果可见不等于课程允许使用；搜索 lab solution 本身被明确禁止。
- 可以交流 tool usage 和 high-level design，但不能替别人形成具体 implementation。
- Course web page 和 staff mailing list 是正式渠道；该学期不用 Blackboard/Piazza。[课件: 01-overview.pptx p.23]
- Labs 一人完成、Autolab 提交；self-scheduled exam 仍受 slot capacity 限制。[课件: 01-overview.pptx p.25]
- Grade appeal 需在 grading 完成后 7 天内书面提出，不是发 email 即可。[课件: 01-overview.pptx p.25]
- Grace days 在 late handin 时自动消耗；应为后期较重 labs 保留。[课件: 01-overview.pptx p.27]
- Programming lab 工时难以上界；start early 是为给 debugging/help 留时间，不是泛泛口号。
- Lecture attendance voluntary，但到场后 electronic communication forbidden，且禁止个人录制。[课件: 01-overview.pptx p.28]

## 全讲快速自测

1. **问：课程主题为何不是“abstraction is bad”？**  
   **答：** Abstraction 用于管理复杂度；课程要求在 bug、performance、安全或 OS interaction 暴露边界时能下探实现。

2. **问：Five realities 的共同结构是什么？**  
   **答：** 都从高层直觉出发，给出实际机器反例，再指出程序员需要理解的 representation/execution/system mechanism。

3. **问：为什么相同 Big-O 的 matrix copy 可以相差近 20 倍？**  
   **答：** Loop nesting 改变二维数组 access pattern，进而改变 cache locality；Big-O 和 op count 未包含这一系统因素。

4. **问：Programmer-centric 对未来 system builder 有何价值？**  
   **答：** 先从使用者角度理解 feature 的行为与价值，日后实现时更清楚应保持哪些性质。

5. **问：Labs、academic integrity 与 start early 为什么是一条因果链？**  
   **答：** Labs 的独立 problem-solving 过程是主要学习载体；提前开始才有时间在卡住时通过官方渠道获得不替代实现的帮助。

## 本段在整讲中的作用

这是整门课和本讲的入口。Randy Bryant 先说明三种课号、授课教师、教材与课程的关系，再回答“为什么程序员需要学习底层系统”这一核心问题。随后他把课程收益分成“立即提升编程能力”和“为后续 systems 课程奠基”两类，并用 five great realities 组织后续内容。本段最后开始 Reality #1，以“平方是否必定非负”挑战学生从数学整数直接类推机器 `int` 的直觉。

## 学习目标

- 准确说出 15-213、18-213、15-513 的对象以及本课程的授课视角。
- 解释“Abstraction is good, but don't forget reality”为什么是课程主题。
- 区分本课程的两类收益：当前编程实践收益与后续课程的基础作用。
- 说明教材为什么不是可选参考书，而是课程内容的一部分。
- 识别数学整数与有限位宽机器整数之间可能存在的差异。

## 前置知识与依赖

- 本讲没有给出正式选课先修课清单，不能据此推断官方 prerequisite。
- 理解本段只需有基本编程经验，并知道高级语言通常通过 abstraction 隐藏机器细节。

# 第 2 节：有限表示、machine-level programming 与 memory reality

> 时间范围：`00:09:58-00:19:50`  
> 内容属性：课程内容。依次完成 Reality #1，讲解 Reality #2，并引入 Reality #3。

## 本段在整讲中的作用

上一节提出 `50000 * 50000` 是否仍满足“平方非负”。本段先用 32-bit 表示解释反常结果，再比较 integer arithmetic 与 floating-point arithmetic 各自保留和失去的数学性质。Randy 随后把“有限表示会让高层直觉失效”推广到 program representation 和 memory system：程序员需要能读 compiler-generated assembly，也需要理解分层内存及错误的 memory reference。结尾建立一个 `struct` 越界写例子，具体后果留到下一节演示。

## 学习目标

- 解释为什么有限位宽会使机器 `int` 的运算结果不同于数学整数。
- 区分 integer overflow 与 floating-point roundoff，并判断课堂给出的结合律例子。
- 说明 assembly language、object code 和 C source 之间的关系。
- 解释本课程为何重在阅读 compiler-generated assembly，而非手写大型 assembly 程序。
- 说出 memory hierarchy 对 performance 和 correctness 的两类影响。

## 前置知识与依赖

- 依赖第 1 节的区分：数学 integer/reals 与机器 `int`/floating-point representation 不是同一对象。
- 需要理解 commutativity（交换律）和 associativity（结合律）的含义。
- 只需知道 C 的 `struct`、array 和 `double` 基本语法；具体 layout 在下一节展开。
- 本段不要求预先掌握 x86-64 指令，课程将从 compiler output 开始建立这项能力。

## 核心教学路径

1. 观察 `50000 * 50000` 的负结果，并追溯到 32-bit bit pattern。
2. 用四数相乘说明：overflow 后结果虽不等于数学乘积，某些代数性质仍保留。
3. 用 `1e20`、`-1e20`、`3.14` 说明 floating-point addition 不满足结合律。
4. 将两类异常统一归因于 finite representation。
5. 由“高层数值模型失效”转向“高层程序模型也会失效”，引出 assembly。

## 教学展开

### 1. `50000 * 50000`：负值不是随机错误（`00:09:58-00:10:49`）

演示延续上一节。`40000 * 40000` 给出预期结果，而把操作数改为 `50000` 后，debugger 显示一个负数。Randy 的解释不是“机器算错了”，而是：当前计算把数表示为 **32-bit values**；乘法产生的 bit pattern 在该有符号解释下恰好代表一个负数。[课件: 01-overview.pptx p.4]

推理链是：

1. 数学乘积为 `2500000000`。
2. 机器表示空间有限。
3. 运算保留下来的有限 bit pattern 被按 signed `int` 解释。
4. 因而机器结果可以为负，数学命题“平方非负”不能直接用于该 `int` 运算。

本讲此处只给直观说明，尚未推导 two's-complement 编码细节。

### 2. Overflow 不等于“完全没有规律”（`00:10:57-00:12:26`）

Randy 再计算 `300 * 400 * 500 * 600`。数学乘积超出表示范围，演示结果虽然仍为正，却显然不是正确的数学乘积。随后他把 `300` 从乘积开头移到末尾，改变求值顺序；不同顺序得到相同的异常结果。

由此强调两层判断必须分开：

- **数值是否等于数学整数运算的结果？** Overflow 后不一定。
- **某些代数结构是否仍保留？** 课堂观察到机器 integer arithmetic 仍具有 commutativity 和 associativity；课件还把 distributivity 一并列为 integer operations 的 “ring” properties。[课件: 01-overview.pptx p.5]

因此 computer arithmetic 不是随机数生成器，而是受确定规则约束；只是不能假设所有熟悉的数学性质都成立。

### 3. Floating-point addition 的结合律反例（`00:13:02-00:14:09`）

Randy 接着问 addition 是否满足 associativity。对课堂讨论的 integer arithmetic，答案仍为是；对 floating point，答案是否定的。原因是 floating-point 可覆盖极宽数量级，但 precision 有限，小量与巨量相加时，小量可能因 roundoff 被丢弃。

课件和口述给出的同一组三个数是 `1e20`、`-1e20` 和 `3.14`：[课件: 01-overview.pptx p.4]

$$
(10^{20} + (-10^{20})) + 3.14 = 0 + 3.14 = 3.14
$$

换一个结合顺序时，`3.14` 相对 `-10^20` 太小，在中间 floating-point 结果中消失：

$$
10^{20} + ((-10^{20}) + 3.14) \approx 10^{20} + (-10^{20}) = 0
$$

同一批操作数因中间 rounding 不同而得到不同结果，所以 floating-point addition 不满足通常意义上的结合律。

### 4. 统一原因：无限对象的有限表示（`00:14:09-00:16:56`）

Randy 把两个现象归到同一根因：计算机用有限表示近似或编码范围潜在无限的数学对象，因此必须接受折衷。

- Integer 常见问题是 **overflow**：结果超出表示空间。
- Floating point 也可能 overflow，但更常见问题是 **roundoff**：低有效位在有限 precision 下被舍弃。

数羊漫画展示 16-bit signed value 从 `32767` 再加一后变成 `-32768` 的环绕直觉；课程后面会解释具体原因。[课件: 01-overview.pptx p.4]

为什么这些 corner cases 值得两周课程时间？Randy 给出风险分层：普通程序也许大多数时候碰不到边界，但 rocket control 中正推力变成负值会影响安全；攻击者也可能利用程序“输入必为正”的错误假设制造 security vulnerability；严肃 scientific computation、桥梁或核电站设计则必须理解 floating-point 特性。结论是：越重视 correctness 或 security，越不能忽略表示边界。[课件: 01-overview.pptx p.5]

### 5. Reality #2：必须能理解 assembly（`00:16:58-00:18:30`）

第二条 reality 从 data representation 转到 program representation。**Machine-level programming** 指理解处理器实际执行的 instructions：

- **Assembly language** 是 machine instructions 的文本表示。
- **Object code / machine code** 是这些 instructions 的 bit-level binary encoding。
- C compiler 把 C source 转换为 machine code；课程要追踪这一转换并理解执行过程。

Randy 特别区分两种学习法：传统课程可能要求学生手写 assembly program；213 更关注读取、分析由 C compiler 生成的 assembly。理由是 compiler 通常比人更擅长且更耐心地生成代码，而程序员仍需借 assembly 理解 bug 出现时的真实行为、compiler 做了或没做的 optimization、性能瓶颈、system software 和 security。[课件: 01-overview.pptx p.6]

本学期采用 **x86-64**，即 Intel 64-bit instruction set；相较旧版课程从 32-bit 内容切换为全程 64-bit。

### 6. Reality #3：memory hierarchy 对程序员可见（`00:18:30-00:19:23`）

现代机器用复杂的 layered memory system 同时追求高 performance 与大 capacity。这个实现细节不会被 “random access memory” 抽象完全隐藏：

- 相同功能的程序可能因 access pattern 不同而有巨大性能差异。
- C program 中的 invalid memory reference 可能破坏数据或导致 crash。

因此课程既要讲 memory hierarchy 如何影响速度，也要讲 memory referencing error 如何表现和预防。课件进一步概括：memory 并非无限、需要 allocation/management，访问性能并不 uniform，cache 与 virtual memory 都会让底层现实暴露出来。[课件: 01-overview.pptx p.7]

### 7. 为越界写实验建立对象（`00:19:23-00:19:50`）

Randy 定义一个含两元素 integer array `a` 和一个 `double d` 的结构体，并让 `fun(i)` 写 `a[i]`：

```c
typedef struct {
    int a[2];
    double d;
} struct_t;

double fun(int i) {
    volatile struct_t s;
    s.d = 3.14;
    s.a[i] = 1073741824; /* Possibly out of bounds */
    return s.d;
}
```

### 1. 先观察：合法写、静默破坏与 crash（`00:19:50-00:21:06`）

`a` 只有两个元素，所以合法 index 是 `0`、`1`。课件列出 system-specific 实验结果：[课件: 01-overview.pptx p.8]

| 调用 | 返回值/现象 | 初步判断 |
| --- | --- | --- |
| `fun(0)` | `3.14` | 写入 `a[0]`，不触及 `d` |
| `fun(1)` | `3.14` | 写入 `a[1]`，不触及 `d` |
| `fun(2)` | `3.1399998664856` | 越界写改变 `d` 的部分 bytes |
| `fun(3)` | `2.00000061035156` | 越界写改变 `d` 的另一部分 bytes |

关键观察是：越界并不保证立刻 crash。`fun(2)`、`fun(3)` 继续执行，却让看似无关的 `d` 改值；`fun(4)` 甚至表面正常；到 `fun(6)` 才崩溃。因此“程序没崩”不能证明 reference 合法。

### 2. 再解释：连续 byte layout 让越界写穿过字段边界（`00:21:11-00:22:48`）

C/C++ 不自动对本例的 array access 做 bounds checking。口述采用如下布局：两个 `int` 各占 4 bytes，随后的 `double d` 占 8 bytes。[课件: 01-overview.pptx p.9]

```text
较低地址
+---------+  a[0], 4 bytes
+---------+  a[1], 4 bytes
+---------+  d 的前 4 bytes
+---------+  d 的后 4 bytes
+---------+  struct 之外的状态
较高地址
```

于是：

- `a[0]`、`a[1]` 命中 array 自身。
- `a[2]`、`a[3]` 按地址计算继续向后，实际覆盖 `d` 的编码，因此返回异常 floating-point value。
- 更大的 index 写出整个 `struct`。Randy 对 `i = 6` 的具体破坏对象只给出“很可能是程序管理 allocation 所用状态”的推测，而非已验证结论；可以确认的只有该写导致 crash。

课件明确标注 **Result is system specific**：字段布局、compiler 和周边内存状态变化时，具体数字或 crash 点都可能不同。[课件: 01-overview.pptx p.8]

### 3. 一般化：memory error 的 action at a distance（`00:22:48-00:24:47`）

这个例子揭示 C programming 难调试的一类根因：[课件: 01-overview.pptx p.10]

1. 程序容易发出 invalid access，例如 out-of-bounds array reference、invalid pointer、错误使用 `malloc/free`。
2. 被破坏的对象可能在逻辑上与当前操作毫无关系，即**空间上的距离**。
3. Corrupted data 可能在数小时、数天甚至数周后才被读取，即**时间上的距离**。
4. 最终 symptom 出现的位置不是 bug 产生的位置，导致严重 debugging nightmare。

应对方法按抽象层次分为：改用带更强 memory safety 的语言；在 C/C++ 中主动进行 bounds checking；理解 data structure 的 machine-level layout；使用检测 memory reference error 的工具。课件举 Valgrind 为工具例子，但 Randy 在此口述只泛称工具。[课件: 01-overview.pptx p.10]

这也是 security 问题：越界写不只造成 accidental bug，也可能成为 vulnerability。

### 4. Reality #4：Asymptotic complexity 不足以预测性能（`00:24:47-00:25:23`）

Randy 先承认 algorithm 和 data structure 的重要性，再指出系统级 optimization 还有另一层：程序员必须理解 code 如何 compile/execute、如何 measure bottleneck，以及 representation、procedure、loop 和 memory system 如何影响 constant factors。即便 algorithm 和 operation count 相同，code organization 仍可能带来数量级差异。[课件: 01-overview.pptx p.11]

结论不是用 low-level optimization 取代 algorithmic analysis，而是需要多层优化，并尽量不破坏 modularity 与 generality。

### 5. Matrix copy：只交换 loop nesting，性能接近相差 20 倍（`00:25:23-00:28:14`）

两个函数都把 `2048 x 2048` 的 `src` 复制到 `dst`，功能、元素数和主要 assignment count 相同；唯一差异是 loop nesting：[课件: 01-overview.pptx p.12]

```c
/* copyji: 固定 j，沿 i 变化 */
for (j = 0; j < 2048; j++)
    for (i = 0; i < 2048; i++)
        dst[i][j] = src[i][j];

/* copyij: 固定 i，沿 j 变化 */
for (i = 0; i < 2048; i++)
    for (j = 0; j < 2048; j++)
        dst[i][j] = src[i][j];
```

在 C 的二维数组访问中，`copyij` 按行连续推进，`copyji` 按列跨行推进。Randy 报告特定机器上两者接近 **20x** 的 performance difference。书封图展示不同 memory access pattern 对 copying throughput（MB/s）的影响：row-by-row 所在位置明显优于 column-wise 所在位置。[课件: 01-overview.pptx p.13]

本段只给结论性原因：hierarchical memory 与 cache memories 偏好某些 access pattern。Cache line、miss rate 等机制将在课程后面展开，不能从本段进一步杜撰。

## 概念、符号与推导

### Address calculation 的课堂直觉

对本例 `int a[2]`，口述采用每个 `int` 4 bytes。若把 `a[0]` 起始地址记为 $A$，则写入位置按例子可理解为：

$$\operatorname{addr}(a[i]) = A + 4i$$

所以 $i=2,3$ 的地址分别落在紧随其后的 8-byte `double d` 两个 4-byte 区域。这里是对课堂布局图的直接表达，不代表所有 C implementation 都必须采用相同 layout。

### Performance 比较的控制变量

- 相同：输入规模、复制元素数、功能、渐进复杂度。
- 不同：inner loop 改变了 address traversal pattern。
- 观察：特定机器接近 20x 差异。
- 结论：operation count 和 asymptotic complexity 不能单独预测真实性能。

### 1. 作为 prerequisite 的价值：让后续课从更高起点开始（`00:29:42-00:30:24`）

### 2. Builder-centric 与 programmer-centric（`00:30:24-00:31:56`）

Randy 先肯定传统 systems courses 的 **builder-centric** 目标：[课件: 01-overview.pptx p.15]

## 教学展开

### 1. 禁止行为：共享的不只是文件（`00:39:37-00:41:15`）

David 延续上一节，把 **sharing code** 展开为多种等价形式：复制、重新键入、观看他人屏幕上的代码、把文件给别人、逐行口述代码，以及逐行 coaching。规则关注的是一个人是否获得了另一个人的 implementation，而不只关注文件是否被直接复制。[课件: 01-overview.pptx p.19]

他随后把 Web solution 单独强调：搜索课程 lab 的现成 solution，本身就越过允许边界；找到后使用当然违规，即便事后改变量名、格式或局部代码也不改变来源。课程材料在世界多地使用，过去学生可能出于展示作品等原因把答案放到 public GitHub，因此“网上搜得到”不表示“课程允许用”。从以前学期学生处复制也同样禁止。[课件: 01-overview.pptx p.19]

这里的结论是：判断标准不能简化成“最后提交的文本是否一模一样”，而应看 implementation 是否由提交者独立产生。

### 2. 允许行为：帮助使用工具，讨论高层设计（`00:41:15-00:42:23`）

David 随即给出可合作的正面边界：[课件: 01-overview.pptx p.19]

- 可以解释 GDB、text editor、登录 shark machines 等 systems/tools 的使用方法。
- 可以讨论 high-level design issue。
- 课堂用 malloc lab 举例：讨论采用 explicit list 还是 segregated list 属于高层设计；逐行告诉对方怎样实现则越界。
- 学生问到重修情形时，David 回答可以使用自己以前学期的 work（`00:41:55-00:42:02`）。

他的压缩表达是 **“High-level, okay; low-level, not okay.”** 但这不是说所有“高层”标签下的交流必然安全；实际判断仍以 syllabus 和“是否替别人写出 implementation”为准。

### 3. 规则背后的学习理由（`00:42:20-00:42:52`）

David 承认现实软件开发常从 Google、Stack Overflow 等处查找和复用代码，但明确说这不是本课程 labs 的做法。本课要求学生自己解决问题，因为课程希望训练的正是拆解问题、调试和形成系统直觉的过程；只得到最终代码而跳过过程，就不会获得对应能力。

David 说明该课程对 cheating 采用单一且严厉的 sanction：被发现后从课程中移除并记 failing grade，且没有例外；即使先 drop，课程方也会恢复注册后给出不及格结果。[课件: 01-overview.pptx p.20]

## 概念、规则与推理

本段无公式推导。

### Academic integrity 的判断框架

Exams 合计 50%，其中 midterm 20%、final 30%；labs 合计 50%，按 effort 加权。Final grade 采用 straight scale，David 口述为 90/80/70 分界。[课件: 01-overview.pptx p.29]

### 4. Data Lab：用受限 C 操作理解 bit representation（`01:01:53-01:03:00`）

学期前三个 labs 覆盖 programs 与 data 的 machine representation。第一个 **Data Lab** 让学生用 C 完成 bit-manipulation puzzles；课件把主题概括为 bit operations、arithmetic，以及 C control/data structure 的 representation。[课件: 01-overview.pptx p.30]

David 用 absolute value puzzle 说明约束：只能使用指定的 bit-level C operators，代码必须 straight-line，不能用 conditional 或 loop。平常会写成“若 `x < 0` 返回 `-x`，否则返回 `x`”，但限制拿走了 `if`，迫使学生直接利用 representation。目的不是寻找最漂亮的 production implementation，而是在约束下暴露数据的位级结构。

### 5. Bomb Lab：从 binary 反推 compiler-generated code（`01:03:00-01:06:04`）

第二个 **Bomb Lab** 用于学习读取和理解 assembly。每个学生得到一个略有不同、包含六个 phases 的 C program binary；课程不给 source code。每个 phase 等待一段输入：输入正确就 defuse 并进入下一 phase，错误则打印 `BOOM` 并记录 explosion。[课件: 01-overview.pptx p.30]

学生必须：

1. 用 GDB 找到各 phase 的 machine code。
2. 设置 breakpoint、single-step compiler-generated assembly。
3. Reverse engineer 每个 phase 期待的输入。
4. 识别 `explode_bomb` 等关键控制点，避免盲目试错。

Defuse 或 explode 的事件会发送到 Autolab，server 用保存的对应 bomb 验证输入；口述称每次 explosion 扣半分。因此真正的学习策略不是猜答案，而是用 debugger 控制执行、检查 state。David 明确希望学生学会在关键函数前设 breakpoint；Bomb Lab 同时训练 assembly reading 和 GDB，且必须使用后者才能有效完成（`01:04:50-01:06:00`）。

### 6. Attack Lab：从 64-bit machine model 理解 exploit（`01:06:04-01:07:00`）

第三个 **Attack Lab** 是该学期针对 64-bit architecture 新开发的 lab，反映课程从 32-bit 全面转向 x86-64。课件把目标概括为 code-injection attacks 的基础。[课件: 01-overview.pptx p.30]

David 口述还提到学生会构造 exploit，并接触现代的 **return-oriented programming (ROP)**。这把前面“理解 assembly 与 memory bug”的 defensive motivation 扩展到 adversarial setting：要理解攻击如何利用 machine-level control flow，才能理解防护为何需要存在。关于现代 stack 防护的那句口述 ASR 严重断裂，不能据此补写具体机制，见待核对项。

### 7. Cache Lab：构造 simulator，再优化 locality（`01:07:00-01:07:37`）

进入 memory hierarchy 后，第四个 **Cache Lab** 分两步：[课件: 01-overview.pptx p.31]

1. 用 C 构建 cache simulator，理解 cache hardware 的行为模型。
2. 优化一个小型 matrix-transpose function，使它在该 simulator 上产生尽可能少的 misses。

这个顺序把第 3 节的 matrix-copy 现象变成可操作 reasoning：先有可测的 cache model，再根据 memory hierarchy 调整 access pattern，通过 miss count 判断是否更好，而不是凭直觉宣称“优化了”。

### 8. Exceptional Control Flow：连接 hardware 与 system software（`01:07:37-01:09:12`）

课程从 hardware 转向 OS interaction 时，使用 **Exceptional Control Flow (ECF)** 作为统一概念。David 认为它让过渡保持 intellectual consistency：控制流不只由当前程序的普通 instruction sequence 决定，系统各层都有事件迫使执行发生非局部变化。[课件: 01-overview.pptx p.32]

他按从低到高的顺序列出：

1. Hardware interrupts 和 exceptions。
2. Hardware 与 OS 共同实现的 process/context switch；由此学习 process 以及如何请求 kernel 创建、管理 process。
3. Linux kernel 提供的软件形式：Unix signal。
4. Application/C 层的 nonlocal jump：`setjmp` / `longjmp`。

课件也按 hardware exceptions、process/process control、Unix signals、nonlocal jumps 汇总这一主题。[课件: 01-overview.pptx p.32]

### 9. Shell Lab：把 ECF 落到真实命令行程序（`01:09:12-01:09:32`）

第五个 **Shell Lab (tshlab)** 要求学生编写自己的 Linux/Unix shell，即登录 Linux 后交互的 command-line program；它是课程第一次系统性接触 concurrency 的 lab。[课件: 01-overview.pptx p.32]

本段在“你将自己写一个”处结束。David 对完成真实 shell 的兴奋感，以及后续 Virtual Memory，放到第 8 节。

1. **Abstraction support 很少。** Allocator 自己正在管理供其他 data structure 使用的 raw memory，按该 lab 的实现约束，学生主要依靠 pointers 和 casts 操作内存，不能像普通应用那样依赖现成分配能力来构造辅助结构。

所以困难不等于代码行数多；难点在于 invariant、low-level representation 与多目标设计空间。本段只给课程预告，没有定义 free-list policy 或评分公式。
