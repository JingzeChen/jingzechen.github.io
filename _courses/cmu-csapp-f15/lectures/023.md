3. **先列三种结构，再逐个实现。** Process：kernel 自动调度、private address spaces；Event：programmer 手工交错、shared address space；Thread：kernel 自动调度、shared address space。[00:15:10-00:17:26] [课件: 23-concprog.pptx p.7]

7. **用 hello 程序后再写 thread server。** `create/join` 先说明生命周期，随后每连接 `Malloc` 参数、peer detach、free/close 建立正确 ownership。[00:49:53-00:59:52]
8. **用错误 scheduling trace 揭示共享风险。** 直接传 `&connfd` 暗含“peer 必先运行”的非法假设；main 先接受第二连接即可覆盖 slot，产生难复现 race。[00:59:52-01:09:30]

- **并发难度的根源不是语法，而是交错空间。** 代码一次运行看起来正确，不代表其他合法 scheduling 也正确。[00:01:03-00:03:35]
- **内核排队与应用并发不是同一件事。** backlog/buffer 让 `connect`、`rio_writen` 返回，但唯一 iterative server flow 仍不能为 client 2 产生 response。[00:09:58-00:13:29]
- **process 隔离把 sharing 变成显式成本。** 普通 globals 不共享，IPC 较麻烦；descriptor table 是副本，但可共同引用同一 kernel open-file/socket state。[00:24:59-00:29:26]
- **event readiness 不提供 message framing。** `select`/`epoll` 告诉程序有输入，不告诉程序已有完整 HTTP request，因而需要 per-connection parser/buffer state。[00:29:56-00:38:45]
- **thread 的共享与独立是两个层次。** 每条 thread 独立保存执行 context 和 stack region，却共享整个 virtual address space，所以 pointer 能越过 stack 的“正常归属”。[00:41:27-00:48:30]
- **Pthreads 参数传递本身就是 ownership contract。** 每连接 heap slot 只能在 peer 复制 descriptor 后释放；socket 则在 `echo` 完成后独立关闭。[00:56:17-00:59:30]
- **`&connfd` race 是本讲的综合例。** 它同时依赖 shared address space、pointer aliasing、stack lifetime、uncontrolled scheduling 与 reused loop state。[01:04:01-01:08:16]

## 关键课堂代码与执行轨迹

### Process-based echo server

```text
listening parent: Accept -> Fork -> Close(parent connfd) -> next Accept
child:            Close(listenfd) -> echo(connfd) -> Close(connfd) -> exit
SIGCHLD handler:  while (waitpid(-1, 0, WNOHANG) > 0) ;
```

fork 后 `refcnt(connfd) = 2`；parent 与 child 各 close 一次后才归零。[00:20:40-00:27:12] [课件: 23-concprog.pptx p.9] [课件: 23-concprog.pptx p.10] [课件: 23-concprog.pptx p.13]

### I/O-multiplexed event loop

```text
active descriptors = {listenfd, connfd_1, ..., connfd_n}
ready = select/epoll(active descriptors)

if listenfd ready: accept and add connfd
for each ready connfd: read only safe work unit, update saved state, respond
```

鲁棒 HTTP handler 不能阻塞等待完整 request 或完整 line；应读取 available bytes 并保存 partial line。[00:29:56-00:38:45] [课件: 23-concprog.pptx p.15] [课件: 23-concprog.pptx p.16]

### Pthreads hello and server

```text
hello: main create -> main/peer concurrent -> main join waits
       peer printf -> return NULL -> join returns -> main exit

server main: Malloc(int) -> Accept into *connfdp -> create(peer, connfdp)
peer:        copy *connfdp -> detach self -> Free(connfdp)
             -> echo(connfd) -> Close(connfd) -> return NULL
```

[00:54:28-00:59:30] [课件: 23-concprog.pptx p.28] [课件: 23-concprog.pptx p.29] [课件: 23-concprog.pptx p.30]

### Wrong shared-stack trace

```text
main accepts client 1: connfd = fd1
main creates peer 1 with &connfd
kernel keeps main running
main accepts client 2: connfd = fd2 (same stack slot overwritten)
peer 1 dereferences &connfd and gets fd2
peer 2 can also get fd2
```

错误不在某一次“坏运气”，而在程序依赖了 kernel 从未承诺的执行顺序。[01:05:59-01:08:16] [课件: 23-concprog.pptx p.32]

## 三种方案对照

| 维度 | Process-based | Event-based | Thread-based |
| --- | --- | --- | --- |
| Flow 交错者 | Kernel | Programmer/event loop | Kernel |
| Address space | 每 process 私有 | 一个共享 address space | 同一 process address space |
| 共享 | 难，需 IPC；较少 unintended sharing | 直接共享显式状态 | 很容易，可能过度共享 |
| 控制开销 | 高 | 很低 | 中等，低于 process |
| 调度控制 | 少 | 高，可选 descriptor 次序 | 少 |
| 多核 | 可 | 本讲单 flow 版本不可 | 可 |
| 主要风险 | process control 与 IPC 成本 | low-level partial-state machine | 稀有 race、unintended sharing、难调试 |

[00:15:10-00:17:26] [01:09:48.860-01:11:00] [课件: 23-concprog.pptx p.7] [课件: 23-concprog.pptx p.34]

## 易错点与待核对项

- 不要把 `connect` 返回等同于 server application 已 `accept`，也不要把 `rio_writen` 返回等同于 server 已读取；课堂中的 client 2 真正阻塞在等 response 的 `rio_readlineb`。[00:09:58-00:11:26]
- 不要只让 child close `connfd`；fork 后 parent 的 descriptor 副本也维持底层 socket 引用。[00:25:39-00:27:12]
- 不要把 descriptor table 副本与 open file table 共享混为一层；process globals 不共享也不表示所有 kernel state 都完全复制。[00:24:59-00:27:55]
- 不要把 readability 当作完整 message；event-based HTTP parser 必须处理 partial request line。[00:35:48-00:38:45]
- 不要把“每 thread 一个 stack”理解成 memory protection；跨 thread pointer 可直接访问其他 stack region。[00:47:49-00:48:30]
- 不要把 detached 理解为不调度；它只改变 join/reap 语义。状态名字幕有 attached/unattached 误识别，以课件 p.32 为准。[课件: 23-concprog.pptx p.32]
- 不要把 main local `connfd` 地址传给所有 peers；它们会共享并竞争同一 stack slot。[01:04:01-01:08:16]
- 具体字幕疑点包括 `printf` 内部锁对象、A/B 公平性指代、IPv4 “4 bytes”、parent/child close 口误、`epoll`/`nginx` 识别、20K/10K control cycles、`void **`、joinable/detached 和最终 20ms artifact boundary；逐节均有 `[需回听]`。

本段先把此前零散出现的进程、异常/信号处理器重新解释为“并发流”，说明应用程序一旦让多个流访问共享资源，就必须面对所有可能的执行交错。老师依次用 Shell Lab、`printf` 信号处理器、十字路口和调度例子建立 race、deadlock、starvation 与 fairness 的问题框架；随后选择服务器作为本周主线，因为迭代式服务器一次只服务一个客户端，天然暴露“一个客户端拖住所有人”的结构缺陷。本段末尾只提出第二客户端究竟阻塞在哪里，答案延续到下一段。[00:00:00-00:09:58] [课件: 23-concprog.pptx p.1] [课件: 23-concprog.pptx p.2] [课件: 23-concprog.pptx p.3] [课件: 23-concprog.pptx p.4]

## 教学展开

1. **从学过的并发形式回接新主题。** 本周要研究如何把 concurrency 放进应用程序。此前进程让多个独立应用运行，信号处理器则是与主程序并发的另一条 flow；因此新内容不是突然出现的新现象，而是把已见过的应用级并发更系统地研究。[00:00:09-00:00:52]

2. **先解释人为什么难以推理并发。** 人脑倾向于按“先做一件事、再做下一件事”的顺序思考；两个流同时存在时，要判断程序是否正确，就要考虑它们所有可能的 interleaving。流数增加时，交错数量呈指数式增长，所以“时间看起来怎样流逝”并不能可靠地代表唯一执行顺序。[00:01:03-00:01:54] [课件: 23-concprog.pptx p.2]

3. **用 Shell Lab 把抽象困难落到共享状态。** shell 主程序与信号处理器是两条并发流，共同访问 jobs list。程序必须阻止某种交错在数据结构处于不一致状态时读取或修改它；这说明即便信号处理器工作不多，共享资源也足以让正确性推理变难。[00:01:54-00:02:39]

4. **把第一个经典问题定义为 race。** race 的结果依赖系统中别处任意的调度决定。Shell Lab 中，child 可能因内核调度先运行并结束，而 parent 尚未来得及把它加入 jobs list；航空订票中，两人同时争最后一个座位，谁成功也取决于系统内部执行次序。[00:02:39-00:04:00] [课件: 23-concprog.pptx p.3]

5. **再定义 deadlock，并给出严格等待环。** deadlock 是多个流等待一个永远不会发生的事件。若主程序的 `printf` 已取得内部资源锁，此时被信号打断，而 handler 又调用 `printf`，handler 会等主程序释放锁；主程序却必须等 handler 返回后才能继续并释放锁，于是双方互相等待，无法前进。[00:04:00-00:05:24] [课件: 23-concprog.pptx p.3]

6. **用四向停车路口强化“条件永不成立”。** 若四辆车严格遵守“先到者先走”，又恰好同时到达，则没有任何一辆是先到者；所有司机都等一个不会出现的“我先到”条件。这是现实类比，不是另一个计算机锁实现。[00:05:27-00:06:02]

7. **由长期不前进转到 starvation 与 fairness。** 若内核总调度 process A 而不给 process B 运行机会，B 就因调度而 starvation。公平策略应让系统中的每个实体得到合理的处理器份额；课件还把 livelock、starvation、fairness 归为外部事件或调度决定阻止子任务前进的一组问题。[00:06:02-00:06:52] [课件: 23-concprog.pptx p.3]

8. **限定课程覆盖范围。** 并发问题已研究数十年，交错爆炸使它成为深而难的主题。本课程不会覆盖全部理论，只选取足以让学生把并发加入程序的一部分，并在接下来几讲继续展开。[00:06:52-00:07:20] [课件: 23-concprog.pptx p.3]

9. **选择服务器作为驱动案例。** 老师给出的理由不是“服务器通常更快”，而是不能只靠一次服务一个客户端的结构写出可用的正确服务器；后续三类并发方案都将围绕服务器展开。[00:07:20-00:07:41]

10. **重放 iterative echo server 的单客户控制流。** 迭代式服务器一次处理一个客户端：在 `accept` 等连接，接受后反复等该客户端写一行、读取、回显，再等下一行；只有客户端关闭、服务器也关闭该连接后，服务器才回到下一次 `accept`。与此同时，client 2 虽已发起连接，也必须等待 server 完成 client 1。[00:07:41-00:09:17] [课件: 23-concprog.pptx p.4]

11. **以一个未决问题结束本段。** 直觉上似乎是 client 2 的 `connect` 会一直等服务器接受连接；老师指出实际行为更微妙：`connect` 启动内核中的建连过程后可能先返回，随后的写也可能返回。本段停在这里，具体阻塞点必须用下一段的 TCP 排队与读操作解释，不能在本段证据内提前下结论。[00:09:17-00:09:58]

## 概念、符号与推导

- **并发流（concurrent flow）**：本段用主程序与 signal handler 说明，两条逻辑执行流可以在同一应用生命周期中交错推进。[00:00:40-00:01:17]
- **交错（interleaving）**：多个流各自操作在全局时间线上的可能排列。正确性分析必须覆盖可能排列，而不能只看一次观测到的执行。[00:01:27-00:02:18]
- **共享资源**：Shell Lab 中的 jobs list 是两条流都访问的对象；危险来自它可能在某次交错中处于不一致状态。[00:02:02-00:02:18]
- **race**：好坏结果依赖任意调度决定，而不是仅由程序员期望的顺序决定。[00:03:01-00:03:35] [课件: 23-concprog.pptx p.3]
- **deadlock**：多个流等待无法发生的事件；`printf` 例中的等待环是“handler 等锁 -> 主程序持锁但等 handler 返回 -> handler 无法返回”。[00:04:00-00:05:24]
- **starvation / fairness**：某个流因其他流持续获得执行机会而无法前进；fairness 要求各实体取得合理份额。本段没有给出形式化公平性公式。[00:06:02-00:06:52]
- **iterative server**：一次只处理一个客户端请求流；结束当前连接后才接受并服务下一客户端。[00:07:41-00:09:17] [课件: 23-concprog.pptx p.4]
- **推导链**：人倾向顺序思考 -> 并发要求覆盖多种交错 -> 共享状态让交错影响结果 -> 出现 race/deadlock/starvation 等问题 -> 需要用服务器案例学习有原则的并发设计。[00:01:03-00:07:41]

本段无公式推导；老师只定性指出可能交错数随并发流数量指数式增长，没有给出具体计数公式。[00:01:40-00:01:54]

## 常见误解与辨析

- **误解：并发错误只会在真正多核并行时出现。** 本段的信号处理器和单核调度交错已经足以产生 race 与 deadlock；关键是流的执行重叠和不可预设的顺序。[00:00:40-00:02:18]
- **误解：race 就是两条流“同时写”。** 课堂定义更宽：只要结果依赖任意调度决定就是 race；Shell Lab 例甚至涉及 child 结束与 parent 更新 jobs list 的先后。[00:03:01-00:03:35]
- **误解：deadlock 只是“程序很慢”。** `printf` 例形成封闭等待环，所等事件不会发生，因此不是等待时间较长，而是没有前进路径。[00:04:00-00:05:24]
- **误解：迭代式服务器只会让后来的客户端稍慢一点。** 若当前客户端长期不结束，后续客户端可能无限期得不到服务；完整故障在下一段展开。[00:07:41-00:09:17]

# 第 2 段：迭代式服务器的根本缺陷与三种并发方案（00:09:58-00:19:57）

## 本段在整讲中的作用

上一段停在“第二客户端到底阻塞在哪里”。本段先把这条执行轨迹补完：`connect` 和 `rio_writen` 可借助内核排队/缓冲返回，真正等待服务器响应的是 `rio_readlineb`。老师随后把一个用户长期不输入的情形推成迭代式服务器的根本失败，再提出 process-based、event-based、thread-based 三种并发服务器设计。末尾先进入进程方案：监听 server 每接受一个连接就 fork 独立 child，使 client 1 的阻塞不再阻止 client 2 获得服务。[00:09:58-00:19:57] [课件: 23-concprog.pptx p.5] [课件: 23-concprog.pptx p.6] [课件: 23-concprog.pptx p.7] [课件: 23-concprog.pptx p.8]

## 教学展开

1. **先回答第二客户端的准确阻塞点。** client 2 的 `connect` 发起建连后可以返回，即使 server 应用尚未 `accept`；服务器端 TCP manager 可把连接请求放入 TCP listen backlog。随后 client 的 `rio_writen` 也可返回，因为内核能先缓冲输入数据。直到 client 调用 `rio_readlineb` 等待回显，而 server 尚未写给它任何数据时，它才必须阻塞。[00:09:58-00:11:26] [课件: 23-concprog.pptx p.5]

2. **明确排队不等于已被应用服务。** 内核可以记住连接请求和待发送数据，使 client 应用继续运行；但读操作不能凭空返回尚不存在的数据。因此“调用返回”只说明内核接受了这一步工作，不说明迭代式 server 已进入 client 2 的业务处理。[00:10:41-00:11:26]

3. **构造迭代式服务器的致命场景。** client 1 建连并完成一次 echo 后，没有写下一行，也没有关闭连接，因为用户离开去吃午饭。server 已在该 `connfd` 上再次 `read`，只能等 client 1 产生数据；等待多久无法确定。[00:11:30-00:12:48] [课件: 23-concprog.pptx p.6]

4. **把局部等待推成全局停服。** server 卡在 client 1 的读操作时，不能返回监听循环服务 client 2；client 2 已写入请求，却在读 server 响应时等待。于是一个慢、失常或永久沉默的 client 可以阻止所有其他 client 获得服务。若这是 Web server，一个用户就可能让整站其他用户都无法取页面。[00:12:48-00:13:29] [课件: 23-concprog.pptx p.6]

5. **由失败条件直接提出 concurrent server。** 解决方式是让每个客户端由一条独立 concurrent flow 处理。若某条 flow 因慢客户端阻塞，其他 flow 仍可服务其他客户端；“并发流之间隔离等待”是此处正确性的核心，而不只是吞吐优化。[00:13:29-00:13:57]

6. **借学生问题区分内核排队与应用级事件处理。** 学生问 server 能否把多个客户端的 read 都排队。老师先思考后指出，纯迭代控制流仍须逐次 `accept`，因而不能在当前写法中取得其他连接的数据；但这个想法接近稍后要讲的 event-based server。[00:14:01-00:15:08]

7. **建立 process-based 方案的两个属性。** 每个 flow 是独立进程，由内核自动调度并交错执行；每个进程有私有地址空间。因此程序员不手工决定每个 flow 何时运行，不同 flow 也不直接共享全局数据。[00:15:10-00:15:46] [课件: 23-concprog.pptx p.7]

8. **建立 event-based 方案的两个属性。** 只有一个程序/地址空间，所有逻辑 flow 可访问同一批全局结构；程序员通过 I/O multiplexing 自己判断事件并手工交错各 flow，而不是让内核替自己切换多个进程。[00:15:46-00:16:34] [课件: 23-concprog.pptx p.7]

9. **把 thread-based 定位为混合体。** 线程像进程一样由内核自动调度，却像事件方案一样共享同一地址空间，所以每条 thread 都可访问程序中的全局变量。老师据“谁负责交错”与“地址空间是否共享”两个维度把它称为 process/event 的 hybrid。[00:16:34-00:17:26] [课件: 23-concprog.pptx p.7]

10. **先展开 process-based echo server 的运行轨迹。** client 1 连接后在 `fgets` 等用户输入；server 从 `accept` 返回并 fork child 1，由 child 1 在该连接上等待数据。即便用户不再输入、child 1 永久阻塞，监听 parent 仍立刻回到 `accept`。[00:17:33-00:18:45] [课件: 23-concprog.pptx p.8]

11. **验证第二客户端不再被第一个拖住。** parent 接受 client 2 后 fork child 2。child 2 独立读取、回显并关闭自己的连接；child 1 的等待只占住自己的 flow，不阻断 parent 或 child 2。老师由此重申：为不同客户端创建并发 flow 是可用 server implementation 的基础。[00:18:45-00:19:47] [课件: 23-concprog.pptx p.8]

12. **以代码问题引向下一段。** 老师说进程版实现“出乎意料地紧凑”，但本段尚未逐行展示描述符关闭、child 回收和引用计数；这些是下一段的实现正确性条件。[00:19:47-00:19:57]

## 概念、符号与推导

- **TCP listen backlog**：server-side TCP manager 可排队尚未被 server 应用 `accept` 的连接请求；它解释本课堂轨迹中 client 2 的 `connect` 为什么先返回。[00:10:41-00:10:59] [课件: 23-concprog.pptx p.5]
- **内核输入缓冲**：client 的 `rio_writen` 可把数据交给内核后返回，数据等待连接处理；这不同于 server 已经读取它。[00:10:59-00:11:18] [课件: 23-concprog.pptx p.5]
- **读阻塞条件**：`rio_readlineb` 需要实际输入才能返回；server 尚未为 client 2 写响应时，client 2 在这里等待。[00:11:18-00:11:26]
- **迭代式故障链**：client 1 不输入 -> server 阻塞在读取 client 1 -> server 不再 `accept`/服务其他连接 -> client 2 阻塞等 server 响应 -> 一个 client 影响全体。[00:11:30-00:13:29] [课件: 23-concprog.pptx p.6]
- **process-based**：内核自动交错 flow；每个 flow 有私有地址空间。[00:15:10-00:15:46] [课件: 23-concprog.pptx p.7]
- **event-based**：程序员以 I/O multiplexing 手工交错 flow；所有 flow 共用一个地址空间。[00:15:46-00:16:34] [课件: 23-concprog.pptx p.7]
- **thread-based**：内核自动交错 thread；thread 共用一个地址空间，是前两者在上述两个维度上的组合。[00:16:34-00:17:26] [课件: 23-concprog.pptx p.7]
- **进程服务器角色划分**：parent/listening server 只持续 `accept` 和 fork；每个 child 只与分配给自己的 client 交互。[00:17:33-00:19:30] [课件: 23-concprog.pptx p.8]

本段无公式推导。

# 第 3 段：进程并发服务器的代码、描述符轨迹与代价（00:19:57-00:29:56）

## 本段在整讲中的作用

上一段用运行图说明“每客户端一个 child”能隔离阻塞，本段把它落实为完整 `echoserverp.c` 控制流，并追踪 `accept`、`fork`、描述符表与内核 open-file/socket 引用计数。老师由此给出进程服务器的三项正确性要求：监听进程回收 zombie child、parent 关闭自己的 `connfd`、child 不使用的 `listenfd` 也应关闭。随后从“隔离清晰但进程昂贵、共享困难”的权衡转向第二种 event-based server。[00:19:57-00:29:56] [课件: 23-concprog.pptx p.9] [课件: 23-concprog.pptx p.10] [课件: 23-concprog.pptx p.11] [课件: 23-concprog.pptx p.12] [课件: 23-concprog.pptx p.13] [课件: 23-concprog.pptx p.14] [课件: 23-concprog.pptx p.15]

## 教学展开

### 课堂代码：`echoserverp.c`

```c
int main(int argc, char **argv)
{
   int listenfd, connfd;
   socklen_t clientlen;
   struct sockaddr_storage clientaddr;

   Signal(SIGCHLD, sigchld_handler);
   listenfd = Open_listenfd(argv[1]);
   while (1) {
      clientlen = sizeof(struct sockaddr_storage);
      connfd = Accept(listenfd, (SA *) &clientaddr, &clientlen);
      if (Fork() == 0) {
         Close(listenfd); /* Child closes its listening socket */
         echo(connfd);    /* Child services client */
         Close(connfd);   /* Child closes connection with client */
         exit(0);         /* Child exits */
      }
      Close(connfd); /* Parent closes connected socket (important!) */
   }
}
```

# 第 4 段：I/O 多路复用、事件粒度与单控制流并发（00:29:56-00:39:55）

## 本段在整讲中的作用

上一段刚提出 server 可维护 active connection 集合，本段完成 event-based 模型：以 `select` 或 `epoll` 找出有 pending input 的 `listenfd`/`connfd`，再在一个顺序 C 控制流中逐个接受或服务事件。老师不仅列优缺点，还用部分 HTTP request 推导出事件服务器最难的设计问题：一次事件处理多少工作；若要抵抗慢或恶意客户端，就必须保存不完整输入的状态。段末转向第三种 thread-based server，并开始回顾传统进程组成。[00:29:56-00:39:55] [课件: 23-concprog.pptx p.15] [课件: 23-concprog.pptx p.16] [课件: 23-concprog.pptx p.17] [课件: 23-concprog.pptx p.18] [课件: 23-concprog.pptx p.19]

## 教学展开

1. **先解决“哪些连接现在可处理”。** server 同时保存 listening descriptor 与一组 connected descriptors，调用 `select`、`epoll` 或类似机制判断其中哪些有 pending input。程序不是盲目对每个 descriptor 做阻塞读，而是先得到 readiness 集合。[00:29:56-00:30:22] [课件: 23-concprog.pptx p.15]

2. **把 pending input 定义为 event。** 输入到达使 descriptor 状态发生变化：事件前没有可读数据，事件后有数据可读。老师把 event 一般化为某种 state change；这里关注的是 socket input arrival。[00:30:22-00:30:55]

3. **按 descriptor 类型分派事件。** 若 ready 的是 `listenfd`，server 调用 `accept` 并把新 `connfd` 加入数组；若 ready 的是一个或多个 connected descriptors，server 以某个次序读取并服务它们。[00:30:55-00:31:13] [课件: 23-concprog.pptx p.15]

# 第 5 段：从进程重构出线程、并发判定与 Pthreads 入口（00:39:55-00:49:53）

## 本段在整讲中的作用

上一段只说 thread-based 与 process-based 相似，本段回答“thread 到底是什么”。老师先拆开传统 process 的 program context、kernel context 与 address space，再把 stack 和执行寄存器组合成 thread context，使同一 process 能容纳多个独立 logical control flow。随后用 A/B/C 调度轨迹严格区分 concurrent、sequential 与 parallel，比较 thread/process 的共享边界和控制成本，最后引出 POSIX Threads 接口。[00:39:55-00:49:53] [课件: 23-concprog.pptx p.19] [课件: 23-concprog.pptx p.20] [课件: 23-concprog.pptx p.21] [课件: 23-concprog.pptx p.22] [课件: 23-concprog.pptx p.23] [课件: 23-concprog.pptx p.24] [课件: 23-concprog.pptx p.25] [课件: 23-concprog.pptx p.26]

## 教学展开

1. **补全 traditional process view。** process 可写成 process context 加 code、data、stack。program context 含 data registers、condition codes、stack pointer（SP）、program counter（PC）；kernel context 则含内核为实现 process 保存的 VM structures、descriptor table、`brk` pointer 等支持状态。[00:39:55-00:40:42] [课件: 23-concprog.pptx p.19]

2. **做一次概念重排而非改变机器状态。** 老师把 stack 从“code/data/stack”大块中抽出来，再把 SP、PC、data registers、condition codes 等 program execution context 放到它旁边，并把这组 context 改名为 thread context。[00:40:44-00:41:27] [课件: 23-concprog.pptx p.20]

3. **定义 thread。** 一个 stack 与一份 thread context 的组合就是 thread；剩余 code、data 与 kernel context 仍属于 process。由此 process 的替代视图是“thread + code/data/kernel context”，原来单线程 process 中这条 thread 就是 main thread。[00:41:27-00:41:55] [课件: 23-concprog.pptx p.20]

4. **解释为什么可在同一 process 中复制 thread。** 每条 thread 只需自己的 stack 区域和少量执行 context，因此可为同一 process 保存多组 thread context。所有 threads 继续共享相同 code、data、virtual address space 与 kernel context。[00:41:55-00:42:52] [课件: 23-concprog.pptx p.21]

5. **列出每线程私有的执行状态。** 每条 thread 有自己的 stack（供 local variables）、PC、SP、registers、condition codes 和 thread ID（TID）；整个 process 仍有 process ID，后者属于 process/kernel context。[00:42:52-00:43:37] [课件: 23-concprog.pptx p.21]

6. **由独立 PC 推出独立 flow。** 不同 thread 虽从同一 code section 取指，却各自保存“下一条执行在哪里”的 PC。内核可以像调度 process 那样分别暂停、恢复和调度每条 thread，因而每条 thread 构成独立 logical control flow。[00:43:37-00:44:22]

7. **说明线程切换为何较轻。** 从 thread 1 切到 thread 2 时，内核保存前者少量 thread context 并恢复后者；因为地址空间与 process kernel context 不变，不必切换 page tables、virtual address space 等较重的 process context。[00:44:22-00:45:06]

8. **比较组织关系：树与 peer pool。** `fork` 产生严格 parent-child process hierarchy；同一 process 中的 threads 不形成这样的树，而是共享 code/data/kernel context 的 peers。老师让学生把它们想成一组可并发调度的 flow。[00:45:06-00:45:47] [课件: 23-concprog.pptx p.22]

9. **给出 concurrency 的时间定义。** 两个 thread 的 flow 若在时间上 overlap，就是 concurrent；否则 sequential。它不要求两个 thread 在同一个瞬间分别占用两个 core。[00:45:47-00:46:03] [课件: 23-concprog.pptx p.23]

10. **逐步执行 A/B/C 单核 trace。** A 先运行；内核保存 A、恢复 B，B 运行；再保存 B、恢复 C 并把 PC 设为 C 的 PC，C 运行；之后恢复 A，A 继续。由整段生命期判断：A 与 B overlap，A 与 C overlap，所以两对 concurrent；B 与 C 不 overlap，所以 sequential。[00:46:03-00:47:05] [课件: 23-concprog.pptx p.23]

11. **再区分 true parallelism。** 单 core 以 time slicing 模拟多 flow 同时推进；若有多个 core，则不同 thread 可同时在不同 core 上实际执行，形成 true parallelism。课件示意为 3 threads 在 2 cores 上运行。[00:47:05-00:47:16] [课件: 23-concprog.pptx p.24]

12. **总结 thread/process 的共同点。** 二者都代表 logical flow，都可与其他 flow concurrent（也可能在不同 core），并都由 kernel context switch。[00:47:16-00:47:49] [课件: 23-concprog.pptx p.25]

13. **总结最重要的共享差异。** threads 共享 code/data，只有各自 local stack 区域；process 通常有私有 address space。可是每线程 stack 仍位于同一个 process virtual address space，未受其他 thread 保护，所以一个 thread 技术上可以访问另一个 thread 的 stack，尽管这样做很危险。[00:47:49-00:48:38] [课件: 23-concprog.pptx p.21] [课件: 23-concprog.pptx p.25]

14. **用课堂测量比较成本。** 老师把差异归因于 thread context 较小。课件给出的 Linux 数字是：创建并 reap 一个 process 约 20K cycles，创建并 reap 一个 thread 约 10K cycles 或更少；因此 process control 约为 thread control 的两倍，但二者都不是零成本。[00:48:38-00:49:16] [课件: 23-concprog.pptx p.25]

15. **引出 Pthreads。** kernel 通过 POSIX Threads（Pthreads）标准接口供 C 程序操纵 threads。老师先提到 create/reap 与类似 `fork`/等待的操作；课件概览还列出取得 TID、终止 thread 与同步 shared variables，具体调用顺序在下一段展开。[00:49:16-00:49:53] [课件: 23-concprog.pptx p.26]

# 第 6 段：Pthreads 执行模型与线程版 echo server（00:49:53-00:59:52）

## 本段在整讲中的作用

上一段建立 thread 的机器模型，本段把它落到 Pthreads API 与可执行代码。老师先用最小 “hello, world” 说明 thread routine 的 `void * -> void *` 接口、peer 关系、`pthread_create`/`pthread_join` 的时间轨迹；再把进程版 echo server 改成每客户端一个 peer thread。代码特意为每个 `connfd` 在 heap 上单独 `Malloc`，thread 启动后 detach 自己、复制 descriptor、释放参数存储并负责 echo/close。为什么不能直接传 main stack 上 `connfd` 的地址，留到下一段用 race trace 证明。[00:49:53-00:59:52] [课件: 23-concprog.pptx p.26] [课件: 23-concprog.pptx p.27] [课件: 23-concprog.pptx p.28] [课件: 23-concprog.pptx p.29] [课件: 23-concprog.pptx p.30] [课件: 23-concprog.pptx p.31]

## 教学展开

1. **先完成 Pthreads API 全景。** `pthread_create` 创建 thread，`pthread_join` 等待/回收 joinable thread，功能近似 process 的 create/wait，但 threads 不形成 parent-child hierarchy。`pthread_self` 取得当前 TID，`pthread_cancel` 请求终止 thread，`pthread_exit` 结束当前 thread；普通 `exit` 结束 process 中所有 threads，从 thread routine `return` 则只结束当前 thread。[00:49:53-00:50:36] [课件: 23-concprog.pptx p.26]

2. **把 shared-variable synchronization 留给后续。** Pthreads 还提供 mutex 初始化、lock/unlock 等共享变量同步接口；老师明确说周四再详细讲，所以本段不把 mutex 机制提前展开。[00:50:36-00:50:44] [课件: 23-concprog.pptx p.26]

3. **用 “hello, world” 建立最小 thread routine。** 沿用 K&R 教新概念时先写最小程序的传统，老师定义 `void *thread(void *vargp)`。POSIX 要求 routine 接收一个 generic pointer 并返回一个 generic pointer；若要传多项数据，调用者须把它们包装在一个对象中，再传该对象地址。[00:50:44-00:52:15] [课件: 23-concprog.pptx p.27]

4. **强调新 thread 是 peer，不是 child。** `Pthread_create` 产生 peer thread，thread pool 不存在 fork 那样严格的 parent-child 关系；课堂模型允许一个 thread join 其他 thread，不以“是否由它创建”建立层级。[00:52:21-00:52:51]

5. **逐项解释 `Pthread_create` 参数。** 第一项 `&tid` 接收新 thread ID；第二项是 attributes，本课程始终传 `NULL`，不展开属性配置；第三项 `thread` 是新 flow 执行的 routine；第四项是传给 routine 的 optional `void *` argument，本例也为 `NULL`。[00:52:51-00:53:37] [课件: 23-concprog.pptx p.27]

6. **说明 routine 的退出值。** peer 执行 `printf("Hello, world!\n")` 后 `return NULL`，因此终止自己且不返回对象。接口也允许返回指向某个 generic object 的 pointer，join 方可通过相应参数取得它。[00:53:37-00:54:28]

7. **按时间展开 hello 执行。** main thread 先运行并调用 `Pthread_create`；create 返回后，main 与 peer 是两条 concurrent flow。main 调用 `Pthread_join(tid, NULL)` 等 peer；peer `printf` 后 `return NULL` 并终止，join 才返回，main 随后 `exit(0)`。[00:54:28-00:55:31] [课件: 23-concprog.pptx p.28]

8. **把进程 server 框架原样迁移到 thread。** main 仍用 `Open_listenfd(argv[1])` 建 listening descriptor，并在无限循环中重置 `clientlen`、调用 `Accept`；区别是每次连接不 `fork`，而是 `Pthread_create` peer routine。[00:55:31-00:56:17] [课件: 23-concprog.pptx p.29]

9. **为本轮 `connfd` 单独分配参数对象。** 每次循环先 `connfdp = Malloc(sizeof(int))`，把 `Accept` 返回值写入 `*connfdp`。老师提前强调这块独立 heap storage 是避免一个“nasty/deadly race”的关键，完整反例下一段才展开。[00:56:17-00:57:11] [课件: 23-concprog.pptx p.29]

10. **创建负责该连接的 peer。** `Pthread_create(&tid, NULL, thread, connfdp)` 把本轮独有的 descriptor pointer 传给 routine；main 不 join 它，而是继续接受后续连接。[00:57:11-00:57:37]

11. **peer 先取得值，再处理参数存储。** routine 把 `vargp` 转为 `int *` 并解引用，复制到自己的 local `connfd`；然后以 `Pthread_detach(pthread_self())` 把自己转为 detached，最后 `Free(vargp)` 释放 main 为参数分配的 heap block。[00:57:37-00:59:06] [课件: 23-concprog.pptx p.30]

12. **解释 detach 的资源语义。** 默认 thread 是 joinable，终止后要由其他 thread join 才释放其保留资源；detached thread 不能再被 join，终止时由系统自动回收相应资源。server 不需要收集每个 client thread 的返回值，因此让 peer 自行 detach，避免未 join 资源不断累积。[00:57:55-00:59:01]

13. **完成连接所有权。** peer 调用 `echo(connfd)` 与 client 交互，结束后 `Close(connfd)`，再 `return NULL`。`Free(vargp)` 与 `Close(connfd)` 管的是两个不同资源：前者是传参 heap block，后者是 connected socket descriptor。[00:59:01-00:59:30] [课件: 23-concprog.pptx p.30]

14. **开始画 thread server execution model。** main thread 作为 listening server 在 `accept` 等 connection request，每个 client 有自己的 peer thread 和传入的 connected descriptor。本段在图解开头结束，local-variable 隔离与 detached 问答进入下一段。[00:59:30-00:59:52] [课件: 23-concprog.pptx p.31]

## 概念、符号与推导

- **thread routine 类型**：`void *thread(void *vargp)`；一个 generic pointer 输入、一个 generic pointer 输出，使接口不依赖具体参数类型。[00:51:32-00:52:15]
- **`pthread_t tid`**：保存 thread ID 的类型；`Pthread_create` 通过 `&tid` 写回新 peer 的 ID。[00:52:51-00:53:11]
- **create 后的并发边界**：`Pthread_create` 返回后 main 与 peer 都可运行，调度次序不能由源代码行顺序推断。[00:54:31-00:55:02] [课件: 23-concprog.pptx p.28]
- **`Pthread_join(tid, NULL)`**：main 等指定 peer 终止；第二项在本例不接收 routine 返回 pointer。[00:55:02-00:55:31]
- **joinable / detached**：thread 在任一时刻处于其中一种状态；默认 joinable，server peer 调用 `Pthread_detach(pthread_self())` 后由系统在终止时自动回收资源。[00:57:55-00:59:01]

- **socket 所有权链**：main 接受连接并把 descriptor value 交给 peer -> peer `echo(connfd)` -> peer `Close(connfd)`。[00:56:43-00:59:30]
- **thread server flow**：一个 main listening thread 加每 client 一个 peer thread；threads 共享 process state，而每个 routine 的 local `connfd` 正常位于自己的 stack。[课件: 23-concprog.pptx p.31]

# 第 7 段：线程共享的力量与 `&connfd` 致命 race（00:59:52-01:09:49）

## 本段在整讲中的作用

上一段给出正确的 thread-based echo server，本段先完成其 execution model，再解释代码中两个看似多余的选择为何必要：client peer 要 detached；连接参数要有每次独立的 heap 存储。老师把“共享同一地址空间”同时作为最大优点和最大风险，随后逐步构造错误版 `Pthread_create(..., &connfd)` 的调度交错，证明 main stack 上同一槽位会被下一次 `Accept` 覆盖，使两个 peer 错用同一 client descriptor。段末开始三方案总结，只讲到 process-based 的隔离优势。[00:59:52-01:09:49] [课件: 23-concprog.pptx p.31] [课件: 23-concprog.pptx p.32] [课件: 23-concprog.pptx p.33] [课件: 23-concprog.pptx p.34]

## 教学展开

1. **完成 thread server execution model。** listening main thread 反复接受 connection request；每个 client 由单独 peer thread 使用创建时传入的 `connfd` 交互。每条 thread 有自己的 stack，因此 routine 中 local `connfd` 等 local variables 占用不同 stack 区域，可以在不主动共享地址时独立运行。[00:59:52-01:00:33] [课件: 23-concprog.pptx p.31]

2. **回答“何时不 detach”。** 学生问是否有不想 detached 的情形。老师给出一个不太强但可想象的例子：worker thread pool 同时做任务，第一个结果到达后，不再需要其余结果，可能希望终止其他 workers；按本讲模型，detach 会放弃其他 thread join/reap/kill 它的能力。[01:00:33-01:01:34]

3. **精确定义两种状态。** 任一 thread 要么 joinable，要么 detached；默认 joinable。joinable thread 可被其他 thread join/reap，若从不 join，终止后保留资源会造成 leak；调用 `pthread_detach(pthread_self())` 后成为 detached，不能再 join，终止时资源自动回收。[01:01:47-01:02:22] [课件: 23-concprog.pptx p.32]

4. **先肯定共享地址空间的直接收益。** thread-based Web server 可让所有 peers 直接访问同一 cache、logging information 或其他 global data structure，不需要 process IPC。这是 threads 相比 process 的核心便利。[01:02:22-01:02:48] [课件: 23-concprog.pptx p.33]

5. **立即把同一性质翻成风险。** 一旦多个 flow 访问 shared resource，就会重现 Shell Lab 的推理困难；共享可能是程序员未意识到、也未打算发生的。低概率 race 在测试中很难复现，但概率不是零。[01:02:48-01:03:23] [课件: 23-concprog.pptx p.33]

6. **用跨 thread stack pointer 展示“local 不等于不可共享”。** 若一条 thread 把自己 local variable 的地址传给另一条 thread，接收方就能解引用并修改调用方 stack 上的 local state。硬件/地址空间不会阻止它；危险来自对象寿命、并发访问和程序员误判。[01:03:23-01:04:01] [课件: 23-concprog.pptx p.32]

7. **提出 echo server 的错误简化。** 正确版每轮 `Malloc(sizeof(int))`，错误版则声明一个 main local `connfd`，每次 `Accept` 覆盖它，再调用：

   ```c
   Pthread_create(&tid, NULL, thread, (void *)&connfd);
   ```

   这看起来少了分配/释放，但所有 peer 收到的其实是 main stack 上同一地址。[01:04:01-01:05:33] [课件: 23-concprog.pptx p.32]

8. **指出错误版偷偷依赖的调度假设。** 它假定新 peer 一定会在 main 返回循环、接受下一 client 之前先运行并解引用 `&connfd`。并发系统不能假定 kernel 采用这个顺序；`Pthread_create` 后 main 或 peer 都可能先运行。[01:05:59-01:06:44]

## 概念、符号与推导

- **peer-per-client**：main thread 只监听/创建 peers；每个 peer 用一份 connected descriptor 服务一个 client。[00:59:52-01:00:16] [课件: 23-concprog.pptx p.31]
