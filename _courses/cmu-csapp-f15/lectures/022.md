## 关键推导、例子与结论边界

- **为什么返回地址链表**：名称与地址可能多对多，所以查询不能只返回一个结构；client helper 逐项尝试，直到连接成功或结果耗尽。[00:11:33-00:12:12] [00:23:18-00:26:20]
- **为什么需要两种 server descriptor**：固定 `listenfd` 接受未来请求，每次 `accept` 另建 `connfd` 处理当前客户；关闭后者不会摧毁监听入口。[00:42:49-00:46:27] [课件: 22-netprog2.pptx p.16]
- **为什么静态 `Content-length = filesize`**：headers 已先独立发送，body 恰是整个文件，因此长度只取文件字节数而不计 headers。[01:00:21-01:03:44] [课件: 22-netprog2.pptx p.40]
- **为什么动态长度/type 由 child 写**：server 在执行前不知道最终 body；生成 `content` 的 CGI program 才能用 `strlen` 给出长度并声明 `text/html`。[01:13:17-01:14:08] [课件: 22-netprog2.pptx p.51]
- **`hostinfo` 例子**：Facebook、Twitter、Google 返回不同数量和版本的地址，具体化 DNS 多结果与协议无关查询。[00:02:03-00:04:18]
- **echo 例子**：服务器端口 15213 与客户端临时端口共同标识会话；Ctrl-D 结束当前连接，服务器继续等待。[00:37:00-00:39:40]
- **HTTP telnet 例子**：现场 200/479-byte HTML 与课件 301/200 两次 transaction 只共享协议结构，不共享路径、状态或 framing。[00:54:02-00:57:33] [课件: 22-netprog2.pptx p.36] [课件: 22-netprog2.pptx p.37]

# 第 1 段：从连接全景回到 socket 地址（00:00:00-00:09:52）

## 本段在整讲中的作用

本段先说明为什么网络编程不能只靠听课记住：socket API 参数多、层次杂，必须反复对照文档与示例代码。随后老师回接上一讲，从域名与 IP 地址复习开始，经 `hostinfo` 的 IPv4/IPv6 演示，重新走一遍服务器先启动、客户端再连接、双方按文件方式读写、客户端关闭而服务器继续等待的完整生命周期，最后把焦点收窄到通用 socket 地址和 `getaddrinfo`。它是后续逐行解释 `open_clientfd`、`open_listenfd` 和 echo 程序的概念底座。[00:00:00-00:09:52] [课件: 22-netprog2.pptx p.1] [课件: 22-netprog2.pptx p.2]

## 教学展开

1. **先交代学习方法，而不是立刻堆 API。** 老师把 sockets API 形容为庞大、难读且混乱；以自己的经验说明，需要多次来回阅读代码、示例和文档，课堂讲解本身不能替代课后研究。书中及 `csapp.c` 中的示例代码因此是本讲的重要学习材料。[00:00:00-00:00:55]

2. **从上一讲的名字到地址转换重新起步。** 域名（老师举出的字幕文本近似 `www.cmu.edu`）可以经 DNS 映射到 IP 地址；IPv4 是 32 位，通常写成点分十进制。老师说明今天会看上一讲演示过的 `hostinfo` 代码，并展示一个很小的修改，使同一程序同时列出 IPv4 与 IPv6 结果。[00:00:55-00:02:03]

3. **用真实站点说明一个名字可能得到多个地址。** 查询 Facebook 时，程序同时给出点分十进制 IPv4 地址和以十六进制、冒号分隔显示的 128 位 IPv6 地址。老师指出 Facebook 把十六进制串 `FACE` 嵌进了 IPv6 地址；接着查询 Twitter、Google，得到的地址数量和类型不同。[00:02:03-00:04:18]

4. **由演示解释 DNS 结果为何会变。** 同一个查询在家里和校园内可能不同，在不同国家或重复查询也可能不同。大型公司把服务器部署在世界各地，并让 DNS 返回或轮换多个服务器地址，以分散流量。因此“域名对应唯一 IP”不是本例呈现的模型。[00:03:24-00:04:18]

# 第 2 段：`getaddrinfo`、`getnameinfo` 与 `hostinfo`（00:09:52-00:19:49）

## 本段在整讲中的作用

## 教学展开

1. **先承接字节序结论。** 老师补完上一段：地址转换 API 会代办二进制地址与文本表示之间的转换，程序员不必亲自翻转字节或安排网络字节序。[00:09:52-00:10:04]

2. **把 `getaddrinfo` 参数分成输入与输出。** 第一个参数是主机，可以是域名、IPv4 点分十进制文本或 IPv6 冒号文本；第二个参数是 service。老师先以“查主机地址”或“查 HTTP 对应端口”说明其多用途，并在这个查询语境中说，前两个参数通常一个是字符串、另一个是空指针。[00:10:04-00:11:12]

4. **解释为什么结果是“指向指针”。** 调用把一个指针的地址交给函数，函数据此返回自己生成的 `addrinfo` 链表。返回链表而不是单个结构，是因为域名与 IP 地址可能呈多对多关系：一个域名可有多个 IP，一个 IP 也可有多个域名。[00:11:33-00:12:12]

8. **以 `hostinfo` 展示标准准备方式。** 程序从命令行取得域名，先把整个 `hints` 清零，再只设置所需条件。课上显示的原版本要求 `AF_INET`，即只要 IPv4，并设置 `SOCK_STREAM`，表示 TCP 字节流连接。[00:15:11-00:16:37]

本段完成 `hostinfo` 的协议无关改造，随后从“地址能查出来”推进到“连接如何真正建立”。老师特意区分运行时顺序与讲解顺序：实际必须先启动服务器，但客户端调用更少、较易理解，所以先逐行解释 `open_clientfd`；再由客户端的 `connect` 反推服务器为什么需要 `bind`、`listen` 和 `accept`，并在段末开始搭建 `open_listenfd`。[00:19:49-00:29:46] [课件: 22-netprog2.pptx p.5] [课件: 22-netprog2.pptx p.19]

## 教学展开

1. **先完成上一段被截断的修改。** `AF_INET` 是仅取 IPv4 的限制；注释掉该设置后，程序会接受域名在 TCP 条件下支持的地址族，因此同一套代码可列出 IPv4 与 IPv6。[00:19:49-00:20:25]

2. **声明为何先讲客户端。** 服务器在真实时间线上必须先就绪，否则客户端无处连接；但客户端少 `bind`、`listen`、`accept` 等步骤，更适合作为代码入口。老师因此暂时假设远端已有服务器在等。[00:20:29-00:21:03] [课件: 22-netprog2.pptx p.5]

3. **把客户端路径拆成三步。** `getaddrinfo` 从服务器名称和端口得到候选地址；`socket` 只在本机分配该连接所需的数据结构并返回文件描述符；`connect` 才像“拨号”，向服务器发送连接请求。服务器接受后，session 才开始。[00:21:03-00:21:55] [课件: 22-netprog2.pptx p.6] [课件: 22-netprog2.pptx p.14]

4. **准备客户端查询条件。** `open_clientfd(hostname, port)` 先清零 `hints`，设置 `SOCK_STREAM` 表示连接，设置 `AI_NUMERICSERV` 表示传入数值端口字符串，并加入课件推荐的 `AI_ADDRCONFIG`，再调用 `getaddrinfo(hostname, port, &hints, &listp)` 得到潜在服务器地址链表。[00:21:56-00:23:14] [课件: 22-netprog2.pptx p.19]

5. **逐个尝试，而不是假定第一个可用。** 对 `listp` 中每个节点，先用节点给出的 `ai_family`、`ai_socktype`、`ai_protocol` 调用 `socket`；若失败就继续下一节点。若成功，再把该节点的 `ai_addr` 和 `ai_addrlen` 交给 `connect`。[00:23:18-00:25:38] [课件: 22-netprog2.pptx p.20]

6. **精确区分 `socket` 与 `connect` 的副作用。** `socket` 返回一个小整数文件描述符，只建立本地内核状态，没有数据上网；`connect` 才尝试联系服务器，可能因服务器不可用或拒绝连接而失败。连接失败时关闭刚建的 descriptor，再试下一个地址；成功时跳出循环。[00:23:41-00:26:02] [课件: 22-netprog2.pptx p.6] [课件: 22-netprog2.pptx p.20]

7. **完成 helper 的清理与返回。** 无论是否找到可连接项，都释放 `getaddrinfo` 链表；若遍历结束时没有成功节点，返回 `-1`，否则返回已连接的 `clientfd`。这个文件描述符之后可像文件一样读写。[00:26:02-00:26:31] [课件: 22-netprog2.pptx p.20]

8. **转到真实先发生的服务器路径。** 服务器也从 `getaddrinfo` 和 `socket` 开始，但目标不是主动拨出，而是在一个端口等客户端。`bind` 把地址/端口与 descriptor 关联，`listen` 把它设为监听 socket，`accept` 在其上等待并接收连接。[00:26:32-00:27:31] [课件: 22-netprog2.pptx p.2]

9. **指出真正阻塞的位置。** 典型情况下，服务器会阻塞在 `accept`，没有客户时可能一直等待；客户端的 `connect` 也会等待连接建立，不过通常有超时。老师说明这些等待行为有参数可调，但当前只讲典型情况。[00:27:31-00:28:29] [课件: 22-netprog2.pptx p.14] [课件: 22-netprog2.pptx p.15]

10. **开始构造 `open_listenfd` 的地址请求。** 本地服务器不是为了查某个远端客户地址，而是借 `getaddrinfo` 填好 socket API 所需结构。它要求 `SOCK_STREAM`，使用 `AI_PASSIVE` 表示被动等待任意本地 IP 上的连接，并以数值字符串给出服务器端口；主机参数为 `NULL`。本段在调用说明中结束。[00:28:35-00:29:46] [课件: 22-netprog2.pptx p.22]

# 第 4 段：完成 `open_listenfd` 并演示迭代式 echo（00:29:46-00:39:42）

## 本段在整讲中的作用

本段接续服务器 helper 的半截调用，完成“取得被动地址候选 -> 建 socket -> 绑定端口 -> 转为监听状态”的全过程。抽象接口随即被一个最小 echo 服务验证：固定服务器端口与临时客户端端口共同标识连接，客户端发送什么，服务器就原样写回；迭代式结构一次只维持一个会话。[00:29:46-00:39:42] [课件: 22-netprog2.pptx p.22] [课件: 22-netprog2.pptx p.24] [课件: 22-netprog2.pptx p.29]

## 教学展开

1. **补完服务器的 `getaddrinfo` 调用。** 因为服务器就是本地主机，主机参数为 `NULL`；端口字符串、已设置的 `hints` 和结果指针一同传入，返回 `listp`。[00:29:46-00:29:59] [课件: 22-netprog2.pptx p.22]

2. **借学生提问解释 `memset`。** `hints` 是已经声明的结构，不是这里动态分配的对象；`memset(&hints, 0, sizeof(struct addrinfo))` 把其每个字节置零。老师称这是当前推荐的标准写法，并把旧的 `bzero` 作为对照。[00:29:59-00:30:54] [课件: 22-netprog2.pptx p.22]

3. **回答两个 flag 的课堂问题。** 老师明确解释 `AI_PASSIVE` 表示用于被动等待连接；被问到 `AI_ADDRCONFIG` 时，他坦言当场不记得精确定义，只说它较隐蔽、不是必需参数，书中有说明。课堂证据到此为止。[00:30:56-00:31:36]

4. **指出协议独立性。** 这份客户端和服务器 helper 都没有写死 `AF_INET`，所以同一套代码可用于 IPv4 或 IPv6。[00:31:36-00:31:53] [课件: 22-netprog2.pptx p.24]

6. **把 `bind` 定位为本段的第一项实质工作。** `bind(listenfd, p->ai_addr, p->ai_addrlen)` 请求内核把这个 descriptor 与候选地址中的服务器端口关联。端口是同一机器上各应用共享、竞争的资源；端口已占用，或进程无权使用受限端口时，调用会失败，于是关闭本轮 descriptor 并尝试下一候选。[00:32:48-00:33:56] [课件: 22-netprog2.pptx p.8] [课件: 22-netprog2.pptx p.23]

8. **解释 `backlog` 的边界。** `listen` 的参数提示内核可排队多少尚未处理的连接请求。过小可能使繁忙服务器拒绝客户；过大又可能增加某些拒绝服务攻击的暴露面。老师把它定位为性能参数，并未给出本讲的最优数值。[00:34:49-00:35:28] [课件: 22-netprog2.pptx p.10]

9. **完成 helper。** 释放地址链；若没有可绑定地址则返回 `-1`。若 `listen(listenfd, LISTENQ)` 失败，关闭 descriptor 并返回 `-1`；成功则返回可供服务器接受连接请求的 `listenfd`。[00:35:28-00:35:44] [课件: 22-netprog2.pptx p.24]

10. **用 echo server 给抽象调用赋予可观察行为。** 老师启动 `echoserveri`，其中 `i` 表示 iterative，只能一次处理一个连接；服务器使用端口 `15213`。普通用户自选端口通常取 1000 以上，而端口号受无符号 16 位范围限制；企业网络可能锁定端口，CMU 环境较宽松。本次演示在 localhost 上进行。[00:35:44-00:37:47]

# 第 5 段：echo 客户端/服务器与 HTTP 分层入口（00:39:42-00:49:40）

## 本段在整讲中的作用

上一段先演示 echo 的外部行为，本段打开实现，分别追踪客户端与迭代式服务器如何把 socket descriptor 当作文件读写。老师借 `accept` 返回新描述符这一点明确区分“长期存在的监听端点”和“只服务一个会话的连接端点”，再用 `telnet` 说明基于 ASCII 的服务器可被手工探测。完成低层 socket 编程后，课堂转入最重要的客户端/服务器应用案例 Web，并把 HTTP 放到 TCP/IP 之上。[00:39:42-00:49:40] [课件: 22-netprog2.pptx p.25] [课件: 22-netprog2.pptx p.30]

## 教学展开

1. **先用“第二客户端会挂住”重申迭代式限制。** 当服务器仍在处理一个客户时，再启动一个客户不会得到及时服务；老师把课堂可见现象描述为客户端挂住，因为服务器一次只能处理一个连接。[00:39:42-00:40:03]

2. **从 echo 客户端主程序开始读。** 客户端以 host 和 port 调用 `Open_clientfd` 得到 `clientfd`，再用 `Rio_readinitb(&rio, clientfd)` 把 RIO 缓冲读状态绑定到该连接。[00:40:03-00:40:46] [课件: 22-netprog2.pptx p.25]

3. **按一轮请求/响应追踪客户端循环。** `Fgets` 从标准输入读一行；只要未遇到 EOF，就以 `Rio_writen(clientfd, buf, strlen(buf))` 把该行发给服务器；接着 `Rio_readlineb` 从同一连接读服务器响应，再由 `Fputs` 输出到终端。`buf` 先作发送缓冲区、后作接收缓冲区，换行符已包含在行内。[00:40:46-00:42:07] [课件: 22-netprog2.pptx p.25]

4. **提炼客户端代码的中心结论。** 网络端点表现为文件描述符：写 descriptor 就把字节送入连接，读 descriptor 就取得服务器回送的字节。输入 EOF 后循环结束，客户端关闭 `clientfd`。[00:42:03-00:42:17] [课件: 22-netprog2.pptx p.25]

5. **转向服务器并准备协议无关的客户地址缓冲区。** 服务器声明 `struct sockaddr_storage clientaddr`；课件说明它有足够空间容纳任意地址族。服务器先用 `Open_listenfd(argv[1])` 创建一次性的 `listenfd`，然后进入无限循环。[00:42:17-00:42:56] [课件: 22-netprog2.pptx p.26]

6. **在 `accept` 处等待并分裂出连接描述符。** 每轮先把 `clientlen` 设成 `sizeof(struct sockaddr_storage)`，再调用 `Accept(listenfd, (SA *)&clientaddr, &clientlen)`。没有客户时该调用阻塞；连接到来后，它把客户 socket 地址写入 `clientaddr`，并返回新的 `connfd`。[00:42:49-00:43:26] [课件: 22-netprog2.pptx p.12] [课件: 22-netprog2.pptx p.15] [课件: 22-netprog2.pptx p.26]

7. **解释为什么必须有两类 descriptor。** `listenfd` 是服务器接收未来连接请求的固定入口；每次 `accept` 新建的 `connfd` 是本次客户端与服务器交换数据的端点。迭代式程序暂时一次只用一个 `connfd`，但这种分离使并发服务器未来可以同时保留多个客户连接。[00:43:20-00:43:46] [课件: 22-netprog2.pptx p.16]

8. **把客户二进制地址转成显示文本。** `accept` 填入客户地址后，服务器将它和实际长度交给 `Getnameinfo`；调用方同时给出 `client_hostname`、`client_port` 两个缓冲区及容量。函数填入主机名和端口字符串，程序据此打印连接来源。[00:43:46-00:45:23] [课件: 22-netprog2.pptx p.26]

12. **从低层 socket 切换到 HTTP。** Web 浏览器是客户端，Web server 是服务器；两者先建立 TCP 连接，再按 HTTP 请求和响应传输 Web content，最后关闭连接。分层关系是 IP 提供 datagram 层、TCP 在其上提供 stream、HTTP 再在 TCP 上规定 Web 语义。[00:48:11-00:49:15] [课件: 22-netprog2.pptx p.30]

## 概念、符号与推导

- **echo 客户端数据序列**：`stdin -> Fgets -> Rio_writen(clientfd) -> Rio_readlineb(clientfd) -> Fputs(stdout)`。[00:40:46-00:42:07] [课件: 22-netprog2.pptx p.25]
- **监听描述符 `listenfd`**：服务器创建一次，在其生命周期内作为客户连接请求的入口。[课件: 22-netprog2.pptx p.16]
- **连接描述符 `connfd`**：每次 `accept` 成功创建一个，只在服务该客户期间存在，可用 Unix I/O 读写。[00:43:12-00:43:46] [课件: 22-netprog2.pptx p.12] [课件: 22-netprog2.pptx p.16]
- **`accept` 的信息流**：输入 `listenfd`、客户地址缓冲区与容量指针；等待连接后，输出客户地址、实际地址长度，并以返回值给出 `connfd`。[课件: 22-netprog2.pptx p.12] [课件: 22-netprog2.pptx p.26]
- **服务器循环不变量**：`listenfd` 始终保留；每轮只创建、使用并关闭一个 `connfd`；当前 `echo` 结束后才接受下一客户，因此是 iterative。[00:45:23-00:46:27]
- **EOF 因果链**：客户端关闭 `clientfd` -> 服务器在对应 `connfd` 上的 RIO 读返回 0 -> `echo` 返回 -> 服务器关闭该 `connfd` -> 外层循环再次 `accept`。[课件: 22-netprog2.pptx p.27]
- **Web 协议分层**：HTTP 使用 TCP stream 传请求/响应；TCP 位于 IP datagram 机制之上；HTTP 响应携带 Web content。[00:48:27-00:49:15] [课件: 22-netprog2.pptx p.30]

# 第 6 段：Web content、HTTP transaction 与 Tiny 总体流程（00:49:40-00:59:38）

## 本段在整讲中的作用

本段把上一段建立的“HTTP 在 TCP 上运行”具体化为 Web 应用语义。老师依次定义 content 与 MIME type，区分静态和动态内容，拆开 URL 中客户端使用的前缀与服务器使用的后缀，再说明 HTTP 请求、响应以及一次真实 telnet transaction 的字节顺序。最后用 239 行的 Tiny Web Server 把协议格式重新接回服务器控制流，为下一段的 `serve_static` 与 CGI 实现铺路。[00:49:40-00:59:38] [课件: 22-netprog2.pptx p.31] [课件: 22-netprog2.pptx p.39]

## 教学展开

1. **先解释 HTTP 为什么能承载不同格式。** Web 不只传 HTML 文本，也能传 JPEG 等二进制图像。课件把 content 定义为“一串字节及其关联的 MIME type”，并列出 `text/html`、`text/plain`、`image/gif`、`image/png`、`image/jpeg`。[00:49:40-00:50:43] [课件: 22-netprog2.pptx p.31]

2. **按经典服务器模型区分静态与动态。** 静态内容已存放在文件中，请求到来时检索并原样返回，例如 HTML、图像、音频；动态内容则为某次请求现场产生，例如服务器程序按当前天气生成页面。请求静态内容时标识内容文件，请求动态内容时标识服务器要执行的程序文件。[00:50:43-00:51:25] [课件: 22-netprog2.pptx p.32]

3. **给经典模型加上时代边界。** 老师指出现代 JavaScript 和客户端编程让 Web 更复杂，客户端也会执行代码并反复通信；本讲仍采用较早、较简单的服务器生成模型。无论静态还是动态，在线路上传送的最终都是字节内容；课件的底线表述是 Web content 与服务器管理的文件相关联。[00:51:25-00:51:55] [课件: 22-netprog2.pptx p.32]

5. **区分客户端和服务器各用 URL 的哪部分。** 以 `http://www.cmu.edu:80/index.html` 为例，客户端从前缀判断协议、服务器主机和端口；服务器使用后缀 `/index.html` 判断静态/动态并在自己的文件系统中找对象。初始 `/` 表示该站点内容根，而不是任意操作系统根目录。[课件: 22-netprog2.pptx p.33]

6. **建立 HTTP 请求结构。** 浏览器要页面时发送 request line，后跟零个或多个 request headers。请求行形为 `<method> <uri> <version>`；老师聚焦最常见的 `GET`，课件同时列出 POST、OPTIONS、HEAD、PUT、DELETE、TRACE。对源服务器，URI 通常是 URL suffix；对 proxy，可能是完整 URL。[00:52:48-00:53:22] [课件: 22-netprog2.pptx p.34]

7. **建立 HTTP 响应结构。** 服务器返回 response line、零个或多个 response headers，可能再跟 content；空行 `\r\n` 把 headers 与 body 分开。响应行形为 `<version> <status code> <status msg>`，例如 `200 OK`、`301 Moved`、`404 Not found`；`Content-Type` 给 body 的 MIME type，`Content-Length` 给 body 长度。[00:53:22-00:54:02] [课件: 22-netprog2.pptx p.35]

9. **解释请求行与 `Host` header。** 演示请求某个为课堂准备的测试页面，并指定 HTTP/1.1。还必须显式给 `Host`，因为同一物理机器可托管许多域名；老师以商业托管商为例，说明服务器靠这一字段判断当前请求属于哪个虚拟站点。[00:55:24-00:56:20] [课件: 22-netprog2.pptx p.34]

## 本段在整讲中的作用

## 概念、符号与推导

- **参数传递链**：URL 中 `?` 后的文本 -> server 的 `cgiargs` -> child 环境变量 `QUERY_STRING` -> CGI program 的 `getenv` -> 按 `&` 拆分 -> `atoi` 得到整数。[01:09:27-01:10:46] [课件: 22-netprog2.pptx p.49]
- **`QUERY_STRING`**：单个字符串，内容是 URI 中 `?` 后的全部文本；对示例为 `15213&18213`。[课件: 22-netprog2.pptx p.49]
- **动态执行链**：server 写通用响应开头 -> `Fork` -> child `setenv` -> `Dup2(fd, STDOUT_FILENO)` -> `Execve(filename, ..., environ)` -> parent `Wait`。[课件: 22-netprog2.pptx p.50]
- **输出通道推导**：`dup2` 让 fd 1 指向 connected socket；所以 CGI program 无需直接调用 socket API，其 `printf`/stdout 字节自然进入客户端连接。[01:11:56-01:12:21] [01:13:39-01:13:55]
- **响应所有权**：server 知道请求成功及自身名称，先写 status/server headers；CGI child 知道最终 `content`，所以生成 `Content-length`、`Content-type` 与 body。[01:13:17-01:14:08] [课件: 22-netprog2.pptx p.51] [课件: 22-netprog2.pptx p.52]
- **长度关系**：`Content-length = strlen(content)`，只计 CGI 构造的 body 字符串，不计 server 或 CGI headers。[01:13:22-01:13:39] [课件: 22-netprog2.pptx p.51]
- **进程隔离条件**：同名环境变量存在于各自进程环境中，因而不同 CGI child 可携带不同请求参数。[01:10:12-01:10:25]

本段没有数学公式推导；上述是程序数据流与描述符重定向的逐步推导。

## 常见误解与辨析

- **误解：`QUERY_STRING` 是全机唯一全局变量，所以并发请求会覆盖。** 老师明确用进程环境隔离消除这一担心。[01:10:12-01:10:25]

- **误解：`execve` 后 stdout 会恢复为终端。** `dup2` 已把 stdout 接到客户端 descriptor；执行新程序后，`printf` 仍走这条连接。[01:11:56-01:12:21] [01:13:39-01:13:55]
- **误解：Tiny server 能独自填写动态 response 的全部 headers。** body 的实际长度和类型由 CGI program 掌握，因此由 child 生成对应 headers。[01:13:17-01:14:08] [课件: 22-netprog2.pptx p.51]

- **误解：机制简单或效率低就意味着 Web 构想价值小。** 老师的结论相反：关键贡献在于把已有简单构件组合成用户真正需要的系统。[01:16:18-01:17:44]
