## 学习目标

完成本讲后，应能够：

1. 用“多个线程是否引用同一变量实例”而不是声明位置来判定共享变量。
2. 区分线程概念内存模型与实际共享地址空间，并解释线程为何能访问另一线程栈上的对象。
3. 把 `cnt++` 展开为 `L_i/U_i/S_i`，逐状态复现正确交错与丢失更新交错。
4. 用 progress graph、trajectory、critical section、unsafe region 和 safe trajectory 表述并发正确性。
5. 精确说明 semaphore 的 `P(s)`、`V(s)` 操作及不变量 $s\ge0$。
6. 解释初值 1 的 mutex 如何通过 forbidden region 阻止轨迹进入 unsafe region，从而实现 mutual exclusion。

## 需要的先修知识

- 进程与线程、虚拟地址空间、线程栈、data segment 和寄存器上下文。
- `Pthread_create`、joinable/detached thread 与 `Pthread_join`。
- C 的全局变量、普通局部变量、函数内 `static` 变量及 `volatile`。
- x86-64 的 load、register update、store，以及内核调度、系统调用与定时器中断的基本概念。

## 核心概念与依赖关系

```text
共享地址空间
  -> 枚举变量实例与引用线程
  -> 识别共享变量
  -> 找出访问共享状态的临界区
  -> 枚举合法交错 / progress-graph trajectories
  -> 识别 unsafe region
  -> 用 P/V 约束轨迹
  -> semaphore invariant s >= 0
  -> forbidden region 包围 unsafe region
  -> mutual exclusion 与正确结果
```

关键依赖是：若没有先正确识别“同一实例被谁引用”，就无法确定哪个临界区应受同一个 mutex 保护；若把 `cnt++` 错当成原子语句，也看不到 unsafe region 的来源。

## 关键推导、例子与结论边界

### 两条必须会手算的丢失更新轨迹

- 第一条错误轨迹：

  $$H_1,L_1,U_1,H_2,L_2,S_1,T_1,U_2,S_2,T_2$$

  两线程各自从 0 得到 1，第二次 `S` 以 1 覆盖 1，最终 `cnt=1`。[00:28:45-00:30:21] [课件: 24-sync-basic.pptx p.12]

- 第二条错误轨迹：

  $$H_1,L_1,H_2,L_2,U_2,S_2,U_1,S_1,T_1,T_2$$

  两个 `L` 都先读到 0；写回顺序虽不同，最终仍是 `cnt=1`。[00:32:50-00:33:30] [课件: 24-sync-basic.pptx p.13]

### mutex 正确性推导

初值 $s=1$。第一个线程成功执行 P 后有 $s=0$，直到它执行 V 才恢复为 1。此时第二个线程若执行 P，理论上的下一格需要 $s=-1$；但 P 在 $s=0$ 时阻塞，所以该转移不可行。所有需要负值的状态形成 forbidden region，并包围原来的 unsafe region，故合法轨迹无法让两个临界区交错。[00:52:20-00:55:33] [课件: 24-sync-basic.pptx p.24]

### 内容边界

- 本讲证明的是 semaphore/mutex 对 `cnt` 临界区的互斥，不是在此优化锁粒度；`goodcnt` 比错误版本慢若干数量级。[00:51:49-00:52:10]
- 本讲只一句说明 counting semaphore 可计数事件或可用资源，并在结尾预告后续高级同步。[00:50:48-00:51:13] [00:56:01-00:56:19]
- **本讲没有教授 producer-consumer**：六段 transcript 与 25 页课件均没有有界缓冲区、producer/consumer 角色、`empty/full` 初始化或 P/V 次序。为保持“exactly as taught”，这里不从其他讲次补入这些内容。

# 第 1 段：从 fork-join 回答到线程共享模型

## 本段在整讲中的作用

老师先补答上一讲遗留的“为什么需要 joinable thread”，用 fork-and-join 并行模型说明 `join` 并非单纯的资源回收手段，而是阶段之间的同步边界。随后，他从线程共享全局状态的便利性转向风险：一旦多个线程共享资源，任意交错就可能造成错误，因此本讲要研究如何控制交错，即 synchronization。为了后续准确识别需要保护的对象，本段先建立“变量实例是否被多个线程引用”的共享判据，再说明线程概念内存模型与实际可访问性的差异，最后用 `sharing.c` 展示一个线程经全局指针访问另一线程栈对象的例子。[00:00:10-00:09:57] [课件: 24-sync-basic.pptx p.2] [课件: 24-sync-basic.pptx p.3] [课件: 24-sync-basic.pptx p.4]

## 教学展开

### 1. 补答：joinable thread 为什么有用

- [00:00:10-00:00:31] 老师回到上一讲的问题：为什么线程有时要保持 joinable，而不是一律 detached。他明确说自己上次的回答不够好，本段先作补充。
- [00:00:32-00:01:43] 他引入 **fork-and-join** 并行编程模型。程序由一系列阶段组成；每一阶段由 master 创建一批 worker，这一步是 fork。每个 worker 处理该阶段问题的一部分，例如把一个数据结构划分为多个块，让不同线程更新各自的块。master 必须等待全部 worker 完成，即逐一 join，之后才能进入下一阶段。
- [00:01:51-00:02:34] 科学计算是典型场景。老师以金属板热传导模拟为例：把空间域划分给多个 worker，每一阶段代表一个时间步；只有所有分区都算完当前时间步，模拟才能整体推进到下一个时间步。这个阶段屏障式需求解释了 joinable thread 的必要性。

### 2. 从共享的便利转向同步问题

- [00:02:42-00:03:17] 线程程序的优点是可以共享全局变量，但共享也会带来非预期后果。为了避免共享数据结构在错误交错下被破坏，需要控制各线程 flow 的交错；老师把这种控制过程定义为 **synchronization（同步）**。
- [00:03:17-00:03:24] 本讲目标随之确定：学习通过正确同步来编写正确线程程序的技术。
- [00:03:24-00:03:54] 老师先划定问题边界：若线程不共享资源，就无须关心它们如何交错。进程之间没有这种共享数据结构时，可以独立运行；问题从引入共享的那一刻开始。

### 3. 共享变量不能只按“全局/栈上”分类

- [00:03:54-00:04:14] 要讨论如何同步，必须先弄清 threaded C program 中“共享”的准确含义。老师否定了“全局变量都共享，栈变量都私有”这一过度简化。[课件: 24-sync-basic.pptx p.2]
- [00:04:14-00:04:38] 定义：变量 `x` 是共享的，当且仅当多个线程引用了 `x` 的某一个实例。若某个变量实例只有一个线程访问，它就不是共享实例；判断对象是“变量实例 + 引用它的线程集合”，而非只看声明位置。[课件: 24-sync-basic.pptx p.2]
- [00:04:38-00:05:04] 为应用这个定义，需要依次回答三个问题：
  1. 线程的内存模型是什么；
  2. 变量实例如何映射到内存；
  3. 哪些线程可能引用每个实例。
  老师说明接下来会按这个次序逐项处理。[课件: 24-sync-basic.pptx p.2]

### 4. 概念内存模型与实际模型的错位

- [00:05:04-00:05:57] 概念上，多个线程运行在同一进程上下文中。每个线程拥有独立的 thread ID、栈、栈指针、程序计数器、条件码和通用寄存器；线程共享其余进程上下文，包括代码、数据、堆、共享库等虚拟地址空间部分，以及打开的文件和已安装的信号处理程序。[课件: 24-sync-basic.pptx p.3]
- [00:05:57-00:06:15] 如果这种概念隔离被严格执行，推理会简单很多。实际中，寄存器值确实由内核为各线程分别保存，因此这一部分真正彼此分离。
- [00:06:15-00:06:38] 但线程共享同一地址空间，所以一个线程可以读写另一个线程的栈。栈在概念图上看似独立、私有，操作上却没有这种访问保护；老师指出，这种概念模型与操作模型的错位会造成困惑和错误。[课件: 24-sync-basic.pptx p.3]

### 5. `sharing.c`：经全局指针跨线程访问栈

- [00:06:38-00:07:21] 代码先定义全局变量 `char **ptr`。`main` 的栈上声明两元素数组 `msgs`，元素是 `"Hello from foo"` 和 `"Hello from bar"`，随后执行 `ptr = msgs`。因此，全局指针保存的其实是 main thread 栈中数组的地址。[课件: 24-sync-basic.pptx p.4]
- [00:07:21-00:08:07] `main` 循环创建两个 peer thread，入口均为 `thread`。Pthreads 会生成系统线程 ID；示例另外把循环索引强制转换为 `void *` 传入，作为自己的逻辑线程编号。老师强调这种传法看起来奇怪，但在这个具体例子中没有 race。创建后，main thread 调用 `Pthread_exit(NULL)`，让 peer threads 继续执行。[课件: 24-sync-basic.pptx p.4]
- [00:08:07-00:08:56] `thread` 取得参数中的逻辑编号 `myid`，声明函数内静态计数器 `cnt`，打印编号、`ptr[myid]` 指向的消息和前置递增后的 `cnt`。结果意图是 thread 0 打印 foo 消息，thread 1 打印 bar 消息。[课件: 24-sync-basic.pptx p.4]
- [00:08:59-00:09:39] 关键并不在打印，而在寻址路径：peer thread 访问全局变量 `ptr`，再由它间接访问 main thread 栈上的 `msgs`。老师明确说这是非常糟糕、绝不建议采用的实践；现实中可能因为程序员忘记某个指针保存的是栈地址而意外发生。[课件: 24-sync-basic.pptx p.4]
- [00:09:39-00:09:57] 有了“栈对象也可能跨线程被引用”的反例，老师转向第二个问题：变量的不同实例究竟如何映射到内存。下一段将复习链接阶段已经学过的相关知识。

## 概念、符号与推导

### 核心定义

- **同步**：控制各线程执行流的交错，使共享数据结构不会因不良交错而出错。[00:02:59-00:03:17]
- **共享变量判据**：变量 `x` 共享，当且仅当多个线程引用 `x` 的某一个实例。[00:04:14-00:04:38] [课件: 24-sync-basic.pptx p.2]
- **fork-and-join**：master 在一个阶段中 fork 出 workers，workers 并行完成各自部分；master join 全部 workers 后才进入下一阶段。[00:00:40-00:01:43]

### 推理链

1. 不共享资源时，线程交错不会破坏共同状态。[00:03:24-00:03:49]
2. 线程共享同一地址空间后，声明在某个线程栈上的对象仍可能被其他线程寻址。[00:06:15-00:06:33]
3. 因而不能由“全局变量/栈变量”二分法直接判断共享性。[00:04:05-00:04:14]
4. 必须先找出变量实例，再列出引用每个实例的线程，最后应用“多线程引用同一实例”的判据。[00:04:14-00:05:04]

本段没有数值公式推导；核心是一个当且仅当定义及其判定步骤。

## 例子与课堂提示

- **热传导模拟** [00:01:51-00:02:34]：用于说明为什么阶段式并行必须 join。每个 worker 负责一个空间分区，但所有分区都完成当前时间步后才能整体前进。
- **进程与线程对照** [00:03:24-00:03:49]：用于突出“共享”才是同步推理的起点。老师不是说进程永远没有通信，而是在本段讨论的独立地址空间模型下说明没有共享数据结构时不必控制这种交错。

## 本段在整讲中的作用

## 教学展开

### 1. 三类变量如何映射到内存

- [00:09:57-00:10:17] **全局变量**是在函数外声明的变量。链接器进行符号解析后，虚拟内存中每个全局变量恰有一个实例。[课件: 24-sync-basic.pptx p.5]
- [00:10:17-00:10:32] **局部变量**是在函数内声明、且没有 `static` 属性的变量。每个执行该函数的线程栈中，都有该局部变量自己的实例。[课件: 24-sync-basic.pptx p.5]
- [00:10:32-00:11:21] **局部静态变量**是在函数内以 `static` 声明的变量。它的名字作用域限于该函数，但虚拟内存中只有一个实例，存储方式与全局变量相同。若多个函数各自声明同名静态变量，编译器会把这些内部名字消歧，使它们仍是不同对象。[课件: 24-sync-basic.pptx p.5]

这里必须分开“作用域”和“实例数”：作用域限制源代码中哪些位置能直接用名字访问对象；它不意味着每个线程各有一份静态对象。[00:10:42-00:11:14]

### 2. 把规则应用到 `sharing.c`

- [00:11:21-00:11:46] `ptr` 是全局变量，所以整个地址空间中只有一个 `ptr` 实例，位于 data segment。[课件: 24-sync-basic.pptx p.6]
- [00:11:46-00:12:21] `i` 和 `msgs` 是 `main` 的非静态局部变量，因此各有一个实例，位于 main thread 的栈上。老师用 `i.m`、`msgs.m` 表示“变量 `i`/`msgs` 在 main stack 上的实例”。[课件: 24-sync-basic.pptx p.6]
- [00:12:21-00:12:53] `myid` 是 peer thread 入口函数中的非静态局部变量。两个 peer thread 各有一份：`myid.p0` 位于 peer thread 0 的栈，`myid.p1` 位于 peer thread 1 的栈。[课件: 24-sync-basic.pptx p.6]
- [00:12:53-00:13:12] `cnt` 是函数内静态变量，因此虚拟内存中只有一个实例，位于 data segment，与 `ptr` 这样的全局变量同类存储。[课件: 24-sync-basic.pptx p.6]

### 3. 按“实例 × 线程”做共享分析

老师没有凭声明形式猜共享性，而是列出每个实例，再逐个检查 main、peer 0、peer 1 是否引用它。[00:13:23-00:17:27]

| 变量实例 | main thread | peer thread 0 | peer thread 1 | 是否共享 |
| --- | --- | --- | --- | --- |
| `ptr` | 是 | 是 | 是 | 是 |
| `cnt` | 否 | 是 | 是 | 是 |
| `i.m` | 是 | 否 | 否 | 否 |
| `msgs.m` | 是 | 是，经 `ptr` 间接引用 | 是，经 `ptr` 间接引用 | 是 |
| `myid.p0` | 否 | 是 | 否 | 否 |
| `myid.p1` | 否 | 否 | 是 | 否 |

[课件: 24-sync-basic.pptx p.7]

- [00:13:48-00:14:19] `ptr` 的唯一实例由三个线程引用，所以共享。
- [00:14:19-00:14:39] `cnt` 不由 main 引用，但两个 peer thread 都引用同一个静态实例，所以共享。
- [00:14:39-00:14:51] `i.m` 只有 main 引用，所以不共享。
- [00:14:51-00:15:08] `msgs.m` 虽位于 main stack，却由 main 直接引用、两个 peer 经 `ptr` 间接引用，所以共享。
- [00:15:08-00:15:20] `myid.p0` 和 `myid.p1` 分别只由所属线程引用；名字相同不等于实例相同，因此都不共享。
- [00:15:35-00:17:27] 最终结论：`ptr`、`cnt`、`msgs` 共享；`i` 和 `myid` 不共享。[课件: 24-sync-basic.pptx p.7]

### 4. 改成 `static myid` 会发生什么

- [00:17:29-00:17:55] 学生问：若把 `myid` 声明成 `static`，第二个线程是否会覆盖它？老师回答会产生 race。原因是原来的 `myid.p0`、`myid.p1` 会变成单个静态实例，两个线程都读写它，结果取决于执行先后。这个反事实再次印证：共享性由实例数和引用关系共同决定。

### 5. 从共享分析转入 `badcnt.c`

- [00:17:55-00:18:20] 线程共享变量很方便，却可能引入“非常糟糕而且令人意外”的错误。老师转向一个名称已暗示有错的程序 `badcnt.c`。[课件: 24-sync-basic.pptx p.8]
- [00:18:21-00:18:59] 程序创建两个线程；每个线程都把同一个全局变量 `cnt` 递增相同的 `niters` 次。`cnt` 声明为 `volatile long`，初值为 0。[课件: 24-sync-basic.pptx p.9]
- [00:18:59-00:19:39] 老师询问 `volatile` 的含义，并在课堂语境中解释：它告诉编译器该值可能在当前代码之外改变，因此不要把它永久保存在寄存器中；访问时要从内存读取或写回内存。下一段和再下一段会显示，这种要求并没有让 `cnt++` 成为不可分割操作。

### 实例数规则

| 声明类别 | 实例规则 | 本例 |

| 函数外全局变量 | 虚拟内存中恰好一个实例 | `ptr` |

### 共享判定推导

对任一变量 `x`：

1. 枚举 `x` 的所有内存实例；
2. 对每个实例列出引用它的线程；
3. 只要至少一个实例被多个线程引用，`x` 就是共享变量。

因此，存储在栈上不推出“私有”，存储在 data segment 也不自动推出“被多个线程引用”。`msgs.m` 是前者的反例；只有 peer threads 引用的 `cnt` 则说明 main 是否引用并非必要条件。[00:13:23-00:17:27] [课件: 24-sync-basic.pptx p.7]

本段无数值公式推导；主要推导是从实例映射和引用矩阵应用共享变量的当且仅当定义。

# 第 3 段：`badcnt` 的指令模型与两种交错

> 时间范围：`00:19:55-00:29:52`
>
> 证据范围：本段课堂转录；同讲课件中的 `badcnt.c`、计数循环汇编和并发执行表。

## 本段在整讲中的作用

本段把“共享变量可能带来同步错误”落实为可逐步追踪的执行证据。老师先说明向线程传递 `&niters` 为什么在此处没有 race，强调 race 不能靠代码形状做模式匹配；然后运行 `badcnt` 展示同一输入有时正确、有时错误。为解释结果，他把一轮 `cnt++` 拆成 `L_i/U_i/S_i` 三条关键指令，以 `H_i`、`T_i` 表示其余头尾代码，并逐状态比较一个正确交错和一个即将产生丢失更新的交错。[00:19:55-00:29:52] [课件: 24-sync-basic.pptx p.9] [课件: 24-sync-basic.pptx p.10] [课件: 24-sync-basic.pptx p.11] [课件: 24-sync-basic.pptx p.12]

## 教学展开

### 1. 传 `&niters` 为什么这次是安全的

- [00:19:55-00:20:10] 两个新线程都执行 `thread`，参数是应执行迭代次数 `niters` 的地址。[课件: 24-sync-basic.pptx p.9]
- [00:20:10-00:20:26] 老师把它与上一讲并发服务器传递 connected file descriptor 地址的例子对照。虽然代码形状同样是“把局部变量地址传给线程”，这一次没有 race。
- [00:20:26-00:21:02] 原因在访问行为：worker 只读取 `niters`，main 也不再修改它；此前的 connected descriptor 会被 main 下一次 `accept` 改写，worker 与 main 因而竞争同一实例。
- [00:21:06-00:21:24] 老师由此提出重要方法论：不能 pattern matching 来判定 race，不能得出“把变量地址传给线程总是错误”这样的规则；必须结合谁读、谁写以及何时读写的上下文推理。

### 2. join 后检查预期值

- [00:21:26-00:21:55] main 向两个线程传入同一个只读迭代次数，然后分别 join。这里再次体现 joinable thread 的用途：只有确认两个 worker 都完成，main 才能检查最终计数。[课件: 24-sync-basic.pptx p.9]
- [00:21:57-00:22:20] 两个线程各递增 `niters` 次，因此预期结果是

  $$cnt_{expected}=2\times niters$$

  若实际 `cnt` 不等于该值，程序输出 `BOOM! cnt=...`；否则输出 `OK cnt=...`。[课件: 24-sync-basic.pptx p.9]
- [00:22:20-00:22:41] 线程例程先从参数地址读取 `niters` 到局部副本，再循环执行 `cnt++`，最后返回。源码看起来“非常无害”，这正是案例的教学张力。

### 3. 同一程序有时正确、有时错误

- [00:22:43-00:23:27] 老师指出线程并发中有许多细微问题。Linux 上以 `niters=10000` 运行，有时得到预期的 `20000`，下一次却可能得到 `13051` 一类完全错误的数。这说明错误依赖具体执行交错，而非确定地由输入映射为同一个错误结果。
- [00:23:27-00:23:46] 为回答“到底发生了什么”，必须下沉到线程计数循环的汇编，而不能把 C 语句 `cnt++` 当成一个原子动作。

### 4. 把一次递增拆成 `H_i/L_i/U_i/S_i/T_i`

- [00:23:46-00:24:02] `H_i`（Head）表示线程 `i` 进入循环并为迭代做准备的头部代码。
- [00:24:02-00:24:28] `L_i`（Load）把共享内存中的 `cnt` 加载到线程 `i` 上下文中的 `%rdx_i`。
- [00:24:28-00:24:37] `U_i`（Update）把该线程自己的 `%rdx_i` 加 1。
- [00:24:37-00:24:50] `S_i`（Store）把更新后的 `%rdx_i` 写回共享内存中的 `cnt`。
- [00:24:50-00:25:07] `T_i`（Tail）把循环中与这一轮 `cnt` 递增没有直接关系的其余尾部代码合并表示。[课件: 24-sync-basic.pptx p.10]

对应的关键汇编是：

```asm
movq cnt(%rip), %rdx   # L_i
addq $1, %rdx          # U_i
movq %rdx, cnt(%rip)   # S_i
```

[课件: 24-sync-basic.pptx p.10]

### 5. 建立并发状态表

- [00:25:13-00:25:34] 一般情况下不能假定某一种特定交错；任何顺序一致的合法交错都有可能发生，即使某个顺序看起来概率很低。[课件: 24-sync-basic.pptx p.11]
- [00:25:34-00:26:23] 老师先假定单核，一次只执行一条指令。执行表记录当前线程、该线程执行的 `H/L/U/S/T`、线程 1 的 `%rdx_1`、线程 2 的 `%rdx_2`，以及内存中共享 `cnt` 的值。内核为每个线程保存独立通用寄存器上下文，所以 `%rdx_1` 与 `%rdx_2` 可以不同。[课件: 24-sync-basic.pptx p.11]

### 6. 正确交错：两个临界区不重叠

初值 `cnt=0`。老师按以下次序走表：[00:26:31-00:28:14]

1. thread 1 执行 `H_1`，不改变 `cnt`；
2. `L_1`：`%rdx_1=0`；
3. `U_1`：`%rdx_1=1`；
4. `S_1`：把 1 写回，`cnt=1`；
5. 内核切到 thread 2，执行 `H_2`；
6. `L_2`：从内存读到 1，`%rdx_2=1`；
7. `U_2`：`%rdx_2=2`；
8. `S_2`：写回 2，`cnt=2`；
9. thread 2 执行 `T_2` 并结束这一轮；thread 1 再执行剩余 `T_1`。

轨迹可记作：

$$H_1,L_1,U_1,S_1,H_2,L_2,U_2,S_2,T_2,T_1$$

最终 `cnt=2`，符合两个线程各递增一次的预期。[课件: 24-sync-basic.pptx p.11]

### 7. 定义临界区并开始错误交错

- [00:28:14-00:28:33] 老师把直接实现 `cnt++` 的 `L_i,U_i,S_i` 三条指令合称为“相对于 `cnt` 的 critical section（临界区）”。正确交错中，thread 1 的整个临界区先完成，thread 2 才进入自己的临界区。[课件: 24-sync-basic.pptx p.11]
- [00:28:33-00:29:24] 第二个合法交错从 `cnt=0` 开始：thread 1 执行 `L_1,U_1`，所以 `%rdx_1=1`，但尚未 `S_1`；此时内核切到 thread 2。thread 2 执行 `L_2`，从仍为 0 的内存 `cnt` 读得 `%rdx_2=0`。thread 1 寄存器里的 1 对 thread 2 不可见，因为它尚未写回共享内存。[课件: 24-sync-basic.pptx p.12]
- [00:29:24-00:29:52] 内核切回 thread 1，`S_1` 把 1 写到 `cnt`，随后执行 `T_1`。之后再次调度 thread 2；本段恰在 thread 2 恢复的位置切断，`U_2/S_2` 和错误结论由下一段继续。

截至切分点，轨迹前缀为：

$$H_1,L_1,U_1,H_2,L_2,S_1,T_1,\ldots$$

此时状态是 `%rdx_1=1`、`%rdx_2=0`、`cnt=1`。[课件: 24-sync-basic.pptx p.12]

## 概念、符号与推导

### 指令记号

| 记号 | 含义 | 是否直接操作 `cnt` |
| --- | --- | --- |
| `H_i` | thread `i` 的循环头部 | 否 |
| `L_i` | `cnt -> %rdx_i` | 是，读 |
| `U_i` | `%rdx_i <- %rdx_i + 1` | 间接更新本地寄存器 |
| `S_i` | `%rdx_i -> cnt` | 是，写 |
| `T_i` | thread `i` 的循环尾部 | 否 |

[00:23:46-00:25:07] [课件: 24-sync-basic.pptx p.10]

### 临界区

相对于共享变量 `cnt`，一次 C 级 `cnt++` 对应的临界区是：

$$C_i=(L_i,U_i,S_i)$$

本段先通过执行表观察其作用；“为什么两个临界区不能交错”以及几何表示将在下一段正式展开。[00:28:14-00:29:52]

### 错误的必要执行事实

错误轨迹中，两线程都在任一线程完成最终有效写回前读到了旧值 0：

$$L_1: %rdx_1\leftarrow0,\qquad L_2: %rdx_2\leftarrow0$$

因此，后续两次本地加一都只能得到 1；第二次写回不会累计为 2，而会覆盖第一次写回。这个结论的最后两步在第 4 段完成。[00:28:45-00:29:52] [课件: 24-sync-basic.pptx p.12]

## 例子与课堂提示

- **传地址不等于必有 race** [00:20:10-00:21:24]：`&niters` 和 connected descriptor 地址外形相似，但前者只读且 main 不再修改，后者会被 main 的下一次 `accept` 改写。判断必须基于共享实例上的实际读写。
- **join 是检查前提** [00:21:26-00:21:55]：若不先 join，main 读 `cnt` 时 worker 可能尚未完成；那会把“何时检查”与“递增是否丢失”两个问题混在一起。
- **同一输入结果漂移** [00:22:57-00:23:27]：`20000` 与 `13051` 的对比用于证明调度交错会影响结果。
- **C 语句不是原子动作** [00:23:27-00:25:07]：必须把 `cnt++` 下沉为 load-update-store，才看得到可被切换的位置。
- **寄存器上下文彼此独立** [00:25:52-00:26:23]：`%rdx_1=1` 不会自动改变 `%rdx_2` 或内存 `cnt`；只有 `S_i` 才更新共享内存。

# 第 4 段：丢失更新、进度图与不安全区域

## 本段在整讲中的作用

## 教学展开

### 1. 完成第一条错误交错：1 覆盖 1

上一段结束时，thread 1 已经把自己的 `%rdx_1=1` 写入 `cnt`，thread 2 则保留早先从旧 `cnt=0` 读到的 `%rdx_2=0`。thread 2 恢复后：[00:29:52-00:30:21]

1. `U_2` 把 `%rdx_2` 从 0 更新为 1；
2. `S_2` 把这个 1 写回 `cnt`；
3. 内存中原本已经是 1，因此第二次写入只是“用 1 覆盖 1”；
4. 两个线程都完成后，`cnt=1`，而不是预期的 2。

完整错误轨迹是：

$$H_1,L_1,U_1,H_2,L_2,S_1,T_1,U_2,S_2,T_2$$

[课件: 24-sync-basic.pptx p.12]

- [00:30:21-00:30:46] 与上一段的正确轨迹相比，决定性差异是临界区的相对位置：正确轨迹中 thread 1 的整个 `L_1,U_1,S_1` 在 thread 2 的整个临界区之前；错误轨迹中两段临界区发生了交错。

### 2. `volatile` 没有把递增变成原子操作

- [00:30:49-00:31:29] 学生就 `volatile`/编译结果提问。老师先确认 `cnt` 的确声明为 `volatile`，然后把注意力放回实际生成的指令序列。
- [00:31:29-00:32:13] 编译器可能以不同方式生成代码；课堂示例采用“加载到寄存器、在寄存器中加一、写回内存”的三步序列。问题正是线程可以在完成这三步之前被中断，让另一个线程插入自己的同类序列。
- [00:32:21-00:32:50] 老师进一步澄清：`volatile` 阻止编译器把变量永久保留在寄存器中。它仍可暂时加载到寄存器计算，但之后必须写回；这与某些局部变量完全不分配栈空间、始终只留在寄存器中的优化不同。也就是说，`volatile` 约束编译器的存取选择，却不提供 mutual exclusion。

### 3. 第二条错误交错：另一种顺序，同样丢失一次更新

- [00:32:50-00:33:30] 老师给出另一种合法顺序：

  $$H_1,L_1,H_2,L_2,U_2,S_2,U_1,S_1,T_1,T_2$$

  thread 1 先执行 `L_1`，读到 0；thread 2 随后也执行 `L_2`，仍读到 0。thread 2 先更新并写回 1；thread 1 恢复后也只把自己的旧副本更新为 1，再写回 1。最终仍是 `cnt=1`。[课件: 24-sync-basic.pptx p.13]
- [00:33:30-00:33:37] 两个错误例子共同表明：问题不是某一条固定调度顺序，而是两个相对于同一共享变量的临界区发生交错。

### 4. 用进度图表示所有并发状态

- [00:33:37-00:34:05] 老师引入 **progress graph（进度图）**。对于 `n` 个线程，它是一个 `n` 维笛卡尔网格，用来刻画并发线程程序的离散执行状态空间。[课件: 24-sync-basic.pptx p.14]
- [00:34:05-00:34:28] 本例有两个线程，所以使用二维坐标系；横轴表示 thread 1 的顺序执行进度，纵轴表示 thread 2 的顺序执行进度。每条边对应执行一条指令。[课件: 24-sync-basic.pptx p.14]
- [00:34:28-00:35:22] 每个点表示两线程目前分别完成到哪一步。例如从原点沿横轴执行 `H_1` 后，点表示 thread 1 已完成 `H_1`、thread 2 尚未执行；点 `(L_1,S_2)` 表示 thread 1 已完成 `L_1`，thread 2 已完成 `S_2`。这里坐标记录的是“已完成”的指令，而不是即将执行的指令。[课件: 24-sync-basic.pptx p.14]

### 5. 合法状态转移组成轨迹

- [00:35:22-00:36:15] 执行就是从一个状态点转移到另一个状态点。时间不能倒退，因此不能向左或向下。在“一次只执行一条指令”的假设下也不能沿对角线移动，因为对角移动意味着两个线程同时各完成一条指令；下一状态只能向右或向上走一格。
- [00:36:15-00:37:03] 一连串合法状态转移组成 **trajectory（轨迹）**，刻画程序的一次可能并发执行。任何满足约束的转移序列都是可行轨迹，也就对应一组可能的线程交错。老师展示的例子是：

  $$H_1,L_1,U_1,H_2,L_2,S_1,T_1,U_2,S_2,T_2$$

  这正是前面得到错误结果的一条可行轨迹。[课件: 24-sync-basic.pptx p.15]

### 6. 临界区的笛卡尔积形成不安全区域

- [00:37:10-00:37:38] 每个线程的 `L_i,U_i,S_i` 都构成相对于共享变量 `cnt` 的临界区。相对于同一个共享变量的临界区内部指令不应彼此交错。[课件: 24-sync-basic.pptx p.16]
- [00:37:38-00:38:20] 在二维进度图中，把两个临界区对应的状态范围组合起来，会得到 **unsafe region（不安全区域）**：其中的点表示两个临界区正在交错。本例的不安全区域包含四个状态点；轨迹只要触及其中一个点，就发生临界区交错并得到错误计数。[课件: 24-sync-basic.pptx p.16]
- [00:38:17-00:38:27] 若轨迹不进入任何不安全区域，就称其为 **safe trajectory（安全轨迹）**。课件给出的形式化说法是：轨迹安全，当且仅当它不进入任何不安全区域；对于本例的 `cnt`，轨迹正确，当且仅当它安全。[课件: 24-sync-basic.pptx p.17]
- [00:38:27-00:38:56] 安全轨迹可以贴着不安全区域边缘经过。例如某点只表示 thread 1 完成了 `H_1`，尚未进入 `L_1,U_1,S_1` 临界区，所以仍然安全；必须按“点表示哪些指令已经完成”来判断边界。[课件: 24-sync-basic.pptx p.17]
- [00:39:00-00:39:20] 另一条轨迹进入不安全区域，即使很快离开，也已经包含会破坏结果的交错，因此是不安全轨迹。

## 概念、符号与推导

### 进度图

对于 `n` 个线程，进度图是 `n` 维离散笛卡尔网格；第 `i` 个轴按 thread `i` 的顺序指令排列。状态点

$$(I_1,I_2,\ldots,I_n)$$

表示每个线程已经完成到相应指令。一次只执行一条指令时，合法转移只能沿某一个轴向前一步。[00:33:37-00:36:15] [课件: 24-sync-basic.pptx p.14]

### 临界区、不安全区域与安全性

- 相对于 `cnt` 的临界区：$C_i=(L_i,U_i,S_i)$。
- 不安全区域：多个线程相对于同一共享变量的临界区发生交错的状态集合。[00:37:10-00:38:12]
- 安全轨迹：不进入任何不安全区域的轨迹。[课件: 24-sync-basic.pptx p.17]
- 本例结论：

  $$trajectory\ is\ correct\ (w.r.t.\ cnt)\iff trajectory\ is\ safe$$

  [课件: 24-sync-basic.pptx p.17]

### 丢失更新的本质

两条错误轨迹虽然调度位置不同，却都满足：`L_1` 与 `L_2` 在能让另一个线程读到新值的写回之前完成，因此两个线程都从 0 计算出 1。后写入的 1 覆盖先写入的 1，一次逻辑更新丢失。[00:29:52-00:33:30]

# 第 5 段：互斥目标与信号量 P/V 语义

> 时间范围：`00:39:43-00:49:36`
>
> 证据范围：本段课堂转录；同讲课件中的互斥、信号量、C API、`badcnt.c` 与互斥用法页面。

## 本段在整讲中的作用

上一段把同步问题表述为“如何阻止轨迹进入 unsafe region”。本段先把答案改写为 mutual exclusion：相对于同一共享变量的临界区不能同时进行。老师解释为什么错误在小迭代数下不易复现、却不能据此依赖调度，然后引入 Dijkstra 的 semaphore 作为经典通用解法。他逐条规定 `P(s)`、`V(s)` 的阻塞、唤醒和原子语义，得到信号量不变量 $s\ge 0$，再映射到 Pthreads 的 `sem_init/sem_wait/sem_post`。结尾开始说明如何以初值 1 的信号量修复 `badcnt`。[00:39:43-00:49:36] [课件: 24-sync-basic.pptx p.18] [课件: 24-sync-basic.pptx p.19] [课件: 24-sync-basic.pptx p.20] [课件: 24-sync-basic.pptx p.21] [课件: 24-sync-basic.pptx p.22]

## 教学展开

### 1. 目标改写为对临界区的互斥访问

- [00:39:43-00:40:02] 要保证安全轨迹，就必须同步两个线程；等价地说，要保证对临界区的 **mutually exclusive access（互斥访问）**。[课件: 24-sync-basic.pptx p.18]
- [00:40:02-00:40:29] 一旦某线程开始执行相对于某共享变量的临界区，就不能让另一个线程插入执行相对于同一共享变量的对应临界区。这里互斥的关联对象是“共享变量（或共同状态）及其临界区”，而非笼统禁止所有线程并发。

### 2. 有时跑对不构成正确性保证

- [00:40:35-00:41:24] 学生问得到正确轨迹的可能性。老师回答：程序有时会对，通常会错，具体取决于内核调度；程序员不能假设某一种调度。如果断言永远不会得到正确答案，同样是在错误地假定内核总安排 unsafe trajectory。偶尔正确只是“走运”。
- [00:41:24-00:41:34] 实验中往往要把 `niters` 设得较大，才容易触发错误。
- [00:41:34-00:42:09] 老师解释调度机会：线程通常在异常把控制权交回内核时才可能被换出。这里列举两类来源：程序执行系统调用而 trap 进内核，或定时器中断发生，把控制权转给内核。
- [00:42:09-00:43:26] 定时器以毫秒量级间隔触发。若每线程只做一两次非常短的递增，又没有系统调用，定时器恰好落在 `L/U/S` 小窗口内的概率很低。随着 `niters` 增大，循环覆盖更多定时器时刻，在关键序列中被切换的机会也增加。但概率解释不能替代同步，因为任何合法调度仍须被程序正确处理。

### 3. 引入 Dijkstra 的信号量

- [00:43:36-00:44:07] 老师把经典解法追溯到 1960 年代的荷兰计算机科学家 Edsger Dijkstra。信号量是最早的经典方案，基础、通用，后来还有许多变体；本讲选择它来解决互斥问题。[课件: 24-sync-basic.pptx p.18]
- [00:44:07-00:44:41] **semaphore（信号量）**被定义为非负的全局整数同步变量，由两个称为 `P` 和 `V` 的操作操纵。字母来自荷兰语，但课堂要求重点掌握操作语义，而不是词源。[课件: 24-sync-basic.pptx p.19]

### 4. `P(s)`：原子测试并递减，或阻塞

- [00:44:45-00:45:16] 若 $s\ne0$，`P(s)` 把 `s` 减 1 并立即返回。检查“是否非零”和减 1 是一个不可分割的原子操作，不能在两者之间被其他线程插入。[课件: 24-sync-basic.pptx p.19]
- [00:45:16-00:45:43] 若 $s=0$，`P(s)` 不把它减成负数，而是挂起当前线程。线程保持阻塞，直到某个 `V` 操作使 `s` 非零并重启它。[课件: 24-sync-basic.pptx p.19]
- [00:45:43-00:46:04] 被重启后，该线程完成原来的 `P`：把 `s` 减 1，然后才把控制权返回调用者。

可按课堂语义写成：

```text
P(s):
    if s != 0, atomically decrement s and return
    else suspend until restarted by V;
         then decrement s and return
```

### 5. `V(s)`：原子递增并唤醒一个等待者

- [00:46:04-00:46:15] `V(s)` 把 `s` 加 1；与前面非原子的 `cnt++` 不同，这个递增本身是原子的。[课件: 24-sync-basic.pptx p.19]
- [00:46:15-00:46:46] 递增后，`V` 检查是否有线程因在 $s=0$ 时执行 `P` 而阻塞。老师用内核维护等待队列来帮助理解。
- [00:46:46-00:47:10] 若存在等待者，`V` 恰好重启其中一个。选择次序不确定，程序不能假设会唤醒哪一个；被选中的线程随后完成自己的 `P`，即把 `s` 减 1。[课件: 24-sync-basic.pptx p.19]

可按课堂语义写成：

```text
V(s):
    atomically increment s
    if threads are blocked in P(s), restart exactly one
```

### 6. 信号量不变量

- [00:47:10-00:47:35] 老师提醒：P/V 规则看起来简单，但初学时并不容易形成直觉。
- [00:47:35-00:48:07] 这些语义施加了关键的 **semaphore invariant（信号量不变量）**：

  $$s\ge0$$

  当 `s=0` 时 `P` 阻塞而不是继续递减，因此由合法 P/V 操作控制的信号量永远不会成为负数。老师预告，这个看似普通的性质将用来强制临界区互斥。[课件: 24-sync-basic.pptx p.19]

### 7. Pthreads API 与 CS:APP 包装

- [00:48:14-00:48:38] Pthreads 提供三个对应操作：`sem_init` 把信号量初始化为任意非负值，`sem_wait` 实现 P，`sem_post` 实现 V。[课件: 24-sync-basic.pptx p.20]

```c
#include <semaphore.h>

sem_init(&s, 0, val);  /* s = val, val >= 0 */
sem_wait(&s);          /* P(s) */
sem_post(&s);          /* V(s) */
```

- [00:48:38-00:48:52] CS:APP 的 `csapp.h` 又提供名为 `P`、`V` 的包装函数；老师称这种命名“old school”，同时指出它更紧凑。[课件: 24-sync-basic.pptx p.20]

### 8. 开始修复 `badcnt`

- [00:48:52-00:49:21] 老师回到会产生错误计数的 `badcnt.c`，提出如何用 semaphore 修复。[课件: 24-sync-basic.pptx p.21]
- [00:49:21-00:49:36] 基本起点是创建一个初值为 1、用于提供互斥的信号量；这种用途下的对象称为 **mutex**。本段在老师追溯该命名的早期论文时切分，具体包围临界区的方法由下一段继续。[课件: 24-sync-basic.pptx p.22]

## 概念、符号与推导

### 信号量与 P/V

- `s`：非负全局整数同步变量。[00:44:07-00:44:29]
- `P(s)`：当 $s>0$ 时，以原子方式完成“测试并减 1”；当 $s=0$ 时阻塞，待 `V` 唤醒后再减 1。[00:44:45-00:46:04]
- `V(s)`：以原子方式把 `s` 加 1；若有 `P` 等待者，恰好唤醒一个，选择顺序未指定。[00:46:04-00:47:10]
- 不变量：

  $$s\ge0$$

  [00:47:35-00:48:07] [课件: 24-sync-basic.pptx p.19]

### 为什么不变量成立

1. 初始化要求 $s\ge0$。[00:48:14-00:48:34]
2. `V` 只做原子加一，不会制造负值。[00:46:04-00:46:15]
3. `P` 只在 $s>0$ 时递减；$s=0$ 时阻塞，不执行 $0\to-1$。[00:44:45-00:45:43]
4. 因此所有合法 P/V 状态都满足 $s\ge0$。下一段会把“不允许到达 $s=-1$”解释成进度图中的 forbidden region。

### 调度概率与正确性的边界

增大 `niters` 会提高定时器切换落入脆弱窗口的机会，但这只是复现错误的概率解释。正确并发程序必须对所有允许的交错成立，不能把“这次没有被切换”当成同步保证。[00:40:43-00:43:26]

## 例子与课堂提示

- **短循环不易复现** [00:41:24-00:43:26]：用于解释为什么 race 可能潜伏；不是证明短循环安全。
- **系统调用与定时器中断** [00:41:34-00:42:49]：用于说明控制何时回到内核、线程何时可能被重新调度。
- **等待队列心智模型** [00:46:15-00:47:10]：可以想象内核保存因 `P(s)` 阻塞的线程队列，但 `V` 选择哪一个没有可依赖的顺序。
- **原子性对照** [00:46:04-00:46:15]：`V` 的递增按定义原子，而普通 `cnt++` 在课堂汇编中是可交错的三步。
- **“恰好一个”** [00:46:33-00:46:52]：一次 `V` 在有等待者时只重启一个，不是广播唤醒所有线程。

# 第 6 段：用 mutex 包围临界区及其进度图证明

> 时间范围：`00:49:36-00:56:21`
>
> 证据范围：本段课堂转录；同讲课件中的互斥用法、`goodcnt.c`、mutex 正确性进度图和总结页面。

## 本段在整讲中的作用

本段把上一段的 P/V 原语真正应用到 `badcnt`：为受保护的共享状态配置初值 1 的 mutex，以 `P` 和 `V` 包围 `cnt++` 的临界区，得到始终正确但明显更慢的 `goodcnt.c`。更重要的是，老师没有只停在代码模式，而是回到进度图证明其正确性：信号量不变量禁止 $s$ 从 0 变成 -1，由此形成包围 unsafe region 的 forbidden region，所有可行轨迹都无法进入错误区域。课堂最后只预告下一讲会研究更高级、更有趣的同步用法；本讲没有讲授 producer-consumer 的缓冲区、计数信号量配置或操作序列。[00:49:36-00:56:21] [课件: 24-sync-basic.pptx p.22] [课件: 24-sync-basic.pptx p.23] [课件: 24-sync-basic.pptx p.24] [课件: 24-sync-basic.pptx p.25]

## 教学展开

### 1. 为共享状态关联初值 1 的 mutex

- [00:49:36-00:49:57] 老师提出基本规则：为程序中每个需要保护的共享变量关联一个唯一 mutex，并把它初始化为 1。课件把适用范围写得更完整：也可以由一个 mutex 保护一组相关的共享变量。本例只关心 `cnt`，所以创建一个名为 `mutex` 的信号量。[课件: 24-sync-basic.pptx p.22]
- [00:49:57-00:50:16] 对每一个相对于 `cnt` 的临界区，先调用 `P(mutex)`，再执行临界区，最后调用 `V(mutex)`：

```text
P(mutex)
    critical section with respect to cnt
V(mutex)
```

[课件: 24-sync-basic.pptx p.22]

### 2. 术语表

- [00:50:16-00:50:29] **binary semaphore（二元信号量）**：值始终是 0 或 1 的信号量。
- [00:50:23-00:50:29] **mutex（互斥量）**：用于提供 mutual exclusion 的二元信号量。
- [00:50:29-00:50:37] 对 mutex 执行 `P` 称为 **locking**。
- [00:50:37-00:50:41] 对 mutex 执行 `V` 称为 **unlocking** 或 **releasing**。
- [00:50:41-00:50:48] 线程 **holding a mutex**，表示它已经锁定但尚未释放该 mutex。
- [00:50:48-00:51:13] **counting semaphore（计数信号量）**用于计数系统中的事件或可用资源，其非负值常可大于 1；这与本例以 0/1 表示互斥占用不同。[课件: 24-sync-basic.pptx p.22]

### 3. `goodcnt.c`：在 C 代码中包围临界区

- [00:51:20-00:51:43] 修复版称为 `goodcnt.c`。先声明保护 `cnt` 的 `sem_t mutex`，再执行 `Sem_init(&mutex, 0, 1)`，使其初值为 1。[课件: 24-sync-basic.pptx p.23]
- [00:51:36-00:51:49] C 语句 `cnt++` 在本例中由 `L/U/S` 三条汇编指令实现；代码在每次递增前后加入 P/V：

```c
volatile long cnt = 0;
sem_t mutex;

Sem_init(&mutex, 0, 1);

for (i = 0; i < niters; i++) {
    P(&mutex);
    cnt++;
    V(&mutex);
}
```

[课件: 24-sync-basic.pptx p.23]

- [00:51:49-00:52:10] 加入互斥后，程序总能得到正确值；课件演示两次 `./goodcnt 10000` 都输出 `OK cnt=20000`。代价是 P/V 有开销，修复版比错误的 `badcnt.c` 慢若干数量级。正确性不是免费的，但不能以速度为由保留 race。[课件: 24-sync-basic.pptx p.23]

### 4. 在进度图中加入 P/V

- [00:52:10-00:52:36] 老师追问“为什么 mutex 有效”，并把 `P(s)`、`V(s)` 装饰到两个线程的进度图：每个线程先执行 P，再进入 `L/U/S` 临界区，退出后执行 V。[课件: 24-sync-basic.pptx p.24]
- [00:52:36-00:53:03] P 使信号量减一，V 使其加一。原点处初始化 $s=1$。[课件: 24-sync-basic.pptx p.24]
- [00:53:11-00:53:36] 若先只沿 thread 1 的轴前进：完成 `H_1` 后仍有 $s=1$；执行 `P_1(s)` 时，P 看到 1，原子减为 0 并进入临界区；从 `L_1` 到 `S_1` 期间一直保持 $s=0$；完成 `V_1(s)` 后恢复为 $s=1$。

### 5. $s\ge0$ 把第二个线程挡在临界区外

- [00:53:36-00:54:13] 老师考察一个企图让两线程同时处在临界区的状态路径：thread 1 已执行 P 并完成 `L_1`，此时 $s=0$；thread 2 执行 `H_2` 后尝试 `P_2(s)`。
- [00:54:13-00:54:28] 若把 P 误想成无条件减一，下一状态会是 $s=-1$；但这个状态不可能发生，因为当 $s=0$ 时，P 的语义是阻塞，不是递减。[课件: 24-sync-basic.pptx p.24]
- [00:54:28-00:55:00] 因而，从 $s=0$ 到 $s=-1$ 的状态转移被禁止。进度图中所有需要 $s=-1$ 的点都不可达，构成 **forbidden region（禁区）**。[课件: 24-sync-basic.pptx p.24]
- [00:55:00-00:55:33] 这个禁区包围原来的 unsafe region。任何合法轨迹都不能进入禁区，也就不能进入其中的不安全区域；两个临界区不会交错，于是实现 mutual exclusion。这是老师给出的 P/V 能提供互斥访问的根本理由。[课件: 24-sync-basic.pptx p.24]

## 概念、符号与推导

### mutex 状态含义

初值为 1 的 mutex `s` 在本例中只有两个可达值：

| `s` | 含义 |
| --- | --- |
| 1 | 没有线程持有 mutex，某个线程可成功执行 P |
| 0 | 某线程已经执行 P、尚未执行 V；其他线程的 P 必须阻塞 |

[00:52:58-00:54:28] [课件: 24-sync-basic.pptx p.24]

### 互斥证明链

1. 初始 $s=1$。[00:52:58-00:53:03]
2. thread 1 的 `P_1(s)` 原子地执行 $1\to0$，然后 thread 1 进入临界区。[00:53:11-00:53:29]
3. 在 thread 1 执行 `V_1(s)` 前，$s$ 保持 0。[00:53:25-00:53:36]
4. 此时 thread 2 的 `P_2(s)` 不能执行 $0\to-1$，而必须阻塞。[00:54:01-00:54:28]
5. 所有标记为 $s=-1$ 的状态不可达，形成 forbidden region。[00:54:28-00:55:00]
6. forbidden region 包围 unsafe region，故可行轨迹无法让两个 `L/U/S` 临界区交错。[00:55:00-00:55:33]
7. thread 1 执行 V 后 $0\to1$，另一个线程才可能完成 P 并进入临界区。[00:53:29-00:53:36]

所以：

$$s\ge0\Longrightarrow \text{forbidden region is unreachable}
\Longrightarrow \text{unsafe region is unreachable}
\Longrightarrow \text{mutual exclusion}$$

[课件: 24-sync-basic.pptx p.24]

### 正确性与性能边界

P/V 包围临界区保证本例结果正确，但每次 `cnt++` 都增加同步开销，导致 `goodcnt` 比 `badcnt` 慢若干数量级。老师在本讲只建立正确性机制，没有在此优化锁粒度或并行性能。[00:51:49-00:52:10]
