## 关键推导、例子与边界

### 1. Unix 文件模型推出窄接口

长度为 $m$ 的文件表示为：

$$
B_0, B_1, \ldots, B_k, \ldots, B_{m-1}
$$

内核不必理解 JPEG、目标代码或文本行的应用语义。设备与 socket 也进入文件抽象，因此磁盘、终端和网络可复用 `open/close/read/write`。但统一的是接口，不是能力：终端与 socket 不支持像普通磁盘文件那样任意 `lseek`。[00:03:53–00:07:22] [课件: 16-io.pptx p.3] [课件: 16-io.pptx p.4]

### 2. `open/read/write/close` 的状态与返回值

```text
pathname + flags --open--> fd
fd --close--> 解除一次打开引用
read(fd, buf, n)  : file → memory，推进 file position
write(fd, buf, n) : memory → file，推进 file position
```

对 `read`：[课件: 16-io.pptx p.12]

| 返回值 | 语义 |
|---:|---|
| `< 0` | 错误 |
| `= 0` | EOF |
| `> 0` | 实际读到字节数，可小于请求量 |

对 `write`，负值是错误，非负值是实际写出量；小于请求量仍可能是合法 short write。对 `open`，负值表示失败；对 `close` 也必须检查返回值。不能用一条统一的“零成功/非零失败”规则套所有系统调用。[00:17:50–00:25:41]

### 3. EOF 与 short count 的两次调用例子

文件剩 100 字节，调用 `read(..., 200)`：[00:32:15–00:32:43]

1. 第一次返回 100，交付最后 100 字节。
2. 再读一次返回 0，明确指示 EOF。

所以正 short count 不等于已经获得 EOF 信号；0 不是错误负值。终端按行交付、网络按可用块交付也会造成 short count。[课件: 16-io.pptx p.15]

### 4. `rio_readn` 的循环不变量

```c
size_t nleft = n;
char *bufp = usrbuf;

while (nleft > 0) {
    if ((nread = read(fd, bufp, nleft)) < 0) {
        if (errno == EINTR)
            nread = 0;
        else
            return -1;
    }
    else if (nread == 0)
        break;
    nleft -= nread;
    bufp += nread;
}
return n - nleft;
```

[课件: 16-io.pptx p.19]

循环始终保持：`nleft` 是未完成量，`bufp` 指向下一待填字节。若一次读到 $k>0$ 字节，两者分别减/加 $k$。终止只因读满、不可恢复错误或 EOF；因此返回量自然是 $n-\text{nleft}$。`EINTR` 被当作可重试中断，其他错误返回 `-1`。

### 5. 缓冲造成两个进度位置

一次大 `read` 后，内核 current file position 已越过整块数据；应用可能只消费其中几个字节。`rio_bufptr` 指向下一未读字节，`rio_cnt` 给出尚未交付的长度。[课件: 16-io.pptx p.22] [课件: 16-io.pptx p.23]

```text
应用已消费 | 内部缓冲未读 | 尚未从文件读取
            ↑ rio_bufptr   ↑ kernel current file position
            <--- rio_cnt -->
```

这解释两个边界：缓冲减少系统调用；同一描述符上不能交错 RIO 缓冲读取与绕开该缓冲的 `rio_readn`，也不能把标准 I/O 与 RIO 两套私有缓冲随意混用。[课件: 16-io.pptx p.21] [01:05:59–01:06:17]

### 6. 目录与 metadata 分工

目录是文件系统按专门格式解释的文件，目录项把 filename 映射到 file，`.` 指自身，`..` 指父目录。目录层次以 `/` 为根；绝对路径从根开始，相对路径从进程 `cwd` 开始。[课件: 16-io.pptx p.7]–[课件: 16-io.pptx p.9]

文件正文是 data；类型、保护、所有者、大小和时间是内核维护的 metadata。调用者分配 `struct stat`，`stat(path,&buf)` 填入结果，随后用 `S_ISREG`、`S_ISDIR`、`S_IRUSR` 等宏或掩码解释 `st_mode`。[00:46:02–00:51:08] [课件: 16-io.pptx p.26] [课件: 16-io.pptx p.27]

边界：课件的 `st_ctime` 注释是 “Time of last change”，不能因口述中的 “created” 而把它记作创建时间。

### 7. 三表模型决定“共享什么”

| 结构 | 作用域 | 保存/指向 |
|---|---|---|
| descriptor table | 每进程一张 | fd 条目指向 open file entry |
| open file table | 系统共享 | file position、`refcnt`、打开状态，指向 v-node |
| v-node table | 系统共享 | 文件类型、大小、访问属性等文件本体信息 |

[课件: 16-io.pptx p.28]

三种关键构造：[课件: 16-io.pptx p.29]–[课件: 16-io.pptx p.34]

| 操作 | descriptor table | open file entry | file position |
|---|---|---|---|
| 同一路径 `open` 两次 | 两个 fd | 两个不同项，共同指向一个 v-node | 独立 |
| `fork` | 父子各一张表 | 对应条目指向同一项，`refcnt+1` | 共享 |
| `dup2(4,1)` | fd 1 复制 fd 4 的条目 | 两个 fd 指向同一项 | 共享 |

### 8. 重定向的引用计数推导

对 shell 子进程执行 `ls > foo.txt`：[课件: 16-io.pptx p.32]–[课件: 16-io.pptx p.34]

1. `open("foo.txt", ...)`，假设返回 fd 4。
2. `dup2(4,1)` 先解除 fd 1 对终端打开项的引用，再让 fd 1 复制 fd 4 的表项。
3. 目标文件打开项现在被 fd 1、fd 4 引用，`refcnt=2`。
4. `close(4)` 后 `refcnt=1`，fd 1 仍有效。
5. `exec` 启动 `ls`；程序照常写 fd 1，数据进入 `foo.txt`。

`dup2(oldfd,newfd)` 的方向是“让 `newfd` 访问 `oldfd` 当前访问的对象”。

### 9. 逐字节与缓冲演示的对照

- 逐字节 `Read/Write` 功能正确，但每个字符进入内核；老师估计一次系统级调用约 20,000–40,000 时钟周期。[00:25:49–00:27:44] [课件: 16-io.pptx p.14]
- RIO 按行复制把一行交给一次可靠写，`strace` 不再显示逐字符写。[00:43:59–00:45:18] [课件: 16-io.pptx p.24]
- 标准 I/O 中六次 `printf` 产生一次 `write(1,"hello\n",6)`，说明 stream 缓冲同样聚合系统调用。[01:03:26–01:04:49] [课件: 16-io.pptx p.40]

### 10. 三类 I/O 的选择边界

| 场景 | 首选 | 原因 |
|---|---|---|
| 日常磁盘文件、终端 | 标准 I/O | 高层、缓冲、接口丰富、处理 short count |
| signal handler | Unix I/O | 低层函数 async-signal-safe |
| 网络 socket | RIO | 显式处理网络 short count，避免标准 stream/socket 限制 |
| 极少数绝对性能需求 | Unix I/O | 最低额外开销，但应用负责所有细节 |

[课件: 16-io.pptx p.43]–[课件: 16-io.pptx p.45]

二进制数据不得交给会特殊解释 `0x0A` 的行函数或把 `0x00` 当终止符的字符串函数；使用 `rio_readn/rio_readnb` 一类字节接口。[课件: 16-io.pptx p.46]

## 复习摘要

- 文件描述符不是 pathname、指针或全系统文件号，而是进程 descriptor table 的小整数索引。
- `0/1/2` 分别是标准输入、输出、错误；代码使用符号名而不是裸数字。
- 每个系统调用都检查其自己的返回约定，包括看似无害的 `close`。
- `read` 返回 0 才表示 EOF；正 short count 是实际完成量，不是错误。
- `write` 也可能 short count，尤其在网络 socket 上；剩余数据必须继续发送。
- RIO 通过循环处理 short count，通过内部缓冲减少系统调用；两类机制解决不同问题。
- `stat` 查询 metadata，不读取文件正文；`st_mode` 同时含类型和保护位。
- 两次 `open` 同一文件得到独立位置；`fork` 与 `dup2` 可让多个描述符共享同一位置。
- `close` 删除一条引用；只有 open file entry 的 `refcnt` 归零，底层打开状态才结束。
- 标准 I/O stream 是 fd 加内存缓冲；多次小操作可合成一次底层系统调用。
- 同一描述符不要混用彼此不知情的缓冲包。
- 熟悉的文本/字符串函数可能破坏二进制数据，函数选择必须匹配数据模型。

## 综合掌握检查

1. **问：Unix 为什么能用同一组 `read/write` 处理磁盘与 socket？**  
   **答：** 它把普通文件、设备和网络连接统一映射到文件抽象；差异由具体文件类型和能力保留。[00:03:53–00:07:22]
2. **问：`read(fd,buf,512)` 返回 100、0、-1 各表示什么？**  
   **答：** 100 是实际读到的 short count，0 是 EOF，-1 是错误。[课件: 16-io.pptx p.12]
3. **问：`rio_readn` 何时可返回小于请求量的非负值？**  
   **答：** 在读满前遇到 EOF 时；一般底层 short read 会被内部循环继续处理。[课件: 16-io.pptx p.18] [课件: 16-io.pptx p.19]
4. **问：缓冲读取后为什么内核位置可能领先应用位置？**  
   **答：** 一次底层 `read` 已把整块移入用户态并推进内核位置，应用尚未消费的部分仍在内部缓冲。[课件: 16-io.pptx p.22]
5. **问：`stat` 和 `read` 取得的数据有什么根本区别？**  
   **答：** `read` 取得文件正文的字节；`stat` 填充内核维护的文件属性结构。[课件: 16-io.pptx p.26]
6. **问：同一 pathname `open` 两次后，为什么两个 fd 的位置独立？**  
   **答：** 每次 `open` 分配独立 open file entry，各自保存 file position，虽指向同一 v-node。[课件: 16-io.pptx p.29]
7. **问：`fork` 后父读一字节，子下一次从哪里读？**  
   **答：** 从父读后推进的位置继续，因为父子描述符条目共享同一 open file entry。[课件: 16-io.pptx p.31]
8. **问：`dup2(4,1)` 后关闭 4，为什么 1 仍有效？**  
   **答：** 复制后两条描述符引用同一打开项；关闭 4 只递减一次引用，fd 1 的引用仍在。[00:59:44–01:01:33]
9. **问：标准 I/O 与 RIO 为什么不能在同一描述符上混用？**  
   **答：** 两者各自预取并维护私有缓冲，一个看不到另一个已从内核取走的数据。[01:05:59–01:06:17]
10. **问：网络 socket 为什么选 RIO 而不是标准 I/O？**  
    **答：** 网络 short count 常见，RIO 为此提供可靠接口；标准 stream 与 socket 的限制交互不良。[课件: 16-io.pptx p.44] [课件: 16-io.pptx p.45]
11. **问：为何 `strlen` 不能度量任意网络包长度？**  
    **答：** 它在首个 `0x00` 停止，而二进制包中的零字节不一定是数据结束。[课件: 16-io.pptx p.46]
12. **问：解决 p.49/p.50 描述符题时第一步是什么？**  
    **答：** 为每次 `open` 画独立打开项，再按 `dup2`、`fork` 和实际读序逐步更新箭头、refcnt 与 file position，不能凭 fd 数字猜。[01:10:08–01:10:38]

## 教学展开

### 1. 从课程任务说明为什么要学低层 I/O [00:00:13–00:02:18]

1. 学生已经使用过 `printf`、`scanf` 一类标准库函数，但本讲首先研究更低一层、直接接到操作系统的 I/O。[00:00:23–00:00:45]

### 2. 预告整讲的四条内容线 [00:02:22–00:03:44]

1. **Unix 低层 I/O**：Unix 及相关操作系统直接支持的接口。
2. **RIO**：把低层 I/O 封装成 robust I/O；老师建议阅读其高质量且篇幅不大的源码，以观察错误和异常条件的处理。[00:02:33–00:03:25]
3. **文件表示**：理解文件背后的数据结构，以及它们如何支撑共享、重定向等行为。
4. **缓冲 I/O**：回到 `printf`、`scanf` 所属的较高层接口，解释它们如何建立在低层 I/O 之上。[课件: 16-io.pptx p.2]

### 3. 把“文件”定义为统一的字节序列 [00:03:53–00:05:48]

老师先给出 Unix 设计的核心：文件在操作系统看来就是一串字节，内核通常不理解文件内部更细的应用结构。若文件有 $m$ 个字节，可写为：

$$
B_0, B_1, \ldots, B_k, \ldots, B_{m-1}
$$

[课件: 16-io.pptx p.3]

这一定义不只覆盖磁盘上的普通文件。Unix 还把 I/O 设备映射成文件，例如磁盘分区 `/dev/sda2`、终端 `/dev/tty2`；课件进一步列出内核映像 `/boot/vmlinuz-3.13.0-55-generic` 与暴露内核数据结构的 `/proc`。[00:04:31–00:05:15] [课件: 16-io.pptx p.3]

网络连接也表现为 socket：发送消息就是向 socket 写，接收消息就是从 socket 读。因此，磁盘文件和网络通信可以复用同一套低层 API。[00:05:15–00:05:48]

### 4. 从统一抽象推出核心操作与文件位置 [00:05:48–00:07:33]

1. 文件的基本操作是打开、关闭、读取和写入，对应 `open()`、`close()`、`read()`、`write()`。[课件: 16-io.pptx p.4]
2. 对许多文件，还要维护 **current file position**：它记录下一次读或写从哪个字节偏移开始。连续读取不会每次都回到开头，而是随着操作推进位置。[00:06:03–00:06:28]
3. `lseek()` 可以显式改变文件位置。[00:06:28–00:06:42] [课件: 16-io.pptx p.4]
4. 统一接口不等于所有对象能力相同。终端不能回退到已经输入的数据，也不能跳到尚未输入的数据；socket 同样不能“跳到未来的包”，所以并非所有文件都适合 seek。[00:06:42–00:07:22]

结论是：应把文件位置理解成一次“打开文件”所关联的状态，但使用前还必须判断具体文件类型是否支持定位。[00:07:13–00:07:33]

### 5. 用类型区分统一抽象中的不同角色 [00:07:34–00:09:57]

老师按本讲需要依次介绍三类文件：[课件: 16-io.pptx p.5]

1. **普通文件（regular file）**：可先理解为磁盘上保存任意数据的文件。[00:07:46–00:07:56]
2. **目录（directory）**：目录本身也是文件，但文件系统会专门解释其中条目；条目描述其他文件的位置或属性。[00:07:56–00:08:18]
3. **套接字（socket）**：跨网络收发消息的连接。[00:08:19–00:08:27]

老师随后点到但不展开管道、符号链接、字符设备和块设备。管道的一端写入、另一端读出，正好说明“文件”抽象如何统一进程间数据流。[00:08:29–00:09:18] [课件: 16-io.pptx p.5]

本段最后回到普通文件：其中只是任意字节；“文本”与“二进制”的区分主要由应用层建立，而非内核替应用解释。具体区别留到下一段继续。[00:09:29–00:09:57]

## 概念、符号与推导

- **文件的字节模型**：长度为 $m$ 的文件由下标 $0$ 到 $m-1$ 的字节组成；这是表示模型，不是在推导文件内容的语义。[课件: 16-io.pptx p.3]
- **统一性推导**：设备、磁盘文件、socket 都映射为文件，因此上层可以复用 `open/close/read/write` 这组窄接口；具体对象仍可限制某些操作。[00:04:25–00:07:13]
- **当前文件位置**：下一次读写使用的偏移。一次读写推进它，`lseek()` 显式改变它；终端和 socket 不适合任意定位。[课件: 16-io.pptx p.4]
- **文件类型**：类型表示文件在系统中的角色。普通文件含任意数据；目录索引一组相关文件；socket 连接另一台机器上的进程。[课件: 16-io.pptx p.5]
- **本段除文件字节序列的形式化表示外，无数值公式推导。**

# 第 2 段：文本、目录、路径名与打开文件

- **时间范围**：00:09:57–00:19:55

## 本段在整讲中的作用

上一段把文件抽象为任意字节序列，本段先说明应用怎样在这串字节上建立“文本”语义，再通过目录层次和路径名解决“如何定位一个文件”，最后落到 `open()`：内核把路径名解析成一个小整数文件描述符，后续所有低层操作都以这个整数为句柄。[00:09:57–00:16:44]

这一段还提前建立系统调用编程纪律：返回值约定不统一，必须逐个查文档并检查每次调用。它直接为下一段的 `close/read/write` 错误处理和后半讲的描述符表模型做准备。[00:17:50–00:19:55]

## 教学展开

### 1. 从“任意字节”区分文本与二进制 [00:09:57–00:11:08]

老师承接上一段末尾的问题：这种区别不是内核对普通文件的分类，而是应用层对内容的解释。[课件: 16-io.pptx p.6]

1. 文本文件使用 ASCII 或其他能够编码非英语文字的字符编码。
2. 图像、目标代码、视频、音频等通常作为二进制文件；其中字节直接编码各种数值或格式字段。
3. 文本处理函数最重要的额外约定是把换行字节 `\n`，即十六进制 `0x0A`，解释为一行结束。
4. 老师联系此前的攻击实验：`0x0A` 会被 `gets` 当作行终止符，因此成为构造输入时需要避开的字节之一。[00:10:52–00:11:08]

### 2. 用打字机解释 LF 与 CRLF [00:11:08–00:13:04]

Linux 和 Mac 文本行使用单个 LF：`\n`，编码为 `0x0A`；Windows 及课件列出的 Internet protocols 使用 CRLF：`\r\n`，编码为 `0x0D 0x0A`。[课件: 16-io.pptx p.6]

老师用老式打字机说明两个动作为什么分开命名：

1. **carriage return** 把承载纸张的字车推回行首。
2. **line feed** 让滚筒把纸推进一行。
3. 打字机左侧手柄一次动作同时完成二者，这就是 “carriage return + line feed” 术语的来源。[00:11:47–00:13:04]

因此跨 Windows 与 Linux/Mac 传送文本时，行尾编码可能需要转换；这不是文件字节模型改变，而是文本约定不同。[00:11:08–00:11:45]

### 3. 目录把文件组织成层次 [00:13:09–00:14:19]

目录也是文件，但文件系统会按专门格式解释它。课件把目录描述为链接数组，每个链接把一个文件名映射到一个文件；至少包含两个特殊条目：[课件: 16-io.pptx p.7]

- `.`：指向目录自身。
- `..`：指向层次结构中的父目录。

这些目录文件彼此指向子目录，形成以 `/` 为根的层次树。内核还为每个进程维护当前工作目录 `cwd`，shell 的 `cd` 命令改变它。[课件: 16-io.pptx p.8]

### 4. 路径名是穿过目录树的导航说明 [00:14:02–00:15:19]

1. **绝对路径名**从 `/` 开始，自根目录逐层定位，例如 `/home/droh/hello.c`。[课件: 16-io.pptx p.9]
2. **相对路径名**以进程当前工作目录为起点，例如当 `cwd` 为 `/home/bryant` 时，`../home/droh/hello.c` 按目录条目逐级导航。[课件: 16-io.pptx p.9]
3. 老师还提到 `~/` 形式可作为到某个用户目录的快捷写法。[00:14:53–00:15:08]

有了路径名，程序才能告诉 `open()` 究竟准备访问层次中的哪一个文件。[00:14:20–00:15:19]

### 5. `open()` 把路径名转换为文件描述符 [00:15:19–00:17:50]

`open()` 接收路径名和一个整数 flags 字段。flags 由预定义的按位标志组成，可用按位或组合，例如只读、读写、追加等。追加的含义是写入时从当时的文件尾开始，而不是从文件开头覆盖。[00:15:19–00:16:29]

课件给出的基本调用是：[课件: 16-io.pptx p.10]

```c
int fd;

if ((fd = open("/etc/hosts", O_RDONLY)) < 0) {
    perror("open");
    exit(1);
}
```

成功后返回 **file descriptor**，即当前进程用来标识某个已打开文件的小整数。它不是路径名，也不是文件内容指针。描述符通常从较小值开始分配，且进程可同时打开的文件数有上限。[00:16:29–00:17:14]

老师现场提到机器的 descriptor limit 为 1024；若真的长期占满，往往意味着程序忘记关闭文件，而不是正常需求。[00:17:14–00:17:50]

### 6. 建立“每次都查并检查返回值”的纪律 [00:17:50–00:19:55]

老师强调各系统调用对错误的编码并不整齐：有的以负数表示错误，有的以零表示错误，必须逐个查看文档。尽管检查会让代码充满条件分支，也不能靠“希望不会出错”来编程。[00:17:50–00:19:05]

对 `open()` 而言，返回负数表示打开失败，例如文件不存在或请求的访问模式没有权限；成功则返回非负描述符。[00:19:10–00:19:31]

每个由 Linux shell 创建的进程一开始已有三个与终端相连的打开文件：[课件: 16-io.pptx p.10]

| 描述符 | 标准名称 | 含义 |
|---:|---|---|
| `0` | `stdin` / `STDIN_FILENO` | 标准输入 |
| `1` | `stdout` / `STDOUT_FILENO` | 标准输出 |
| `2` | `stderr` / `STDERR_FILENO` | 标准错误 |

本段在老师准备说明“代码中应使用符号名而不是裸数字”时结束，结论在下一段开头补完。[00:19:31–00:19:55]

## 概念、符号与推导

- **文本行**：以 `\n` 结束的字符序列；`\n = 0x0A = LF`。[课件: 16-io.pptx p.6]
- **CRLF**：`\r\n = 0x0D 0x0A`，把回到行首与推进一行编码成两个字节。[课件: 16-io.pptx p.6]
- **目录条目**：文件名到文件的映射；`.` 与 `..` 使当前目录和父目录可被路径导航。[课件: 16-io.pptx p.7]
- **路径名依赖**：绝对路径依赖根目录；相对路径依赖进程 `cwd`。因此相同相对字符串在不同 `cwd` 下可能定位不同文件。[课件: 16-io.pptx p.8] [课件: 16-io.pptx p.9]
- **flags 组合**：每个标志占一个位或位域位置，多个选项通过按位或组合；老师没有在本段列出完整 flags 表。[00:15:26–00:16:29]
- **文件描述符 `fd`**：`open()` 成功返回的进程局部小整数，后续低层 I/O 用它引用已打开文件；`fd < 0` 表示本次打开失败。[课件: 16-io.pptx p.10]
- **本段无进一步公式推导。**

### 易错点与边界

- **误区：文本文件是内核中的独立底层格式。** 普通文件仍是任意字节，文本/二进制主要是应用解释。[00:09:57–00:10:35]
- **误区：CR 和 LF 是同一个动作。** 前者回行首，后者进纸一行；不同系统选用不同 EOL 字节序列。[00:11:26–00:13:04]
- **误区：目录只是 UI 中的容器，不是文件。** Unix 文件系统把目录存成由文件系统解释的特殊文件。[00:13:09–00:13:59]

# 第 3 段：`close/read/write`、短计数与逐字节演示

- **时间范围**：00:19:55–00:29:53
- **转录覆盖**：标准描述符命名的收尾至 `strace` 过滤系统调用演示开始
- **课件范围**：[课件: 16-io.pptx p.10]–[课件: 16-io.pptx p.14]

## 本段在整讲中的作用

本段完成 Unix I/O 四个基础动作中的后三个：`close()` 结束访问，`read()` 从当前文件位置复制到内存，`write()` 从内存复制到当前文件位置。重点并非只背签名，而是理解返回值、EOF、short count 和每次调用后文件位置的变化。[00:20:03–00:25:41]

老师随后故意展示“正确但极慢”的逐字节复制程序，再用 `strace` 准备揭示每个字符都触发系统调用。这个性能反例为下一段的 short count 处理和 RIO 缓冲封装建立需求。[00:25:49–00:29:53]

## 教学展开

### 1. 结束上一段：用符号名引用标准描述符 [00:19:55–00:20:03]

老师补完边界处被截断的句子：虽然标准输入、输出、错误可靠地占用描述符 `0/1/2`，代码仍应使用 `STDIN_FILENO`、`STDOUT_FILENO`、`STDERR_FILENO` 这类名称，而不是散落裸数字。[课件: 16-io.pptx p.10]

### 2. `close(fd)` 只接收描述符，也必须检查返回值 [00:20:03–00:21:52]

`open()` 用路径名和 flags 建立打开文件；`close()` 则不再需要路径名，只接收相应的文件描述符。成功关闭表示程序已结束对该打开文件的访问。[课件: 16-io.pptx p.11]

```c
int retval;

if ((retval = close(fd)) < 0) {
    perror("close");
    exit(1);
}
```

老师用多线程预告解释“关闭怎么也会出错”：共享内存的两个执行部分可能都尝试关闭同一描述符，第二次关闭已经关闭的文件就会失败，并可能造成严重错误。因此，即使 `close()` 看起来无害也要检查返回码。[00:20:27–00:21:48]

他还现场纠正自己对 `perror()` 的描述：`perror()` 打印带有系统错误说明的消息，本身并不退出；示例中的 `exit(1)` 才终止程序。[00:21:12–00:21:41]

### 3. `read(fd, buf, n)` 的输入、阻塞与返回值 [00:21:52–00:24:47]

调用者提供三个量：[课件: 16-io.pptx p.12]

1. `fd`：要读取的打开文件。
2. `buf`：调用者预先静态分配或动态分配的内存缓冲区。
3. `n`：最多允许写入 `buf` 的字节数，用来约束边界。

`read` 从当前文件位置向内存复制至多 `n` 个字节，然后推进文件位置。老师用终端和网络说明它可能阻塞：终端读取可等到用户输入一行并按回车，网络读取可等到连接上有数据到达。[00:22:16–00:23:13]

返回类型是有符号的 `ssize_t`：[00:23:45–00:24:32]

| 返回值 | 含义 |
|---:|---|
| `> 0` | 实际读到的字节数 |
| `= 0` | 检测到 EOF，例如文件耗尽或网络连接关闭 |
| `< 0` | 错误 |

若正返回值小于请求的 `n`，就是 **short read/short count**。它可能正常发生，程序必须预期，而不能把“少于请求量”自动当作错误。[课件: 16-io.pptx p.12]

### 4. `write(fd, buf, n)` 对称地从内存写出 [00:24:47–00:25:41]

`write()` 接收描述符、保存待写数据的缓冲区和请求字节数，从内存向当前文件位置复制，并推进位置。它返回实际写出的字节数；负值表示错误，少于 `n` 的正值是 short write，不一定是错误。[课件: 16-io.pptx p.13]

老师特意保留了“不保证一次全写完”这一反直觉点：即便程序明确要求把数据写到文件或网络，底层调用仍可能只接受其中一部分，之后必须继续处理。[00:25:02–00:25:34]

### 5. 用逐字节复制证明接口可用，再暴露性能问题 [00:25:49–00:27:48]

课件程序每次从标准输入读 1 字节，再向标准输出写 1 字节：[课件: 16-io.pptx p.14]

```c
#include "csapp.h"

int main(void)
{
    char c;

    while (Read(STDIN_FILENO, &c, 1) != 0)
        Write(STDOUT_FILENO, &c, 1);
    exit(0);
}
```

这里使用的是 CS:APP 的大写包装函数 `Read`、`Write`。每次最多请求 1 字节，因此一次成功的正计数不可能再是更小的正值。循环在读到 EOF，即返回 0 时结束。[00:25:49–00:26:19]

功能正确并不等于实现合理。每个 `read/write` 都进入内核、执行操作系统代码，再切回当前进程。老师估计一次这类切换约需 20,000–40,000 个时钟周期；若百万字节逐个处理，时间主要浪费在重复进入操作系统上。[00:26:19–00:27:44]

### 6. 用 `strace` 准备观察真实系统调用 [00:27:48–00:29:53]

老师运行网页所附的复制标准输入程序。终端界面看起来像“一次读入并回显一整行”，但程序实际上逐字符写回；终端驱动只是等到完整一行后才唤醒读取代码。[00:27:57–00:28:56]

`strace` 可以记录程序对操作系统的调用。无筛选时会输出大量难读信息，所以老师改用参数把观察范围限制到特定函数；本段在筛选命令即将给出时结束。[00:28:56–00:29:53]

## 概念、符号与推导

- **关闭语义**：`close(fd)` 操作的是一次打开得到的描述符，不是再次按路径查找文件。[00:20:03–00:20:23]
- **读取状态转移**：若当前位置为 $p$，成功读到 $k>0$ 个字节，则复制的范围从 $p$ 开始，下一位置推进到 $p+k$；本段未讨论并发修改等额外条件。[课件: 16-io.pptx p.12]
- **写入状态转移**：若成功写出 $k>0$ 个字节，当前位置同样推进 $k$。[课件: 16-io.pptx p.13]
- **short count**：对请求量 $n$，若 `0 < k < n`，返回 $k$ 是短计数而非自动错误；`read` 的 `k=0` 专门表示 EOF。[00:23:14–00:24:45]
- **边界安全前提**：`buf` 必须已经分配，传给 `read` 的最大长度不得超过可写空间；老师以此说明长度参数防止该调用溢出缓冲区。[00:22:03–00:22:26]
- **性能因果链**：逐字节操作 $\rightarrow$ 每字节一次或两次系统调用 $\rightarrow$ 频繁进入内核 $\rightarrow$ 正确但极慢。[00:26:19–00:27:44]

## 教学展开

### 1. `strace` 证实逐字节读写 [00:29:53–00:30:53]

过滤到低层 `write` 后，老师输入的字符串显示为一系列一字节写调用；同时追踪读和写时，`strace` 输出走标准错误，程序回显走标准输出，两者在同一终端交错，所以画面较乱。[00:29:53–00:30:35]

### 2. short count 有具体的数据源原因 [00:30:53–00:31:45]

老师按发生场景解释：[课件: 16-io.pptx p.15]

1. **读到文件末尾附近**：剩余字节少于请求量。
2. **从终端读文本行**：终端处理器按一行交付，以换行字符终止。
3. **读写网络 socket**：长消息被拆成较小网络块，单次调用可能只处理其中一块。

课件同时给出经验边界：普通磁盘文件读取除 EOF 外通常没有短计数，普通磁盘文件写入通常没有短计数；但最佳实践仍是一律允许 short count，而不是把实现习惯写成接口假设。[课件: 16-io.pptx p.15]

### 3. 学生提问把 EOF 语义分成两次调用 [00:31:45–00:32:48]

学生问：EOF 时返回 0，算不算 short count？老师回答“是非常短的 count，但不是负数”，继而给出精确过程：[00:31:45–00:32:46]

- 文件只剩 100 字节，程序请求 200 字节。
- 第一次 `read` 返回 100，并交付最后 100 字节。
- 再调用一次 `read`，这次返回 0。
- 返回 0 才是已经检测到真正 EOF 的专用信号；它不是错误负值。

这个例子说明，拿到一个正的 short count 并不能单独证明已经到 EOF，程序通常要根据协议或继续读取来判断。[00:32:15–00:32:43]

### 4. 网络分块与终端实现都不能成为固定计数假设 [00:32:50–00:34:50]

老师说网络包通常约为 1000 字节，并提到常见 1500 字节的 MTU；实际返回块大小还依赖协议层和路径实现。因此应用不应期待某个固定单次计数。[00:32:50–00:33:35]

另一位学生追问极长终端行。老师没有猜测具体上限，只说即使底层实现怎样分块，也不应造成这里所说的接口错误；程序仍必须允许短计数。教学结论不是记住某个终端缓冲大小，而是不要依赖它。[00:33:35–00:34:18]

### 5. 从麻烦推出 RIO 两类接口 [00:34:18–00:37:47]

直接处理每次 short read/short write 很烦，所以应用通常把低层 Unix I/O 包在库中。Professor O’Hallaron 编写的 RIO 就是课程和教材提供的 robust I/O 封装，Proxy Lab 会使用它。[00:34:18–00:35:42] [课件: 16-io.pptx p.17]

RIO 有两类函数：[课件: 16-io.pptx p.17]

2. **带缓冲的输入**：`rio_readlineb` 读取文本行，`rio_readnb` 读取二进制字节；程序从用户态内部缓冲区消费数据，空时才再次调用内核。[00:37:00–00:37:47] [课件: 16-io.pptx p.17]

### 6. 逐行读 `rio_readn` 的循环 [00:37:56–00:39:48]

课件源码如下；这是老师要求学生值得仔细研读的可靠 I/O 模式：[课件: 16-io.pptx p.19]

```c
ssize_t rio_readn(int fd, void *usrbuf, size_t n)
{
    size_t nleft = n;
    ssize_t nread;
    char *bufp = usrbuf;

    while (nleft > 0) {
        if ((nread = read(fd, bufp, nleft)) < 0) {
            if (errno == EINTR)
                nread = 0;
            else
                return -1;
        }
        else if (nread == 0)
            break;
        nleft -= nread;
        bufp += nread;
    }
    return (n - nleft);
}
```

老师在本段先解释三个输入仍是 `fd`、用户缓冲区和请求量 `n`；主循环重复 `read`，直至读够、发生不能恢复的错误，或遇到 EOF。[00:38:07–00:39:22]

他特别提示错误路径有细节：源码把信号中断 `EINTR` 视为可重试条件，把本次 `nread` 当作 0 后继续；其他负返回直接返回 `-1`。本段停在一般错误分支，EOF 和更新变量的讲解在下一段继续。[00:39:22–00:39:48]

## 概念、符号与推导

- **EOF 的两阶段观察**：末尾不足请求量时可先返回正 short count；下一次在位置已经到末尾时返回 0。[00:32:15–00:32:43]
- **`rio_readn` 循环不变量**：`nleft` 是仍需读取的字节数，`bufp` 指向用户缓冲区下一处写入位置；初始为 `n` 与 `usrbuf`。[课件: 16-io.pptx p.19]
- **一次成功迭代**：若底层返回 `nread=k>0`，则 `nleft -= k`，`bufp += k`，已完成区间与待写位置同步前移。[课件: 16-io.pptx p.19]
- **终止条件**：`nleft==0` 表示读满；`nread==0` 表示 EOF；不可恢复负返回表示错误。[00:39:06–00:39:48]
- **返回量推导**：初始请求为 $n$，剩余为 `nleft`，故实际读入量为 $n-\text{nleft}$。本段口述尚未走到最后一行，源码已明确给出。[课件: 16-io.pptx p.19]
- **RIO 接口边界**：`rio_readn` 只有遇到 EOF 才返回正 short count；`rio_writen` 的目标是不向调用者返回 short count。[课件: 16-io.pptx p.18]

### 1. `rio_readn` 以三种条件结束 [00:39:49–00:40:43]

承接上一段源码，底层 `read` 返回 0 表示 EOF，循环随即停止。此时 `rio_readn` 不丢弃之前已经读到的数据，而是返回 $n-\text{nleft}$，因此可能是小于请求量的非负 short count。[00:39:49–00:40:07] [课件: 16-io.pptx p.19]

每次正读取后执行两项同步更新：剩余量 `nleft -= nread`，下一写入地址 `bufp += nread`。循环持续到：

1. 已经得到请求的 `n` 字节；
2. 发生不可恢复错误；
3. 遇到 EOF。

老师指出可靠代码初看条件很多、略显凌乱，但逐条研究后每个分支都有明确原因，而且每次底层调用都检查了错误。[00:40:07–00:40:43]

### 2. 缓冲输入把“大块内核读取”与“小块应用消费”分开 [00:40:43–00:42:47]

缓冲区只是与某个文件连接关联的一段字符/字节数组。需要输入时，RIO 先用一次较大的 Unix `read` 尽量填充数组；应用随后每次要少量字节时，先从数组中取，只有未读区耗尽才再次进入内核。[00:40:43–00:41:56]

因果链是：[课件: 16-io.pptx p.20] [课件: 16-io.pptx p.22]

```text
一次较大的 read 填充内部缓冲区
        ↓
应用从未读部分逐字节或逐行取走
        ↓
未读计数归零后才 refill
        ↓
显著减少系统调用次数
```

此时必须区分两种“位置”：内核的 current file position 已经前进到整块读取之后，而应用只消费到 `rio_bufptr`。二者之间就是“已从文件读入、但尚未交给用户代码”的 buffered portion。[00:42:27–00:43:15] [课件: 16-io.pptx p.22]

### 3. `rio_t` 把缓冲状态集中在一个结构中 [00:43:15–00:43:59]

```c
typedef struct {
    int rio_fd;                /* descriptor for this internal buf */
    int rio_cnt;               /* unread bytes in internal buf */
    char *rio_bufptr;          /* next unread byte in internal buf */
    char rio_buf[RIO_BUFSIZE]; /* internal buffer */
} rio_t;
```

[课件: 16-io.pptx p.23]

- `rio_fd` 把状态绑定到具体描述符。
- `rio_cnt` 表示内部数组中尚未交付给应用的字节数。
- `rio_bufptr` 指向下一未读字节。
- `rio_buf` 保存实际缓存数据。

这四项正好实现上一页图中的未读区：指针给出起点，计数给出长度，数组给出存储。[00:43:15–00:43:59]

### 4. RIO 按行复制示例 [00:43:59–00:45:39]

{

    rio_t rio;

# 第 6 段：描述符表、打开文件表、v-node 与 `fork` 共享

- **时间范围**：00:49:48–00:59:44
- **转录覆盖**：`stat` 查询的收尾至 `dup2` 重定向机制的引入
- **课件核验**：[课件: 16-io.pptx p.27]–[课件: 16-io.pptx p.32]
- **材料说明**：本段 prompt 标为“仅 transcript”；页码由原始 `materials.jsonl` 核验，三表图与课堂口述逐项对应

## 本段在整讲中的作用

前半讲一直把 `fd` 当作小整数使用，本段揭示它背后的三层间接关系：进程私有的 descriptor table 指向全局 open file table，后者再指向保存文件属性的 v-node。文件位置和引用计数位于“打开实例”层，而不是描述符数字或文件本体层。[00:51:08–00:55:08]

老师随后用“同一路径 `open` 两次”和 `fork` 做对照：前者得到两个独立打开实例和两个位置，后者复制描述符表却共享原打开实例和位置。该差异是理解关闭、父子进程读写和下一段 `dup2` 重定向的中心依赖。[00:55:12–00:59:44]

## 教学展开

### 1. 完成 `stat` 的调用模式 [00:49:48–00:51:08]

普通 `stat` 命令可打印任意文件的元数据；要查 C 接口，应使用 `man 2 stat`，因为 Unix man page 分节，而系统调用/系统接口通常位于第 2 节。[00:49:48–00:50:23]

`stat` 函数接收路径名和指向调用者缓冲区的指针，把结果按预定义 `struct stat` 布局写入。老师把它概括成常见系统接口模式：先分配规定结构，再传地址让函数填充。[00:50:23–00:51:08] [课件: 16-io.pptx p.27]

### 2. 三张表把“进程、一次打开、文件本体”分层 [00:51:08–00:55:08]

老师先警告这是期末考试高频而且可以很刁钻的内容，应结合教材、练习题和旧试题反复追踪。[00:51:27–00:51:58]

| 层次 | 作用域 | 课堂中的关键内容 |
|---|---|---|
| **descriptor table** | 每个进程一张 | 以 `fd` 为索引；每个有效条目指向一个 open file table entry |
| **open file table** | 所有进程共享 | 每次 `open` 创建一个条目；保存 current file position、`refcnt` 等打开状态 |
| **v-node table** | 所有进程共享 | 保存文件访问属性、大小、类型等文件本体信息，可由 `stat` 观察 |

[课件: 16-io.pptx p.28]

描述符 `0/1/2` 指向进程继承的标准流对应打开项；其余条目来自程序执行中尚未关闭的打开文件。老师再次把 file position 定义为下一次读/写所在位置。[00:52:42–00:53:43]

open file table 的 `refcnt` 记录有多少描述符表条目仍指向该打开项。只有所有引用都关闭，内核才不再需要这个打开项。v-node 则保存文件本身的属性；老师将其展开为 virtual node，并把 `stat` 信息放在这一层。[00:53:44–00:55:08]

### 3. 同一路径 `open` 两次得到独立文件位置 [00:55:12–00:56:58]

若一个程序对相同 pathname 调用两次 `open`：[课件: 16-io.pptx p.29]

```text
fd A ──> open-file entry A (file pos A, refcnt 1) ──┐
                                                    ├──> same v-node/file
fd B ──> open-file entry B (file pos B, refcnt 1) ──┘
```

两个描述符可读同一个文件的不同位置；一个描述符推进位置不会自动推进另一个，因为它们指向不同 open file entries。[00:55:12–00:55:57]

老师还说，可把一个打开实例用于写在前面、另一个用于读取已经写过的内容。两个独立打开同时写同一文件虽然系统允许，却很容易把内容弄乱；“合法”不等于“正确设计”。[00:55:59–00:56:27]

### 4. `fork` 复制描述符表，但共享打开实例 [00:57:11–00:58:56]

`fork()` 创建子进程时，子进程得到父进程 descriptor table 的副本。表是两张，但对应条目仍指向同一批 open file entries，因此每个被继承项的 `refcnt` 加 1。[课件: 16-io.pptx p.30] [课件: 16-io.pptx p.31]

```text
parent fd k ──┐
              ├──> one open-file entry (shared file pos, refcnt 2) ──> v-node
child  fd k ──┘
```

于是父进程读一次会推进共享 file position，子进程下一次读从推进后的位置继续，而不是从 fork 时的位置各走各的。[00:57:29–00:58:01]

父子进程之后仍可各自打开或关闭条目，使图变得更复杂。每次关闭一个描述符只减少一次引用；必须所有相关引用都关闭，打开项才真正从内核角度结束。[00:58:09–00:58:47]

课件补充：`exec` 默认不改变这种打开文件继承关系；需要不同处理时可使用 `fcntl` 调整相关标志。本段口述未展开该点。[课件: 16-io.pptx p.30]

### 5. 从共享模型引出 `dup2` 和重定向 [00:58:56–00:59:44]

老师介绍 `dup2`：它复制当前进程 descriptor table 中的一个条目。最常见用途是 shell 的 I/O redirection：[课件: 16-io.pptx p.32]

```text
ls > foo.txt       标准输出改写到文件
command < input    标准输入改从文件读取
```

实现思想不是改写 `ls` 内部的输出函数，而是在程序开始执行前让描述符 `1` 指向目标文件的 open file entry；输入重定向同理处理描述符 `0`。[00:59:04–00:59:44]

本段在老师准备具体解释 `dup2(4, 1)` 时结束，复制方向、旧引用计数与关闭多余描述符由下一段完成。

## 概念、符号与推导

- **索引关系**：`fd` 只是在某进程 descriptor table 中的索引；表项再指向 open file entry。[00:52:16–00:52:56]
- **每次打开原则**：每执行一次成功 `open`，分配一个新的 open file table entry，因此同一文件可有多个独立 file position。[00:52:42–00:55:57]
- **文件本体共享**：多个打开项可指向同一 v-node，说明“同一个文件”不推出“同一个打开状态”。[课件: 16-io.pptx p.29]
- **`fork` 共享推导**：复制的是 descriptor table；条目中的指针值继续指向原 open file entries，所以 file position 被父子共享，`refcnt` 增加。[00:57:11–00:58:29]
- **关闭条件**：关闭一个描述符只解除一条指针并递减 `refcnt`；当引用归零，打开项才可释放。[00:58:22–00:58:47]
- **重定向依赖**：程序把输出写到 fd 1；若 shell 预先让 fd 1 指向磁盘打开项，同样的写调用自然进入文件。[00:59:04–00:59:44]

## 例子与课堂提示

### 例子

- **两次打开同一文件**：两个描述符、两个 open file entries、一个 v-node，专门检验独立 file position。[00:55:12–00:55:57] [课件: 16-io.pptx p.29]
- **两个独立写者**：内核允许，但位置和写入交互可能破坏文件，用来区分 API 合法性与应用正确性。[00:55:59–00:56:27]
- **父读、子再读**：两张描述符表指向同一打开项，因此父进程推进的位置会被子进程观察到。[00:57:29–00:58:01]
- **引用计数**：多次 fork 可制造多条指向同一打开项的引用，解释为什么一次 `close` 不一定真正关闭底层打开文件。[00:58:22–00:58:47]
- **`ls > foo.txt`**：shell 通过改描述符表实现重定向，应用仍向“标准输出”编号写，不需要知道目标已变。[课件: 16-io.pptx p.32]

### 易错点与边界

- **误区：描述符表是全系统共享。** 每个进程各有一张；共享的是 open file table 和 v-node table。[课件: 16-io.pptx p.28]
- **误区：同一路径 `open` 两次共享位置。** 两次 `open` 创建不同打开项，所以位置独立。[课件: 16-io.pptx p.29]
- **误区：`fork` 后父子位置独立。** 它们共享原 open file entry，因此位置共同推进。[课件: 16-io.pptx p.31]
- **误区：任一进程 `close(fd)` 就立刻销毁文件的打开项。** 只有 `refcnt` 降到零才真正失去所有引用。[00:58:22–00:58:47]
- **误区：文件元数据复制到每个描述符条目。** 图把类型、大小、访问属性放在 v-node 层，打开项主要保存位置和引用计数。[课件: 16-io.pptx p.28]
- **考试提示**：追踪题应逐操作画三层箭头和 refcnt，不能只按描述符数字猜输出。[00:51:27–00:51:58]

# 第 7 段：`dup2` 重定向、标准 I/O、接口选型与二进制边界

- **时间范围**：00:59:44–01:09:38
- **转录覆盖**：`dup2(4,1)` 的具体效果至 Richard Stevens 参考书建议
- **课件范围**：[课件: 16-io.pptx p.32]–[课件: 16-io.pptx p.47]

## 本段在整讲中的作用

本段先用三表模型精确完成 shell 输出重定向：`dup2(oldfd,newfd)` 先解除 `newfd` 的旧指向，再让它复制 `oldfd` 的表项。随后老师回到应用最常用的标准 I/O，以一次 `strace` 展示缓冲怎样把六次 `printf` 合成一次 `write`。[00:59:44–01:04:49]

最后，整讲把 Unix I/O、RIO 和标准 I/O 放在同一层次图中比较，给出面向磁盘/终端、signal handler、网络 socket 的选择规则，并以二进制数据反例划定文本和字符串函数的适用边界。[01:05:01–01:09:38]

## 教学展开

### 1. `dup2(4,1)` 让标准输出改指向磁盘文件 [00:59:44–01:00:54]

以 `ls > foo.txt` 为背景，shell 的子进程在 `exec` 前先打开输出文件，假设得到 fd 4；此时 fd 1 仍指向终端。[课件: 16-io.pptx p.32] [课件: 16-io.pptx p.33]

调用：

```c
dup2(4, 1);
```

把当前进程 descriptor table 的 **oldfd 4** 条目复制到 **newfd 1**。结果是 fd 1 与 fd 4 都指向目标磁盘文件的同一个 open file entry，其 `refcnt` 变为 2；fd 1 原来指向终端的打开项失去该引用。[00:59:44–01:00:54] [课件: 16-io.pptx p.34]

于是被执行程序仍对标准输出 fd 1 调用 `write`，数据却进入磁盘文件。输入重定向同理，只是改写 fd 0 的表项。[01:00:01–01:00:14]

### 2. 关闭多余 fd 4 不会破坏 fd 1 [01:00:54–01:02:44]

完成复制后通常关闭 fd 4，避免泄漏多余描述符。`close(4)` 只删除 fd 4 这一条引用，把目标打开项 `refcnt` 从 2 降到 1；fd 1 仍有效并继续指向目标文件。[01:00:54–01:01:33]

老师回应学生问题时强调 `dup2` 的方向容易想反：`dup2(oldfd,newfd)` 是“希望今后用 `newfd` 访问 `oldfd` 当前访问的对象”。在复制前，它会先解除 `newfd` 原先的指向并递减对应引用计数，再复制 `oldfd` 条目，否则旧目标会在表中留下无法通过 `newfd` 到达的引用状态。[01:01:39–01:02:25]

结论：`dup2` 强大但危险；多表项和引用计数下，忘记关闭或弄反方向很容易制造 bug。[01:02:25–01:02:44]

### 3. 标准 I/O 把描述符与内存缓冲包装成 stream [01:02:45–01:03:26]

标准 I/O 是 C 标准库 `libc` 提供的高层接口，K&R 附录也有文档。课件列出：[课件: 16-io.pptx p.36]

- `fopen/fclose`：打开、关闭；
- `fread/fwrite`：字节 I/O；
- `fgets/fputs`：文本行 I/O；
- `fscanf/fprintf`：格式化 I/O。

它把打开文件建模为 **stream**，即文件描述符加用户态内存缓冲区的抽象。C 程序开始时已有 `stdin`、`stdout`、`stderr` 三个 `FILE *` 流，分别关联描述符 0、1、2。[课件: 16-io.pptx p.37]

老师把标准 I/O 的主要增值概括为与 RIO 相似的 buffering：应用不必亲自处理每次低层调用和部分短计数。[01:02:45–01:03:26]

### 4. 六次 `printf` 在底层只形成一次 `write` [01:03:26–01:04:49]

示例逐字符调用 `printf` 输出 `hello\n`：[课件: 16-io.pptx p.40]

```c
int main()
{
    printf("h");
    printf("e");
    printf("l");
    printf("l");
    printf("o");
    printf("\n");
    fflush(stdout);
    exit(0);
}
```

`strace` 显示底层只有：

```text
write(1, "hello\n", 6) = 6
```

字符先积累在 `stdout` 缓冲区，直到刷新条件触发才一次写出。课件列出换行、显式 `fflush`、`exit` 或从 `main` 返回等刷新时机；老师说在这个终端示例中换行通常已经触发刷新，因此后面的 `fflush(stdout)` 很可能是冗余的。[01:03:52–01:04:49] [课件: 16-io.pptx p.39]

这与 RIO 演示得到同一性能结论：应用可逐字符表达意图，但用户态缓冲把系统调用聚合成大块操作。[课件: 16-io.pptx p.38]

### 5. 比较 Unix I/O、RIO 与标准 I/O [01:05:01–01:06:19]

三者的层次关系不是互斥实现：标准 I/O 和 RIO 最终都建立在低层 Unix I/O 上。[课件: 16-io.pptx p.42]

| 接口 | 课堂定位 | 主要优点 | 主要限制 |
|---|---|---|---|
| Unix I/O | `open/read/write/lseek/stat/close` | 最通用、额外层最少；能查 metadata；async-signal-safe | short count 和高效文本行缓冲都难处理 |
| 标准 I/O | C 标准库 stream | 缓冲减少系统调用，自动处理 short count，接口丰富且标准化 | 不提供 metadata 接口；不适合 signal handler；socket 限制会相互冲突 |
| RIO | 课程/教材封装 | 对 short count 和网络传输给出可靠、清晰接口 | 与其他缓冲层混用会产生状态冲突 |

[课件: 16-io.pptx p.43] [课件: 16-io.pptx p.44]

老师专门回答“已有标准 I/O，为何还写 RIO”：标准 I/O 对终端和磁盘文件很好，但不是为网络连接设计；RIO 的主要使用场景是网络。[01:05:25–01:05:59]

同一数据源上不能随意混合标准 I/O 与 RIO，因为两者各有一个彼此不可见的预取缓冲区。某层已从内核读走、但尚未交给应用的数据，另一层完全不知道，顺序就会混乱。[01:05:59–01:06:17]

### 6. 按使用场景选择尽可能高层的接口 [01:06:19–01:07:31]

老师先说 raw Unix I/O 从应用角度很痛苦，尤其是 short count 和错误码，因此通常应包在库后使用。标准 I/O 提供 `printf/scanf` 等丰富、跨系统且较标准化的能力，适合日常磁盘文件和终端。[01:06:19–01:07:05]

课件的选择规则是：[课件: 16-io.pptx p.45]

1. 一般使用能满足需求的最高层接口，并理解其语义。
2. 磁盘文件或终端：优先标准 I/O。
3. signal handler：使用 async-signal-safe 的 raw Unix I/O，不用标准 I/O。
4. 极少数需要绝对最高性能的场景：考虑 raw Unix I/O。
5. 网络 socket：使用 RIO，避免标准 I/O。

### 7. 二进制数据不能交给文本行或 C 字符串语义 [01:07:31–01:08:36]

老师指出学生反复犯的错误：对 JPEG、网络包等没有“文本行”语义的数据使用面向行的接口。[01:07:31–01:07:48]

- `fgets`、`scanf`、`rio_readlineb` 会特殊解释 EOL，例如 `0x0A`，跨系统文本处理还可能转换 LF/CRLF。
- `strlen`、`strcpy`、`strcat` 把字节 `0x00` 当作字符串终止符。
- 二进制数据内部可以合法包含 `0x0A` 或 `0x00`，所以这些函数会提前停止或改变解释。
- 应使用不赋予行/字符串语义的 `rio_readn` 或 `rio_readnb` 等字节接口。

[课件: 16-io.pptx p.46]

结论不是“熟悉的函数总是更安全”，而是必须先确认数据模型，再选择函数。[01:08:17–01:08:36]

## 概念、符号与推导

- **`dup2` 方向**：`dup2(oldfd,newfd)` 使 `newfd` 成为 `oldfd` 当前表项的副本；`dup2(4,1)` 是 4 指向的对象变成 1 的对象，不是反过来。[课件: 16-io.pptx p.32]
- **引用计数变化**：复制前解除 fd 1 对终端项的引用；复制后 fd 1、fd 4 同指目标项，目标 `refcnt=2`；再 `close(4)` 后为 1，fd 1 仍可用。[00:59:44–01:01:33] [课件: 16-io.pptx p.34]
- **stream 模型**：标准 I/O stream 包含文件描述符和内存缓冲区；它不是新的内核文件类型。[课件: 16-io.pptx p.37]
- **缓冲摊销**：多次小 `printf` 先写用户态缓冲，最终一次 `write(1,buf,6)`，把多次系统调用固定成本合并。[01:03:26–01:04:49]
- **接口依赖**：标准 I/O、RIO $\rightarrow$ Unix I/O $\rightarrow$ 内核；高层便利并未取消底层语义，只是封装它。[课件: 16-io.pptx p.42]
- **缓冲层不可见性**：两个独立缓冲包若交替读取同一描述符，各自的“下一字节”状态不一致，因此不能混用。[01:05:59–01:06:17]

## 例子与课堂提示

### 例子

- **`ls > foo.txt`**：shell 子进程先 `open` 得 fd 4，再 `dup2(4,1)`，最后关闭 4 并执行程序；fd 1 的既有调用自然写入文件。[课件: 16-io.pptx p.32] [课件: 16-io.pptx p.33] [课件: 16-io.pptx p.34]
- **关闭 fd 4**：只让目标项引用数从 2 到 1，反证“关闭任一别名就使所有别名失效”的误解。[01:01:20–01:01:33]
- **`printf` 输出 `hello\n`**：六次库调用对应一次低层 `write`，直观展示标准 I/O buffering。[课件: 16-io.pptx p.40]
- **标准 I/O 与 RIO 冲突**：两个缓冲区都可能预取，服务于“每个描述符选定一套缓冲体系”的工程边界。[01:05:59–01:06:17]
- **JPEG/网络包**：其中 `0x0A`、`0x00` 是普通数据，不能让行函数或字符串函数把它们当终止符。[01:07:31–01:08:23]

### 易错点与边界

- **误区：`dup2(4,1)` 让 4 指向 1。** 恰好相反，1 复制 4 的当前表项。[01:01:39–01:02:16]
- **误区：复制后必须保留 fd 4，否则 fd 1 也失效。** 两个描述符是两条引用，关闭 4 后 1 仍保留目标项。[01:00:54–01:01:33]
- **误区：每次 `printf` 都立即触发 `write`。** 标准 I/O 先缓冲，刷新条件到来才写内核。[01:03:26–01:04:49]
- **误区：标准 I/O 既高层又通用，所以 socket 也首选它。** 课堂明确要求网络使用 RIO，避免标准 I/O 的 stream/socket 限制。[01:05:25–01:05:59] [课件: 16-io.pptx p.44]
- **误区：可以在同一描述符上交错标准 I/O 与 RIO。** 两套私有缓冲无法同步，读序会混乱。[01:05:59–01:06:17]
- **误区：文本函数只是在二进制上“慢一点”。** 它们会把合法字节解释成终止符或 EOL，属于语义错误。[01:07:31–01:08:36]
