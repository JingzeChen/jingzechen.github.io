## 核心概念与依赖关系

```text
fork / execve / waitpid / zombie
        ↓ 产生异步回收需求
signal: send ≠ receive
        ↓
pending + blocked(signal mask)
        ↓
普通信号不排队      pnb = pending & ~blocked
        ↓                         ↓
SIGCHLD 不能计数          内核返回用户态前决定接收
        ↓                         ↓
循环 wait 全部孩子       default action / handler
                                  ↓
                       同进程并发 + 共享全局状态
                                  ↓
              mask、G0–G5、async-signal-safe、SIO
                                  ↓
                  调度交错与先行关系（fork 前阻塞）
                                  ↓
                 条件等待与 sigsuspend 原子操作
```

```text
普通调用/返回纪律
    ↓ 受控突破
setjmp 保存活动栈环境，首次返回 0
    ↓

```

## 关键推导、例子与结论边界

- **shell 动机**：后台作业不应阻塞 read/evaluate 循环，但终止后必须回收；信号只负责通知，`waitpid` 才完成回收。[00:07:13–00:09:37]
- **非排队推导**：每类信号只有一个 pending bit；对已经为 1 的位再次置 1 不增加信息，所以 handler 调用数不能计数同类事件。[00:17:29–00:19:32]
- **接收公式**：`pnb = pending & ~blocked` 只选出 pending 且未 blocked 的类型；blocked 信号仍可 pending。[00:28:34–00:29:50]
- **Bomb Lab 示例**：程序能安装 `SIGINT` handler 改写 `Ctrl-C` 的默认动作；但最初 `printf` 版本稍后被判定不安全。[00:32:23–00:33:49] [课件: 15-ecf-signals.pptx p.24] [课件: 15-ecf-signals.pptx p.33]
- **`printf` 死锁**：main 持有终端 lock 时被 handler 打断，handler 再等同一 lock；main 又要等 handler 返回才能释放。[00:51:21–00:52:51]
- **五子进程示例**：五次终止可能合并为少数 `SIGCHLD` 接收；循环 `wait` 到 `ECHILD` 才能全部回收。[00:54:35–00:59:14]
- **job list 竞态**：保护 `addjob` 与 `deletejob` 的单次访问仍不足够；必须保证 add happens-before delete。[01:03:27–01:09:45]
- **`pause` 竞态**：目标信号可落在检查 flag 与进入 `pause` 之间，造成永久睡眠；`sigsuspend` 消除这条缝隙。[01:13:40–01:18:59]
- **证据边界**：视频没有详细讲解 `setjmp`/`longjmp`；所有寄存器恢复、`foo/bar`、P1/P2/P3 与 `restart.c` 细节只引用补充课件，不附伪造时间戳。[01:19:01–01:19:15] [课件: 15-ecf-signals.pptx p.48] [课件: 15-ecf-signals.pptx p.49] [课件: 15-ecf-signals.pptx p.50] [课件: 15-ecf-signals.pptx p.51] [课件: 15-ecf-signals.pptx p.52] [课件: 15-ecf-signals.pptx p.53] [课件: 15-ecf-signals.pptx p.54]

## 易错点与待核对项

- 不要把 send/deliver 与 receive 合并为一个瞬时动作。[00:13:41–00:15:40]
- 不要把 blocked 理解为拒绝递送；它只推迟接收。[00:18:07–00:18:39]
- 不要把 `kill` 函数名理解为效果必然是终止，也不要混淆 `/bin/kill -9 -24817` 中信号编号与负 PGID。[00:14:43–00:15:02] [00:22:34–00:24:07]
- 不要把 handler 当成另一个进程；它与 main 共享地址空间和全局状态。[00:34:55–00:36:28]
- `volatile` 处理编译器可见性，`sig_atomic_t` 只保证 flag 的单次读/写；二者都不让 `flag++` 或复杂结构更新自动安全。[00:46:51–00:49:21]
- 不要在 handler 中调用 `printf`、`sprintf`、`malloc`、`exit`；课程安全输出使用 SIO，终止使用 `_exit`。[00:50:12–00:54:13]
- 不要假设 fork 后 parent 先运行，也不要在 fork 后才阻塞 `SIGCHLD`。[01:05:37–01:08:22]
- [需回听 00:55:31] 口述称 `ccount` 初值为 0，但课件代码在创建孩子前设置 `ccount = N`；程序分析以代码为准。[课件: 15-ecf-signals.pptx p.34]

# 第 1 节：从 shell 的后台子进程问题引出信号

## 本段在整讲中的作用

本段承担整讲的动机铺垫。老师先把本讲放回异常控制流（Exceptional Control Flow, ECF）的层级图中：上一讲讨论硬件/内核层面的异常和进程上下文切换，本讲上移到内核与应用协作的 **Linux 信号**，以及应用内部的 **C 非局部跳转**。[00:00:05–00:00:38] [课件: 15-ecf-signals.pptx p.2] 信号语义细碎且容易混淆，所以课堂主体放在信号；非局部跳转只作点题，细节留给教材与末尾补充课件。[00:00:17–00:00:38] [课件: 15-ecf-signals.pptx p.3]

老师没有直接给信号下完整定义，而是先追问一个具体的 shell 问题：前台子进程可以由父 shell 同步 `waitpid` 并回收，后台子进程却不能阻塞 shell 的下一轮读命令；那么后台子进程结束后，shell 如何及时得知并回收它？[00:07:13–00:09:15] 这个问题把上一讲的 `fork`、`execve`、`waitpid` 和本讲的信号连接起来，也为后续 Shell Lab 的作业控制与 `SIGCHLD` 处理建立主线。[课件: 15-ecf-signals.pptx p.6] [课件: 15-ecf-signals.pptx p.7] [课件: 15-ecf-signals.pptx p.8]

## 教学展开

### 1. 先交代本讲范围与 ECF 层级

1. 老师宣布继续研究异常控制流，这次关注更高层机制：Linux signals 与 C non-local jumps。[00:00:05–00:00:16] [课件: 15-ecf-signals.pptx p.1]
2. 信号有许多微妙语义，因而占课堂绝大部分时间；非局部跳转仅介绍思想，完整内容应查教材和课件末尾补充页。[00:00:17–00:00:38]
3. 课件把 ECF 分成不同层级：异常依赖硬件与内核，进程上下文切换依赖硬件定时器与内核，信号连接内核和应用，非局部跳转发生在应用代码内部。[课件: 15-ecf-signals.pptx p.2]

### 2. 从 Linux 进程层级回顾 `fork`

老师从上一讲的事实出发：Linux 创建新进程只有 `fork` 这一条路径，因此系统中的进程自然形成父子层级。[00:00:56–00:01:20]

- 系统启动后的第一个进程是 PID 为 1 的 `init`；其他进程都是它的后代。[00:01:09–00:01:20] [课件: 15-ecf-signals.pptx p.4]
- `init` 会创建长期运行、提供服务的 daemon，例如 Web 服务器；还会最终产生 login shell，为用户提供命令行界面。[00:01:28–00:01:54]
- `pstree` 可以查看这种进程树。[课件: 15-ecf-signals.pptx p.4]

这段回顾的作用不是重新讲进程，而是确定 shell 也处在普通的父子进程关系中：shell 为用户创建子进程，子进程还可能继续创建后代。[00:02:02–00:02:35]

### 3. 把 shell 定义为普通应用程序

shell 是“代表用户运行程序的应用程序”，并没有特殊的进程身份。[00:02:35–00:02:43] [课件: 15-ecf-signals.pptx p.5] 例如用户输入 `ls`，shell 创建子进程，再在子进程中执行 `ls`。[00:02:09–00:02:27]

老师顺带给出 shell 的历史例子：Linux 默认 shell 是 Bash；更早的 Unix 中有 Stephen Bourne 创建的 `sh`（Bourne shell），以及 Berkeley Unix 的 `csh`。[00:02:43–00:03:15] [课件: 15-ecf-signals.pptx p.5]

### 4. shell 主循环：read → evaluate

shell 的执行是一连串 read/evaluate 步骤。[00:03:15–00:04:15] [课件: 15-ecf-signals.pptx p.5]

1. 打印提示符 `> `。
2. 等待用户输入命令行并回车；命令行通常由命令名及空格分隔的可选参数组成。[00:03:23–00:03:44]
3. 若终端输入 EOF（`Ctrl-D`），shell 退出。[00:03:45–00:04:01]
4. 否则调用 `eval(cmdline)` 求值；返回后重新打印提示符，开始下一轮。[00:04:01–00:04:15]

这里的重要控制流性质是：shell 自身的主循环必须持续存在，不能因为某个后台作业尚未结束就停止接受命令。

### 5. `eval` 如何解析并执行命令

老师随后逐行解释简化版 `eval`。[00:04:15–00:07:44] [课件: 15-ecf-signals.pptx p.6]

1. **解析命令行**：`parseline` 把输入转换成 `argv`；`argv[0]` 是命令，后续元素是参数，并返回命令行末尾是否有 `&`。[00:04:21–00:05:24]
2. **识别前后台**：末尾有 `&` 表示后台作业，shell 不等它结束便继续下一次 read；没有 `&` 表示前台作业，shell 必须等待。[00:04:41–00:05:14]
3. **忽略空行**：若 `argv[0] == NULL`，说明用户只按了回车，直接返回。[00:05:24–00:05:35]
4. **处理内建命令**：`jobs`、`bg`、`fg` 等由 shell 自己实现，不需要创建外部程序；`builtin_command(argv)` 识别并执行它们。[00:05:36–00:06:14]
5. **执行外部程序**：若不是内建命令，shell 调用 `fork`。子进程调用 `execve(argv[0], argv, environ)`，用目标程序替换自身。[00:06:15–00:06:42]
6. **处理 `execve` 失败**：成功的 `execve` 不返回；若返回，说明出错，示例打印 “Command not found” 后退出子进程。[00:06:42–00:07:12]
7. **父进程分流**：前台作业由父进程调用 `waitpid(pid, &status, 0)` 等待并回收；后台作业只打印 PID 与命令行，然后立即返回主循环。[00:07:13–00:07:44]

由此得到一个刻意简化但关键的结论：在这份代码里，前台与后台作业的核心差别，就是 shell 是否立即对它调用 `waitpid`。[00:07:44–00:07:54]

### 6. 暴露后台作业的资源回收缺口

前台路径是完整的：父 shell 等待并回收终止子进程，让内核释放其残留状态。[00:07:59–00:08:20] 后台路径却只打印消息并返回 read/evaluate 循环，之后没有代码重新处理该子进程。[00:08:20–00:08:40] [课件: 15-ecf-signals.pptx p.7]

因此后台作业终止后会成为 zombie；而 shell 通常长期不退出，这些 zombie 不会由当前示例回收。积累足够多时会形成内核资源泄漏，甚至耗尽系统资源。[00:08:40–00:08:50] [课件: 15-ecf-signals.pptx p.7]

### 7. 用异常控制流补上“异步通知”

解决方向不是让 shell 主动、持续地轮询每个后台作业，而是让内核在子进程终止时打断 shell 的常规处理并发出通知；shell 收到通知后再调用 `waitpid` 回收子进程。[00:08:50–00:09:15] [课件: 15-ecf-signals.pptx p.8]

课件随后用 “Today” 页标记从 Shells 转入 Signals。[课件: 15-ecf-signals.pptx p.9] Unix 中，这种通知机制叫 **signal**：信号是内核递送给进程的小消息，用来告知系统中发生了某类事件。[00:09:15–00:09:37] 它类似上一讲的异常，但此处机制由软件实现；信号总是由内核发送，有时是应另一个进程的请求而发送。[00:09:37–00:09:57]

## 概念、符号与推导

### 进程层级与 shell

- **`init`**：本课堂所述启动进程，PID 为 1，是其他进程的祖先。[00:01:09–00:01:20] [课件: 15-ecf-signals.pptx p.4]
- **daemon**：由 `init` 创建的长期运行服务程序。[00:01:28–00:01:40]
- **login shell**：接受用户命令并代表用户运行程序的应用。[00:01:40–00:02:09]
- **内建命令**：由 shell 自身实现，如 `jobs`、`bg`、`fg`；不走外部程序的 `fork`/`execve` 路径。[00:05:36–00:06:14]

### 前台与后台作业

- **前台作业**：命令行不以 `&` 结束；父 shell 等待指定子进程终止并回收它。[00:04:41–00:05:14] [课件: 15-ecf-signals.pptx p.6]
- **后台作业**：命令行以 `&` 结束；父 shell 不立即等待，直接接受下一条命令。[00:04:41–00:05:04]
- **zombie 问题链**：后台作业终止 → 示例 shell 没有后续 `waitpid` 路径 → 终止状态保留 → 长寿命 shell 中持续积累 → 内核资源泄漏。[00:07:59–00:08:50] [课件: 15-ecf-signals.pptx p.7]

### `eval` 的控制流骨架

```text
cmdline
  → parseline(cmdline, argv)，得到 bg
  → 空行？返回
  → 内建命令？由 shell 直接执行
  → 否则 fork
       ├─ child: execve(argv[0], argv, environ)
       └─ parent:
            ├─ foreground: waitpid(pid, &status, 0)

```

这一控制流来自老师对课件代码的逐步解释。[00:04:21–00:07:44] [课件: 15-ecf-signals.pptx p.6]

1. **误解：shell 是内核中的特殊程序。** 老师明确把 shell 定义为普通应用；它通过系统调用创建、执行和回收进程。[00:02:35–00:02:43]

# 第 2 节：信号的发送、接收、pending 与 blocked 语义

> 时间范围：00:09:57–00:19:56
> 依据：课堂 transcript 与 `15-ecf-signals.pptx` 第 10–14 页

## 本段在整讲中的作用

上一段用 shell 无法同步等待后台子进程的问题引出信号；本段开始建立后续所有代码都依赖的严格词汇。老师反复强调信号是 Linux 中最棘手的语义之一，因此必须把 **发送（send/deliver）**、**接收（receive）**、**待处理（pending）** 和 **阻塞（blocked）** 分开说，不能把“内核已记录一个信号”误认为“用户处理器已经执行”。[00:13:09–00:15:40]

教学链条是：先用常见信号说明一个信号携带的信息极少，再精确定义发送与接收，最后用两个位向量解释为什么普通信号不排队、阻塞为何只推迟接收。[课件: 15-ecf-signals.pptx p.10] [课件: 15-ecf-signals.pptx p.11] [课件: 15-ecf-signals.pptx p.12] [课件: 15-ecf-signals.pptx p.13] [课件: 15-ecf-signals.pptx p.14]

## 教学展开

### 1. 信号只携带类型 ID 与“已经到达”这一事实

信号是“小消息”，因为它没有任意载荷；本讲模型中只有唯一整数 ID 和该信号已经被递送这一事实。[00:09:57–00:10:23] 信号类型既有整数编号，也有符号名称。[00:10:32–00:10:41] [课件: 15-ecf-signals.pptx p.10]

老师按用途列出四类例子：

1. **`SIGINT`**：用户在命令行按 `Ctrl-C` 时，内核把它发送给前台进程；默认动作是终止，因此用户重新得到 shell 提示符。[00:10:32–00:11:05]
2. **`SIGKILL`（编号 9）**：也会终止目标进程，但其独特之处是不能被忽略或覆盖，因而是失败保险式的终止手段。[00:11:09–00:11:32]
3. **`SIGSEGV`**：进程访问受保护或非法内存区域时，由内核发送；默认动作是终止程序。[00:11:39–00:12:02]
4. **`SIGALRM`**：程序可以安排未来给自己发送该信号，例如三秒后触发，用来构造定时器或超时保护。[00:12:07–00:12:36]
5. **`SIGCHLD`**：子进程终止或停止时，内核发送给父进程；shell 将依靠它得知有子进程需要回收。[00:12:40–00:13:05]

这些例子先说明信号类型表示“发生了哪一类事件”，但不代表每类信号都采用相同的默认动作，也不代表信号携带该事件的详细记录。

### 2. 精确定义“发送”：只更新目标进程上下文中的状态

内核向目标进程 **发送/递送（send/deliver）** 一个信号，是指内核更新目标进程上下文中的某些状态。[00:13:41–00:14:14] [课件: 15-ecf-signals.pptx p.11] 在发送这一刻，除了位状态改变之外不要求立即发生用户可见动作；老师明确说“没有立即影响”。[00:14:05–00:14:18]

内核发送信号有两类原因：

- 内核自己检测到系统事件，例如子进程终止；课件还给出除零产生 `SIGFPE` 的例子。[00:14:19–00:14:33] [课件: 15-ecf-signals.pptx p.11]
- 另一个进程请求内核代为发送，例如调用 `kill` 系统调用。[00:14:33–00:14:47]

`kill` 这个名字容易误导：它是通用的信号发送接口，所发信号的效果不一定是杀死目标进程。[00:14:45–00:15:02]

### 3. 精确定义“接收”：内核迫使目标进程作出反应

目标进程 **接收（receive）** 信号，是指内核终于强制该进程对已递送的信号采取动作。[00:15:08–00:15:40] [课件: 15-ecf-signals.pptx p.12] 可能的反应包括：

- 忽略信号；
- 终止进程，课件注明可伴随 core dump；
- 捕获信号，执行用户级 signal handler。[00:15:40–00:15:58]

捕获路径类似异步中断触发异常处理器，但执行位置不同：异常处理器在内核中；signal handler 是程序 C 代码中的普通函数，在当前进程的用户空间执行。[00:15:58–00:16:25]

控制流顺序为：主程序执行到 `Icurr` 附近 → 进程接收信号 → 内核把控制交给 handler → handler 执行并返回 → 主程序从原本要执行的下一条指令 `Inext` 继续。[00:16:25–00:17:07] [课件: 15-ecf-signals.pptx p.12]

### 4. 用 pending 定义“已发送但尚未接收”

如果信号已由内核发送、但目标进程尚未接收，它就是 **pending signal**。[00:17:16–00:17:28]

普通信号的关键限制是：同一类型在任意时刻最多只有一个 pending 实例。[00:17:29–00:17:47] 若某进程已经有 pending 的 `SIGCHLD`，随后又递送一个 `SIGCHLD`，第二次递送不会积累出第二个项目；它对已有 pending 状态没有新增效果，可视为被丢弃。[00:17:47–00:18:07] [课件: 15-ecf-signals.pptx p.13]

所以，**信号不排队（signals are not queued）**。收到一次某类型信号只说明至少一次对应事件发生过，不能直接推出事件恰好发生一次。

### 5. 用 blocked 定义“允许递送、推迟接收”

进程可以阻塞某些信号的 **接收**，却不能靠阻塞阻止信号被 **递送**。[00:18:07–00:18:24] 被阻塞的信号仍可进入 pending 状态，只是在解除阻塞之前，进程不会被迫对它作出反应。[00:18:28–00:18:39] [课件: 15-ecf-signals.pptx p.13]

因此三种状态应按时间顺序理解：事件导致递送 → 对应类型进入 pending → 若 blocked 则停留；若未 blocked，则内核可让进程接收并清除 pending 状态。一个 pending 信号至多接收一次。[00:18:28–00:18:42]

### 6. 两个位向量解释全部状态

内核在每个进程上下文中维护两个位向量：[00:18:42–00:19:56] [课件: 15-ecf-signals.pptx p.14]

- `pending`：表示当前 pending 信号的集合。递送类型 `k` 时，内核置位 `pending[k]`；接收该类型时清零。
- `blocked`：表示当前被阻塞信号的集合，也叫 **signal mask**；进程可通过 `sigprocmask` 设置或清除其中的位。

老师用位向量反推“不排队”：每个信号类型 `k` 只有一个 pending bit；对已经为 1 的位再次置 1，状态不变。[00:18:53–00:19:32]

## 概念、符号与推导

### 核心术语

- **signal type / `k`**：由小整数 ID 标识的信号类别；符号名如 `SIGINT`、`SIGCHLD`。[00:10:08–00:10:41]
- **send/deliver**：内核更新目标进程上下文中的信号状态，不等于目标已执行动作。[00:13:49–00:15:02]
- **receive**：内核强制目标进程按默认动作或已安装 handler 对信号作出反应。[00:15:08–00:15:58]
- **pending**：已发送、尚未接收。[00:17:16–00:17:28]
- **blocked / signal mask**：被推迟接收的信号集合。[00:18:07–00:18:39] [00:19:36–00:19:56]

### 位状态推导

对某一信号类型 `k`：

```text
deliver(k): pending[k] ← 1
receive(k): pending[k] ← 0
blocked[k] = 1: 可以 deliver(k)，但暂不 receive(k)
```

由于 `pending[k]` 只有 0/1 两种状态：

```text
pending[k] 已为 1，再次 deliver(k)
→ 仍然是 1
→ 不能记录第二次到达
→ 同类型普通信号不排队
```

这是老师在 [00:18:53–00:19:32] 根据位向量给出的直接解释。[课件: 15-ecf-signals.pptx p.13] [课件: 15-ecf-signals.pptx p.14]

本段没有数值计算公式；有上述位状态推导。

## 例子与课堂提示

- **`SIGINT` 与 `SIGKILL` 对照**：两者默认效果都可表现为终止，但 `SIGINT` 可在后续通过 handler 改写，`SIGKILL` 不能忽略或覆盖；用于说明“效果相似”不等于“控制权限相同”。[00:10:32–00:11:32]
- **`SIGALRM` 三秒超时**：说明信号不只来自故障或其他进程，也可以由程序安排给自己，用于时间边界。[00:12:07–00:12:36]
- **`SIGCHLD` 与 shell**：一次接收只意味着至少一个子进程发生了终止/停止事件；本节先埋下“不排队”限制，后面会据此修正 child handler。[00:12:40–00:13:05] [00:17:29–00:18:07]
- **`kill` 名字误导**：阅读代码时应看第二个信号参数和该类型动作，不能仅凭函数名断定目标终止。[00:14:43–00:15:02]
- **中断类比**：只用于理解控制临时转入 handler 再返回；不要因此把用户级 signal handler 当成内核异常处理器。[00:15:58–00:17:07]

## 常见误解与边界

1. **误解：发送信号就会立即运行 handler。** 发送只更新目标进程状态；接收才触发动作。[00:13:49–00:15:40]
2. **误解：阻塞会拒绝或丢掉信号。** 阻塞只推迟接收；信号仍可被递送并 pending。[00:18:07–00:18:39]
3. **误解：五次同类型事件一定产生五次 handler 调用。** 同类型只有一个 pending bit，后续递送可合并，不能用普通信号计数。[00:17:29–00:18:07]
4. **误解：signal handler 在内核中。** 它是当前进程 C 代码中的用户级函数；内核负责安排接收和控制转移。[00:16:14–00:16:56]
5. **边界：信号只给出类型和到达事实。** 本讲此处不为信号附加事件详情或计数。[00:10:08–00:10:23]
6. **边界：`SIGKILL` 是不可忽略/不可覆盖的例外。** 后面介绍安装 handler 时不能把规则泛化到它。[00:11:09–00:11:32]

# 第 3 节：进程组发送信号与内核接收算法

> 时间范围：00:19:56–00:29:50
> 依据：课堂 transcript 与 `15-ecf-signals.pptx` 第 15–21 页

## 本段在整讲中的作用

上一段用 `pending` 和 `blocked` 建立了单进程内的信号状态。本段回答两个操作层问题：**信号如何选中一个进程或整组作业**，以及 **内核何时检查并让目标进程接收信号**。老师先用 shell 的前后台 process group 解释 `/bin/kill`、键盘和 `kill` 函数的目标范围，再回到内核从异常返回用户态的时刻，推导 `pnb = pending & ~blocked` 的接收选择算法。[00:20:10–00:29:50]

## 教学展开

### 1. process group 是信号群发的目标单位

每个进程恰好属于一个 process group。[00:20:14–00:20:29] [课件: 15-ecf-signals.pptx p.15] 图中 shell 的 `pid=10, pgid=10`；它创建的前台作业首进程为 `pid=20, pgid=20`，该作业再创建的 `pid=21`、`pid=22` 子进程继承 `pgid=20`。[00:20:29–00:21:31]

shell 可以通过 `setpgid` 改变进程组，通过 `getpgrp` 取得当前进程的组。[00:20:54–00:21:04] 建立进程组的价值在于：一个信号操作可以面向整个作业的所有进程，而不必逐个 PID 发送。[00:21:35–00:21:56]

### 2. `/bin/kill`：正 PID 选进程，负 PID 选进程组

`/bin/kill` 程序可以请求内核向单个进程或整个进程组发送任意信号。[00:21:44–00:22:03] [课件: 15-ecf-signals.pptx p.16]

课堂示例 `forks 16` 产生两个不同 PID、同属 `pgid=24817` 的循环子进程。[00:22:03–00:22:34]

- `/bin/kill -9 24818`：第一个参数 `-9` 指定 `SIGKILL`，第二个正数指定 PID 24818，只向该进程发送。[00:22:34–00:23:33]
- `/bin/kill -9 -24817`：目标参数前再带负号，表示 PGID 24817，向组内两个子进程都发送 `SIGKILL`；之后 `ps` 中二者都消失。[00:23:33–00:24:07]

这里两个负号角色不同：`-9` 是信号编号选项，`-24817` 是负的目标进程组 ID。[课件: 15-ecf-signals.pptx p.16]

### 3. 键盘：`Ctrl-C`/`Ctrl-Z` 面向前台进程组

在终端输入 `Ctrl-C`，内核向前台进程组发送 `SIGINT`；输入 `Ctrl-Z`，内核向前台进程组发送 `SIGTSTP`。[00:24:07–00:24:36] [课件: 15-ecf-signals.pptx p.17]

- `SIGINT` 的默认动作是终止进程。[00:24:36–00:24:39]
- `SIGTSTP` 的默认动作是停止/挂起进程，直至收到 `SIGCONT`。[00:24:39–00:24:45]

老师演示一个前台父子程序：两者同属一个前台组。按 `Ctrl-Z` 后 shell 报告 suspended，`ps w` 中父子状态首字母都为 `T`；执行 shell 内建命令 `fg` 将作业恢复到前台；再按 `Ctrl-C`，两进程终止，下一次 `ps` 已看不到它们。[00:24:55–00:26:03] [课件: 15-ecf-signals.pptx p.18]

课件同时给出 `ps` 状态图例：`S` 为 sleeping，`T` 为 stopped，`R` 为 running；第二个字符 `s` 表示 session leader，`+` 表示 foreground process group。[课件: 15-ecf-signals.pptx p.18]

### 4. C 程序用 `kill` 函数主动发送

第三种发送方式是 `kill(pid, signal)` 系统调用。[00:26:03–00:26:18] 示例 `fork12` 创建 `N` 个无限循环的子进程并记录 PID，然后逐个调用 `kill(pid[i], SIGINT)`。[00:26:18–00:26:47] [课件: 15-ecf-signals.pptx p.19]

父进程随后循环 `wait` 回收这些已终止的子进程，并用 `WIFEXITED` 区分正常退出和异常终止。[课件: 15-ecf-signals.pptx p.19] 老师说明这里函数返回后程序很快会退出，逐个回收不是展示发送机制的必要部分，但代码仍做了“应尽的清理”。[00:26:48–00:27:10]

### 5. 内核在返回用户态前检查信号

老师用进程 A/B 的上下文切换图转入接收问题。[00:27:10–00:28:23] 假设 A 在用户态运行，定时器中断、其他中断或系统调用 trap 等异常让控制进入内核；调度器决定从 A 切换到 B。[00:27:20–00:28:15] [课件: 15-ecf-signals.pptx p.20]

关键检查点是：内核准备从异常处理返回、把控制交还给进程 B 的用户代码之前，检查 B 的 pending signals。[00:28:15–00:28:34]

### 6. 推导 pending-nonblocked 集合 `pnb`

内核计算：

```text
pnb = pending & ~blocked
```

其中 `~blocked` 把未阻塞类型标为 1，再与 `pending` 按位与，得到所有“已 pending 且未 blocked”的信号。[00:28:34–00:28:54] [课件: 15-ecf-signals.pptx p.21]

接着分两种情况：

1. 若 `pnb == 0`，没有当前可接收的信号，内核直接把控制交给目标进程逻辑流中的下一条指令。[00:28:54–00:29:08]
2. 若 `pnb != 0`，内核选择最小的非零位 `k`，强制进程接收对应信号；接收触发该信号的动作。对 `pnb` 中其他非零位重复，处理完后才回到进程下一条指令。[00:29:08–00:29:50]

## 概念、符号与推导

### PID 与 PGID

- **PID**：标识单个进程。
- **PGID**：标识进程所属的唯一 process group；组内进程可以有不同 PID、相同 PGID。[00:20:21–00:21:31]
- **前台进程组**：终端键盘产生的 `SIGINT`/`SIGTSTP` 的群发目标。[00:24:07–00:24:45]

### 接收集合推导

对每个信号位 `k`：

```text
pnb[k] = pending[k] AND NOT blocked[k]
```

真值含义：

| `pending[k]` | `blocked[k]` | `pnb[k]` | 当前是否可接收 |
|---:|---:|---:|---|
| 0 | 0 | 0 | 否，尚未递送 |
| 0 | 1 | 0 | 否，尚未递送且被阻塞 |
| 1 | 1 | 0 | 否，保持 pending，等待解除阻塞 |
| 1 | 0 | 1 | 是，内核可迫使进程接收 |

该表只是对老师给出的按位公式逐位展开，没有加入额外机制。[00:28:34–00:29:23] [课件: 15-ecf-signals.pptx p.21]

### 接收算法

```text
准备返回进程 p 的用户态
→ 计算 pnb
→ pnb == 0：恢复 p 的下一条指令
→ 否则选择最小置位 k
→ 让 p 接收 k 并触发动作
→ 对其余置位重复
→ 恢复 p 的下一条指令
```

## 例子与课堂提示

- **PGID 20 的前台作业**：首进程改变到以自身 PID 为 PGID 的新组，后代继承该 PGID；服务于“一个作业可能由多个进程组成”。[00:20:29–00:21:31]
- **`/bin/kill -9 -24817`**：同时杀死两个不同 PID 的进程；服务于负目标参数表示进程组，而非单一 PID。[00:22:03–00:24:07]
- **`Ctrl-Z → ps → fg → Ctrl-C → ps`**：用状态变化实证停止、继续和终止；同时说明键盘信号作用于整个前台组。[00:24:55–00:26:03]
- **`fork12`**：展示用户程序通过 `kill` 请求内核发送信号，并提醒终止子进程后仍应考虑回收。[00:26:03–00:27:10]
- **异常返回检查点**：信号可以早已递送，但内核在准备恢复某进程用户态时才检查是否接收，进一步巩固“发送不等于接收”。[00:27:20–00:29:23]

## 常见误解与边界

1. **误解：`Ctrl-C` 只发给前台作业的父进程。** 它面向整个前台进程组，所以组中的父子进程都可能收到。[00:24:07–00:24:39]
2. **误解：负数目标永远是信号编号。** `/bin/kill -9 -24817` 中 `-9` 选信号，`-24817` 选进程组，位置决定含义。[课件: 15-ecf-signals.pptx p.16]

4. **误解：进程一被调度就先执行一条用户指令再看信号。** 检查发生在内核返回该进程用户态之前。[00:28:15–00:28:34]
5. **误解：blocked 位会从 `pending` 中删掉信号。** `pending & ~blocked` 只把它排除在当前可接收集合之外；pending 状态仍可保留。[00:28:34–00:28:54]
6. **边界：本段算法选择“最小非零位”。** 笔记保留课堂给出的选择规则，不外推实时信号、优先级或其他平台机制。[00:29:08–00:29:45]

# 第 4 节：安装处理器、并发逻辑流与嵌套处理

> 时间范围：00:29:50–00:39:49
> 依据：课堂 transcript 与 `15-ecf-signals.pptx` 第 22–28 页

## 本段在整讲中的作用

上一段说明内核如何选出可接收信号，本段继续回答“接收后到底执行什么”。老师先列默认动作，再用 `signal` 安装用户 handler；接着把 handler 重新解释成与主程序重叠的并发逻辑流，以此揭示真正的风险：它与主程序共享全局状态，而且一个 handler 还可能被另一类型的 handler 打断。[00:29:50–00:39:49]

## 教学展开

### 1. 每种信号先有预定义默认动作

进程接收信号必定触发某种动作。老师列出三类默认动作：[00:29:50–00:30:16] [课件: 15-ecf-signals.pptx p.22]

- 终止进程；
- 停止进程，直至 `SIGCONT` 使其继续；
- 忽略信号。

默认动作不是唯一选择，程序可以修改某些信号被接收时的行为。[00:30:16–00:30:30]

### 2. `signal` 修改动作，而不是“发送一个信号”

函数原型为：

```c
handler_t *signal(int signum, handler_t *handler);
```

[课件: 15-ecf-signals.pptx p.23]

老师指出 `signal` 和 `kill` 一样名字容易误导：`signal` 并不发送信号，而是修改指定 `signum` 的动作。[00:30:23–00:30:55]

第二个参数有三种含义：

1. `SIG_IGN`：忽略该类型。
2. `SIG_DFL`：恢复该类型的默认动作。
3. 用户函数地址：把该函数安装为 signal handler；函数接收一个整数参数，即触发它的信号编号。[00:31:02–00:31:43] [课件: 15-ecf-signals.pptx p.23]

把函数注册为动作叫 **installing a handler**；信号到来后执行该函数叫 **catching/handling the signal**。[00:31:43–00:32:00]

handler 会打断进程当时的逻辑流；它返回后，控制回到被打断位置并继续执行。[00:32:03–00:32:23]

### 3. `sigint.c`：用 Bomb Lab 的 `Ctrl-C` 行为连接代码与体验

示例在 `main` 中调用 `signal(SIGINT, sigint_handler)`，安装一个返回 `void`、接收整数信号编号的处理器，然后调用 `pause()` 等待信号。[00:32:23–00:33:16] [课件: 15-ecf-signals.pptx p.24]

用户按 `Ctrl-C` 产生 `SIGINT`，进程接收后运行 `sigint_handler`。该处理器打印 “So you think you can stop the bomb with ctrl-c, do you?” 等消息，短暂 sleep，最后退出。[00:33:16–00:33:49] [课件: 15-ecf-signals.pptx p.24]

老师用学生在 Bomb Lab 中试图按 `Ctrl-C` 退出时看到的提示说明：那不是终端的固定行为，而是 bomb 程序安装了自己的 `SIGINT` handler。[00:33:16–00:33:49]

### 4. handler 是并发逻辑流，但不是另一个进程

并发的定义是逻辑流在时间上重叠。[00:33:52–00:34:19] 先前见过的进程并发较易推理，因为不同进程有独立地址空间；若要共享内存，必须额外使用机制。[00:34:19–00:34:55]

signal handler 是课程中第二次遇到的并发形式：主程序的逻辑流执行时，信号接收使控制转入 handler；handler 运行后返回，主程序再继续。两段逻辑流在时间上重叠，因此并发。[00:34:55–00:35:48] [课件: 15-ecf-signals.pptx p.25]

与两个进程不同，handler 在 **同一个进程** 中执行，能访问主程序的所有全局变量与全局状态。[00:35:48–00:36:28] 这正是信号难处理的根源：主逻辑流和 handler 可能在任意中断点观察或修改同一数据。

### 5. 用 A/B 时间图再现“递送”和“接收”的间隔

老师再画一遍时间线：[00:36:42–00:37:53] [课件: 15-ecf-signals.pptx p.26]

1. 进程 A 的主程序执行时，一个信号被递送给 A；此刻只是 pending 位被置位，没有立即运行 handler。
2. 控制进入内核，调度器从 A 切换到 B，B 运行一段时间。
3. 再次进入内核并准备调度 A 时，内核发现 pending 位，于是让 A 接收该信号，执行用户 handler。
4. handler 返回时短暂回到内核，再由内核恢复 A 原本要执行的下一条主程序指令。

这个图把上一段抽象的 pending 状态与本段的并发流统一起来。

### 6. 不同类型 handler 可以嵌套

handler 自身也可能被信号打断。[00:37:54–00:38:54] 假设主程序接收信号 `s`，进入 handler S；S 执行过程中又接收另一类型 `t`，于是转入 handler T。T 返回到 S 的被打断指令，S 完成后再返回主程序。[课件: 15-ecf-signals.pptx p.27]

因此逻辑返回栈是：

```text
main → handler S → handler T → handler S → main
```

### 7. 同类型隐式阻塞与显式阻塞

内核会自动阻塞当前正在处理的同类型信号：某 `SIGINT` handler 运行期间，不能再被另一个 `SIGINT` 的接收打断。[00:38:54–00:39:23] [课件: 15-ecf-signals.pptx p.28]

但它仍可能被其他类型信号打断；若程序需要更强约束，就要用 `sigprocmask` 显式阻塞/解除阻塞一组信号。[00:39:16–00:39:49] 课件列出的集合辅助函数包括 `sigemptyset`、`sigfillset`、`sigaddset`、`sigdelset`。[课件: 15-ecf-signals.pptx p.28]

## 概念、符号与推导

### handler 安装与执行

- **default action**：每种信号预定义的终止、停止或忽略动作。[00:29:57–00:30:16]
- **install**：用 `signal(signum, handler)` 把函数地址注册为该类型动作。[00:31:02–00:31:43]
- **catch/handle**：进程接收信号后实际执行该函数。[00:31:43–00:32:00]
- **`pause()`**：示例中让进程挂起，等待一次会运行 handler 的信号事件；handler 执行后 `pause` 返回。[00:32:51–00:33:16]

### 并发与共享状态

```text
时间重叠的逻辑流 ⇒ concurrent flows
handler 与 main 在同一进程 ⇒ 共享地址空间和全局状态
任意接收点可能打断 main ⇒ 共享状态可能在中间状态被 handler 观察
```

前两步由老师在 [00:33:52–00:36:28] 明确定义；最后一步是老师随后要解决的风险方向，本段尚未给出保护代码。

### 嵌套与阻塞规则

- 当前处理类型 `s` 被内核隐式阻塞，所以 handler S 不被另一个 `s` 接收重入。[00:38:54–00:39:16]
- 另一类型 `t` 仍可被接收，因此 handler T 可以嵌套打断 S。[00:37:54–00:39:21]
- 显式 `sigprocmask` 用于阻塞程序指定的信号集合。[00:39:23–00:39:49]

本段无数学公式推导。

## 常见误解与边界

1. **误解：调用 `signal` 就向进程发送了信号。** 它修改某类型的动作；发送由内核执行。[00:30:23–00:30:55]
2. **误解：handler 是独立进程。** 课件明确写 separate logical flow, not process；它在当前进程内并共享全局状态。[课件: 15-ecf-signals.pptx p.25]
3. **误解：信号递送后 handler 立刻执行。** A/B 图中递送只置 pending，实际接收可发生在后续恢复 A 时。[00:36:50–00:37:43]
4. **误解：一个 handler 被打断后，内层 handler 返回主程序。** handler T 返回 handler S 的中断点，S 完成后才回 main。[00:38:01–00:38:54]
5. **误解：隐式阻塞会屏蔽所有信号。** 默认只阻塞当前正在处理的同类型；其他类型仍可嵌套。[00:38:54–00:39:23]
6. **边界：示例 `sigint.c` 用了 `printf`、`fflush`、`exit`。** 本段只展示安装和控制流；后续老师会说明这些函数并非 async-signal-safe，并给出安全改写。[课件: 15-ecf-signals.pptx p.24]

# 第 5 节：显式阻塞与安全 signal handler 的规则

> 时间范围：00:39:49–00:49:45
> 依据：课堂 transcript 与 `15-ecf-signals.pptx` 第 28–32 页

## 本段在整讲中的作用

上一段以 handler 的嵌套和共享全局状态结束，本段给出第一组工程化约束：怎样用 signal set 和 `sigprocmask` 划出不会被某类信号接收打断的区域，以及怎样按 G0–G5 编写尽量安全的 handler。[00:39:49–00:49:45]

老师把信号难点归纳为三类：handler 可能不安全并破坏共享状态，普通信号不排队因而不能用于计数，以及不同 Unix 系统的语义不完全可移植。[00:42:10–00:44:18] 本段集中处理第一类，后两类分别在后续 child-reaping 与 `sigaction` 示例中展开。

## 教学展开

### 1. signal set 本质上仍是位向量

老师接续上一段的辅助函数：signal set 可以看成位向量，`sigemptyset`、`sigfillset`、`sigaddset`、`sigdelset` 分别建立空集、加入全部信号、加入一个信号、删除一个信号；这些操作实质上设置或清除向量位。[00:39:49–00:40:05] [课件: 15-ecf-signals.pptx p.28]

### 2. 临时阻塞 `SIGINT`，再恢复进入前的 mask

老师逐行解释一段将在 Shell Lab 中反复使用的模式。[00:40:05–00:42:10] [课件: 15-ecf-signals.pptx p.29]

```c
sigset_t mask, prev_mask;

Sigemptyset(&mask);
Sigaddset(&mask, SIGINT);

Sigprocmask(SIG_BLOCK, &mask, &prev_mask);

/* 不希望被 SIGINT 接收打断的代码区 */

Sigprocmask(SIG_SETMASK, &prev_mask, NULL);
```

教学顺序如下：

1. `Sigemptyset(&mask)` 生成全零集合。[00:40:26–00:40:34]
2. `Sigaddset(&mask, SIGINT)` 把 `SIGINT` 加入集合。[00:40:34–00:40:48]
3. `Sigprocmask(SIG_BLOCK, &mask, &prev_mask)` 将集合中的 `SIGINT` 加入当前 blocked set，同时把进入前的 blocked set 保存到 `prev_mask`。[00:40:48–00:41:31]
4. 临界代码区运行期间，`SIGINT` 可以被递送并 pending，但不会被接收，因此对应 handler 不会打断该区。[00:41:31–00:41:50]
5. `SIG_SETMASK` 用保存的 `prev_mask` 完整恢复旧状态，而不是假定旧状态为空后简单解除某一位。[00:41:50–00:42:10]

### 3. 三类困难决定安全规则的必要性

老师先展示为什么不能随意写 handler：[00:42:10–00:44:18]

1. **不安全 handler**：可能造成死锁；也可能在主程序更新链表等共享结构的中间状态时插入执行，读到或修改不一致结构，导致损坏。[00:42:21–00:43:32]
2. **不排队语义**：若把 handler 调用次数当作事件次数，就会漏计；只有排队机制才可能保留每次事件，而普通信号没有。[00:43:32–00:43:58]
3. **可移植性差异**：Solaris、BSD 或不同 Unix 版本的信号处理语义可能不同。[00:43:58–00:44:18]

随后老师从第一项开始，给出一组“汇集来的经验规则”。[00:44:21–00:44:49]

### 4. G0：让 handler 尽可能简单

最简单的 handler 只设置一个全局标志并立即返回。[00:44:49–00:45:22] 老师提到 CMU CERT 的合规建议只允许这种形式；教学意图是把复杂工作留给常规控制流，让异步执行窗口越短越好。

### 5. G1：只调用 async-signal-safe 函数

handler 中调用的函数必须具有 async-signal safety。[00:45:26–00:45:45] `printf`、`sprintf`、`malloc`、`exit` 等常用函数不安全；原因和替代输出接口将在下一段详细解释。[课件: 15-ecf-signals.pptx p.31] [课件: 15-ecf-signals.pptx p.32]

### 6. G2：进入时保存 `errno`，退出前恢复

`errno` 是系统级函数发生错误时设置的全局变量。handler 内调用系统函数可能改写它，因此进入 handler 时应复制旧值，返回前再恢复，避免异步处理破坏被打断代码正在检查的错误状态。[00:45:45–00:46:07] [课件: 15-ecf-signals.pptx p.31]

典型骨架是：

```c
void handler(int sig) {
    int olderrno = errno;
    /* handler work */
    errno = olderrno;
}
```

### 7. G3：访问共享结构时临时阻塞所有相关信号

若 main 与 handler 都访问同一共享数据结构，两边在读写该结构时都要临时阻塞信号。[00:46:16–00:46:51] 否则 main 可能只完成链表更新的一半就被打断，handler 看到一个暂时不满足结构不变量的对象。[00:42:46–00:43:17]

课件的规则写成“temporarily blocking all signals”，强调保护共享结构的整个访问区。[课件: 15-ecf-signals.pptx p.31]

### 8. G4：共享全局变量声明为 `volatile`

`volatile` 防止编译器把共享变量长期只保存在寄存器中，迫使相关读写走内存。[00:46:51–00:47:17] 老师构造一个 main 自旋等待、handler 设置全局变量的场景：若 main 只反复读取寄存器缓存，它可能永远看不到 handler 写入内存的变化。[00:47:17–00:47:58]

所以供 main 与 handler 共享的全局变量应声明为 `volatile`。[00:47:58–00:48:04]

### 9. G5：只读/写的 flag 使用 `volatile sig_atomic_t`

老师把 flag 限定为“只读取或整体写入”的变量，例如 `flag = 1`；`flag++` 这类读-改-写操作不属于该定义。[00:48:04–00:48:25] [课件: 15-ecf-signals.pptx p.31]

声明为 `volatile sig_atomic_t` 后，系统保证对该 flag 的单次读取或写入是原子的，即一个不可中断的 load/store；这类访问不需要像复杂共享结构那样再单独保护。[00:48:25–00:48:58]

老师补充，多数系统上 `sig_atomic_t` 实际是 `int`，但使用标准类型才能保持可移植性。[00:48:58–00:49:21]

### 10. 引出 async-signal safety

本段最后开始定义：函数若是 **reentrant**，或根本不会被信号中断，就可以安全地在 handler 中调用。[00:49:24–00:49:45] [课件: 15-ecf-signals.pptx p.32] reentrant 的具体含义在下一段继续。

## 概念、符号与推导

### mask 操作的状态变化

设进入临界区前的 signal mask 为 `B_old`，要额外阻塞的集合为 `M`：

```text
SIG_BLOCK 后：B_current = B_old ∪ M
SIG_SETMASK(&prev_mask) 后：B_current = B_old
```

这里的集合表示来自课堂对 blocked bit vector 与代码的解释。[00:40:26–00:42:10] 关键不是“最后把 `SIGINT` 打开”，而是恢复进入前的完整 `B_old`，保留调用者原本阻塞的其他信号。

### `volatile` 与 `sig_atomic_t` 的职责

- `volatile`：约束编译器的寄存器缓存行为，使异步更新可被内存读写观察。[00:46:51–00:48:04]
- `sig_atomic_t`：保证 flag 的单次读或写不可分割。[00:48:20–00:49:21]
- 二者组合用于简单全局 flag；老师没有声称它让任意复合表达式或数据结构操作原子化。

# 第 6 节：async-signal safety、输出死锁与正确回收子进程

> 时间范围：00:49:45–00:59:39
> 依据：课堂 transcript；对应完整课件材料 `15-ecf-signals.pptx` 第 32–35 页

## 本段在整讲中的作用

本段完成上一节未讲完的 async-signal-safe 定义，并用两个失败程序把抽象规则变成可观察后果：handler 中重入 `printf` 可能永久死锁；把一次 `SIGCHLD` handler 调用等同于一个子进程终止，会因信号不排队而漏回收。[00:49:45–00:59:39]

教学结论是两条可直接用于 shell 的纪律：handler 只调用安全函数，输出使用课程提供的 SIO；接收 `SIGCHLD` 只证明“至少一个子进程终止”，因此 handler 必须循环 `wait`，直至没有更多已终止子进程。[课件: 15-ecf-signals.pptx p.32] [课件: 15-ecf-signals.pptx p.33] [课件: 15-ecf-signals.pptx p.34] [课件: 15-ecf-signals.pptx p.35]

## 教学展开

### 1. 可重入函数为什么可用于 handler

老师接着定义 reentrant：函数访问的数据都在自己的栈帧内，不使用全局变量，也不经指针访问全局变量。[00:49:45–00:49:55] 多个调用实例各有独立局部变量副本，因此可同时存在，不会共享同一内部状态。[00:49:55–00:50:04] 这构成 async-signal-safe 的一种来源。[课件: 15-ecf-signals.pptx p.32]

POSIX 保证 117 个函数具有 async-signal safety。老师列出的常用安全函数是 `_exit`、`write`、`wait`、`waitpid`、`sleep`、`kill`；常用但不安全的有 `printf`、`sprintf`，课件还列出 `malloc` 与 `exit`。[00:50:04–00:50:33] [课件: 15-ecf-signals.pptx p.32]

不幸的是，`write` 是列表中唯一的输出函数；handler 又经常需要打印诊断信息，于是产生实际矛盾。[00:50:29–00:50:54]

### 2. `printf` 重入如何形成死锁

老师构造一个可以实际复现的程序：[00:50:54–00:52:51]

1. main 在紧密循环中不断调用 `printf`。[00:51:02–00:51:15]
2. `printf` 内部先获取终端输出的 lock，以确保同一时刻只有一个实例写共享终端。[00:51:21–00:51:57]
3. 某次 main 的 `printf` 已持有 lock、尚未释放时，进程接收信号，控制转入 handler。[00:52:00–00:52:14]
4. handler 也调用 `printf`，第二次调用试图获取同一个 lock；因为 lock 已由被打断的 main 持有，它只能等待。[00:52:14–00:52:28]
5. main 只有在 handler 返回后才能继续并释放 lock；handler 却在等这个 lock，双方形成循环等待，事件永远不会发生。[00:52:28–00:52:51]

老师把这种“进程等待一个永远不会发生的事件”称为经典 deadlock。[00:52:32–00:52:51]

### 3. 用课程 SIO 库安全输出

直接使用 `write` 较难，所以老师在 `csapp.c` 中提供了一个可重入 Safe I/O（SIO）小库。[00:53:02–00:53:31] [课件: 15-ecf-signals.pptx p.33]

- `Sio_puts`：输出字符串；
- `Sio_putl`：输出一个 `long`；
- `Sio_error`：输出消息并退出。[00:53:14–00:53:51]

这些接口可以在课程的 signal handler 中安全使用。[00:53:51–00:53:57] 原 Bomb Lab `SIGINT` 示例改用 `Sio_puts`、`sleep` 和 `_exit` 后，handler 中每个调用都是 async-signal-safe。[00:53:57–00:54:13] [课件: 15-ecf-signals.pptx p.33]

### 4. 错误的 `SIGCHLD` handler：一次调用只 `wait` 一次

老师回到开场 shell 问题，安装 `SIGCHLD` handler 来回收后台子进程。[00:54:13–00:54:56]

`fork14` 创建 `N` 个子进程，每个 sleep 一段时间后退出；父进程把全局 `ccount` 设为 `N`，然后自旋到 `ccount == 0`。[00:54:56–00:55:31] handler 每次执行只调用一次 `wait(NULL)`、把 `ccount` 减一并输出被回收 PID。[00:55:31–00:56:11] [课件: 15-ecf-signals.pptx p.34]

当 `N=5`，实际只打印两次 “Handler reaped child”，即五个孩子终止却只回收两个，`ccount` 无法归零。[00:56:11–00:56:44]

### 5. 失败根因：递送次数可能折叠成一次接收

错误假设是“一次 handler 执行对应一个子进程终止”。[00:56:44–00:57:05] 实际上多个 `SIGCHLD` 可以在进程尚未被调度接收时连续递送，它们反复设置同一个 pending bit；即使递送三次，也可能只接收一次。[00:57:05–00:57:38]

因此一次 `SIGCHLD` 接收能推出的是：

```text
至少一个子进程已经终止
```

而不能推出：

```text
恰好一个子进程已经终止
```

[00:57:38–00:58:12]

### 6. 正确 handler：循环回收，直到没有更多孩子

修复方法是在 handler 中循环调用 `wait`，一次信号接收后把当前所有可回收的终止子进程都处理掉。[00:58:12–00:58:46] [课件: 15-ecf-signals.pptx p.35]

```c
while ((pid = wait(NULL)) > 0) {
    ccount--;
    Sio_puts("Handler reaped child ");
    Sio_putl((long)pid);
    Sio_puts(" \n");
}
if (errno != ECHILD)
    Sio_error("wait error");
```

当没有更多子进程可回收时，`wait` 返回 `-1` 且 `errno == ECHILD`；课堂代码把它视为正常循环终点，只有其他 `errno` 才报告错误。[00:58:40–00:59:06]

修改后运行 `N=5` 的程序，五个子进程全部被回收。[00:59:06–00:59:14]

老师再次列出信号问题清单：handler 易写得不安全、语义易理解错、不同 Unix 版本还可能不可移植。[00:59:14–00:59:39] 本段解决前两项，下一段从旧系统处理器复位差异开始解决第三项。

## 概念、符号与推导

### async-signal-safe 与 reentrant

- **reentrant**：每个并发调用实例只使用自己的栈上数据，不共享可变全局状态。[00:49:45–00:50:04]
- **async-signal-safe**：可重入，或不会被信号中断；因此在异步 handler 中调用不会因内部共享状态遭到重入破坏。[课件: 15-ecf-signals.pptx p.32]
- **安全名单以课堂列举为边界**：`_exit`、`write`、`wait`、`waitpid`、`sleep`、`kill`；不安全例子是 `printf`、`sprintf`、`malloc`、`exit`。[00:50:12–00:50:33] [课件: 15-ecf-signals.pptx p.32]

### `printf` 死锁的等待环

```text
main printf 持有 lock
→ signal handler 打断 main
→ handler printf 等待同一 lock
→ lock 只有 main 恢复后才释放
→ main 只有 handler 返回后才恢复
→ 永久等待（deadlock）
```

该因果环来自 [00:51:21–00:52:51]。

### `SIGCHLD` 的正确逻辑量词

```text
receive(SIGCHLD) ⇒ terminated_children_count ≥ 1
receive(SIGCHLD) ⇏ terminated_children_count = 1
```

因此正确操作不是“处理一个”，而是“检查并回收所有当前已终止者”。[00:57:38–00:58:46]

## 常见误解与边界

1. **误解：函数平时线程内可用，handler 中也必然可用。** `printf` 的内部 lock 在异步重入时会形成死锁。[00:51:21–00:52:51]

## 本段在整讲中的作用

## 教学展开

### 1. 旧 Unix 的三种信号语义差异

老师从三个可移植性问题讲起：[00:59:39–01:01:48] [课件: 15-ecf-signals.pptx p.36]

1. 某些旧系统在捕获一次信号后会把动作恢复为默认值，因此 handler 每次运行时还得重新安装自己；Linux 不要求这样做。[00:59:39–01:00:00]
2. 某些系统上的 slow syscall 被信号打断后会返回错误 `errno == EINTR`，用户代码必须重试。[01:00:00–01:01:42]
3. 某些系统不会自动阻塞当前正在处理的同类型信号。[01:01:42–01:01:48]

### 2. `read` 为什么是 slow syscall，`EINTR` 从何而来

老师用 `read` 解释 slow syscall：内核向磁盘控制器发出请求后，不会占着 CPU 等数据，而是调度其他进程；数据到达并产生中断后，`read` 才完成并返回。[01:00:10–01:00:44]

在某些系统中，若等待期间进程接收信号，内核会中止这次尚未完成的系统调用，使 `read` 返回错误 `EINTR`。[01:00:54–01:01:23] 这不是用户传参错误，只是调用碰巧被信号打断；如果接口不自动重启，用户程序就要循环重试直到成功。[01:01:23–01:01:42]

### 3. 用 `sigaction` 构造课程的 `Signal` 包装器

解决方案是用更新、可预测的 `sigaction` 取代直接使用旧 `signal` 语义。[01:01:48–01:02:08] 老师在 `csapp.c` 中提供大写 `Signal` 包装器，调用形式与小写 `signal` 相同，但内部配置 `sigaction`。[01:02:08–01:02:37] [课件: 15-ecf-signals.pptx p.36]

```c
handler_t *Signal(int signum, handler_t *handler)
{
    struct sigaction action, old_action;

    action.sa_handler = handler;
    sigemptyset(&action.sa_mask);
    action.sa_flags = SA_RESTART;

    if (sigaction(signum, &action, &old_action) < 0)
        unix_error("Signal error");
    return old_action.sa_handler;
}
```

课堂强调的效果是：当前处理类型会被阻塞，且被信号打断的 slow syscall 在可能时自动重启。[01:02:37–01:02:55] 因此课程代码应调用大写 `Signal` 包装器。[01:02:29–01:02:55]

### 4. 看似保护正确的作业表程序

老师随后研究并发逻辑流产生的微妙错误。[01:03:01–01:03:27] 简化 shell 维护 job list：创建孩子后加入作业，孩子终止后由 `SIGCHLD` handler 从表中删除。[01:03:27–01:03:48]

main 的循环做：

```text
Fork
→ child: Execve("/bin/date", ...)
→ parent: block all signals
→ addjob(pid)
→ restore previous mask
```

[01:03:49–01:04:18] [课件: 15-ecf-signals.pptx p.37]

handler 则循环 `waitpid(-1, NULL, 0)` 回收所有终止子进程，并在每次 `deletejob(pid)` 前阻塞所有信号，之后恢复；同时保存和恢复 `errno`。[01:04:18–01:04:53] [课件: 15-ecf-signals.pptx p.38]

因此 main 的 `addjob` 与 handler 的 `deletejob` 各自都保护了共享作业表，单次数据结构修改不会被另一 handler 插入。[01:04:53–01:05:16]

### 5. 课堂提问：什么执行顺序仍会使程序失败？

老师让学生找隐藏 bug。[01:05:16–01:05:37] 学生指出：fork 后可能先调度 child，child 运行 `/bin/date` 并终止，而 parent 还没来得及 `addjob`。[01:05:37–01:06:23]

错误交错为：

```text
parent: Fork
child: Execve → terminate
parent: receive SIGCHLD → handler: deletejob(pid)  // 作业尚不存在
parent: addjob(pid)                                // 加入已终止作业
```

最终 job list 中留下一个永远不会再由相应终止事件删除的陈旧项。[01:06:23–01:06:44]

根因是程序暗含了“父进程先于子进程运行”的假设；fork 后不能假设父子调度顺序，也不能假设 child 会运行多久。[01:05:53–01:06:22] 老师借此提醒，并发错误来自多种可能交错，即使每个局部临界区看似正确也会失败。[01:06:44–01:07:15]

### 6. 无法控制调度，但可以控制 handler 的执行窗口

修复目标是防止 `SIGCHLD` handler 在父进程登记作业之前运行。[01:07:24–01:07:44] 程序不能控制 parent/child 谁先执行，也不能控制 child 生命周期，却可以用 mask 控制 handler 何时能接收 `SIGCHLD`。[01:07:44–01:08:00]

正确顺序从 **fork 前** 开始：[01:08:00–01:09:36] [课件: 15-ecf-signals.pptx p.39]

1. main 构造只含 `SIGCHLD` 的 `mask_one`，在 `Fork()` 前调用 `Sigprocmask(SIG_BLOCK, &mask_one, &prev_one)`。[01:08:00–01:08:22]
2. child 继承 parent 的 blocked bit vector，因此 fork 返回 child 路径时 `SIGCHLD` 也被阻塞。[01:08:22–01:08:51]
3. child 将来可能创建并回收自己的孩子，所以在 `Execve` 前恢复 `prev_one`，解除继承来的临时阻塞。[01:08:51–01:09:25]
4. parent 在 `SIGCHLD` 仍被阻塞时保护作业表并执行 `addjob(pid)`；之后恢复旧 mask，才允许 pending 的 `SIGCHLD` 被接收。[课件: 15-ecf-signals.pptx p.39]

本片段在老师即将说明“handler 只能在 `addjob` 后运行”时结束，结论在下一节开头补完。[01:09:25–01:09:36]

## 概念、符号与推导

### `sigaction` 包装器中的字段

- `action.sa_handler = handler`：指定用户处理函数。[课件: 15-ecf-signals.pptx p.36]
- `sigemptyset(&action.sa_mask)`：课件注释与课堂效果说明当前处理类型会被阻塞；本讲不继续展开字段细节。
- `action.sa_flags = SA_RESTART`：尽可能自动重启被信号打断的 slow syscalls。[01:02:37–01:02:55]
- 返回 `old_action.sa_handler`：保留原动作的 handler 地址。[课件: 15-ecf-signals.pptx p.36]

### 第一版程序的先行关系缺口

第一版仅保证：

```text
单次 addjob 内不被 handler 打断
单次 deletejob 内不被其他 handler 打断
```

却没有保证：

```text
addjob(pid) happens before deletejob(pid)
```

所以共享结构“每次操作原子”仍不足以保证跨操作的业务顺序。[01:04:53–01:06:44]

### mask 建立正确先行关系

```text
block(SIGCHLD)
→ Fork
→ parent addjob(pid)
→ unblock(SIGCHLD)
→ handler may deletejob(pid)
```

若 child 早终止，`SIGCHLD` 只能先 pending；因为 blocked，handler 不能越过 `addjob` 执行。该推导由 [01:07:24–01:09:36] 和课件 p.39 给出。

## 常见误解与边界

1. **误解：Linux 上运行正确就表示所有 Unix 上语义相同。** 老师列出动作复位、`EINTR`、同类型阻塞三类差异。[00:59:39–01:01:48]
2. **误解：`EINTR` 表示 `read` 参数错误。** 它可能只表示 slow syscall 被信号打断，需要重试或由 `SA_RESTART` 自动处理。[01:00:54–01:02:55]
3. **误解：main 和 handler 分别保护 `addjob`/`deletejob` 就没有竞态。** 数据结构局部一致仍不能保证添加先于删除。[01:04:53–01:06:44]
4. **误解：fork 返回后 parent 必然先运行。** 调度顺序没有这种保证；child 可以先完成并终止。[01:05:37–01:06:22]
5. **误解：在 `addjob` 前一刻阻塞 `SIGCHLD` 足够。** child 可能已在 fork 后、阻塞前终止；必须在 fork **之前** 阻塞。[01:07:24–01:08:22]
6. **误解：child 不需要恢复继承的 mask。** 它执行的新程序可能需要正常处理自己的 `SIGCHLD`，所以 `execve` 前恢复。[01:08:22–01:09:25]

# 第 8 节：等待信号、`sigsuspend` 与非局部跳转补充

> 时间范围：01:09:36–01:19:15
> 依据：课堂 transcript 与 `15-ecf-signals.pptx` 第 39–54 页；第 48–54 页为课堂明确指定的补充阅读

## 本段在整讲中的作用

本段先收束作业表竞态：因为 parent 在 `addjob` 后才解除 `SIGCHLD`，handler 不可能先删除未登记作业。[01:09:36–01:10:05] 随后老师提出真实 shell 的另一个同步问题：所有 `wait` 都放在 `SIGCHLD` handler 后，main 如何高效等待前台作业结束？课堂依次否定忙等、`pause` 和固定 `sleep`，最终用 `sigsuspend` 把“临时解除 mask + 挂起”等待合成不可分割操作。[01:10:12–01:18:59]

视频最后只用一句话点到 non-local jumps，并明确让学生看教材和补充课件。[01:19:01–01:19:15] 因用户要求完整保留该主题，本节在课堂时间线之后单列 p.48–54：内容均来自课件，不能视为老师在视频中逐页讲授。

## 教学展开

### 1. 完成修正版作业表的因果证明

`SIGCHLD` 在 fork 前已被阻塞，parent 完成 `addjob` 后才解除阻塞；因此即使 child 很早终止，handler 也只能在作业已经入表后运行。[01:09:36–01:09:45] [课件: 15-ecf-signals.pptx p.39]

老师明确提示该错误与修复和 Shell Lab 直接相关，学生要避免依赖 parent 先运行的假设。[01:09:45–01:10:05]

### 2. 新问题：`wait` 全在 handler，main 如何等前台作业？

简化 shell 曾在 main 中直接 `wait` 前台孩子；真实 shell 则让 `SIGCHLD` handler 负责所有 `wait`/回收，main 不能再同时等待同一孩子。[01:10:12–01:10:40]

解决思路是让 handler 回收前台作业时设置一个全局 PID flag，main 等这个 flag 从 0 变为非零。[01:10:41–01:11:32] [课件: 15-ecf-signals.pptx p.40]

```c
volatile sig_atomic_t pid;

void sigchld_handler(int s)
{
    int olderrno = errno;
    pid = Waitpid(-1, NULL, 0);
    errno = olderrno;
}
```

handler 只设置 flag 并恢复 `errno`，符合前述简化原则；示例还安装一个空的 `SIGINT` handler。[课件: 15-ecf-signals.pptx p.40]

### 3. 忙等正确，但浪费处理器

main 在 fork 前阻塞 `SIGCHLD`，fork 后 parent 把 `pid=0`，再解除阻塞；随后循环检查 flag：[01:11:32–01:12:13] [课件: 15-ecf-signals.pptx p.41]

```c
while (!pid)
    ;
```

这个版本在课堂设定下逻辑正确，但紧密自旋不断消耗 CPU，等待时间又未知，所以极其浪费。[01:12:13–01:12:38]

### 4. `while (!pid) pause();` 有检查-睡眠竞态

学生常想到在循环里用 `pause()`，让进程等待 handler 后再检查 flag。[01:12:38–01:13:09]

必须保留循环，因为程序还安装了其他 handler，例如 `SIGINT`；任一 handler 都可让 `pause` 返回，但 main 只应在 `SIGCHLD` handler 已设置 `pid` 后结束等待。[01:13:09–01:13:40]

然而这段代码仍然错误：

```c
while (!pid)       /* 检查时 pid == 0 */
    pause();       /* 调用前存在窗口 */
```

若 `SIGCHLD` 恰在条件检查之后、`pause()` 执行之前被接收，handler 已把 `pid` 设为非零；随后 main 仍进入 `pause`，等待一个已经发生、可能不会再来的信号，于是永久阻塞。[01:13:40–01:15:02] [课件: 15-ecf-signals.pptx p.42]

### 5. `sleep(1)` 没有该竞态，但快慢无法兼得

把 `pause` 换成固定 `sleep(1)` 后，main 最终会醒来重查 flag，因此是正确的；但一秒在系统尺度上太慢。[01:15:02–01:15:34]

即使用纳秒级 sleep，也必须选择时长：太大增加响应延迟，太小又频繁唤醒、接近忙等的低效率。[01:15:34–01:15:59]

### 6. `sigsuspend` 把改 mask 与等待合成原子操作

`sigsuspend(const sigset_t *mask)` 接收一个 signal mask。老师将它解释为以下三步的不可中断版本：[01:15:59–01:17:13] [课件: 15-ecf-signals.pptx p.43]

1. 临时使用给定 mask；
2. 挂起进程等待信号；mask 的改变与进入等待之间没有可插入信号接收的窗口；
3. handler 执行使等待返回后，恢复原来的 mask。

消除竞态的关键是前两步原子执行，信号不可能恰好落在“解除阻塞之后、真正 pause 之前”的缝隙里。[01:16:19–01:17:05]

### 7. 正确等待循环

完整模式如下：[01:17:13–01:18:59] [课件: 15-ecf-signals.pptx p.44]

```c
Sigprocmask(SIG_BLOCK, &mask, &prev); /* mask 含 SIGCHLD */
if (Fork() == 0)
    exit(0);

pid = 0;
while (!pid)
    Sigsuspend(&prev);  /* prev 中 SIGCHLD 原本未阻塞 */

Sigprocmask(SIG_SETMASK, &prev, NULL);
```

推理顺序：

1. fork 前阻塞 `SIGCHLD`，所以 child 即使立即终止，handler 也暂时不能运行。[01:17:13–01:17:33]
2. parent 安全地把 `pid` 置零。[01:17:33–01:17:40]
3. `Sigsuspend(&prev)` 原子地临时采用旧 mask；旧 mask 中 `SIGCHLD` 未阻塞，所以 pending 的 `SIGCHLD` 可以被接收，handler 设置 `pid`。[01:17:40–01:18:20]
4. 若先被其他信号（如 `SIGINT`）打断，`pid` 仍为 0，循环再次调用 `Sigsuspend(&prev)`；因此不能去掉 `while`。[01:18:27–01:18:48]
5. 一旦 `SIGCHLD` handler 设置非零 `pid`，循环退出。方案不忙等，也没有检查-睡眠窗口。[01:18:48–01:18:59]

### 8. 课堂结束与证据边界

老师在 [01:18:59] 宣布本讲结束。随后只描述 non-local jumps 是 C 中一种“奇怪的机制”，可以让函数转移到一个并非直接调用者的位置；详细内容应看教材和附加课件。[01:19:01–01:19:15] 课件总结信号提供进程级异常处理，可由用户程序触发并用 handler 定义效果，但 handler 必须格外谨慎；非局部跳转在进程内部提供异常控制流，并受栈纪律约束。[课件: 15-ecf-signals.pptx p.45] [课件: 15-ecf-signals.pptx p.46]

### 9. 补充课件：`setjmp` 建立返回环境（非视频逐页讲授）

课件把 non-local jump 定义为强大但危险的用户级控制转移机制：它以受控方式打破普通“调用—返回”纪律，可用于错误恢复与信号处理。[课件: 15-ecf-signals.pptx p.48]

```c
int setjmp(jmp_buf j);
```

- 必须先于 `longjmp` 调用；
- 在 `j` 中标记未来跳转的返回位置；
- 保存当前寄存器上下文、stack pointer 与 PC；
- 第一次直接调用返回 0；函数在源码中调用一次，却可能因后续跳转表现为返回多次。[课件: 15-ecf-signals.pptx p.48]

### 10. 补充课件：`longjmp` 恢复环境

```c
void longjmp(jmp_buf j, int i);
```

`longjmp` 让先前由 `j` 记住的 `setjmp` 位置“再次返回”，这次返回值为 `i`。它在 `setjmp` 之后调用，本身不会按普通调用/返回路径返回。[课件: 15-ecf-signals.pptx p.49]

课件给出的实现模型是：从 jump buffer 恢复寄存器上下文（含 stack pointer、base pointer、PC），把 `%eax` 设为 `i`，再跳到保存的 PC。[课件: 15-ecf-signals.pptx p.49]

### 11. 补充课件：从深层 `bar` 直接回到 `main`

课件示例的目标是从深层函数直接回到原始调用者。[课件: 15-ecf-signals.pptx p.50] [课件: 15-ecf-signals.pptx p.51]

```text
main: setjmp(buf) 首次返回 0
→ case 0 调用 foo()
→ error1 == 0，所以 foo 调用 bar()
→ error2 == 1，所以 bar 执行 longjmp(buf, 2)
→ 恢复 main 中 setjmp 的环境
→ setjmp 表现为返回 2
→ switch 进入 case 2，打印 error2 条件
```

`longjmp(buf, 1)` 与 `longjmp(buf, 2)` 用返回值把不同深层错误映射到 `switch` 的不同处理分支。[课件: 15-ecf-signals.pptx p.50] [课件: 15-ecf-signals.pptx p.51]

### 12. 补充课件：必须遵守栈纪律

合法模式中，`P1` 调用 `setjmp(env)` 后继续调用 `P2`，递归/嵌套到 `P3`；`P3` 执行 `longjmp(env, 1)` 时，保存环境所属的 `P1` 调用仍未结束，因此可以丢弃其上的 `P2/P3` 栈帧并恢复 `P1`。[课件: 15-ecf-signals.pptx p.52]

非法边界是：`P2` 保存 `env` 后已经返回，随后 `P1` 再调用 `P3`，而 `P3` 试图跳回已完成的 `P2` 环境。课件结论是只能跳到“已经调用但尚未完成”的函数环境。[课件: 15-ecf-signals.pptx p.53]

### 13. 补充课件：`Ctrl-C` 后重启处理循环

最后的 `restart.c` 把信号与非局部跳转组合：[课件: 15-ecf-signals.pptx p.54]

```c
sigjmp_buf buf;

void handler(int sig)
{
    siglongjmp(buf, 1);
}
```

`main` 首次执行 `sigsetjmp(buf, 1)` 返回 0，安装 `SIGINT` handler 并输出 `starting`；进入循环后每秒输出 `processing...`。按 `Ctrl-C` 运行 handler，`siglongjmp` 回到保存位置，使条件走 `else` 并输出 `restarting`，然后重新进入处理循环。[课件: 15-ecf-signals.pptx p.54]

## 概念、符号与推导

### 三种等待方案比较

| 方案 | 正确性 | 效率 | 课堂结论 |
|---|---|---|---|
| `while (!pid) ;` | 正确 | 持续占 CPU | wasteful [01:12:13–01:12:38] |
| `while (!pid) pause();` | 有检查-等待竞态 | 不忙等 | 可能永久挂起 [01:13:40–01:15:02] |
| `while (!pid) sleep(1);` | 正确 | 响应慢；时长难选 | too slow [01:15:02–01:15:59] |
| `while (!pid) Sigsuspend(&prev);` | 原子解除阻塞并等待 | 不忙等 | 目标方案 [01:15:59–01:18:59] |

### `sigsuspend` 建立的顺序

```text
block(SIGCHLD)
→ Fork
→ pid = 0
→ atomic { temporary mask = prev; suspend }
→ SIGCHLD handler: pid = Waitpid(...)
→ recheck pid
```

原子块消除了 `if (!pid)` 与 `pause()` 之间的丢失唤醒窗口。[01:13:40–01:18:59]

### 非局部跳转的双返回模型（补充课件）

```text
setjmp(j) 直接执行：返回 0
longjmp(j, i) 恢复 j：原 setjmp 位置再次返回 i
```

因此 `setjmp` 源码调用一次、动态上可返回多次；`longjmp` 调用一次、但不返回其调用点。[课件: 15-ecf-signals.pptx p.48] [课件: 15-ecf-signals.pptx p.49]

### 栈纪律边界（补充课件）

```text
允许：目标 setjmp 所在函数仍在调用栈上
禁止：目标函数已经返回，其保存环境已不再有效
```

[课件: 15-ecf-signals.pptx p.52] [课件: 15-ecf-signals.pptx p.53]

## 常见误解与边界

1. **误解：忙等不阻塞，所以是最佳响应方案。** 它逻辑正确，却无意义地消耗 CPU。[01:12:13–01:12:38]
2. **误解：在检查后调用 `pause` 等价于原子等待。** 两条语句之间可以接收目标信号，造成丢失唤醒和永久阻塞。[01:13:40–01:15:02]
3. **误解：把 sleep 调得足够短就同时高效且及时。** 老师指出时长太大则慢、太小则低效，没有自然的固定值。[01:15:34–01:15:59]
4. **误解：`sigsuspend` 返回就一定是 `SIGCHLD`。** 其他 handler 也可使它返回，所以仍需 `while (!pid)` 检查条件。[01:18:27–01:18:48]
5. **误解：视频详细讲授了 non-local jumps。** 老师只在结尾点题；p.48–54 是指定补充阅读，不应配造课堂时间戳。[01:19:01–01:19:15]
6. **误解：`longjmp` 可以跳回任何历史函数。** 目标 `setjmp` 所在函数必须仍未完成，受栈纪律约束。[课件: 15-ecf-signals.pptx p.52] [课件: 15-ecf-signals.pptx p.53]
7. **边界：课件展示 `sigsetjmp(buf, 1)`。** 材料没有在本讲文字中解释第二参数 `1` 的独立语义，本笔记不补写外部定义。[课件: 15-ecf-signals.pptx p.54]

## 本段掌握检查

### 1. 为什么 `while (!pid) pause();` 可能永久阻塞？

**答：** `SIGCHLD` 可在条件检查后、`pause` 前被接收并设置 `pid`；main 随后仍进入 `pause`，但目标事件已经过去，可能再无信号唤醒。[01:13:40–01:15:02]

### 2. `sigsuspend(&prev)` 如何消除这个窗口？

**答：** 它原子地临时采用 `prev` mask 并进入挂起，解除 `SIGCHLD` 阻塞与等待之间不能插入信号接收；handler 后再检查 flag。[01:15:59–01:18:59]

### 3. 为什么正确代码仍把 `Sigsuspend` 放在 `while (!pid)` 中？

**答：** `SIGINT` 等其他信号也可能执行 handler 并使等待返回；循环确保只有 `SIGCHLD` handler 真正设置 `pid` 后才继续。[01:13:09–01:13:40] [01:18:27–01:18:48]

### 4. `setjmp` 与 `longjmp` 的返回行为有何不对称？

**答：** `setjmp` 调用一次但可先返回 0、再因 `longjmp(j,i)` 表现为返回 `i`；`longjmp` 自身不返回调用点，而是恢复保存环境。[课件: 15-ecf-signals.pptx p.48] [课件: 15-ecf-signals.pptx p.49]

### 5. non-local jump 的栈纪律是什么，`restart.c` 如何组合信号？

**答：** 只能跳到仍在调用栈上、尚未完成函数的保存环境；`restart.c` 的 `SIGINT` handler 调用 `siglongjmp` 回到 `sigsetjmp`，输出 `restarting` 后继续处理循环。[课件: 15-ecf-signals.pptx p.52] [课件: 15-ecf-signals.pptx p.53] [课件: 15-ecf-signals.pptx p.54]
