## 全讲目标

老师沿两条相互连接的主线展开本讲 [00:00:00–00:00:30] [课件: 18-vm-systems.pptx p.2]：

1. **硬件地址翻译线：** 从一个可手算的 14-bit VA/12-bit PA 系统出发，逐位走过 `VA → TLB → page table → PA → cache`；再换成 Core i7 的 48-bit VA、分层 TLB、四级页表与 virtually indexed/physically tagged L1 cache。
2. **操作系统映射线：** 从 Linux process address space 与 `vm_area_struct` 出发，解释 page-fault handler 如何判定访问，随后用 memory mapping、shared objects 和 private COW 重新解释 `fork`、`execve` 与 user-level `mmap`。

讲授的最终落点不是把虚拟内存只看作“磁盘缓存”，而是把它看成贯穿硬件翻译、进程隔离、共享、装载和系统调用的统一机制 [01:10:32–01:10:48]。

## 全讲核心链路

### 1. 地址翻译与数据访问

简化系统和 Core i7 的共同骨架是：

```text
CPU generates VA
  → split VPN | VPO
  → look up VPN in TLB
      hit: obtain PPN
      miss: walk page table(s), then obtain PPN or fault
  → form PA = PPN | PPO, where PPO = VPO
  → split PA into CT | CI | CO
  → access cache; on miss continue to lower cache/memory levels
```

玩具系统用 `0x03D4` 展示 TLB hit + cache hit，用 `0x0020` 展示 TLB miss + page-table hit + cache miss [00:04:52–00:15:13] [课件: 18-vm-systems.pptx p.8] [课件: 18-vm-systems.pptx p.9]。Core i7 则把 48-bit VA 拆为 `VPN(36) | VPO(12)`，再把 VPN 分成四个 9-bit page-table indices；TLB hit 可跳过 walk，miss 时从 `CR3` 开始级联 [00:24:58–00:35:55] [课件: 18-vm-systems.pptx p.14] [课件: 18-vm-systems.pptx p.17]。

### 2. Mapping、fault 与进程语义

```text
VM area ↔ backing object
  → page absent on first access
  → page fault
  → kernel checks area range and protection
      no area: segmentation fault
      permission violation: protection exception / segmentation fault
      legal access: fault in file-backed or demand-zero page
```

在此基础上：shared mapping 让不同进程的不同 VA 指向相同 physical pages；private COW 也先共享，但把 PTE 标为 read-only，在第一次 write fault 时复制目标页 [00:53:32–01:04:57] [课件: 18-vm-systems.pptx p.24] [课件: 18-vm-systems.pptx p.27]。`fork` 利用 COW 延迟 data-page copy；`execve` 只重建 areas/page tables/mappings，并由后续 faults 按需载入新程序；`mmap` 把同一机制提供给用户程序 [01:00:33–01:17:29] [课件: 18-vm-systems.pptx p.28] [课件: 18-vm-systems.pptx p.29] [课件: 18-vm-systems.pptx p.30]。

### 004｜四级页表、L1 并行查找与 Linux 开场（00:29:53–00:39:49）

详见 [notes/sections/004.md](#section-04)。老师先完成 PTE 字段：P、R/W、U/S、WT、A、PS、XD，以及最终 Level 4 PTE 的 D bit；前三层权限作用于可达 pages，最后一层直接描述 actual page，dirty bit 帮 OS 判断 victim 是否需写回 [00:29:53–00:33:18] [课件: 18-vm-systems.pptx p.15] [课件: 18-vm-systems.pptx p.16]。

36-bit VPN 分成 4×9 bits，从 `CR3 → L1 → L2 → L3 → L4 PTE → PPN`，每级 512 entries，覆盖量依次为 512 GB、1 GB、2 MB、4 KB [00:33:26–00:35:55] [课件: 18-vm-systems.pptx p.17]。因为 L1 的 CI+CO 恰好位于不因翻译改变的 12-bit VPO/PPO 中，cache 可以在 MMU 翻译同时先选组，最后等待 physical tag；课件称之为 virtually indexed, physically tagged [00:36:09–00:38:27] [课件: 18-vm-systems.pptx p.18]。之后开始 Linux layout 的 `.text/.data/.bss/heap` [00:38:32–00:39:49] [课件: 18-vm-systems.pptx p.19]。

### 005｜Linux VM areas 与 page-fault handling（00:39:49–00:49:41）

详见 [notes/sections/005.md](#section-05)。老师补全 mapped libraries、downward user stack 与 high-address kernel，并用 48-bit address 的高位扩展规则解释 stack/kernel 之间的空洞 [00:39:49–00:41:41]。translation 对 kernel 也始终开启，因此 kernel 通过一片按偏移对应 DRAM 的 virtual region 访问 physical memory [00:41:46–00:43:25] [课件: 18-vm-systems.pptx p.19]。

Linux 数据结构链是 `task_struct → mm_struct → pgd/mmap → vm_area_struct`；调度时 `pgd` 装入 `CR3`，areas 保存范围、权限和 shared/private flags [00:44:00–00:46:28] [课件: 18-vm-systems.pptx p.20]。page-fault handler 据此分出不存在的地址、权限违规和合法但 absent 的 page，只有第三种正常调页；前两种向进程报告 segmentation fault [00:46:32–00:49:06] [课件: 18-vm-systems.pptx p.21]。

### 006｜Memory mapping、shared objects 与 private COW（00:49:41–00:59:34）

详见 [notes/sections/006.md](#section-06)。VM area 与 disk object 的 association 称为 memory mapping；regular file 可给 executable code 提供初值，anonymous file 是概念上的全 0 backing，首次 fault 分配 demand-zero page，写脏后按普通页和 swap 处理 [00:50:42–00:53:32] [课件: 18-vm-systems.pptx p.22] [课件: 18-vm-systems.pptx p.23]。

两个进程可在不同 VA 映射同一 shared object，最终使用相同 physical pages；老师以多个 Apache processes 的 shared cache 为例 [00:53:32–00:55:55] [课件: 18-vm-systems.pptx p.24] [课件: 18-vm-systems.pptx p.25]。private COW 初始也共享，但 area 标为 private COW、PTE read-only；读不复制，写触发 protection fault，handler 创建 R/W 副本并重启 instruction [00:56:01–00:59:13] [课件: 18-vm-systems.pptx p.26] [课件: 18-vm-systems.pptx p.27]。

### 007｜`fork` COW 与 `execve`（00:59:34–01:09:28）

详见 [notes/sections/007.md](#section-07)。老师先把多核访问的具体 ordering 归入 consistency model，并说明超出本处范围 [00:59:34–01:00:32]。`fork` 必须复制 `mm_struct`、`vm_area_struct`s 与 page tables，但不立即复制全部 data pages；两边 PTE 设 read-only、areas 设 private COW，直到某方写某页才经 fault 复制该页并 restart write [01:00:33–01:04:57] [课件: 18-vm-systems.pptx p.28]。

`execve` 不创建新进程，而是在 current process 中释放旧 areas/page tables、建立新程序 mappings：`.text/.data` private file-backed，`.bss`、heap、stack private demand-zero，shared-library 的只读内容可 shared file-backed，而 writable per-process state 需 private COW [01:04:57–01:09:28] [课件: 18-vm-systems.pptx p.29]。

### 008｜Demand loading、user-level `mmap` 与 `mmapcopy`（01:09:28–01:17:37）

详见 [notes/sections/008.md](#section-08)。`execve` 把 `RIP` 指向 `.text` entry 时只完成 structures/mappings；第一条 instruction 和后续 data access 才 fault in 所需 pages。大型非零初始化 array 说明按需装载也能避免复制未访问的 file-backed data [01:09:28–01:11:24] [课件: 18-vm-systems.pptx p.29]。

`mmap(start,len,prot,flags,fd,offset)` 把 file 中 `[offset, offset+len)` 与一个同长 virtual region 关联；`start` 是 hint，真实地址看返回 pointer；`MAP_ANON` 产生 demand-zero backing，`MAP_PRIVATE/MAP_SHARED` 决定共享语义 [01:11:24–01:15:26] [课件: 18-vm-systems.pptx p.30] [课件: 18-vm-systems.pptx p.31]。`mmapcopy` 打开 `argv[1]`、取 size、以 `PROT_READ|MAP_PRIVATE` 映射整个文件，再 `Write(1,bufp,size)`；`write` 读取映射区时 pages 按需 fault in [01:15:26–01:17:29] [课件: 18-vm-systems.pptx p.32]。最后 segment 是周末告别 [01:17:32–01:17:37]。

## 重点误区总表

| 误区 | 本讲纠正 |
|---|---|
| TLB miss 就是 page fault | TLB miss 只要求查 PTE；PTE present 时仍可完成翻译 [00:12:19–00:13:35] |
| PPN 与 cache tag 天然相等 | 玩具参数中的重合纯属巧合；二者独立 [00:15:57–00:17:13] |
| Core i7 没有 TLB hierarchy | 老师撤回上一讲说法，明确有 L1 d/i-TLB 与 unified L2 TLB [00:20:27–00:21:58] |
| L1 必须等完整 PA 才开始 | CI/CO 可由 VPO 提前使用，physical tag 稍后比较 [00:36:33–00:38:27] |
| page fault 都应把页调入 | 地址不存在或权限违规应报告 fault；只有合法 absent page 正常调入 [00:46:32–00:49:06] |
| COW 在 `fork` 时复制全部 data | 只复制描述结构；data page 在首次 write 时逐页复制 [01:01:55–01:04:57] |
| `execve` 创建新进程并立即加载全部内容 | 它替换 current process mappings，code/data 按访问 fault in [01:05:18–01:10:32] |
| `mmap` 立即把文件复制进 buffer | 它先建立 mapping；缺页在实际访问时按 backing file 填充 [01:14:02–01:15:26] |

# 001｜简化内存系统与地址翻译示例 1（前半）

**时间范围：00:00:00–00:10:00**

## 本段在整讲中的作用

# 002｜地址翻译示例 2与 Core i7 内存层次开场

## 本段在整讲中的作用

## 教学展开

### 1. 收尾示例 1：纠正 byte offset

老师明确纠正上一段的口误：物理地址中的 cache offset 实际为 0，不是 2 [00:10:00-00:10:13]。因此 set 5、tag=`0x0D` 命中后，应取该 cache line 的 byte 0，值为 `0x36`；cache 把它交给 MMU，再由 MMU 交回处理器，通常进入寄存器 [00:10:14-00:10:31] [课件: 18-vm-systems.pptx p.8]。

### 2. 示例 2：拆解虚拟地址 `0x0020`

CPU 把 `0x0020` 交给 MMU [00:10:48-00:10:58]。老师先写出位串，再标出 VPO、VPN、VPN 低位构成的 TLBI，以及剩余 TLBT [00:10:58-00:11:26]。结果是：VPN=`0x00`、VPO=`0x20`、TLBI=0、TLBT=`0x00` [课件: 18-vm-systems.pptx p.9]。

### 3. TLB miss：tag 相等仍可能无效

TLBI=0 指向 set 0，目标 tag 为 0 [00:11:26-00:11:57]。老师逐项检查：`0x03`、`0x09` 等 tag 不匹配；其中虽有 tag 0，但 valid=0，因此只是数值巧合，不能命中 [00:12:04-00:12:19]。结论是 TLB miss，代价是离开芯片去内存读取页表项 [00:12:19-00:12:35]。

### 4. 页表 hit：由 VPN 取得 PPN

MMU 用 VPN 0 检查页表第 0 项 [00:12:35-00:13:04]。该项 valid=1，说明页在物理内存中，并给出 PPN=`0x28`；内存把 PTE/PPN 返回给 MMU [00:13:04-00:13:35] [课件: 18-vm-systems.pptx p.6] [课件: 18-vm-systems.pptx p.9]。这里是 TLB miss，但不是 page fault。

### 5. 形成物理地址并发生 cache miss

MMU 把 VPO=`0x20` 原样复制为 PPO，并与 PPN=`0x28` 拼接，得到物理地址 `0xA20` [00:13:35-00:14:12]。cache 从中取 CO=0、CI=`0x8`、CT=`0x28`；于是检查 set 8 [00:14:13-00:14:48]。该行有效 tag 是 `0x24`，与 `0x28` 不同，故 cache miss；cache 必须把物理地址交给主存取字节 [00:14:48-00:15:13] [课件: 18-vm-systems.pptx p.7] [课件: 18-vm-systems.pptx p.9]。

### 6. 用学生提问澄清两个位宽问题

学生问页偏移大小如何决定。老师回到 64 B 页，所以 VPO/PPO 都是 6 位，并提示这是可能出现在考试中的基本推导 [00:15:14-00:15:45]。另一问题询问 PPN 与 cache tag 长度是否相关；老师反复强调二者在这个例子中对齐完全是巧合、彼此独立 [00:15:57-00:17:13]。若 cache 有更多 sets，CI 需要更多位并会越过当前页内偏移位段，此时 CT 就不再与 PPN 对齐 [00:16:25-00:16:57]。

### 7. 转入真实 Core i7

老师从 [00:17:28] 开始介绍与实验室 shark 机器相近的高端桌面 Core i7/x86-64 系统 [00:17:28-00:17:56]。一个 processor package 含 4 个 core；每个 core 有自己的 CPU/寄存器和指令执行能力 [00:17:56-00:18:28]。每个 core 有分离的 32 KB、8 路 L1 d-cache 与 i-cache，前者保存数据、后者保存指令 [00:18:28-00:19:11]；再下一级是同一 core 内可同时容纳数据和指令的 256 KB、8 路 unified L2 [00:19:11-00:19:33]；core 外还有所有 core 共享的 8 MB、16 路 L3 [00:19:35-00:19:45] [课件: 18-vm-systems.pptx p.12]。本段最后只给出 L1 访问约 4 cycles [00:19:45-00:19:54]，L2/L3 时延留到下一段。

## 教学展开

### 1. 补全 cache 访问代价

L2 比 L1 更大、距离 core 更远，访问约 10 cycles [00:19:54-00:20:02]。L3 在 core 外，访问需跨过连接，老师给出的量级约为 30–50 cycles [00:20:02-00:20:27]。这与上一段的 L1 约 4 cycles 一起展示了层次越远、容量越大、延迟越高的关系；课件同时给出 L1/L2/L3 的容量和相联度 [课件: 18-vm-systems.pptx p.12]。

### 2. 明确纠正：Core i7 有 TLB 层次

老师主动说明，他上一讲课后曾错误地说系统没有 TLB hierarchy；真实 Core i7 确实有 [00:20:27-00:20:45]。第一级分成 data TLB 与 instruction TLB：L1 d-TLB 有 64 entries、4-way，因此是 $64/4=16$ sets [00:20:45-00:21:16]；L1 i-TLB 有 128 entries、4-way；其下还有更大的 512-entry、4-way unified L2 TLB [00:21:17-00:21:50] [课件: 18-vm-systems.pptx p.12]。

老师观察到 i-TLB 比 d-TLB 大，并猜测可能是 instruction miss 的代价更大，但马上两次声明自己不确定，只是在推测 [00:21:17-00:21:48]。这不能整理成已证实的设计原因。

### 3. 为什么在分离 L1 下放一个 unified L2 TLB

老师先把“为何不直接扩大两个 L1 TLB”作为设计问题 [00:21:50-00:22:53]。若预先把所有晶体管预算固定分给 d-TLB 与 i-TLB，程序实际的 data PTE 与 instruction PTE 工作集比例一旦偏斜，某一边仍会 capacity miss，另一边的空余又不能借用 [00:22:53-00:24:06]。统一的 L2 相当于对两类需求“hedge your bets”：L1 miss 的 penalty 因 L2 存在而下降，同时共享容量可适应不同程序的比例 [00:24:06-00:24:27]。老师把这说成设计思路，而非形式化证明。

### 4. 从 CPU 的 48 位 VA 开始端到端翻译

CPU 生成 48 位虚拟地址；页大小 4 KB，即 $2^{12}$ B，所以 VA 分为 VPN 36 位与 VPO 12 位 [00:24:44-00:25:20] [课件: 18-vm-systems.pptx p.13] [课件: 18-vm-systems.pptx p.14]。先查 L1 d-TLB：16 sets 需要 4 位 TLBI，VPN 余下 32 位是 TLBT [00:25:20-00:25:47]。

- **TLB hit：** 直接取得 PPN，把 VPO 原样复制为 PPO，再拼成 PA [00:25:47-00:26:01]。
- **TLB miss：** 用稍后展开的 multi-level lookup 访问页表，最终定位 PTE、取出 PPN，再与 PPO 拼成 PA [00:26:01-00:26:45]。

课件把物理地址画为 PPN 40 位、PPO 12 位，共 52 位 [课件: 18-vm-systems.pptx p.14]。

### 5. PA 进入 L1 d-cache

L1 d-cache 有 64 sets，因此 CI 占 6 位；课件同时给出 CO 6 位、CT 40 位 [00:26:45-00:27:01] [课件: 18-vm-systems.pptx p.14]。老师特别指出，PA 的 CI+CO 共 12 位，恰好与 VA 的 12 位 VPO 完全相同；这一次不是玩具系统中的偶然，而是 Intel 实现 L1 lookup 所依赖的设计条件，也是 L1 cache 不能任意做大的根源 [00:27:01-00:27:56]。具体并行技巧留到下一段。

cache 用 CI 选择 set，再用 CT 比较 tag [00:27:56-00:28:18]。hit 时把 32/64 位结果返回 CPU；miss 时依次向 L2、L3、主存请求 [00:28:18-00:28:32]。老师又补充“最坏情况”甚至可能因 page fault 从磁盘取得页，但最终结果仍回到 CPU [00:28:32-00:28:39]。

### 6. 开始读取 Core i7 第 1–3 级 PTE

第 1–3 级中的每个 PTE 不直接指向数据页，而是给出下一级 page table 的物理基址；例如 L1 PTE 保存 L2 table 的物理地址 [00:28:47-00:29:26] [课件: 18-vm-systems.pptx p.15]。P 位是 present/valid：P=1 表示 child page table 在物理内存；P=0 时，相关磁盘位置可放在供 OS 使用的字段中 [00:29:26-00:29:42] [课件: 18-vm-systems.pptx p.15]。老师刚开始转向 read-only/read-write 权限时本段结束 [00:29:42-00:29:53]，其语义在 004 继续。

| 项目 | 数量与字段 | 证据 |

# 004｜Core i7 四级页表、L1 并行查找与 Linux 地址空间开场

**时间范围：00:29:53–00:39:49**

## 本段在整讲中的作用

本段完成真实 Core i7 地址翻译的两个核心机制。前半先讲第 1–4 级 PTE 的权限/状态位，并从 CR3 出发走完四级页表 [00:29:53-00:35:55]；随后解释 L1 cache 如何利用 VPO=PPO，在地址翻译尚未完成时就并行选组，这也反过来约束 L1 大小 [00:36:09-00:38:27]。最后切换到 Linux 进程虚拟地址空间，只讲到 `.text/.data/.bss` 与 heap/brk，为下一段的完整布局和 VMA 结构开场 [00:38:32-00:39:49]。

## 教学展开

### 1. 完成 Core i7 第 1–3 级 PTE 字段

R/W 位控制该 PTE 所能到达的全部页面是只读还是可写 [00:29:53-00:30:15]。U/S 位区分用户态可访问还是仅 supervisor/kernel mode 可访问，内核借此保护自己的代码与数据 [00:30:15-00:30:29] [课件: 18-vm-systems.pptx p.15]。

WT 位选择 child page table 的 write-through 或 write-back cache policy；老师说他知道的系统都用 write-back，因为 miss penalty 很大 [00:30:29-00:30:45]。课件还画出 `CD` 位，但老师在 [00:30:45] 明确说忘记它的作用，因此本段不为它补定义。

A/reference 位在 MMU 读写该 PTE 指向的 page table 时置位 [00:30:50-00:31:04]。PS 位表示 4 KB 或 4 MB page size，老师口述后随即转向 XD [00:31:04-00:31:13]；课件限定 PS 在 Level 1 PTE 中定义 [课件: 18-vm-systems.pptx p.15]。XD 位可禁止从该 PTE 可达的所有页取指，老师把现代系统中 stack 防 code-injection attack 与此联系起来 [00:31:13-00:31:29]。

### 2. 第 4 级 PTE 直接描述物理页

最后一级不再指向下一张 page table，而是指向实际 4 KB page；40 位 physical base address 与低 12 位页内偏移配合 [00:31:37-00:32:01] [课件: 18-vm-systems.pptx p.16]。它保留 P、R/W、U/S、WT、A、XD 等语义，并新增 D/dirty 位：MMU 写该页时置 D；OS 选它为 victim 时据此判断是否必须写回 [00:32:01-00:32:32] [课件: 18-vm-systems.pptx p.16]。

学生追问 protection 位差异。老师澄清：XD 禁止从页中装入/执行指令；U/S 决定谁能访问页，supervisor 表示仅 kernel，user 则 user code 与 kernel code 都能访问 [00:32:33-00:33:18]。

### 3. 从 CR3 走完四级页表

内核为每个进程维护一组 page tables，并把第一级表的物理基址放在 CR3 [00:33:26-00:33:53]。36 位 VPN 平分成四个 9 位字段 VPN1–VPN4，每个字段可索引 $2^9=512$ 个 PTE [00:33:53-00:34:21] [课件: 18-vm-systems.pptx p.17]。

1. VPN1（最高 9 位）在 CR3 指向的 L1 page global directory 中选 L1 PTE；每项覆盖 512 GB region，所以老师说多数当时的程序只需初始化一个 L1 entry [00:34:21-00:34:57]。
2. L1 PTE 给出 L2 page upper directory 的物理地址；VPN2 在其中选 L2 PTE [00:35:02-00:35:13]。
3. 同样级联到 L3 page middle directory，再由 VPN3 选项 [00:35:13-00:35:23]。
4. VPN4（VPN 最低 9 位）在 L4 page table 中选择最终 PTE；该项给出 actual page 的 PPN [00:35:23-00:35:42]。
5. 取出 40 位 PPN，与原样复制的 12 位 VPO/PPO 拼成 PA [00:35:42-00:35:55]。

课件给出的逐级覆盖量依次为 512 GB、1 GB、2 MB、4 KB per entry [课件: 18-vm-systems.pptx p.17]。

### 4. L1 cache 的“cute trick”

此前模型是先由 MMU 完成 PA，再把 PA 送到 physically addressed cache [00:36:09-00:36:33]。真实 Intel 实现利用一个不变量：PA 的 PPO 与 VA 的 VPO 完全相同，而 L1 的 CI+CO 又完全落在这 12 位内 [00:36:33-00:37:07] [课件: 18-vm-systems.pptx p.18]。

因此 MMU 收到 VA 后可立即把 VPO 送给 L1：cache 在地址翻译同时提取 CI、选择 set，并读出该 set 的所有候选 lines [00:37:07-00:37:57]。只有最终 tag check 必须等待翻译得到 PPN/CT [00:37:57-00:38:15]。这样 MMU translation 与 L1 lookup 的前半部分并行 [00:38:15-00:38:27]。课件称此设计为 “virtually indexed, physically tagged”，并明确 cache 是为此 carefully sized [课件: 18-vm-systems.pptx p.18]。

### 5. 转入 Linux 进程虚拟地址空间

老师说明理解 Linux VM 后，就能真正理解 `fork`、`exec` 与 loading [00:38:32-00:38:46]。每个进程因 VM 而呈现相似布局：program text 通常从 `0x00400000` 开始，其后是来自可执行文件 `.data` 的 initialized data、表示 uninitialized data 的 `.bss`，然后 heap 从 initialized-data 一侧向高地址增长 [00:38:46-00:39:35] [课件: 18-vm-systems.pptx p.19]。内核用进程上下文中的 `brk` 记录 heap 顶端 [00:39:35-00:39:49]。本段在该句结束，不提前展开其上的映射区和 stack。

### 四级索引与物理地址

$$
VPN(36)=VPN_1(9)\,|\,VPN_2(9)\,|\,VPN_3(9)\,|\,VPN_4(9)
$$

$$
PA=PPN(40)\,|\,PPO(12),\qquad PPO=VPO.
$$

第一级基址来自 CR3；每一级 PTE 的 physical base address 把遍历带到下一层，L4 PTE 才产生最终 PPN [00:33:26-00:35:55] [课件: 18-vm-systems.pptx p.17]。

### L1 并行查找条件

L1 的 `CI(6) | CO(6)` 总共 12 位，完全位于 VPO/PPO 内。因此选组与读 ways 不依赖 PPN，可与翻译并行；物理 tag CT 则必须等待 PPN [00:36:33-00:38:27] [课件: 18-vm-systems.pptx p.18]。

## 例子与课堂提示

1. **权限是层层约束。** Level 1–3 的 R/W、U/S、XD 对该项可达的所有页生效，不只是 page table 自身 [00:29:53-00:31:29]。
2. **dirty 位服务于替换。** OS 选择 victim 后看 D，只有被写脏的页才需要写回 [00:32:14-00:32:32]。
3. **多数程序只需少量顶层项。** 一个 L1 entry 覆盖 512 GB，用来解释多级页表为何不用把整个理论地址空间的低层表都常驻 [00:34:21-00:34:57]。
4. **并行不等于虚拟 tag。** cache 可以用 VPO 选组，但最终仍用翻译后的 physical CT 做 tag check [00:37:07-00:38:15]。

# 005｜Linux 进程地址空间、VM areas 与缺页处理

**时间范围：00:39:49–00:49:41**

## 本段在整讲中的作用

上一段刚从 Core i7 的四级页表与 L1 并行查找切换到 Linux，并讲到低地址处的 `.text/.data/.bss` 与向上增长的 heap。本段继续沿地址从低到高补全进程布局，再把“页表能否翻译”提升为“内核如何判断一次访问是否合法”：Linux 用 `task_struct → mm_struct → vm_area_struct` 描述进程地址空间，缺页处理程序再根据 area 的范围和权限区分非法地址、保护违规与正常按需调页 [00:39:49–00:49:06] [课件: 18-vm-systems.pptx p.19] [课件: 18-vm-systems.pptx p.20] [课件: 18-vm-systems.pptx p.21]。段末的 ELF 问答把这些 area 与下一段的 memory mapping、后面的 `execve` 连接起来 [00:49:27–00:49:41]。

## 教学展开

### 1. 按地址顺序补全 Linux 进程布局

老师从上一段的 heap 顶端继续：heap 上方有供 shared libraries 使用的 memory-mapped region；用户可访问空间的高端是向低地址增长的 user stack，由 `%rsp` 指向；再往高处是 kernel code and data [00:39:49–00:40:17] [课件: 18-vm-systems.pptx p.19]。因此这张图的主线是：低地址的程序映像和向上增长的 heap，与高地址的向下增长 stack 相对；kernel 位于更高区域。

老师立即提醒图不按比例：stack 顶端与 kernel 起点之间实际有很大空洞 [00:40:09–00:40:27]。原因是这里使用 48 位虚拟地址，而地址装在 64 位表示中时，高位必须像符号扩展一样复制第 47 位：若 48 位地址的最高位为 0，其余高位全为 0；若为 1，其余高位全为 1 [00:40:27–00:41:08]。所以老师用简化说法概括：kernel address 的最高位为 1，user address 的最高位为 0；kernel 位于 64 位地址空间顶部 [00:41:08–00:41:41]。他同时说这是布局细节，真正重要的是后面的“每个进程都有包含 kernel 的虚拟地址空间” [00:41:41–00:42:00]。

### 2. kernel 仍通过虚拟地址访问物理内存

kernel code/data 存在于每个进程的虚拟地址空间中；此外，kernel virtual memory 还保留一片区域映射 DRAM，使内核能够访问物理地址 [00:41:46–00:42:29] [课件: 18-vm-systems.pptx p.19]。老师强调地址翻译不能在 kernel mode 下关闭：内核运行时产生的仍是 virtual address [00:42:29–00:42:46]。

这片映射区域按偏移与物理地址对应：访问区域内 offset 0 会翻译到 physical address 0，offset 1 会翻译到 physical address 1；因此内核读写这片 virtual region，效果就是读写 physical memory [00:42:46–00:43:25]。这是老师用来解释“内核既不能绕过翻译，又怎样接触物理内存”的具体机制。

### 3. 区分各进程相同与不同的 kernel 内容

kernel code 等部分对所有进程相同；但页表、task/mm structures、kernel stack 等进程专属数据构成该进程的 context，必须随进程而不同 [00:43:25–00:44:00] [课件: 18-vm-systems.pptx p.19]。这里的“kernel 存在于每个进程地址空间”不等于“每个进程拥有互不相干的一份 kernel code”，而是同一布局中既有 identical 部分，也有 process-specific context。

### 4. Linux 把虚拟内存组织成 areas

Linux 将进程虚拟空间组织为一组 areas；老师把 area 类比为 segment，即一段连续且内容相关的内存，例如 code、data、shared libraries、stack 各有对应 area [00:44:00–00:44:32] [课件: 18-vm-systems.pptx p.20]。

数据结构链按老师的讲解顺序是：

1. 每个进程有 `task_struct`；
2. `task_struct.mm` 指向 `mm_struct`；
3. `mm_struct.pgd` 保存 Level 1 page table（page global directory）的地址；
4. `mm_struct.mmap` 指向 `vm_area_struct` 集合；
5. 每个 `vm_area_struct` 用 `vm_start`/`vm_end` 表示范围，用 `vm_prot` 表示读写权限，用 `vm_flags` 表示 shared 或 private，并通过 `vm_next` 串接课堂图中的下一区域 [00:44:32–00:46:28] [课件: 18-vm-systems.pptx p.20]。

进程被调度运行时，kernel 把 `pgd` 对应值装入 `CR3`；只改变 `CR3` 就切换了地址空间，新进程随即不再通过当前页表访问前一进程的空间 [00:44:44–00:45:33]。这把前面硬件层的 `CR3 → L1 page table` 与 Linux 的进程 context 接了起来。

### 5. 缺页处理程序按 area 做三类判断

处理器执行指令并发现目标页不在内存时触发 page fault；fault handler 随后不能一概“把页读入”，而要判断故障地址与访问类型 [00:46:32–00:47:03] [课件: 18-vm-systems.pptx p.21]。

1. **地址不属于任何 area。** kernel 沿 area 结构查找，却找不到覆盖该地址的 `vm_start ≤ address < vm_end` 区间，说明访问的是不存在的虚拟页；这是错误，产生 segmentation fault [00:47:03–00:47:38]。
2. **地址在 area 中，但访问违反 `vm_prot`。** 例如写 code/text 的只读 area。若已有 PTE，MMU 可由 PTE permission 发现非法写；老师此处讨论的情形是缺少 PTE，MMU 只知道要 fault，并不知道 area 级权限，故 kernel 在 handler 中检查 `vm_prot`，形成 protection exception；Linux 对用户进程同样报告 segmentation fault [00:47:44–00:48:36]。
3. **地址与权限都合法，只是页尚未驻留。** 这是 normal page fault；kernel 将请求页调入，然后让访问结果回到 CPU 路径 [00:48:41–00:49:06]。

### 6. ELF 问答为 `exec` 建立连接

学生问到 executable 中的 segments。老师回答：ELF binary 开头列出不同 segments，`exec` 装载 binary 时会为这些 segments 创建对应 areas [00:49:27–00:49:41]。本段只建立“ELF segment → VM area”的关系；各 area 如何获得初始内容，要到 memory mapping 与 `execve` 部分继续。

## 易错点与辨析

- **误区：kernel mode 可以关闭地址翻译。** 老师明确说 translation 始终发生；内核同样生成 virtual address [00:42:29–00:42:46]。

- **误区：切换进程需要逐项改写所有翻译。** 老师在此强调的是切换页表根：把新进程的 `pgd` 装入 `CR3` [00:45:03–00:45:33]。
- **误区：kernel 映射在每个进程中就意味着所有 kernel 数据都相同。** code 等可相同，但 context structures 和 kernel stack 等是 process-specific [00:43:25–00:44:00]。

# 006｜Memory mapping、共享对象与 private COW

**时间范围：00:49:41–00:59:34**

## 本段在整讲中的作用

本段先收束上一节关于 VM areas 的学生提问：area 是 page-fault handler 用来判定地址与权限的 kernel 结构，`exec` 则依据 executable segments 建立这些 areas [00:49:41–00:50:42]。随后老师引入本讲最后一个主题 memory mapping，把“area 从哪里取得初始字节”解释为“area 与 disk object 的关联”，再从 regular/anonymous backing 推到 shared object 与 private copy-on-write object [00:50:42–00:59:34] [课件: 18-vm-systems.pptx p.22] [课件: 18-vm-systems.pptx p.23]。COW 在本段完成机制定义，但它为何让 `fork` 高效，要到 007 才回答。

## 教学展开

### 1. 回答 areas 在何时使用

老师先接着 [00:49:41] 说明：`exec` 装载 binary 时为其中各 segments 创建 areas。学生继续问这些 area structures 怎样参与地址访问；老师强调 MMU 不认识它们，它们是在 page fault 已发生后由 kernel 使用 [00:49:41–00:50:27]。课堂图把它们画成 list；老师补充真实系统使用“某种 tree，可能是 red-black tree”，但这是带有不确定措辞的 aside，不应写成他在此严格确认的实现规格 [00:50:27–00:50:42]。

### 2. 定义 memory mapping：area 与 disk object 关联

老师把 mapping 定为本讲最后一个主题，并说明它将解释 `fork` 与 `exec` 的内部工作 [00:50:42–00:51:03]。VM area 通过关联一个 disk object 初始化；因此 area 中每个 page 都对应 object/file 的某一部分，页面的 initial contents 来自该对象 [00:51:03–00:51:40] [课件: 18-vm-systems.pptx p.23]。

这里的关键不是“先把整个文件复制进内存”，而是先建立 area 与 object 的关系。具体页面何时进入 physical memory，由后续访问和 page fault 决定。

### 3. 两类 backing：regular file 与 anonymous file

第一类是 regular file。code area 可映射到 executable binary 的某一段，初始 code bytes 就来自该文件部分；老师用它解释 executable 内容怎样进入内存 [00:51:41–00:52:21] [课件: 18-vm-systems.pptx p.23]。

第二类是 anonymous file。老师把它描述为任意大小、内容全为 0、实际上并不存在的“文件”，是一种概念技巧，用来创建 zero-initialized pages [00:52:21–00:52:49]。第一次访问造成 fault 时，kernel 分配一张全 0 physical page，称为 demand-zero page；“demand”表示需要时才产生，“zero”表示初值全 0 [00:52:50–00:53:10]。页面一旦被写而变 dirty，就按普通 dirty page 处理；dirty pages 会在 memory 与专用 swap file 之间搬移 [00:53:11–00:53:32] [课件: 18-vm-systems.pptx p.23]。

### 4. Shared object：不同 VA 可以落到同一组 physical pages

通常进程互不共享内容，但 mapping 允许多个进程映射同一 object [00:53:32–00:53:47]。老师先让 process 1 的一个 area 映射某个 file object，再让 process 2 映射同一 object；两边的 virtual address 可以完全不同 [00:53:47–00:54:42] [课件: 18-vm-systems.pptx p.24] [课件: 18-vm-systems.pptx p.25]。

因为 object 是有唯一标识的 file，kernel 能发现已有其他进程映射它，并让新 area 的 PTE 指向相同 physical pages [00:54:47–00:55:19]。结果是两个进程各自访问不同虚拟区间，实际读写同一片 physical memory。

老师给出的用途是多个 fork 出来的 Apache server processes 共享 memory cache：cache 可以表现为 disk file，访问文件区域时相应 pages 被带入 physical memory，所有进程由共享映射看到同一份 cache [00:55:21–00:55:55]。这是示例，不是说所有 shared mapping 都必须用于 Apache 或 cache。

### 5. Private COW：先共享，写时再分离

对象也可以是 private，即跨进程的写入结果不应互相可见。老师引出一种特别重要的 private copy-on-write (COW) object，并预告它会成为 `fork` 的关键 [00:56:01–00:56:49]。

初始状态与 shared object 相似：两个进程的 areas 映射同一 object 和同一组 physical pages；但 areas 被标记为 private COW，课件同时标出相应 private-area PTEs 被设为 read-only [00:56:49–00:57:14] [课件: 18-vm-systems.pptx p.26]。

- **只读：** 两进程继续从共同 physical page 读取，不发生复制 [00:58:18–00:58:37]。
- **若为 shared mapping 的写：** 修改会反映到共享物理内容，并最终反映到 disk object [00:57:14–00:57:41]。
- **private COW 的写：** 系统不把修改写到共同 object，而是为目标 page 建立单独副本，把副本映射到未用 physical region，再在副本上完成写 [00:57:41–00:58:52]。课件进一步把硬件/内核动作串为：对 read-only private page 的写触发 protection fault；handler 创建新的 R/W page；返回后重新执行该 instruction [课件: 18-vm-systems.pptx p.27]。

所以 “copy-on-write” 的精确含义是：不是映射时复制，也不是读取时复制，只在第一次写某个 page 时复制该 page。老师把它概括为一种在需要高效共享时常用的基础系统概念 [00:58:56–00:59:13]。

## 概念、符号与推导

| 概念 | 本段定义 | 证据 |
|---|---|---|
| memory mapping | VM area 与 disk object 关联，page 初始字节来自 object 对应部分 | [00:51:03–00:51:40] [课件: 18-vm-systems.pptx p.23] |

## 例子与课堂提示

- **executable code 是 regular file-backed 的样例。** 它说明 mapping 给的是初始内容来源，不要求 loader 预先复制完整 binary [00:51:41–00:52:21]。
- **anonymous file 是有意的抽象。** 老师说它“当然并不存在”，其用途是表达任意大小的全 0 backing，从而实现 demand-zero [00:52:21–00:53:10]。

## 易错点与辨析

- **误区：调用 mapping 就立即复制全部文件。** 本段定义的是 area-object association；实际 page 在 fault 时按需进入物理内存 [00:51:03–00:53:10]。
- **误区：anonymous file 是磁盘上真实的全零文件。** 老师明确说它并不存在，是生成 zero pages 的概念技巧 [00:52:21–00:52:49]。
- **误区：shared object 要求两个进程使用同一 VA。** 课件和口述都强调 VA 可以不同，最终 physical pages 相同即可 [00:54:17–00:55:19] [课件: 18-vm-systems.pptx p.25]。
- **误区：private COW 从一开始就有两份 physical copy。** 初始仍共享；只有 writer 的目标 page 在写 fault 后获得副本 [00:56:49–00:58:52]。
- **误区：COW 的写会更新原 shared object。** private COW 正是为了不把该进程的修改反映到共同 object；系统改写新副本 [00:57:32–00:58:18]。

# 007｜Consistency model、`fork` 的 COW 与 `execve` 重建地址空间

**时间范围：00:59:34–01:09:28**

## 本段在整讲中的作用

本段先回答上一节末尾关于多核并发内存访问的追问：memory system 会提供 ordering guarantees，但具体 consistency model 超出当前范围 [00:59:34–01:00:32]。随后老师兑现前面两次铺垫，把 private COW 用于解释 `fork` 为什么不必复制全部 physical memory，再把 memory mapping 用于解释 `execve` 怎样在当前进程中撤销旧地址空间并建立新程序的 areas [01:00:33–01:09:28] [课件: 18-vm-systems.pptx p.27] [课件: 18-vm-systems.pptx p.28] [课件: 18-vm-systems.pptx p.29]。本段结束在 `execve` 即将设置 program counter 的句中，实际设置 `RIP` 及 demand loading 在 008 开头完成。

## 教学展开

### 1. 多核写入顺序属于 consistency model

老师称学生的问题“非常好”，但明确标为超出本处范围：多个 cores 会向 memory system 送入多条 instructions 和 addresses，memory system 负责给这些操作某种 ordering，并提供关于可观察顺序的非平凡保证 [00:59:34–01:00:13]。每种 processor 都提供某种 consistency model；本讲不继续定义具体规则 [01:00:13–01:00:32]。因此这里能确认的是“系统提供顺序保证”，不能从本段推出保证的具体强弱或某种命名模型。

### 2. 先说明朴素 `fork` 为什么昂贵

老师回到“COW 为什么有用”。`fork` 要让 child 获得与 parent 初始内容相同、之后又彼此独立的 address space [01:00:33–01:01:04]。朴素做法会复制所有 page tables、其他 kernel structures 和所有实际 memory；进程使用的 virtual pages 越多，要复制并重新映射的 physical data 越多，开销可能极大 [01:01:04–01:01:46]。

这一步提出的矛盾是：语义要求“看起来是完整私有副本”，但立即复制所有 data pages 对时间和空间都太贵。COW 正是这个矛盾的延迟求值方案 [01:01:46–01:01:55]。

### 3. `fork` 返回前实际复制什么、共享什么

kernel 仍必须创建内部描述结构的 exact copies：`mm_struct`、各 `vm_area_struct` 和 page tables；老师说这部分无法绕过，但相对于进程可能使用的大量实际数据，它们没有那么大 [01:01:55–01:02:27] [课件: 18-vm-systems.pptx p.28]。

接着 kernel 做两类标记：

1. 把 parent 和 child 中每个 page 的 PTE 都标为 read-only；
2. 把两边每个 `vm_area_struct` 都标为 private COW [01:02:27–01:02:50]。

返回时，两进程有内容相同的 page tables 和 area structures，因此看到相同的 virtual-memory contents；这些 copied page tables 的 PTE 暂时仍让两进程共享同一批 physical pages [01:02:50–01:03:15]。也就是说，“复制 page tables”与“复制 data pages”是两件事：前者立即发生，后者按写入需要发生。

### 4. 第一次写如何经过 fault 完成分离

只读期间两进程继续共享 physical pages [01:03:06–01:03:15]。某个进程第一次写某页时，动作严格按老师的顺序发生：

1. write 遇到 PTE 的 read-only 标志，触发 fault [01:03:15–01:03:44]；
2. kernel 查该 page 所在 area 的 flags，发现它是 private COW，而不是普通非法写 [01:03:44–01:03:50]；
3. handler 复制 target page，并把新副本映射到新的 physical region [01:03:50–01:04:00]；
4. fault handler 返回时重新启动原 write instruction；此时写入落到副本 [01:04:00–01:04:16] [课件: 18-vm-systems.pptx p.27]。

复制因此被推迟到尽可能晚，而且只复制绝对需要写的 pages [01:04:16–01:04:34]。从未被写的区域不需要复制，parent/child 一直共享其 physical data，这就是 `fork` 在空间上的高效表示 [01:04:34–01:04:57] [课件: 18-vm-systems.pptx p.28]。

### 5. `execve` 的第一步：不是新建进程，而是替换当前地址空间

老师转到 `execve`：它在 current process 中 load and run 一个 new program；它不创建新进程，而是在同一进程内换成新的 virtual address space [01:04:57–01:05:42]。因此首先释放旧 areas 的 `vm_area_struct`s 和旧 page tables，再为新程序创建新的 area structures 与 page tables [01:05:18–01:05:56] [课件: 18-vm-systems.pptx p.29]。

### 6. 新地址空间各 area 的 backing

老师按地址空间中的区域逐项说明新 mappings：

- **Program text 与 initialized data：** 分别由 executable binary 中 code 与 initialized-data 部分 backing；老师将它们归为 private、file-backed [01:05:56–01:06:41] [课件: 18-vm-systems.pptx p.29]。
- **`.bss`：** binary 指定它为 uninitialized data，因此建立成 private demand-zero area，系统给初始值 0 [01:06:41–01:07:05]。
- **Heap：** 其 pages 也属于 private demand-zero [01:07:05–01:07:14]。
- **Shared-library region：** 多进程在 memory 中共享 `libc` 的 file-backed 内容；`.text` 和相应 initialized portions 来自 shared-object file [01:07:14–01:07:58] [课件: 18-vm-systems.pptx p.29]。
- **Writable library state：** 老师用 random-number generator 的 retained state/static variables 举例，这些状态必须因进程而异，所以写入的数据部分需要 private COW，而不能让所有进程互相覆盖 [01:07:58–01:08:55]。
- **Stack：** private demand-zero [01:08:55–01:09:00]。

老师随后总结：`execve` 建立由目标 object file backing 的新 areas，为 `.bss` 与 stack 建立 anonymous backing，并建立对应 `libc` 的 shared-object mapping [01:09:00–01:09:26]。本段最后只说“然后设置 program counter”，具体设置到 `.text` entry point 的动作在下一节继续 [01:09:26–01:09:28]。

## 概念、符号与推导

### `fork` 的对象复制与 data-page 共享

| 时点 | Kernel structures | Physical data pages | 权限/标志 |
|---|---|---|---|
| `fork` 建立 child | 复制 `mm_struct`、`vm_area_struct`s、page tables | parent/child 暂时共享 | PTEs read-only；areas private COW |
| 两边只读 | 各自结构不变 | 继续共享 | 不触发复制 |
| 某方首次写 page | 结构用于识别 COW fault | 只复制目标 page，writer 改指新页 | 新页可写，原 instruction restart |

以上过程来自 [01:01:55–01:04:57] 与 [课件: 18-vm-systems.pptx p.27] [课件: 18-vm-systems.pptx p.28]。本段没有数值公式推导；核心推导是把朴素成本从“立即复制全部 data pages”变成“固定复制描述结构 + 按实际写集合逐页复制”。老师没有在本段给出复杂度公式，故不额外量化。

### `execve` 的区域分类

| Area | Backing/共享属性（按本讲） | 证据 |
|---|---|---|
| Program `.text` | private, file-backed by executable | [01:05:56–01:06:41] |
| Initialized `.data` | private, file-backed by executable | [01:06:10–01:06:41] |
| `.bss` | private, demand-zero/anonymous | [01:06:41–01:07:05] |
| Heap | private, demand-zero | [01:07:05–01:07:14] |
| Shared-library code/data | shared, file-backed；可写 state 另需 private COW | [01:07:14–01:08:55] |
| User stack | private, demand-zero/anonymous | [01:08:55–01:09:18] |

课件把上述总体步骤概括为：free old areas/tables → create new areas/tables → map object/anonymous backing → set PC → pages faulted in as needed [课件: 18-vm-systems.pptx p.29]；最后两步跨到 008。

## 例子与课堂提示

- **“可能近乎无界”的朴素复制。** 老师用拥有大量 virtual pages 的进程说明，真正大的不是 `mm_struct` 本身，而是全部 actual data pages [01:01:04–01:02:27]。
- **read-only 是 COW 的触发器，不是最终语义。** `fork` 后本来逻辑上可写的页也先标 read-only，让 hardware fault 把第一次写引到 kernel [01:02:27–01:04:16]。
- **只读页永不复制。** 这不是遗漏，而是 COW 的空间收益：两个 private address spaces 可以安全共享从未写过的 physical data [01:04:34–01:04:57]。
- **library state 的反例。** `libc` code 可共享，但 random generator 等带 static state 的 writable data 必须按进程分离，用于说明“同一个 shared object region 内也要区分共享只读内容与私有可写状态” [01:07:58–01:08:55]。

## 易错点与辨析

- **误区：`fork` 完全不复制 page tables。** 老师明确说 `mm_struct`、areas 与 page tables 必须复制；延迟的是大规模 physical data-page copying [01:01:55–01:02:27]。
- **误区：parent 与 child 的 copied PTEs 一开始指向不同 physical pages。** 它们初始共享同一 pages，只有 writer 的目标页后来改指副本 [01:02:50–01:04:16]。
- **误区：COW fault 就是非法写导致的 segmentation fault。** kernel 读取 area flag 后识别 private COW，创建副本并重启指令；它是用 protection fault 实现合法语义 [01:03:25–01:04:16]。
- **误区：`execve` 创建一个新进程。** 它保留 current process 身份但释放旧 VM areas/page tables，并在当前进程内运行新程序 [01:05:18–01:05:56]。
- **误区：整个 `libc` mapping 对所有进程的可写状态都共享。** 老师专门说明 static/retained state 必须有 private COW 部分 [01:07:58–01:08:55]。

# 008｜`execve` 的按需装载、用户态 `mmap` 与 `mmapcopy`

**时间范围：01:09:28–01:17:37**

## 本段在整讲中的作用

本段完成全讲最后一条因果链。老师先收尾 `execve`：设置 `RIP` 时只建立 mappings，并未把程序内容复制到 memory，后续 code/data 由 page faults 按需装入 [01:09:28–01:11:24] [课件: 18-vm-systems.pptx p.29]。然后把 kernel 使用的 memory-mapping 机制开放到 user level，逐项解释 `mmap` 的地址、长度、权限、共享方式、文件描述符和偏移，最后用 `mmapcopy` 展示“一次 mapping + 一次 `write`”怎样按缺页逐步读取文件 [01:11:24–01:17:29] [课件: 18-vm-systems.pptx p.30] [课件: 18-vm-systems.pptx p.31] [课件: 18-vm-systems.pptx p.32]。本节覆盖到 transcript 最后一条告别 [01:17:32–01:17:37]。

## 教学展开

### 1. 完成 `execve`：先建立映射，再按需装页

接上一段，loader 把 program counter `RIP` 设置为 `.text` 的 entry point [01:09:28–01:10:02]。老师特别要求注意：此时没有实际程序内容被复制到 physical memory；已经做的只是创建 kernel data structures，并把 virtual-address regions 与 backing objects 建立 mappings [01:09:36–01:10:02] [课件: 18-vm-systems.pptx p.29]。

当 CPU 尝试取 entry-point 的第一条 instruction 时，Linux 才因访问把所需 code page fault in；之后 data pages 也只在真正被 reference/access 时进入 memory [01:10:02–01:10:32]。这使 loading 与 VM 紧密结合，并把未访问内容的成本完全推迟 [01:10:32–01:10:48]。

老师给出 eager-loading 反例：loader 也可以循环读取 object files，把内容全部复制到 memory 并同步创建 PTE，但这会浪费工作。若程序有一个很大的、预先初始化为非零值的 array，而运行只访问其中很小部分，eager copy 仍会在 load time 搬完整个 array [01:10:48–01:11:24]。demand paging 只为实际触及的 pages 付出代价。

### 2. `mmap` 把同一 mapping 能力提供给用户程序

老师引入 kernel 提供的 `mmap` system call：用户程序可请求 kernel 把一段 virtual memory 映射到一个 object [01:11:24–01:11:52]。课件给出的接口是 [课件: 18-vm-systems.pptx p.30]：

```c
void *mmap(void *start, int len,
           int prot, int flags, int fd, int offset)
```

参数按课堂顺序解释如下：

1. `start`：希望映射开始的 virtual address；可为 0，让 kernel 选择地址 [01:11:52–01:12:10] [课件: 18-vm-systems.pptx p.30]。
2. `len`：映射 virtual region 和 file region 的字节数 [01:12:03–01:12:10]。
3. `fd`：由 `open` 返回的 file descriptor，指定 backing file/object [01:12:10–01:12:35]。
4. `offset`：从该 file 的 `offset` bytes 处开始，取 `len` bytes 与 virtual region 关联 [01:12:35–01:12:51] [课件: 18-vm-systems.pptx p.31]。
5. `prot`：指定 `PROT_READ`、`PROT_WRITE` 等访问权限 [01:12:51–01:13:05]。
6. `flags`：指定 `MAP_ANON`、`MAP_PRIVATE`、`MAP_SHARED` 等对象/共享属性 [01:13:05–01:13:28]。

若使用 anonymous mapping，得到的是 demand-zero backing，不需要有效 file descriptor；mapping 仍可标为 private 或 shared [01:13:13–01:13:28]。kernel 返回实际 mapped area 起点；`start` 只是偏好/hint，若该区域已占用，kernel 可选其他 unused virtual range，所以返回指针不一定等于传入 `start` [01:13:35–01:14:02] [课件: 18-vm-systems.pptx p.30]。

### 3. `mmap` 返回时仍只是 mapping

老师再次强调调用后“nothing gets copied”：本质是把 file 中从 `offset` 开始的 `len` bytes，与 virtual address space 中同样大小的 region 建立 association [01:14:02–01:14:37] [课件: 18-vm-systems.pptx p.31]。

若把该 region 当大 array 顺序扫描，每遇到尚不存在的 page 就触发 page fault；kernel 按 file 对应部分的 contents 将 page 带入，因而程序像访问 memory 一样得到文件字节 [01:14:41–01:15:26]。这里的自动按页载入正是前面 normal page fault 和 file-backed area 的组合。

### 4. `mmapcopy`：由 file mapping 直接交给 `write`

老师最后用 `mmapcopy.c` 说明用途，并将目标描述为“把文件复制到 standard output，而不把数据显式传入 user-space buffer” [01:15:26–01:15:54] [课件: 18-vm-systems.pptx p.32]。他先口误说从 standard input 到 standard output，随后在解释 driver 时纠正：程序打开 command line 传入的 `argv[1]` 文件 [01:15:31–01:16:12]。

driver 的课堂执行顺序是：

1. 检查恰有一个 filename argument；
2. `Open(argv[1], O_RDONLY, 0)` 得到 `fd`；
3. `Fstat(fd, &stat)` 得到 `stat.st_size`；
4. 调用 `mmapcopy(fd, stat.st_size)` [01:16:02–01:16:32] [课件: 18-vm-systems.pptx p.32]。

`mmapcopy` 本身先执行：

```c
bufp = Mmap(NULL, size,
            PROT_READ,
            MAP_PRIVATE,
            fd, 0);
Write(1, bufp, size);
```

也就是从 file offset 0 开始，把整个文件以 read-only、private 方式映射；随后只发出一次 `Write`，descriptor 1 是 standard output [01:16:22–01:17:24] [课件: 18-vm-systems.pptx p.32]。`write` 为取得 `bufp` 中连续 bytes 会读取映射区；尚未驻留的 pages 在这个过程中 fault in，然后 bytes 被写到 fd 1 [01:17:03–01:17:24]。老师用此对比朴素的用户循环：后者通常显式 `read` 再 `write`，这里则是一处 mapping 和一次 write system call [01:15:44–01:16:00]。

## 概念、符号与推导

### `execve` 的 demand-loading 链

`create areas/page tables and mappings → set RIP to .text entry → instruction fetch touches absent page → page fault → fault in required code/data page → resume` [01:09:28–01:10:32] [课件: 18-vm-systems.pptx p.29]。这里没有“先完整复制 executable”的步骤。

### `mmap` 的区间对应关系

按本讲接口，一段长度为 `len` 的 virtual region 被关联到 file descriptor `fd` 所指文件中从 `offset` 开始的 `len` bytes [01:11:52–01:12:51]：

```text
virtual: [returned_start, returned_start + len)
file:    [offset, offset + len)
```

这是对课堂图的区间表达 [课件: 18-vm-systems.pptx p.31]，不是额外引入的地址对齐规则。页面仍由访问触发 faults 后按需载入 [01:14:28–01:15:26]。

### `mmapcopy` 的系统调用对比

老师对比的路径是：朴素方法显式 `read` + `write`；示例方法 `Mmap` + 单次 `Write` [01:15:44–01:16:00]。他没有在本段给出性能公式或精确 syscall 成本，因此不做额外量化。

## 例子与课堂提示

- **大型非零初始化 array。** 它服务于说明 demand loading 不仅节省零页，也能避免把 file-backed、非零的未访问数据在 load time 全部复制进来 [01:11:09–01:11:24]。
- **`start` 是 hint。** 代码不能假定返回值等于传入地址；应使用 `mmap` 返回的 pointer [01:13:35–01:14:02] [课件: 18-vm-systems.pptx p.30]。
- **把 mapped region 当 array 扫描。** 每次触及 absent page 都自动 fault in，初始内容由 file 对应片段决定 [01:14:41–01:15:26]。
- **老师在 `mmapcopy` 入口处自我纠正。** 数据源不是 standard input，而是 `argv[1]` 指定、经 `Open` 打开的文件；终点 fd 1 才是 standard output [01:15:31–01:16:22] [课件: 18-vm-systems.pptx p.32]。

## 易错点与辨析

- **误区：`execve` 设置 `RIP` 前已经把 `.text/.data` 全装入 RAM。** 此时只建立 structures/mappings；第一次取指及后续访问才按需 fault in [01:09:28–01:10:32]。
- **误区：`mmap(start, ...)` 必定在 `start` 映射。** `start` 是优选位置，kernel 可返回其他 unused address；真实起点以返回 pointer 为准 [01:13:35–01:14:02]。
- **误区：file-backed mapping 返回时文件已经复制到用户 buffer。** 返回时只有 mapping；访问 absent page 才从 backing file 取得内容 [01:14:02–01:15:26]。
- **误区：`MAP_ANON` 仍必须提供普通 file descriptor。** 老师说明 anonymous mapping 代表 demand-zero backing，此时不需要 file descriptor [01:13:13–01:13:28]。
- **误区：示例复制的是 stdin。** 口头开场有此说法，但老师立刻纠正，代码明确打开 `argv[1]`；只有输出使用 fd 1 [01:15:31–01:17:24]。

## 本段掌握检查

### Q1. `execve` 设置 `RIP` 时，哪些工作已经完成，哪些尚未完成？

**答：** kernel areas/page tables 与 object mappings 已建立，`RIP` 指向 `.text` entry；code/data pages 尚未整体复制，要由实际取指和数据访问触发 faults 后按需装入 [01:09:28–01:10:32]。

### Q2. `mmap` 中 `fd`、`offset` 与 `len` 共同指定什么？

**答：** 它们指定 backing file 中从 `offset` 开始的 `len` bytes；该文件区间被关联到一个同样长的 virtual-memory region [01:12:10–01:12:51] [课件: 18-vm-systems.pptx p.31]。

### Q3. 为什么程序必须使用 `mmap` 的返回值而非假定 `start`？

**答：** `start` 只是地址 hint；若冲突，kernel 会选其他 unused region，返回实际 mapped-area pointer [01:13:35–01:14:02]。

### Q4. 顺序读取一个 file-backed mapped array 时，absent page 怎样获得内容？

**答：** 读取触发 page fault，kernel 从 backing file 的对应部分 fault in 该 page，其 bytes 由所映射文件区间决定 [01:14:41–01:15:26]。

### Q5. `mmapcopy` 的两个核心调用及其参数目的是什么？

**答：** `Mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0)` 把整个输入文件只读私有映射；`Write(1, bufp, size)` 将映射区的 `size` bytes 写到 standard output，并在读取映射区时按需 fault in pages [01:16:22–01:17:24] [课件: 18-vm-systems.pptx p.32]。
