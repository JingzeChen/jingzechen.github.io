## 学习目标

完成本讲后，应能把高级语言中的 function、procedure 或 method 还原为 Linux x86-64 上由硬件能力与 ABI 共同实现的一组状态变化，并能独立完成以下任务：

- 从一次 `P -> Q` 调用中分离三类职责：把控制传入 callee 并返回正确位置、传递参数与返回值、分配并回收调用期间需要的局部状态。[课件: 07-machine-procedures.pptx p.2]
- 画出 runtime stack 的地址方向，说明 `%rsp` 指向当前栈顶、栈向低地址增长，以及 `pushq`、`popq`、`call`、`ret` 对 `%rsp`、memory 和 `%rip` 的影响。[课件: 07-machine-procedures.pptx p.4] [课件: 07-machine-procedures.pptx p.5] [课件: 07-machine-procedures.pptx p.6] [课件: 07-machine-procedures.pptx p.9]
- 熟记前六个 integer/pointer 参数寄存器 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，知道第 7 个及以后参数使用 caller 提供的 stack area，返回值位于 `%rax`。[课件: 07-machine-procedures.pptx p.15]
- 区分静态 function definition、一次动态 invocation 和该 invocation 的 stack frame，解释 recursion 中同一份 code 为什么可以同时对应多份 private state。[课件: 07-machine-procedures.pptx p.18] [课件: 07-machine-procedures.pptx p.19]
- 判断 local value 可以留在 register，还是因为取地址、跨 call 存活或其他需求必须进入 stack frame；理解 `%rbp` 通常可省略、但可在需要稳定 frame reference 时使用。[课件: 07-machine-procedures.pptx p.20] [课件: 07-machine-procedures.pptx p.32]
- 区分 caller-saved、callee-saved 与 `%rsp` 的特殊恢复责任，并能从一段 prologue/body/epilogue 验证约定是否得到履行。[课件: 07-machine-procedures.pptx p.40] [课件: 07-machine-procedures.pptx p.41] [课件: 07-machine-procedures.pptx p.42]
- 手工执行 `multstore -> mult2`、`call_incr -> incr`、`call_incr2 -> incr` 和递归 `pcount_r`，持续记录 `%rip`、`%rsp`、关键寄存器和相关 memory slot。
- 解释为什么 ordinary calling convention 已足以支持 direct recursion 与 mutual recursion，以及为什么 stack 的 LIFO discipline 与正常 call/return lifetime 匹配。[课件: 07-machine-procedures.pptx p.53] [课件: 07-machine-procedures.pptx p.54]

## 先修知识

- 能把 memory 视为按 byte address 编号的数组，能区分较高地址与较低地址，并能做简单十六进制地址运算。
- 熟悉基本 x86-64 register 名称，知道 `%rip` 表示当前 instruction pointer，`%rsp` 表示 stack pointer。
- 能阅读 `movq`、`movl`、`addq`、`subq`、`imulq`、`leaq`、`testq`、`je`、`andl`、`shrq`、`pushq`、`popq`、`call`、`ret` 等本讲出现的 instructions。
- 理解 C 的 argument、return value、automatic local variable、pointer、dereference `*p`、address-of `&v1`、recursive call 与 unsigned right shift。
- 知道写入 32-bit register 会把对应 64-bit register 的高 32 bits 清零；本讲用这一点解释 `movl $3000,%esi` 和 `andl $1,%ebx`。

## 老师教学主线

老师采用“先拆职责，再逐层实现，最后用递归合并”的顺序：

1. **定义 procedure 的问题空间。** Function、procedure、method 在本讲关注的机器机制上统一处理；实现由 x86-64 hardware 与 Linux ABI convention 共同组成。Procedure 需要处理 control、data 和 local storage，且只执行本次调用真正需要的工作。[课件: 07-machine-procedures.pptx p.2] [课件: 07-machine-procedures.pptx p.3]
2. **建立 stack 坐标系。** Outstanding calls 的 state 具有 LIFO lifetime，因此 ordinary memory 中的一段区域被作为 runtime stack；`%rsp` 指向 top，新增内容时向低地址移动。[课件: 07-machine-procedures.pptx p.4]
3. **先完成 control path。** `pushq`/`popq` 给出栈项的 8-byte 更新规则；`call` 保存下一条 instruction 的地址并跳到 callee，`ret` 取回该地址并回到 caller。[课件: 07-machine-procedures.pptx p.5] [课件: 07-machine-procedures.pptx p.6] [课件: 07-machine-procedures.pptx p.8] [课件: 07-machine-procedures.pptx p.9]
4. **再完成 data path。** ABI 规定参数位置与 `%rax` return location；`mult2`/`multstore` 让同一份 disassembly 同时展示 control flow 与 `%rdi/%rsi/%rdx/%rax` 的 data flow。[课件: 07-machine-procedures.pptx p.15] [课件: 07-machine-procedures.pptx p.16]
5. **从 invocation lifetime 推出 frame。** 每个尚未返回的 invocation 都需要自己的 arguments、locals、saved state 和 return information；`yoo -> who -> amI -> amI` 展示 frame 随动态调用链增长和回收。[课件: 07-machine-procedures.pptx p.18] [课件: 07-machine-procedures.pptx p.19] [课件: 07-machine-procedures.pptx p.21] [课件: 07-machine-procedures.pptx p.31]
6. **解释 local storage 不是固定模板。** 固定大小 frame 可用成对的 `%rsp` subtraction/addition 管理；`incr` 的状态全在 registers，而 `call_incr` 因为需要 `&v1`，必须在 stack 中给 `v1` 一个可寻址位置。[课件: 07-machine-procedures.pptx p.32] [课件: 07-machine-procedures.pptx p.33] [课件: 07-machine-procedures.pptx p.34]
7. **从跨 call live value 推出 register-saving contract。** `%rdx` 被 callee 覆盖的反例说明双方必须协调，继而引出 caller-saved 与 callee-saved，并由 `call_incr2` 验证 `%rbx` 的 save-use-restore bracket。[课件: 07-machine-procedures.pptx p.39] [课件: 07-machine-procedures.pptx p.40] [课件: 07-machine-procedures.pptx p.43] [课件: 07-machine-procedures.pptx p.44]
8. **用 recursion 汇总全部机制。** `pcount_r` 同时使用 argument/return registers、callee-saved `%rbx`、recursive `call`、return address 和逐层 unwind，证明 recursion 不需要特殊 instruction。[课件: 07-machine-procedures.pptx p.46] [课件: 07-machine-procedures.pptx p.52]
9. **回到 ABI 的整体价值。** Private frames、register-saving conventions 与 LIFO stack 让独立生成的 code 和 tooling 可以共享同一 machine contract；老师建议用 hand execution 或 debugger single-step 建立真正的状态直觉。[课件: 07-machine-procedures.pptx p.53] [课件: 07-machine-procedures.pptx p.54]

## 概念依赖

```text
hardware registers/instructions
        +
Linux x86-64 ABI convention
        |
        +--> control
        |      call: push return address + jump
        |      ret : pop return address + jump back
        |
        +--> data
        |      arguments 1..6 -> %rdi,%rsi,%rdx,%rcx,%r8,%r9
        |      arguments 7+   -> caller-provided stack area
        |      return value   -> %rax
        |
        +--> state lifetime
               nested calls -> LIFO -> runtime stack
               one invocation -> one private stack frame
               live across call -> stack slot or preserved register
               register reuse -> caller/callee saving contract
               repeated ordinary calls -> direct/mutual recursion
```

必须按以下依赖顺序理解关键结论：

- **Return point -> return address -> `call`/`ret`。** 只有先明确“callee 应回到 caller 的哪一条 instruction”，才能理解为何 `call` 压入 next-instruction address，而不是 call 本身地址。
- **Stack direction -> `%rsp` 更新 -> frame cleanup。** 栈向低地址增长，所以分配和 push 使 `%rsp` 减小；只有在 `ret` 前恢复 `%rsp`，top 才重新指向正确 return address。
- **ABI data locations -> caller/callee cooperation。** Hardware 不知道哪个 C value 是第几个 argument；caller 与 callee 因共同约定才可独立编译并互相调用。
- **Invocation lifetime -> private frame -> recursion。** Frame 属于一次动态 invocation，而不是一份静态 source；因此同一个 recursive function 的多层状态可以同时存在。
- **Value lifetime -> storage choice。** 只在当前计算中使用的 value 可留在 caller-saved register；需要 memory address 的 object 必须有 memory slot；跨 call 的 live value必须由 caller 保存或放在 callee-saved register 中。
- **Callee-saved `%rbp` -> stable frame pointer。** 若某层把 `%rbp` 用作 frame reference，所有更深的 compliant callees 都须在改写后恢复它，外层返回后才能继续可靠定位自己的 frame。

## 关键推导与例子

### 1. `pushq`、`popq`、`call`、`ret` 的状态方程

设 `Val(Src)` 为 source value，`RA` 为 call 后下一条 instruction 地址：

```text
pushq Src:
    value <- Val(Src)
    %rsp  <- %rsp - 8
    M[%rsp] <- value

popq Dest:
    value <- M[%rsp]
    %rsp  <- %rsp + 8
    Dest  <- value

call Target:
    %rsp  <- %rsp - 8
    M[%rsp] <- RA
    %rip  <- Target

ret:
    RA    <- M[%rsp]
    %rsp  <- %rsp + 8
    %rip  <- RA
```

在 `multstore` 的 `0x400544: callq 0x400550 <mult2>` 中，下一条 instruction 位于 `0x400549`。若 call 前 `%rsp=0x120`，则 call 后 `%rsp=0x118`、`M[0x118]=0x400549`、`%rip=0x400550`；`ret` 后 `%rsp=0x120`、`%rip=0x400549`。[课件: 07-machine-procedures.pptx p.10] [课件: 07-machine-procedures.pptx p.11] [课件: 07-machine-procedures.pptx p.12] [课件: 07-machine-procedures.pptx p.13]

### 2. 固定 frame 的建立与回收

若 compiler 在 compile time 已知当前 function 需要 $n$ bytes：

$$
\%rsp_{body}=\%rsp_{entry}-n,
\qquad
\%rsp_{before\ ret}=\%rsp_{body}+n=\%rsp_{entry}
$$

所以固定 frame 不必通过 `%rbp` 搜索边界。`subq $n,%rsp` 建立 local area，`addq $n,%rsp` 在 `ret` 前恢复它。回收只改变当前 stack boundary，不会自动清零旧 memory bytes。

### 3. `incr` 与 `call_incr`：register value 和 addressable object

```c
long incr(long *p, long val) {
    long x = *p;
    long y = x + val;
    *p = y;
    return x;
}
```

`incr` 中 `p -> %rdi`、`val -> %rsi`、old value `x -> %rax`，更新后的 `y` 可复用 `%rsi`，因此无需显式 local stack area。[课件: 07-machine-procedures.pptx p.33]

`call_incr` 则需要执行 `incr(&v1,3000)`。因为 `&v1` 必须是 callee 可 dereference 的 memory address，compiler 执行 `subq $16,%rsp`，把 `v1=15213` 放在 `8(%rsp)`，再用 `leaq 8(%rsp),%rdi` 传递地址。[课件: 07-machine-procedures.pptx p.34]

调用结果同时存在两处：

$$
M[\&v1]_{after}=15213+3000=18213,
\qquad
\%rax=v2=15213
$$

随后 `addq 8(%rsp),%rax` 得到：

$$
\operatorname{return}(call\_incr)=18213+15213=33426
$$

这组课件快照同时说明 `leaq` 计算 address 而不读取 contents、side effect 与 return value 可以不同，以及 cleanup 必须先把 `%rsp` 移回 return address。[课件: 07-machine-procedures.pptx p.35] [课件: 07-machine-procedures.pptx p.36] [课件: 07-machine-procedures.pptx p.37] [课件: 07-machine-procedures.pptx p.38]

### 4. `call_incr2`：跨 call live value 与 `%rbx`

`call_incr2(long x)` 返回 `x+v2`，但 `%rdi` 既承载入口 `x`，又必须在调用 `incr` 前改成 `&v1`。因为 `%rdi` 是 caller-saved，原 `x` 不能继续依赖它。Compiler 采用：[课件: 07-machine-procedures.pptx p.43] [课件: 07-machine-procedures.pptx p.44]

```text
pushq %rbx          保存 caller 的 old %rbx
subq $16,%rsp       建立 locals
movq %rdi,%rbx      当前 %rbx 保存 x，跨 incr call 存活
...
call incr
addq %rbx,%rax      x + v2
addq $16,%rsp       先回收后分配的 locals
popq %rbx           再恢复先保存的 old %rbx
ret
```

Exit 顺序必须与 setup 相反，这是 LIFO 在 prologue/epilogue 中的直接结果。

### 5. `pcount_r`：ordinary convention 支持 recursion

课堂 C recurrence 为：[课件: 07-machine-procedures.pptx p.46]

$$
P(0)=0,
\qquad
P(x)=(x\mathbin{\&}1)+P(x\gg1),\quad x\ne0
$$

其中 `x` 是 `unsigned long`。每个非 base invocation：

1. `pushq %rbx` 保存 caller 的 `%rbx`。
2. 把本层 `x&1` 放入 `%rbx`。
3. 把 `x>>1` 放入 `%rdi`，递归调用同一 function。
4. 返回时 `%rax=P(x>>1)`，callee-saved contract 保证本层 `%rbx=x&1`。
5. `addq %rbx,%rax` 得到 `P(x)`。
6. `popq %rbx` 恢复 caller state，随后 `ret` 恢复 caller control。[课件: 07-machine-procedures.pptx p.47] [课件: 07-machine-procedures.pptx p.48] [课件: 07-machine-procedures.pptx p.49] [课件: 07-machine-procedures.pptx p.50] [课件: 07-machine-procedures.pptx p.51] [课件: 07-machine-procedures.pptx p.52]

因此 recursive call 没有专用 instruction；区别只在动态 stack 上同时存在更多 ordinary invocation state。

## 易错点

- **把图的上下方向当作地址方向。** 本讲图中 stack top 常画在下方；判断增长必须看地址，新增空间使 `%rsp` 数值减小。
- **把 return address 写成 call instruction 的地址。** Return address 是 call 后下一条 instruction；`0x400544` 的 call 压入 `0x400549`。
- **以为 `pop` 或 frame cleanup 会擦除 memory。** 它们只移动 `%rsp`、改变哪些 bytes 属于当前 stack；旧 bit pattern 可暂时保留。
- **以为 `call` 自动传参数、建立完整 frame。** `call` 只负责保存 return address 和改变 control；data placement、locals 与 saving 按 ABI 和实际需要分别实现。
- **把 `%rax` 当成第一个 argument register。** `%rax` 是 return location；第一个 integer/pointer argument 是 `%rdi`。
- **以为函数最多只有六个参数。** 前六个 integer/pointer arguments 使用 registers，第 7 个及以后使用 stack。
- **把 stack frame 当作每个 function 固定的一份对象。** Frame 对应一次 invocation；递归的每一层都有独立 state，frame 大小和字段也可不同。
- **以为所有 locals 都必须落栈。** `incr` 的 locals 可 registerize；`call_incr` 的 `v1` 因 `&v1` 才必须拥有 memory address。
- **混淆 `leaq` 与 memory load。** `leaq 8(%rsp),%rdi` 得到 `%rsp+8`，不读取该地址中的 `15213`。
- **混淆 `incr` 的 side effect 与 result。** 它把 `v1` 更新为 `18213`，却返回 old value `15213`；`call_incr` 最终返回二者之和 `33426`。
- **把 caller-saved 理解成由 callee 保存。** Caller 若需要 old value 跨 call 存活，就必须自行保存；callee 可自由改写该类 registers。
- **把 callee-saved 理解成不可修改。** Callee 可以使用，但必须先保存 entry value，并在 return 前恢复。
- **忘记 epilogue 的逆序。** 后建立的 local area 必须先回收，才能 pop 更早保存的 register；否则 `ret` 也无法看到正确 return address。
- **以为 `%rbp` 永远是 frame pointer，或永远只是普通 register。** 它通常可省略，也可在需要稳定 reference 时作 frame pointer；无论哪种用途，均受 callee-saved rule 约束。
- **把 recursive result 放错 register。** `pcount_r` inner result 在 `%rax`，本层 bit 在 `%rbx`；原 transcript 在 `00:59:46` 的冲突仍按 section 保留为 `[需回听 00:59:46]`。
- **把 ABI 能防止的 clobber 与错误 memory write 混为一谈。** Saving convention 保护 compliant register use；课件明确指出显式 buffer overflow 仍可破坏其他 frame。[课件: 07-machine-procedures.pptx p.53]

## 掌握标准

### 基础达标

- 不看资料画出地址方向、`%rsp`、stack top，并写出 push/pop/call/ret 的状态变化顺序。
- 不看资料写出前六个 integer/pointer argument registers、`%rax` return register，以及 arguments 7+ 的位置。
- 能用一句话区分 ABI convention 与 hardware instruction support。
- 能解释 frame 属于 invocation，并画出三层递归时的 return address 与 private state。

### 应用达标

- 给定包含 instruction addresses 的 call site，能算出 return address，并追踪 call 前后与 ret 前后的 `%rip/%rsp`。
- 能从 assembly 判断 local object 是否在 stack、某个 `leaq` 是否传递 address、某个 value 是否跨 call 仍 live。
- 能按 ABI 判断寄存器由谁保存，并验证 save/restore 是否成对、epilogue 顺序是否正确。
- 能逐条执行 `call_incr`，得到 `v1=18213`、`v2=15213` 和 return value `33426`。

### 综合达标

- 能从 `pcount_r` 的 C recurrence 独立解释 base path、recursive setup、inner return、sum、restore 和 unwind。
- 能说明 `%rbp` 的 stable frame-reference 能力为什么依赖 callee-saved contract。
- 能对一段陌生但同类的 procedure assembly 同时标注 control、data、local storage 和 register-saving 四条线，而不是套固定 prologue 模板。
- 能通过 hand trace 或 debugger single-step 预测并核对每条 instruction 后的 `%rsp`、关键 registers 与 relevant memory。

### 参考答案

1. Passing control、passing data、managing local storage；hardware 提供 registers/instructions，但参数位置、保存责任与 stack layout 需要所有参与者共同采用 ABI convention。
2. `%rsp=0x118`；新 value 写入 `M[0x118]` 成为 top，原 top 仍在较高地址。
3. `%rsp` 从 `0x120` 变为 `0x118`，`M[0x118]=0x400549`，`%rip=0x400550`。
4. `ret` 把当前 `%rsp` 所指 value 当 return address；若仍指向 local area，就会把 data 当作 address。
5. `%rdi,%rsi,%rdx,%rcx,%r8,%r9`；return value 在 `%rax`；第 7 个及以后参数在 caller 提供的 stack area。
6. Frame 对应动态 invocation，不对应静态 code；每个尚未返回的调用都需要 private arguments、locals、saved state 与 return information。
7. Compiler 已知固定 allocation 大小，可用成对的 `subq/addq` 和固定 `%rsp` offsets；运行时大小未知的 local array/buffer 等情况可能需要 `%rbp` 提供稳定 reference。
8. `incr` 把 `*p` 从 `15213` 更新为 `18213`，同时在 `%rax` 返回 old value `15213`；caller 再相加得到 `33426`。
9. `leaq` 计算 address `%rsp+8`，`movq` 则读取该 address 中的 contents。
10. Caller-saved 由需要 old value 的 caller 在 call 前保存；callee-saved 由要改写它的 callee 保存并在 return 前恢复；`%rsp` 可在 body 中变化，但退出时必须恢复到正确 stack state。
11. `%rdi` 将被改成 `&v1` 且可被 callee 改写，`x` 又跨 call 仍 live；`%rbx` 是 callee-saved，但本函数要改写它，所以也必须为自己的 caller 保存 entry value。
12. `%rax=P(x>>1)`，`%rbx=x&1`；两者先相加形成当前 `%rax=P(x)`，随后 pop 只恢复 `%rbx`，不改 `%rax`。
13. 每次普通 call 都独立保存 return address、按需建立 private frame 并遵守相同 saving rules；stack 只依赖动态 LIFO 顺序，不依赖 function names 是否相同。
14. 不能。约定防止 compliant register use 相互破坏，但错误 pointer 或课件提到的 buffer overflow 仍可写坏其他 frame。[课件: 07-machine-procedures.pptx p.53]

# 第 1 节：过程机制、ABI 与运行时栈的方向

> 时间范围：`00:00:00-00:10:00`  
> 内容属性：从整门课的 machine-level programming 主线进入 procedure，先建立 ABI、过程调用的三类职责，再引入 x86-64 runtime stack。

## 本段在整讲中的作用

本段回答两个入口问题：高级语言中的 function/procedure/method 到机器层究竟需要完成哪些工作，以及这些工作为何不能只靠处理器硬件自行决定。Randy Bryant 先把 procedure 拆成 **control、data、memory management** 三类机制，再说明 Linux x86-64 的具体实现由硬件能力与 **ABI（Application Binary Interface）约定**共同组成。随后，他以“调用期间需要、返回后即可丢弃”的生命周期为理由，引出 runtime stack、`%rsp` 和向低地址增长的规则。

本段还给出全讲的阅读原则：x86-64 为降低调用开销，只使用某次调用真正需要的机制，因此不能期待每个函数都有固定、完整的 prologue/epilogue 模板。[课件: 07-machine-procedures.pptx p.2] 后续六节分别把 control、data、local storage、register saving 和 recursion 填入这套框架。

## 学习目标

- 区分 function、procedure、method 在本讲语境中的用词差异与共同机器机制。
- 解释 ABI 为什么是 software convention，而不是一条单独的硬件指令。
- 按老师顺序说出 procedure 的三类职责：传递控制、传递数据、管理局部存储。
- 说明 x86-64 为什么只实现某次调用实际需要的部分。
- 画出 `%rsp`、栈顶、地址增长方向和栈增长方向之间的关系。

## 前置知识与依赖

- 依赖前两讲的基本 machine-code 视角：memory 可看作 byte array，寄存器保存当前执行状态。
- 需要知道 C function 可以有参数、返回值和 automatic local variables。
- 本段尚未要求记住参数寄存器，也尚未解释 `call`/`ret` 的具体状态变化；这些分别在第 3 节和第 2 节展开。
- 课程开头提到 Bomb Lab，只是在提醒当前 machine-level material 与 lab 的关系，不构成本段新的 Bomb Lab 规则。

## 核心教学路径

1. 把 function、procedure、method 统一到同一类机器层问题。
2. 说明实现来自 x86-64 hardware 与 Linux ABI convention 的组合。
3. 将 procedure 分解成 control、data、memory management 三类职责。
4. 从调用频繁且函数可能很短，推出“只做必要工作”的低开销原则。
5. 从 procedure state 的嵌套生命周期推出 LIFO stack discipline。
6. 定义 `%rsp`、栈顶与“向低地址增长”，并提醒课件图的视觉方向容易反直觉。

## 教学展开

### 1. Machine-level programming 是课程核心，当前内容直接服务 Bomb Lab（`00:00:00-00:00:40`）

Randy 先把当前连续几讲的 machine-level programming 称为课程核心之一，因为后续许多主题都建立在这套执行模型之上。他提醒学生已经拿到 Lab 2/Bomb Lab；完成当天内容后，应已具备解决大部分 phase 所需的过程调用知识，因此不要拖到最后才开始。

这里的教学作用是把“procedure calling convention”从孤立汇编规则连接到 reverse engineering：读函数调用时，必须知道控制去了哪里、参数在哪里、返回值在哪里以及哪些状态会被保留。

### 2. Function、procedure、method 在本讲覆盖同一类机制（`00:00:40-00:01:09`）

老师说明本讲会使用 **procedure** 一词，但 C 的 function、一般语言中的 procedure、object-oriented programming 中的 method，在当前机器层讨论中“roughly the same thing”。这不是说三者在语言语义上完全等价，而是说本讲关注的共同机制相同：进入一段代码、传入数据、保存调用状态、返回调用点。

课件标题将本讲主题定为 *Machine-Level Programming III: Procedures*。[课件: 07-machine-procedures.pptx p.1]

### 3. ABI：硬件能力之上的共同二进制约定（`00:01:09-00:03:20`）

Procedure 的实现一部分来自 x86-64 hardware，另一部分来自系统参与者共同遵守的约定。老师把后者称为 **ABI（Application Binary Interface）**：compiler、operating system、library/tool 等需要在 machine-program level 对资源和接口形成共同理解。

关键层次是：

```text
高级语言调用
    ↓ compiler 按约定翻译
Linux x86-64 ABI
    ├─ 参数和返回值放在哪里
    ├─ 哪些寄存器可被改写、哪些必须恢复
    └─ 栈如何组织调用状态
    ↓ 使用
x86-64 指令与寄存器机制
```

ABI 是可查阅的标准文档，不是处理器自动强制出的唯一方案。老师用平台差异说明这一点：Linux、Windows、OS X 和 FreeBSD 的 ABI 大体相似，却可能在细节上不同。共同约定让不同 compiler 生成的 object code、OS 与 debugger 等工具能够协作；若各自选择参数位置或保存规则，独立编译的代码便无法可靠调用。[课件: 07-machine-procedures.pptx p.2]

### 4. Procedure 的第一类职责：传递控制（`00:03:20-00:04:24`）

老师用 `P` 调用 `Q` 的抽象例子拆解 control：

```c
P(...) {
    ...
    y = Q(x);
    print(y);
    ...
}
```

调用发生时，执行必须从 `P` 跳到 `Q` 的第一条代码；`Q` 到达 return point 后，又必须回到 **`P` 中 call 之后的位置**，而不是任意返回到 `P`。因此系统必须保存 return information。课件把这两步概括为 “to beginning of procedure code” 和 “back to return point”。[课件: 07-machine-procedures.pptx p.2]

本段只定义问题；`call` 如何保存下一条指令地址、`ret` 如何取回该地址，在第 2 节逐状态追踪。

### 5. Procedure 的第二类职责：传递参数和返回值（`00:04:24-00:05:07`）

在例子中，`P` 的值 `x` 要成为 `Q` 内部的参数 `i`，而 `Q` 的计算结果又要返回给 `P` 并赋给 `y`。这要求双方对 data placement 有共同约定：caller 把 argument 放到 callee 预期的位置，callee 把 return value 放到 caller 预期的位置。[课件: 07-machine-procedures.pptx p.2]

此处没有指定具体寄存器。第 3 节才给出前六个 integer/pointer arguments 的顺序与 `%rax` 返回规则。

### 6. Procedure 的第三类职责：分配并回收局部存储（`00:05:07-00:05:46`）

`Q` 可能需要 local data，例如课件中的 `int t` 与 `int v[10]`。这些对象在 procedure execution 期间需要空间，而 function return 后其 automatic local state 应被回收，否则连续调用会无界消耗 storage。[课件: 07-machine-procedures.pptx p.2]

这里建立的是生命周期约束：

```text
进入 Q -> Q 的局部状态开始需要空间
执行 Q -> 参数、局部变量、临时状态仍有效
返回 P -> Q 的该次调用状态不再需要
```

本段还没有声称所有 locals 都必须放在 stack；后续会看到能留在 registers 的值通常不需要 stack space。

### 7. x86-64 的优化原则：只做本次调用需要的工作（`00:05:46-00:07:22`）

Procedure call 可能很频繁，而良好 modular style 又会产生许多只做少量工作的短函数。若每次调用都无条件执行完整的状态保存和内存分配，overhead 会盖过实际计算。因此 x86-64 implementation 采用的原则是：

- 不需要 local storage，就不分配也不回收。
- 没有对应 data，就不执行多余传递。
- 不修改某个需保存的 register，就不为它生成 save/restore。
- 只组合本次 procedure 所需的机制。[课件: 07-machine-procedures.pptx p.2]

这提高效率，却使汇编阅读没有一份每次照抄的固定模板。判断某条 `pushq`、`subq` 或 register move 的目的，必须回到该函数真实的数据生命周期与调用关系。

课件用 agenda 将后续内容排成 stack structure、calling conventions、passing control、passing data、managing local data、recursion。[课件: 07-machine-procedures.pptx p.3]

### 8. Runtime stack 只是普通 memory 中按栈规则管理的一段（`00:07:22-00:08:46`）

在讲 control transfer 前，老师先引入 stack。它不是一种与 main memory 分离的特殊存储器，而是 ordinary memory byte array 中被程序按 stack discipline 使用的区域。它承载与 outstanding procedure calls 相关的 control information、data 和 local storage。[课件: 07-machine-procedures.pptx p.4]

为什么 LIFO 合适？若 `P` 调 `Q`，`Q` 又调 `R`，则 `R` 必须先返回给 `Q`，`Q` 才能返回给 `P`。最后创建的调用状态最先失效，恰好符合 last-in, first-out：

```text
调用顺序：P -> Q -> R
入栈顺序：P 状态，Q 状态，R 状态
返回顺序：R -> Q -> P
回收顺序：R 状态，Q 状态，P 状态
```

### 9. `%rsp` 指向栈顶，栈向较低地址增长（`00:08:46-00:10:00`）

x86-64 stack 从较高地址一侧向较低地址增长。Register `%rsp` 保存当前 stack top 的地址；课件更精确地写成当前 stack 中的最低地址，即 “top” element 的地址。[课件: 07-machine-procedures.pptx p.4]

课堂画法把高地址放在图上方、低地址放在图下方，因此“栈顶”通常画在底部，新增空间时 `%rsp` 数值减小：

```text
较高地址
    +-----------------------+  stack bottom / 较早状态
    | 已有调用状态          |
    +-----------------------+
    | 当前 top element      |  <- %rsp
    +-----------------------+
    | 尚未属于当前 stack    |
    +-----------------------+
较低地址

分配更多 stack space：%rsp 向低地址移动，即数值减小
```

“top 在图的 bottom”“增长却做 subtraction”都容易违反日常直觉。老师要求先固定地址方向，再读后续每次 `pushq`、`call` 和 frame allocation；第 2 节会把该规则落实为 8-byte 状态变化。

## 概念、符号与推导

### 关键定义

- **ABI**：binary/machine-program level 的共同接口约定，规定独立代码如何交换控制、数据并保存状态。
- **Caller / callee**：本段暂以 `P`/`Q` 表示调用方与被调用方；正式术语在第 5 节引入。
- **Runtime stack**：ordinary memory 中按 LIFO discipline 管理 procedure state 的区域。
- **Stack pointer `%rsp`**：保存当前 stack top 地址的 x86-64 register。
- **Return point**：caller 中紧随 procedure call、被调用函数结束后应继续执行的位置。

### 本段的状态关系

若分配 $n$ bytes 的 stack space，且该操作只通过移动 stack pointer 完成，则课堂方向关系为：

$$\%rsp_{\text{new}} = \%rsp_{\text{old}} - n$$

本段只建立方向；具体 instruction sequence 和 alignment 约束留待后文。

### 三类机制的依赖

```text
procedure invocation
├─ control：进入 callee + 回到 caller 的正确 return point
├─ data：arguments -> callee；return value -> caller
└─ memory management：调用期间分配；返回时回收

三者共享基础：ABI convention + registers/instructions + runtime stack
```

## 关键概念与依赖关系

- Machine-level execution -> 需要明确 control、data 与 storage 的真实位置。
- Hardware capability + ABI convention -> Linux x86-64 calling convention。
- Nested call/return lifetime -> LIFO discipline -> runtime stack。
- Stack grows toward lower addresses -> allocation decrements `%rsp`。
- “Only mechanisms required” -> 不存在所有函数都相同的固定 frame 模板。
- 本节 stack model -> 第 2 节 `push/pop/call/ret` -> 第 4 节 stack frame -> 第 7 节 recursion。

## 常见误解

- **误解：Function、procedure、method 在所有语言语义上完全相同。** 老师只是在本讲 machine-level calling mechanism 的范围内统一称呼。
- **误解：ABI 就是 x86-64 硬件规范本身。** ABI 是各系统参与者共同遵守的软件/二进制接口约定，不同 OS 可以采用不同细节。
- **误解：每次 procedure call 都必须完成三类机制的完整模板。** 三类是可能需要承担的职责；具体代码只执行本次调用必要的部分。
- **误解：所有 local variables 都在 stack。** 本段只说需要 memory allocation 的 local state 可由 stack 管理；能保存在 registers 的值未必落栈。
- **误解：Runtime stack 是一种独立于 ordinary memory 的硬件存储。** 它是普通 memory 中按 stack discipline 管理的区域。
- **误解：图上向下增长等于地址增加。** 本讲图中栈向图下方扩展恰好对应较低地址，`%rsp` 数值减小。

## 本段掌握检查

1. **问：ABI 为什么是 procedure 能跨 compiler、library 和 OS component 协作的基础？**  
   **答：** 因为各方必须共同约定参数、返回值、寄存器保存和 stack organization；只共享硬件指令而没有这些位置规则仍无法可靠互调。

2. **问：Procedure call 必须解决哪三类问题？**  
   **答：** 把控制转入 callee 并回到正确 return point、传入 arguments 并返回 result、在调用期间分配且在返回后回收所需 local state。

3. **问：为什么 runtime stack 与 procedure call/return 自然匹配？**  
   **答：** Callee 必须先于 caller 返回，最后创建的调用状态最先失效，正好符合 LIFO。

4. **问：为什么不能看到一个短函数没有 stack allocation 就判断 compiler 漏了步骤？**  
   **答：** Linux x86-64 implementation 只使用实际需要的机制；若数据都能留在 registers，就无需为 local storage 调整 `%rsp`。

5. **问：向 stack 添加空间时 `%rsp` 为什么减小？**  
   **答：** x86-64 stack 向较低地址增长；`%rsp` 指向当前 top，所以新 top 的地址数值更小。

# 第 2 节：`push`/`pop` 与 `call`/`ret` 的控制流轨迹

> 时间范围：`00:10:00-00:19:58`  
> 内容属性：承接栈向低地址增长的规则，先定义 8-byte push/pop，再用 `multstore` 调用 `mult2` 精确追踪 return address、`%rsp` 与 `%rip`。

## 本段在整讲中的作用

第 1 节说明 procedure 必须把控制转入 callee，并在结束后回到 caller 中正确的位置；本段给出这一职责的机器实现。老师先把栈的抽象操作落实成 `pushq`/`popq` 对 `%rsp` 和 memory 的有序更新，再说明 `call`/`ret` 只负责 procedure 的 **control component**：`call` 保存 return address 并跳转，`ret` 取回 return address 并跳回。

核心例子是 `multstore` 在地址 `0x400544` 调用 `mult2`。课件连续四页显示调用前、进入 callee、到达 `ret`、返回 caller 四个快照，使“return address 是 call 后下一条 instruction 的地址”成为可手工验证的状态变化，而不是需要死记的口号。[课件: 07-machine-procedures.pptx p.10] [课件: 07-machine-procedures.pptx p.11] [课件: 07-machine-procedures.pptx p.12] [课件: 07-machine-procedures.pptx p.13]

## 学习目标

- 按正确先后顺序展开 `pushq Src` 与 `popq Dest`。
- 解释移动 `%rsp` 为什么等价于分配/回收 stack space，却不会擦除 memory bytes。
- 区分 `call`/`ret` 的 control responsibility 与完整 procedure call 的其他职责。
- 从 disassembly 计算 return address，并追踪 `%rsp`、`%rip` 和 top-of-stack。
- 解释为什么 `ret` 前必须把 `%rsp` 恢复到指向正确 return address 的位置。

## 前置知识与依赖

- 依赖第 1 节：stack grows toward lower addresses，`%rsp` 指向当前 top。
- 需要能阅读十六进制减法，例如 `0x120 - 8 = 0x118`。
- 需要知道 `%rip` 是 instruction pointer/program counter；普通汇编代码通常不通过通用 `mov` 直接改写它。
- 本段不解释参数与返回值寄存器，也不解释为什么 `multstore` 保存 `%rbx`；分别留到第 3、5、6 节。

## 核心教学路径

1. 重申图中地址方向与 `%rsp` 的减法增长规则。
2. 将 `pushq` 展开为“先减 `%rsp`，后写 memory”。
3. 将 `popq` 展开为“先读 memory，后加 `%rsp`，再交付 destination”。
4. 强调 deallocation 只改变 stack boundary，不清零旧 bytes。
5. 从 `multstore`/`mult2` disassembly 抽出 `call` 与 `ret`。
6. 用四个地址快照完成 caller -> callee -> caller 的闭环。

## 教学展开

### 1. 固定坐标：图向下是低地址，新增栈项令 `%rsp` 减小（`00:10:00-00:10:34`）

老师从上一节未完的栈图继续：图上的 arrow 表示 bytes 的地址朝上方增大；stack top 画在下方，因此向 stack 加数据时，`%rsp` 朝更低地址移动。读图时应以 address number 为准，而不是凭“top 应该在纸上方”的直觉。[课件: 07-machine-procedures.pptx p.4]

### 2. `pushq Src`：先建立新栈顶，再写入 8 bytes（`00:10:34-00:11:15`）

课件给出的顺序是：[课件: 07-machine-procedures.pptx p.5]

1. Fetch operand at `Src`。
2. `%rsp = %rsp - 8`。
3. 将 operand 写入新 `%rsp` 指向的地址。

用状态表达：

$$
t \leftarrow \operatorname{Val}(Src),\qquad
\%rsp \leftarrow \%rsp - 8,\qquad
M[\%rsp] \leftarrow t
$$

先减后写很重要。旧 `%rsp` 已指向旧 top element；若先写，就会覆盖旧 top，而不是创建新项。

```text
pushq Src 前                     pushq Src 后
较高地址                         较高地址
+------------------+             +------------------+
| 旧 top           | <- %rsp_old | 旧 top           |
+------------------+             +------------------+
| 非 stack 空间    |             | Src 的 8-byte 值 | <- %rsp_new
+------------------+             +------------------+
较低地址                         较低地址

%rsp_new = %rsp_old - 8
```

`q` 表示 quad word；老师指出在这些指令名中后缀常被省略，因此课堂的 `push`/`pushq` 指同一 8-byte 操作。

### 3. `popq Dest`：先读取当前 top，再把边界上移 8 bytes（`00:11:15-00:12:01`）

课件把 `popq Dest` 展开为：[课件: 07-machine-procedures.pptx p.6]

1. 读取 `M[%rsp]`。
2. `%rsp = %rsp + 8`。
3. 将读出的 value 存入 `Dest`；该 destination 必须是 register。

为避免因为先移动 `%rsp` 而读错位置，可写成：

$$
t \leftarrow M[\%rsp],\qquad
\%rsp \leftarrow \%rsp + 8,\qquad
Dest \leftarrow t
$$

```text
popq Dest 前                     popq Dest 后
较高地址                         较高地址
+------------------+             +------------------+
| 下一项           |             | 下一项           | <- %rsp_new
+------------------+             +------------------+
| 当前 top = t     | <- %rsp_old | bytes 仍是 t，    |
+------------------+             | 但已不属 stack    |
较低地址                         +------------------+
                                  较低地址
```

### 4. Push/pop 可理解为常见复合操作，回收不等于擦除（`00:12:01-00:13:34`）

学生问能否用多条 ordinary instructions 表达 push/pop。老师回答除少数 corner cases 外，可以把它们理解为 arithmetic on `%rsp` 加 memory move；因为模式常见，instruction set 提供了单独指令。

老师随后强调 **deallocate 不会 magically erase data**。`pop` 只让 `%rsp` 增加，使原 top 不再处于当前 stack 区间；其 bit pattern 仍可暂时留在 memory，直到以后被覆盖。这是 stack ownership/liveness 的改变，不是 secure deletion。

### 5. `call`/`ret` 只实现 control transfer（`00:13:34-00:15:31`）

老师重新展示两个 C functions 及 disassembly：[课件: 07-machine-procedures.pptx p.8]

```c
long mult2(long a, long b) {
    long s = a * b;
    return s;
}

void multstore(long x, long y, long *dest) {
    long t = mult2(x, y);
    *dest = t;
}
```

```asm
0000000000400550 <mult2>:
  400550: mov    %rdi,%rax
  400553: imul   %rsi,%rax
  400557: retq

0000000000400540 <multstore>:
  400540: push   %rbx
  400541: mov    %rdx,%rbx
  400544: callq  400550 <mult2>
  400549: mov    %rax,(%rbx)
  40054c: pop    %rbx
  40054d: retq
```

`call label` 和 `ret`/`retq` 处理的只是三类 procedure mechanism 中的 **passing control**。它们不会自动决定 arguments 如何放置，也不会自动为所有 locals 建立统一 frame。[课件: 07-machine-procedures.pptx p.9]

老师还说 disassembly 中偶尔出现 `rep; ret`，在本课程当前分析层次可以按 `ret` 理解；本段不展开该前缀的历史或微架构原因。

### 6. Call 前状态：`%rip = 0x400544`，`%rsp = 0x120`（`00:15:31-00:16:03`）

老师使用很小、并不真实的 stack address `0x120` 方便手算。执行前：[课件: 07-machine-procedures.pptx p.10]

```text
%rip = 0x400544  -> callq 0x400550 <mult2>
%rsp = 0x120

stack:
0x130  ...
0x128  ...
0x120  old top <- %rsp
```

Disassembly 表明 `callq` 从 `0x400544` 到下一条 `mov` 的地址 `0x400549`，所以 **return address 是 `0x400549`**，不是 call 本身的地址，也不是 callee 起点。

### 7. 执行 `call`：push return address，并把 `%rip` 改为 callee entry（`00:16:03-00:18:33`）

该 `call` 的可观察效果分三步理解：[课件: 07-machine-procedures.pptx p.9] [课件: 07-machine-procedures.pptx p.11]

1. `%rsp: 0x120 -> 0x118`。
2. `M[0x118] = 0x400549`，保存 call 后下一条 instruction 的地址。
3. `%rip = 0x400550`，开始执行 `mult2`。

```text
callq 后 / mult2 入口

%rip = 0x400550
%rsp = 0x118

较高地址
0x120  caller 原 top
0x118  0x400549       <- %rsp，return address
较低地址
```

若保存 `0x400544`，`ret` 后会再次执行同一个 call，形成错误循环。因此 return address 必须是 **next instruction**。老师还回答学生：普通程序不先把 callee address 显式 `mov` 入 `%rip`；call instruction 自身完成 target control transfer。

### 8. Callee 到达 `ret`：top-of-stack 仍是 return address（`00:18:33-00:19:58`）

`mult2` 执行到 `0x400557: retq` 时，课件状态为：[课件: 07-machine-procedures.pptx p.12]

```text
%rip = 0x400557  -> retq
%rsp = 0x118
M[0x118] = 0x400549
```

`ret` 假设当前 `%rsp` 指向应跳转的 address。它将该地址从 stack 取出，使 `%rsp` 增加，并把 program counter 设置为该值。到本段末尾，老师已经讲到“数值并不会从 memory 消失，只是不再属于 stack”；`%rip` 和 `%rsp` 的最终快照在第 3 节开头完成。[课件: 07-machine-procedures.pptx p.13]

## 概念、符号与推导

### Push/pop 的顺序不变量

```text
push：read Src -> decrement %rsp -> write M[%rsp]
pop ：read M[%rsp] -> increment %rsp -> write Dest
```

两者都改变 stack boundary；只有 push 写入 stack memory，pop 不负责清零旧位置。

### `call`/`ret` 的配对状态

令 `RA` 为 call 后下一条 instruction 的地址，`Target` 为 callee entry：

```text
call Target:
    %rsp <- %rsp - 8
    M[%rsp] <- RA
    %rip <- Target

ret:
    RA <- M[%rsp]
    %rsp <- %rsp + 8
    %rip <- RA
```

这是本讲为理解状态变化采用的语义模型；不表示汇编程序需要手写这些伪指令。

### `multstore -> mult2` 完整地址轨迹

| 时刻 | `%rip` | `%rsp` | `M[0x118]` | 含义 |
| --- | --- | --- | --- | --- |
| call 前 | `0x400544` | `0x120` | 未作为当前 return slot | caller 将调用 `mult2` |
| call 后 | `0x400550` | `0x118` | `0x400549` | 已进入 callee |
| ret 前 | `0x400557` | `0x118` | `0x400549` | callee 准备返回 |
| ret 后 | `0x400549` | `0x120` | bytes 可仍保留 | caller 从下一条继续 |

## 关键概念与依赖关系

- Stack grows down -> `push` 先 `%rsp -= 8`。
- LIFO -> `pop` 从当前 `%rsp` 读取后 `%rsp += 8`。
- Caller 的 next instruction address -> return address -> `ret` 的 target。
- `call` push return address + jump target；`ret` pop address + jump address。
- 正确 `%rsp` -> 正确 return address -> 正确 control flow。
- 本节 control path -> 第 3 节 data path -> 第 4、5 节 local stack management。

## 例子与课堂提示

- **学生把 push/pop 拆成多条指令**（`00:12:01-00:12:32`）：帮助把专用 mnemonic 还原成 register + memory state change。
- **Deallocation 不擦除**（`00:13:11-00:13:27`）：区分逻辑 stack membership 与物理 bytes。
- **虚构的小地址 `0x120`**（`00:15:36-00:15:47`）：只为十六进制演算方便，不代表真实 Linux process 的 stack address。
- **`%rip` 与“RIP”玩笑**（`00:15:47-00:15:56`）：用于记住 instruction pointer 名称，不影响机制。
- **若返回到 call 本身会循环**（`00:16:31-00:16:50`）：解释 return address 为什么取 `0x400549`。

## 常见误解

- **误解：`pushq` 先写旧 `%rsp`，再移动 pointer。** 正确顺序是先减 8，再写新 top。
- **误解：`popq` 会删除或清零 memory 中的旧值。** 它只读值并移动 `%rsp`；旧 bytes 可仍存在。
- **误解：`call` 自动传参数并建立所有 locals。** 本段明确说它只处理 control component。
- **误解：Return address 是 call instruction 自己的地址。** 它是 call 后下一条 instruction 的地址。
- **误解：`ret` 知道 caller 的函数名。** `ret` 只相信 `%rsp` 所指的 address；stack 被破坏或 `%rsp` 未恢复就会跳错。
- **误解：`retq` 与 `ret`、`callq` 与 `call` 是本讲中的不同控制机制。** 在当前 64-bit 代码语境中，老师把带/不带 `q` 的写法视为同一操作。

## 本段掌握检查

1. **问：为什么 `pushq` 必须先 decrement `%rsp`？**  
   **答：** 旧 `%rsp` 已指向旧 top；先减 8 才能建立一个不覆盖旧 top 的新 slot。

2. **问：`popq` 后原 stack slot 的数据发生了什么？**  
   **答：** Value 已读入 destination，`%rsp` 增加使该 slot 不再属于 stack，但 memory bytes 不保证被清零。

3. **问：执行地址 `0x400544` 的 call 后，为什么压入 `0x400549`？**  
   **答：** `0x400549` 是 call 后下一条 instruction，callee 返回后应从那里继续 caller。

4. **问：该 call 执行后 `%rsp` 和 `%rip` 各是什么？**  
   **答：** `%rsp = 0x118`，`M[0x118] = 0x400549`，`%rip = 0x400550`。

5. **问：`call`/`ret` 没有完成完整 procedure protocol 的哪些部分？**  
   **答：** 它们不独自规定 argument/return-value data placement，也不自动管理所有 local storage 或 register saving。

# 第 3 节：参数/返回寄存器与每次调用独立的栈帧

> 时间范围：`00:19:58-00:29:52`  
> 内容属性：先完成 `ret` 的控制流闭环，再从 passing control 转向 passing data，最后用递归 call chain 引出 stack frame 与可选 `%rbp`。

## 本段在整讲中的作用

第 2 节已经把 return address 放到 stack top，本段开头完成 `ret` 后的 `%rip/%rsp` 恢复。随后老师讲 ABI 的第二类职责：前六个 integer/pointer arguments 使用 registers，return value 使用 `%rax`，更多参数才使用 stack。`multstore`/`mult2` 再次出现，用同一段代码把 argument path 和 result path 对齐。

后半段进入第三类职责 local storage。老师从“单线程中同一时刻只有一个 procedure instance 在执行，但可能有许多尚未返回的 instances”推出 stack frame：每次调用都拥有自己的 state block。`yoo -> who -> amI -> amI ...` 的递归链说明 frame 绑定的是 **一次 invocation**，不是一份 function source code。[课件: 07-machine-procedures.pptx p.18] [课件: 07-machine-procedures.pptx p.19]

## 学习目标

- 完成 `mult2` 的 `ret` 状态变化并解释 caller 从哪里恢复。
- 按 ABI 顺序记住六个 integer/pointer argument registers 与 `%rax` return register。
- 说明第 7 个及以后的 arguments 为什么要进入 memory stack。
- 从 `mult2`/`multstore` 汇编标出 arguments 与 return value 的流向。
- 区分 function definition、一次 procedure invocation 与该 invocation 的 stack frame。
- 解释 recursion 为什么要求 reentrant code 和每次调用的 private state。

## 前置知识与依赖

- 依赖第 2 节：`call` 已在 stack top 保存 return address，`ret` 从 `%rsp` 所指位置取回。
- 需要熟悉 x86-64 register 名称和 C argument 的从左到右顺序。
- 本节只讨论 integer/pointer arguments；floating-point 使用另一组 registers，但老师未在本段列出其具体名称。
- `%rbp` 只在结尾引入；是否使用、如何恢复在第 4、7 节继续说明。

## 核心教学路径

1. 完成 `ret`：pop return address -> `%rsp` 复原 -> `%rip` 回到 caller。
2. 从 control 转到 data，给出六个 argument registers 与 `%rax`。
3. 解释更多 arguments 走 stack、register passing 相对旧 IA-32 的性能动机。
4. 用 `mult2`/`multstore` 对照 C parameters 与 machine registers。
5. 从 local state 的有限 lifetime 推出 stack allocation。
6. 用递归 call chain 说明每个 outstanding invocation 都需要自己的 frame。
7. 引入 `%rsp` 与可选 frame pointer `%rbp`。

## 教学展开

### 1. `ret` 完成控制流闭环（`00:19:58-00:20:27`）

承接上节状态，`ret` 从 `M[0x118]` 取得 `0x400549`，令 `%rsp` 回到 `0x120`，并把 `%rip` 设为 `0x400549`。Caller 因而从 call 后的 `mov %rax,(%rbx)` 继续：[课件: 07-machine-procedures.pptx p.13]

```text
ret 前                         ret 后
%rip = 0x400557                %rip = 0x400549
%rsp = 0x118                   %rsp = 0x120
M[0x118] = 0x400549            M[0x118] bytes 可仍在，已不属 stack
```

老师把机制概括为一个巧妙配对：call push next-instruction address，ret 再将其用作 next program counter。单个 primitive 很简单，但组合后建立出 procedure call/return。

### 2. ABI 的 data rule：六个 argument registers 与 `%rax`（`00:20:27-00:22:14`）

Passing control 完成后，老师转向 passing data。Linux x86-64 ABI 对 integer/pointer arguments 的前六个位置规定如下：[课件: 07-machine-procedures.pptx p.15]

| 参数序号 | Register |
| --- | --- |
| 1 | `%rdi` |
| 2 | `%rsi` |
| 3 | `%rdx` |
| 4 | `%rcx` |
| 5 | `%r8` |
| 6 | `%r9` |
| Return value | `%rax` |

这个顺序没有老师要求学生推导的内在规律，需要记忆或查表。规则属于 ABI convention，并非 hardware 自动知道 C 的“第一个参数”。Callee code 是在 compiler 假定 caller 已遵守相同规则的前提下生成的。

Floating-point arguments 走另一组 registers；本段不列寄存器名，因此笔记也不外推。当前所有例子都限定在 integer 或 pointer data。

### 3. 超过六个参数时使用 stack（`00:22:14-00:22:51`）

若 function 有超过六个 integer/pointer arguments，第 7 个及以后由 caller 放在 memory stack 上，callee 从约定位置取出。老师暂不展示七参数的繁杂例子，指出教材另有示例。[课件: 07-machine-procedures.pptx p.15]

与 IA-32 时代所有 arguments 多经 stack 传递相比，x86-64 尽可能使用 registers，动机是 register access 通常比 memory access 快。应注意“前六个”不是“函数最多只能收六个”。

### 4. `mult2`：parameters 从 `%rdi/%rsi` 进入，result 从 `%rax` 出去（`00:22:51-00:24:26`）

课件把 data annotation 直接写进 disassembly：[课件: 07-machine-procedures.pptx p.16]

```asm
# long mult2(long a, long b)
# a in %rdi, b in %rsi
mult2:
    movq  %rdi, %rax      # %rax = a
    imulq %rsi, %rax      # %rax = a * b
    ret                   # return value already in %rax
```

`multstore(long x, long y, long *dest)` 的三个 arguments 同理进入 `%rdi`、`%rsi`、`%rdx`。在 call 前，code 把 `dest` 从 `%rdx` 移到 `%rbx`；`mult2` 返回后，caller 假定 `%rax` 中就是 `t`，再执行 `mov %rax,(%rbx)` 写到 `*dest`：[课件: 07-machine-procedures.pptx p.16]

```text
caller multstore                     callee mult2
x -> %rdi --------------------------> a
y -> %rsi --------------------------> b
dest -> %rdx -> %rbx (先保存)

                       call mult2
                       %rax <- a*b
                       ret

t <- %rax
M[%rbx] <- %rax   即 *dest = t
```

本段只观察 `%rbx` 跨 call 保存 `dest` 的事实；为什么 callee 不会破坏它，要到 register-saving convention 才能证明。

### 5. 统一 ABI 让独立编译的代码互调（`00:24:26-00:25:33`）

只要 caller 和 callee 遵守同一 binary interface，不同 compiler 生成的 modules 仍能交换 arguments 和 result。这正是 ABI 的工程价值：callee 不需要知道 caller 的 source language 细节，只需要相信入口 registers/stack layout；caller 同样相信 result 和 saved state 的规则。

学生问为什么 call/return 使用 8 bytes。老师说明 x86-64 address 是 64 bits，即 8 bytes；课堂中的 push/pop 也按 8-byte values 操作。与 IA-32 的 4-byte 情形不同。

### 6. 从 passing data 转向 managing local data（`00:25:33-00:26:18`）

老师没有为了 stack arguments 强行构造七参数函数，而是进入 procedure 的第三类机制：若有不能只留在 registers 的 local data，应该放在哪里、何时分配、何时释放？回答需要 **stack frame** 概念。

### 7. 每个 outstanding invocation 都有自己的 stack frame（`00:26:18-00:28:19`）

老师先限定 single-threaded model：任一时刻只有一个 function instance 正在执行，其余 callers 暂停但尚未返回。当前 callee 可能需要 arguments、local variables、temporaries 和 return pointer；return 后，这次调用的 state 按正确程序逻辑就不再需要。

因此可以在调用时将 state 压到 stack，更深调用继续压入，返回时按相反顺序回收。每个 block 称为一个 **stack frame**，更精确地说，是 particular call / particular procedure instantiation 的 frame。[课件: 07-machine-procedures.pptx p.18]

课件对支持 recursion 的语言提出 reentrant 要求：同一个 procedure 可以同时有多个尚未结束的 instantiations，每份都需要独立保存 arguments、locals 和 return pointer。[课件: 07-machine-procedures.pptx p.18]

### 8. `yoo -> who -> amI`：frame 跟随动态调用链（`00:28:19-00:29:25`）

课堂 call chain 为：[课件: 07-machine-procedures.pptx p.19]

```text
yoo()
  -> who()
       -> amI()
            -> amI()
                 -> amI()
       -> amI()       # who 返回到第二个 call site 后还可再调用
```

在最深处尚未返回时，stack 必须保留每个 outstanding call：

```text
较高地址 / 较早调用
+---------------------------+
| yoo frame                 |
+---------------------------+
| who frame                 |
+---------------------------+
| amI frame：第 1 层        |
+---------------------------+
| amI frame：第 2 层        |
+---------------------------+
| amI frame：第 3 层        | <- %rsp，当前 instance
+---------------------------+
较低地址 / 较晚调用
```

同一份 `amI` code 对应多个 frame；各层 local state 不因 code address 相同而合并。返回时最深 `amI` frame 先消失，然后逐层回到 `who`。

### 9. `%rsp` 与可选 `%rbp`（`00:29:25-00:29:52`）

老师最后说明 stack frame 传统上可由两个 pointers 描述：`%rsp` 是 stack pointer，`%rbp` 可作 base/frame pointer。但现代生成代码中的 `%rbp` 是 **optional**，下一节将解释固定大小 frame 如何只靠 `%rsp` 管理，以及何时才需要 `%rbp`。[课件: 07-machine-procedures.pptx p.20]

## 概念、符号与推导

### Integer/pointer data convention

```text
arguments 1..6: %rdi, %rsi, %rdx, %rcx, %r8, %r9
arguments 7+  : caller-provided stack area
return value  : %rax
```

这些是位置约定，不保证 values 在 procedure 内始终留在原寄存器；callee 可根据 ABI 对 caller-saved registers 重新使用，详见第 5、6 节。

### Frame 的动态含义

设 function `F` 同时有 $k$ 个尚未返回的 recursive invocations，则需要的是 $k$ 份 invocation state，而不是一份共享 local state：

$$
\operatorname{frames}(F) = \operatorname{outstanding\ calls}(F)
$$

这只是对课堂 stack-frame relation 的表达，不表示每个 frame 大小相同。

### Call chain 与 stack order

```text
dynamic calls: yoo -> who -> amI_1 -> amI_2 -> amI_3
frame order  : [yoo][who][amI_1][amI_2][amI_3 <- top]
returns      : amI_3 -> amI_2 -> amI_1 -> who -> yoo
```

## 关键概念与依赖关系

- ABI register order -> caller/callee 对 argument location 的共同假设。
- `%rax` convention -> callee result 可被 caller 直接消费。
- Arguments 7+ -> memory stack -> caller frame 的 argument-build area。
- Invocation state 的有限 lifetime -> stack allocation/deallocation。
- Recursion -> 同一 code 多个 simultaneous instances -> 每次调用 private frame。
- Optional `%rbp` -> 固定 frame 可只用 `%rsp` -> 第 4 节的 frame management。

## 常见误解

- **误解：第一个参数由 `%rax` 传递。** `%rax` 用于 return value；第一个 integer/pointer argument 是 `%rdi`。
- **误解：六个 registers 表示函数最多有六个参数。** 第 7 个及以后按 ABI 放在 stack。
- **误解：Arguments 进入寄存器后永远不会改变。** 这些入口 locations 不等于永久 storage；callee 可复用 caller-saved registers。
- **误解：`multstore` 返回后 `%rax` 中仍是 caller 原值。** Caller 按约定把 `%rax` 解释为 `mult2` 的 result。
- **误解：一个 recursive function 只有一个 frame。** 每个尚未返回的 invocation 都有自己的 state/frame。
- **误解：每个 frame 必须有 `%rbp`。** `%rbp` 是可选 frame pointer；许多固定大小 frames 只靠 `%rsp` 和编译期已知 offsets。

## 教学展开

### 1. `%rbp` 通常不作为专用 frame pointer（`00:29:52-00:30:47`）

老师指出本课程接下来看到的 code，除少数 special cases 外，通常不会把 `%rbp` 用作 base/frame pointer。它可以像普通 register 一样用于其他目的。因而只观察当前 `%rsp` 时，未必能从一个独立数值直接判断 frame 的完整边界；只能确定 topmost stack region 属于当前最深 procedure，具体 offsets 由生成的 code 自己管理。[课件: 07-machine-procedures.pptx p.20]

Return addresses、saved registers 和 local data 都在同一条 runtime stack 上，并不是三条相互隔离的 stack。阅读时要依据当前 `%rsp` 与 instruction sequence 判断每个 slot 的角色。

### 2. 固定大小 frame：入口减多少，出口就加多少（`00:30:47-00:34:06`）

此前简单例子只借 stack 保存 return address，没有显式 local allocation。一般 procedure 若需要 $n$ bytes，可在 setup code 中执行：

```asm
subq $n, %rsp     # allocate frame area
    ...
addq $n, %rsp     # deallocate the same area
ret
```

学生问：没有 `%rbp`，程序如何知道 return 时恢复到哪里？老师回答，compiler 在生成 code 时已经知道固定 frame 需要例如 16 bytes，因此入口减 16、出口加 16；不需要运行时再搜索 frame boundary。

$$
\%rsp_{\text{body}} = \%rsp_{\text{entry}} - n,
\qquad
\%rsp_{\text{before ret}} = \%rsp_{\text{body}} + n = \%rsp_{\text{entry}}
$$

### 3. Variable-size allocation 是需要稳定 base pointer 的特殊情况（`00:34:06-00:34:34`）

如果 function 在运行时才知道 local array 或 buffer 需要多少空间，compiler 无法只靠一个 compile-time constant 表示整个 `%rsp` movement。老师说这些 special cases 会使用 `%rbp`，以保留 frame 中一个稳定 reference point，随后才能在 `%rsp` 继续变化时定位 state 或恢复边界。

本段只给出使用动机，没有展示 variable-length array 的具体 prologue/epilogue，不能补造 instruction sequence。

### 4. Recursion：不断增加 frame，也会不断消耗有限 stack（`00:31:08-00:33:33`）

在回答 frame-pointer 问题前，老师继续演示 `yoo -> who -> amI`。每次 call 都可能创建新的 frame；`amI` 自递归时，stack 随 depth 继续向低地址增长。系统通常限制 stack 总大小，因此 runaway recursion 会不断请求 frame，最终超过限制；这是 recursion 相比 iteration 的一个空间风险。

```text
递归加深                                      递归回退

[yoo]                                         [yoo]
[who]                                         [who]
[amI #1]                                      [amI #1]
[amI #2]            -> deepest return ->      [amI #2] 被回收
[amI #3] <- %rsp                               [amI #3] 先被回收
```

这套机制的正面效果是每层 `amI` 都有 private local state；负面约束是 depth 会消耗更多 stack space。Recursive call 不需要不同于 ordinary call 的特殊硬件机制，正因为每次 ordinary call 已经建立隔离的 state。[课件: 07-machine-procedures.pptx p.21] [课件: 07-machine-procedures.pptx p.22] [课件: 07-machine-procedures.pptx p.23] [课件: 07-machine-procedures.pptx p.24] [课件: 07-machine-procedures.pptx p.25] [课件: 07-machine-procedures.pptx p.26] [课件: 07-machine-procedures.pptx p.27] [课件: 07-machine-procedures.pptx p.28] [课件: 07-machine-procedures.pptx p.29] [课件: 07-machine-procedures.pptx p.30] [课件: 07-machine-procedures.pptx p.31]

### 5. x86-64/Linux stack-frame layout（`00:34:34-00:36:31`）

老师按从较高地址的 caller frame 到较低地址的 current top 解释 frame：[课件: 07-machine-procedures.pptx p.32]

```text
较高地址
+--------------------------------------+
| caller frame                         |
| arguments 7+ for current call        |  caller 预先放置
+--------------------------------------+
| return address                       |  call instruction push
+--------------------------------------+
| old %rbp (optional)                  |
+--------------------------------------+
| saved registers + local variables    |
+--------------------------------------+
| argument build                       |  当前函数为下一次 call 准备
+--------------------------------------+ <- %rsp，current stack top
较低地址

%rbp：若使用，指向 frame 中稳定位置
```

各区域都是 **if needed**：

- Arguments 7+ 由 caller 为当前 call 准备。
- Return address 由 `call` push，在 callee 第一条 instruction 前已存在。
- Old `%rbp` 只在使用 frame pointer 时保存。
- Saved register context、local variables 和 temporary space 按需分配。
- Argument-build area 用于当前 procedure 将要调用的下一个 procedure。

典型 code 在 procedure 开头 decrement `%rsp`，返回前 increment 回去。Frame 不是固定字段全部出现的 struct，而是按 ABI 和需求形成的 layout。

### 6. `incr`：pointer、update 与 old value return 全部留在 registers（`00:36:31-00:38:43`）

课堂 C code：[课件: 07-machine-procedures.pptx p.33]

```c
long incr(long *p, long val) {
    long x = *p;
    long y = x + val;
    *p = y;
    return x;
}
```

对应汇编：

```asm
incr:
    movq (%rdi), %rax    # x = *p；也预放到 return register
    addq %rax, %rsi      # %rsi = val + x = y
    movq %rsi, (%rdi)    # *p = y
    ret                  # return x in %rax
```

入口 data flow：`p -> %rdi`，`val -> %rsi`。第一条既读取 old value `x`，又把它放在最终 return location `%rax`；`%rsi` 在使用原 `val` 后可直接改写为 `y`。整个 procedure 不需要保存跨其他 call 的 local state，也不调用下级函数，因此没有显式 `%rsp` allocation。

```text
初始：%rdi = p, %rsi = val, M[p] = x
movq ：%rax = x
addq ：%rsi = x + val = y
movq ：M[p] = y
ret  ：caller 得到 %rax = x
```

这段 code 同时提醒：C variable name 不等于永久 register；compiler 可以让 `%rsi` 先代表 `val`，随后代表 `y`。

### 7. `call_incr`：`&v1` 迫使 local variable 落栈（`00:38:43-00:39:44`）

Caller code 为：[课件: 07-machine-procedures.pptx p.34]

```c
long call_incr() {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return v1 + v2;
}
```

`v1` 不能只保存在 register，因为 `&v1` 必须产生一个能被 callee dereference 的 memory address；普通 register value 本身没有这里所需的 C object address。Compiler 因此生成：

```asm
call_incr:
    subq $16, %rsp          # allocate 16-byte frame area
    movq $15213, 8(%rsp)    # v1 lives at M[%rsp+8]
    ...
```

本段在老师解释这两条 instruction 时结束。当前 frame 快照为：

```text
较高地址
+--------------------------+
| caller return address    |  entry 时由上级 call 留下
+--------------------------+
| v1 = 15213               |  8(%rsp)
+--------------------------+
| unused / padding         |  0(%rsp)
+--------------------------+ <- %rsp after subq $16
较低地址
```

老师下一节会说明为什么保留 unused space、怎样用 `leaq` 形成 `&v1`、`incr` 怎样更新该 slot，以及 frame 如何回收。

## 概念、符号与推导

### Fixed frame 与 dynamic frame

| Frame 情形 | Boundary strategy | 本段证据 |
| --- | --- | --- |
| Compile-time fixed size | `%rsp -= n`，退出前 `%rsp += n` | 老师以 16 bytes 为例 |
| Runtime-variable size | 可能保留 `%rbp` 作为稳定 reference | Variable-size array/buffer 例外 |

### Addressability 决策

```text
local value 只参与 register-computable expression
    -> 可能完全保留在 registers（incr 的 x/y）

local object 的 address 被需要（&v1）
    -> 必须有 memory location
    -> call_incr 在 stack frame 中分配 v1
```

### `incr` 的函数语义

设调用前 $M[p] = x$，参数为 $v$：

$$
M[p]_{\text{after}} = x + v,
\qquad
\operatorname{return} = x
$$

它返回 old value，不是 updated value。

## 关键概念与依赖关系

- Fixed allocation size -> paired `%rsp` subtraction/addition -> `%rbp` 可省略。
- Variable allocation size -> 需要 stable frame reference -> `%rbp` 特殊用途。
- Recursive depth -> outstanding frames -> private state + stack consumption。
- Frame layout 按需 -> no universal prologue template。
- Local value 可 registerize -> `incr` 无 local stack allocation。
- Address-of local -> object 必须在 memory -> `call_incr` 分配 stack slot。

## 教学展开

### 1. 16-byte frame 中只有 8 bytes 保存 `v1`（`00:39:44-00:40:34`）

`call_incr` 的完整 code 为：[课件: 07-machine-procedures.pptx p.34]

```asm
call_incr:
    subq $16, %rsp
    movq $15213, 8(%rsp)
    movl $3000, %esi
    leaq 8(%rsp), %rdi
    call incr
    addq 8(%rsp), %rax
    addq $16, %rsp
    ret
```

老师指出 compiler 经常分配多于显式 local object 大小的 stack space，与 address alignment 等 conventions 有关；当前只需接受 frame 中存在 unused space，不要求掌握其精确 alignment rule。

```text
`subq $16,%rsp` 与 store 后：

较高地址
+--------------------------+
| caller return address    |  16(%rsp)
+--------------------------+
| v1 = 15213               |   8(%rsp)
+--------------------------+
| unused                   |   0(%rsp)
+--------------------------+ <- %rsp
较低地址
```

“分配”仍只是 decrement `%rsp`；不需要向 allocator 请求 heap block。

### 2. `movl $3000,%esi` 为第二个 `long` argument 准备值（`00:40:34-00:42:39`）

第二个 argument `val=3000` 按 ABI 放入 `%rsi`。Generated code 却写 `%esi`：

```asm
movl $3000, %esi
```

老师解释，`3000` 是能放入 32 bits 的正数；写 `%esi` 会把 `%rsi` 的高 32 bits 清零，因此最终完整 `%rsi` 恰好是 64-bit value `3000`。Compiler 偏好这个 encoding，是因为课堂所述情况下 `movl` 比相应 `movq` 少一个 encoded byte。

```text
执行前：%rsi = 任意旧 64-bit pattern
写 %esi：low32 = 3000, high32 = 0
执行后：%rsi = 3000
```

这不是说所有 `long` 常量都可无条件用 32-bit move，尤其不能把此处正数 zero-extension 直接套到任意 negative/large value。

### 3. `leaq 8(%rsp),%rdi` 计算 `&v1`，不读取 `v1`（`00:42:39-00:43:34`）

第一 argument 是 pointer `&v1`，应进入 `%rdi`：

```asm
leaq 8(%rsp), %rdi
```

Address expression `8(%rsp)` 看似 memory operand，但 `leaq` 不 dereference；它把 computed effective address `%rsp+8` 写入 `%rdi`。因此：

```text
%rdi = %rsp + 8 = address of v1
%rsi = 3000      = val
M[%rdi] = 15213  = current *p
```

老师提醒先前见过 `leaq` 被 compiler 用作 arithmetic，而这里正是其原本的 pointer/address-building 用途。

### 4. `incr` 同时更新 stack local，并返回 old value（`00:43:34-00:44:45`）

执行 `call incr` 时，control mechanism 先暂时把 `call_incr` 内的 return address 压到更低地址；进入 `incr` 后，它按上一节代码执行：[课件: 07-machine-procedures.pptx p.33] [课件: 07-machine-procedures.pptx p.35] [课件: 07-machine-procedures.pptx p.36]

```text
输入：p = &v1, val = 3000, v1 = 15213

x = *p           -> x = 15213, %rax = 15213
y = x + val      -> y = 18213
*p = y           -> v1 stack slot becomes 18213
return x         -> %rax = 15213
```

返回 `call_incr` 后同时存在两种结果：

- Memory side effect：`M[8(%rsp)] = v1 = 18213`。
- Register return：`%rax = v2 = 15213`。

这正是 C source 中 `v1` 与 `v2` 的不同含义；不要把 updated memory value 和 returned old value混为一谈。

### 5. 计算 `v1 + v2 = 33426`（`00:44:20-00:44:45`）

Caller 执行：

```asm
addq 8(%rsp), %rax
```

所以：

$$
\%rax = v2 + v1 = 15213 + 18213 = 33426
$$

`%rax` 随即成为 `call_incr` 自己的 return value。课件逐页显示 stack slot 从 `15213` 变为 `18213`，再由 caller 读取。[课件: 07-machine-procedures.pptx p.35] [课件: 07-machine-procedures.pptx p.36]

### 6. Cleanup：先恢复 `%rsp`，才能让 `ret` 读到正确地址（`00:44:45-00:46:10`）

Compiler 知道入口分配了 16 bytes，因此执行：

```asm
addq $16, %rsp
ret
```

状态变化：[课件: 07-machine-procedures.pptx p.37] [课件: 07-machine-procedures.pptx p.38]

```text
cleanup 前                      addq $16,%rsp 后
较高地址                        较高地址
+------------------+            +------------------+
| caller return addr|            | caller return addr| <- %rsp
+------------------+            +------------------+
| v1 = 18213       |            | old v1 bytes，    |
+------------------+            | 已不属 frame      |
| unused           | <- %rsp    +------------------+
+------------------+            较低地址
较低地址
```

`ret` 永远把当前 `%rsp` 所指 value 当成 return address。因此 `addq $16,%rsp` 不是可选的 housekeeping；若漏掉，`ret` 会把 local/unused area 中的 data 当 address，破坏 control flow。

### 7. Thought experiment：caller 的 `%rdx=15213` 被 callee 覆盖（`00:46:10-00:47:47`）

老师把问题推进到 registers。假设 `yoo` 想跨 call 保留 `%rdx`：[课件: 07-machine-procedures.pptx p.39]

```asm
yoo:
    ...
    movq $15213, %rdx
    call who
    addq %rdx, %rax
    ...
    ret

who:
    ...
    subq $18213, %rdx
    ...
    ret
```

`who` 返回时，`%rdx` 已不再可靠地保存 `15213`。仅凭“caller 先写了 register”不能要求任意 callee 保持它；双方需要 ABI coordination。

### 8. Caller 与 callee 的术语（`00:47:47-00:48:10`）

当 `yoo` 调 `who`：

- `yoo` 是 **caller**，发起 call 的 procedure。
- `who` 是 **callee**，被调用的 procedure。

同一 procedure 的角色取决于某条调用边：`who` 对 `yoo` 是 callee；若 `who` 再调 `amI`，它对 `amI` 又是 caller。

### 9. 两类 register-saving contract（`00:48:10-00:49:42`）

老师定义两种责任分配：[课件: 07-machine-procedures.pptx p.40]

**Caller-saved**：若 caller 在 call 后仍需要某个 register 的 old value，caller 必须在 call 前自行保存；它应假定 callee 可以改写该 register。

**Callee-saved**：若 callee 想使用/改写某个此类 register，callee 必须先保存原值，return 前恢复；caller 因而可以相信该 register 跨 call 不变。

```text
caller-saved contract                 callee-saved contract

caller 有 live value                  caller 有 live value
caller save if needed                 call callee
call callee                           callee save before modifying
callee may clobber                    callee use register
caller restore                        callee restore before return
```

本段结束时老师开始列具体 register class；完整表在下一节。

## 概念、符号与推导

### `call_incr` 的完整 state trace

| 阶段 | `%rsp` 相对 frame | `M[8(%rsp)]` | `%rdi` | `%rsi` | `%rax` |
| --- | --- | --- | --- | --- | --- |
| allocate/store | local base | `15213` | 未设置 | 未设置 | 未定 |
| setup | local base | `15213` | `%rsp+8` | `3000` | 未定 |
| `incr` return | local base | `18213` | pointer | 可改写 | `15213` |
| add result | local base | `18213` | 不再需要 | 不再需要 | `33426` |
| cleanup | entry value | slot 已离开 frame | - | - | `33426` |

### Saving convention 的选择问题

两类约定都能保护 live value，差别在责任：

```text
值跨 call 仍 live
├─ register 是 caller-saved -> caller 在需要时 save/restore
└─ register 是 callee-saved -> 修改它的 callee save/restore
```

具体 register 属于哪类由 ABI 规定，不由某次 caller 临时声明。

## 关键概念与依赖关系

- `&v1` -> `leaq` computes address -> pointer in `%rdi`。
- Positive `3000` + 32-bit destination write -> `%rsi` obtains correct 64-bit value。
- `incr` side effect + `%rax` result -> `call_incr` returns `33426`。
- Paired `subq/addq` -> `%rsp` points to caller return address before `ret`。
- Cross-call live register value -> potential clobber -> saving convention。
- Saving responsibility -> caller-saved vs callee-saved -> 第 6 节 register map。

## 常见误解

- **误解：16-byte frame 说明 `v1` 占 16 bytes。** `long v1` 的课堂 slot 是 8 bytes，另 8 bytes 未使用。
- **误解：`leaq 8(%rsp),%rdi` 把 `v1=15213` 读进 `%rdi`。** 它写入的是 address `%rsp+8`，不是该 address 的 contents。

- **误解：Local frame 回收后可以直接 `ret`，无需恢复 `%rsp`。** `ret` 按当前 `%rsp` 取 address；必须先跳过 locals。
- **误解：Caller-saved 意味着 callee 帮 caller 保存。** 恰好相反，值若重要，caller 自己在 call 前保存。

# 第 6 节：寄存器分类、`call_incr2` 与递归 `pcount_r` 的下潜

> 时间范围：`00:49:42-00:59:41`

## 教学展开

### 1. Caller-saved：return、argument 和 temporary registers 都可被 callee 改写（`00:49:42-00:50:19`）

课件将下列 registers 列为 caller-saved：[课件: 07-machine-procedures.pptx p.41]

| Register | ABI 角色 | 跨 call 假设 |
| --- | --- | --- |
| `%rax` | return value | callee 可改写 |
| `%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9` | arguments 1-6 | callee 可改写 |
| `%r10`, `%r11` | temporaries | callee 可改写 |

这解释了前面 code 为什么经常覆盖 argument registers：callee 收到值后可以把这些 registers 当 temporary storage；`%rax` 也可在 procedure 内多次变化，只需 return 时放入最终 result。若 caller 在 call 后仍依赖其中某个 old value，它必须先另行保存。

### 2. Callee-saved 与 special `%rsp`（`00:50:19-00:51:12`）

课件列出的 callee-saved registers 是 `%rbx`、`%r12`、`%r13`、`%r14` 和 `%rbp`：[课件: 07-machine-procedures.pptx p.42]

- Callee 若不修改它们，无需做任何事。
- Callee 若要修改，必须保存 entry value，并在 return 前恢复。
- `%rbp` 可兼作 frame pointer；不作 frame pointer 时仍按 callee-saved register 对待。

`%rsp` 是 special form of callee save：procedure body 可以通过 push/pop、sub/add 改变它，但退出时必须恢复为使 caller control state 正确的值。老师的简化提醒是不要随意改 `%rsp`，除非明确知道 frame 与 return-address layout。

```text
caller-saved:
%rax %rdi %rsi %rdx %rcx %r8 %r9 %r10 %r11

callee-saved:
%rbx %rbp %r12 %r13 %r14

special restored stack state:
%rsp
```

### 3. `call_incr2` 的新问题：入口 `x` 必须跨 call 存活（`00:51:12-00:52:13`）

课堂将之前的无参数 caller 改为：[课件: 07-machine-procedures.pptx p.43]

```c
long call_incr2(long x) {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return x + v2;
}
```

入口时 `x` 在 `%rdi`。但调用 `incr(&v1,3000)` 前，ABI 又要求第一 argument `&v1` 进入 `%rdi`，因此原 `x` 会被覆盖；而 `incr` 返回后仍要计算 `x+v2`。这正是 **value live across a call** 的场景。

Compiler 选择 `%rbx` 保存 `x`。因为 `%rbx` 是 callee-saved，任何更深的 well-behaved callee 都会在返回时保持本层看到的 `%rbx` value。

### 4. `push %rbx`、使用 `%rbx`、`pop %rbx`（`00:52:13-00:53:58`）

完整 code：[课件: 07-machine-procedures.pptx p.43] [课件: 07-machine-procedures.pptx p.44]

```asm
call_incr2:
    pushq %rbx
    subq  $16, %rsp
    movq  %rdi, %rbx
    movq  $15213, 8(%rsp)
    movl  $3000, %esi
    leaq  8(%rsp), %rdi
    call  incr
    addq  %rbx, %rax
    addq  $16, %rsp
    popq  %rbx
    ret
```

进入时先 `pushq %rbx`，保存 caller 所拥有的 old `%rbx`；再分配 16-byte locals。然后 `%rbx = x`，可安全跨越 `call incr`。返回后 `%rax=v2`，执行 `addq %rbx,%rax` 得到 `x+v2`。

Stack layout：

```text
较高地址
+---------------------------+
| caller return address     |
+---------------------------+
| saved old %rbx            |  pushq %rbx
+---------------------------+
| v1 = 15213 / later 18213  |  8(%rsp)
+---------------------------+
| unused                    |  0(%rsp)
+---------------------------+ <- %rsp in body
较低地址
```

Exit 必须逆序撤销 setup：先 `addq $16,%rsp` 回收后分配的 local area，再 `popq %rbx` 恢复先前保存的 register，最后 `ret`。这就是 LIFO discipline 在 prologue/epilogue 中的直接表现。

### 5. “Only what is needed” 再次出现（`00:53:42-00:54:21`）

`call_incr2` 之所以出现 `%rbx` save/restore，是因为它确实要跨 call 保存 `x`，且会改写 `%rbx`。先前函数没有这一需要，所以没有同样 sequence。ABI 并不要求所有 callee 无条件 push 每个 callee-saved register；只要求 **凡是实际改写的 callee-saved register 都恢复**。

### 6. Recursive popcount 的定义与 unsigned 前提（`00:54:21-00:56:21`）

老师将所有机制组合到 recursive population count：[课件: 07-machine-procedures.pptx p.46]

```c
long pcount_r(unsigned long x) {
    if (x == 0)
        return 0;
    else
        return (x & 1) + pcount_r(x >> 1);
}
```

Recurrence 为：

$$
P(0)=0,
\qquad
P(x)=(x\mathbin{\&}1)+P(x\gg1),\quad x\ne0
$$

每层取当前 least-significant bit，再对其余 bits 递归计数。`x` 是 `unsigned long`，所以 `x >> 1` 是 logical right shift，最终趋向 0；老师明确说若使用会复制 sign bit 的 arithmetic right shift，这种递归对 negative signed values 会很糟糕。

老师也指出 recursive version 通常比 iterative version 生成更多 code/stack work；这是低层调用机制的开销观察，不是说 recursion 需要另一套 compiler rule。

### 7. Base case：先假设 result 为 0，再测试 `x`（`00:56:21-00:57:19`）

Generated code 的开头：[课件: 07-machine-procedures.pptx p.47]

```asm
pcount_r:
    movl  $0, %eax
    testq %rdi, %rdi
    je    .L6
    ...
.L6:
    rep; ret
```

入口 `x` 在 `%rdi`。`movl $0,%eax` 先设置 potential return value 0；`testq %rdi,%rdi` 测试 `x` 是否为 zero。若 equal/zero flag 成立，`je .L6` 直接跳到 return。`je` 在此与 `jz` 表达同一条件。

Base case 不需要 push `%rbx`，因为 branch 在任何 save 之前就返回；再次体现 only mechanisms required。

### 8. Recursive case：保存 `%rbx` 并保留本层 bit（`00:57:19-00:58:47`）

当 `x!=0`：[课件: 07-machine-procedures.pptx p.48] [课件: 07-machine-procedures.pptx p.49]

```asm
pushq %rbx
movq  %rdi, %rbx
andl  $1, %ebx
shrq  %rdi
```

步骤如下：

1. `pushq %rbx` 保存 caller 的 old `%rbx`。
2. Copy current `x` from `%rdi` to `%rbx`。
3. `andl $1,%ebx` 只保留 least-significant bit；写 `%ebx` 同时清零 `%rbx` 高 32 bits，所以 `%rbx` 最终严格为 0 或 1。
4. `shrq %rdi` 将 argument 改为 `x>>1`，为 recursive call 准备第一参数。

本层不能把 `x&1` 留在 caller-saved argument register，因为 recursive call 会再次使用并改写它；放入 callee-saved `%rbx` 后，内层 invocation 有义务在返回时恢复本层看到的 `%rbx`。

### 9. Recursive `call pcount_r`：相同 code，新 invocation/new frame（`00:58:47-00:59:41`）

执行：[课件: 07-machine-procedures.pptx p.50]

```asm
call pcount_r
```

新的 invocation 获得 `%rdi=x>>1`，并由 `call` push 新 return address。它若非 base case，也会 push 自己进入时看到的 `%rbx`，再将 `%rbx` 改为自己的 bit。于是每层 stack 保存上一层需要恢复的 value：

```text
以 x = 5 (binary 101) 为状态示意：

调用 pcount_r(5)：本层 bit 1 保存在 %rbx，call pcount_r(2)
  调用 pcount_r(2)：先 push 外层 bit 1；本层 bit 0 放 %rbx，call pcount_r(1)
    调用 pcount_r(1)：先 push 中层 bit 0；本层 bit 1 放 %rbx，call pcount_r(0)
      调用 pcount_r(0)：%rax = 0，直接 return
```

`x=5` 只是对课堂 recurrence 与汇编的手执行示意，并非老师口述的具体输入。可确认的机制是：inner call return 后，recursive result 在 `%rax`，而 callee-saved contract 保证本层 bit 仍在 `%rbx`。第 7 节从这个状态继续。

## 概念、符号与推导

### Register-saving map

```text
callee may clobber:
  %rax, %rdi, %rsi, %rdx, %rcx, %r8, %r9, %r10, %r11

callee must preserve if used:
  %rbx, %rbp, %r12, %r13, %r14

must restore stack state on exit:
  %rsp
```

### `call_incr2` 的双重保存

`%rbx` 在本层有两个不同时间尺度的 value：

```text
entry old %rbx -> push 到 stack，供本层最终 return 前恢复
x              -> 放入当前 %rbx，供 incr return 后继续计算
```

更深 callee 也遵守同一 contract，所以本层 `%rbx=x` 能跨 `call incr` 保持。

### `pcount_r` 的 per-level state

每个 non-base invocation 需要保存：

- Return address：由 recursive `call` 保存。
- Caller 的 `%rbx`：由本层 `pushq %rbx` 保存。
- 本层 `x&1`：保存在当前 `%rbx`。
- Recursive argument `x>>1`：放入 `%rdi`。

## 关键概念与依赖关系

- Argument/return registers -> caller-saved -> callee 可直接复用。
- `%rbx` callee-saved -> live-across-call value 可安全存放。
- Save before modify + restore before return -> independently compiled code cooperation。
- Prologue order -> epilogue reverse order -> LIFO。
- `pcount_r` recurrence -> base case + per-level bit + smaller recursive argument。
- Per-level `%rbx`/return address -> ordinary frames support recursion。

- **`call_incr2` 比 `call_incr` 多一个 parameter**（`00:51:31-00:52:13`）：专门制造跨 call live value，说明 `%rbx` 的用途。[课件: 07-machine-procedures.pptx p.43]
- **Push/pop 与 sub/add 的 reverse order**（`00:53:19-00:53:38`）：是 stack discipline，不是审美上的对称。
- **Base case 不 push `%rbx`**：路径直接返回，因此无需执行 recursive path 的 save work。[课件: 07-machine-procedures.pptx p.47]
- **Unsigned right shift**（`00:55:47-00:56:00`）：保证每次 shift toward zero；不能忽略 type premise。
- **Recursive code 比 iterative code 更大**（`00:56:00-00:56:15`）：来自 call/frame/save overhead，是课堂的总体观察，未做性能 benchmark。

## 常见误解

- **误解：Argument registers 因为有 ABI 角色，所以 callee 必须保持它们。** 它们是 caller-saved，callee 可以改写。
- **误解：Callee-saved `%rbx` 可以直接使用，无需任何 setup。** 当前 function 若改写它，必须先保存 caller 的 value 并在退出前恢复。
- **误解：`call_incr2` 把 `x` 留在 `%rdi` 也没问题。** `%rdi` 必须改成 `&v1`，且 `incr` 可继续改写它。
- **误解：Epilogue 可按与 prologue 相同的顺序执行。** 后分配的 local area 必须先回收，才能 pop 先保存的 `%rbx`。
- **误解：`pcount_r` 对 signed negative input 也会按同样 recurrence 到 0。** 课堂明确限定 `unsigned long` 和 logical right shift。
- **误解：每层 `%rbx` 都共享同一个 bit。** 每个 invocation 先将 caller `%rbx` 压入自己的 stack state，再使用当前 `%rbx` 保存本层 bit。

## 教学展开

### 1. Recursive result 与本层 bit 相加（`00:59:41-01:00:00`）

Recursive `call pcount_r` 返回后，well-behaved convention 提供两个值：[课件: 07-machine-procedures.pptx p.51]

- `%rax = pcount_r(x >> 1)`，即 inner recursive result。
- `%rbx = x & 1`，即当前 invocation 在 call 前保存的 bit。

因此：

```asm
addq %rbx, %rax
```

实现：

$$
\%rax \leftarrow P(x\gg1)+(x\mathbin{\&}1)=P(x)
$$

Transcript 在此一句第二次也说 `%rbx`，但从 instruction、前后文和课件可确认 recursive result 在 `%rax`，见待核对项。

### 2. `popq %rbx; ret`：先履行保存 contract，再恢复 caller control（`01:00:00-01:00:32`）

当前 invocation 已经不再需要自己的 bit，但它进入时曾 push caller 的 `%rbx`。Exit code：[课件: 07-machine-procedures.pptx p.52]

```asm
popq %rbx
rep; ret
```

`popq` 恢复 caller 在 call 前看到的 `%rbx`，同时使 `%rsp` 上移到当前 invocation 的 return address；`ret` 再 pop 该 address，回到上一层 `addq` 后的位置。两次 stack objects 的顺序是：

```text
当前层 body 期间
较高地址
+---------------------------+
| return address to caller  |
+---------------------------+
| saved caller %rbx         | <- %rsp
+---------------------------+
较低地址

pop %rbx 后：%rsp -> return address
ret 后     ：%rsp -> caller 的 frame top，%rip -> caller continuation
```

这说明 `%rbx` 的 callee-saved property 不是“寄存器神奇地不变”，而是每个会改写它的 invocation 都显式 save/restore。

### 3. 逐层 unwind 得到总 bit count（`00:59:41-01:00:32`，基于课堂 code 的手执行）

用第 6 节的示意输入 `x=5 (101₂)` 可检查整个回溯；这仍是对课堂 code 的推演，不是老师口述的新例子：

```text
pcount_r(0) = 0

pcount_r(1): bit=1, inner=0 -> %rax=1，restore caller %rbx，return
pcount_r(2): bit=0, inner=1 -> %rax=1，restore caller %rbx，return
pcount_r(5): bit=1, inner=1 -> %rax=2，restore caller %rbx，return
```

每层拥有 private saved `%rbx` 和 return address，所以内层可执行相同 code，而不会抹掉外层尚未使用的 bit。

### 4. `%rbp`：frame pointer 的可靠性来自 callee-saved rule（`01:00:32-01:02:13`）

老师回到第 4 节的 special case。若 function 因 compile-time unknown allocation 等原因将 `%rbp` 指向 frame 的稳定起点，它可能继续调用许多 procedures，甚至进入深层 recursion。外层希望这些 calls 返回后 `%rbp` 仍指向自己的 frame。

这正由 callee-saved contract 保证：[课件: 07-machine-procedures.pptx p.42]

```text
outer function:
    %rbp = stable pointer into outer frame
    call inner

inner 若使用 %rbp：
    save outer %rbp
    use/modify %rbp
    restore outer %rbp
    ret

outer resumes:
    %rbp still points to outer frame
```

所以“`%rbp` 可作 frame pointer”与“`%rbp` 是 callee-saved”不是两个偶然并列的事实；后者使前者能够跨任意 compliant calls 保持可靠。

### 5. ABI 让 compiler、OS 与 debugger 共用同一套 machine contract（`01:01:52-01:02:42`）

只要所有 code 遵守 argument locations、return register、register saving、stack/return conventions，各层就能互相信任 state。老师说明新 processor 生命周期早期需要仔细制定 ABI，参与者包括 compiler writers、operating-system implementers，以及 GDB 等 debugging tools 的实现者。

共同标准不仅让一个 compiler 调自己的 code，也让 independently generated modules 和 tools 能解释 call boundaries、register meaning 与 stack state。

### 6. 最有效的掌握方法：hand-execute 或 debugger single-step（`01:02:42-01:03:21`）

老师说这些 pieces 可以讲很久，但真正建立直觉的方式是：

1. 选很小的 procedure example。
2. 手工记录每条 instruction 后的 `%rsp`、registers 和 relevant memory。
3. 或在 debugger 中逐条运行，核对预测。
4. 确认 call、return、save、restore 和 local-state lifetime 如何拼合。

这也是 Bomb Lab 的直接学习方法。只背 register 表而不能预测 state change，不算真正掌握 calling convention。

### 7. Private frames 使每层 recursion 的 state 共存（`01:03:21-01:04:00`）

Deep recursion 中，当前只执行最内层 invocation，但所有 outstanding outer calls 的 state 仍保存在各自 frames：saved registers、locals 和 saved return pointer。[课件: 07-machine-procedures.pptx p.53]

```text
同一 function code
        │
        ├─ invocation #1 -> frame #1：private state
        ├─ invocation #2 -> frame #2：private state
        └─ invocation #3 -> frame #3：private state
```

Register-saving convention 则阻止一个 compliant call 意外破坏另一个 call 的 live data。课件限定了边界：若 C code 本身显式越界写等，仍可能破坏别的 frame；这种 buffer overflow 留到 Lecture 9。[课件: 07-machine-procedures.pptx p.53]

### 8. Stack discipline 与语言生命周期必须匹配（`01:04:00-01:05:29`）

若 `P` calls `Q`，正常 C procedure semantics 要求 `Q` 先 return，`P` 才继续并最终 return。因此 `Q` 的 state 在恢复 `P` 时已经可以回收，符合 LIFO。[课件: 07-machine-procedures.pptx p.53]

老师提到某些更复杂语言场景不能假设 frame state 在 function return 后立即失效，可能需要其他 allocation mechanism，例如把相关 activation state 放到 heap。此处只是边界提醒，没有定义 closure、continuation 或具体语言 runtime，不能据此扩展。

对 C 和老师所称的 commonplace languages，这种 call/return lifetime 与 stack 正好匹配；C 的设计者明确利用了这一点。

### 9. Mutual recursion 不需要新机制（`01:05:29-01:05:57`）

除 direct recursion `P -> P` 外，还可以有 mutual recursion：

```text
P calls Q
Q calls P
P calls Q
...
```

每条 call edge 都按相同 ABI：push return address，按约定传 data，按需建立 frame/save registers。Stack 只关心动态调用顺序，不要求 callee 的 symbol name 与 caller 不同，因此 mutual recursion 与普通 nested calls 使用同一机制。[课件: 07-machine-procedures.pptx p.53]

### 10. 全讲总结：procedure 的中心是 stack discipline 与共同约定（`01:05:57-01:06:33`）

最后一页总结：[课件: 07-machine-procedures.pptx p.54]

- Stack 与 call/return 的 LIFO 顺序匹配。
- Direct recursion 和 mutual recursion 都由 normal calling conventions 支持。
- Local stack frame 与 callee-saved registers 可安全保存跨调用所需值。
- First six integer/pointer arguments 主要放 registers；arguments 7+ 位于 caller-provided stack area。
- Result 在 `%rax` 返回。
- Pointer 是 value 的 address；课堂示例指向 stack local，也可指向 global object。

老师最后再次连接 Bomb Lab：通过 lab 检查 stack contents、单步 procedure，会让这些规则从表格变成可操作的 execution model。

## 概念、符号与推导

### `pcount_r` 的 unwind invariant

对任一 non-base invocation，在 recursive call 返回时：

$$
\%rax=P(x\gg1),\qquad \%rbx=x\mathbin{\&}1
$$

执行 `addq %rbx,%rax` 后：

$$
\%rax=P(x)
$$

随后恢复 `%rbx` 只改变 caller-visible register state，不改变已经算好的 `%rax` result。

### Frame pointer 可靠性的 contract chain

```text
outer uses %rbp as frame pointer
    -> inner calls may execute
    -> every inner modifier of %rbp saves/restores it
    -> outer resumes with same %rbp
    -> outer frame references remain valid
```

### Recursion 的普通调用归纳

Base case 使用普通 return。假设深一层 invocation 遵守 ABI 并返回正确 result，则当前层可从 `%rax` 取 result、从 preserved `%rbx` 取 private bit、恢复 caller state 并普通 return。因此每层只需同一 calling convention；不需要 recursion-specific instruction。

## 关键概念与依赖关系

- Recursive result `%rax` + per-level bit `%rbx` -> current result。
- `pop %rbx` -> caller register state restored；`ret` -> caller control restored。
- `%rbp` callee-saved -> stable frame pointer across nested calls。
- Private frame + register-saving contract -> calls 不意外互相破坏 state。
- Call/return LIFO -> stack allocation/deallocation。
- Same normal mechanism -> direct recursion + mutual recursion。
- Hand trace/debugger -> 验证整套 execution model。

## 常见误解

- **误解：Recursive call 返回时 result 也在 `%rbx`。** Result 在 `%rax`，当前层 bit 在 `%rbx`。
- **误解：`pop %rbx` 会丢掉刚算出的 result。** Result 已在 `%rax`；pop 只履行 `%rbx` 的 callee-saved contract。
- **误解：`%rbp` 之所以稳定，是因为 inner functions 不能使用它。** Inner function 可以使用，但若改写必须保存并恢复。
- **误解：Private frames 能阻止所有 memory corruption。** ABI 防止 compliant use 的意外 clobber；错误 pointer/overflow 仍可跨 frame 写坏数据。
- **误解：Mutual recursion 需要 compiler 生成特殊 call instruction。** 动态 call stack 对 function names 无特殊要求，普通 convention 足够。
- **误解：Stack 适合所有语言中的所有 activation lifetimes。** 老师明确指出若 state 必须在 return 后存活，就需其他机制。
