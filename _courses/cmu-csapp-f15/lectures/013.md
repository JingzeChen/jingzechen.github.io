### 需要的先修知识

1. **C compilation basics：** 知道 source、preprocessor directive、assembly、object file 与 executable 是不同阶段的制品；能阅读简单 function declaration/definition 与 global variable。
2. **Machine code 与 calling convention：** 能读本讲给出的 x86-64 `mov`、`callq` 反汇编，知道 `%edi` 在示例中承载第一个 argument、`%rip` 指向 next instruction。
3. **Memory layout：** 理解 code、global data、stack、heap 的基本区别，知道 ordinary local variables 通常由 compiler 放在 stack。
4. **Addresses 与 hexadecimal：** 会做小规模 hexadecimal addition，能区分 absolute address、module-relative offset 与 PC-relative displacement。
5. **C function pointers：** 能读 `void (*addvec)(int *,int *,int *,int)`，理解变量可保存 function address 并被调用。
6. **Shell/GCC command line：** 能区分 input-file order 与 options，能识别 `-L.`, `-lmine`, `-I.`, `-Wl,...`, `-shared` 等本讲命令中的角色；不要求预先知道它们的实现。

### 老师的教学主线

本讲严格沿“构建一个简单程序 -> 打开 object file -> 解决名称 -> 修补地址 -> 打包库 -> 延迟链接 -> 截获库调用”推进：

1. **两个 C modules -> separate compilation：** `main.c/sum.c` 分别形成 `.o`，再由 linker 合成 executable；先说明为何需要这种分工 [00:00:58–00:05:15]。
2. **Separate objects -> linker 两项任务：** 跨 module name 必须绑定 definition，合并后的新位置必须回写到 every reference [00:05:15–00:09:15]。
3. **任务 -> ELF 数据结构：** `.symtab` 保存“符号是谁”，relocation sections 保存“哪里以后要改”，各 code/data sections 保存待合并内容 [00:09:15–00:15:06]。
4. **符号表 -> scope 与 duplicate definitions：** 先分 global/external/local，再分 strong/weak；用 puzzles 展示“能链接”与“语义正确”不是一回事 [00:15:08–00:32:42]。
5. **已选 definition -> concrete relocation：** 合并 `.text/.data`，由 `array` absolute reference 推到 `sum` PC-relative call，并用 `objdump` 的前后结果核验 [00:32:42–00:44:05]。
6. **Fully linked file -> process image：** Sections 可映射到 read-only/read-write segments，继而定位 heap、shared libraries 与 stack [00:44:05–00:48:13]。
7. **可执行程序 -> reusable libraries：** 两个朴素 packaging 方案都不理想，于是引入带 index 的 `.a`，只抽取解决当前 unresolved references 的 members [00:48:13–00:59:53]。
8. **Static duplication -> shared/dynamic linking：** 不在 build 时复制 routines，而把部分 resolution/relocation 推迟到 load time；甚至由 running program 主动 `dlopen/dlsym` [00:59:53–01:11:06]。
9. **可改写的 resolution time -> interpositioning：** 分别在 preprocessing、static linking、dynamic loading 阶段让 apparent call 先命中 wrapper，再回到 real function [01:11:06–01:21:22.70]。

### 核心概念与依赖关系

```text
C source modules
  |
  v
cpp -> cc1 -> as
  |
  v
relocatable ELF .o
  |-- sections: .text/.rodata/.data/.bss
  |-- .symtab: definitions and references
  `-- .rel.text/.rel.data: later fix-ups
  |
  v
symbol resolution
  |-- global / external / local
  `-- strong / weak duplicate rules
  |
  v
relocation
  |-- merge like sections
  |-- choose final symbol locations
  `-- patch absolute and PC-relative references
  |
  +------------------------+
  |                        |
  v                        v
static executable          partially linked executable
via .a archives            + needed .so information
  |                        |
  v                        v
direct loading             loader -> dynamic linker
                           |
                           +-- load-time linking
                           `-- run-time dlopen/dlsym
                                      |
                                      v
                           library interpositioning
                           compile / link / load-run
```

依赖顺序不能倒置：不知道 symbols/relocation entries 就无法解释 archive 为何只抽取某些 members；不知道 load-time symbol lookup 就无法解释 `LD_PRELOAD`；不知道 wrapper 如何找到 real function，就无法说明 `RTLD_NEXT` 为什么避免递归。

### 关键推导、例子与结论边界

1. **构建流水线：**

   ```text
   main.c -> cpp -> cc1 -> as -> main.o
   sum.c  -> cpp -> cc1 -> as -> sum.o
   main.o + sum.o -> ld -> prog
   ```

   GCC 是 driver，`ld` 才是图中的 linker；`.o` 是 relocatable，不是可直接运行的 executable [00:01:49–00:03:34] [课件: 13-linking.pptx p.4]。

2. **Symbol resolution invariant：** every symbol reference 必须关联 exactly one definition [00:06:40–00:06:56] [课件: 13-linking.pptx p.7]。Duplicate definitions 的课堂规则是：

   ```text
   strong + strong               -> linker error
   one strong + one/more weak    -> choose strong
   weak + weak                   -> choose one arbitrarily
   ```

   Functions 和 initialized globals 是 strong，uninitialized globals 是 weak；老师给出 `-fno-common` 让多个 weak definitions 变成 error [00:21:30–00:23:33] [课件: 13-linking.pptx p.16] [课件: 13-linking.pptx p.17]。

3. **课堂纠错必须保留：** `p2` 根据 `double x` 发出 8-byte write；linker 选择 `p1` 的 4-byte strong `int x=7` location，所以越界覆盖 `y` [00:30:37–00:31:09] [课件: 13-linking.pptx p.18]。00:25:25–00:30:37 的中间说法有自我否定，不能替代最终版本。

4. **Absolute relocation：** `main.o` 中 `%edi` immediate 暂填 `00 00 00 00`；entry `a: R_X86_64_32 array` 要求 linker 从 `.text+0xa` 起写入 `array` 最终 address，linked result 为 `0x601018` [00:36:31–00:42:09] [课件: 13-linking.pptx p.21] [课件: 13-linking.pptx p.22]。

5. **PC-relative relocation：** `f: R_X86_64_PC32 sum-0x4` 描述 `callq` 的 4-byte field；linked displacement 为 `0x5`，运行时使用 next-instruction `%rip`：

   ```text
   0x4004e8 = 0x4004e3 + 0x5
   sum address = next-instruction address + signed displacement
   ```

   [00:39:44–00:43:36] [课件: 13-linking.pptx p.21] [课件: 13-linking.pptx p.22]。老师没有在课堂给一般化 relocation 代数公式，因此不外加未讲的符号通式。

6. **ELF 与 loading 边界：** `.bss` 中 uninitialized globals 不为初值占 object-file data space，但 load 时仍需 memory [00:12:38–00:13:25] [课件: 13-linking.pptx p.11]。p.23 将 `.data/.bss` 同画入 read/write segment；不能把“`.bss` 不占文件初值空间”误读为“运行时不占内存”。

7. **Address-space 图是课堂简化：** 图从 `0x400000` 附近的 code/data 到 upward heap/`brk`、shared-library mapped region、downward stack/`%rsp` 与 kernel-only memory [00:45:23–00:47:33] [课件: 13-linking.pptx p.23]。老师主动说实际 large-object allocations 更复杂，且对原因只提出猜测 [00:47:33–00:48:05]。

8. **Archive member selection：** 对 `libmine.a` 的课堂算法，unresolved set 的演化是：

   ```text
   libtest.o -> -lmine:  {} -> {libfun} -> {}       success
   -lmine -> libtest.o:  {} -> {} -> {libfun}       error at end
   ```

   [00:55:59–00:59:50] [课件: 13-linking.pptx p.30]。结论是 library 放在依赖它的 objects 之后；不把该单向 archive scan 无条件外推到所有 linker inputs。

9. **Load-time dynamic linking：** Static linker 只记录 needed `.so` 与 relocation/symbol information，形成 partially linked executable；loader `execve` 装入 executable/`.so` 并调用 `ld-linux.so` 完成 fix-ups，最后得到 fully linked program in memory [01:03:44–01:06:01] [课件: 13-linking.pptx p.33]。

10. **Run-time API：**

    ```text
    handle = dlopen("./libvector.so", RTLD_LAZY)
    addvec = dlsym(handle, "addvec")
    addvec(x, y, z, 2)
    dlclose(handle)
    ```

    [01:07:11–01:09:59] [课件: 13-linking.pptx p.34] [课件: 13-linking.pptx p.35]。每步包含 return/error check；function-name string 不是 function 本身。

11. **Interpositioning 的三条 mapping：**

    ```text
    compile time: malloc/free --macros--> mymalloc/myfree
    link time:    malloc -> __wrap_malloc
                  __real_malloc -> malloc
    load/run:     LD_PRELOAD makes wrapper malloc win first
                  wrapper -> dlsym(RTLD_NEXT,"malloc") -> libc malloc
    ```

    [01:14:13–01:21:05] [课件: 13-linking.pptx p.43] [课件: 13-linking.pptx p.45] [课件: 13-linking.pptx p.46] [课件: 13-linking.pptx p.48] [课件: 13-linking.pptx p.49]。

12. **Transcript-end boundary：** Metadata duration 是 4893.0 秒，但 supplied transcript exact end 是 4882.70 秒。最后 record id 801 从 4874.96 到 4882.70，完整包含 “see you on Thursday” 与 cache labs 提醒；笔记不补造 metadata 末尾额外 10.30 秒。

### 易错点与待复核

1. 把 GCC driver 当成 linker，或把 `.o` 当成可直接运行的 executable。
2. 把 symbol resolution（选 definition）与 relocation（定位置、修 reference）混成一步。
3. 把 local linker symbol 等同于 stack local variable；带 `static` 的 module/function-scope objects 才可能形成 local linker symbols，普通 locals 由 compiler 管理。
4. 认为 `.bss` “不占文件数据空间”就“不占运行内存”。
5. 认为 linker 会按 C types 检查同名 definitions；课堂 puzzle 正说明 compiler access width 与 linker 选中的 object size 可以不一致。
6. 采用老师在 00:28:36 的暂时改口，而遗漏 00:30:37–00:31:09 的最终纠正。
7. 把 `sum` call field 中的 `0x5` 当 absolute address，或用 call opcode address `0x4004de` 而非 next instruction `0x4004e3` 作 PC-relative 基准。
8. 把课堂 address-space diagram 当成所有 Linux binaries/allocators 的完整固定布局；老师明确称其为 simplification。
9. 认为把 `.a` 放上 command line 就一定会抽取后面才需要的 member；课堂算法按当前 unresolved list 决定。
10. 混淆 `-L.`（library search path）、`-lmine`（library shorthand）与 `-I.`（include search path）。
11. 把 `#include` 当作 linking；它在 preprocessor 阶段已展开，到 linker 时早已消失 [01:06:25–01:07:06]。
12. 认为 shared library 不需要 linking；它只是把一部分 resolution/relocation 延迟到 load/run time。
13. 混淆 loader 与 dynamic linker，或混淆 disk 上 partially linked executable 与 memory 中 fully linked program。
14. Compile-time interposition 不改 `int.c` 文本，但需要通过替代 header 重新 preprocess/compile；link-time 方法操作 object symbols；load/run-time 方法只要求 executable。
15. 只记 `LD_PRELOAD` 而忘记 `RTLD_NEXT`：前者负责让 call 先进 wrapper，后者负责让 wrapper 找到真实同名 function、防止递归。
16. 所有无法由课件消歧的 ASR 片段均在各段“待核对项”中用 `[需回听 HH:MM:SS]` 标记；重点回听 00:25:40–00:31:14、00:42:55、01:06:11、01:10:22、01:16:20、01:19:55。

# 第 1 段：从独立编译到链接器的两项任务

**时间范围：** 00:00:00–00:09:52  
**对应课件：** [课件: 13-linking.pptx p.1]–[课件: 13-linking.pptx p.9]

## 本段在整讲中的作用

老师用本段完成课程视角的第一次转换：从“程序如何与硬件交互”转向“程序如何与系统软件交互”，并把 linking 定义为系统构建程序的过程 [00:00:05–00:00:30]。整讲随后要回答两个问题：链接器怎样把多个模块组合成程序，以及这种机制怎样支持 library interpositioning，从而截获标准 C 库等库中的函数调用 [00:00:36–00:00:51] [课件: 13-linking.pptx p.2]。

本段先用 `main.c + sum.c` 建立贯穿全讲的运行示例，再从独立编译的动机推到链接器的两项核心工作：symbol resolution 与 relocation。结尾只开始定义 object file 的种类，为下一段的 ELF 结构与符号分类准备术语。

## 教学展开

### 1. 宣布主题与最终应用 [00:00:00–00:00:58]

1. 老师说明课程开始研究 system software，而 linking 是系统构建程序的过程 [00:00:05–00:00:30]。
2. 主体先讲 linking，末尾再讲 library interpositioning；后者能截获库函数调用，且能力来自链接机制 [00:00:36–00:00:51] [课件: 13-linking.pptx p.1] [课件: 13-linking.pptx p.2]。

### 2. 用两个 C 模块建立例子 [00:00:58–00:01:49]

- `main.c` 声明 `sum`，定义全局数组 `int array[2] = {1, 2};`，调用 `sum(array, 2)`，再把结果作为 `main` 的返回值 [00:00:58–00:01:34] [课件: 13-linking.pptx p.3]。
- `sum.c` 中的 `sum(int *a, int n)` 顺序累加数组的 `n` 个元素并返回总和 [00:01:09–00:01:18] [课件: 13-linking.pptx p.3]。
- 老师指出，把和作为退出状态返回并不是自然的程序设计；这里只是为了避免编译器把示例代码优化掉 [00:01:38–00:01:42]。

### 3. 沿 GCC 驱动展示静态链接流水线 [00:01:49–00:03:34]

对每个 `.c` 模块，GCC 驱动依次调用：

```text
main.c -> cpp -> cc1 -> as -> main.o
sum.c  -> cpp -> cc1 -> as -> sum.o
main.o + sum.o -> ld -> prog
```

- `cpp` 是 C 预处理器，`cc1` 是实际编译器；编译器产生汇编，再由 `as` 汇编器产生 `.o` 文件 [00:02:09–00:02:36]。
- 两个源文件分别生成 `main.o`、`sum.o`，所以这是 separately compiled [00:02:36–00:03:22]。
- 链接器 `ld` 把两个 relocatable object files 合成一个可加载、可运行的 fully linked executable object file [00:02:47–00:03:28] [课件: 13-linking.pptx p.4]。
- 课件给出的驱动命令是 `gcc -Og -o prog main.c sum.c`，随后可执行 `./prog` [课件: 13-linking.pptx p.4]。

### 4. 回答“为什么要独立编译” [00:03:34–00:05:15]

老师先反问为什么不把全部代码写在一个大文件中，然后给出两类理由：

1. **模块性。** 相关函数可放入不同源文件，也可构造常用函数库；程序不必成为单体代码块 [00:03:38–00:04:09] [课件: 13-linking.pptx p.5]。
2. **时间效率。** 修改一个模块时，只重新编译该模块，再重新链接；其他模块不必重编译 [00:04:12–00:04:39] [课件: 13-linking.pptx p.6]。
3. **空间效率。** 库可以聚合大量函数，但最终程序只需要链接自己实际调用的那一小部分 [00:04:41–00:05:07] [课件: 13-linking.pptx p.6]。

### 5. 推出链接器的第一项工作：符号解析 [00:05:15–00:07:24]

- 在链接器语境中，程序定义并引用的全局变量和函数是 symbols [00:05:23–00:05:39]。
- `void swap() { ... }` 定义符号 `swap`；调用 `swap()` 引用该符号；`int *xp = &x;` 同时定义 `xp` 并引用 `x` [00:05:45–00:06:11] [课件: 13-linking.pptx p.7]。
- 汇编器把符号定义写入 object file 的 symbol table。老师把它描述为结构体数组，每项保存名称、大小、位置等信息 [00:06:18–00:06:35] [课件: 13-linking.pptx p.7]。
- **Symbol resolution 的目标：** 把每个 symbol reference 恰好关联到一个 symbol definition [00:06:40–00:06:56]。之所以需要“解析”，是因为多个模块可能出现同名全局符号，链接器必须决定后续引用对应哪个定义 [00:06:58–00:07:11]。

### 6. 推出第二项工作：重定位 [00:07:24–00:09:15]

符号引用获得唯一的定义后，链接器才进入 relocation：

1. 把多个模块的代码和数据合成一个可直接加载执行的 executable object module [00:07:24–00:07:39] [课件: 13-linking.pptx p.8]。
2. 每个函数或变量在 `.o` 中最初只有相对于本模块的偏移，因为编译时还不知道最终装入位置 [00:07:44–00:08:23]。
3. 链接器决定每个 symbol 在最终可执行文件、也即程序执行时所对应的最终内存位置 [00:08:26–00:08:39]。
4. 链接器把所有相关引用更新为与新位置一致的值 [00:08:45–00:09:01]。

老师把这一步压缩成两句话：“对每个定义，决定它放在哪里；对每个引用，把它改到正确位置” [00:08:55–00:09:01]。

### 7. 开始建立 object file 分类 [00:09:15–00:09:52]

- Relocatable object file（`.o`）是汇编器输出；它虽是二进制文件，却不能直接装入内存执行，仍需链接器处理 [00:09:19–00:09:39] [课件: 13-linking.pptx p.9]。
- Executable object file 由链接器生成，可进入加载、执行阶段；老师在本段末尾刚开始引出其历史名称 `a.out` [00:09:44–00:09:52] [课件: 13-linking.pptx p.9]。
- 第三类 shared object file（`.so`）尚未在本段口述展开，留到下一段。

## 概念、符号与推导

### 核心概念

| 概念 | 本段中的定义 | 证据 |
|---|---|---|
| Separate compilation | 每个源模块独立经过预处理、编译、汇编，产生各自的 `.o` | [00:01:49–00:03:22] |
| Relocatable object file | 可与其他 `.o` 合并，但尚不能直接装入执行的 object file | [00:03:15–00:03:28]、[00:09:24–00:09:39] |
| Symbol | 链接器处理的全局变量或函数及其名称 | [00:05:23–00:05:39] |
| Symbol definition/reference | 定义创建对象；引用使用某个已定义或待解析的对象 | [00:05:45–00:06:11] |
| Symbol table | 汇编器写入 object file 的结构体数组，记录符号名称、大小、位置等 | [00:06:18–00:06:35] |
| Symbol resolution | 每个符号引用恰好绑定一个符号定义 | [00:06:40–00:06:56] |
| Relocation | 合并代码/数据，确定符号最终位置，并修补所有引用 | [00:07:24–00:09:01] |

### 符号与过程关系

```text
source modules
  -> 分别产生 relocatable object files
  -> symbol resolution：reference -> exactly one definition
  -> relocation：确定 definition 的最终位置并修补 reference
  -> fully linked executable object file
```

本段无代数公式推导；老师给出的是上述过程推导。关键前提是：编译器/汇编器生成 `.o` 时不知道多个模块合并后的最终地址，因此必须保留符号信息，交由链接器解析与重定位。

## 例子与课堂提示

4. **“偏移”到“最终位置”：** `.o` 中的位置不是最终运行地址；重定位的教学重点是定义的位置变化与引用修补必须成对完成 [00:07:44–00:09:01]。

## 易混点与边界

- **GCC 不等于链接器。** 此处 GCC 是 compiler driver；它调度 `cpp`、`cc1`、`as`，再调用 `ld` [00:01:55–00:02:47]。
- **`.o` 不等于可执行文件。** `.o` 仍是 relocatable，不能在本例中直接加载执行 [00:09:24–00:09:39]。
- **符号解析不负责摆放地址。** 它先决定“引用对应哪个定义”；重定位再决定“定义最终放哪里并怎样修补引用” [00:06:40–00:08:49]。

# 第 2 段：ELF 结构与链接器符号

**时间范围：** 00:09:52–00:19:49  
**对应课件：** [课件: 13-linking.pptx p.9]–[课件: 13-linking.pptx p.15]

## 本段在整讲中的作用

上一段已经把链接拆成 symbol resolution 与 relocation，但要解释二者如何落在真实文件上，还缺两层基础：object file 采用什么结构，以及链接器究竟能看见哪些 symbols。本段依次补齐三类 object file、统一的 ELF 格式、关键 ELF sections 和三类 linker symbols，最后回到 `main.c/sum.c` 标注哪些名字由链接器处理，并以 local static variable 过渡到下一段的重复符号解析。

## 教学展开

### 1. 补完三类 object file [00:09:52–00:10:29]

- **Executable object file：** `a.out` 这一称呼来自早期 Unix 默认可执行文件名的历史习惯 [00:09:52–00:10:05] [课件: 13-linking.pptx p.9]。转录说“very first Linux systems”，与同句后半的 Unix 表述不一致，见待核对项。
- **Shared object file（`.so`）：** 用于现代 shared libraries，后面会讲它怎样在 load time 或 run time 动态链接 [00:10:11–00:10:26] [课件: 13-linking.pptx p.9]。
- 连同上一段的 relocatable `.o`，三类文件分别面向“继续合并”“直接装入执行”“动态装入并链接” [课件: 13-linking.pptx p.9]。

### 2. 引入统一的 ELF 格式 [00:10:29–00:10:55]

`.o`、executable 与 `.so` 都使用 ELF（Executable and Linkable Format）的同一总体格式；它们虽是 binary，却不是无结构的字节堆，而是划分为多个 sections [00:10:29–00:10:55] [课件: 13-linking.pptx p.10]。

### 3. 从文件头顺序讲解 ELF 主体 [00:11:01–00:15:06]

老师沿文件布局从前往后讲：

1. **ELF header**：给出 word size、byte ordering、文件类型等总体属性 [00:11:01–00:11:13] [课件: 13-linking.pptx p.11]。
2. **Segment header table**：老师说明它用于 executable，指出代码、已初始化/未初始化数据、shared libraries 等在内存中的放置 [00:11:20–00:11:43]；课件还列 page size、virtual addresses 与 segment sizes [课件: 13-linking.pptx p.11]。
3. **`.text`**：机器代码；名称是历史遗留 [00:11:53–00:12:01]。
4. **`.rodata`**：只读数据，例如 `switch` 的 jump tables；`.text` 与 `.rodata` 都不应被写入 [00:12:01–00:12:17] [课件: 13-linking.pptx p.11]。
5. **`.data`**：已初始化的 global variables [00:12:24–00:12:28]。
6. **`.bss`**：未初始化的 global variables。它们需要 symbol-table entries，装入时也要分配内存，但无需在 `.o` 中为初值占文件空间 [00:12:38–00:13:25]。老师给出历史释义 “Block Started by Symbol”，并用 “Better Save Space” 作记忆法 [00:13:06–00:13:18] [课件: 13-linking.pptx p.11]。
7. **`.symtab`**：symbol table；包含 procedures、global variables 以及带 `static` 属性的对象，每个 symbol 有一项 [00:13:35–00:13:57] [课件: 13-linking.pptx p.12]。
8. **`.rel.text` / `.rel.data`**：assembler 留给 linker 的“待修补便签”。前者描述代码中需要修改的 instruction references，后者描述合并后需要修改的 pointer data [00:14:02–00:14:38] [课件: 13-linking.pptx p.12]。
9. **`.debug`**：源代码信息与 machine code 的对应关系，由 `gcc -g` 产生，用于 symbolic debugging [00:14:38–00:15:00] [课件: 13-linking.pptx p.12]。
10. **Section header table**：记录各 section 的 offset 与 size，使工具能定位前述 sections [00:15:00–00:15:06] [课件: 13-linking.pptx p.12]。

### 4. 从文件结构转向三类 linker symbol [00:15:08–00:18:27]

1. **Global symbols**：模块 `m` 定义、其他模块可以引用的 symbols；典型是没有 `static` 的 C functions 与 global variables [00:15:08–00:16:08] [课件: 13-linking.pptx p.13]。
2. **External symbols**：模块 `m` 引用、却由别的模块定义的 global symbols。`main.c` 调用 `sum` 时，`sum` 对 `main.c` 就是 external symbol [00:16:11–00:16:34]。
3. **Local symbols**：只在模块内定义和引用；典型是带 `static` 的 functions 与 global variables [00:16:34–00:17:28]。

老师特别切断一个常见混淆：local linker symbol 不是函数中的 local C variable。普通局部变量由编译器在 stack 上管理，链接器并不知道它们 [00:16:42–00:17:01] [课件: 13-linking.pptx p.13]。

随后老师把 `static` 提升为 C 的模块抽象手段：库中要对外暴露的函数不加 `static`；只供模块内部使用的函数加 `static`，从而获得 information hiding [00:17:30–00:18:22]。

### 5. 在运行示例上辨认 symbols [00:18:27–00:19:24]

- `array` 是 `main.c` 内定义并引用的 global symbol。
- `main` 是定义于 `main.c` 的 global symbol。
- `sum` 在 `main.c` 中是 external reference，在 `sum.c` 中有 global definition。
- `val`、`i`、`s` 是 stack 上的 local C variables，链接器不处理它们 [00:18:27–00:19:24] [课件: 13-linking.pptx p.14]。

### 6. 引出 local static C variable [00:19:24–00:19:49]

老师开始比较 local non-static 与 local static。课件中的 `f()` 和 `g()` 各自定义一个 `static int x`；本段只讲到 `f` 中这个 `x` 的函数作用域，存储位置与唯一符号名在下一段继续 [00:19:24–00:19:49] [课件: 13-linking.pptx p.15]。

## 概念、符号与推导

### ELF 的信息分工

| 内容 | ELF 位置 | 为什么链接需要它 |
|---|---|---|
| 文件总体属性 | ELF header | 解释其 word size、byte order、类型与机器属性 |
| executable 的内存映射信息 | Segment header table | 指导各 memory segments 的放置 |
| code / read-only data | `.text` / `.rodata` | 构成只读内容 |
| initialized / uninitialized globals | `.data` / `.bss` | 区分需要保存初值与只需装入时分配空间的数据 |
| names, sizes, locations | `.symtab` | 支持 symbol resolution |
| 待修补位置与方法 | `.rel.text` / `.rel.data` | 支持 relocation |
| 调试映射 | `.debug` | 支持 `gcc -g` 的 symbolic debugging |
| section offsets / sizes | Section header table | 定位文件内各 sections |

### 三类 symbol 的模块视角

设当前模块为 `m`：

```text
在 m 定义，可被其他模块引用     -> global symbol
在 m 引用，在其他模块定义       -> external symbol
只在 m 内定义并引用             -> local symbol
函数内普通自动变量              -> 不是 linker symbol
```

同一个 `sum` 会因观察模块不同而扮演不同角色：对 `main.c` 是 external symbol；对定义它的 `sum.c` 是 global symbol [00:16:11–00:16:34] [课件: 13-linking.pptx p.14]。

本段无公式推导；逻辑推导是：链接器要解析跨模块引用，ELF 必须同时保存“符号是什么”（`.symtab`）与“哪里以后要改”（relocation sections）。

## 例子与课堂提示

1. **BSS 记忆法：** “Better Save Space” 不是正式全称，而是老师用于记住未初始化变量不占 object-file 数据空间的课堂提示 [00:13:06–00:13:25]。
2. **Assembler 的便签：** relocation entry 被类比为 assembler 留给 linker 的 note：“这里引用的最终地址现在不知道，之后修补” [00:14:02–00:14:38]。
3. **库的 public/private 边界：** 对外 API 不加 `static`，内部 helper 加 `static`；该例服务于 C 模块级 abstraction 和 information hiding [00:17:30–00:18:22]。
4. **`val/i/s` 反例：** 名字存在于 C 源码不等于它就是 linker symbol；这些 local variables 属于 compiler/stack 范畴 [00:19:09–00:19:24]。

## 易混点与边界

- ELF 是三类 object file 的统一**格式**，不表示三类文件具有相同的可执行时机 [00:10:29–00:10:42]。
- `.bss` 不占相应的文件数据空间，不等于变量在运行内存中不占空间；装入时仍须分配 [00:12:38–00:12:59]。
- `.symtab` 记录 linker symbols；不能由此推断所有 C local variables 都在其中。
- 老师口述把 segment header table 的内存区域讲得较宽；课件明确其字段是 page size、virtual addresses 与 memory segment sizes [课件: 13-linking.pptx p.11]。不要把 segment 与 section 在所有语境中视为同义词。
- 本段只引出 local static 的例子；其 `.data/.bss` 存储与 `x.1/x.2` 命名属于下一段。

## 本段掌握检查

1. **问：三类 object file 各自面向什么阶段？**  
  **答：** `.o` 用于继续合并；executable 可复制到内存执行；`.so` 可在 load time 或 run time 动态装入和链接 [课件: 13-linking.pptx p.9]。
2. **问：`.data` 与 `.bss` 的教学区别是什么？**  
  **答：** `.data` 保存 initialized globals；`.bss` 表示 uninitialized globals，文件中无需保存其初值空间，但装入后仍需内存 [00:12:24–00:13:25]。
3. **问：`.symtab` 与 relocation sections 分别回答什么问题？**  
  **答：** `.symtab` 记录符号的名称、大小、位置等；relocation sections 记录哪些代码或数据引用以后必须修补以及怎样修补 [00:13:35–00:14:38]。
4. **问：`sum` 对 `main.c` 与 `sum.c` 分别是什么 symbol？**  
  **答：** 对引用它的 `main.c` 是 external；对定义它且允许别的模块引用的 `sum.c` 是 global [00:16:11–00:16:34]。
5. **问：为什么 `val` 不是 local linker symbol？**  
  **答：** 它是函数内 local C variable，由 compiler 在 stack 上管理，linker 不知道它 [00:19:09–00:19:16]。

# 第 3 段：强弱符号规则与危险的同名全局变量

**时间范围：** 00:19:49–00:29:45  
**对应课件：** [课件: 13-linking.pptx p.15]–[课件: 13-linking.pptx p.18]

## 本段在整讲中的作用

本段把上一段“每个 reference 必须绑定唯一 definition”的抽象要求落到重复定义上。老师先完成 local static variable 的存储解释，再定义 strong/weak symbols 和三条选择规则，最后连续用 linker puzzles 展示：链接成功不等于程序正确，尤其同名全局变量的类型或大小不一致时会产生跨模块内存破坏。段尾的学生提问让老师先纠正幻灯片判断，再转回 local static 的生命周期，为下一段开头的再次精确纠错留下现场上下文。

## 教学展开

### 1. 完成 local static variable 的双重属性 [00:19:49–00:21:04]

- `f()` 与 `g()` 中各自的 `static int x` 都只有本函数能引用，作用域像普通 local C variable [00:19:49–00:20:11]。
- 由于有 `static`，它不在 stack 上，而像 global 一样存于 `.data`（课件补充：未初始化时也可能在 `.bss`）[00:20:11–00:20:29] [课件: 13-linking.pptx p.15]。
- Compiler 为两个 `x` 各分配空间，并用类似 `x.1`、`x.2` 的唯一 local symbol names 消除歧义；示例都已初始化，所以进入 `.data` 并各有 symbol-table entry [00:20:35–00:21:01] [课件: 13-linking.pptx p.15]。

结论是：local static 同时具有“函数内作用域”和“静态存储位置/持续生命周期”，不能简单归为 stack local 或 module-visible global。

### 2. 为重复定义建立 strong/weak 分类 [00:21:04–00:22:12]

老师重申 symbol resolution 的约束：每个 symbol reference 最终只能对应一个 definition；若多个模块提供同名 definition，就按强弱分类 [00:21:04–00:21:30]。

- **Strong symbols：** procedures/functions，以及 initialized global variables。
- **Weak symbols：** uninitialized global variables。

例子中，`int foo = 5;` 与函数 `p1` 是 strong；另一个模块的 `int foo;` 是 weak，函数 `p2` 仍是 strong [00:21:35–00:22:12] [课件: 13-linking.pptx p.16]。

### 3. 给出三条 linker symbol rules [00:22:12–00:23:36]

1. **多个 strong definitions：报 linker error。** 因而多个模块定义同名函数，或多处初始化同名 global，都不允许 [00:22:19–00:22:56]。
2. **一个 strong 加若干 weak：选择 strong。** 所有对同名 weak symbol 的 references 也解析到 strong definition [00:22:35–00:23:13]。
3. **多个 weak：任意选择一个。** 这能成功链接，却可能隐藏错误 [00:23:13–00:23:17]。

老师补充，使用 GCC 的 `-fno-common` 可让多个 weak definitions 触发错误，从而把隐患提前暴露 [00:23:20–00:23:33] [课件: 13-linking.pptx p.17]。

### 4. 说明为什么必须理解这些规则 [00:23:36–00:24:14]

Linker errors 往往难调试，因为程序员通常不知道 linker 内部怎样选 definitions。老师以此为动机进入 puzzles：真正危险的不只是显式错误，还有“链接器按规则成功选择，但选择破坏了源模块各自假设”的程序 [00:23:36–00:24:08]。

### 5. Puzzle 1：两个同名函数 [00:24:14–00:24:31]

两个 modules 都定义 `p1()`；函数是 strong，所以出现 two strong symbols，链接时报错 [00:24:14–00:24:31] [课件: 13-linking.pptx p.18]。

### 6. Puzzle 2：两个同型 weak `int x` [00:24:34–00:25:25]

两个 modules 分别定义 `p1`、`p2`，同时各有未初始化 `int x`。Linker 任意挑一个 `x`，所有 references 共用它 [00:24:34–00:24:55]。因为两边都把它视作 `int`，选择哪一个在尺寸上暂不造成差异；但老师追问“这真是你想要的吗”，强调意外共享本身就是设计风险 [00:25:00–00:25:19] [课件: 13-linking.pptx p.18]。

### 7. Puzzle 3：不同类型的 weak `x` [00:25:25–00:26:47]

一个 module 中有 `int x; int y;`，另一个有 `double x;`，三个变量在此都是未初始化 globals，因而 `x` 的两个 definitions 都 weak。老师尝试说明 linker 任意选择造成的尺寸错配，但口述在 00:26:15 后出现自我中断，并在学生问题后暂时说幻灯片“不太对” [00:26:15–00:28:43]。这一处不能把老师的中间说法当作最终结论；精确纠正在下一段 00:30:37–00:31:04 完成。

### 8. Puzzle 4：strong `int x=7` 对 weak `double x` [00:26:47–00:28:09]

一个 module 定义 initialized `int x = 7`，所以它是 strong；另一个 module 以 `double x` 使用同名 weak symbol。Linker 必然选 4-byte `int x` 的位置，而第二个 module 的 compiler 仍按其源声明生成对 `double` 的访问。老师在本段先说这种写入会越过 `x` 并覆盖相邻 `y`，称其 “really nasty” [00:26:47–00:27:38] [课件: 13-linking.pptx p.18]；经课堂来回后，最终确认留到下一段。

另一个较简单情形是 strong `int x=7` 与 weak `int x`：weak module 的 references 都指向 initialized strong variable，可能违反它以为 `x` 未初始化的意图 [00:27:51–00:28:09]。

### 9. 课堂提问与 local static 的用途 [00:28:09–00:29:45]

- 老师刚要提出“不同 compiler 的相同 weak structs 可能采用不同 alignment rules”的 nightmare scenario，就被提问打断 [00:28:09–00:28:21] [课件: 13-linking.pptx p.18]。
- 在讨论中老师一度表示学生说得对，并说 slide “not quite right” [00:28:21–00:28:43]；由于后面再次修正，复习时应以 00:30:37 后的最终版本为准。
- 另一个问题转向 function-local `static`：它用于让值在多次 function invocations 之间保留；老师同时预告，这种 state 在之后讲 threads 时通常会导致 non-thread-safe code [00:28:45–00:29:37]。

## 概念、符号与推导

### Strong/weak 判定与解析规则

```text
procedure/function definition     -> strong
initialized global               -> strong
uninitialized global             -> weak

strong + strong                  -> link-time error
one strong + one-or-more weak    -> choose strong
weak + weak                      -> choose one arbitrarily
```

### 类型错配为何危险

Linker 主要按 symbol name 做解析，而每个 module 的 compiler 已依据本模块声明决定访问宽度。于是“地址来自被选中的 definition”和“访问宽度来自引用方编译时类型”可能不一致。老师在本段展开该问题，但最终、无歧义的 8-byte write 对 4-byte object 推导出现在下一段 [00:30:37–00:31:04]。

本段无数值公式推导。其关键条件链为：

```text
同名 definitions
  -> strong/weak rule 选择一个地址
  -> 所有 references 解析到该地址
  -> 各 module 仍执行自己编译出的访问宽度
  -> 类型/大小不一致时可能越界写入相邻对象
```

## 例子与课堂提示

1. **`x.1` / `x.2`：** 展示 compiler 如何让两个 function-local static variables 同名却保有独立 storage 和 symbol entries [00:20:35–00:21:01]。
2. **两个 `int x;`：** 不是“没报错就没问题”；所有模块意外共享一个对象，可能已经违背设计 [00:24:34–00:25:19]。
3. **`int x` 对 `double x`：** 用于展示 symbol name 相同却类型不一致时，linker 选择与 compiler access width 脱节。
4. **保留跨调用状态：** function-local static 的合理用途是保存下一次调用需要的值；老师随后以早期伪随机数生成器作例子，该例在下一段开头完成 [00:29:26–00:29:45]。

## 易混点与边界

- `static` 在本例中同时影响 scope 与 storage：作用域局部，但不在 stack；不要只凭“local”判断存储位置。
- Strong/weak 是 linker 对 program symbols 的分类，不是 C 类型系统中的强/弱类型。
- “多个 weak 任意选一个”不代表 linker 会检查两边的 C types 是否兼容。
- `-fno-common` 是老师在本讲给出的防护选项 [课件: 13-linking.pptx p.17]；本笔记不扩展其版本历史或其他编译器行为。
- 00:25:25–00:31:04 是现场纠错链。不能静默整理成一条看似从未动摇的讲解；应保留“初说法 → 学生质疑 → 暂时改口 → 下一段最终确认”。

## 本段掌握检查

  **答：** Scope 限于该函数；storage 不在 stack，而在 `.data`；compiler 为它建立唯一 local symbol entry，例如 `x.1` [00:19:49–00:21:01]。

# 第 4 段：从全局变量准则到 relocation entry

**时间范围：** 00:29:45–00:39:44  
**对应课件：** [课件: 13-linking.pptx p.18]–[课件: 13-linking.pptx p.21]

## 本段在整讲中的作用

本段先收束 strong/weak symbol puzzles：老师完成对 `int x=7` 与 `double x` 冲突的最终纠错，并把危险规则转化为可执行的 global-variable 编程准则。随后讲授重心从链接第 1 步 symbol resolution 切换到第 2 步 relocation：链接器怎样合并 sections、决定 symbol addresses，以及 compiler/assembler 怎样用 relocation entries 把暂时无法确定的引用交给 linker 修补。

## 教学展开

### 1. Local static 的持久状态例子 [00:29:45–00:30:06]

承接上一段学生关于 function-local static 的问题，老师以早期 pseudo-random number generator 为例：一次调用计算出的伪随机值存入 static variable，下一次调用把它作为起始值。因此，需要值跨 function invocations 保留时会使用 `static` [00:29:45–00:30:06]。这补完了上一段“作用域局部、存储期持久”的实际用途。

### 2. 最终修正 `double x` 写入的推理 [00:30:07–00:31:13]

老师重新检查 p.18 的 strong/weak puzzle，并明确修正：

1. 模块 `p1` 定义 initialized `int x = 7`，所以 `x` 是 strong，分配的对象大小为 4 bytes [课件: 13-linking.pptx p.18]。
2. 模块 `p2` 声明 `double x`；该模块的 compiler 根据 `double` 生成 8-byte write [00:30:42–00:30:48]。
3. Linker 按规则把所有 `x` references 解析到 strong `int x` 的 4-byte memory location [00:30:53–00:31:03]。
4. 因此，`p2` 的 8-byte write 会越过这 4-byte object，覆盖其后的 `y` [00:31:04–00:31:09]。

这里是上一段课堂来回后的最终版本，必须以此为准，而不能采用 00:28:36 的暂时改口。

### 3. 回答存储位置问题 [00:31:14–00:31:54]

学生问题的原句没有被 ASR 记录。老师回答中可以可靠提取两点：global variables 在 `.data`，不在 stack；普通 function-local variables 通常由 compiler 在 stack 上连续分配 [00:31:24–00:31:43]。由于缺少问题原文，不进一步推断学生具体问了 `x`、`y` 的哪种布局。

### 4. 把 symbol puzzles 转化为编程准则 [00:31:54–00:32:42]

老师依次给出四项建议 [课件: 13-linking.pptx p.19]：

1. **能避免 global variables 就避免**，因为 strong/weak rules 会制造隐蔽错误 [00:31:54–00:32:02]。
2. **必须使用 global 时，能加 `static` 就加**，把 scope 限制在当前 module [00:32:02–00:32:16]。
3. **定义 global variable 时初始化它**，使它成为 strong；若多个 modules 初始化同名 global，linker 会直接报错，问题更早暴露 [00:32:19–00:32:33]。
4. **引用 external global variable 时使用 `extern`**，明确告诉 compiler 这是外部定义 [00:32:33–00:32:42]。

### 5. 从 symbol resolution 切换到 relocation [00:32:42–00:34:09]

此时假设 linker 已把每个 symbol reference 关联到某个 definition，下一任务是把 relocatable object files 合并成一个 executable [00:32:42–00:33:05]。

运行示例中：

- `main.o` 有 `main` 的 code，也有 initialized `array` 的 data。
- `sum.o` 只有 `sum` 的 code，没有 initialized data [00:33:05–00:33:18]。
- 还有 system code/data。老师说明 libc startup code 在用户代码前运行，完成初始化，最后调用 `main(argc, argv)`；`main` 返回后控制回到 startup code，由它完成退出流程 [00:33:18–00:34:01] [需回听 00:33:54]。

### 6. 合并同类 sections [00:34:09–00:35:09]

- Linker 把 system code、`main.o`、`sum.o` 的 `.text` 按其决定的顺序连续放入 executable 的一个 combined `.text` [00:34:09–00:34:45] [课件: 13-linking.pptx p.20]。
- 它同样把各 object files 的 `.data` 合成 combined `.data` [00:34:47–00:34:56]。
- Symbol tables 与 debug information 也随之合并 [00:35:03–00:35:09]。

### 7. 合并带来的地址问题 [00:35:09–00:36:31]

一旦 sections 被重新摆放，linker 必须给 `main`、`sum`（口述一处说成 `swap`）和各 data arrays 选择最终 absolute addresses [00:35:09–00:35:45]。但 compiler 生成单个 `.o` 时不知道 linker 将选择什么地址，于是留下 relocation entries，存放在 object file 的 relocation sections；每一项告诉 linker 哪个 symbol reference 要在合并时 patch up [00:35:45–00:36:27]。

### 8. `array` 的 absolute relocation entry [00:36:31–00:39:28]

在 `main.c` 中有两个待处理 references：global array `array` 与 function `sum` [00:36:31–00:36:53]。老师先讲 `array`：

```text
0000000000000000 <main>:
   4: be 02 00 00 00       mov $0x2,%esi
   9: bf 00 00 00 00       mov $0x0,%edi
             a: R_X86_64_32 array
```

[课件: 13-linking.pptx p.21]

1. `sum` 的第一个参数是 array address；按此前约定，第一个参数放入 `%edi` [00:37:02–00:37:17]。
2. Compiler 尚不知道 `array` 的最终 address，所以 immediate field 暂填全 0；opcode `bf` 后的 4 bytes 是占位字段 [00:37:28–00:37:42]。
3. `main` 是该 `.text` 中唯一 function，从 offset `0` 开始，图中 instruction addresses 都是相对于这个 section 开头的 offsets [00:38:03–00:38:35]。
4. Relocation entry `a: R_X86_64_32 array` 告诉 linker：从 `.text` offset `0xa` 开始的 4 bytes 是对 `array` 的 32-bit absolute-address reference [00:38:41–00:39:14]。
5. Relocation 时，linker 要把 `array` 的最终 absolute address 写进这 4-byte field [00:39:07–00:39:28]。

### 9. 转向 `sum` 的 relocation [00:39:28–00:39:44]

老师开始讲第二项：compiler 不知道 function `sum` 最终位于哪个 module、甚至是否会有 definition [00:39:28–00:39:44]。具体的 PC-relative entry 从下一段继续。

## 概念、符号与推导

### Relocation 的两层动作

```text
section relocation:
  input .text sections -> combined executable .text
  input .data sections -> combined executable .data

symbol/reference relocation:
  为每个 definition 选择最终 address
  按 relocation entries 修补每个 reference field
```

### `array` entry 的具体字段

| 项目 | 值 | 含义 |
|---|---:|---|
| Instruction start | `.text + 0x9` | `mov $0x0,%edi` 的 opcode 起点 |
| Relocation offset | `.text + 0xa` | 4-byte immediate field 起点 |
| Relocation type | `R_X86_64_32` | 本例要求 32-bit absolute value |
| Symbol | `array` | 待写入其最终 address |
| Before relocation | `00 00 00 00` | 未知地址的占位值 |

本段没有一般化 relocation 公式；老师通过具体 offset 与字段推导“compiler 留占位值和 entry，linker 再按 entry 写最终 address”。

## 例子与课堂提示

1. **Pseudo-random generator：** 服务于 local static 跨调用保存状态的用途，同时老师预告这种状态会给 thread safety 带来问题 [00:29:45–00:30:06]。
2. **8-byte write / 4-byte object：** 服务于“linker 不做 C type compatibility 检查”的危险后果；必须保留老师最终纠正后的版本 [00:30:37–00:31:09]。
3. **初始化 global：** 不是为了给变量任意初值，而是让 duplicate definitions 变成 multiple strong symbols，从静默选取转为 linker error [00:32:19–00:32:33]。
4. **Relocation entry 像 reminder：** Compiler 不知道最终 address，就用全 0 占位并留下机器可执行的修补说明 [00:35:45–00:36:27]。

## 易混点与边界

- 最终内存破坏结论是 `p2` 的 compiler 发出 **8-byte** write，而 linker 让它落到 **4-byte** strong `int x`；不是“linker 把写入也改成 4 bytes”。
- “Global variables go in `.data`”是老师回答中的概括；本讲前面已区分 initialized globals 在 `.data`、uninitialized globals 在 `.bss` [课件: 13-linking.pptx p.11]。应结合初始化状态理解。
- Relocation 不只是拼接 bytes；一旦拼接改变位置，symbol addresses 与所有 references 必须同步更新。
- `%edi` 在此被用来传入 address，是该示例反汇编的呈现；不要从本段扩展未讲授的地址模型或 ABI 细节。
- 本段只完成 `array` 的 absolute relocation；`sum` 的 PC-relative relocation 在第 5 段。

# 第 5 段：PC-relative relocation 与 executable loading

**时间范围：** 00:39:44–00:49:35  
**对应课件：** [课件: 13-linking.pptx p.21]–[课件: 13-linking.pptx p.24]

## 本段在整讲中的作用

上一段用 `array` 展示了 absolute relocation，本段用 `sum` 完成 PC-relative relocation：先读 `.o` 中的 placeholder 和 `sum-0x4` entry，再对照 linked executable 验证 linker 写入的具体地址与 displacement。随后老师说明静态链接完成的 executable 为什么可以直接装入内存，并把 ELF sections 映射到课堂版 Linux virtual-address-space 图。段末从“可装入的程序”转向“怎样打包可复用 API”，为 static libraries 铺路。

## 教学展开

### 1. `sum` reference 在 `.o` 中仍未知 [00:39:44–00:40:18]

Compiler 不知道 `sum` 最终位于哪个 module，也不知道是否会找到 definition，所以先生成一个 displacement 全 0 的 `callq`，同时留下 relocation entry [00:39:44–00:40:18]：

```text
   e: e8 00 00 00 00       callq 13 <main+0x13>
             f: R_X86_64_PC32 sum-0x4
```

[课件: 13-linking.pptx p.21]

Entry 表示从 `.text` offset `0xf` 开始的 4 bytes 是一个对 symbol `sum` 的 PC-relative reference [00:39:58–00:40:18]。

### 2. 解释 `-0x4` bias [00:40:18–00:41:19]

`call` 使用 PC-relative addressing，field 中不是 `sum` 的 absolute address，而是相对当前 `%rip`/program counter 的 signed offset [00:40:29–00:40:44]。执行时 program counter 指向下一条 instruction；relocation field 本身有 4 bytes，因此 entry 带 `-0x4` bias，使 linker 拥有计算正确 displacement 所需的信息 [00:40:44–00:41:16]。

老师称这是 arcane detail，并把完整一般算法留给教材；课堂要求是理解 relocation entry 已包含 linker 修补所需的足够信息，而不是自行推导未讲授的通式 [00:41:04–00:41:16]。

### 3. 对照 relocated `.text` 验证 `array` [00:41:19–00:42:09]

用 `objdump -dx prog` 查看 linked executable：

```text
4004d9: bf 18 10 60 00    mov $0x601018,%edi
```

原先全 0 的 4-byte immediate 已被 patch 成 `array` 的最终 address `0x601018` [00:41:19–00:42:00] [课件: 13-linking.pptx p.22]。这验证了上一段 `R_X86_64_32 array` entry 的效果。

### 4. 用具体算式验证 `sum` [00:42:09–00:43:36]

Linked code 中：

```text
4004de: e8 05 00 00 00    callq 4004e8 <sum>
4004e3: ...                next instruction
4004e8: ...                <sum>
```

`callq` 的 immediate field 被 linker 写成 signed displacement `0x5`。CPU 以 next-instruction address 为基准：

```text
target = next instruction address + signed displacement
0x4004e8 = 0x4004e3 + 0x5
```

[00:42:16–00:43:28] [课件: 13-linking.pptx p.22]

因此，PC-relative field 里出现 `5` 并不是把 `sum` 放在 address `5`，而是表示 `sum` 在下一条 instruction 之后 5 bytes。

### 5. 区分 compiler 与 linker 的职责 [00:43:36–00:44:05]

老师说“compiler has all the smarts”：compiler/assembler 识别 reference 的种类并生成 relocation entry；linker 逐项执行 entry 指示，最终让 references 具有运行时有效的目标 [00:43:36–00:43:52]。这里的重点不是贬低 linker，而是说明本例修补规则已编码在 entry 中。

### 6. 从 executable file 映射到内存 [00:44:05–00:45:23]

完成静态链接后，object file 的 code/data 可以在本例中无需进一步修改地装入 memory [00:44:05–00:44:20]：

- `.init`、`.text`、`.rodata` 组成课堂图中的 read-only code segment；bytes 可从 executable 直接装入 [00:44:20–00:44:56] [课件: 13-linking.pptx p.23]。
- `.data` 与 `.bss` 对应 read/write data segment [00:45:03–00:45:16] [课件: 13-linking.pptx p.23]。口述把二者都说成可“copied directly”，但前面已说明 `.bss` 不为未初始化值占文件空间；应把 p.23 理解为 loader 为该 segment 建立相应内存，而不是凭空从文件复制 `.bss` 初值。

### 7. 讲解课堂版 Linux address-space 图 [00:45:23–00:47:33]

老师从低地址向高地址说明 [课件: 13-linking.pptx p.23]：

1. 图中 executable 从 `0x400000` 附近装入；code 与 data 来自 executable [00:45:23–00:46:04]。
2. Data segment 之后是 run-time heap，由 `malloc` 管理并向高地址增长；heap 顶端由 kernel 维护的 `brk` 表示 [00:46:04–00:46:21] [00:47:19–00:47:29]。
3. User stack 位于用户可见地址空间顶部并向低地址增长；其顶部由 `%rsp` 指示 [00:46:30–00:46:59] [00:47:21–00:47:29]。
4. Stack 上方是 user code 不可见的 kernel memory；非法访问会产生 segmentation fault [00:46:30–00:46:48]。
5. Heap 与 stack 之间的大空隙内有 shared-library memory-mapped region，`.so` files 将装到这里 [00:47:00–00:47:10]。

### 8. 老师主动标注内存图的简化 [00:47:33–00:48:13]

老师补充，实际观察 `malloc` addresses 时会看到图中未表达的另一类高地址分配：很大的 objects 会来自高地址、向下的一片区域，而向上的 conventional heap 用于较小 objects [00:47:33–00:47:57]。他明确说不确定为何这样实现，只猜测可能为了给 large/small objects 使用不同 allocation algorithms [00:47:57–00:48:05]。这是一项课堂观察与猜测，不应提升为本讲已证明的机制。

### 9. 转向 library packaging [00:48:13–00:49:35]

链接的重要优势是能把 abstractions 做成 libraries，并通过 API 提供给其他 programmers [00:48:13–00:48:37]。一段学生问题没有被转录完整；老师只可靠地表示自己做过相关实验，allocation 会增长到某个很大的 limit，但他不知道该问题的确定答案 [00:48:41–00:49:23]。随后他回到主线：程序员希望定义 API、实现并打包 API，再让别人使用 [00:49:23–00:49:35] [课件: 13-linking.pptx p.24]。

## 概念、符号与推导

### 两种 relocation 的本例对照

| Reference | `.o` 中 entry | Linked field | 解释 |
|---|---|---|---|
| `array` address | `R_X86_64_32 array` at `0xa` | `0x601018` | 4-byte absolute address |
| `sum` call | `R_X86_64_PC32 sum-0x4` at `0xf` | `0x00000005` | 从 next `%rip` 到 `sum` 的 signed displacement |

### 本段唯一明确算式

```text
0x4004e8 = 0x4004e3 + 0x5
sum address = next-instruction address + call displacement
```

前提：x86-64 `callq` 在本例采用 PC-relative addressing，执行 call 时 `%rip` 已指向下一条 instruction [00:40:29–00:40:58]。

### Executable 到 memory 的课堂映射

```text
低地址
  read-only code segment (.init, .text, .rodata)
  read/write data segment (.data, .bss)
  heap  --brk--> 向上增长
  ... shared-library mapped region ...
  stack <--%rsp-- 向下增长
  kernel-only memory
高地址
```

这是老师明确称为 simplification 的课堂图，不用于推导本讲未覆盖的现代地址随机化或具体 allocator policy。

## 例子与课堂提示

1. **`0x5` 不是 function address：** 它服务于区分 absolute 与 PC-relative addressing；要加到 next `%rip` 才得到 `sum` [00:42:09–00:43:28]。
2. **`objdump` 前后对照：** `objdump -r -d main.o` 显示 placeholder/entries，`objdump -dx prog` 显示 linker 修补后的 executable [课件: 13-linking.pptx p.21] [课件: 13-linking.pptx p.22]。
3. **Memory-map 边界：** 老师提醒 `.init` 无需在本讲深究 [00:44:33–00:44:40]，同时把 shared-library region 先放入地图，供动态链接部分使用。
4. **大对象分配：** 老师明确标成简化之外的观察和猜测；复习时应保留不确定性 [00:47:33–00:48:05]。

## 易混点与边界

- `sum-0x4` 的 `-0x4` 与最终 field `0x5` 不是同一个数：前者属于 relocation entry 的 bias，后者是 linker 算出的 concrete displacement。
- Program counter 的基准是 `0x4004e3`（next instruction），不是 call opcode address `0x4004de` [课件: 13-linking.pptx p.22]。
- “Linker blindly follows entries”不能理解为 linker 不做 symbol resolution；symbol resolution 是前一步，本句话只描述 relocation patch 的职责分工。
- 本段“无需进一步修改即可装入”针对前面完成静态链接的 executable；动态链接 executable 会在后续由 dynamic linker 继续解析。
- p.23 是概念图。老师自己说明实际 heap behavior 更复杂，且对原因不确定。

## 本段掌握检查

1. **问：`f: R_X86_64_PC32 sum-0x4` 描述什么位置和 reference？**  
  **答：** `.text` offset `0xf` 起的 4-byte field，是对 `sum` 的 PC-relative reference；`-0x4` 配合 next-instruction `%rip` 基准 [00:39:58–00:41:16]。
2. **问：为什么 linked `callq` field 是 `5`，却能调用 `0x4004e8`？**  
  **答：** CPU 用 next instruction `0x4004e3` 加 signed displacement `0x5`，得到 `0x4004e8` [课件: 13-linking.pptx p.22]。
3. **问：本例中 compiler/assembler 与 linker 怎样分工？**  
  **答：** 前者识别 reference、留下 placeholder 和 relocation entry；后者解析 symbol 后按 entry 修补 concrete field [00:43:36–00:43:52]。
4. **问：课堂内存图中 heap、shared libraries、stack 的相对位置和增长方向是什么？**  
  **答：** Heap 在 data 后向上；shared libraries 映射在 heap/stack 间；stack 位于用户空间高处并向下 [00:46:04–00:47:29] [课件: 13-linking.pptx p.23]。
5. **问：老师对“大对象来自高地址区域”的解释有多确定？**  
  **答：** 他报告了观察，但明确说不确定原因，只猜测可能为大小对象采用不同 algorithms [00:47:33–00:48:05]。

# 第 6 段：Static library archive 与命令行顺序

**时间范围：** 00:49:35–00:59:34  
**对应课件：** [课件: 13-linking.pptx p.24]–[课件: 13-linking.pptx p.30]

## 本段在整讲中的作用

上一段把“把 API 打包给别人使用”作为问题提出。本段先排除两个朴素但不理想的打包办法，再给出 Unix 的传统方案 static library：用带索引的 `.a` archive 汇集 relocatable object files，由 linker 只抽取解决当前 unresolved references 的成员。后半通过 `libvector.a` 和 `libmine.a` 两个例子，把 symbol resolution 扩展为一个有状态的、从左到右的 command-line scan，并解释为什么 library 通常放在命令行末尾。

## 教学展开

### 1. 两个朴素打包方案及其缺点 [00:49:35–00:50:54]

老师问：怎样把 math、I/O、memory management、string manipulation 等常用 functions 提供给其他 programmers [00:49:35–00:49:50] [课件: 13-linking.pptx p.24]？

1. **全部函数放进一个大 source file。** 使用者链接一个巨大 object file。对于有数百 functions 的 libc，这会臃肿且在 time/space 上低效 [00:49:50–00:50:13]。
2. **每个函数一个 source/object file。** 只链接需要的 binaries，更有效率；但 programmer 必须明确列出所有文件并维护 Makefile，GCC command line 可能极长 [00:50:17–00:50:45]。

需要的是兼得二者：library 可作为一个整体传给 linker，而 executable 只吸收实际需要的函数。

### 2. 定义 static library / archive [00:50:54–00:52:15]

- Static library 是 `.a` archive：把相关 `.o` files 串接到一个文件，并在开头放 index/table of contents，记录各 member `.o` 的 offset [00:50:54–00:51:47] [课件: 13-linking.pptx p.25]。
- Programmer 把整个 archive 传给 linker；linker 查看 unresolved external references，只把能解决它们的 archive members 链入 executable [00:51:47–00:52:04]。
- 因此，即使 libc archive 很大，若程序只需要 `printf`，老师在此简化地说只会取入 `printf.o`；其依赖成员也会根据引用继续处理 [00:52:04–00:52:13]。

### 3. 用 `ar` 创建和更新 archive [00:52:15–00:53:04]

各 library source 先分别经过 translators 形成 `.o`，再交给 archiver `ar`：

```text
ar rs libc.a atoi.o printf.o ... random.o
```

[课件: 13-linking.pptx p.26]

老师以 `printf` 变化为例：只重编译相应 source，再更新 archive [00:52:44–00:53:04]。课件明确强调 archiver 允许 incremental updates，即替换 archive 中变化的 `.o` [课件: 13-linking.pptx p.26]。

### 4. 常见 static libraries 与命名 [00:53:04–00:53:43]

- `libc.a`：C standard library。老师口述“约 1,500 object files”；课件给当时示例的精确值为 4.6 MB、1496 object files，涵盖 I/O、allocation、signals、strings、date/time、random numbers、integer math [00:53:04–00:53:13] [课件: 13-linking.pptx p.27]。
- `libm.a`：math library。老师口述“数百 functions”；课件给 2 MB、444 object files，含 `sin`、`cos`、`tan`、`log`、`exp`、`sqrt` 等 [00:53:13–00:53:20] [课件: 13-linking.pptx p.27]。
- 命名惯例是 `lib` prefix 加用途名称 [00:53:20–00:53:36]。

### 5. 构造 `libvector.a` 例子 [00:53:43–00:54:43]

Library 由两个 members 构成 [课件: 13-linking.pptx p.28]：

```c
z[i] = x[i] + y[i];  /* addvec */
z[i] = x[i] * y[i];  /* multvec */
```

`main2.c` 定义 `x={1,2}`、`y={3,4}`、`z`，只调用 `addvec(x,y,z,2)`，随后用 `printf` 输出结果 [00:53:43–00:54:34]。`addvec.o` 与 `multvec.o` 被打包成 `libvector.a` [00:54:20–00:54:43]。

### 6. Linker 只抽取被引用的 members [00:54:43–00:55:59]

输入是 `main2.o`、`libvector.a` 和 `libc.a` [00:54:43–00:55:17]：

- `main2.o` 对 `addvec` 的 unresolved reference 使 linker 从 `libvector.a` 取出 `addvec.o`，不取未使用的 `multvec.o`。
- `printf` reference 使其从 `libc.a` 取出 `printf.o`，并处理 `printf.o` 所调用的其他 modules [00:55:17–00:55:36]。
- `main2.o + addvec.o + printf.o + dependencies` 被静态合并为 fully linked executable `prog2c`；`c` 表示此例在 compile time linking [00:55:36–00:55:54] [课件: 13-linking.pptx p.29]。

### 7. 给出 static-library resolution algorithm [00:55:59–00:57:08]

Linker 按 command line 从左到右扫描 `.o` 与 `.a` [00:55:59–00:56:17]：

1. 维护当前 unresolved references 列表。
2. 遇到新 object/archive `obj`，用其中 definitions 尝试解决**当前**列表中的 references [00:56:22–00:56:57]。
3. 扫描结束若列表仍非空，则 linker error [00:57:03–00:57:08]。

关键是单向顺序：一个 archive 已经经过后，后面新出现的 unresolved reference 不会自动让课堂算法回头重扫该 archive。

### 8. 用 `libmine.a` 证明 order matters [00:57:08–00:59:34]

`libtest.o` 引用 archive `libmine.a` 中定义的 `libfun` [00:57:31–00:58:45]。命令选项含义：

- `-L.`：先在 current directory 搜索 library files [00:57:49–00:58:08]。
- `-lmine`：`libmine.a` 的缩写写法 [00:58:08–00:58:20]。

正确顺序：

```text
gcc -L. libtest.o -lmine
```

先读 `libtest.o`，把 `libfun` 加入 unresolved list；随后读 `libmine.a`，找到 definition 并解决它 [00:58:24–00:59:04]。

错误顺序：

```text
gcc -L. -lmine libtest.o
```

先读 archive 时尚无待解决的 `libfun`，所以不抽取成员；后读 `libtest.o` 才出现 unresolved `libfun`，而 command line 已结束，于 00:59:34 得到 linker error [00:59:04–00:59:34] [课件: 13-linking.pptx p.30]。

## 概念、符号与推导

### Archive 的结构与选择单位

```text
libvector.a
  index / table of contents
  addvec.o
  multvec.o
```

Library 作为一个文件出现在 command line，但 linker 的抽取单位是 member `.o`，这正是“易于分发”和“只带入所用 code”同时成立的原因。

### 左到右 unresolved-set 演化

正确顺序：

```text
start              U = {}
scan libtest.o     U = {libfun}
scan libmine.a     U = {}
end                success
```

错误顺序：

```text
start              U = {}
scan libmine.a     U = {}          (当前无需求，不取 member)
scan libtest.o     U = {libfun}
end                error
```

这里 `U` 只是对老师“current unresolved references list”的记号化整理，不引入额外 linker algorithm。向量例子的明确关系是 `z[i]=x[i]+y[i]` 和 `z[i]=x[i]*y[i]` [课件: 13-linking.pptx p.28]。

## 例子与课堂提示

1. **Libc 只用 `printf`：** 说明 archive member extraction 的空间收益；后续 dependencies 仍按 unresolved references 继续取入。
2. **`libvector.a`：** `main2` 只调用 `addvec`，所以 `multvec.o` 留在 archive 外，不进入 `prog2c` [00:55:17–00:55:43]。
3. **命令行 moral：** 老师的直接结论是 libraries 放在 command line 末尾 [课件: 13-linking.pptx p.30]。
4. **Cryptic linker error：** 错序造成的 `undefined reference to 'libfun'` 并不说明 archive 中没有 `libfun`，而可能是扫描时机不对；错误消息的评价在下一段开头完成。

## 易混点与边界

- `.a` 不是一个已经 fully linked 的大 object；它是带 index 的 relocatable `.o` collection。
- Linker 接收整个 archive，不代表 executable 复制整个 archive；只取能解决 references 的 member objects。
- `-L.` 是 search path，`-lmine` 是 library name shorthand；二者不是同一选项。
- Command-line order 影响的是 archive member selection。此处不能把它简化成“linker 永远不会处理前面的 definitions”；普通 `.o` 与 `.a` 的课堂算法角色不同。
- 课件列出的 library size/member counts 属于该讲示例时点，不应外推为恒定版本事实。

## 本段掌握检查

  **答：** 前者让使用者链接巨大 object，time/space 低效；后者虽可只选所需函数，却让 command line/Makefile 管理负担过重 [00:49:50–00:50:45]。

# 第 7 段：Shared libraries 与动态链接的两个时机

**时间范围：** 00:59:34–01:09:34  
**对应课件：** [课件: 13-linking.pptx p.30]–[课件: 13-linking.pptx p.35]

## 本段在整讲中的作用

本段先用上一段的 order error 强调 static archive 的实践陷阱，再从 static library 的 duplication 与更新成本推出 shared library。老师区分 load-time 和 run-time dynamic linking：前者由 loader 与 dynamic linker 自动完成；后者由程序调用 `dlopen`/`dlsym` 主动选择 library 与 function。到段末，运行时例子刚获得 `libvector.so` handle 并准备按名字查找 `addvec`，下一段继续完成 function-pointer 调用。

## 教学展开

### 1. 收束 static-library order error [00:59:34–00:59:53]

错误顺序在 command line 结束时仍留有 unresolved `libfun`，于是产生 cryptic linker error；若不知道从左到右 ordering rule，很难从报错判断真正原因 [00:59:34–00:59:50] [课件: 13-linking.pptx p.30]。

### 2. 从 static 的缺点推出 shared libraries [00:59:53–01:01:00]

老师把 static libraries 称为 old-fashioned solution，并提出 modern shared/dynamic libraries [00:59:53–01:00:04]。

Static linking 的问题包括 [课件: 13-linking.pptx p.31]：

1. 每个 stored executable 都包含自己使用的 library routines，例如大量 programs 各自带一份 `printf` [01:00:04–01:00:29]。
2. Running processes 中也会出现重复；shared libraries 让多个 processes share library routine 的一份 code [01:00:29–01:00:48]。
3. 课件还指出，system library 的小 bug fix 会要求静态链接的 applications 显式 relink [课件: 13-linking.pptx p.31]。

### 3. 定义 shared library 与两个 linking times [01:01:00–01:02:43]

- Shared library 包含 code/data，但这些内容不在生成 executable 时复制并完成链接；references 的处理推迟到 executable 被装入 memory，甚至推迟到 program 已运行之后 [01:01:00–01:01:56]。
- Shared library、dynamic link library、Windows DLL、Linux `.so` 在此指同一类机制 [01:02:02–01:02:12] [课件: 13-linking.pptx p.31]。
- **Load-time linking：** executable 第一次被加载运行时发生；Linux 常由 `ld-linux.so` 自动处理，`libc.so` 通常以此方式链接 [课件: 13-linking.pptx p.32]。
- **Run-time linking：** program 已开始执行后主动发生；Linux 使用 `dlopen()` interface [课件: 13-linking.pptx p.32]。
- Shared routines 可被 multiple processes share；老师要求暂时接受，等 virtual memory 课程再解释 [01:02:21–01:02:40]。

### 4. 创建 `libvector.so` [01:02:43–01:03:44]

同样使用 `addvec.c` 与 `multvec.c`，但不再用 `ar` 生成 `.a`，而是：

```text
gcc -shared -o libvector.so addvec.c multvec.c
```

`-shared` 指示 GCC 生成 `libvector.so` [01:02:50–01:03:26] [课件: 13-linking.pptx p.33]。C standard library 对应的 shared object 是 `libc.so`，其中含 `printf` 等 routines [01:03:26–01:03:39]。

### 5. Link time 只形成 partially linked executable [01:03:44–01:04:46]

`main2.c` 仍调用 `addvec`，先编译为 `main2.o` [01:03:44–01:03:49]。Static linker 此时：

- 不把 `addvec`、`printf` code 复制到 executable。
- 在 symbol/relocation information 中留下“load 时修补这些 references”的记录。
- 记录 program 需要哪些 `.so` files [01:04:00–01:04:33] [01:05:09–01:05:17]。

因此磁盘上的 `prog2l` 是 partially linked executable，不能按前一段 static executable 的方式直接开始执行 [01:04:26–01:04:39] [课件: 13-linking.pptx p.33]。

### 6. Loader 与 dynamic linker 在 load time 完成工作 [01:04:46–01:06:01]

1. Loader（老师在此指出相关 system call 是 `execve`）把 executable 和它所需的 `.so` files 放入 memory [01:04:46–01:05:17]。
2. Loader 调用 dynamic linker `ld-linux.so` [01:05:17–01:05:26] [课件: 13-linking.pptx p.33]。
3. Dynamic linker 对 `addvec`、`printf` 等 unresolved references 做类似 static linker relocation 的 fix-up；它们的 concrete addresses 到 program load 时才确定 [01:05:26–01:05:53]。
4. 完成后得到 memory 中 fully linked、可直接执行的 program [01:05:53–01:06:01]。

### 7. 课堂问答：`#include` 不属于 linking [01:06:01–01:07:06]

学生提问原句残缺，但老师明确回答：`#include` 与 `#define` 由 C preprocessor 处理，preprocessor 把 included file 展开成新的 C source；等 linker 运行时，这些 directives 早已不存在 [01:06:25–01:07:06]。这把“header inclusion”和“library code linking”两个经常混淆的阶段分开。

### 8. 转向 run-time dynamic linking [01:07:11–01:08:24]

Program 可以在运行中任意决定从某个 `.so` 加载、链接并调用 function，Linux 提供 `dlopen` interface [01:07:11–01:07:45]。例子仍要调用 `libvector.so` 中的 `addvec`，但 `dll.c` 编译时没有静态声明它依赖 `libvector`，可像 standalone C program 一样编译 [01:07:45–01:08:18]。

Program 声明 function pointer：

```c
void (*addvec)(int *, int *, int *, int);
```

其参数对应两个 input arrays、一个 output array 与 size [01:08:24–01:08:38] [课件: 13-linking.pptx p.34]。

### 9. `dlopen` 获得 library handle [01:08:38–01:09:34]

```c
handle = dlopen("./libvector.so", RTLD_LAZY);
```

[课件: 13-linking.pptx p.34]

- `dlopen` 动态装入 `libvector.so`，`RTLD_LAZY` 表示把 function-reference resolution 延后到真正需要时 [01:08:38–01:09:09]。
- 返回值是后续 calls 使用的 handle；null 表示 error，例如 `.so` 不存在，可用 `dlerror()` 报告 [01:09:09–01:09:24]。
- 打开成功后，老师开始说明用 `dlsym(handle, ...)` 按 function name 查找；具体返回值与调用在下一段 [01:09:24–01:09:34]。

## 概念、符号与推导

### Static 与 shared 的关键差别

| 时点 | Static library | Shared library（load-time） |
|---|---|---|
| Build/link command | 从 `.a` 复制所需 member code | 记录 needed `.so` 与 unresolved relocation info |
| 磁盘 executable | Fully linked（本讲模型） | Partially linked |
| Program load | 直接装入前面已修补的 code/data | Loader 装入 executable/`.so`，dynamic linker 修补 references |
| Routine copies | 各 executable/process 可能重复 | Library routines 可跨 processes share |

### Load-time pipeline

```text
main2.c -> main2.o
main2.o + references to libc.so/libvector.so
  -> static linker records dependencies/relocations
  -> prog2l (partially linked on disk)
  -> loader execve
  -> dynamic linker ld-linux.so resolves and relocates
  -> fully linked executable in memory
```

### Run-time API 前半链

```text
dlopen("./libvector.so", RTLD_LAZY)
  -> handle or NULL/error
handle + symbol-name string
  -> dlsym ...（下一段完成）
```

本段无数值公式推导；核心推导是把 resolution/relocation 的**执行时机**从 build time 延迟到 load time 或 run time。

## 例子与课堂提示

1. **`printf` duplication：** 用最常见 library function 说明 static executables/running programs 重复 code 的成本 [01:00:12–01:00:48]。
2. **同一个 `libvector`：** `.a` 与 `.so` 版本都由 `addvec/multvec` 构造，使差异聚焦在 packaging/linking time，而非 API 本身 [01:02:43–01:03:26]。
3. **`#include` 问答：** Header 展开发生在 preprocessor，不能用它解释 linker 怎样找到 `printf` implementation [01:06:25–01:07:06]。
4. **Null handle：** `dlopen` 的 failure path 是例子的一部分；动态选择 library 必须检查装入是否成功 [课件: 13-linking.pptx p.34]。

## 易混点与边界

- Shared library 并非“不链接”，而是把一部分 symbol resolution/relocation 延迟到 load/run time。
- 磁盘上的 partially linked executable 与 memory 中 dynamic linker 完成后的 fully linked program 是两个不同状态。
- Loader 与 dynamic linker 不是同一个角色：loader 组织装入并调用 dynamic linker，后者解析 `.so` symbols 和修补 references [课件: 13-linking.pptx p.33]。
- `#include <stdio.h>` 提供 declarations，经 preprocessor 展开；它不把 `printf` machine code 放入程序。
- `RTLD_LAZY` 的课堂解释只涉及延迟 function-reference resolution；不补充本讲未涉及的 flags 或 loader policy。
- 本段结束时只完成 `dlopen` 和 `dlsym` 的引入，尚未讲 `dlsym` 返回的 pointer 如何直接调用及 `dlclose`。

## 本段掌握检查

1. **问：Static libraries 的三项缺点是什么？**  
  **答：** Stored executables 重复 library routines、running programs 重复，以及 library bug fix 需要 applications relink [课件: 13-linking.pptx p.31]。
2. **问：Load-time dynamic linking 中 static linker、loader、dynamic linker 分别做什么？**  
  **答：** Static linker 留 dependency/relocation info；loader 装入 executable 和 `.so`；dynamic linker 在 memory 中解析并修补 references [01:03:44–01:06:01]。
3. **问：为什么 `#include` 在 linker 阶段已不存在？**  
  **答：** Preprocessor 早先已把 included file 展开为 C source，linker 接触的是后续 object files [01:06:25–01:07:06]。
4. **问：Run-time example 在 compile time 为什么不必知道 `libvector.so`？**  
  **答：** Program 运行后通过 `dlopen` 选择 `.so`，并用 function pointer 接收按名字查到的 function [01:07:11–01:08:38]。
5. **问：`dlopen("./libvector.so", RTLD_LAZY)` 返回什么，怎样识别失败？**  
  **答：** 返回供后续 `dlsym` 使用的 handle；null 表示失败，例子调用 `dlerror()` 输出原因 [01:08:38–01:09:24]。

# 第 8 段：Library interpositioning 的三条实现路径

**时间范围：** 01:09:34–01:19:33  
**对应课件：** [课件: 13-linking.pptx p.35]–[课件: 13-linking.pptx p.47]

## 本段在整讲中的作用

本段先完成上一段的 run-time dynamic linking 例子：`dlsym` 按名字返回 `addvec` function pointer，程序像调用普通 function 一样调用它。随后课程进入整讲的案例 library interpositioning，用同一个 `malloc(32)`/`free(p)` 程序依次展示 compile-time、link-time、load/run-time 三种截获路径。三者目标一致：让原本对 library function 的 call 先进入 wrapper，执行 tracing/checking，再调用真正的 library implementation；差别在于改写 reference 的时机和需要掌握的程序制品。

## 教学展开

### 1. 用 `dlsym` 完成 run-time function lookup [01:09:34–01:09:59]

打开 `.so` 获得 `handle` 后，把 handle 与 function-name string 传给 `dlsym`：

```c
addvec = dlsym(handle, "addvec");
if ((error = dlerror()) != NULL) {
    fprintf(stderr, "%s\n", error);
    exit(1);
}
```

[课件: 13-linking.pptx p.35]

`dlsym` 返回指向所查 function 的 pointer；程序随后直接用 function-pointer name 调用 `addvec(x,y,z,2)`，就像调用 statically defined function，最后用 `dlclose(handle)` unload shared library [01:09:34–01:09:59] [课件: 13-linking.pptx p.35]。

### 2. Function-pointer 课堂问答与 linking recap [01:10:13–01:11:06]

### 3. 定义 library interpositioning [01:11:06–01:12:10]

Library interpositioning 是截获 arbitrary library function calls 的 linking technique [01:11:16–01:11:34] [课件: 13-linking.pptx p.38]。典型流程：

1. Program 表面上调用某 library function。
2. Linking mechanism 让 call 先解析到 wrapper。

4. Wrapper 再调用真正的 function，保持原有功能 [01:11:34–01:11:56]。

```c

```

### 6. Compile-time interpositioning：用 header macros 改写 calls [01:14:13–01:16:08]

先实现 wrappers [课件: 13-linking.pptx p.42]：

- `mymalloc(size)` 调用真正的 `malloc(size)`，打印 requested size 与 returned pointer，再返回 pointer。
- `myfree(ptr)` 调用真正的 `free(ptr)`，打印 freed pointer。

再提供 current-directory `malloc.h` [课件: 13-linking.pptx p.43]：

```c
#define malloc(size) mymalloc(size)
#define free(ptr)    myfree(ptr)
void *mymalloc(size_t size);
void myfree(void *ptr);
```

Build 时使用 `-I.`：

```text
gcc -Wall -DCOMPILETIME -c mymalloc.c
gcc -Wall -I. -o intc int.c mymalloc.o
```

`-I.` 让 preprocessor 先找到 current directory 的 `malloc.h`；宏把 application 中 apparent `malloc/free` calls 展开成 `mymalloc/myfree` [01:14:36–01:15:56]。运行 `intc` 后 wrapper 输出 `malloc(32)=address` 与 `free(address)` [课件: 13-linking.pptx p.43]。

### 7. Link-time interpositioning：用 `--wrap` 改写 symbol resolution [01:16:08–01:17:53]

Compile-time 方法不改 application source，但需要用替代 header 重新 compile。Link-time 方法可从 relocatable objects 开始，不依赖这种预处理改写 [01:16:08–01:16:31]。

Wrappers 使用 linker 约定名称 [课件: 13-linking.pptx p.44]：

```c
void *__wrap_malloc(size_t size) {
    void *ptr = __real_malloc(size);
    printf("malloc(%d) = %p\n", (int)size, ptr);
    return ptr;
}
```

`__wrap_free` 同理调用 `__real_free`。Link command：

```text
gcc -Wall -Wl,--wrap,malloc -Wl,--wrap,free -o intl int.o mymalloc.o
```

[课件: 13-linking.pptx p.45]

- GCC 的 `-Wl` 把后面的 argument 交给 linker，并把 comma 分隔转换为 linker arguments [01:16:44–01:17:07]。
- `--wrap,malloc` 指示 special symbol resolution：`malloc -> __wrap_malloc`，`__real_malloc -> malloc` [01:17:12–01:17:46]。
- 因此 application call 进入 wrapper，而 wrapper 内的 `__real_malloc` 最终进入 libc implementation。

### 8. Load/run-time interpositioning：只要求 executable [01:17:53–01:19:33]

老师强调这是最强的边界：不需要 application source 或 `.o`，只需 executable，就能在 program load/run 时截获 library calls [01:17:53–01:18:10]。

Shared wrapper 自己定义名为 `malloc` 的 function，并在内部查找下一处真正定义 [课件: 13-linking.pptx p.46]：

```c
mallocp = dlsym(RTLD_NEXT, "malloc");
ptr = mallocp(size);
```

`RTLD_NEXT` 表示跳过当前 wrapper，在 dynamic linker normally searched 的下一个位置取 libc `malloc` address [01:18:18–01:18:59]。返回的 `mallocp` 是 function pointer；wrapper 调用它取得 block，再打印 size/address [01:18:59–01:19:07]。`free` wrapper 同样使用 `dlsym(RTLD_NEXT,"free")`，先调用真实 `free` 再打印 [01:19:07–01:19:22] [课件: 13-linking.pptx p.47]。

本段结束时老师刚开始说明怎样 build runtime version `intr`；`.so` build 与 `LD_PRELOAD` command 在下一段完成 [01:19:22–01:19:33]。

## 概念、符号与推导

### Run-time dynamic call 的完整 API 链

```text
handle = dlopen("./libvector.so", RTLD_LAZY)
addvec = dlsym(handle, "addvec")
addvec(x, y, z, 2)
dlclose(handle)
```

每一步都检查 `dlerror`/return status [课件: 13-linking.pptx p.34] [课件: 13-linking.pptx p.35]。

### 三种 interposition 的 reference 改写点

| 时机 | 机制 | Apparent `malloc` 最终先到哪里 | 最低所需 application 制品 |
|---|---|---|---|
| Compile time | Local header macro + `-I.` | `mymalloc` | 可重新 preprocess/compile 的 source |
| Link time | `-Wl,--wrap,malloc` | `__wrap_malloc` | Relocatable object files |
| Load/run time | Dynamic lookup order + wrapper `.so` | Wrapper-defined `malloc` | Executable |

### 真函数回边

```text
compile time: mymalloc      -> malloc
link time:    __wrap_malloc -> __real_malloc -> malloc
load/run:     malloc wrapper -> dlsym(RTLD_NEXT,"malloc") -> libc malloc
```

本段无数学公式推导；推导重点是同一个 semantic call 在不同生命周期阶段如何被重定向，并怎样避免 wrapper 递归调用自己。

## 概念、符号与推导

### Runtime interposition 的完整 resolution chain

```text
LD_PRELOAD=./mymalloc.so ./intr
  -> dynamic linker searches mymalloc.so first
  -> intr's malloc reference resolves to wrapper malloc
  -> wrapper calls dlsym(RTLD_NEXT,"malloc")
  -> lookup continues after wrapper and finds libc malloc
  -> real allocation occurs; wrapper logs result
```

`free` 路径完全同构。

### 三种时机的最终统一

```text
compile time: source-level token/reference rewrite by macros
link time:    relocatable-object symbol resolution rewrite by --wrap
load/run time: dynamic symbol search-order rewrite by LD_PRELOAD
```

三者的共同不变量是：apparent library call 先进入 wrapper，wrapper 再显式抵达 real function。本段无数学公式推导。

## 例子与课堂提示

1. **Build command 不提 wrapper：** `gcc -Wall -o intr int.c` 服务于证明运行时方法不需要修改 source、也不需要 application `.o` 的特殊 relink [01:19:41–01:19:55]。
