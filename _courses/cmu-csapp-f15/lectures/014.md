## 老师的教学主线

本讲严格沿以下问题链推进：

1. **普通控制流为什么不够**：branch/jump/call/return 只能依据 program state，真实系统还要响应磁盘、网络、键盘、非法指令和 timer 等 system events。[00:00:24-00:02:31]
2. **ECF 在哪些层级出现**：从硬件/内核共同实现的 exceptions，上移到 context switch、signals，再到 C runtime 的 nonlocal jumps；本讲聚焦前两者。[00:02:36-00:04:53] [课件: 14-ecf-procs.pptx p.5]
3. **最低层怎样把控制交给内核**：event 触发 exception，异常号索引 exception table，handler 处理后选择当前指令、下一指令或 abort。[00:05:02-00:07:46]
4. **不同事件为什么有不同返回结果**：external interrupt 返回下一条；intentional trap 完成 system call 后继续；recoverable fault 装页并重试；unrecoverable event 中止或发信号。[00:07:47-00:17:52]
5. **从异常怎样过渡到进程**：timer/fault/trap 让内核取得控制，scheduler 才可能保存 A context、恢复 B context；这正是 process context switch 形式的 ECF。[00:18:02-00:28:17]
6. **程序怎样控制进程**：先立返回值检查规则，再按 PID、状态、终止、`fork` 展开创建和生命周期。[00:28:17-00:39:49]
7. **多次 `fork` 怎样推理**：不能猜全序，改用 process graph 保存偏序，再以 topological sort 验证输出。[00:39:49-00:48:09]
8. **进程终止后为什么还没消失**：退出状态要交给 parent，所以形成 zombie；`wait`/`waitpid` 同时承担同步与 reaping。[00:48:10-00:59:55]
9. **怎样在 process 中运行不同 program**：`fork` 只复制，`execve` 才替换 program image；初始 stack 把 `argc/argv/envp` 交给新程序。[00:59:55-01:08:52]
10. **为什么 Unix 保留两步接口**：可只创建同代码 replicas，也可在 `fork`/`execve` 之间配置 child；最后用四组 API 总结 process control。[01:08:52-01:11:49]

## 核心概念与依赖关系

```text
physical control flow
  + system-state changes
          |
          v
Exceptional Control Flow
  |
  +-- exceptions
  |     +-- asynchronous: interrupts -> I_next
  |     +-- synchronous
  |           +-- trap -> I_next
  |           +-- fault -> I_current or abort
  |           +-- abort -> terminate
  |
  +-- process context switch
        exception -> kernel -> scheduler
        -> save registers/address space context
        -> restore another process context
                    |
                    v
          logical control flows + private address spaces
                    |
                    v
              concurrent processes

process control
  +-- getpid/getppid
  +-- exit                    -> terminate
  +-- fork                    -> create child
  |     +-- process graph     -> partial order / feasible output
  |     +-- child terminates  -> zombie
  |                              -> wait/waitpid -> reap
  +-- execve                  -> replace program in current process
        ^
        |
   standard pattern: fork child -> child execve
```

依赖顺序是明确的：先理解 exception 如何让内核取得控制，才能解释 scheduler 和 context switch；先区分复制但分离的 parent/child，才能画 process graph；先理解 terminated child 为什么保留状态，才能理解 `wait` 既同步又回收；先区分 process 与 program，才能准确说出 `fork` 创建 process、`execve` 替换 program。[课件: 14-ecf-procs.pptx p.7] [课件: 14-ecf-procs.pptx p.26] [课件: 14-ecf-procs.pptx p.34] [课件: 14-ecf-procs.pptx p.42] [课件: 14-ecf-procs.pptx p.49]

## 关键推导、例子与结论边界

1. **异常 handler 的三类结局**：`event -> handler -> {I_current, I_next, abort}`。这是一条控制流分类，不是所有 exception 都 abort。[00:05:42-00:06:42] [课件: 14-ecf-procs.pptx p.7]
2. **异常表查找**：`exception table[k] -> handler k`。`k` 是 event 类型的唯一编号和表索引；课堂没有给表项地址公式或布局。[00:07:10-00:07:46] [课件: 14-ecf-procs.pptx p.8]
3. **同步异常三分法**：trap 有意并到 `I_next`；fault 无意但可能恢复，重试 `I_current` 或 abort；abort 无意且不可恢复。[00:10:18-00:13:23] [课件: 14-ecf-procs.pptx p.10]
4. **`syscall` 寄存器例子**：`open` 的 ID 2 放 `%rax/%eax`，参数按 `%rdi,%rsi,%rdx,%r10,%r8,%r9`，返回仍在 `%rax`。负值表示错误；课堂未推导 `cmp $0xfffffffffffff001` 的常量边界。[00:13:23-00:15:43] [课件: 14-ecf-procs.pptx p.12]
5. **两个 `movl` 的分流**：`a[500]` 地址有效但缺页，装页后重执行；`a[5000]` 地址无效，没有页面可装，内核发 `SIGSEGV`。[00:15:43-00:17:52] [课件: 14-ecf-procs.pptx p.13] [课件: 14-ecf-procs.pptx p.14]
6. **Context switch**：异常进入内核 -> 保存当前寄存器 -> scheduler 选择下一进程 -> 载入其寄存器 -> 切换地址空间 -> 从暂停处恢复。Kernel 是共享代码，不是单独 process。[00:21:59-00:28:17] [课件: 14-ecf-procs.pptx p.20] [课件: 14-ecf-procs.pptx p.21] [课件: 14-ecf-procs.pptx p.22] [课件: 14-ecf-procs.pptx p.26]
7. **并发判定**：A/B、A/C 的 logical flow 时间区间重叠，所以并发；B 完成后 C 才开始，所以 B/C 顺序。该定义不依赖 core 数量。[00:24:04-00:26:15] [课件: 14-ecf-procs.pptx p.24]
8. **错误退出状态的课堂纠正**：[课件: 14-ecf-procs.pptx p.28]-[课件: 14-ecf-procs.pptx p.30] 的 error path 写 `exit(0)`；学生指出后，老师确认通常应采用非零，例如 `exit(1)`。笔记保留课件与口述差异。[00:30:23-00:30:48]
9. **基本 `fork`**：parent/child 都从独立的 `x == 1` 出发，child 得 2、parent 得 0；输出顺序不可预测，但数值由各自 flow 决定；两者都能使用复制的 `stdout` descriptor。[00:35:27-00:39:44] [课件: 14-ecf-procs.pptx p.35]
10. **Process graph**：顶点是语句执行，边是 happens-before；任一拓扑排序是 feasible total order。它允许交错，不允许逆转单条 flow 的边。[00:40:37-00:44:08] [课件: 14-ecf-procs.pptx p.36]
11. **两次连续 `fork` 计数**：进程数 `1 -> 2 -> 4`，故 `L0/L1/Bye` 分别打印 1/2/4 次；数量正确仍不够，还要满足偏序。[00:44:08-00:45:35] [课件: 14-ecf-procs.pptx p.39]
12. **Zombie 边界**：terminated child 保留 exit status/OS table state；active orphan 仍执行，不是 zombie；parent 退出不自动杀死 child。[00:48:10-00:54:12] [课件: 14-ecf-procs.pptx p.42] [课件: 14-ecf-procs.pptx p.44]
13. **`wait` 的两个结果**：函数返回 terminated child PID，`child_status` 指针接收状态；先 `WIFEXITED`，再 `WEXITSTATUS`。普通 `wait` 取任意 child，`waitpid` 可指定 PID。[00:54:12-00:59:55] [课件: 14-ecf-procs.pptx p.45] [课件: 14-ecf-procs.pptx p.47] [课件: 14-ecf-procs.pptx p.48]
14. **新程序栈**：`argc` 在 `%rdi`，`argv` 在 `%rsi`，`envp` 在 `%rdx`；后两者是以 `NULL` 结束的 pointer arrays，指向 null-terminated strings。[01:03:06-01:05:58] [课件: 14-ecf-procs.pptx p.50]
15. **`execve` 边界**：替换当前 program 的 code/data/stack，新建 heap/stack，但保留同一 process 的 PID/open files；成功不返回，错误才返回。课件还列 signal context，口述未展开其字段。[01:02:06-01:03:26] [课件: 14-ecf-procs.pptx p.49]
16. **`fork` + `execve` 分离**：只 fork 可得到运行相同代码的 server replicas；两步之间还可执行 child-specific 配置。课堂只举 block/unblock signals，不讲具体 signal-mask 规则。[01:06:23-01:10:33] [课件: 14-ecf-procs.pptx p.51]

## 易错点与待核对项

1. 不要把 exception 等同于错误或 abort；trap 可以是程序有意的 system call，fault 也可能恢复。
2. 不要把 external interrupt 写成当前 instruction 引起；最后总结处 transcript 的双重 “internally” 与课件冲突。[需回听 01:10:51] [课件: 14-ecf-procs.pptx p.52]
3. 不要把 system-level function 与 `syscall` instruction 混为一层；`open` wrapper 负责准备寄存器并执行指令。
4. 不要把 process 与 program/processor 混淆，也不要把 kernel 当作单独 process。
5. 不要把 concurrency 限定为多核同瞬间执行；本讲按 logical flows 是否在时间上重叠定义。
6. 不要把 waiting-to-be-scheduled 误归为 stopped；本讲的 running 包括正在执行和可被调度等待执行。
7. 不要认为 `fork` 调用两次或 parent 一定先执行；它一次调用、两处返回，父子调度顺序无保证。
8. 不要仅凭输出行数判断多 `fork` 程序可行；必须检查 process graph 的 happens-before 边。
9. 不要把 orphan 与 zombie 画等号，也不要认为 parent 退出会级联杀死 active child。
10. 不要把 `wait` 返回值当 exit status；返回的是 PID，状态由指针与宏解释。
11. 不要认为 `execve` 创建 process 或成功后会执行下一行；它替换当前 program，成功不返回。
12. `waitpid` options、完整 wait-status 编码、virtual memory 内部实现、signal 语义都被老师留给教材或后续讲次，本讲笔记不外推。
13. 关键 ASR 疑点已逐项保留在各节“待核对项”：`open`/`read` 号 [需回听 00:15:02]、`init` [需回听 00:52:28]、`waitpid` [需回听 00:59:21]、`argc/argv/envp` [需回听 01:05:11]、总结中的 `execve` [需回听 01:11:41]。

# 第 1 节：从物理控制流到异步异常

- 时间范围：00:00:00-00:09:56
- 对应主题：控制流、异常控制流层级、异常、异常表、异步异常（中断）
- 主要课件：[课件: 14-ecf-procs.pptx p.1] 至 [课件: 14-ecf-procs.pptx p.9]

## 本段在整讲中的作用

本段从处理器最朴素的工作方式出发：机器启动后，每个核逐条读取并执行指令，这条实际执行的指令序列就是物理控制流。老师先回顾此前用于改变控制流的分支、跳转、过程调用和返回，再指出它们只能响应程序状态，无法独立响应磁盘或网络数据到达、`Ctrl-C`、非法指令、定时器到期等系统状态变化。由此引出本讲核心问题：系统怎样在正常程序控制流之外，把控制权交给能够处理系统事件的代码。[00:00:00-00:02:24] [课件: 14-ecf-procs.pptx p.1]-[课件: 14-ecf-procs.pptx p.4]

随后老师建立异常控制流（Exceptional Control Flow, ECF）的完整层级，把异常、进程上下文切换、信号和非本地跳转放在同一框架下，再聚焦最低层的“异常”。本段完成异常的一般处理模型、异常表索引机制以及异步异常（中断）的定义，为下一段比较 trap、fault、abort，并分析系统调用和页故障做准备。[00:02:25-00:09:56] [课件: 14-ecf-procs.pptx p.5]-[课件: 14-ecf-procs.pptx p.9]

## 教学展开

1. **从逐条执行定义控制流。** 老师先说明，从启动到关机，CPU 所做的事情就是一次读取并解释一条指令；多核机器的每个核也各自逐条执行。指令实际经过的序列称为控制流，其中硬件真正执行出的序列称为物理控制流（physical control flow）。通常它顺序前进，但并非永远只执行内存中的下一条指令。[00:00:24-00:01:14] [课件: 14-ecf-procs.pptx p.3]

2. **回顾已有的改流机制，并指出能力边界。** 此前学过的两组机制是 jumps/branches 与 call/return。分支会检查条件码，再根据比较结果决定是否转移，因此这些机制响应的是程序状态。真实系统还必须响应系统状态，例如磁盘或网络数据到达、用户键入 `Ctrl-C`、程序执行非法指令，以及系统定时器到期；只靠普通分支和调用返回并不足够。[00:01:15-00:02:24] [课件: 14-ecf-procs.pptx p.4]

3. **由系统状态变化引出 ECF。** 因为上述事件发生在程序正常控制流之外，系统需要“异常控制流”。老师把 event 解释为状态的变化，并强调 ECF 存在于系统的所有层级。[00:02:25-00:03:17] [课件: 14-ecf-procs.pptx p.5]

4. **按实现层级给出 ECF 分类。** 最低层是 exceptions：响应低层系统事件，由硬件与操作系统软件共同实现。更高一层是 process context switch：当前进程会被暂停，机器转而执行另一进程的指令，由操作系统软件和硬件定时器支持。再高一层是 signals，由操作系统软件实现；最高一层是 C 的 `setjmp()`/`longjmp()` 非本地跳转，由 C 运行时库实现，可打破“被调函数只能返回调用者”的普通调用/返回模式。信号与非本地跳转留到下一讲，本讲处理异常和进程。[00:03:18-00:04:53] [课件: 14-ecf-procs.pptx p.5]-[课件: 14-ecf-procs.pptx p.6]

5. **定义异常及内核。** 异常是响应某个 event，把控制从用户代码转移到操作系统内核。内核不是“操作系统所有程序”的同义词，而是操作系统中始终驻留内存的部分；列文件、改目录等程序可以属于操作系统工具，但不因此都是内核。[00:05:02-00:05:41] [课件: 14-ecf-procs.pptx p.7]

6. **沿控制权路径解释异常处理。** 用户代码执行到当前指令 `I_current` 附近时，处理器状态发生变化；异常把控制交给内核中的 exception handler，内核执行 exception processing。处理后只有三类去向：返回并重新执行 `I_current`、返回并执行下一条 `I_next`，或者中止当前程序。老师提前指出，重执行当前指令对页故障和虚拟内存尤其重要。[00:05:42-00:06:42] [课件: 14-ecf-procs.pptx p.7]

7. **拆分硬件与软件的职责。** 真正修改程序计数器（PC/IP）、完成控制转移的是硬件；异常发生后运行哪段处理代码，则由操作系统内核预先建立和决定。因此异常不是“纯硬件”或“纯软件”机制，而是二者协作。[00:06:43-00:07:09] [课件: 14-ecf-procs.pptx p.7]

8. **用异常表把事件类型映射到处理程序。** 每种 event 有唯一异常号 `k`。硬件用 `k` 索引 exception table（也称 interrupt vector），取出异常处理程序 `handler k` 的地址；此后每次异常 `k` 发生，都调用同一个 `handler k`。[00:07:10-00:07:46] [课件: 14-ecf-procs.pptx p.8]

9. **先讲第一类异常：异步异常。** 异步异常由处理器外部事件引起，也称 interrupts。外部设备通过置位处理器的 interrupt pin 通知处理器；处理程序完成后返回“下一条”指令。因此从用户程序视角看，执行中间像插入了一小段处理程序，随后原程序继续，通常不会改变其正常执行结果。[00:07:47-00:09:11] [课件: 14-ecf-procs.pptx p.9]

10. **用定时器说明内核如何重新取得控制。** 外部定时器每隔几毫秒触发一次中断，并对应专门的异常号。这样即使用户程序进入无限循环，内核仍能周期性取得机器控制权，再决定调度新进程还是让当前进程继续。老师随后开始补充外部设备 I/O 中断，完整说明跨入下一段。[00:09:12-00:09:56] [课件: 14-ecf-procs.pptx p.9]

## 概念、符号与推导

### 1. 控制流与物理控制流

- **控制流（control flow / flow of control）**：CPU 从启动到关机实际读取、解释的一系列指令。
- **物理控制流（physical control flow）**：硬件层面真实出现的指令执行序列；多核时每个核各有自己的序列。[00:00:36-00:01:08] [课件: 14-ecf-procs.pptx p.3]
- **已有改变机制**：jumps/branches、call/return；它们依据程序状态改变下一条指令。[00:01:15-00:01:55] [课件: 14-ecf-procs.pptx p.4]

### 2. 异常控制流的层级

| 层级 | 机制 | 本段给出的实现主体 | 课堂中的控制流变化 |
|---|---|---|---|
| 低层 | Exceptions | 硬件 + OS 软件 | 系统 event 触发到内核的控制转移 |
| 较高层 | Process context switch | OS 软件 + 硬件定时器 | 一个进程暂停，改为执行另一进程 |
| 更高层 | Signals | OS 软件 | 本讲暂不展开 |
| C 运行时层 | `setjmp()` / `longjmp()` | C runtime library | 打破普通 call/return 返回关系 |

[00:02:36-00:04:53] [课件: 14-ecf-procs.pptx p.5]

### 3. 异常处理路径

本段的符号关系可写成：

`event -> exception -> exception handler -> {重新执行 I_current；执行 I_next；abort}`

其中 event 是处理器状态的变化；异常负责把控制转入内核，handler 完成 exception processing。该表达只是课堂流程的结构化重述，不是额外的数学公式。[00:05:36-00:06:42] [课件: 14-ecf-procs.pptx p.7]

### 4. 异常号与异常表

对异常号 `k`，硬件执行的查找关系是：

`exception table[k] -> handler k 的入口地址`

`k` 是每类 event 的唯一编号，也是异常表（interrupt vector）的索引。老师没有推导异常表的地址计算公式，也没有给出表项宽度；本段无数值公式推导。[00:07:10-00:07:46] [课件: 14-ecf-procs.pptx p.8]

### 5. 异步异常（interrupt）

- **原因**：处理器外部发生状态变化，而不是当前指令有意或无意直接造成。
- **通知方式**：外部设备置位 processor interrupt pin。
- **返回位置**：处理完后返回 `I_next`。
- **课堂实例**：定时器中断；磁盘 DMA 完成后的 I/O 中断；键盘 `Ctrl-C`；网络包或磁盘数据到达。[00:07:47-00:09:56] [课件: 14-ecf-procs.pptx p.9]

## 常见误解与边界

- 不要把“控制流”误解为源代码的静态排列；这里首先指 CPU 实际执行出的指令序列。[00:00:51-00:01:08] [课件: 14-ecf-procs.pptx p.3]
- 不要认为 branches/jumps/call/return 已足以处理所有控制变化；它们响应程序状态，ECF 要解决的是系统状态变化。[00:01:15-00:02:31] [课件: 14-ecf-procs.pptx p.4]
- 不要把 kernel 等同于整个操作系统软件集合；老师在此采用“始终驻留内存的 OS 部分”这一界定。[00:05:02-00:05:35] [课件: 14-ecf-procs.pptx p.7]
- 不要把 exception 与 abort 画等号。一般异常处理后可能重执行当前指令、继续下一条指令，也可能中止；具体取决于异常类别。[00:06:16-00:06:42] [课件: 14-ecf-procs.pptx p.7]
- 不要说异常完全由内核软件完成：硬件负责实际控制转移，内核负责建立并提供处理程序。[00:06:43-00:07:09] [课件: 14-ecf-procs.pptx p.7]
- 不要把 interrupt 理解为当前指令内部引起的异常；本段的定义明确要求事件来自处理器外部，并通常返回下一条指令。[00:07:47-00:08:48] [课件: 14-ecf-procs.pptx p.9]

### 1. 为什么分支、跳转、调用和返回不足以构成一个有用系统的全部控制转移机制？

**答：**它们主要响应程序内部状态；系统还必须响应磁盘/网络数据到达、`Ctrl-C`、非法指令和定时器到期等系统状态变化，因此需要 ECF。[00:01:15-00:02:31] [课件: 14-ecf-procs.pptx p.4]

### 2. 本讲给出的四层 ECF 机制及其实现主体分别是什么？

**答：**exceptions 由硬件与 OS 软件共同实现；process context switch 由 OS 软件与硬件定时器支持；signals 由 OS 软件实现；`setjmp()`/`longjmp()` 非本地跳转由 C 运行时库实现。[00:02:36-00:04:28] [课件: 14-ecf-procs.pptx p.5]

### 3. 异常处理结束后可能转向哪里？

**答：**重新执行当前指令 `I_current`、继续下一条指令 `I_next`，或者中止当前程序。[00:06:16-00:06:42] [课件: 14-ecf-procs.pptx p.7]

### 4. 异常号 `k` 如何确定要运行的处理程序？

**答：**硬件以唯一异常号 `k` 为 exception table（interrupt vector）的索引，读取 `handler k` 的入口地址；同类异常再次发生时仍调用该处理程序。[00:07:10-00:07:46] [课件: 14-ecf-procs.pptx p.8]

### 5. Timer interrupt 为什么能防止用户程序永久垄断处理器？

**答：**外部定时器每隔几毫秒触发中断，使控制进入内核；内核于是能决定调度其他进程或让当前进程继续，即使当前程序处于无限循环也不例外。[00:09:12-00:09:56] [课件: 14-ecf-procs.pptx p.9]

## 教学展开

### 1. 为什么需要 process graph

嵌套或重复 `fork` 很快变得难以凭直觉分析。不同进程间不能预设完整执行顺序，但程序本身仍强制若干局部先后关系；process graph 正是捕捉这些 partial-order constraints 的工具。[00:39:49-00:40:37] [课件: 14-ecf-procs.pptx p.36]

### 2. 定义图的组成和解释规则

1. 每个 vertex 对应一次 statement execution。[00:40:37-00:40:41]
2. 有向边 `a -> b` 表示 a happens before b。[00:40:41-00:40:46]
3. 边可以标注当前 variable value；`printf` 顶点可以标注该次输出。[00:40:46-00:40:58]
4. 每张图从一个没有入边的顶点开始。[00:40:58-00:41:04]
5. 图的任一 topological sort 都是一种 feasible total ordering。老师把拓扑排序解释为对全部顶点排成一列，并使所有边都从左指向右。[00:41:04-00:41:22] [课件: 14-ecf-procs.pptx p.36]

### 3. 把单次 `fork` 例子画成两条分支

1. parent 先令 `x = 1` 并执行 `fork`；之后 parent 和 child 各有一条 logical flow，各自打印修改后的 `x` 并退出。[00:41:22-00:41:51] [课件: 14-ecf-procs.pptx p.37]
2. 两条 flow 并发，顶点可以交错，但每条 flow 自己的边序必须保持。[00:41:51-00:42:14]
3. 课件把原图顶点重标为字母，便于只讨论顺序。[课件: 14-ecf-procs.pptx p.38]

### 4. 用拓扑序区分可行与不可行交错

1. `A, B, E, C, F, D` 是一个拓扑排序，因而可行。老师把它解释为 child 执行一个语句后被换出，parent 执行一个语句，再切回 child，最后 parent 完成。[00:42:14-00:43:10] [课件: 14-ecf-procs.pptx p.38]
2. 每执行很少语句就 context switch 在现实中不太可能，但只要不违反边，它仍是语义上可行的调度。[00:43:10-00:43:21]
3. 若一个总顺序让 child 的 `F` 出现在同一 child flow 的 `E` 之前，它就不可行，因为代码路径要求 E 先于 F；图中会出现指向左侧的边。[00:43:29-00:44:08]

### 5. 两次连续 `fork`：进程数翻倍两次

函数依次执行：

```c
printf("L0\n");
fork();
printf("L1\n");
fork();
printf("Bye\n");
```

1. `L0` 发生在第一个 `fork` 前，只打印一次。[00:44:08-00:44:26]
2. 第一次 `fork` 后有两个进程，两者都打印 `L1`，并且两者都执行第二次 `fork`。[00:44:26-00:44:49]
3. 第二次 `fork` 让两个进程各产生一个 child，最终共有四个进程，因而 `Bye` 打印四次。[00:44:49-00:45:01] [课件: 14-ecf-procs.pptx p.39]
4. 课件给出的可行输出保持了每条路径的先后关系；以 `L0` 后立刻出现 `Bye` 开头的输出不可行，因为任何进程到达 `Bye` 前，都必须先经过第一个 `fork`、打印一次 `L1`、再经过第二个 `fork`。[00:45:01-00:45:35] [课件: 14-ecf-procs.pptx p.39]

### 6. 只在 parent 中嵌套 `fork`

1. parent 打印 `L0`，执行第一个 `fork`。第一个 child 得到 0，不进入 `fork() != 0` 的 parent 分支，直接走到末尾打印 `Bye`。[00:45:35-00:46:30] [课件: 14-ecf-procs.pptx p.40]
2. original parent 得到非零返回，打印 `L1`，再执行第二个 `fork`。[00:46:30-00:46:52]
3. 第二个 child 得到 0，不进入第二层 `fork() != 0`，离开条件后打印 `Bye`；original parent 得到非零返回，打印 `L2`，最后也打印 `Bye`。[00:46:52-00:47:16]
4. 因此输出项目固定为 `L0` 一次、`L1` 一次、`L2` 一次、`Bye` 三次；具体交错受各自产生关系和 flow 内边约束。[课件: 14-ecf-procs.pptx p.40]
5. 课件的 infeasible output 把三个 `Bye` 都放在 `L2` 前。前两个可以来自两个 child，但 original parent 的 `Bye` 必须在其 `L2` 后，所以这个总顺序不可能。[00:47:19-00:48:01] [课件: 14-ecf-procs.pptx p.40]

### 7. Child 中嵌套版本留作练习

老师展示条件改为 `fork() == 0` 的 nested-in-children 版本，并明确让学生自行分析，没有在口述中完整展开。课件给出一组 feasible output 与一组 infeasible output，可作为练习答案边界；不能把课堂未讲的逐节点推导伪装成老师口述。[00:48:01-00:48:09] [课件: 14-ecf-procs.pptx p.41]

### 8. 进程终止不等于内核立刻删除

1. 进程因任何原因 terminate 后，系统仍保留少量状态，直到 parent reap 它。原因是 parent 可能需要 child 的 exit status。[00:48:10-00:48:37] [课件: 14-ecf-procs.pptx p.42]
2. 保留状态包括 exit status 和一些 OS tables；terminated 但尚未删除的进程称为 zombie。[00:48:37-00:49:08]
3. parent 调用 `wait` 或 `waitpid` reap zombie，得到退出状态信息，随后 kernel 才删除该 child 的残留状态。[00:49:08-00:49:32] [课件: 14-ecf-procs.pptx p.42]

## 概念、符号与推导

### Process graph

```text
vertex            = 一次语句执行
a -> b            = a happens before b
edge label        = 可记录当前变量值
printf label      = 可记录输出
topological sort  = 所有边从左向右的顶点总排序
```

推理规则：

```text
候选输出顺序能对应某个 topological sort -> feasible
候选输出顺序迫使某条 happens-before 边向左 -> infeasible
```

[00:40:37-00:41:22] [课件: 14-ecf-procs.pptx p.36]

### 两次连续 `fork` 的计数

课堂按控制流逐层展开：

```text
开始：1 个进程
fork #1 后：2 个进程
两个进程都执行 fork #2：4 个进程
```

因此 `L0`、`L1`、`Bye` 的打印次数分别为 1、2、4。[00:44:08-00:45:01] [课件: 14-ecf-procs.pptx p.39]

### Parent 中嵌套 `fork` 的局部约束

```text
original parent: L0 -> L1 -> L2 -> Bye_P
first child:     L0 -> Bye_C1
second child:    L0 -> L1 -> Bye_C2
```

这三条链只记录由课件代码直接强制的顺序。跨链之间除创建先后引入的边外，可以交错；尤其不能把“某个 child 的 `Bye` 可早于 `L2`”误写成“所有三个 `Bye` 都可早于 `L2`”。[00:45:35-00:48:01] [课件: 14-ecf-procs.pptx p.40]

### Zombie 与 reaping

```text
child terminates
  -> kernel 保留 exit status / OS table state
  -> child 成为 zombie
  -> parent 调用 wait 或 waitpid
  -> parent 取得状态，kernel 删除 zombie
```

[00:48:10-00:49:32] [课件: 14-ecf-procs.pptx p.42]

本段没有数学公式推导；进程数量是按每次实际执行 `fork` 的进程数逐层计数。

# 第 6 节：回收子进程与 `wait`/`waitpid`

- **时间范围**：00:49:37-00:59:34
- **对应主题**：孤儿进程、僵尸资源风险、两个终端演示、`wait` 同步、多子进程状态检查、`waitpid` 引入
- **实际课件范围**：[课件: 14-ecf-procs.pptx p.42]-[课件: 14-ecf-procs.pptx p.48]

## 本段在整讲中的作用

上一段以“parent 不 reap child 会怎样”结束。本段先回答：parent 自己终止后，未被它回收的 orphan child 最终由 PID 1 的 `init` process 回收；真正需要程序员持续处理的是 shell、server 这类长时间不退出的 parent，否则其 terminated children 会以 zombie 形式积累内核状态。[00:49:37-00:50:57] [课件: 14-ecf-procs.pptx p.42]

老师随后用两个终端演示区分两种情形：child 已终止但 parent 活着时显示为 `<defunct>` zombie；child 尚未终止时，即使 parent 已退出，child 仍继续运行，并不会自动变成 zombie 或被杀死。[00:50:57-00:54:12] [课件: 14-ecf-procs.pptx p.43] [课件: 14-ecf-procs.pptx p.44]

在现象之后，本段转入控制接口。`wait` 既让 parent 与某个 child 的终止同步，也完成 reaping 并取回状态；多 child 时，`wait` 不保证具体顺序，`waitpid` 才允许指定 PID。这个区别为后续 shell 等待前台作业、异步回收后台作业奠定基础。[00:54:12-00:59:34] [课件: 14-ecf-procs.pptx p.45] [课件: 14-ecf-procs.pptx p.46] [课件: 14-ecf-procs.pptx p.47] [课件: 14-ecf-procs.pptx p.48]

## 教学展开

### 1. Parent 先终止：orphan 交给 `init` 回收

1. 若 parent 在未回收 child 的情况下终止，系统安排最早存在、PID 为 1 的 `init` process 接手并最终 reap 该 orphan child。[00:49:37-00:50:04] [课件: 14-ecf-procs.pptx p.42]
2. 因而普通短命 parent 的 orphan children 最终有人回收；程序员尤其要关注长期运行的 parent，例如 shells 和 servers。[00:50:04-00:50:17]
3. 长期 server 可能创建数百万 children。每个 child 终止后都保留内核状态，若 parent 从不 reap，资源持续累积，老师把它类比为 memory leak，严重时可耗尽内核空间并使系统崩溃。[00:50:17-00:50:49]
4. 结论：长时间运行的程序必须使用 `wait` 或 `waitpid` 回收 children。[00:50:49-00:50:57] [课件: 14-ecf-procs.pptx p.42]

### 2. Zombie 演示：child 终止，parent 无限循环

1. `fork7` 创建 child；child 打印自己的 PID 后 `exit(0)`，parent 打印 PID 后进入 infinite loop，因此 parent 一直活着却从不 reap child。[00:50:57-00:51:29] [课件: 14-ecf-procs.pptx p.43]
2. 程序用 `&` 放到后台运行，否则当前终端会一直被无限循环占用，无法继续输入 `ps` 检查。[00:51:29-00:51:57]
3. `ps` 显示 parent PID 6639 正在运行，child PID 6640 标为 `<defunct>`，即 zombie。[00:51:57-00:52:17] [课件: 14-ecf-procs.pptx p.43]
4. 执行 `kill 6639` 终止 parent 后，再运行 `ps`，6640 已消失：parent 退出使 orphan zombie 由 PID 1 的 `init` reap。[00:52:19-00:52:37]

### 3. Non-terminating child 演示：parent 退出不杀 child

1. `fork8` 的 child 打印 PID 后进入 infinite loop；parent 打印 PID 后立即 `exit(0)`。[00:52:37-00:53:16] [课件: 14-ecf-procs.pptx p.44]
2. 运行后，parent PID 6675 已终止，但 `ps` 仍显示 child PID 6676 正在执行。child 继续运行，因为 parent 退出本身不会终止尚在运行的 child。[00:53:16-00:53:44]
3. 显式 `kill 6676` 后 child 才终止。此时它没有原 parent，因而由 `init` reap；再次 `ps` 时已不在系统中。[00:53:44-00:54:12] [课件: 14-ecf-procs.pptx p.44]

### 4. `wait` 的基本语义

1. `wait` 是最简单的同步并回收 child 的函数。课件声明为 `int wait(int *child_status)`。[00:54:12-00:54:29] [课件: 14-ecf-procs.pptx p.45]
2. 调用者会暂停，直到它的某一个 child 终止；`wait` 不指定是哪一个 child，只等待任意一个由该 parent 创建的 child。[00:54:29-00:54:50]
3. 返回值是刚终止 child 的 PID。若 `child_status != NULL`，它指向的整数会被写入 child 的终止原因和 exit status 编码。[00:54:50-00:55:05]
4. 状态要通过 `<sys/wait.h>` 中的宏检查。课件列出 `WIFEXITED`、`WEXITSTATUS`、`WIFSIGNALED`、`WTERMSIG`、`WIFSTOPPED`、`WSTOPSIG`、`WIFCONTINUED`；老师只在本段实际演示前两个，其余细节要求查教材。[00:55:05-00:55:14] [课件: 14-ecf-procs.pptx p.45]

### 5. `fork9`：`wait` 为输出增加 happens-before 约束

1. child 打印 `HC: hello from child` 后调用 `exit(0)`。[00:55:14-00:55:28] [课件: 14-ecf-procs.pptx p.46]
2. parent 打印 `HP: hello from parent`，然后 `wait(&child_status)`；child 终止前，parent 停在这里。[00:55:28-00:55:36]
3. `wait` 返回后，parent 才打印 `CT: child has terminated`，离开分支后打印 `Bye`。[00:55:36-00:55:42]
4. 因此 `HC` 与 `HP` 的先后可以变化，但 `CT` 必须在 child 的 `HC` 和 `exit` 之后，且 parent 的 `Bye` 在 `CT` 后。课件把 `HP, CT, Bye, HC` 明确列为 infeasible。[00:55:42-00:57:23] [课件: 14-ecf-procs.pptx p.46]
5. 学生询问 `HP, HC, CT, Bye`，老师确认可行：parent 先打印 HP，切到 child 打印 HC 并退出，再回到 parent 使 `wait` 返回。[00:56:50-00:57:23]

### 6. `fork10`：创建 N 个 child，再回收 N 次

1. 第一重循环执行 N 次 `fork`。每个 child 立即以 `100+i` 为 exit status 终止；parent 继续循环创建其余 children。[00:57:40-00:58:27] [课件: 14-ecf-procs.pptx p.47]
2. parent 在第二重循环中调用 N 次 `wait(&child_status)`，保证所有 N 个 children 都被 reap。[00:58:27-00:58:52]
3. `wait` 返回 PID；`child_status` 接收状态。先用 `WIFEXITED(child_status)` 判断是否通过正常 `exit` 终止，只有成立时才用 `WEXITSTATUS(child_status)` 取出 `100+i`。[00:58:52-00:59:07]
4. 若 `WIFEXITED` 为 false，示例只报告 child 非正常终止。若多个 children 已经完成，`wait` 以任意顺序取回，不能要求按创建顺序。[00:59:07-00:59:21] [课件: 14-ecf-procs.pptx p.47]

### 7. 引出 `waitpid`

`waitpid` 与 `wait` 相似，但可等待具有指定 process ID 的特定 child，而不是任意 child。本段在函数说明中间结束，完整边界与 `execve` 转场由下一段继续。[00:59:21-00:59:34] [课件: 14-ecf-procs.pptx p.48]

## 概念、符号与推导

### Orphan、zombie 与 active child

| 状态 | 是否仍执行 | 原 parent 是否存在 | 本段处理 |
|---|---|---|---|
| Zombie child | 否，已经 terminated | 可能存在 | parent `wait`/`waitpid`；若 parent 终止则由 `init` reap |
| Orphan but active child | 是 | 否 | 继续运行；以后终止时由 `init` reap |
| Active child with parent | 是或等待调度 | 是 | parent 退出不会自动杀死它 |

[00:49:37-00:54:12] [课件: 14-ecf-procs.pptx p.42] [课件: 14-ecf-procs.pptx p.43] [课件: 14-ecf-procs.pptx p.44]

### `wait` 的两个输出通道

```c
int child_status;
int child_pid = wait(&child_status);
```

- 函数返回值：终止 child 的 PID。
- 指针输出：`child_status`，编码终止原因和 exit status。
- 解释顺序：先用 `WIFEXITED(child_status)` 判断正常终止，再用 `WEXITSTATUS(child_status)` 取 exit status。[00:54:20-00:55:14] [00:58:35-00:59:07] [课件: 14-ecf-procs.pptx p.45] [课件: 14-ecf-procs.pptx p.47]

### `wait` 带来的同步边

对 `fork9`，可保留以下必要顺序：

```text
child:  HC -> exit
parent: HP -> wait returns -> CT -> Bye
                 ^
                 |
            child has terminated
```

`HC` 与 `HP` 无固定先后；`CT` 不得早于 child terminate，`Bye` 不得早于 CT。[00:55:19-00:57:23] [课件: 14-ecf-procs.pptx p.46]

本段没有数学公式推导；N 次创建/N 次等待是循环次数与 child 数的直接对应。

## 常见误解与边界

1. **误解：orphan 就是 zombie。** Orphan 只表示原 parent 已终止；`fork8` 的 orphan child 仍在 active running，直到被显式 kill。[00:52:37-00:53:58]
2. **误解：parent 退出会杀死 child。** `fork8` 直接展示 child 在 parent 退出后继续无限循环。[00:53:16-00:53:44]
3. **误解：zombie 仍在执行用户代码。** Zombie 已 terminated，只剩退出状态和 OS table 状态待回收。[00:50:17-00:50:40]
4. **误解：`wait` 等待指定 PID。** 普通 `wait` 等任意一个 child；指定 child 是 `waitpid` 的用途。[00:54:33-00:54:50] [00:59:21-00:59:34]
5. **误解：`wait` 返回 exit status。** 返回值是 PID；exit status 通过 `child_status` 指针和宏取得。[00:54:50-00:55:05]
6. **误解：可以无条件调用 `WEXITSTATUS`。** 示例先检查 `WIFEXITED`，确认 child 正常退出后才读取 exit status。[00:58:52-00:59:07]
7. **误解：一次 `wait` 会回收所有 children。** 一次只对应一个已终止 child；`fork10` 创建 N 个后调用 N 次。[00:57:40-00:58:35]
8. **边界：状态宏的完整位编码不在课堂展开。** 老师把其余宏细节明确交给教材。[00:55:05-00:55:14]

### 8. 为什么先 `fork` 再由 child `execve`

1. 若当前程序直接调用成功的 `execve`，旧 program 会被替换，无法回来继续工作。[01:06:23-01:06:31]
