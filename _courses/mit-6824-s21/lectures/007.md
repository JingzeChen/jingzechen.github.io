## 核心概念与依赖关系

```text
leader election restriction
  -> majority overlap + at least-as-up-to-date
  -> elected leader contains potentially committed prefix
  -> AppendEntries prev-index/term check
  -> Log Matching + follower adopts leader suffix
  -> matchIndex majority evidence
  -> current-term commit rule
  -> State Machine Safety across leader changes

persistent currentTerm/votedFor/log[]
  -> durable-before-ack
  -> committed entries survive reboot
  -> replay reconstructs service state
  -> periodic snapshot captures applied prefix
  -> log compaction bounds replay/log size
  -> InstallSnapshot repairs follower beyond retained prefix
  -> service/Raft atomic boundary prevents state rollback

client timeout/leader change
  -> clerk retries and rotates replicas
  -> stable request ID enables duplicate detection
  -> reply only after commit + apply + execution
  -> external operation history
  -> total order + real time + read-from constraints
  -> linearizability / single-machine behavior
```

关键依赖是：election restriction 防止未来 leader 缺少可能 committed 的 prefix；`AppendEntries`/Log Matching 只负责让实际 logs 收敛；current-term commit rule 决定何时可把 entry 暴露给 state machine。Snapshot 不是绕开这些安全条件，而是在“已安全 apply 的 prefix”上换一种持久化/传输表示。

## 关键推导、例子与结论边界

### 1. Election freshness 不是 longest-log rule

Candidate 至少与 voter 一样新，当且仅当 last term 更高，或 last term 相同且 last index 不小于 voter：

$$
(candidate.lastTerm,candidate.lastIndex)
\ge_{lex}
(voter.lastTerm,voter.lastIndex).
$$

Figure 7 还提醒：log 图没有显示 `currentTerm`，失败 election 即使未改变 log，也会改变后续投票。[00:03:39-00:10:54]

### 2. Figure 8 的 commit 条件

Leader 以 replication count 推进到 $N$ 时，除 majority 的 `matchIndex[i] >= N` 外，还必须有：

$$
log[N].term = currentTerm.
$$

Previous-term entry 不能只因暂时位于多数就直接 commit；一个 current-term entry committed 后，earlier prefix 才随 `commitIndex` 间接 committed。[00:20:05-00:24:52]

### 3. Durable-before-ack

$$
persist(new\ log/term/vote)
\longrightarrow
send\ RPC\ success/reply.
$$

反序会留下 crash window：leader 已把 success 计入 majority，但 reboot 后 entry 不存在，最终可能撤销已回复 client 的 operation。[00:40:39-00:48:53]

### 4. Snapshot/state-history duality

$$
snapshot_i \equiv apply(S_0,log[1..i]),
$$

所以恢复可使用：

$$
snapshot_i + log[i+1..n].
$$

只有 service 能证明 snapshot 覆盖 through $i$；Raft 据此 compact prefix。若 follower 需要的 index 早于 leader 保留日志起点，才转用 `InstallSnapshot`。[00:50:03-00:59:59]

### 5. Snapshot rollback 边界

- Old snapshot 不得覆盖已经 apply 到更高 index 的 state machine。
- Snapshot 若与现有 log 在 last-included index/term 对齐，只删除被覆盖 prefix，保留有效 suffix。
- Log 可以删除 uncommitted conflicting tail；state machine/committed prefix 不可回退。[01:00:18-01:11:31] [01:35:44-01:36:57]

### 6. Linearizability 的可满足与不可满足 history

第一例存在顺序：

$$
Wx1 < Rx1 < Wx2 < Rx2.
$$

第二例的 stale read 产生：

$$
Wx2 < Rx2 < Rx1 < Wx2,
$$

约束成环，因此不存在合法 total order。[01:20:31-01:29:02]

### 7. Partition 中 safety 与 liveness 的结论

Minority old leader 可能暂时仍自认为 leader，但拿不到 majority：

$$
no\ majority
\rightarrow no\ commit
\rightarrow no\ apply
\rightarrow no\ client\ success.
$$

这保持 safety，却让该 attempt 无法完成；liveness 由 clerk timeout、尝试其他 replicas 或等待 network heal 来恢复。[01:31:25-01:33:57]

## 易错点与待复核项

- 不要用 log 长度替代 `(lastTerm,lastIndex)` freshness；也不要忽略 candidate/RPC 的 current term。
- `nextIndex` 是下一发送位置的猜测，`matchIndex` 是已确认最高匹配位置；课堂板书在 12/13/14 上有 off-by-one 混用，应以变量语义和 Lab definition 为准。
- Majority copies 不自动等于 previous-term entry 可直接 commit；必须通过 current-term entry 建立安全 commit point。
- “最终调用 persist”不够；必须在把 success 暴露给 leader/client 之前 durable。
- Snapshot compaction 不把 logical index 重置为 0；本地 slice 需要 base offset。
- Snapshot 通过 apply channel 交给 service，不代表 Raft library 可直接覆盖 key/value state。
- Clerk retry 可能重复已执行 operation；request ID/duplicate detection 是正确性需要，不只是优化。
- `Start()` return 面向 service；client reply 要等 commit、apply 与 execution。
- [需回听 01:10:03-01:10:06] “reject all snapshots” 与上下文明显冲突，应核对是否为 “reject old snapshots”。
- [需回听 01:37:42-01:39:24] `matchIndex/nextIndex` 板书数值互相矛盾，不能据自动字幕固定 off-by-one 实现。

## 教学展开

### 1. 先列出本讲要解决的四组问题

- [00:00:55-00:01:08] 第三组是 **persistence 与 snapshot**：哪些 Raft state 必须进入 persistent storage，以及这为什么直接关系 Lab 2C/2D。

## 概念、符号与推导

### Majority overlap

若集群有 $N$ 个节点，选举需要超过半数的票。任意两个这样的集合不可能互不相交；否则两者大小之和会超过 $N$。老师在本段用这一交集解释为何前一轮 election/replication 的信息有机会约束后一位 leader。[00:03:04-00:03:39]

### Log up-to-date 比较

课堂规则可写为：candidate 的 log 至少和 voter 一样新，当且仅当

$$
candidate.lastTerm > voter.lastTerm
$$

或

$$
candidate.lastTerm = voter.lastTerm
\quad\text{且}\quad
candidate.lastIndex \ge voter.lastIndex.
$$

比较顺序是先 term、后 index；不能把它缩成“谁的 log 更长”。[00:03:39-00:04:52] [课件: l-raft2.txt p.1]

### 两层拒绝条件

1. **Election term 层：** 若 RPC 中 term 小于接收者的 `currentTerm`，接收者拒绝；candidate 看到更高 term 后退为 follower。[00:07:47-00:08:14]
2. **Log freshness 层：** term 合格后，follower 仍只投给 log 至少与自己一样新的 candidate。[00:04:15-00:04:52]

本段没有对 Raft safety 作完整形式证明；majority overlap 与 up-to-date comparison 是后续 Leader Completeness 推理的组成部分，不应单独夸大为全部证明。

## 概念、符号与推导

### `AppendEntries` 的前驱校验

Follower 只有在自己的 log 中存在满足下式的前驱 entry 时，才能接受紧随其后的新 entries：

$$
follower.log[prevLogIndex].term = prevLogTerm.
$$

若 index 不存在或 term 不同，则返回失败。[00:13:20-00:14:14]

### Leader 为每个 follower 维护的两个量

- `nextIndex[f]`：leader 下一次准备从哪个位置给 follower `f` 发送 entry。初始化很乐观，失败后回退。[00:14:21-00:15:29]
- `matchIndex[f]`：leader 已由成功响应确认 follower `f` 与自己匹配到的位置，是保守的复制下界。[00:16:27-00:18:00]

课堂的核心关系是：失败响应只缩小 leader 对 `nextIndex` 的猜测；成功响应才扩大 `matchIndex` 所代表的已知范围。两者不能互换。

### 冲突覆盖步骤

1. Heartbeat 在 `(prevLogIndex=12, prevLogTerm=5)` 处失败。[00:13:20-00:14:14]
2. Leader 回退 `nextIndex`。[00:15:10-00:15:29]
3. 新 RPC 在 `(prevLogIndex=11, prevLogTerm=3)` 处找到共同前缀。[00:15:29-00:16:02]
4. Follower 删除该点之后与 leader 冲突的 term-4 entry，接受 term-5 entry。[00:16:02-00:16:09]
5. 成功响应让 leader 更新该 follower 的复制进度。[00:16:16-00:18:00]

本段尚未给出完整 commit 公式；“majority replication 是否足够”的限定条件留到下一段 Figure 8。

## 教学展开

### 1. Figure 8(a)-(c)：构造“多数副本仍可被覆盖”

- [00:20:05-00:20:16] 初始 entry 1 已由所有服务器 committed，作为不会再改变的共同前缀。
- [00:20:16-00:20:33] term 2 的 leader 在 index 2 追加 term-2 entry，但当时没有确认 majority，因此它尚未 committed。
- [00:20:33-00:20:47] 隔离的一端在 term 3 当选并追加另一个 index-2 entry；它同样没有 majority，所以 term-3 entry 也未 committed。
- [00:20:47-00:21:13] 随后原先持有 term-2 entry 的服务器在 term 4 成为 leader，把 term-2 entry 复制给更多节点，直到从日志分布看已有三份。

### 2. 拒绝“只数 majority 就 commit previous-term entry”

- [00:21:14-00:21:40] 直觉会说三份就是 majority，可以把 index 2 交给 state machine。老师明确说不行，commit reasoning 比 replica count 更细。
- [00:21:47-00:22:34] 他给出规则：leader 以多数 `matchIndex` 推进 `commitIndex` 时，目标 entry 必须来自 **leader 当前 term**。Figure 8(c) 的 index-2 entry 来自 term 2，而当前 leader 在 term 4，因此不能仅凭此时的三份副本直接宣布它 committed。
- [00:22:36-00:23:40] Figure 8(d) 展示反例路径：term-4 leader 若在建立本 term 的 committed entry 前失联，另一个持有 term-3 冲突 entry 的服务器仍可能成为后续 leader，并把 term-3 entry 复制回来，擦除先前出现在多数日志上的 term-2 entry。

### 3. Figure 8(e)：本 term entry 如何使旧前缀一并安全

- [00:23:41-00:24:12] 另一条路径中，term-4 leader 先追加并复制一个 term-4 entry 到 majority。这个本 term entry 可按 commit rule 直接 commit。

## 概念、符号与推导

### Current-term commit 条件

本段口述的 leader 侧推进规则可整理为：寻找某个 $N$，满足

$$
N > commitIndex,
$$

$$
\left|\{i \mid matchIndex[i] \ge N\}\right| > \frac{clusterSize}{2},
$$

并且

$$
log[N].term = currentTerm.
$$

此时 leader 可令 `commitIndex = N`；所有不大于 $N$ 的前缀 entries 随顺序 apply 而一并 committed。[00:21:47-00:24:12]

### Figure 8 的反证链

1. term-2 entry 复制到多数，但 term-4 leader 尚未 commit 任一本 term entry。[00:20:47-00:22:34]
2. 若错误地只按多数副本 apply term-2 entry，client/state machine 已观察到它。[00:21:14-00:21:40]
3. term-4 leader 离开后，持有冲突 term-3 entry 的服务器仍可通过合法 election 成为后续 leader。[00:22:36-00:23:27]
4. 新 leader 覆盖 term-2 entry；同一 index 便可能执行不同 command，违反 safety。[00:23:17-00:23:40]
5. 所以 leader 不能用 replica count 直接 commit previous-term entry。

### 为什么当前 term entry 足够

课堂只给出 Figure 8 的直观推理：当前 term entry 能复制到 majority，意味着未来 election 的 majority 与这组节点相交；配合 election restriction，未来 leader 不能缺少这段已确认前缀。老师没有在本段展开完整形式证明，因此笔记不把这段口述扩成论文证明。[00:23:41-00:24:34]

# 第 5 段：持久化承诺、写入时机与 service replay

## 本段在整讲中的作用

上一段列出 `currentTerm`、`votedFor`、`log[]` 三项 persistent state，本段逐项回答“如果不保存会坏什么”，并把抽象 safety 落到写入顺序：state 变化时持久化，尤其 follower 必须先把新 entries 写入 durable log，才能回复 `AppendEntries` 成功。[00:40:04-00:48:53] 随后老师区分 Raft library 的恢复与上层 service 的恢复：Raft log 活下来还不等于 key/value table 已恢复；service 可以从空状态按相同 total order replay log，重建相同 state。[00:49:03-00:50:03] 这个全量 replay 的性能问题正好引出下一段 snapshots。

## 教学展开

### 1. 为什么 `log[]` 必须进入 stable storage

- [00:40:04-00:40:25] Stable storage 写入昂贵，可能成为 bottleneck；所以每一项持久化都应能解释必要性，不能只因为 Figure 2 列出就机械保存。

### 2. `currentTerm` 与 `votedFor` 共同约束 election

## 概念、符号与推导

### Durable-before-ack 顺序

Follower 对新 entries 的关键 happens-before 关系是：

$$
append\ to\ persistent\ log
\;\longrightarrow\;
reply\ success\ to\ AppendEntries.
$$

若颠倒顺序，存在 execution：reply success -> leader 汇成 majority -> follower 在实际落盘前 crash -> reboot 后 entry 消失。这个 execution 会破坏已 committed entry 的持久性。[00:48:14-00:48:53]

### Client-visible commitment 链

$$
majority\ accepts
\rightarrow leader\ commits
\rightarrow applyCh
\rightarrow service\ executes
\rightarrow client\ receives\ success.
$$

一旦最后一步发生，系统不能在 reboot 后回到缺少该 operation 的状态。[00:41:02-00:42:28]

### Persistent state 的职责

- `log[]`：保住可能参与 commit majority 的 commands。[00:40:39-00:42:28]
- `votedFor`：防止 reboot 后在同一 term 对不同 candidates 重复投票。[00:42:44-00:43:07]
- `currentTerm`：维持 term 单调并拒绝 stale RPC，同时解释当前 `votedFor`。[00:42:53-00:43:20]

### Replay 的确定性前提

若所有 replica 从相同初态 $S_0$ 开始，按同一 total order 执行 commands $c_1,\ldots,c_n$，且状态转移确定，则

$$
S_n = apply(\cdots apply(apply(S_0,c_1),c_2)\cdots,c_n)
$$

在各 replica 上相同。[00:49:21-00:50:03] 老师没有在本段讨论外部 side effects 的恢复协议，因此不在此扩展。

# 第 6 段：Snapshots、log compaction 与 service/Raft API

> 时间范围：`00:50:03-00:59:59`
>
> 证据范围：仅本段课堂 transcript。该分段没有课件材料，snapshot/API 细节按 2021 课堂口述记录。
>
> 复习标记：**State-history duality 与 ownership boundary**。Service 知道状态已包含哪些 operations；Raft 知道可截断哪些 log entries。两者必须通过带 index 的 snapshot API 协作。

## 本段在整讲中的作用

本段先完成上一节跨边界的 replay 论证：从相同空状态按相同顺序重放 operations，各 replica 会得到相同 service state。[00:50:03-00:50:14] 随后老师指出全量 replay 对长寿命系统过慢，因而引入 periodic snapshots。Snapshot 同时解决两件事：缩短 reboot 时的状态重建，并允许 Raft 丢弃已被 state machine state 吸收的 log prefix。[00:50:24-00:53:21] 接下来重点转为 abstraction boundary：service 才知道自己的 snapshot 覆盖到 index $i$，Raft 才能据此 compact log；Lab 2D 因此必须新增双向 API。[00:53:32-00:57:53] 最后老师说明仅有本地 snapshot 还不够：若 follower 落后到 leader 已删除的前缀之前，`AppendEntries` 无法补齐，leader 必须发送 `InstallSnapshot RPC`。[00:58:04-00:59:59]

## 教学展开

### 1. 完成 deterministic replay 的恢复思路

- [00:50:03-00:50:14] 每个 service 从同一空 state 出发，按相同 total order replay 所有 operations，应得到与其他 replica 相同的 state。这是 replicated state machine 能从 durable log 重建上层状态的基础。
- [00:50:24-00:50:38] 问题是时间：服务若运行数年，从“历史开端”重放整个 log 会很慢，不适合作为常规恢复方案。

### 2. Snapshot 的两个直接目标

- [00:50:38-00:50:58] 替代策略是 periodic snapshots。第一目标是更快重建过去某一点的 service state；第二目标是 **log compaction**，即删除已经由 snapshot 表达的 Raft log prefix。
- [00:51:08-00:51:35] 假设 application 已 apply 前一千或一百万个 operations，当前 state 已包含从起点到 index $i$ 的全部效果。
- [00:51:38-00:51:58] 老师称其为 state replication 与 log replication/replay 的对偶：保存执行到 $i$ 后的 state，在恢复语义上等价于从 0 重做这些 operations。
- [00:52:00-00:52:36] 一旦 snapshot 已 durable，就可以丢弃 through $i$ 的 log prefix，周期性重复便能控制 log 大小。Snapshot 自身必须在 stable storage；否则 log 已删、snapshot 又随 crash 消失，恢复依据会两头落空。

### 3. Snapshot + log tail 的 reboot 路径

- [00:52:45-00:53:21] Follower reboot 后加载 Raft persistent state，也由 service 加载最新 snapshot；然后只 replay snapshot 之后仍保留的 log tail，把 service 追到当前状态。
- 这里 snapshot 并不替代所有 log。尚未包含在 snapshot 中的后缀仍负责表达后续 operations。

### 4. 为什么 service 与 Raft 必须合作

- [00:53:32-00:54:24] 学生指出 snapshot 似乎打破原本的 abstraction：Raft 不应理解 key/value state machine 的内部状态。老师同意存在更紧的 coupling，但强调二者必须“play together”。
- [00:54:14-00:54:24] 若 service 错报自己已 apply 到哪里，Raft 可能错误截断仍需要的 log，产生 inconsistent results。课堂假设组件非恶意，但 API contract 必须准确。
- [00:54:30-00:54:57] Raft library 无法自己判断 service state 已包含哪个 index；只有 service 能声明“我已 snapshot through $i$”，Raft 才可删除 $0..i$ 的 entries。

### 5. Lab 2D 增加的 API 边界

- [00:54:58-00:55:41] Lab 2A-2C 中，主要接口是 Raft 经 `apply channel` 向 service 上送 committed messages，以及 service 调 `Start()` 向 Raft 提交 command。
- [00:55:43-00:56:14] Lab 2D 的 snapshot/compaction 需要更多交互。论文描述协议机制，但没有规定 course lab 必须采用的 service/Raft API，因此课程必须选择一套具体接口。
- [00:56:19-00:57:16] 老师提到当时 API 中有 `CondInstallSnapshot` 一类操作，目标是让 Raft state 与 service state 的 snapshot 安装保持一致/原子地协调。该 API 并非唯一设计，其他接口也能实现同一 boundary contract。

### 6. 正常 snapshot 流程由 service 驱动

- [00:57:29-00:57:53] Service 周期性决定做 snapshot，并告诉 Raft：snapshot bytes 是什么、它覆盖 through index $i$。Raft 将 snapshot 与相应 metadata 持久化，并截断 through $i$ 的 log prefix。
- [00:57:58-00:58:30] Reboot 时 follower 从 durable snapshot 恢复 application state；完整 key/value 恢复主要在 Lab 3 出现，Lab 2 重点是 Raft 自己如何管理被截断日志与传输 snapshot。

### 7. `AppendEntries` 到不了的历史缺口

- [00:58:32-00:59:13] Leader 的 log 已 compact 成从 $i$ 附近开始的 suffix。若新节点或长期离线 follower 的进度仍在 $i$ 之前，leader 即使不断回退 `nextIndex`，也没有更早 entries 可发送。
- [00:59:13-00:59:49] 这时 leader 必须直接把 snapshot 发送给 follower，让 follower 以该 state/index 为新基线，再从剩余 log tail 继续 catch-up；这就是 Lab 2D 要实现的 `InstallSnapshot RPC`。
- [00:59:50-00:59:59] 老师转到当天 homework：收到 snapshot 是否可能让 state machine 倒退。问题在下一段完整提出。

## 概念、符号与推导

### Snapshot 的语义

令 service 在按序执行 through log index $i$ 后的状态为 $S_i$。Snapshot 保存的是某种可恢复表示：

$$
snapshot_i \equiv S_i
\equiv apply(S_0, log[1..i]).
$$

因此 durable `snapshot_i` 建立后，恢复所需数据可由

$$
snapshot_i + log[i+1..n]
$$

组成，而不再需要 `log[1..i]`。[00:51:08-00:53:21]

### Compaction 的前提

只有 service 明确确认 snapshot 覆盖 through $i$ 后，Raft 才能删除对应 prefix：

$$
service\ confirms\ snapshot_i\ durable
\rightarrow Raft\ may\ discard\ log[1..i].
$$

未执行、未被 snapshot 包含的 entries 仍须保留。本段没有说 snapshot 可删除任意 suffix，也没有把 snapshot index 重新编号为 0。

### 两条数据流

1. **Service -> Raft：** `Start(command)`；以及 snapshot bytes + covered index $i$。[00:54:58-00:57:53]
2. **Raft -> Service：** committed command 或待安装 snapshot，经 `apply channel` 交付。后一条在第 8 段进一步澄清。[00:55:19-00:55:41]

### `InstallSnapshot` 触发条件

若 follower 所需的 `nextIndex` 早于 leader 当前保留日志的起点，则 leader 没有可用 `AppendEntries` 修复的 prefix。必须先传 snapshot，之后再传 log tail。[00:58:32-00:59:49]

## 概念、符号与推导

### State-machine monotonicity

令 follower 已 apply 到 index $a$，收到 snapshot 覆盖到 index $s$。若

$$

$$

直接用该 snapshot 覆盖 service state 会丢掉 indexes $(s,a]$ 已执行 operations 的效果。只要其中有 operation 已回复 client，未来状态就不能再表现得像它没发生。[01:00:24-01:00:55] [01:09:33-01:09:58]

### Safety 与 liveness 的分离

- **Safety 要求：** 无论 snapshot 多晚到，都不能撤销已 applied/client-visible state。

## 概念、符号与推导

### Snapshot 安装的 prefix/suffix 判断

设 snapshot 覆盖到 `(lastIncludedIndex=s, lastIncludedTerm=t)`。若 follower 现有 log 在该位置有相同 index/term，则 snapshot 对应一个已知 prefix；可删除被 snapshot 覆盖的 prefix，但保留 $s$ 之后的 suffix。[01:10:06-01:11:00]

本段没有给出 Figure 13 全部 receiver steps，也没有确认学生未讲完的 step-6 解读；实现细节应以 paper/Lab 为准。

### Operation 的完成路径

$$
client\ RPC
\rightarrow service.Start(command)
\rightarrow Raft\ replication/commit
\rightarrow applyCh
\rightarrow service\ executes
\rightarrow client\ reply.
$$

Client reply 在最后，不能因 `Start()` 返回就提前发生。[01:13:21-01:14:15]

### Retry identity

同一个 logical request 的多次 network attempts 必须携带同一 request ID：

$$
attempt_1.id = attempt_2.id = logicalRequest.id.
$$

否则 service 无法区分“同一请求重传”与“client 发起的新操作”。[01:14:58-01:16:40]

### Linearizability 三条件

对 history $H$，若存在 total order $<$，满足：

1. 所有 completed operations 在 $<$ 中可比较；
2. 若 $A$ 的 response 早于 $B$ 的 invocation，则 $A < B$；
3. 每个 read 返回 $<$ 中它之前最近 write 的值；

则该 history linearizable。[01:18:28-01:19:57] 本段定义基于 external behavior，不要求暴露 Raft 的内部 linearization point。

- **并发 clients** [01:17:33-01:17:49]：用于说明“像单机”仍需 precise specification，因为重叠 operations 可有多个合法先后次序。

### 1. 补全第三个定义条件

### 2. History 记录的是 operation interval，不是内部实现步骤

- [01:20:31-01:20:53] 判断方法是查看一个 execution/history，问是否存在满足定义的 total order，即使原始 operations 有并发重叠。
- [01:20:57-01:21:30] 老师画三个 clients。每个 operation 有 start/invocation 和 end/response；例如 `Wx1` 表示把 `x` 写成 1，线段从 client 发请求开始，到收到 service 回复结束。

### 3. 不需要知道 write 在内部“哪一瞬间发生”

- [01:22:24-01:23:03] 学生困惑于一次 write 为何持续一段时间。老师解释，从 client 视角，发请求是开始，收到 response 是结束。
- [01:23:06-01:23:34] 区间内部可能经过 service、Raft、replication、apply channel 等很多步骤，但 linearizability specification 不要求观察这些内部机制；只使用 invocation、response、arguments 与 return values。
- 因此，重叠 operations 可以在各自区间内选择一个符合所有约束的抽象线性点。

### 4. 第一例：找到合法 total order

- [01:23:35-01:24:28] 三个 clients 并发执行。课堂目标不是按线条左端机械排序，而是寻找任意满足 real-time/value constraints 的全序。
- [01:24:31-01:24:52] 老师构造顺序：

  $$
  Wx1 < Rx1 < Wx2 < Rx2.
  $$

- [01:24:53-01:25:42] 检查 real-time：`Wx1` 必须早于后来不重叠的 `Wx2`；两个 reads 的位置又必须与返回值一致，`Rx1` 放在 `Wx1` 后、`Wx2` 前，`Rx2` 放在 `Wx2` 后。

## 概念、符号与推导

### History 中的记号

- `Wx1`：write `x=1`。
- `Rx2`：read `x`，返回 2。
- 每项 operation 是区间 $[invocation,response]$，不是原始图上的单点。[01:20:57-01:23:34]

### 两类约束

1. **Real-time constraint：** 若 A response 早于 B invocation，则 $A < B$。
2. **Value constraint：** `Rxv` 必须放在某次 `Wxv` 之后，且它与 read 之间不能有另一 write 改掉该值。

重叠 operations 没有强制 real-time 顺序，允许选择能满足 value constraints 的排列。[01:24:21-01:25:51]

### 第一例的可满足顺序

$$
Wx1 < Rx1 < Wx2 < Rx2.
$$

该顺序同时尊重 `Wx1` 与 `Wx2` 的非重叠时序，并让两个 reads 分别看到其前一 write，因此 linearizable。[01:24:31-01:26:10]

### 第二例的约束环

从口述可抽取：

$$
Wx2 < Rx2 \quad (Rx2\ returns\ 2),
$$

$$
Rx2 < Rx1 \quad (real\ time),
$$

$$
Rx1 < Wx2 \quad (Rx1\ returns\ old\ value\ 1).
$$

合并得到

$$
Wx2 < Rx2 < Rx1 < Wx2,
$$

形成 cycle，所以不存在 total order。[01:27:15-01:28:34]

## 概念、符号与推导

### Linearizability 比 serializability 多的约束

课堂层面的关系可表示为：

$$
linearizable\ history
\Rightarrow
\text{存在合法串行顺序且尊重 real time}.
$$

本段只指出 serializability 不要求 real-time matching，没有讨论数据库中的事务、冲突/视图可串行化等更细分类。[01:30:45-01:31:13]

### Partition 场景的 safety/liveness 链

Minority old leader 无法满足：

$$
\left|successful\ AppendEntries\ acknowledgements\right| > \frac{N}{2}.
$$

因此：

$$
no\ majority
\rightarrow no\ commit
\rightarrow no\ applyCh\ delivery
\rightarrow no\ service\ execution
\rightarrow no\ success\ reply.
$$

Safety 得以保持，但该 request 在这条网络路径上没有 liveness；clerk 需要 timeout/retry 到 majority 一侧。[01:32:09-01:33:57]

### 可回退与不可回退集合

- 可删除：与新 leader 冲突且尚未 committed/applied 的 log tail。[01:36:18-01:36:57]
- 不可撤销：state machine 已执行的 committed prefix，以及已向 client 暴露的结果。

### Replication progress 语义

$$
matchIndex[f] = \text{leader 已确认 follower f 匹配的最高 log index},
$$

$$
nextIndex[f] = \text{leader 下次准备给 follower f 发送的 index}.
$$

失败只调整试探位置；成功才扩大已确认范围。[01:37:18-01:39:24]

### 1. Log Matching invariant 补全

- [01:39:57-01:40:18] Follower 只有在 `prevLogIndex=11` 位置确实有 `prevLogTerm=3` 时才回复成功；这就是 RPC 发送前驱 index/term 的目的。

## 概念、符号与推导

### Log Matching Property

若两个 logs 在 index $i$ 都包含 term $t$ 的 entry，则：

$$
log_A[i].term = log_B[i].term = t
\Rightarrow
log_A[1..i] = log_B[1..i].
$$

课堂用 `prevLogIndex/prevLogTerm` 的成功检查说明该 invariant 怎样让单点校验代表整个 prefix。[01:39:57-01:40:36]

### Copy-on-write 的一致性点

令 fork 时刻 service state 为 $S_i$：

1. Parent/child 初始映射相同 physical pages；
2. Child 读取的逻辑视图保持为 $S_i$；
3. Parent 对后续状态 $S_{i+1},S_{i+2},...$ 的写触发按页复制；
4. Child 写盘得到的 snapshot 仍对应 $S_i$。

这减少 stop-the-world 时间，但不意味着没有内存/IO 成本；修改页会逐步复制，child 仍需把 snapshot 写盘。[01:41:16-01:44:02]

### Logical index 与 physical offset

若 snapshot 覆盖 through logical index $s$，compact 后本地 slice 的位置 0 可表示 logical index $s$（或按实现保留 boundary entry），后续访问需要转换：

$$
physicalPosition = logicalIndex - baseIndex.
$$

老师只明确“keep counting”与“add offset everywhere”，没有规定 Lab 的 dummy entry 布局；具体映射由实现选择。[01:45:23-01:47:23]

### `Start()` 与完成事件

$$
Start(command)\ returns\ to\ service
\not\Rightarrow command\ committed,
$$

$$
command\ applied/executed
\Rightarrow service\ may\ complete\ client\ RPC.
$$

两次 return 面向不同调用者，不能混为一谈。[01:47:49-01:48:27]

1. **问：为什么在某个 index 的 term 匹配就能推断此前 prefix 匹配？**  
   **答：** Raft 维护 Log Matching invariant；`AppendEntries` 只在前驱 index/term 匹配时延伸日志，因此相同 index+term 的 entry 具有相同前缀。[01:39:57-01:40:36]

2. **问：`fork` 做 snapshot 时，OS 一开始复制什么、不复制什么？**  
   **答：** 初始复制 page-table 等映射 metadata，但 parent/child 共享 physical memory pages；某方写页时才按 copy-on-write 复制该页。[01:42:11-01:43:39]

3. **问：为什么 child 能写出一致 snapshot，而 parent 仍处理新 requests？**  
   **答：** Child 保持 fork 时刻的地址空间视图；parent 后续写通过 COW 获得自己的页，不改变 child 看到的旧页。[01:42:57-01:44:02]

4. **问：Log compaction 后 logical index 是否从 0 重新开始？**  
   **答：** 不会。Index 持续递增；实现只是在本地数组访问时增加 `baseIndex`/offset 映射。[01:45:23-01:47:23]

5. **问：`Start()` 立即返回为什么不等于可以回复 client？**  
   **答：** 它只返回调用它的 service，command 仍可能未 commit；service 要等 apply channel 交付并执行后才完成 client RPC。[01:47:27-01:48:27]
