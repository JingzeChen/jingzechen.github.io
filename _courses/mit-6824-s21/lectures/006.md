## 核心概念与依赖关系

| 概念 | 课堂中的作用 | 依赖/边界 |
|---|---|---|
| `GetTask` RPC | worker 请求可执行 task | coordinator 可立即回复、阻塞回复或让 worker 重试 |
| `FinishedTask` RPC | worker 汇报具体 task 完成 | handler 更新 task state 后可唤醒等待者 |
| `Done task` | 告诉 worker 整个 job 已完成 | 不等同于“当前暂时没有 task” |
| coordinator state | 记录 files、task 数量、issued/done、timestamps、`isDone` | 由 `Mutex` 保护；不要承担数据排序/计算 |
| Map-before-Reduce barrier | 全部 Map 完成后才允许 Reduce | “全部已发出”不等于“全部已完成” |
| temporary file + atomic rename | worker 完整写完后发布 intermediate/final result | 课堂只讲机制，不给出完整命名和冲突协议 |
| condition variable | 等待“有 task 可发”这一 predicate | 唤醒后必须重新检查；周期 Broadcast 覆盖 timeout |
| channel queue | coordinator 内组织 tasks/done/workers | 不能直接跨 machine 联系 worker；远程动作仍是 RPC |
| timeout/reissue | task 长时间未完成时重新调度 | Lab 把 failed 与 very slow 合并；paper 的 backup task 区分 laggard |
| lock/atomic | 建立共享 state 的互斥与可见性 | 不要持锁跨越可能阻塞的 RPC/channel send |

核心依赖链可以概括为：

$$
\text{RPC contract}
\rightarrow \text{coordinator task state}
\rightarrow \text{worker execution/files}
\rightarrow \text{completion or timeout}
\rightarrow \text{next scheduling decision}
$$

这只是课堂控制流的整理，不是新增算法或形式化证明。

## 关键推导、例子与结论边界

### 调度与等待

- 当所有 Map tasks 已发出但尚未完成时，coordinator 既不能发新 Map，也不能发 Reduce，因此要等待完成或 timeout 使 predicate 改变。
- condition variable 可在 `FinishedTask` 后立即唤醒，固定 sleep 则要等 interval 结束；若 task 本来很长，两者差异可能不明显。
- worker polling 与 coordinator-blocking RPC 都可行。后者减少反复“无任务”RPC，前者让 coordinator 快速返回但增加 traffic。
- channel 示例通过本地 queue 和 worker-specific goroutines 调度 RPC；RPC 失败后把 task 放回 queue。该示例未定义完整 worker registry 和 `exit`，也未区分 Map/Reduce。

### 文件、crash 与 retry

- Map worker 写 temporary intermediate files 后 atomic rename；Reduce worker读取属于自己的所有 Map outputs、sorting、apply Reduce，再原子发布最终文件。
- coordinator 用 issued timestamps 识别超时。Lab 给 task 一个十秒 failure timeout，但周期检查的 sleep interval 可自行选择。
- paper 把 worker failure 后的 restart 与未失败但很慢的 backup task 分开；Lab 统一以 timeout 触发 reissue。
- paper 中 mapper 把 intermediate files 留在本地，是因为当时 network bandwidth 是 bottleneck；最终 output 才写共享存储。

### Concurrency 与退出

- 修改共享 server state 时 lock；对相关 state 的 read 也要同步。单次 `isDone` 可考虑 atomic，但多字段 invariant 更适合 coarse-grained lock。
- 若持锁调用可能阻塞的 RPC/channel operation，其他 threads 可能无法获取 state lock，整个 server 难以前进。
- coordinator 的 pull 架构不需主动等待所有 workers 退出：可对后续 `GetTask` 回复 `Done`，也可先关闭，让迟到 worker 从 connection failure 得知结束。
- 多个 deferred functions 按 LIFO 执行；新 goroutine 不继承创建者当前持有的 lock。

### 证据边界

- 老师多次明确个人方案可能不完美，channel 示例也不完整；本讲不提供可提交的完整 Lab solution。
- `00:42:03-00:49:38` 是 breakout/等待，录音没有各组讨论内容。
- Interface 具体写法、Raft timeout 毫秒范围、channel ordering/fairness 和 `unexpected EOF` 根因都没有得到确定通用答案。

## 易错点与待复核项

1. 把 `Done` 当成“暂时无 task”，会让 worker 过早退出。
2. 把“Map tasks 已全部分配”当成“Map phase 已完成”，会过早启动 Reduce。
3. 认为 Go channel 能直接跨机器传 task，混淆了进程内同步与 RPC。
4. 在 coordinator 中读取文件、sorting 或执行 Map/Reduce，使控制面成为 bottleneck。
5. 用两个 RPC 分别探测和领取 task，而一次 reply 就能表达相同结果。
6. 持锁发送 RPC 或 channel message，导致其他 goroutines 无法访问 server state。
7. 把 race 称为 benign，假设 reader 最终一定看到 write，或用无锁 reads 拼接多个相关字段。
8. 把 backup task 与 failure retry 混为一谈。
9. 假定 grading 会保留对 test/config files 的修改，或默认评分环境能下载 external dependencies。
10. 把字幕不清的 timeout 范围、channel fairness 或 interface 写法整理成确定规范。

## 分段导读

### 1. `00:00:05-00:10:05`｜从 RPC 契约到 MapReduce 调度骨架

老师先把本讲定位为 Lab 1 MapReduce Q&A，并说明会走读个人方案、比较替代设计、讨论常见 bug、给一般建议，再回答现场与课前问题。他明确称展示方案“可能不完美”，所以课堂重点是设计过程，不是唯一答案。

第一步从 `rpc.go` 的 API 开始。任务分为 `Map`、`Reduce` 和让 worker 退出的 `Done`。worker 用 `GetTask` 请求工作，coordinator 回复 task type、task identity 与 Map/Reduce 数量等 metadata；worker 完成后用 `FinishedTask` 报告具体任务。第二步是 coordinator state：输入 files、Map/Reduce 数量、issued/done 状态、issued timestamps、`isDone`，并用 `Mutex` 防止并发 handler 竞态。

第三步让 worker 形成“请求 -> 执行 -> 汇报 -> 再请求”的 loop。第四步补数据路径：Map worker 读取输入、调用 Map、写 temporary intermediate files，再 atomic rename；Reduce worker读取该 partition 来自所有 Map tasks 的中间结果、sorting、按 key 聚合 values、调用 Reduce并原子发布最终文件。sorting 放在 reducer，是因为单个 mapper 只有部分 keys。

最后回到 coordinator：先发 Map，全部 Map 完成后才发 Reduce；当前无 task 可发但阶段未完成时必须等待。本段只提出等待问题，condition variable 在下一段展开。常见误解是把 `Done` 当单任务完成、让 coordinator 做 sorting、或在 Map 仅“全部发出”时就进入 Reduce。完整问题、例子、5 个掌握检查和待核对项见 [001](#section-01)。

### 2. `00:10:07-00:20:03`｜Condition variable、阻塞 RPC 与等待位置

当 Map 已全部分配但尚未完成、也没有 task 超时时，coordinator 不能发 Reduce，只能等 predicate 改变。老师方案用 condition variable：没有 task 时 wait；收到 signal 后回到 loop 顶部重新检查，而不是假定条件必然成立。

唤醒来自两类事件。`FinishedTask` handler 先更新 done state 再 `Broadcast`；另一个周期 goroutine 定时 `Broadcast`，使 coordinator 重新检查 timestamps 和 timeout。老师不记得演示间隔是一秒还是十秒，并说本处具体数值不重要。

学生要求解释 condition variable。老师回答它适合等待某个异步 predicate 变 true；channels、condition variables 等高层同步原语建立在 locks 上，但提供更贴近条件的推理方式。学生再问固定 sleep：功能上可相近，但 condition variable 可在 worker 十毫秒后完成时立即唤醒，而一秒 polling 必须等 interval 结束；若所有 task 都很长，差距可能较小。

另一个学生区分全局完成与阶段内暂时无 task。全局完成时 coordinator 返回 `Done`；暂时无 task 可选择立即回复让 worker sleep/retry，或像老师方案一样让 `GetTask` handler 等待，使 worker 阻塞在 RPC。后一方案的 traffic 优势跨到下一段。完整问答、权衡、5 个掌握检查和待核对项见 [002](#section-02)。

### 3. `00:20:05-00:30:03`｜`defer`、锁的执行上下文与 channel 调度备选

老师先回答 coordinator 端等待的优点：worker 不必持续发送“有任务吗”的 RPC；两种设计都可行。随后学生围绕 `defer Unlock` 提问。课堂回答是新 goroutine 不继承创建者已持有的 lock；普通同步 function call 仍在同一执行流中，调用期间 lock 继续持有；deferred functions 在函数返回时运行，多个 defers 按 LIFO，而非老师一开始口误的 FIFO。

老师接着强调 server boundary：coordinator 的 lock 与 worker 的 lock 互不干涉，不同 machines 只通过 RPC 通信。在此基础上展示不完整的 channel 草图：外部通过 `workers` channel 报告 worker；coordinator 用 buffered `tasks` channel 存任务，用 `done` channel 收完成；每个 worker 对应一个本地 goroutine，从 queue 取 task 后真正发 RPC。

buffer 容量设为 `numTask`，让初始 tasks 全部入队而不阻塞。coordinator 收到 `numTask` 次 done 后关闭 tasks channel。RPC call 失败或 timeout 时，worker-specific goroutine 把 task 放回 queue，让其他 worker 或自己重试。channel 没有跨服务器发送 task，它只把任务交给 coordinator 内负责 RPC 的 goroutine。

老师明确说示例不完整、与 Lab 1 spec 不完全相同，也没有分 Map/Reduce。段末聊天区发现 `exit` 未定义，修正在下一段。完整问答、权衡、5 个掌握检查和待核对项见 [003](#section-03)。

### 4. `00:30:03-00:40:02`｜Channel 方案追问：RPC 方向、状态保护与失败边界

老师承认 `exit` 未定义，并说可把它做成与 `done` 类似的 boolean channel。学生问 `workers` channel 谁来填；老师设想外层 `mrcoordinator` 跟踪 worker crash、重启和新 server 加入，再发送 worker IDs，但这部分没有展示，也不是 Lab 1 给定模型。

学生进一步问 coordinator 能否主动 call worker。老师说概念上可以，但 workers 必须成为 RPC servers，coordinator 成为 client；这会改变 worker discovery 和连接职责，不是 Lab 1 引导方向。完成计数也不能因换成无限 loop 而消失：无论语法如何，必须记录已从 `done` 读了多少次，直到 `numTask`。

对“取 task、RPC 失败、再放回 channel”的问题，老师限定在当前 buffered channel 中说明：先取出腾出容量，再放回，不会因该一步阻塞；channels 内部用 locks，直接 lock 可能更轻，但此处预计没有巨大差异。选择原语时，Mutex 自然地保护 coordinator/Raft log 等 shared state；channel 更适合 task queue、ready value 或具体 command，二者可以混用。

若远程 worker failure，`call_worker` 返回 false，task 可 requeue；若 goroutine 本身 crash，课堂采用 process 一并 crash 的模型。永久失联 worker 对应的 goroutine 可能一直重试，许多 worker churn 会留下许多 goroutines，直到 tasks 完成、channel 关闭后退出。完整问答、权衡、5 个掌握检查和待核对项见 [004](#section-04)。

### 5. `00:40:03-00:50:01`｜Coordinator 瓶颈、冗余 RPC 与 breakout 讨论空档

### 6. `00:50:01-00:59:57`｜调试工具、MapReduce 延伸问题与代码组织

### 7. `00:59:58-01:09:56`｜Go 抽象、文件边界、timeout 与 task 重发

老师引用 Frans 的判断：Go 的 garbage collection 和 memory management 使学生较少处理 C++ 式 segfault 问题。接着学生问 `AppendEntriesArgs` 与 `RequestVoteArgs` 都有 `term` 时怎样复用 function。老师对 interface 细节并不确定；现场建议包括 type assertion/cast 或在 interface 中放 getters/setters。最终设计建议是不要强求抽象：若共同逻辑只需 term，就直接传 term；否则两个相近 functions 也可能更清楚。

学生可在 `raft` folder 添加任意数量的 `.go` files，没有命名硬性要求；grading 会替换 test/config 等 framework files，external dependencies 也可能在评分环境中不可用。RPC args/reply 用 pointers 的主要理由是避免复制可能很大的 structs。Locks 与 channels 可以并用。

Timeout 应从“为什么等待”推导。MapReduce task failure timeout 给了十秒，检查 sleep 较自由；Raft timeout 要给 leader 多次 heartbeat 机会并随机化，避免同时 election。老师没有确认适用于所有实现的毫秒数，应根据 heartbeat/RPC 频率和 tests 中的 traffic 调整。

Paper 区分 worker failed 后 restart task 与针对未失败 laggard 的 backup task；Lab 用 timeout 同时怀疑 failed 或 extremely slow worker，超时就 reissue，因此不保留精细区分。最后再次强调 machines 间只通过 RPC，本地 synchronization 不跨 server。完整问答、5 个掌握检查和待核对项见 [007](#section-07)。

### 8. `01:09:56-01:19:53`｜Race、阻塞调用、退出协议与读写可见性

课堂经验规则是修改 coordinator/Raft state 时 lock，常见形式为 lock 后 `defer Unlock`；但发送 RPC、向 channel send 等可能阻塞的操作不应包在该 lock 内，否则等待线程持续持锁，server 其他 threads 无法推进。

对 `isDone` 这类看似 benign race，老师要求用 atomic 或 lock。不能假设某次 read 漏掉 true、下次总会看到；课堂用 per-core/store buffer 说明 write 可能不向 reader 可见，进程甚至可能不退出。Locks 提供所需的可见性关系。

Worker 退出可通过 coordinator 对 `GetTask` 回复 `Done`；也可在 coordinator 关闭后由 worker 从 socket/connection failure 退出。Pull architecture 中 coordinator 不主动等待每个 worker acknowledgement，也可能先退出。把 workers 变成 RPC servers 后可主动发 exit，但老师认为收益不明显。`unexpected EOF` 高度 implementation-specific，课堂没有统一修复。

学生误读“不能编辑 main files”为“不能添加 files”，老师再次鼓励拆分自有 files。随后追问 writer lock、reader 不 lock 是否可行；老师说 read 也要同步，并以不同 cores 的 visibility 初步解释。多字段反例跨到下一段。完整问答、5 个掌握检查和待核对项见 [008](#section-08)。

### 9. `01:19:54-01:26:31`｜多字段一致性、粗粒度锁与 channel 阻塞语义

老师补完多字段反例：writer 在 lock 内依次更新 `a`、`b`，无锁 reader 可能先看到新 `b`、后看到新 `a`，从而读出 writer 从未共同持有的 pair。映射到 Raft，term 与 leader-state 可能组成不存在的 snapshot。并发实现必须依赖 language/platform guarantees，而不是偶然 compiler/processor 行为。

课堂结论是共享可变 state 的 read 也要 lock。只有孤立单 word 才勉强有讨论特殊处理的空间；lock-free 需要理解 compiler、language memory model、processor 和 memory consistency。简单 killed/boolean state 可用 atomic，相关 state 则用 coarse-grained lock 更便于确保“只有我在触碰”。

最后一个技术问答讨论 channels。Unbuffered channel 不限于一个 producer 和一个 consumer；多个 producers/consumers 都可参与，操作会等待匹配方。多个 producers 也不必机械把 buffer 设为 server 数量；是否 buffer 取决于 consumer loop 和允许的积压。老师对 ordering/fairness guarantee 明确不确定，只用 lock competition 类比，并未确认 FIFO 公平性。

## Q&A 教学顺序

### 1. 先交代 Q&A 范围与课堂路线（`00:00:05-00:01:25`）

本讲面向刚提交的 MapReduce Lab 1，也会谈一些可复用于后续实验的 Go 编程问题。老师邀请学生随时语音或在聊天区提问，然后给出五步 agenda：

4. 给出一般性建议；
5. 时间允许时回答现场问题和课前提交的问题。

这里首先建立的是讨论边界：课堂不是发布唯一标准答案，而是借一份方案解释设计选择。

### 2. 第一步：先定义 worker/coordinator 的通信 API（`00:01:41-00:03:32`）

老师从 `rpc.go` 开始，因为在写任务逻辑前，必须先决定两个角色怎样交流。他先区分三种 task type：

- `Map`：执行 Map 阶段工作；
- `Reduce`：执行 Reduce 阶段工作；
- `Done`：coordinator 告诉 worker 整个作业已结束，worker 应退出。

接着定义两类 RPC 的职责，而不是展示其完整代码：

- **GetTask RPC**：worker 请求工作；请求本身几乎不需要参数，coordinator 回复任务类型、该类型中的任务编号，以及执行所需元数据，例如 Map/Reduce task 数量。
- **FinishedTask RPC**：worker 告知 coordinator 某个具体任务已完成；参数需要标识 task type 与 task identity，回复内容并不重要。

课堂中的第一个真实学生插问是“能否把文件字体放大一些”（`00:02:18-00:02:26`）。老师调整显示后继续，未改变技术内容。

### 3. 第二步：为 RPC handler 准备 coordinator state（`00:03:40-00:05:19`）

有了通信契约后，老师转到 coordinator。coordinator 同时处理多个请求，因此状态首先包含一个 `Mutex`，用来防止多个并发执行流同时读写共享状态。

随后按用途列出状态：

- Map task 所需的输入文件信息；
- Map task 和 Reduce task 的数量；
- 哪些任务已经发出、哪些已经完成；
- 已发任务的时间戳，用来判断任务是否长时间未完成并需要重新发出；
- coordinator 是否已经完成整个作业的布尔状态。

在这个阶段，`GetTask` handler 先具备设置回复和识别“全部完成”的能力，但实际挑选任务的逻辑尚未补上；`FinishedTask` handler 则根据任务类型，把对应完成标记设为 true。老师借此强调一种实现顺序：先把 handler 的输入、输出和状态变化搭起来，再填调度策略。

### 4. 第三步：让 worker 形成请求、执行、汇报循环（`00:05:24-00:06:12`）

worker 的控制流被讲成一个循环：

1. 调用 coordinator 的 `GetTask`；
2. 根据返回类型执行 Map、Reduce，或在 `Done` 时退出；
3. 执行完成后调用 `FinishedTask`；
4. 回到循环再次请求任务。

此时仍只是 sender 和控制流骨架，Map/Reduce 的实际数据处理在下一步补入。这个顺序让通信错误与数据处理错误可以分开思考。

### 5. 第四步：处理临时文件与原子发布（`00:06:19-00:08:27`）

老师先提到为 intermediate file 添加辅助处理：创建 temporary file，并使用 `os.Rename`。随后说明 Map worker 的职责：读取输入文件，应用 Map function，把键值结果写入 intermediate files，并通过 atomic rename 发布，避免并发执行在最终文件上发生冲突。

Reduce worker 则读取“所有 Map task 为该 Reduce task 产生的中间文件”，汇总后排序，再对同一 key 的全部 values 应用 Reduce function，最后同样把 temporary reduce file 原子重命名为最终输出。

老师特别解释为什么 sorting 在 reducer 侧：单个 mapper 只能看到自己产生的部分 keys；reducer 才能收集属于该 reduce partition 的所有 Map 输出（`00:07:39-00:08:10`）。

### 6. 第五步：回到 coordinator，建立 Map-before-Reduce 的调度（`00:08:32-00:10:05`）

worker 完成后，剩下的复杂点是 coordinator 怎样决定“现在能发什么任务”。老师给出的阶段关系是：

1. 先尝试发出所有可发的 Map tasks；
2. 只有全部 Map tasks 完成后，才进入 Reduce tasks；
3. 如果当前没有可发任务但阶段又未完成，coordinator 必须等待某个状态变化，再重新检查；
4. 持续到所有 Map 和 Reduce tasks 完成。

片段结束时，老师刚提出“无任务可发时怎样等待”，具体的 condition variable 和唤醒机制留到第 2 段。

## 机制与权衡

- **先定 RPC 契约**：把角色边界和必要元数据先说清楚，可避免 worker 与 coordinator 各自形成不兼容的状态假设。
- **coordinator 持有控制面状态**：它记录任务分配、完成与超时信息；数据计算仍由 workers 执行。
- **Map/Reduce 阶段屏障**：Reduce 依赖全部 Map 输出，因此不能在 Map 尚未全部完成时开始发 Reduce task。
- **临时文件加 atomic rename**：先写临时结果，再原子发布最终文件，降低并发尝试或失败重试对可见结果的干扰。
- **worker 拉取任务**：本方案中 worker 主动发 `GetTask`，coordinator 作为 RPC server 回复；后续课堂会比较 coordinator 主动调用 worker 的替代方向。
- **时间戳支持重试**：已发任务长时间未完成时可重新发出，但本段尚未给出检查周期和等待实现。

本段无公式推导。课堂给出的是角色、状态和控制流依赖，不是复杂度或概率计算。

# 002｜Condition variable、阻塞 RPC 与等待位置

> **课堂时间**：`00:10:07-00:20:03`  
> **整理模式**：`transcript-only`；只记录口述机制与现场问答，不重建屏幕代码。  
> **复习标记**：`condition variable`、`predicate`、`Broadcast`、`timeout`、`liveness`、`blocking RPC`、`Done task`

## 本段在整讲中的作用

上一段留下的问题是：Map tasks 已全部发出但尚未全部完成时，coordinator 既不能发新的 Map task，也不能提前发 Reduce task，此时 `GetTask` 应怎样等待。本段先讲老师方案中的 condition variable，再由三组学生追问比较 sleep、周期检查、worker 端等待和 coordinator 端等待，形成 Lab 1 调度活性的核心 Q&A。

## Q&A 教学顺序

### 1. 用 condition variable 等待“有任务可发”（`00:10:07-00:11:13`）

老师先补完个人方案：当所有 Map tasks 都已分配、尚有任务未完成且没有任务超时时，coordinator 不能进入 Reduce 阶段，只能等待。Reduce 阶段也有相同情形。condition variable 让 handler 在当前 predicate 不成立时休眠，收到 signal 后回到循环顶部，再检查是否出现可发任务。

这里的 predicate 不是单一布尔字段，而是“当前存在可合法发出的 Map/Reduce task，或者整个作业已经结束”。老师强调唤醒后是重新检查，而不是默认某个具体任务必然可发。

### 2. 两类唤醒来源：完成事件与周期性超时检查（`00:11:13-00:12:59`）

老师列出状态可能改变的两个原因：

- worker 完成任务，可能使下一阶段变得可进入；
- 已发任务等待过久，可能意味着 worker failure，需要重新发出。

为覆盖超时，coordinator 启动一个 goroutine，隔一段时间执行 `Broadcast`，把等待者唤醒后重新检查时间戳。老师对演示中的具体间隔记不清，先说“每秒左右”，又提到可能是十秒，并明确说具体数值在此并不重要（`00:11:53-00:12:07`）。

另一处 `Broadcast` 位于处理 `FinishedTask` 的 handler：先把任务状态更新为 done，再唤醒等待的调度逻辑。老师用这一点总结个人方案：`Mutex` 保护 coordinator 共享状态，condition variable 负责等待状态变化。

### 3. 学生问：condition variable 到底适合什么问题？（`00:13:23-00:15:15`）

学生请求进一步解释 condition variable。老师把它定义为：当执行流要等待某个 predicate/condition 在未来异步变为 true 时，这是一种自然的同步工具。

Lab 1 中，“有 task 可发”会因 worker 完成或失败/超时而异步变真。因此 condition variable 不是为了保存任务数据，而是为了表达“条件暂时不成立，等变化后再判断”。老师补充，channels、condition variables 等高层同步原语最终建立在 locks 之上；它们提供了更贴近“等待条件”的推理方式。

### 4. 学生问：在循环里 sleep 是否一样？（`00:15:22-00:16:40`）

老师回答：周期 sleep 在某些工作负载下效果相近，但响应速度不同。若循环固定 sleep 一秒，即使 worker 在十毫秒后完成，也要等睡眠结束才会再次调度；condition variable 可以被完成事件立即唤醒，因此可能有更好的 liveness。

老师同时保留边界：如果每个任务本来都至少需要五秒，那么每秒轮询一次与 condition variable 的实际差距可能不大。这不是“sleep 一定错误”，而是及时性和简单性的权衡。

### 5. 学生问：暂时无任务时，worker 收到什么？（`00:16:44-00:19:47`）

学生把两个状态区分开：作业已经完成，和 Map 仍在运行但当前无任务可发。老师先回答最终完成状态：coordinator 返回额外的 `Done task`，并把自身 `isDone` 设为 true；worker loop 收到 `Done` 后退出。

学生澄清问的是“中间等待”。老师随后说明两种都可行的设计：

- **worker 等待**：coordinator 立即回复“现在没有任务”，worker sleep 后再请求；
- **coordinator 等待（老师方案）**：`GetTask` handler 暂不返回，worker 阻塞在 RPC call 上，直到 coordinator 真正有 task 可回复。

老师方案的 worker loop 中没有 sleep，因为阻塞发生在 RPC；condition variable 则在 coordinator 侧控制 handler 何时可返回。

### 6. 学生追问：把等待放在 coordinator 有什么优势？（`00:19:50-00:20:03`）

问题在本段末尾提出，答案跨到下一段：老师即将从 RPC 数量与网络流量比较两种方案。本节不提前吸收下一段结论。

## 机制与权衡

- **condition variable vs polling**：前者可在完成事件发生后立即唤醒；后者实现直观，但响应至少受 sleep interval 限制。
- **事件唤醒加周期唤醒**：完成事件负责及时推进阶段，周期 Broadcast 负责重新检查 timeout，二者覆盖不同状态变化来源。
- **等待在 coordinator**：减少 worker 重复请求，但会让一个 RPC handler 长时间阻塞。
- **等待在 worker**：coordinator 快速回复，worker 逻辑承担 sleep/retry，代价是额外 RPC traffic。
- **Done 与暂时无任务不同**：`Done` 表示全局终止；阶段内暂时无任务只表示需要等待。

本段无公式推导。可把课堂控制关系记为：

$$
\text{wake-up} \rightarrow \text{re-check predicate} \rightarrow
\begin{cases}
\text{return task}, & \text{task available} \\
\text{wait again}, & \text{otherwise}
\end{cases}
$$

该式只整理老师所说的循环，不增加实现细节。

## 例子与课堂提示

- `00:10:30-00:10:59` Map 全部分配但未完成：解释为什么不能发 Reduce，也不能忙等。
- `00:11:45-00:12:16` 周期 goroutine：解释 timeout 不会主动发信号时如何重新检查。
- `00:12:23-00:12:55` `FinishedTask` 后 Broadcast：解释完成事件怎样缩短下一次调度等待。
- `00:16:02-00:16:22` 十毫秒完成对比一秒 sleep：解释 liveness 差异。
- `00:18:43-00:19:47` worker sleep 与阻塞 RPC：解释等待责任可以放在不同角色。

## 常见误解纠正

1. **误解：condition variable 自己判断哪个 task 可发。** 纠正：它只负责等待和唤醒；被唤醒后仍要重新检查 predicate。
2. **误解：收到 signal 就保证条件已经成立。** 纠正：老师方案回到循环顶部再次检查。
3. **误解：`Done` 可以表示“现在暂时没任务”。** 纠正：`Done` 让 worker 退出；暂时无任务时老师方案保持 RPC 阻塞。
4. **误解：sleep 方案一定不能通过。** 纠正：老师说两种设计都可行，差异主要在及时性和通信行为。
5. **误解：课堂确认了固定检查周期。** 纠正：老师明确记不清演示中的一秒或十秒，且说本处具体数值不重要。

# 003｜`defer`、锁的执行上下文与 channel 调度备选

> **课堂时间**：`00:20:05-00:30:03`  
> **整理模式**：`transcript-only`；channel 示例被老师明确称为不完整且不同于 Lab 1 规格。  
> **复习标记**：`RPC traffic`、`defer`、`LIFO`、`goroutine`、`lock ownership`、`channel`、`buffered channel`、`task retry`

## 本段在整讲中的作用

本段先回答上一节的等待位置权衡，再借学生对 `defer` 和 goroutine 的追问澄清锁只属于本地并发执行。随后老师展示一个 channel-based 调度草图，目的只是说明 channels 如何在 coordinator 进程内部组织任务队列和 worker-specific goroutines，并非给出 Lab 1 的另一份完整实现。

## Q&A 教学顺序

### 1. coordinator 端等待可以减少重复 RPC（`00:20:05-00:20:29`）

老师回答上一段末尾的问题：worker 阻塞在一次 `GetTask` call 上时，大致是“一项任务对应一次请求”；若 coordinator 持续回复“无任务”，worker 就会 sleep、醒来、再请求，产生更多 network traffic。老师同时强调两种方案都可行并能工作，不能把这一权衡写成正确/错误二分。

### 2. 学生问：函数里启动 goroutine 时，`defer Unlock` 何时发生？（`00:20:30-00:23:46`）

老师按三个层次回答：

1. 新 goroutine 是独立运行的执行流；即使创建它的函数当前持有 lock，新 goroutine 也不会“继承已获得的锁”。
2. 创建函数中的 `defer Unlock` 在该函数返回时执行，任意 return path 都会触发。
3. 普通同步函数调用仍在同一执行流中运行；调用者持有的 lock 在进入和返回被调函数期间仍保持持有，除非代码明确解锁。

学生继续问多个 `defer` 的顺序。老师先口误说 FIFO，立即纠正为 LIFO：后注册的 deferred function 先执行。因此多个 defers 的顺序需要小心，而“lock 后立即 defer unlock”是很实用的策略。

### 3. 先划清服务器边界：本地锁不跨 RPC（`00:23:49-00:24:39`）

老师汇总此前讨论的替代同步设计，并特别澄清：课堂展示的 Mutex、condition variable 或 channel 都是在单个 server/process 内协调 threads/goroutines。worker 与 coordinator 之间只通过 RPC 通信；coordinator 上的 lock 与 worker 上的 lock 互不干涉。这个边界是理解后续 channel 示例的前提。

### 4. 引入一个“不同于 Lab 规格”的 channel 草图（`00:24:39-00:26:14`）

示例假设 coordinator 接收一个 `workers` channel，外部组件通过它报告 worker 加入、失败后重启等变化。coordinator 内另有：

- `tasks` channel：把待做任务交给负责调用 worker 的本地 goroutine；
- `done` channel：收集任务完成通知。

老师当场纠正自己的说法：不能通过 channel 直接把任务跨服务器发给 worker。channel 只连接 coordinator 内部执行流；真正跨服务器的动作仍是 RPC。

### 5. 为每个 worker 建一个发任务的 goroutine（`00:26:14-00:26:42`）

一个 coordinator goroutine 持续从 `workers` channel 读取 worker identity。每看到一个 worker，就启动一个 `issueWorkerTaskThread`，由该执行流专门向对应 worker 发 RPC。这样 worker 的动态加入被转换成本地 goroutine 的创建。

### 6. buffered task queue 与完成计数（`00:26:47-00:27:54`）

coordinator 把 `numTask` 个任务放入 buffered `tasks` channel，容量也设为 `numTask`，因此初始装入整个任务集合时不会因队列容量不足而阻塞。随后 coordinator 从 `done` channel 读取 `numTask` 次，以完成通知数量判断全部任务结束；之后关闭 `tasks` channel并退出。

老师明确简化了示例：这里没有区分 Map 与 Reduce，只把它当成一组待运行任务。

### 7. RPC 失败时把任务放回 channel（`00:27:54-00:29:54`）

每个 worker-specific goroutine 从 `tasks` channel 取一个 task，再通过 RPC 调用 worker。调用成功就向 `done` channel 发完成通知；调用失败或超时，就把 task 重新放回 `tasks` channel，让其他 worker 或同一执行流以后重试。

`tasks` channel 被 coordinator 关闭后，range/读取循环退出；另一个 `exit` 信号用于停止监听新 workers 的 goroutine。老师再次提醒：这是复杂示例，且不完全符合 Lab 1 指定架构，只用于展示 channel 可以怎样表达队列和工作流。

### 8. 聊天区发现 `exit` 未定义（`00:30:00-00:30:03`）

问题刚出现便到达分段边界；老师的修正位于下一段，本节不提前补答案。

## 机制与权衡

- **长轮询式阻塞 RPC**：减少 repeated polling RPCs，但让 server handler 等待更久。
- **`defer Unlock`**：覆盖多个 return path，降低漏解锁风险；多个 defers 按 LIFO 执行。
- **锁不被 goroutine 继承**：新执行流必须自行获取访问共享状态所需的锁。
- **channel 是进程内队列**：它可连接 coordinator goroutines，不能替代跨机器 RPC。
- **buffered channel**：容量足够时可一次装入全部 tasks；容量选择与“初始发送是否阻塞”直接相关。
- **失败重入队**：RPC failure 后把 task 放回队列，使任务不因某个 worker 不可达而丢失。

本段无公式推导。完成判断的课堂级关系是：收到 `numTask` 个 `done` 通知，才认为这个简化任务集合完成；老师没有在此处理重复完成通知等扩展情形。

## 例子与课堂提示

- `00:20:05-00:20:21` 一项 task 一次 RPC 对比 polling：用于解释 network traffic。
- `00:21:38-00:22:58` 多个 defers 的 LIFO 顺序：用于提醒 unlock 与其他清理动作的先后。
- `00:24:17-00:24:37` 不同 servers 的 locks 互不关联：用于纠正“分布式锁从本地 Mutex 自动获得”的误解。
- `00:26:49-00:27:17` 容量为 `numTask` 的 buffered channel：用于说明初始入队不阻塞。
- `00:28:42-00:29:02` RPC 失败后 requeue：用于说明 worker failure 下任务如何保留。

## 常见误解纠正

1. **误解：创建 goroutine 会把当前 lock ownership 一并传过去。** 纠正：老师说新 goroutine 不从“已持锁”状态开始。
2. **误解：`defer` 按注册顺序 FIFO 执行。** 纠正：老师当场纠正为 LIFO。
3. **误解：调用普通 helper function 会自动释放调用者的 lock。** 纠正：同一执行流在函数调用期间仍持锁。
4. **误解：coordinator 可用 Go channel 直接联系远程 worker。** 纠正：channel 只在本 server 内；远程通信仍由 RPC 完成。
5. **误解：channel 示例是完整 Lab 1 参考实现。** 纠正：老师明确说它不完整、没有分 Map/Reduce，且架构与 lab specification 不同。

# 004｜Channel 方案追问：RPC 方向、状态保护与失败边界

> **课堂时间**：`00:30:03-00:40:02`

## 本段在整讲中的作用

这一段几乎全部由学生追问推动。大家检查 channel 草图中的缺失变量、worker 来源、循环计数、回队列性能和失败场景，老师据此明确哪些部分未展示、哪些架构虽可能但不是 Lab 1 引导方向，并给出 Mutex 与 channels 的选择准则。末尾从替代设计转向通过测试但不理想的 Lab 1 方案。

## Q&A 教学顺序

### 1. 聊天区问：`exit` 在哪里定义？（`00:30:03-00:30:23`）

老师承认示例里没有定义，这是学生发现的真实缺口。他说 `exit` 可以和 `done` 类似，是另一个传递 boolean 的 channel。这个回答进一步证明屏幕内容只是说明思路的草图，不是完整实现。

### 2. 学生问：谁把 worker 放进 `workers` channel？（`00:30:27-00:31:36`）

老师说明该 channel 是传给 coordinator 的输入。可以想象 `mrcoordinator` 的 main 层负责跟踪 worker crash、恢复和新 server 加入，再把 worker ID 放入 channel。示例没有展示这部分；它假设存在一个外部 worker-membership 管理者。

这与 Lab 1 实际提供的接口不同，因此不能把这一假设反推为实验要求。

### 3. 学生问：Lab 1 能否由 coordinator 主动 RPC worker？（`00:31:38-00:32:42`）

老师回答“可以”，但不是实验引导的方向。要让 coordinator 主动 `call_worker`，workers 需要成为 RPC servers，coordinator 成为 RPC client；或者仍可改变 handler 分工，让 worker 发某些请求。核心是 RPC 方向由谁暴露 server endpoint 决定。

Lab 1 更自然的给定方向是 coordinator 作为 server、workers 主动请求 task。替代方向在概念上可行，但会改变启动、发现和连接职责。

### 4. 学生问：完成计数循环能否不用 `i`？（`00:32:45-00:34:02`）

学生想用无限 `for` 加 `select` 代替计数循环。老师指出无论语法怎样写，都必须保存“已经从 `done` 读了多少次”的状态，因为不是收到一次就完成，而是要收到 `numTask` 次。`i` 不是因为 Go 强制要求未使用循环变量，而是这个逻辑确实需要计数。

### 5. 学生问：从 `tasks` 取出失败后再放回，有什么问题？（`00:34:03-00:35:00`）

老师说在该例中不会因回放本身阻塞：先取走一个元素腾出 buffer，再放回一个元素；`tasks` 又是 buffered channel。性能方面，channels 内部用 locks，直接 locks 通常更轻量，但老师预计这里不会有巨大性能影响。

老师没有声称此模式在任意容量、任意并发条件下都不阻塞；判断限定在展示的 channel 容量与“一取一放”流程。

### 6. 学生问：一开始如何在 Mutex、channel 或混合方案间选择？（`00:35:00-00:37:10`）

老师给出按问题形状选择的经验：

- **Mutex** 自然地保护一块共享 state。例如 coordinator 状态或 Raft log，每次修改时确保没有其他执行流同时修改。
- **channel** 适合等待某类值、命令或工作 ready，像 task queue 或已有的 apply channel；老师把它类比成一种更具体的 condition variable/queuing system。
- 对大多数 shared-state modifications 和 race conditions，locks 更直接、更容易推理。

老师并不排斥混合使用；关键是不要为了 channels 而把简单的共享状态保护改造成曲折的消息握手。

### 7. 学生问：worker-specific goroutine 自己崩溃怎么办？（`00:37:12-00:39:39`）

问题先区分两种失败：

- `call_worker` 返回 false：远程 worker 不可达，当前 goroutine 仍活着，可把 task 放回队列继续循环；
- goroutine 本身 crash：课堂采用的模型是 goroutine crash 会导致整个 process crash，而不是只悄悄丢失这一条执行流。

若某个远程 worker 永久失败，与它绑定的 goroutine 可能不断尝试、不断得到 false。大量 workers 失败又有新 workers 加入时，可能留下许多无法联系旧 worker 的 goroutines。等全部 tasks 完成、coordinator 关闭 channel 后，这些 goroutines 才退出。老师把它作为设计的潜在资源问题，而不是说该草图已经优雅解决 worker lifecycle。

### 8. 转向常见但能通过测试的设计问题（`00:39:39-00:40:02`）

老师结束 channel 示例，开始谈 Lab 1 中看到的 common but passing mistakes。第一个是把过多工作推给 coordinator，使其成为 bottleneck；具体例子在下一段继续。

## 机制与权衡

- **pull architecture**：worker 请求任务，符合 Lab 1 给定方向，coordinator 不必发现并主动连接每个 worker server。
- **push architecture**：coordinator 主动调用 worker，需要 workers 暴露 RPC server，并解决 worker registration/lifecycle。
- **Mutex vs channel**：前者保护共享 state，后者表达队列、ready event 或命令流；可混合，不必二选一。
- **requeue retry**：RPC 返回失败后保留 task，但不会自动回收永久失联 worker 对应的 goroutine。
- **示例完整性**：未定义 `exit` 和未展示 worker registry 是课堂主动承认的缺口。

本段无公式推导。`numTask` 次完成通知只是简化示例的计数规则，课堂未讨论重复通知去重。

- **checkpoint vs replicated coordinator**：checkpoint 简单且符合小状态、deterministic job；Raft 提供更强复制但复杂度可能不成比例。
- **combiner tradeoff**：Map 后局部合并可减少中间条目；它不替代 reducer 对完整 partition 的 sorting。
- **local intermediate files**：节省 network bandwidth；最终输出才写共享存储。
- **代码拆分**：减少巨型文件和重复状态更新，但过度抽象也可能在下一段被质疑。

本段无公式推导。老师没有给出 checkpoint interval、partition size 或性能数字。

### 1. Go 相比 C++ 少掉哪些调试负担？（`00:59:58-01:00:30`）

### 2. 学生问：两个不同 structs 都有 `term`，能否共用一个 function？（`01:00:31-01:03:26`）

学生以 `AppendEntriesArgs` 和 `RequestVoteArgs` 为例，希望 function 接受“任何含 term field 的 struct”。问答经历了几次修正：

1. 老师先说普通 function 参数需要具体 type；
2. 学生澄清要跨两个 types 复用；
3. 老师表示可能使用 `interface`，但明确说自己不确定细节；
4. 现场补充意见是：若传 interface，访问具体 field 前需要 type assertion/cast，或者在 interface 中定义 getters/setters，通过方法访问；
5. 老师最后建议不要为了复用而强迫不同 types 进入复杂抽象。若共同逻辑只需要 `term`，最简单的是让 helper 直接接收 term value；否则两个相似但不同的 functions 也可接受。

### 3. 学生问：拆成多个 files 有命名约定吗？（`01:03:27-01:04:41`）

老师说放在 `raft` folder 内即可，没有特定命名规范，可创建任意数量的 `.go` files。grading scripts 会替换属于 testing framework 的必要 files，例如 config/test files，因此修改这些文件会被覆盖。

老师还提醒谨慎使用 external dependencies，例如 GitHub Go packages；评分环境可能缺少这些依赖。这个回答把代码组织自由与提交环境约束分开：自有 `.go` files 可以增加，测试框架和外部包不能随意假设。

### 4. 为什么 RPC `args` 和 `reply` 常用 pointers？（`01:04:42-01:05:08`）

老师回答 pointer 可避免调用时复制可能很大的 structs，因此 passing by reference 可能更便宜。这是性能和可修改 reply 的接口背景；课堂没有比较 escape analysis 或具体 copy cost。

### 5. Locks 与 channels 能否同时使用？（`01:05:09-01:05:18`）

老师直接回答可以，并说在 Raft 会同时用到。它呼应第 4 段的选择准则：不同原语解决不同形状的问题，混合使用不是冲突。

### 6. Timeout 应怎样选择？（`01:05:19-01:07:43`）

老师先区分 Lab 1 与 Raft：

- MapReduce Lab 对 worker task 给出十秒 failure timeout；至于检查循环 sleep 多久，学生有较大自由。
- Raft tests 对 timeout 更敏感，但老师口述的可行毫秒范围字幕不清，不能提炼为精确推荐。

选择 timeout 的方法是先问“为什么等待”：Raft follower 用 election timeout 判断 leader 是否可能死亡，因此应允许收到若干次 heartbeat，而不是一个 heartbeat 稍晚就开始 election；还需随机化范围，避免所有 servers 同时发起 elections。老师以大约两到三次、或两到五次 heartbeat 作为思考尺度，但强调实现相关、没有适用于所有人的完美数字。

更通用的指标是：在 timeout 前希望给对端多少次 RPC/heartbeat 机会，以及 tests 是否显示 RPC/bit 数量过多。这个推理方式也适用于 Lab 1 的重试周期，但具体机制不同。

### 7. Paper 的 backup tasks 与 Lab 1 timeout 重发有何区别？（`01:07:47-01:09:16`）

有学生实现了 backup tasks，老师说很有意思但 Lab 1 不要求。paper 区分：

- **restart/reissue after worker failure**：worker 被判断失败，原任务必须重新执行；
- **backup task for a laggard**：原 worker 未失败，只是执行太慢，为缩短尾部时间再启动一份相同任务。

paper 中 coordinator 通过 worker heartbeats 区分 failure；Lab 1 简化设计用同一个 timeout 同时覆盖“可能失败”和“极慢”，超时就重发，因此没有清晰保留 backup-task 与 failure-restart 的区别。

# 008｜Race、阻塞调用、退出协议与读写可见性

> **课堂时间**：`01:09:56-01:19:53`  
> **整理模式**：`transcript-only`；关于 memory model 的表述按课堂回答记录，不扩展为 Go 语言规范。  
> **复习标记**：`data race`、`lock`、`blocking RPC`、`channel send`、`atomic`、`memory visibility`、`Done reply`、`closed socket`、`unexpected EOF`

## 本段在整讲中的作用

本段把 Lab 1 的 concurrency 问题从“用哪种原语”推进到“何时必须持锁、何时必须释放”。老师先给出共享 state 的粗粒度锁规则，再解释持锁执行 RPC/channel 操作会阻止整个 server 前进。随后回答所谓 benign race、worker/coordinator 的退出方式和 `unexpected EOF`，并通过学生追问深入到无锁 read 是否能看到最新 write。论证在分段末尾尚未完成，由第 9 段接续。

## Q&A 教学顺序

### 1. 修改 server state 时 lock；可能阻塞的调用外不要持锁（`01:09:56-01:10:48`）

老师给出的经验规则是：修改 coordinator 或 Raft server state 时要 lock，常见函数入口就是 lock 后立刻 `defer Unlock`。例外不是“该状态不重要”，而是执行可能阻塞的操作前应释放锁，例如发送 RPC、向 channel 发送数据。

原因是调用线程可能长期等待；若同时持有 server 的共享 lock，其他 threads 无法取得锁，整个 server 的 state machine 可能停止推进。

### 2. “Benign” data race 仍要处理（`01:10:48-01:12:35`）

老师以 `isDone = true` 为例：开发者可能认为某次 read 暂时没看到 true 也没关系，下次会看到，因此 race 是 benign。课堂回答反对这种推理：race detector 已指出缺少同步，行为没有课堂所需的保证。简单布尔状态可用 atomic operation，或在访问前后 lock/unlock。

老师进一步用 visibility 解释：一个线程的 write 可能留在某种 buffer 中，另一个线程不一定看到；锁建立同步，使后续 reader 看到先前 write。最坏的课堂例子是 process 可能永远观察不到 `isDone`，从而不退出。

### 3. Worker 怎样“干净退出”？（`01:12:36-01:13:01`）

老师列出多种都可接受的方案：coordinator 通过 worker 的请求回复退出信号；或者 coordinator 结束并关闭 socket，worker 下次 RPC 失败后退出。课堂称后者较“messy”，但仍认可其功能性。

### 4. `unexpected EOF` 应怎样处理？（`01:13:02-01:13:35`）

老师说这个错误何时由 client 触发有些 confusing，且高度依赖具体实现。如果学生在奇怪时机遇到，需要查看该实现；没有足够上下文时不必过度担心。课堂未提供统一根因或修复步骤。

### 5. 学生追问：coordinator 要等 workers 都退出吗？（`01:13:35-01:16:21`）

学生担心某个 worker 很久后才来请求 task，而 coordinator 在 `Done()` 为 true 后已经 shutdown。老师先纠正措辞：在 pull 架构中 coordinator 不是主动“发送 Exit RPC”，而是在 worker 的 `GetTask` 请求上回复“done, please exit”。coordinator 不等待 worker acknowledgement，也可能先于 worker 退出。

若 worker 之后才联系 coordinator，它看到 connection closed，随后退出。若真的要 coordinator 主动逐个发送 exit 并等待，可以把 workers 做成 RPC servers，但老师认为这没有明显 utility。Lab 的“足够干净”退出允许 coordinator 先结束。

### 6. 学生问：未来 labs 能添加更多 files 吗？（`01:16:23-01:17:15`）

老师再次确认可以，而且几乎鼓励拆分。学生此前把“不能修改其他 main files”误读成“只能有指定三个文件”；老师澄清限制是不要修改提供的 main/framework 文件，不是禁止增加自己的 source files。

### 7. 学生追问：为什么一个 read 与多个 writes 也算危险？（`01:17:16-01:19:53`）

学生认为 read 总能发生在 write 之前或之后，因此不理解 undefined/unsynchronized behavior。老师用多核与 store buffer 的课堂模型解释：不同 threads 可在不同 cores 上，write 没有 lock 时可能停留在写线程的 buffer，reader 可能一直看不到新值；locks 会建立/刷新所需的可见性。

学生进一步问“write 有 lock、read 没 lock是否可以”，老师回答 read 也需要 lock。另一位发言者补充：若程序依赖多个相关字段，reader 可能看到彼此不一致的时刻。具体的多字段顺序例子跨到下一段；本节只保留问题和初步回答。

## 机制与权衡

- **粗粒度 state lock**：容易知道何时只有一个执行流修改 state，便于推理；持锁时间过长则会降低并发。
- **阻塞边界**：RPC/channel operation 可等待外部事件，持锁跨越它们可能让其他 server threads 无法进展。
- **atomic vs Mutex**：单个简单状态可用 atomic；一组相关 state 通常需要 lock 保持一致观察。
- **reply-based shutdown**：适合 worker pull model，不要求 coordinator 知道每个 worker 的 server endpoint。
- **socket-close shutdown**：实现简单但 worker 通过错误得知结束；老师仍视为可接受。
- **EOF 诊断**：必须结合具体 call path，transcript 没有一刀切答案。

本段无公式推导。课堂的顺序约束可概括为：

## 本段在整讲中的作用

这是本讲技术内容的收尾。老师与学生补完“reader 为什么也要 lock”：多个相关字段可能以不同顺序对其他 core 可见，reader 会拼出系统从未真实拥有过的状态。随后讨论何时用 atomic、为什么粗粒度 lock 有利于推理，并纠正“unbuffered channel 只能连接两个 goroutines”与“多个 producers 必须配置足够大 buffer”的误解。最后老师把后续问题移到 office hours；Vim color scheme 的闲聊不属于 Lab 机制。

## Q&A 教学顺序

### 1. 多字段无锁 read 可能看到不存在的组合（`01:19:54-01:20:50`）

老师续接上段：假设 thread 1 在 lock 内依次赋值 `a`、`b`，另一个不加锁的 thread 可能先看到新 `b`，后看到新 `a`。如果程序分别读取 term 和“是否 leader”等相关字段，就可能组合出一个在 writer 的受保护 state 中从未同时存在的 pair。

因此问题不仅是单个值 stale，而是跨字段 invariant 被破坏。并发实现必须依据 platform/language 提供的 guarantees 推理，不能依据“通常按源码顺序传播”的直觉。

### 2. 学生确认：只要读共享 server state 也要 lock 吗？（`01:20:53-01:23:18`）

课堂回答是“要”。老师说，只有单个 machine word 的孤立读写才勉强有讨论特殊处理的空间；一旦读取多个 pieces of data，无锁推理会迅速复杂化。要玩 lock-free 技巧，需要真正理解 compiler、language memory model、processor 与 memory consistency，成本很高；即使当前 compiler 上看似工作，未来也没有课堂所需保证。

学生觉得给单次 read 包 lock/unlock 很烦。老师建议简单状态可考虑 atomic bool 一类工具；对大部分 server state，coarse-grained lock 反而方便，因为可以确定自己是唯一触碰这组状态的执行流。课堂没有提供 lock-free Lab 方案。

### 3. 学生问：channel 是否只能在两个 threads 之间？（`01:23:22-01:24:13`）

学生担心 unbuffered channel 会永久阻塞，并推断 election 类 channel 的 buffer 必须等于 server 数量、unbuffered 只能一对一。老师否定这两个绝对结论：channel 可以有多个 consumers，也可以有多个 producers；unbuffered send 会等待某个 receiver，但并不要求参与者数量只能是两个。

### 4. 多 producers 是否一定需要 buffered channel？（`01:24:13-01:25:24`）

老师继续说“不一定”。若 consumer 在循环中持续接收，多个 producers 可以分别等待并最终由 consumer 接走。是否会阻塞、是否能及时被调度取决于整体 schedule 和消费逻辑，buffer 并不是“允许多 producer”的必要条件。

谈到 ordering/fairness guarantees 时，老师转而询问其他教师，并以 lock acquisition 作类比：多个执行流一直竞争时，不应轻易假设某一个一定在有限时间内获得机会；他提到这种情况下 randomization 可能有用。老师的表述带有明显不确定性，transcript 没有形成正式的 Go channel fairness 结论。

## 机制与权衡

- **单值可见性 vs 多字段 invariant**：即使每个 field 都能单独读取，缺少共同 synchronization 仍可能得到不一致组合。
- **atomic vs coarse lock**：atomic 适合孤立简单状态；coarse lock 可让一组相关 state 的读写形成可推理的整体。
- **unbuffered channel**：send/receive 需要 rendezvous，会阻塞等待对端，但参与者可多于两个。
- **buffered channel**：解耦一部分 producer/consumer 时序；容量大小应由允许积压多少消息决定，而不是机械等于 producer 数。
- **fairness 不确定性**：课堂没有确认正式排序保证，不应从本段推出 FIFO producer fairness。

本段无公式推导。多字段反例可忠实表示为：

$$
\text{writer states}: (a_0,b_0) \rightarrow (a_1,b_1)
$$

而无锁 reader 可能观察到课堂所说的混合 pair：

$$
(a_0,b_1)
$$

该 pair 用于表达老师的口头例子，不声称是唯一可能的重排序结果。
