## 概览

本讲是围绕 Lab 2A/2B 提交问题展开的 Q&A。课堂先建立以 test、hypothesis 和 RPC trace 为核心的调试方法，再沿一种具体但非唯一的 Raft/Go 结构讨论 goroutine、coarse-grained locking、election timer、`RequestVote`、heartbeat/`AppendEntries`、`Start`、commit 与 apply channel。最后的自由问答集中在真实 bug：timer goroutine leak、用超长 timeout 掩盖 failure、nil channel、heartbeat-only replication 的进展速度，以及 race detector 能否证明共享读取安全。

这些笔记只以本讲 transcript 为事实边界。课堂展示的代码组织、timer 数值和 helper naming 都作为案例与 tradeoff 记录，不整理成可直接提交的 Lab solution；遇到讲者明确表示不确定的片段，也保留不确定性。

## 学习主线

1. **先让失败可解释**：从 test scenario 出发，提出可证伪 hypothesis，用稳定、细粒度 RPC trace 验证。
2. **再划清 concurrency boundary**：共享 Raft state 在 lock 内原子变化，RPC/channel 等可能阻塞的操作不跨 lock，reply 回来后重验 term/role/context。
3. **按协议因果链复习**：timer 触发 election，RequestVote 受 term 与 log freshness 约束，leader 用 AppendEntries 复制，majority 与 current-term rule 推进 commit，单一 applier 按序输出。
4. **用 test behavior 反查误解**：偶尔通过、调大 timeout、只靠 heartbeat、race detector 无报告，都不是单独成立的正确性证明。

# 001｜怎样用测试与日志形成可证伪的调试闭环？

## 本节角色

- **时间范围**：`00:00:03–00:09:34`
- **核心问题**：Lab 2A/2B 的失败往往依赖并发时序，怎样避免靠猜测改代码，而是从测试和 RPC trace 中定位具体失效场景？
- **在全讲中的位置**：这是后续 voting、heartbeat、`Start` 与 commit 讨论的方法论入口。讲者先说明实现顺序，再回答提交问题中出现最多的 debugging 困惑。
- **边界**：本节只整理课堂给出的调试流程和日志原则，不推导任何可直接提交的 Raft 实现。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：面对一个尚未通过的 Lab，第一步是什么？

**A：从第一个 test case 开始。** 即使尚未写代码、测试必然失败，它仍提供了一个明确的行为目标。结合 lab hints 写出最小一段相关代码后立即重跑；通过就进入下一个 test，失败则停下来研究当前 test。

课堂给出的重点不是“先把完整 Raft 写完”，而是让测试逐步限定问题空间。test name 往往提示它覆盖的 scenario，测试代码则说明它怎样建立 leader、断开 peer、等待 agreement 或检查 apply 结果。

### Q2：测试失败后，是否应该先尝试一个看起来可疑的改动？

**A：不应该先改。** 先形成一个能被证据推翻的 hypothesis：测试构造了什么场景，自己的状态转换或消息处理为何会在该场景下失效。随后用 trace 检查 hypothesis，必要时增加更细日志，再修正代码并重跑同一个测试。

讲者甚至会把 hypothesis 写进文本文件，分别收集 supporting evidence 与 counter-evidence。这样修复有清楚理由，而不是把 bug 从一个 corner 移到另一个 corner；偶然通过一次测试也不能证明猜测正确。

### Q3：这里所说的“messages”具体指什么？

**A：所有 RPC。** 讲者使用 `util.go` 中的 `DPrintf`，系统记录协议运行中的消息，以便从失败点向前追踪。日志不是事后临时加的一两行，而是持续存在的 protocol trace。

### Q4：日志粒度应该怎样选择？

**A：倾向于 fine-grained，先尽量收集，再过滤。** 原因是分析之前未必知道需要哪一层信息；若日志已经完整，就不必为了增加一个字段而重新等待偶发失败。讲者把输出导入 editor，或用 `grep` 之类的 Unix utility 筛出关注的 peer、RPC 或事件。

### Q5：怎样让大量输出仍然可读？

**A：固定每行格式。** 课堂明确提到至少让 source、destination 和 RPC 本身容易识别。稳定格式使文本过滤可靠，也让同一条消息链可以沿发送者、接收者和事件类型串起来。

### Q6：debug print 怎样进入 log file，而不是只出现在 standard output？

**A：把 standard output 重定向或 pipe 到文件。** 课堂回答没有引入额外 logging framework；基本工具已经足以保留完整失败现场。

## 机制梳理

调试闭环可以概括为：

1. 运行一个明确的 test case，并保存输出。
2. 读 test，写下它试图建立的 distributed scenario。
3. 提出关于错误状态或错误消息顺序的 hypothesis。
4. 从 RPC trace 的异常结果向前回溯，寻找最早偏离预期的位置。
5. 用新增日志、重复运行或反例证据确认或推翻 hypothesis。
6. 只在证据支持后修复，并用同一个 test 验证，再进入下一项。

这里的关键不是日志越多越好，而是日志必须能回答三个问题：**哪个 server、在何时、对哪条 RPC 做了什么**。后面的 timer、term、vote、log index 等字段都服务于这个目标。

## 例子与取舍

- **例子：测试名称提供线索。** 若测试名称表明它在检查 backup 或 agreement，就先读测试如何 disconnect/reconnect peers，而不是把所有失败都归因于 election。
- **例子：从失败向后找。** 当最终表现是没有 commit，trace 应先定位哪一步不再前进，再向前检查对应的 RPC 与状态变化，而不是只看最后一行报错。
- **取舍：全量记录 vs. 运行成本。** fine-grained logging 会生成大量文本，但能减少复现低概率并发 bug 的次数；课堂选择先保存完整信息，再用格式与过滤降低认知负担。
- **取舍：简单工具 vs. 调试基础设施。** 本节讲者本人使用 `DPrintf`、文件和文本过滤，认为结构清楚比工具复杂更重要；更强的可视化留到下一节。

## 常见误解

- **误解：测试偶尔通过，说明修复正确。** 并发测试的一次成功可能只是时序改变；必须让 trace 支持因果解释。
- **误解：看到可疑代码就先改，测试能告诉我对不对。** 这种做法可能掩盖原 bug 或制造新的 interleaving，缺少可证伪判断。
- **误解：只在失败后补几条 print 就够。** 加日志本身会改变 timing；持续、同粒度的 trace 更可能保存原始失败现场。
- **误解：日志只需要写“进入某函数”。** 没有 server、方向和 RPC 内容，跨节点事件无法重建。

## 掌握检查

1. 为什么“读测试并形成 hypothesis”必须发生在改代码之前？
2. 一条用于 Raft 调试的日志，至少应带哪些上下文才能跨 peer 追踪？
3. 如果修复后测试只通过一次，哪些证据仍然缺失？
4. fine-grained logging 为什么反而可能减少总调试时间？
5. 你能否为一次“未达成 agreement”写出一个具体、可被 trace 推翻的 hypothesis？

## 掌握检查参考答案

1. 先读测试才能明确它构造的 scenario，并提出可由 trace 推翻的原因；先改代码会失去判断改动是否针对 root cause 的依据，还可能只把 bug 移到别处。
2. 至少要有发出事件的 server/source、destination、RPC 类型与内容，并保持固定格式；elapsed time 还能帮助还原事件顺序与等待时长。
3. 仍缺少完整 trace 对因果链的支持、counter-evidence 的排除，以及重复运行中该解释仍成立的证据；一次成功可能只是并发 timing 改变。
4. 它在偶发失败发生时已保存完整前史，之后可直接过滤所需字段，不必新增 print、改变 timing 后再等待复现。
5. 例如：“重连后仍未 agreement，是因为预期发送的 RPC 没有发出。”若 trace 显示该 RPC 已按稳定格式从目标 server 发往目标 peer，这个 hypothesis 就被推翻，应继续向后检查消息链。

## 复习项

- [ ] 能口述 `test → scenario → hypothesis → trace → fix → rerun` 的闭环。
- [ ] 能解释为什么测试代码本身是调试证据，而不仅是评分工具。
- [ ] 能为 RPC log 设计稳定字段，并说明每个字段回答什么问题。
- [ ] 能区分“测试现象”“关于原因的 hypothesis”和“支持 hypothesis 的 trace”。
- [ ] 能说明盲目调 timeout 或改条件为什么可能只是转移 bug。

# 002｜日志怎样把 election、partition 与偶发并发 bug 变成可读事件？

## 本节角色

- **时间范围**：`00:09:35–00:18:38`
- **核心问题**：当 2B backup test 产生数千行日志，怎样编码时间、topic 和 server，使 election 与 log replication 的因果链可见？若加入 logging 后 bug 消失，又怎样保留失败证据？
- **在全讲中的位置**：承接第 001 节的调试闭环，TA Jose 展示一种日志呈现工具，随后讲者回答 timing-sensitive failure 的复现问题。
- **边界**：课堂只展示诊断方法；颜色、列布局和 Python `rich` 都是工具选择，不是 Raft 正确性的组成部分。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：一条结构化 Raft 日志可以怎样组织？

**A：用稳定列编码 elapsed milliseconds、topic、server 和 free-form message。** elapsed time 有助于检查 timer event 与 RPC failure 花了多久；topic 按 Raft 事件分类，例如 timer、election、vote、log、commit/apply；server 列指出发出事件的 peer；最后一列保留具体上下文。

Jose 特别说明 topic 不是有高低顺序的 log level，而是互相独立的事件类别。不同类别频率不同，后处理时可以选择保留或隐藏。

### Q2：为什么要把格式化与着色放到 Python，而不是 Go？

**A：Go 侧只输出简单、稳定的数据，Python 侧负责 coloring、structuring 与 filtering。** 这样协议代码不承担复杂呈现逻辑，而脚本可以利用现成库；课堂示例主要使用 `rich`，规模约一百行。

### Q3：颜色和按 server 分列究竟帮助了什么？

**A：它们降低了重建跨节点顺序的认知成本。** 在三 peer 的 election test 中，按列后能直接看到三个 server 启动、一个成为 candidate、另外两个投票、获得多数后成为 leader，之后持续 heartbeat。timer topic 太密时可以隐藏；vote、leader、commit/apply 则用不同颜色形成视觉模式。

### Q4：backup test 中怎样看 partition 行为？

**A：把测试动作也写入 trace。** 示例先识别 `S0` 为 leader，再断开 `S2–S4`。左侧两个 peer 没有 majority，因此收到的 entry 不会 commit。随后断开左侧、重连右侧三个 peer，右侧形成 majority，出现新的 candidate/leader；绿色和紫色的“阶梯”显示 entry 被接收、传播与 apply。

大量 dropped RPC 会掩盖主线，因此工具可以临时忽略对应 topic。过滤是保留原始数据后的视图选择，不是从源头停止记录。

### Q5：如果加入 debug print 后 bug 不再出现，怎么办？

**A：始终以相同、较细粒度记录，并重复运行很多次，分别保存每次日志。** logging 可能改变 timing，但长期反复测试仍可能触发原 bug。讲者会让测试 overnight 运行，保留全部 run，出现失败后只深入研究那一份 trace。

## 机制梳理

结构化日志把 execution 映射为两个维度：

- **横向是 peer**：每一列固定对应一个 server，便于识别谁是 candidate、谁投票、谁被 partition。
- **纵向是时间**：elapsed milliseconds 保留 timer、RPC latency 和状态转换顺序。
- **topic 是可切换的观察层**：timer 太密可隐藏；排查 election 时保留 vote/leader；排查 2B 时保留 log/commit/apply。
- **测试事件是外部因果标记**：disconnect、reconnect、leader detection 若不进入 trace，协议事件就缺少场景边界。

对于 Heisenbug，机制不是试图消除 logging 的 timing 影响，而是避免“失败后才改变 instrumentation”。固定 instrumentation 加多次独立运行，能让某次失败保留完整前史。

## 例子与取舍

- **三 peer election**：隐藏 timer 后，candidate、两张 vote、leader 与 heartbeat 的顺序一眼可见。
- **五 peer backup test**：partition 后少数派持续收到或产生动作但不能 commit；多数派重连后重新 election 并推进 entry。
- **取舍：颜色 vs. 原始文本。** 颜色适合快速识别 pattern，但可靠分析仍依赖稳定字段；脚本只是 raw log 的一个 rendering。
- **取舍：过滤噪声 vs. 丢失证据。** 课堂做法是保存所有 topic，再在查看时隐藏 timer 或 dropped RPC，避免提前删掉后来才发现重要的信息。
- **取舍：logging 改变 timing。** 固定 logging 会增加开销，却比失败后反复修改 print 更可控；重复运行用样本数量弥补偶发性。

## 常见误解

- **误解：topic 就是 debug/info/error level。** 课堂中的 topic 表示 Raft 子系统，没有等级关系。
- **误解：只记录 Raft 内部事件即可。** 没有 test 的 disconnect/reconnect 标记，很难解释为何某组 peer 突然不能 commit。
- **误解：日志美化就是调试结论。** 颜色和分列只让 pattern 更显眼，仍需用状态与 RPC 语义验证 hypothesis。
- **误解：加 print 后不失败，说明 bug 被修好了。** 这更可能意味着 timing 被扰动；应保存固定 trace 并重复运行。
- **误解：为了减少文件大小，应在产生时关闭“无关”事件。** 在不知道 root cause 前，过早删掉 topic 可能让失败不可解释。

## 掌握检查

1. elapsed milliseconds 对 timer 与 RPC failure 分析分别有什么作用？
2. 为什么 test harness 的 disconnect/reconnect 事件也应出现在日志里？
3. 在五 peer 的 partition 示例中，为什么左侧两个 peer 的 entry 不能 commit？

# 003｜多个 goroutine 怎样围绕一个 Raft state 协作？

## 本节角色

- **时间范围**：`00:18:39–00:28:28`
- **核心问题**：`ticker`、incoming RPC、`Start`、outgoing RPC reply 和 apply channel 同时活动时，怎样给它们分工并保持 log apply 的顺序？
- **在全讲中的位置**：讲者先画出其实现的整体结构，再进入具体 voting 与 append 路径。这个结构是“一种可行设计”，课堂反复强调并非唯一答案。
- **边界**：本节讨论 ownership、serialization 与阻塞风险，不给出 goroutine loop 或 condition variable 的完整实现。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：课堂展示的 Raft library 对外有哪些主要交互？

**A：服务通过 `Start` 发起一条 log operation，Raft 通过 apply channel 输出已提交内容。** 内部的 `Raft` struct 保存 Figure 2 中的 state，课堂设计用一个 Raft lock 保护这些字段。

### Q2：哪些 goroutine 会访问 Raft state？

**A：至少包括 `ticker`、专用 applier、每个 incoming RPC 的 handler、调用 `Start` 的 goroutine，以及每个 outgoing RPC 的发送/回复 goroutine。** Go RPC library 会为 incoming message 启动独立执行流；leader 向多个 peers 发送 RPC 时也需要并行，因此可能同时存在很多发送 goroutine，尤其当消息延迟时。

### Q3：为什么课堂实现使用 coarse-grained locking？

**A：让 RPC handler 和 `Start` 对共享 Raft state 的读写各自形成一个较大的 atomic critical section。** 多个 goroutine 仍可并发等待网络或运行其他工作，但真正修改 Raft struct 时由同一把 lock 串行化。这样日志中受保护的状态变化也按 lock acquisition 排序，更容易推理。

### Q4：专用 applier goroutine 做什么？

**A：它是唯一写 apply channel 的执行流。** 当 incoming append 或 reply processing 推进 `commitIndex` 时，代码 signal condition variable；applier 被唤醒后按 Raft log 顺序取出尚未 apply 的 entries，并逐个交给 apply channel。没有工作时继续等待。

### Q5：为什么不让每个 RPC handler 自己写 apply channel？

**A：apply 必须严格按 log order。** 多个 handler 各自发送会引入额外协调；单一 applier 自然拥有输出顺序，只需沿 `lastApplied` 到 `commitIndex` 前进。课堂回答强调这是更容易组织的方式，不是唯一可能结构。

### Q6：图右侧的 goroutine 是什么？

**A：incoming RPC handlers。** 课堂举出的主要类型是 `AppendEntries` request 和 `RequestVote` request。它们在接收端运行，与发送端等待 reply 的 goroutine 不是同一个角色。

### Q7：outgoing RPC 为什么单独启动 goroutine？

**A：leader 需要并行联系多个 peers，且不能把 Raft lock 持有到网络等待结束。** 每个发送 goroutine 负责发送、等待 response；response 到达后再获取 Raft lock，更新必要状态，然后释放。

## 机制梳理

课堂结构可以按 ownership 理解：

- **Raft struct**：共享协议状态，由单一 coarse-grained mutex 保护。
- **`ticker`**：周期检查 election timeout；leader 路径还会触发 heartbeat。
- **incoming RPC handler**：获取 lock，原子检查 term/log 条件并更新 reply/state。
- **`Start` caller**：进入 Raft 后获取 lock，检查 leadership 并改变本地 log 状态。
- **outgoing RPC goroutine**：网络等待期间不持 lock；reply 回来后获取 lock 再解释结果。
- **applier**：独占 apply channel 的输出顺序，通过 condition variable 被事件唤醒。

这套结构把“协议状态的原子修改”和“可能长时间阻塞的外部操作”分开：前者放在 lock 内，网络 RPC 与 channel send 则需要谨慎安排在 lock 外。

## 例子与取舍

- **例子：多个慢 RPC。** 某些 peer response 很晚时，发送 goroutine 可以积累；Raft lock 仍让它们的 reply processing 一次一个发生。
- **例子：commitIndex 前进。** handler 不直接把一批 entry 发到 apply channel，而是更新共享状态并 signal applier；applier负责顺序输出。
- **取舍：单一 mutex。** 优点是少 interleaving、状态不变量更容易维护；缺点是 critical section 若包含阻塞操作，会把整个 peer 卡住甚至形成 deadlock。
- **取舍：单一 applier。** 优点是顺序天然明确；代价是需要 condition variable 或类似唤醒机制，并在读取共享 state 与发送 channel 之间处理好 lock boundary。
- **取舍：每 RPC 一个 goroutine。** 获得并行网络 I/O，但必须识别 stale reply，且不能假设 reply 到达顺序等于 request 发出顺序。

## 常见误解

- **误解：用了一个 lock，就没有 concurrency。** 网络等待、不同 handler 和 goroutine 仍并行；lock 只序列化临界区。
- **误解：每个 RPC handler 都可以按自己完成的顺序 apply。** completion order 不等于 log order，apply channel 必须保持后者。
- **误解：启动 outgoing goroutine 会把父 goroutine 持有的 lock 自动交给它。** lock 的 ownership 不因 `go` 调用而转移；新 goroutine 的发送路径按课堂设计不持有该 lock。
- **误解：专用 applier 只是性能优化。** 在课堂结构中，它首先是顺序与阻塞边界的组织方式。
- **误解：展示的结构是 Lab 唯一正确架构。** 讲者明确说每年会尝试不同实现，本节描述的是便于推理的一种。

## 掌握检查

1. 请区分 incoming RPC handler 与 outgoing RPC reply goroutine 的执行位置和职责。
2. 为什么多个 response 可以并行到达，却仍需要串行更新 Raft state？
3. 单一 applier 如何帮助保持 apply order？
4. condition variable 在这里传递的是 log entry 本身，还是“状态可能可推进”的通知？
5. 哪些操作可能阻塞，因此不应简单放进 coarse-grained critical section？

## 掌握检查参考答案

1. incoming handler 在接收 RPC 的 peer 上检查并更新本地 Raft state；outgoing goroutine 在发送端等待网络 reply，reply 到达后再取得发送端的 Raft lock 并解释结果。
2. replies 虽可并行到达，但它们会读写同一份 term、role、log 或 progress state；用同一把 lock 串行化 mutation，才能把相关状态转换作为原子步骤推理。
3. 它是 apply channel 的唯一 writer，沿 log 的 `lastApplied` 到 `commitIndex` 顺序逐项输出，避免多个 handler 按完成先后打乱 log order。
4. condition variable 传递的是“共享状态可能已有可 apply 工作”的通知；entry 仍由 applier 从受保护的 Raft log/state 中检查和取得。
5. 网络 RPC round trip 与 apply channel send 都可能等待外部参与者，因此不能不加区分地放在持有全局 Raft lock 的临界区内。

# 004｜锁可以在哪里释放，哪里绝不能跨越阻塞操作？

## 本节角色

- **时间范围**：`00:28:29–00:36:17`
- **核心问题**：fine-grained critical sections 之间会发生什么？为什么不能持 Raft lock 跨 RPC 或 apply channel send？
- **在全讲中的位置**：这是上一节架构图的风险分析，为后面的 `RequestVote` 与 `AppendEntries` 发送/回复路径建立 lock discipline。
- **边界**：课堂给出 deadlock 场景与设计原则，但没有要求所有实现都采用同一种 applier 或 buffer 配置。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：同一个 RPC handler 中先 lock/update/unlock，做些别的事，再 lock/update/unlock，有什么风险？

**A：两个 critical section 各自 atomic，但它们之间什么都可能发生。** 其他 incoming RPC 或 goroutine 可以改变 term、role、log 等 Raft state。第二段若继续依赖第一段建立的 assumption，就必须重新检查；否则它是在新 state 上执行旧判断。

课堂将这称为 fine-grained locking 带来的额外 interleavings。讲者更偏好把一次 handler 的相关 state transition 合在一个 critical section，以减少需要枚举的 interleaving。

### Q2：发送 RPC 后，是否仍然无法避免重新检查条件？

**A：是。网络 RPC 不能持 lock 等待，因此 reply 回来时必须重新确认上下文。** 课堂强调“不持 lock 跨 sending over the network”；网络期间 term、leadership 或 peer progress 都可能改变，reply handler 不能沿用发送前的全部 assumption。

### Q3：持 lock 发 RPC 为什么可能 deadlock？

**A：本 peer 等待远端 RPC，而远端可能反向发 RPC 给本 peer；本 peer 的 handler 又需要同一把 lock。** 若两个操作互相依赖，Raft lock 被网络等待长期占用，response 或反向 request 无法处理，形成环形等待。

### Q4：RPC arguments 应在什么时候准备？

**A：课堂建议在持 lock 的调用方中生成稳定 arguments，再启动不持 lock 的发送 goroutine。** 有学生提出也可以让新 goroutine 先取 lock、准备参数、释放后发送；这并非不允许，但会增加发送前可发生的 interleaving。另一名学生指出，晚准备有时能看到更新的 progress；讲者回答这取决于实现，而其展示方案给同一轮 peers 使用同一组已准备信息。

这里的本质取舍是 snapshot consistency 与 freshness：较早复制参数使一轮发送依据同一 state，较晚生成可能更“新”，却需要重新验证更多条件。

### Q5：为什么不应该持 lock 写 apply channel？

**A：channel send 可能阻塞。** 对 unbuffered channel，必须等 receiver；即使 buffered channel 也不能把容量当作永不阻塞的保证。若 applier 持有 Raft lock 等 receiver，而上层服务此时调用 `Start` 并等待同一 lock，同时又没有读取 apply channel，就可能构成 deadlock。

### Q6：单一 applier goroutine 是否自动解决这个问题？

**A：不自动解决。** applier 仍需读取共享 Raft state，因此某个阶段要取 lock；关键是不要在实际阻塞的 channel send 期间继续持 lock。单一 goroutine解决的是输出顺序，lock release 解决的是阻塞环。

### Q7：再创建一个 goroutine 是唯一解吗？

**A：不是。** 课堂承认有多种安排方式，只强调需要明确推理阻塞和 lock ownership。展示实现选择在写 apply channel 前释放 lock，认为持 lock 做 channel operation 通常是坏实践。

## 机制梳理

锁边界可用两条规则检查：

1. **跨边界后 assumption 失效**：每次 unlock 到下一次 lock 之间，共享 state 都可能变化；重新进入时要重新验证 term、role、index 等条件。
2. **未知时长操作不得占住全局协议锁**：RPC round trip 和 channel send 都可能等待外部参与者，若持 lock，外部参与者可能反过来等待本 peer 的该 lock。

因此典型事件被拆成三个阶段：在 lock 内读取并复制一致参数；在 lock 外执行 RPC/channel operation；结果回来后重新取 lock，并以**当前 state**判断结果是否仍适用。

## 例子与取舍

- **例子：两个 critical sections。** 第一段观察自己是 candidate，unlock 后收到更高 term RPC 变成 follower；第二段若不重查 role，就可能按过时 candidate 逻辑更新 state。
- **例子：双向 RPC。** A 持 lock 等 B，B 向 A 发送需要 A handler 取 lock 的消息；A 无法处理，B 的进展也可能依赖该消息。
- **例子：apply channel。** 上层在 `Start` 内等待 Raft lock，applier 持 lock 等上层读取 channel，两者相互等待。
- **取舍：coarse-grained lock。** 减少普通 state mutation 之间的 interleaving，但必须主动切开网络与 channel 这些阻塞点。
- **取舍：提前准备 RPC args。** 保证一轮参数来自同一 state snapshot；代价是发送时可能已不是最新 state，reply 时必须做 freshness check。

## 常见误解

- **误解：每个小 critical section 正确，整个 handler 就正确。** section 之间的 state 变化可能破坏跨段 assumption。
- **误解：RPC handler 可以持 lock，因为它只是在执行函数调用。** 接收端 handler 可在本机 critical section 内处理 state；危险的是发送端持 lock 跨网络等待。
- **误解：新 goroutine 继承父 goroutine 的 mutex ownership。** Go mutex 不随 `go` 语句转移 ownership。
- **误解：buffered channel 可以彻底消除 deadlock。** buffer 只改变何时阻塞，无法作为永久不阻塞的协议保证。
- **误解：有了单一 applier 就可以一直持 lock。** 输出 ownership 与 channel send 的阻塞边界是两个独立问题。

## 掌握检查参考答案

1. 两段之间 lock 已释放，其他 RPC 或 goroutine 可以改变 term、role、log 等共享 state；第二段若沿用第一段的判断，就是在新状态上使用旧 assumption。
2. A 持有自己的 Raft lock 等待发往 B 的 RPC；B 又向 A 发出一个需要 A 的 handler 取得同一把 lock 的 RPC。A 无法处理 B 的请求，而双方进展又互相等待，形成等待环。

4. 单一 applier 解决 apply output 的顺序 ownership；send 时不持 lock 则避免 channel 阻塞与 Raft lock 形成死锁环。两者不是同一个保证。

# 005｜election timer 怎样在检测粒度、随机化与活性之间平衡？

## 本节角色

- **时间范围**：`00:36:18–00:44:45`
- **核心问题**：`Make` 启动哪些 goroutine，`ticker` 怎样判断 election timeout，50 ms 检查粒度会不会让 election 更容易冲突？
- **在全讲中的位置**：从整体 concurrency 结构进入 voting 的第一步，覆盖初始化、timer 检查与 candidate 启动 election 前的 state transition。
- **边界**：课堂展示的 `50 ms` tick、`1000–1300 ms` timeout 是讲者该版实现的选择，不是可脱离测试约束直接照抄的唯一配置。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：`Make` 初始化后会启动什么？

**A：构造 Raft state、apply channel 与 condition variable，把自己设为 follower，设置 election timeout，建立空 log，并启动 applier 与 `ticker` 两个 goroutine。** snapshot state 在这次 Lab 2A/2B Q&A 中不展开。

### Q2：`ticker` 如何检查 timeout？

**A：课堂实现每隔约 50 ms 运行一次 `tick`。** `tick` 获取 Raft lock；若当前是 leader，走 heartbeat 路径；否则比较 current time 与预先记录的 election deadline。deadline 已过就重新设置 timeout，并启动 election。

### Q3：为什么保存一个 deadline，而不是只数 sleep 次数？

**A：课堂通过“现在是否越过 election time”判断 timeout。** 这使随机化结果成为明确时刻，`ticker` 只是周期观察它；实际触发可能比 deadline 晚不到一个 tick interval。

### Q4：每 50 ms 才检查一次，会不会把很多随机 timeout 压到同一个时间点，导致 contested election？

**A：会让观察粒度更 coarse，但课堂认为足够。** 示例随机 timeout 落在 `1000–1300 ms`，50 ms polling 会量化触发时刻，却仍留下多个可能槽位。真正约束是不能太慢，也不能太快。

### Q5：timeout 太慢或太快分别有什么问题？

**A：太慢会延迟 leader replacement；太快会不断重启 election。** candidate 需要时间让 RequestVote 往返，部分 vote 可能 delay；如果上一轮还没机会完成就开始下一轮，系统会产生更多冲突而非更快收敛。

### Q6：函数名后的大写 `L` 是什么意思？

**A：这是讲者自己的 convention，表示 callee 假定 caller 已持有 Raft lock。** 它把 lock precondition 放进名字，帮助 review 调用路径；讲者明确称其为一次编码实验，并非 Go 或 Lab API 规则。

### Q7：启动 election 时先改变哪些 state？

**A：课堂按 Figure 2 描述：提高 `currentTerm`，转为 candidate，把 `votedFor` 设为自己，并在 persistent state 改变后持久化；随后才发起 RequestVote。** 自己的一票计入 vote count。

### Q8：RequestVote arguments 为什么包含 `LastLogIndex` 与 `LastLogTerm`？

**A：接收者需要判断 candidate 的 log 是否 up-to-date。** 参数还带 `Term` 和 `CandidateId`。讲者给相关 struct 写 `String` formatter，使 `%v` 的日志输出保持标准格式，便于过滤。

## 机制梳理

timer 路径由三个不同尺度组成：

- **heartbeat interval**：leader 周期发消息维持 authority。
- **election timeout range**：follower/candidate 等待多长时间后认为需要新 election，并在 peers 间随机化。
- **polling interval**：`ticker` 多久检查一次 deadline，只决定检测精度，不等同于 timeout 本身。

触发 election 后，term、role 和 self-vote 构成一个 state transition。由于 term 与 vote 属于需要持久化的状态，课堂强调先更新并 persist，再向 peers 构造 RequestVote。随机化用于降低 peers 同时成为 candidate 的概率，但不能替代正确的 vote/log checks。

## 例子与取舍

- **课堂数值例子**：timeout 为 `1 s + [0, 300 ms)` 随机量，tick 约 `50 ms`；因此检查只会近似 deadline，而非纳秒级触发。
- **取舍：短 timeout。** failure detection 快，但 delayed/dropped RPC 更容易让 election 尚未完成就被下一轮打断。
- **取舍：长 timeout。** election 更有完成空间，但真正 leader failure 后恢复更慢。
- **取舍：polling vs. 单独 timer。** polling 结构简单、行为集中；代价是触发精度受 tick interval 限制。课堂本段只展示前者。
- **取舍：`L` 命名 convention。** 能暴露 lock precondition，但依赖团队一致遵守，编译器不会替你验证。

## 常见误解

- **误解：50 ms tick 意味着 election timeout 是 50 ms。** tick 只是检查频率，deadline 在更长且随机化的区间。
- **误解：timeout 越短，系统恢复越快。** 过短会制造重复 election，反而损害 liveness。
- **误解：随机化可以弥补 vote 逻辑错误。** 它只减少同时竞选概率，不决定谁有资格获票。
- **误解：成为 candidate 后可以先发 RPC，再更新 term/self-vote。** 课堂顺序先形成并持久化本 term 的 candidate state。
- **误解：函数名带 `L` 会自动加锁。** 它只声明 caller-held lock 的约定。

## 掌握检查

1. election deadline、randomized range 与 `ticker` polling interval 各自控制什么？
2. 为什么 polling 的 coarse granularity 不必等于 election 一定冲突？
3. timeout 太短时，delayed vote 会怎样与下一 term 交错？
4. candidate 启动 election 前为什么要先更新并持久化 term/vote state？
5. `LastLogTerm` 与 `LastLogIndex` 为接收端提供哪类判断依据？

## 掌握检查参考答案

1. deadline 是某个 peer 本轮等待的目标时刻；randomized range 让不同 peers 的目标时刻分散；polling interval 只决定多久观察一次 deadline，也就是检测精度。
2. polling 会把触发时刻量化，但 `1000–1300 ms` 的随机范围仍覆盖多个约 50 ms 的检查槽位，所以它增加同时触发的可能性，却不等于必然冲突。
3. 上一轮 delayed vote 可能在 candidate 已因 timeout 开始下一轮后才到达，使不同 election 的消息交错；过短 timeout 因而会在一轮尚未完成时制造更多竞选。
4. term、candidate role 与 self-vote 共同定义本轮 election，且 term/vote 属于 persistent state；先形成并持久化这组状态，发出的 RequestVote 才有一致上下文。
5. 它们让接收端判断 candidate 的 log 是否 up-to-date：最后 entry 的 term 是首要比较依据，term 相同时再用最后 index 区分长短。

# 006｜一张 vote 需要同时满足 term、身份与 log 新旧哪些条件？

## 本节角色

- **时间范围**：`00:44:46–00:55:30`
- **核心问题**：candidate 如何并行收票并拒绝过期 reply，receiver 又怎样处理 higher term、重复 RequestVote 与 up-to-date 检查？
- **在全讲中的位置**：完整走过 RequestVote 的 sender、reply handler 与 receiver 三个角色，为成为 leader 后初始化 `nextIndex` 做铺垫。
- **边界**：只总结课堂解释的判定关系，不给出可粘贴的 handler 条件表达式。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：candidate 怎样向 peers 发 RequestVote？

**A：先在持 lock 的上下文构造参数，跳过自己，并把 self-vote 计为 1；随后为每个 peer 启动发送 goroutine。** 每个 goroutine 在网络调用期间不持 Raft lock，分别等待自己的 reply。

### Q2：为什么课堂说新 goroutine 没有“继承”原来的 lock？

**A：父执行流持有 lock 并不让新 goroutine 自动拥有它。** 发送 goroutine 的作用正是让 RPC 在 lock 外并行进行。reply 到达后，它再获取 lock，进入 response processing。

### Q3：接收端 `RequestVote` handler 能不能取 lock？

**A：能，而且课堂实现一开始就取本机 Raft lock。** 学生的混淆来自把 sender 的网络等待与另一台机器上的 receiver handler 视为同一件事。receiver handler 和 sender reply handler 都可在各自 peer 上用 lock 原子处理 state；禁止的是 sender 持 lock 跨网络。

### Q4：reply 带来更高 `Term` 时，candidate 做什么？

**A：退回 follower 并进入 reply 指示的新 term。** higher term 是 Figure 2 对所有 server 的共同规则。进入新 term 时，课堂实现清空本 term 的投票记录（`votedFor = -1`）、变为 follower，并持久化相关 state。

### Q5：收到 `VoteGranted` 后，达到 majority 就一定能成为 leader 吗？

**A：还要确认自己仍处于发起该 election 的同一 term。** vote replies 可并行到达且可能延迟；Raft lock 序列化 vote count 的更新，但 serialization 不能让旧 reply 变新。只有当前上下文仍有效，majority 才能推动 candidate 成为 leader。

### Q6：成为 leader 时为什么把 `nextIndex` 初始化为本地 last index 加一？

**A：这是一个 optimistic guess，假设 followers 已与 leader 一样新。** 若猜错，后续 AppendEntries reply 会让 leader back off。课堂把它描述为起始估计，而非已证实的 follower progress。

### Q7：receiver 怎样判断 candidate 的 log up-to-date？

**A：先比较最后一条 entry 的 term；term 相同时再比较 last log index。** candidate 的 last term 更高则更新；last term 相等时，candidate 的 last index 至少不短才算更新。这对应课堂对 Figure 7 election restriction 的解释。

### Q8：higher-term candidate 到来时，为什么不能自动 grant vote？

**A：进入更高 term 与授予 vote 是两项独立判断。** receiver 必须先更新 term/role，但仍需检查 candidate log 是否 up-to-date，以及自己本 term 是否尚未投给其他 candidate。

### Q9：为什么允许 `votedFor == CandidateId` 时再次返回 grant？

**A：同一 candidate 的 RequestVote 或 reply 可能 delay/lost 后重发。** receiver 可以对同一 candidate 重复确认，而不能在一个 term 内改投另一个 candidate。

### Q10：grant vote 时还会发生什么 timer 动作？

**A：课堂实现重置 election timeout。** 这表示 receiver 已参与当前有效 election；它不会因一个 stale lower-term request 而延后自己的 timeout。

## 机制梳理

RequestVote 横跨三个并发边界：

1. **candidate 准备发送**：在 lock 内冻结本轮的 term、candidate id 和 log freshness 信息。
2. **receiver 判票**：在 receiver 自己的 lock 内，先处理 higher term，再联合判断 vote history 与 log up-to-date。
3. **candidate 处理 reply**：重新取 lock，先处理 reply 的 higher term，再确认 reply 属于当前 election，最后才累计有效 vote。

这里有两类 consistency：mutex 保证同一 peer 内 vote count/state mutation 不同时发生；term check 保证异步 reply 没有跨 election 污染当前状态。两者缺一不可。

## 例子与取舍

- **重复请求例子**：receiver 已投给 candidate A，A 的 response 丢失后重发；再次 grant A 不违反“一 term 一 candidate”。
- **higher term 例子**：candidate B 的 term 更高，但 log 比 receiver 旧；receiver 更新到新 term、成为 follower，却仍拒绝 B 的 vote。
- **stale reply 例子**：candidate 已因其他 RPC 进入新 term，旧 election 的最后一票此时到达；majority count 不能让它在新上下文中错误成为 leader。
- **取舍：optimistic `nextIndex`。** follower 都较新时少一次探测；落后时要通过 conflict/backoff 纠正。
- **取舍：共享 vote count。** lock 可让多个 reply goroutine安全累加，但代码必须把 count 与发起 election 的 term 绑定起来。

## 常见误解

- **误解：higher term 自动意味着 candidate 值得投票。** term 决定 receiver 更新 epoch，log freshness 决定 candidate 是否有资格。
- **误解：一 term 只能对 RequestVote 返回一次 true。** 可以对同一 candidate 重复确认，禁止的是改投不同 candidate。
- **误解：拿到 majority 的旧 replies 仍可成为 leader。** reply 必须仍属于当前 term/current election。
- **误解：Raft lock 能自动过滤 stale network result。** lock 只序列化处理，仍需显式检查 term 与 role。
- **误解：`nextIndex = lastIndex + 1` 已证明 follower up-to-date。** 这只是 leader 初始化时的 optimistic guess。

## 掌握检查

1. receiver 为什么要先响应 higher term，再单独判断是否 grant vote？
2. last term 相等与不相等时，up-to-date 比较分别看什么？
3. 为什么允许对同一 candidate 重复 grant，却不允许改投另一 candidate？
4. candidate reply handler 中，mutex 与 term validation 分别防止什么？
5. 构造一个旧 vote reply 在新 term 到达的场景，并说明它为何必须被忽略。

## 掌握检查参考答案

1. higher term 要求 receiver 先进入新的协议 epoch 并成为 follower；grant vote 仍是独立资格判断，还要满足本 term 的 vote history 与 candidate log freshness。
2. last term 不同时，term 更高的 log 更 up-to-date；last term 相同时，再比较 last index，candidate 至少不短才满足条件。
3. 同一 candidate 的请求或 reply 可能 delay/lost 后重发，重复确认保持幂等；改投另一 candidate 则破坏一个 term 内不投给不同 candidate 的约束。
4. mutex 防止并行 reply 同时修改 vote count 与 Raft state；term validation 防止已经过期的 election reply 在新的 term/context 中产生作用。
5. candidate 在 term 1 发出 RequestVote，随后因另一个 higher-term RPC 进入 term 2 并成为 follower；此时 term 1 的最后一张 grant 才到达。它属于旧 election，不能把当前 peer 推回 leader。

# 007｜heartbeat 与 AppendEntries 共用路径时，怎样处理复制参数和迟到 reply？

## 本节角色

- **时间范围**：`00:55:31–01:05:27`
- **核心问题**：leader 怎样用同一条 send-appends 路径发送 heartbeat 与 entries，为什么必须复制 Go slice，多个 outstanding RPC 又会怎样影响 `nextIndex` 与 reply handling？
- **在全讲中的位置**：从 election 胜出切换到 leader replication，覆盖 send side、goroutine/lock 边界、reply freshness 与 conflict backoff。
- **边界**：课堂展示了自己代码的组织方式，也承认某些 decrement 分支来自迭代历史；本节不把不确定片段包装成规范答案。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：新 leader 的第一轮 heartbeat 与普通 AppendEntries 是两套代码吗？

**A：课堂实现共用 `sendAppends` 路径。** heartbeat 本质上是通常没有 entries 的 AppendEntries；如果 follower 落后，即使由 heartbeat path 触发，也可能携带需要补齐的 log entries。

### Q2：给一个 peer 的 AppendEntries arguments 怎样决定 entries 范围？

**A：依据该 peer 的 `nextIndex`，从 leader log 中取它尚未拥有的后缀。** 新 leader 的 optimistic `nextIndex` 可能让首轮 entries 为空；失败 reply 再帮助 leader向前回退。

### Q3：为什么要把 entries 从 Raft log copy 到 arguments 的独立 slice？

**A：Go slice 可能共享底层 memory。** 如果 RPC arguments 直接引用受 lock 保护的 log slice，释放 lock 后其他 goroutine 修改 log，正在发送的 RPC 看到的数据就可能变化或产生 race。课堂在持 lock 时分配并 copy 所需 entries，使 arguments 成为自己的快照。

### Q4：发送每个 AppendEntries 时 lock 到底在哪里？

**A：外层 caller 持 lock，逐 peer 准备参数并启动 goroutine；新 goroutine 在不持 lock 的情况下发送 RPC。** response 返回后该 goroutine再获取 lock 处理 reply。如果 caller 仍在为其他 peers 准备发送，reply handler 会等到 caller 释放 lock。

### Q5：课堂关于 `defer Unlock` 的追问想澄清什么？

**A：想确认 unlock 会沿 surrounding execution path 在退出/return 时执行，从而保证持 lock 的准备阶段结束。** 对 Raft 推理更重要的结论是：启动的 goroutine不拥有 caller 的 lock，reply processing 必须自行重新获取。

### Q6：为什么 reply handler 要检查发送时的 term 与当前 term？

**A：RPC 可能很慢，返回时 leader 可能已进入另一 term 或不再是 leader。** 若 reply 带更高 term，先转 follower；只有 reply 对应的 term 仍匹配当前上下文，才处理 success/conflict。

### Q7：success reply 怎样影响 progress？

**A：课堂按 Figure 2 更新该 peer 的 `matchIndex` 与 `nextIndex`。** 这些值表达 leader 对 follower 已复制前缀的认识，后续也用于判断是否形成 majority replication。

### Q8：failure reply 怎样 back off？

**A：若 reply 提供有效 conflict 信息，走 fast backtracking；没有 conflict information 时，课堂代码有逐一回退的 fallback。** 讲者对该 fallback 是否仍属必要表示不完全确定，因为代码经历了多次迭代；能确认的 downside 是可能在下一轮多发送一些 entries。

### Q9：如果同一 peer 有多个 outstanding RPC，`nextIndex` 会不会在 reply 前已经改变？

**A：会，这个担忧有效。** 同一 peer 的多个 reply 可能以不同顺序到达，Raft state 在其间也可能改变。课堂没有把“取 lock”当作充分答案，而是承认 reply order 与 state freshness 需要纳入设计推理。

## 机制梳理

send-appends 路径把一次复制拆为：

- 在 lock 内读取 peer progress，构造 `PrevLogIndex`/`PrevLogTerm`、commit 信息与 entries snapshot。
- 对 entries 做独立 copy，避免 arguments 与可变 Raft log 共享 backing array。
- 在 lock 外并行发送 RPC。
- reply 回来后重新获取 lock，先做 term/context validation。
- success 时推进 progress；conflict 时保守回退或使用 conflict metadata 快速定位匹配点。

heartbeat 与 data append 的区别主要是某次 arguments 中 entries 是否为空，而不是两套完全不同的协议。相同 send path 减少重复，但也要求每次都根据 peer 当前 `nextIndex` 生成内容。

## 例子与取舍

- **例子：首轮 heartbeat。** 假设 followers 与新 leader 同步，`nextIndex` 指向 leader log 末尾后一位，entries 为空。
- **例子：落后 follower。** heartbeat tick 触发同一路径时，按 `nextIndex` 取出的后缀非空，因此同时承担 catch-up。
- **例子：slice alias。** arguments 若只是 log slice view，lock 释放后的 append/overwrite 可能改变发送内容；copy 用空间换稳定 snapshot。
- **取舍：fast backtracking。** 利用 conflict term/index 减少 round trips；逐一回退更简单但可能慢且多发数据。
- **取舍：多个 outstanding RPC。** 提高并行度和响应速度，却使 reply reordering 与 progress regression 更难处理。

## 常见误解

- **误解：heartbeat 永远没有 entries。** 通常为空，但 follower 落后时共用路径可能携带 entries。
- **误解：Go slice 赋值就是深拷贝。** slice 可共享底层数组，课堂明确执行 copy 以隔离 RPC arguments。
- **误解：reply handler拿到 lock 后，reply 就一定有效。** lock 只保证当前处理原子，term/role/request context 仍可能过期。
- **误解：同一 peer 的 RPC replies 必按发送顺序返回。** 网络延迟允许重排，也可能同时 outstanding。
- **误解：课堂代码里出现的每个 fallback 都是 Raft 规范要求。** 讲者对逐一 decrement 的必要性明确保留意见，应回到 Figure 2 与测试证据判断。

## 掌握检查

1. 为什么 heartbeat 与 log replication 可以共用 AppendEntries path？
2. `nextIndex` 如何决定某个 peer 收到的 entries 后缀？
3. Go slice 的 backing array 对异步 RPC 造成什么风险？
4. reply handler取 lock 后，为什么还必须检查 term/context？
5. 同一 peer 多个 outstanding RPC 可能怎样重排 `nextIndex`/`matchIndex` 更新？

## 掌握检查参考答案

1. heartbeat 本来就是 AppendEntries 的一种使用；同一路径根据 follower 是否缺少 suffix 决定 entries 为空还是非空，因此无需把保活与复制拆成两套协议。
2. `nextIndex` 表示 leader 估计该 peer 下一条需要的 log index，所以发送内容是从该位置开始的 leader log 后缀；估计过于乐观时再由失败 reply 纠正。
3. slice 可能共享 backing array；lock 释放后 Raft log 若被其他 goroutine 改动，异步 RPC arguments 可能随之变化或与写入形成 race，而独立 copy 保留发送时快照。
4. lock 只让本次 reply processing 与其他 state mutation 串行，不能证明 reply 仍新鲜；RPC 返回时 term、role 或 request context 都可能已改变。
5. 较新的 success 可能先推进 progress，较早的 failure 却后到；若不判断 reply 与当前 progress 的关系，迟到结果可能按旧观察回退或覆盖较新的认识。

## 问答序列

### Q1：什么时候检查是否可以推进 `commitIndex`？

**A：课堂实现在处理 AppendEntries reply、更新 `matchIndex` 后检查。** leader 由各 peer 的 replication progress 判断某个 index 是否已出现在 majority 上，这对应 Figure 2 中 leader 的 commit 规则。

### Q2：majority 已复制某条 entry，为什么还要检查它的 term？

**A：leader 不能仅按副本数直接提交 previous-term entry。** 课堂把这与 Figure 8、Section 5.4 联系起来：leader 需要先通过 majority 提交本 `currentTerm` 的 entry；一旦较新的 current-term entry 提交，之前的 entries 会随 log prefix 一起成为 committed。

### Q3：`commitIndex` 前进后怎样唤醒 applier？

**A：signal condition variable。** applier 持有 `lastApplied`，被唤醒后检查是否有尚未送出的 committed entries，按序推进；若没有工作，就在 condition variable 上继续 `Wait`。

### Q4：为什么发送 apply channel 前释放 lock？

**A：channel send 可能阻塞。** 课堂代码先在 lock 内确定下一条要 apply 的 entry，再在发送前 unlock，延续第 004 节的 deadlock discipline。单一 applier 保证顺序，unlock 避免 channel receiver 与 Raft lock 构成等待环。

### Q5：这里用 `Broadcast` 而不是 `Signal` 有特殊理由吗？

**A：没有。** 课堂只有一个等待的 applier，因此讲者回答两者在这个场景效果相同。

### Q6：不用 condition variable，定时 sleep 后检查行不行？

**A：可以构造别的设计，但讲者不喜欢散落的 random sleeps。** 其实现只在 `ticker` 使用 sleep；其他进展由事件 signal。把 apply 检查塞进 `ticker` 也可能工作，但讲者认为独立职责更容易推理，并承认这是 taste 而非唯一正确性要求。

### Q7：`Start` 做了什么？

**A：服务调用 `Start` 后，Raft 获取 lock，确认自己是否仍为 leader；若不是则返回失败标志。若是，则建立带当前 term 的 entry，append 到本地 log，持久化该 log state，并调用与 heartbeat 共用的 send-appends 路径。** 因此 `Start` 的关键差异是先产生新 entry，发送机制本身复用。

### Q8：为什么把 log 抽成单独结构并记录 `index0`？

**A：为了将来 2D 截断 log prefix 时隐藏 index translation。** 课堂结构提供 append、slice、first/last index、entry access、cut start/end 等操作。对 2A/2B/2C，`index0` 通常仍为 0；snapshot 细节留到后续。

### Q9：什么时候 reset election timeout？

**A：课堂回顾强调，只在收到 current term 的 leader message，或因更高 term 转为 follower 时 reset；不因 lower-term stale message 延后 timeout。** 这防止落后的 sender 持续压制有效 election。

### Q10：AppendEntries 只在 heartbeat 发，还是也在 `Start` 发？

**A：课堂展示两处都触发。** 只靠 heartbeat 也有人完成 Lab 2，但受每秒 heartbeat 次数约束，会延迟新 command 的 replication；后续 Lab 3 还有 progress speed 检查。讲者不在 reply handler 中立即继续发送，尽管承认别的实现会这样做。

### Q11：为什么实践中常见 3、5、7 个 Raft servers？

**A：课堂解释它反映 failure tolerance 与运维恢复时间的权衡。** 例如三节点坏一个后仍有时间修复/替换，再回到三节点；并非测试无法构造更多节点，而是这些规模贴近典型使用。

### Q12：写 persistent state 时 crash，怎样避免 partial state？

**A：stable storage update 必须具有 atomic 效果。** tester 的 simulated persistence 会原子更新；真实系统可先写临时文件再 atomic rename，或使用 write-ahead log。若 term/vote/log 持久状态只写了一部分，重启后不一致会是灾难性问题。

## 机制梳理

从 client command 到 state machine 的因果链是：

1. `Start` 只在当前 leader 上接受 command，append 并 persist 本地 entry。
2. send-appends 路径把 follower 缺失的 suffix 复制出去。
3. replies 更新 `matchIndex`；leader寻找 majority 已复制的候选 index。
4. 候选 entry 必须属于 `currentTerm` 才能由该规则直接推进 commit。
5. `commitIndex` 前进后 signal applier。
6. 单一 applier 按 `lastApplied` 顺序输出，并在 channel send 期间不占 Raft lock。

event-driven condition variable 让“有新 committed work”直接唤醒 applier；heartbeat/ticker 则承担时间驱动的 leader/election 职责。两者分开减少无关 polling。

## 例子与取舍

- **Figure 8 取舍**：previous-term entry 即使达到多数，也不能只凭计数直接宣布 commit；等待 current-term entry 建立安全的 leader commitment 证据。
- **`Signal` vs. `Broadcast`**：单 waiter 时效果相同；课堂没有为 `Broadcast` 赋予额外协议语义。
- **condition variable vs. sleep**：前者事件驱动且职责清晰；后者代码可能更直观，却引入检查延迟与更多 timing behavior。
- **`Start` 立即发 vs. heartbeat 批量发**：立即发降低 client latency；只在 heartbeat 发可以工作但限制 progress speed。
- **atomic persistence**：临时文件加 rename 或 WAL 都是课堂给出的真实系统方向；tester 把这一层抽象成原子模拟。

## 常见误解

- **误解：majority 复制任何 term 的 entry 都可直接 commit。** Figure 8 限制 leader 直接推进的是 current-term entry。
- **误解：`Broadcast` 表示 Raft 要唤醒多个 state machines。** 课堂这里只有一个 applier，使用它没有特殊理由。
- **误解：`Start` 返回 leader 就代表 command 已 committed。** `Start` 只是本地接受并发起 replication，commit 还依赖后续 majority progress。
- **误解：heartbeat path 永远只能发空消息。** 它调用相同 send-appends，根据 follower progress 也可能带 entries。
- **误解：调用 persist 就天然防止 partial disk write。** 原子性需要 storage mechanism 或 tester abstraction 提供。

## 掌握检查

1. 为什么 current-term check 能避免 Figure 8 中 previous-term entry 的错误提交？
2. `commitIndex` 与 `lastApplied` 为什么必须是两个概念？
3. condition variable 的 signal 在这里代表什么状态变化？
4. `Start` 接受 command 与 command committed 之间还缺哪些步骤？
5. 为什么 lower-term message 不应重置当前 peer 的 election timeout？

## 掌握检查参考答案

1. majority 计数本身不能让 leader 直接提交 previous-term entry；课堂依据 Figure 8 要求先提交一条 current-term entry，届时更早的 log prefix 才随之 committed。
2. `commitIndex` 表示协议已认定 committed 的最大位置，`lastApplied` 表示已经按序送到 state machine 的最大位置；apply channel 可能阻塞，所以后者可以暂时落后。
3. signal 表示 `commitIndex` 可能已前进、applier 可能有新工作；它不是 entry payload，applier 醒来后仍检查 `commitIndex` 与 `lastApplied`。
4. 还要把本地 entry 持久化并复制到 followers，由 replies 更新 replication progress，满足 majority 与 current-term commit 条件，再由 applier 按序送入 apply channel。
5. lower-term sender 已落后，若它的 message 也延后 timeout，就可能持续压制当前 peer 发起有效 election；课堂只在 current/new term 的 leader context 下 reset。

# 009｜真实失败里，timer leak、超长 timeout 与 nil channel 分别暴露什么？

## 本节角色

- **时间范围**：`01:16:27–01:25:01`
- **核心问题**：开放问答中的具体 bug 怎样表现？调大 election timeout 为什么可能只是降低复现率？timer、channel 和 snapshot index 的误解如何从测试中显现？
- **在全讲中的位置**：从协议 walkthrough 转入学生实际 debugging experience，重新连接第 001–002 节的方法论与 timer/test 行为。
- **边界**：本节保留课堂参与者的经验与不确定语气，不把单个 bug 推广为所有失败的原因。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：log abstraction 中的 `index0` 是底层 array 的什么位置？

**A：它表示当前保留 log 的第一个全局 index，主要为 2D snapshot 服务。** 在 2A/2B/2C 中通常为 0；若 snapshot 覆盖到 index 10，前面的 prefix 被剪掉，`index0` 变成 10。被 snapshot 包含的旧 state 不必继续保留在 log 中。

### Q2：`300–700 ms` election timeout、`100 ms` heartbeat 是否合理？

**A：讲者认为该学生的区间合理，同时提醒测试要求在 5 秒内选出 leader，可能需要不止一轮 election。** 课堂展示过更大的 timeout；重点是留出数轮通信空间，又不能让 recovery 超过 test liveness window。

### Q3：课堂分享的“最烦人 bug”是什么？

**A：一个学生用独立 sleeping goroutine 实现 heartbeat timer 与 election timer，server shutdown 时忘记停止其中一个。** 长测试中 goroutine 数量逐渐增长，最终资源耗尽，race detector 让整个运行崩溃。学生起初怀疑 lab RPC code，后来确认是未停止 timer 导致的 leak。

这个案例展示了 root cause 与表面症状的距离：失败出现在 race-enabled long run，真正错误却是 lifecycle cleanup。

### Q4：把随机 election timeout 上限调到 1500 ms 后，偶发 agreement failure 变少，是否应继续调高？

**A：讲者第一判断是仍有另一个 bug。** 正常通过不应依赖如此长的 timer；TA补充，多数“调 timeout 修好”的情况只是改变 bug 出现频率，并未修复原因。

### Q5：是否应该故意把 timeout 压低来暴露 bug？

**A：课堂认为 push boundaries 是不错的测试思路，但边界仍应参考 paper guideline 与 lab 环境。** 测试的 heartbeat 频率限制与论文环境不完全相同，因此可以比 paper 的具体示例稍高；原则是 election timeout 显著大于 heartbeat interval，让 candidate 有时间应对 delayed/dropped messages。

### Q6：未初始化 channel 的 bug 怎样表现？

**A：学生发送后一直无法被接收，最后发现 channel 从未初始化，仍是 nil channel。** 课堂没有展开 Go nil channel 的完整语义，只把它记录为一个真实 failure source。

### Q7：heartbeat timer 在课堂代码哪里？

**A：同一个 `ticker` 每约 50 ms 调用 `tick`；若当前是 leader，就走 send-appends，从而产生 heartbeat。** 这与学生使用两个独立 sleeping timers 的 leak 案例形成对照，但课堂没有宣称单 ticker 是唯一安全设计。

### Q8：为什么不能让 election timeout 非常接近 heartbeat interval？

**A：candidate 需要完成 RequestVote 往返，消息还可能 delay 或 drop。** 太接近时，一次正常抖动就会触发新 election；系统对网络不确定性的容忍空间消失。

## 机制梳理

开放问答揭示了三类与“协议条件写错”不同的 failure：

- **lifecycle failure**：timer goroutine 未随 server shutdown 停止，长期积累后才爆发。
- **timing mask**：调大 timeout 降低 bad interleaving 的频率，但 agreement bug 仍在。
- **initialization failure**：nil channel 让通信路径永久无法前进，看起来像 receiver 或协议没有响应。

这些问题都需要第 001 节的证据闭环：观察 goroutine count/long-run behavior、保存失败 run、验证 timeout 改变的是频率还是逻辑、确认 channel lifecycle。只看最终“未达成 agreement”不足以区分三者。

## 例子与取舍

- **timer leak 例子**：短测试可能全过，overnight 或 race run 才因 goroutine 持续增长失败，说明测试时长本身是一项诊断维度。
- **timeout mask 例子**：随机区间扩大到 1500 ms 后失败减少；这是一条关于 timing sensitivity 的证据，不是修复证明。
- **boundary testing**：降低 timeout 可以增加并发压力、帮助复现，但过度偏离 lab constraints 会制造不代表目标环境的新失败。
- **单 ticker vs. 多 timer goroutines**：集中 timer lifecycle 更易观察；多个 timer 可分工，但 shutdown/cancel 必须完整。
- **snapshot index abstraction**：用 `index0` 隔离 global index 与 slice offset，减少 2D 截断影响；在 2A/2B 中不应把它误当作当前 commit point。

## 常见误解

- **误解：timeout 调大后通过率提高，就证明 timeout 原来太小。** 它也可能只隐藏 race 或错误 reset 行为。
- **误解：所有 long-run crash 都是 lab RPC infrastructure 的 bug。** 课堂案例最终是自己的 timer goroutine leak。
- **误解：server 被 kill 后，sleeping goroutine 自然会停止。** 生命周期必须显式设计和验证。
- **误解：channel 已声明就可正常 send/receive。** 学生案例表明初始化遗漏会让路径停住。
- **误解：`index0` 是 `commitIndex` 或 `lastApplied`。** 它是保留 log slice 的全局起始 index。

## 掌握检查

1. 为什么 timer leak 可能只在 race-enabled long run 中出现？
2. timeout 增大后失败率降低，支持了什么 hypothesis，又没有证明什么？
3. 怎样区分“协议没有发送”与“发送到了未初始化 channel”？
4. heartbeat/election 的时间尺度为什么必须给 delayed RPC 留余量？
5. snapshot 后 `index0` 与 slice offset 的关系怎样变化？

## 掌握检查参考答案

1. 每次 shutdown 漏掉的 timer goroutine 会缓慢累积，短测试尚未耗尽资源；long run 才显出持续增长，race-enabled 运行的额外开销又让最终崩溃更容易出现。
2. 它支持 failure 对 timing/interleaving 敏感这一 hypothesis；它没有证明原 timeout 不合理，也没有证明 agreement 的 root cause 已修复。
3. 用 trace 分别确认发送动作、channel 的初始化/lifecycle 与接收动作：若协议路径已尝试发送而 channel 从未初始化，停滞证据指向 initialization，而不是消息根本未产生。
4. candidate 需要完成 RequestVote 往返，而消息可能 delay 或 drop；两种时间尺度过近会让正常延迟在一轮 election 完成前就触发下一轮。
5. snapshot 截断 prefix 后，`index0` 变为当前保留 slice 第一个元素的全局 index；例如 `index0 = 10` 时，slice offset 0 对应全局 log index 10。

- **核心问题**：`Start` 与 `ticker` 到底发送哪些 entries？heartbeat 限额怎样影响 test progress？读静态 `peers` 是否算 race，condition variable 又怎样唤醒 applier？

- **边界**：课堂对 `rf.killed` 的 race 问题没有给出确定结论；本节保留该不确定性，不补充 transcript 之外的断言。
- **证据边界（transcript-only / no-slides）**：仅依据本节时间范围内的 transcript；本节没有可用课件材料，不从课堂屏幕、slides 或未口述代码补充结论。

## 问答序列

### Q1：`Start` 发的 AppendEntries 与 heartbeat 发的 AppendEntries 有什么不同？

**A：调用的是同一 send-appends function。** `Start` 先把新 command append 到 Raft log，`ticker` 不新增 entry；两者触发发送时，都根据每个 peer 的 `nextIndex` 从同一 Raft log 复制正确 suffix 到 arguments。

### Q2：heartbeat 是否只会发送空 entries？

**A：多数情况下为空，但不保证。** 若 follower 落后，heartbeat 触发的 send-appends 也会取出缺失 entries。`Start` 触发时，通常会立即带上刚 append 的 entry。

### Q3：只在 heartbeat timer 发送 actual entries，会导致“无法 agreement”吗？

**A：课堂回答认为这通常不是无法 agreement 的原因。** 参与者确认有人只靠 heartbeat 发送也完成整个 Lab 2，但会更慢；因此偶发 agreement failure 还应寻找其他证据，而不能仅凭 trigger 位置下结论。

### Q4：为什么仍不推荐 heartbeat-only？

**A：实验限制每秒 heartbeat 次数，且后续测试检查 progress speed。** 若 client command 必须等下一个周期才复制，每条操作增加几十到上百毫秒等待，真实服务吞吐/延迟也不理想。`Start` 触发立即复制能把“有新工作”与网络发送直接连接。

### Q5：测试怎样区分 heartbeat 与带 entry 的 AppendEntries？

**A：课堂先以“heartbeat 通常没有 entries”解释概念，随后说明测试不一定逐条机械计数，而会观察系统是否在约束下足够快地取得 progress。** 每个 `Start` 可以产生 AppendEntries；心跳频率限制不意味着实际 client appends 也只能每秒十次。

### Q6：多个 goroutine 同时读取 `rf.peers`，不加 lock 会被 race detector 报告吗？

**A：若该 slice 构造后不再修改，多个 reader 本身没有 writer 冲突。** 课堂讨论指出 `peers` 是静态的，因此没有对应修改者；讲者也说自己一直运行 race detector，没有看到这里的 complaint。

### Q7：那 `rf.killed` 呢？

**A：课堂没有得出确定结论。** 参与者追问 kill 与其他操作同时发生是否形成 race，讲者表示不确定；随后讨论又回到 `killed` 不修改 `peers`。因此不能用这段对话证明 `rf.killed` 的同步方案正确或错误。

### Q8：apply condition variable 再次怎样工作？

**A：当 `matchIndex` 更新并使新 entry 可 commit 时，相关线程 signal condition variable。** applier 被唤醒，检查 `commitIndex` 与 `lastApplied` 之间是否有内容；有则按序推送到 apply channel，没有则继续 sleep/wait。

## 机制梳理

`Start` 与 `ticker` 是两种**触发源**，不是两种 replication algorithm：

- `Start` 改变 log state，然后立即触发 send-appends，优化新 command latency。
- `ticker` 不新增 command，周期触发同一路径，维持 leadership 并为落后 peer 提供再次 catch-up 的机会。
- send-appends 始终以 `nextIndex` 和当前 Raft log 决定每个 peer 的 payload，因此 trigger 不直接决定 entries 内容。

测试同时观察 safety、liveness 与 progress。heartbeat-only 可能保持最终 liveness，却在有限 heartbeat rate 下拖慢 progress。race 讨论则提醒：是否需要 lock 取决于是否存在 concurrent writer，不是“两个 goroutine 同时读”这一事实本身；但课堂未解决的变量不能擅自下结论。

## 例子与取舍

- **例子：同步 follower。** `ticker` 触发时没有缺失 suffix，AppendEntries 为空，发挥 heartbeat 作用。
- **例子：落后 follower。** 同样由 `ticker` 触发，但 `nextIndex` 指向更早位置，payload 含 entries，发挥 catch-up 作用。
- **例子：新 command。** `Start` append 后立刻触发同一发送路径，避免等待下一 heartbeat tick。
- **取舍：heartbeat-only。** 路径更少、Lab 2 可能通过；代价是 client-visible latency 和后续 progress test 风险。
- **取舍：lock-free read。** immutable shared data 可并发读；一旦存在 writer 或 lifecycle mutation，就需要重新评估。课堂只确认 `peers` 的静态前提。

## 常见误解

- **误解：从 `Start` 来的 RPC 与从 `ticker` 来的 RPC 采用不同 log 选择规则。** 两者复用同一 send-appends 逻辑。
- **误解：heartbeat 的定义要求 AppendEntries 永远为空。** 在课堂实现中，周期触发也可顺带补发 follower 缺失 entries。
- **误解：heartbeat-only 偶尔失败，所以 failure 一定由发送太慢造成。** 课堂明确说 agreement failure 很可能另有 bug。
- **误解：每秒十次 heartbeat 限额等于每秒只能复制十条 client commands。** `Start` 可额外触发带 entries 的 AppendEntries。
- **误解：任何无锁读取都会触发 race detector。** race 需要冲突访问；课堂讨论的 `peers` 前提是初始化后不变。

## 掌握检查

1. 为什么 trigger source 不足以判断 AppendEntries 是否为空？
2. heartbeat-only 如何同时满足“最终可复制”与“进展太慢”这两个描述？
3. Lab 3 的 progress concern 与真实 client latency 有什么对应关系？
4. 多 reader 访问静态 `peers` 与访问可能变化的 state 有何区别？
5. condition variable 被 signal 后，applier 为什么仍要重新检查条件？

## 掌握检查参考答案

1. `Start` 与 `ticker` 都调用同一 send-appends path；payload 由该 peer 的 `nextIndex` 和当前 Raft log 决定，所以 heartbeat 触发也可能带 entries，`Start` 触发也不是另一套选择规则。
2. 周期 heartbeat 最终仍可反复尝试复制，因此可能达到 agreement；但新 command 必须等待下一个 tick，受 heartbeat 频率限制而增加 latency、降低 progress speed。
3. 测试检查能否快于受限 heartbeat 节奏取得 progress；真实服务中同样的等待会让 client operation 每次多等几十毫秒，形成可见延迟与吞吐限制。
4. 静态 `peers` 只有并发 readers、没有 writer，课堂据此认为不会产生冲突访问；可能变化的 state 若同时被读写，就不能沿用这个前提。课堂没有解决 `rf.killed` 的具体同步结论。
5. signal 只表示“现在可能有可 apply 工作”；applier 醒来后仍要比较 `commitIndex` 与 `lastApplied`，有内容才按序发送，没有则继续等待。
