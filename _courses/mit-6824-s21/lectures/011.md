## 学习目标

1. 从 replicated state machine 的两种常见架构定位 Chain Replication（CR）在系统中的角色。
2. 能画出 `client -> head -> ... -> tail -> client` 的 update flow，以及 `client -> tail` 的 query flow。
3. 能解释为什么 tail application 是 commit point，以及 head 过早 reply 怎样违反 linearizability。
4. 能按老师的三个 case 处理 head、middle、tail failure，并说明 configuration service 为什么是避免 split brain 的必要角色。
5. 能复述 tail 端添加新 replica 的 online copy、delta catch-up 与 serving barrier。
6. 能比较 CR 与 Raft 在 client load、message fan-out、read path、failure availability 和大状态同步上的权衡。
7. 能说明多条旋转 chains 怎样扩展 read throughput，以及该优化依赖的负载与 consistency scope。

## 需要的先修知识

- Replicated state machine：相同 initial state、相同 operation order、相同 resulting state。
- Raft/Paxos/ZAB 的 consensus、leader、majority、log replication 与 snapshot/checkpoint。
- Primary-backup replication、GFS master、VM-FT test-and-set server。
- Linearizability 的 real-time order：已完成 write 之后开始的 read 不能返回 write 之前的值。
- Network partition、failure suspicion、split brain、reliable FIFO channel。
- ZooKeeper session、ephemeral znode、watch 与 sequential znode。

## 老师的教学主线

1. **用 ZooKeeper 回到 coordination context。** 任意 replica read 能扩展吞吐，但可能牺牲 linearizability；ZLocks 能做 leader election/soft locks，却不自动提供 transactional critical section。[00:02:39-00:25:26]
2. **从已有系统抽象两种架构。** 一种把所有 operations 都送入 Raft/Paxos；另一种把 consensus-backed configuration service 与 data-plane primary-backup protocol 分开。[00:25:40-00:32:16]
3. **定义 CR normal path。** Writes 进入 head，沿 reliable FIFO chain 传播；tail 应用后 reply。Reads 只到 tail；tail 因而成为提交与可见性的汇合点。[00:32:17-00:39:18]
4. **用反例验证 commit point。** 若 head 提前 reply，write 已完成但 tail 尚未更新，随后的 tail read 返回旧值，直接违反 linearizability。[00:39:23-00:50:17]
5. **枚举 failure recovery。** Head failure 删除未提交 suffix；middle failure 由 predecessor 重发缺失 updates；tail failure 由 predecessor 接任。所有 membership change 必须来自 configuration service。[00:50:28-01:00:50]
6. **恢复 replication factor。** 在旧 tail 继续服务时向新 server 复制 base state，记录并传输增量；新 tail 追平之前不能服务 clients。[01:00:55-01:04:42]
7. **比较 CR 与 Raft。** CR 分散 head/tail client load、降低 head fan-out、让 tail 单机读，recovery shape 也简单；代价是任一 chain member 不可达都会阻塞 writes，必须重配置后才能恢复。[01:04:53-01:08:30]
8. **用多 chains 扩展 reads。** Objects/shards 映射到不同 ordered chains，同一批 servers 轮换 tail 角色；负载均匀时 reads 并行扩展，每条 chain 的 CR 路径不变。[01:08:35-01:17:04]
9. **用课后问答界定边界。** 老师保留跨 chains 全局 linearizability 的未决性，并指出 configuration version 仍可能挡不住 partitioned old tail 与 stale client；paper 的 proxy path 只被课堂推测为相关动机。[01:17:37-01:31:51]

## 核心概念与依赖关系

```text
replicated state machine
  -> 两种系统架构
     -> all operations through Raft/Paxos
     -> configuration service + primary/backup
        -> Chain Replication data plane
           -> head orders updates
           -> reliable FIFO propagation
           -> tail applies update
              -> write reply / commit point
              -> tail-only query
                 -> linearizable observation

failure/partition
  -> configuration service chooses one chain
     -> head/middle/tail reconfiguration
     -> avoid split brain
     -> temporary unavailability while reconfiguring

tail read bottleneck
  -> shard objects over rotated chains
     -> multiple legal tails
     -> parallel reads if load is balanced
     -> per-chain protocol unchanged
```

## 一致性、可用性、性能与权衡

| 设计点 | 课堂收益 | 课堂代价或前提 |
| --- | --- | --- |
| Head 接收 writes、tail 接收 reads/replies | Client-facing load 至少分散到两台 server | Client 必须知道 current head/tail |
| Update 沿 chain 顺序传播 | Head fan-out 为 1；failure cases 呈 prefix 结构 | Write latency 穿过整条 chain |
| Tail-only reads | 单机本地 query；与 commit visibility 对齐 | 单链的 tail 可成为 read bottleneck |
| Tail 才能 reply write | 已完成 write 后的 read 能看到新值，支持 linearizability | 不能用 head 早回减少 client latency |
| 所有 chain members 参与 write | 每个 successor 了解 predecessor 的 ordered prefix | 任一 member unreachable 时 write 停止，必须 reconfigure |
| Configuration service 唯一决定 topology | 防止 partition 下多个 heads/split brain | Configuration path 本身要强一致；reconfiguration 有短暂停顿 |
| Tail 端在线加入 replica | Base copy 很大时仍可让旧 chain 继续服务 | 必须记录 delta，并在新 tail serving 前建立 catch-up barrier |
| Rotated multi-chain sharding | 多个 servers 各自作为某些 shards 的 tail，扩展 reads | 依赖 shard/load 分布；跨 chains 的全局 order 本讲未解决 |
| Control/data plane 分离 | 小 metadata 用 consensus，大 state 用专门同步协议 | 系统由两个组件构成，配置与数据协议必须正确衔接 |

## 关键结论与边界

- **Commit point 不是 head 接受 write，而是 tail 应用 update。** 这是 write reply 与 read visibility 对齐的时刻。[00:36:25-00:38:20]
- **Head 过早 reply 的反例无需故障。** 普通传播延迟就能让完成后的 read 在 tail 看到旧值。[00:49:07-00:50:17]
- **Configuration service 不只是 convenience。** Server 不能根据局部连接状况自行晋升；partition 下这样做会产生 split brain。[00:53:00-00:54:35]
- **CR recovery 简单不等于 CR failure 时不停服。** 三类 data-plane repair 较直接，但任一 chain member failure 都先阻塞整条 write path，直到新 configuration 建立。[01:00:10-01:08:24]
- **多 chains 不是任意 replica reads。** 同一个 object 仍固定映射到一条 chain，并从那条 chain 的 tail 读取。[01:09:52-01:13:36]
- **跨 objects/chains 的全局 linearizability 没有课堂结论。** 老师明确犹豫并把 transactions 留到后续。[01:24:10-01:31:51]
- **Version number 不是 stale old-tail 问题的完整答案。** Partitioned old tail 与 stale client 可能共享同一旧 version；课堂只推测 proxy 与此有关。[01:28:54-01:31:02]

# 001. 课程衔接、RSM 回顾与 ZooKeeper 简单锁

> 时间范围：`00:00:00-00:09:59`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

老师先处理课程事务并更正此前对 Go `defer` 的说明，随后把本讲放回复制状态机（replicated state machine, RSM）的连续脉络中：先补完上一讲没有讲完的 ZooKeeper locks，再进入 Chain Replication。真正的 Chain Replication 尚未在本段展开；本段的技术作用是重申“相同初始状态 + 相同顺序的操作 = 相同最终状态”，并用 ZooKeeper 的读扩展性与非线性化读作为后续一致性/性能权衡的参照。[00:00:00-00:06:25]

## 教学展开

1. **课程事务与代码更正。** 老师提醒周四 quiz 和 final project proposal；随后纠正自己此前的说法：`defer` 即使写在某个 lexical block 中，也是在函数返回时执行，不是在离开该 block 时执行。[00:00:14-00:02:23]
2. **说明本讲的两段内容。** 本讲先结束 ZooKeeper locks，再讨论 Chain Replication；二者都处在 replicated state machine 的背景下。[00:02:39-00:03:07]
3. **回顾 RSM。** 客户端把操作交给服务；ZAB、Raft 等复制协议让多数服务器接受命令；各副本以相同顺序应用相同操作。只要初始状态相同，副本就保持相同状态，故障时其他机器才可能接管。[00:03:07-00:04:07]
4. **引出读性能与一致性的交换。** ZooKeeper 可由任意 peer 服务 read，因此 read throughput 能随服务器数增加；代价是某个 peer 可能尚未看到最新 update，所以该接口不提供 linearizable reads。老师强调，这并不等于 ZooKeeper 无法支持有用程序，它提供的是面向 configuration/coordination programs 的另一组保证。[00:04:11-00:06:16]
5. **构造 simple ZooKeeper lock。** `acquire` 循环尝试创建名为 `lf` 的 ephemeral znode。创建成功者获得锁；创建失败者调用 `exists` 设置 watch，并等待 znode 消失的通知。`release` 删除 `lf`，删除触发所有等待者的 watch；它们重新竞争，下一轮仍只有一个客户端创建成功。[00:06:25-00:09:35]
6. **指出两个关键 primitive。** Watch 负责在 lock znode 删除时唤醒等待者；`EPHEMERAL` 的故障语义在本段末尾刚被提出，完整解释延续到下一段。[00:09:35-00:09:59]

## 概念、符号与推导

- **Replicated state machine (RSM)**：所有副本从同一 state 出发，按同一 order 应用同一 operations，从而得到同一 state。[00:03:57-00:04:07]
- **Linearizability**：本段没有给出形式定义，只用反面直觉说明：若任意 replica 可以返回尚未包含 latest update 的值，就不能把 read 看成发生在符合 real-time order 的单一点。[00:04:34-00:05:21]
- **`lf`**：表示 lock file/lock znode 的伪代码名称。[00:06:46-00:07:11]
- **Watch**：由失败的竞争者通过 `exists` 注册；目标 znode 消失时产生 notification。[00:07:31-00:08:09]
- **Ephemeral znode**：与 client session 关联的 znode。本段只提出它用于处理持锁客户端在 `release` 前崩溃的情形，删除机制在下一段完成。[00:09:46-00:09:59]
- 本段无公式推导。

# 002. Ephemeral、排队锁与 ZLock 的故障边界

> 时间范围：`00:09:59-00:19:55`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

本段接续 simple ZooKeeper lock，先补齐 ephemeral znode 在客户端故障时的作用，再从 herding effect 推导出 sequential-znode lock。老师随后把重点从“互斥是否成立”转到“持锁者故障时 critical section 是否原子”，明确 ZooKeeper lock（ZLock）弱于单机 Go mutex。这一边界为后面 configuration service 的用法提供背景：分布式锁适合 leader election 和容错协调，但不能自动把一串外部状态修改变成 atomic transaction。[00:09:59-00:19:55]

## 教学展开

1. **补齐 `EPHEMERAL` 的故障语义。** 若客户端在调用 `release` 前崩溃，ZooKeeper 判断 session 已失效后代替客户端删除 ephemeral lock znode，删除触发其他等待者的 notifications，系统因此不会永久卡在无人释放的锁上。[00:09:59-00:10:27]
2. **发现 simple lock 的 herding effect。** 以 1000 个客户端为例，1 个创建成功，999 个 watch 同一个 znode；锁释放时 999 个同时重试，但仍只有 1 个成功。每次释放都会产生大量注定失败的请求，网络消息并非免费，这在实践中是性能问题。[00:10:36-00:11:48]
3. **提出 better lock。** 使用 `SEQUENTIAL` 创建 `lock-0`、`lock-1` 等依次编号的 ephemeral znodes。客户端取得编号 `n` 后读取 children；若 `n` 最小则获得锁，否则只 watch 自己的直接 predecessor `p`。[00:11:51-00:14:46]
4. **把竞争者排成队。** 每个客户端只等待前驱；`lock-0` 删除时只唤醒 `lock-1` 的持有者，后者必然成为最小编号。老师将其类比为 multicore programming 中的 ticket lock，收益是锁交接只唤醒下一位，而不是唤醒所有等待者。[00:14:46-00:15:47]
5. **澄清伪代码。** 课堂问题问“第 4 行的 watch 做什么”；老师更正：第 4 行只找 predecessor `p`，watch 应属于下一行对 `p` 的等待操作。[00:15:58-00:16:40]
6. **解释 session failure detection。** 客户端与 ZooKeeper 通过 session 和 heartbeat 保持联系。服务一段时间收不到客户端消息便关闭 session，并删除该 session 创建的 ephemeral znodes；网络恢复后，旧 session 不会复活，客户端必须 retry 或建立新 session。[00:16:44-00:17:51]
7. **区分 ZLock 与 Go lock。** ZooKeeper 可能在持锁客户端仍处于网络分区时判定其失效并撤销锁。若客户端已执行 critical section 的一部分，其他客户端接手时可见 intermediate state；因此 ZLock 不保证整个 critical section 的 atomicity。老师开始列举它仍然适用的用途，首先是 leader election，具体延续到下一段。[00:17:53-00:19:55]

## 概念、符号与推导

- **Herding effect**：同一状态变化唤醒大量等待者，造成高峰请求，但只有一个请求能取得资源。[00:10:36-00:11:40]
- **`SEQUENTIAL`**：让 ZooKeeper 为创建的 znode 附加单调递增序号；客户端可据此形成全序队列。[00:12:48-00:13:50]
- **`n` 与 `p`**：`n` 是客户端自己的 sequential znode 编号；`p` 是紧邻 `n` 的较小编号，即直接前驱。[00:13:50-00:14:46]
- **Session**：客户端与 ZooKeeper 的有效关系；heartbeat timeout 使服务关闭 session，并清理该 session 的 ephemeral nodes。[00:17:01-00:17:47]
- **Critical-section invariant**：进入 critical section 前 invariant 成立，中间步骤可能暂时破坏 invariant，正常退出时重新建立。若持锁者中途失效并被撤销锁，中间状态就可能暴露。[00:18:43-00:19:20]
- 本段无公式推导。

## 例子与课堂提示

- `1000 -> 999 -> 998` 的等待者数量用于量化 herding：每轮几乎所有唤醒和重试都没有进展。[00:10:43-00:11:30]
- `lock-10` 只 watch `lock-9`，用于说明 predecessor watch 怎样把广播唤醒变成一对一交接。[00:14:26-00:15:21]
- 临时网络分区的例子说明 failure detector 只能根据 session/heartbeat 作决定；恢复连接的客户端不能继续使用已关闭 session。[00:16:44-00:17:47]
- 易错点：distributed lock 的 mutual exclusion 不等于 critical section 的 transactional atomicity。[00:17:53-00:19:20]

# 003. Soft Locks 与两种复制状态机架构

> 时间范围：`00:19:56-00:29:55`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

老师先回答“较弱的 ZooKeeper lock 到底有什么用”，再于 `00:25:40` 正式为 Chain Replication 搭台：把此前课程中的系统归纳为两种 replicated-state-machine 架构。第一种让所有业务操作都经过 Paxos/Raft；第二种把“小而强一致的 configuration service”与“大数据上的 primary-backup replication”分开。Chain Replication 将被定位为第二种架构中的数据复制协议。[00:19:56-00:29:55]

## 教学展开

1. **Leader election 用途。** 多个客户端竞争 ZLock，成功者成为 leader。若前任持锁者留下 intermediate state，新 leader 可负责 cleanup；也可用老师所说的 ready trick：先完成一组 writes，最后才 expose 结果，使外部观察更接近一次 atomic publication。[00:19:56-00:20:16]
2. **Soft lock 用途。** 以 MapReduce worker 为例，worker 对 input file 加锁，执行 map task 后释放。无故障时任务只执行一次；若 worker 中途失败，ZooKeeper 释放锁，另一个 worker 可能再次执行同一任务。这里 lock 是 common-case performance optimization，正确性必须允许 duplicate execution。[00:20:19-00:21:48]
3. **为什么不能去掉 `EPHEMERAL`。** 若创建 persistent lock znode，持锁客户端 crash 后 znode 无人删除，会 deadlock。让其他进程擅自删除也不安全，因为原客户端可能只是 partitioned、仍认为自己持锁；这又回到无法区分 crash 与 partition 的 consensus 问题。[00:22:04-00:23:50]
4. **课堂追问进一步界定语义。** Soft lock 就是操作在故障下可能执行两次。纯 leader election 本身未必留下中间状态，但 leader 常会写 configuration；ready trick/atomic rename 用于最后一次性暴露准备好的内容。[00:24:11-00:25:26]
5. **切入两种 RSM 架构。** Approach 1 是像 Lab 3 一样，让 `put`、`get` 等所有 operations 经过 Raft/Paxos/ZAB，并从 apply channel 更新服务 state。[00:25:40-00:27:06]
6. **提出更常见的 Approach 2。** Configuration server 自身可由 Raft/Paxos/ZAB 复制，只负责 coordinator/master role；每个 data replica group 另跑 primary-backup protocol。GFS 是 master 决定 chunk replica group，再由 chunk replicas 做 P/B；VM-FT 是 test-and-set server 记录 primary，primary/backup 另有执行复制通道。[00:27:06-00:29:03]
7. **用大状态提出性能问题。** 若 Lab 3 的 key/value state 达到 TB 级，所有业务与复制均绑在 Raft 中，会面对频繁 log flush 和巨大 checkpoint/snapshot 的传输问题。老师在段尾提出问题，答案在下一段展开。[00:29:14-00:29:55]

## 概念、符号与推导

- **Ready trick**：先写好内容，最后通过单一“ready/expose”动作让结果可见；本段课堂只给出概念和 rename 提示，没有完整协议。[00:20:02-00:20:14; 00:24:49-00:25:04]
- **Soft lock**：无故障 common case 避免重复工作，但 failure case 允许同一 operation 再执行；它优化性能而不提供 exactly-once guarantee。[00:20:19-00:21:48]
- **Approach 1**：configuration、operation ordering 与 state replication 都由同一 Paxos/Raft-based RSM 承担。[00:25:50-00:27:06]
- **Approach 2**：consensus-backed configuration service + 每个 replica group 的 primary-backup replication。[00:27:21-00:29:03]
- **Checkpoint size**：老师在本段只提出“巨大 key/value state 会带来多大的 checkpoint”这一问题，定性答案在下一段；本段无数值或公式推导。[00:29:14-00:29:55]

## 例子与课堂提示

- MapReduce map task 可重复执行，说明 soft lock 适用于“duplicate work 可接受”的任务；若 operation 非幂等且不可重复，该例不能直接套用。[00:20:31-00:21:44]
- Persistent znode 的反例展示 availability 与 safety 的夹击：不删会 deadlock，误删则可能出现两个持锁者。[00:22:36-00:23:50]
- GFS 和 VM-FT 都被老师用来证明 configuration/master 与 data replication 分层并非新发明，而是此前课程已经见过的共同结构。[00:28:13-00:28:58]
- 易错点：老师没有说 Approach 1 不可用；他说 Approach 2 更常见，而 Spanner 等系统仍会采用 Approach 1 风格。[00:27:06-00:27:21]

## 本段掌握检查

1. **问：ZLock 的两个主要适用场景是什么？**  
   **答：**Leader election/cleanup，以及允许 failure case 重复执行的 soft lock。[00:19:36-00:21:48]

# 004. Chain Replication 的 Head/Tail 路由与提交点

> 时间范围：`00:29:55-00:39:55`  
> 证据：本段 transcript；[课堂讲义：`l-cr.txt` p.1](/assets/courses/mit-6824-s21/lectures/011/materials/l-cr.txt)。

## 本段在整讲中的作用

本段完成两种架构的比较并正式定义 Chain Replication（CR）。老师从“大状态不适合一体化 checkpoint”推到 configuration/data plane 分离，再依次给出 master、head、tail、update path、query path、commit point 与无故障时的 linearizability 直觉。最后以 breakout question 检验：为什么必须由 tail 而不是 head 对 write 回应。[00:29:55-00:39:55]

## 教学展开

1. **回答 checkpoint 问题。** Checkpoint 大小随 key/value state 大小增长；若 state 巨大，向新 replica 发送 snapshot 也会巨大。因而常把小状态的 configuration service 与复制大量数据的 P/B protocol 分开，以便后者使用更专门的 synchronization/resynchronization 方案。[00:29:55-00:30:50]
2. **比较组件数量。** Approach 1 的优点是单一组件：Raft 同时负责 operation ordering 与 configuration。Approach 2 有两个组件：consensus-backed configuration service 和独立 primary-backup scheme；后者无需自行决定 replica group membership。[00:31:02-00:32:16]
3. **定位 Chain Replication。** CR 正是 Approach 2 中的 primary-backup replication scheme，假设已经存在 configuration service，paper 称之为 master。老师预告其特点：query 只涉及 tail、failure recovery 简单、`put/get` 可 linearizable，并且实际系统采用过这一设计。[00:32:17-00:33:54]
4. **建立 topology。** Configuration service 记录某条 chain 包含哪些 servers，以及谁是 head/tail。示例链是 `S1 -> S2 -> S3`，`S1` 为 head，`S3` 为 tail；client 可先从 configuration service 获取该映射。[00:34:00-00:35:09]
5. **Update/write path。** Client 把 write 发给 head；head 在本地应用 state change，再经 reliable FIFO channel 向后继转发。每个 intermediate server 先应用再转发，直到 tail 应用 update；随后 **tail** 向 client 返回 acknowledgment。[00:35:09-00:36:20]
6. **Query/read path。** Client 直接把 read/query 发给 tail，tail 只在本地读取并立即回答，不涉及其他 nodes。于是 writes 在 head 入口排序，reads 与 write acknowledgment 则在 tail 汇合，head/tail 至少分担了 client workload。[00:36:25-00:38:07]
7. **确定 commit point。** Tail 应用 update 的时刻是 write 的 commit point，因为该 update 从此对所有后续 tail reads 可见；在此之前中间副本上的 state 不对 read path 暴露。[00:36:25-00:38:20]
8. **给出无故障 linearizability 直觉。** Head 为 writes 选择 total order，各 replicas 依 FIFO 顺序应用；tail 只暴露已经走完整条 chain 的 updates。Write 已收到 tail reply 后才开始的 read 必然在 tail 看到该 write。[00:38:23-00:39:18]
9. **提出课堂反例题。** 老师让学生讨论：若 head 收到 write 后过早回复，而 update 尚未到 tail，怎样破坏 linearizability。具体答案在第 005/006 段展开。[00:39:23-00:39:55]

## 概念、符号与推导

- **Master/configuration service**：决定 chain membership、head 与 tail；CR data protocol 依赖它提供配置。[00:32:36-00:34:39]
- **Head**：update/write 的唯一 client entry，确定 writes 的处理顺序。[00:34:50-00:35:41]
- **Tail**：query/read 的唯一入口，也是 write reply 的发送者。[00:36:05-00:37:03]
- **Reliable FIFO link**：相邻 replicas 之间可靠且按序传递 updates 的 channel。[00:35:31-00:35:58]
- **Commit point**：tail 应用 update 的时刻；此时 update 开始能被 query 看见，也是在此之后才能 reply write client。[00:36:25-00:38:20]
- **无故障 linearizability 推导**：head total-order writes → 每个 successor 依 FIFO 应用相同顺序 → tail 应用后才 reply → real-time 上晚于 reply 的 read 访问同一 tail，故能观察该 write。[00:38:23-00:39:18]
- 本段没有数值公式推导。

## 例子与课堂提示

- `S1 -> S2 -> S3` 例子固定了路由：write 到 `S1`，依次经过 `S2` 到 `S3`，由 `S3` 回应；read 直接到 `S3`。[00:34:30-00:37:03]
- 与 Lab 3 Raft 对比：课堂实现让 read 走 Raft log；即使做 read-only optimization，leader 仍需先与 majority 联系。CR 的 tail read 只访问一个 server。[00:37:13-00:38:07]
- `[课堂讲义: l-cr.txt p.1]` 与口述一致地列出 head/tail 路由、tail reply、configuration service 和 linearizability 直觉。讲义还含本段未口述的扩展论点；这些不作为本段课堂事实展开。
- 易错点：不能把“某副本已经写入”直接等同于 committed；只有 tail 已处理才满足本讲定义的 commit point。

## 本段掌握检查

1. **问：Chain Replication 属于哪种 RSM 架构？**  
   **答：**Consensus-backed configuration service 加独立 primary-backup data replication 的 Approach 2。[00:31:20-00:32:42]
2. **问：Write 和 read 分别发给谁？**  
   **答：**Write/update 发给 head 并沿 chain 传播；read/query 直接发给 tail。[00:35:09-00:37:03]
3. **问：为什么由 tail 回应 write client？**  
   **答：**Tail 应用后 write 才对 read path 可见；该时刻才是 commit point。[00:36:05-00:38:20]
4. **问：CR 的 read 为什么只涉及一个 server？**  
   **答：**所有 query 都路由到 tail，而 tail 的 state 只包含按 chain 顺序到达并可见的 updates，可本地回答。[00:36:39-00:38:07]
5. **问：无故障时 linearizability 的关键链条是什么？**  
   **答：**Head 排 write 顺序，FIFO 保持该顺序，tail 应用后才 reply，后续 reads 又都在 tail 执行。[00:38:23-00:39:18]

# 005. 过早 ACK 的线性化反例

> 时间范围：`00:39:55-00:49:52`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

本段是上一段 breakout question 的课堂活动与答案开头。老师让学生用具体 execution 检验 protocol 改动，而不是只接受“tail 是 commit point”的口头结论。`00:40:32-00:47:43` 没有可用讨论 transcript，因此笔记不推测各 breakout room 内容；回到主课堂后，老师构造 `S1/S2/S3` 与 write-then-read 的反例，答案在本段末尾跨界到第 006 段才完整结束。[00:39:55-00:49:52]

## 教学展开

1. **布置讨论。** 问题是：update 仍会沿 `S1 -> S2 -> S3` 传播，但若 `S1`（head）在 update 到达 tail 前就 reply client，会怎样破坏 linearizability。学生也可讨论其他 CR 问题。[00:39:55-00:40:03]
2. **Breakout room。** `00:40:03` 左右开始分组；转录在 `00:40:32-00:47:43` 无语音内容，之后是关闭 breakout rooms 的课堂协调，`00:48:58` 回到主讲。[00:40:03-00:48:58]
3. **恢复 protocol execution。** Client 1 向 head `S1` 发 write；`S1` 本地处理后立刻回 acknowledgment，同时 update 仍在向 `S2`、`S3` 传播。[00:49:07-00:49:44]
4. **安排违反 real-time order 的 read。** Client 1 已经收到 write 成功 reply，但在 `S2` 尚未把 update 送达 `S3` 时，client 又向 tail `S3` 发 read。[00:49:35-00:49:52]

# 006. 三类节点故障与重配置

> 时间范围：`00:49:53-00:59:52`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

本段先闭合“head 过早 ACK”的 linearizability 反例，再从正常路径转向故障路径。老师用同一组不一致进度 `S1:[U1,U2,U3]`、`S2:[U1,U2]`、`S3:[U1]` 依次枚举 head、middle、tail failure，说明 chain topology 把 recovery 缩成三个局部情形；configuration service 负责唯一合法的 membership change，从而避免 split brain。[00:49:53-00:59:52]

## 教学展开

1. **闭合过早 ACK 反例。** Tail `S3` 尚未收到 write，因此返回旧值；client 在 write 已成功返回后仍读不到自己的 write，违反 linearizability。结论是：必须等 tail 处理 update，由 tail 发送 acknowledgment，tail application 才是 commit point。[00:49:53-00:50:17]
2. **设定 recovery 状态。** Head `S1` 已处理 `U1,U2,U3`，middle `S2` 已处理 `U1,U2`，tail `S3` 只处理 `U1`。由于 updates 依次向后传播，越靠后的 server 拥有越短的 update prefix。[00:50:28-00:51:35]
3. **Head failure。** Configuration service 判定 `S1` gone，删除它并把 `S2` 提升为新 head。丢失的 `U3` 尚未到 tail、没有 committed，因此可视为从未发生；未来 clients 改发 `S2`，无需额外 state repair。[00:51:38-00:52:58]
4. **为什么不能由 `S2` 自行接管。** `S2` 无法区分 `S1` crash 与二者 partition；若自行成为 head，仍在另一 partition 服务的 `S1` 也可能继续接受 commands，形成 two heads/split brain，破坏 total order。只有 configuration service 可宣布新 chain，并通知 servers/clients。[00:53:00-00:54:50]
5. **相邻链路假设。** 学生追问 updates 是否保证按序到达；老师指出 CR 需要相邻 servers 之间的 reliable FIFO connection，并推测实现可使用 TCP。[00:55:01-00:55:36]
6. **Middle failure。** 若 `S2` 失败，configuration service 把 `S1` 与 `S3` 接成新 chain。`S1` 必须把 `S3` 尚未看到的 in-flight updates（例中 `U2,U3`）重发，使新 successor 追上 predecessor。[00:55:38-00:56:58]
7. **Tail failure。** 若 `S3` 失败，`S2` 成为新 tail，clients 得知新配置。所有曾在旧 tail committed 的 updates 也必然已在 `S2`，所以没有 committed update 丢失；老师把这一情形也归为 straightforward。[00:57:01-00:58:32]
8. **Client reply 的歧义。** 新 tail 可能拥有旧 tail 尚未 ACK 的 operations；client 通常会 retry，并需要与 Lab 3 类似的 duplicate suppression/deduplication。老师指出 paper 对具体选择并不十分清楚；无 reply 只表示 operation 可能成功也可能未成功。[00:58:53-00:59:52]

## 概念、符号与推导

- **Update-prefix shape**：示例状态满足 `Hist(S3)` 是 `Hist(S2)` 的 prefix，`Hist(S2)` 是 `Hist(S1)` 的 prefix。[00:50:51-00:51:24]
- **Committed update**：已由 tail 处理的 update。Head-only 或 middle-only update 尚未 committed，head failure 时可以消失。[00:52:30-00:52:58]
- **Reconfiguration**：configuration service 删除 failed server、指定新的 head/tail/predecessor/successor，并把新配置通知参与者。[00:52:06-00:54:35]
- **Split brain**：旧 head 与自行晋升的新 head 同时服务，各自建立 operation order。[00:53:00-00:54:13]
- **恢复推导**：head fail 只删未提交 suffix；middle fail 由 predecessor 重发 successor 缺失 suffix；tail fail 由 predecessor 接任，保留旧 tail 的全部 committed prefix。[00:51:38-00:58:32]
- 本段无数值公式推导。

## 例子与课堂提示

- `S1:[U1,U2,U3] / S2:[U1,U2] / S3:[U1]` 是贯穿三类 failure 的同一白板例子，服务于“committed prefix 不丢、partial suffix 如何处理”的比较。[00:51:02-00:58:20]
- 网络 partition 反例说明 local failure suspicion 不足以授予 head 权限，configuration service 是 safety boundary。[00:53:00-00:54:35]
- Tail failure 后 retry 的问答提醒：replication 保住 state 不等于 client 自动获得 exactly-once reply；request identity/deduplication 是另一层机制。[00:58:53-00:59:52]
- 易错点：`U2` 在示意中尚未到旧 tail，但 tail fail 后 `S2` 成为新 tail，它可能随 reconfiguration 变成 completed；client 是否看到 reply 仍有歧义。

## 本段掌握检查

1. **问：为什么 head 提前 ACK 会破坏 linearizability？**  
   **答：**Write 已返回后，tail 仍可能保持旧 state，随后的 tail read 会返回 write 前的值。[00:49:53-00:50:17]
2. **问：Head failure 时为什么可丢掉 `U3`？**  
   **答：**`U3` 未到 tail、没有 committed，client 不可能已收到合法的 tail acknowledgment。[00:51:38-00:52:58]
3. **问：Middle failure 需要额外做什么？**  
   **答：**Predecessor 把 failed middle 可能未送到 successor 的 updates 重新发送。[00:55:38-00:56:58]
4. **问：Tail failure 为什么不丢 committed updates？**  
   **答：**任何到达旧 tail 的 update 必先经过它的 predecessor，新 tail 已拥有这些 updates。[00:57:23-00:58:25]
5. **问：为什么 `S2` 不能自行成为 head？**  
   **答：**它无法区分 crash 与 partition，自行晋升可能与仍存活的 `S1` 形成 split brain。[00:53:00-00:54:35]

# 007. 加入新 Tail 与 CR/Raft 权衡

> 时间范围：`00:59:52-01:09:52`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

老师先总结 CR recovery 为何比 Raft Figure 7/8 简单，再补上长期运行系统必须具备的 replica addition。随后回到本讲的核心比较：CR 把 client RPC 分散到 head/tail、让 head 每次只向一个 successor 发送、tail 独立服务 reads，但任何单节点失联都会阻塞整条 write path，必须 reconfigure 后才能恢复。这一段同时呈现性能优势和可用性代价。[00:59:52-01:09:52]

## 教学展开

1. **总结 recovery 简洁性。** CR 只需考虑 head、middle、tail 三类失败。原因一是 updates 沿 chain 单向传播；原因二是 configuration decision 已外包给 configuration manager。老师将其与 Raft paper Figure 7/8 的多种 log state 情形对比。[00:59:58-01:00:50]
2. **为什么必须补副本。** 若只在 failure 时删除 replicas，chain 会从 3 变 2、再变 1、最终归零；长期系统必须把 replacement server 加回来。[01:00:55-01:01:16]
3. **选择在 tail 端扩展。** 示例从 `S1(head) -> S2(tail)` 加入 `S3`，目标是让 `S3` 成为新 tail。`S3` 先从 `S2` 复制完整旧 state；复制 GB/TB 数据可能需要几十分钟甚至数小时，在此期间原 chain 继续服务，`S2` 记录复制开始后尚未传给 `S3` 的 updates。[01:01:18-01:02:30]
4. **切换 tail。** Base copy 完成后，`S3` 告诉 `S2` 自己 ready；`S2` 发送积累的 remaining updates。`S3` 应用这些 updates 后成为 tail，旧 `S2` 把仍找它的 clients redirect 到 `S3`。[01:02:30-01:03:19]
5. **回答“追赶是否永无止境”。** 一旦建立正常 FIFO/TCP channel，积累的 updates 之后可继续 pipeline；新 updates 会按普通 CR path 从 `S2` 转发给 `S3`。关键不是世界停止产生 updates，而是 `S3` 在处理完切换点前的 backlog 之前不服务 client requests。[01:03:26-01:04:42]
6. **性能优点一：分散 client RPC。** Writes 进入 head，reads 与 write acknowledgments 在 tail，client-facing load 不必全压在 Raft leader 上。[01:04:53-01:06:02]
7. **性能优点二：head fan-out 为 1。** CR head 只向一个 successor 发一次 update；Raft leader 则向 peers 复制 log entries。CR 整条 chain 仍有逐跳消息，但 head 本身只承担一个下游 send。[01:06:06-01:06:29]
8. **性能优点三：read 只访问 tail。** 即使 Raft 使用 read-only optimization，不把 read 追加到 log，leader 仍需确认 majority；CR tail 可单机回答 query。加上三类 failure recovery 简单，这是 CR 的主要吸引力。[01:06:31-01:07:15]
9. **主要 availability 代价。** CR write 必须经过当前 chain 的每个 server；任何一个 server unreachable，write 都不能 ACK，必须先 reconfigure，因此有短暂 downtime。Raft 只要剩余 servers 仍构成 majority，就可继续 commit，无需因一个 follower failure 立刻停服。[01:07:24-01:08:30]
10. **引出多链优化。** 因单链 reads 都压在一个 tail，老师提出把 objects/volumes 分到多条 chains，并旋转同一组 servers 在各 chain 中的位置；本段结束时刚画出 `CH1: S1 -> S2 -> S3` 与 `CH2` 的开头。[01:08:35-01:09:52]

## 概念、符号与推导

- **Tail extension**：先复制旧 tail state，再传递 copy 期间积累的 update suffix，最后才让新 server 对 client 可见。[01:01:18-01:04:42]
- **Backlog/catch-up condition**：新 tail 不必等系统不再产生 writes；只需处理完旧 tail 定义的切换 backlog，并让后续 updates 进入正常 ordered stream。[01:03:26-01:04:34]
- **CR write availability condition**：当前配置中的每个 chain member 都必须参与 update propagation；一个 member unreachable 即需要 reconfiguration。[01:07:24-01:08:24]
- **Raft progress condition（课堂比较）**：剩余 peers 仍能形成 majority 时可继续接受/commit writes。[01:07:59-01:08:19]
- **Tradeoff 推导**：线性链降低 head fan-out、简化 failure state → 但 commit path 包含所有 chain members → 单节点 failure 立即阻塞，需 master 改配置。
- 本段无数值公式推导。

## 例子与课堂提示

- 从 3 replicas 一路删到 0 的口头例子说明“failure removal”本身不是完整的 availability story，replacement 必须进入 protocol。[01:00:55-01:01:16]
- GB/TB state copy 需要很久，呼应老师开场对巨大 Raft checkpoint 的担忧：separate P/B protocol 可以设计在线 copy + delta catch-up。[01:01:53-01:02:30]
- “Infinite loop”问题用于澄清 tail switch 的 barrier：新节点先追平，再对 client serving；后续更新通过同一 FIFO stream pipeline，不是反复做全量 copy。[01:03:26-01:04:42]
- 易错点：`head sends once` 指 head 只向直接 successor 发一次，不是整条 update 只产生一条网络消息。[01:06:06-01:06:29]

## 本段掌握检查

1. **问：为什么新 replica 通常加在 tail？**  
   **答：**旧 tail 可在继续服务时提供 base state、记录增量，再把新节点切换为唯一 read/reply endpoint。[01:01:18-01:03:19]
2. **问：全量复制期间怎样不丢新 updates？**  
   **答：**旧 tail 记录 copy 开始后的 updates，base copy 完成后发送 backlog，随后进入正常 pipeline。[01:02:01-01:04:16]
3. **问：CR 相比 Raft 怎样分摊 client load？**  
   **答：**Writes 到 head，reads 和 write replies 由 tail 处理，而不是全由 leader 承担。[01:05:35-01:06:02]
4. **问：CR 为什么单节点 failure 就可能短暂停服？**  
   **答：**Current chain 的所有 members 都在 write path 上，缺一环就无法让 tail commit，必须先 reconfigure。[01:07:24-01:08:24]
5. **问：Raft 在同一情形下为何可能继续？**  
   **答：**只要接受 entry 的 servers 仍构成 majority，单个 follower failure 不阻止 progress。[01:07:59-01:08:19]

- `[需回听 01:01:11]` 老师描述 replicas 递减到零后的结果时字幕缺词；不影响“必须添加 replacement”结论。

# 008. 多链分片的读扩展与架构总结

> 时间范围：`01:09:52-01:19:52`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

本段完成多链（multiple chains）优化，并用它收束 CR 与“一切都走 Raft”两种架构的取舍。老师说明同一组 servers 可在不同 shard chain 中轮换 head/middle/tail，使每台机器都承担一部分 tail reads；在负载均匀时 read throughput 随 tails 增长，同时每条 chain 内仍保持 linearizability。正式授课结束后，问答又澄清 Raft read 和 tail addition 的边界。[01:09:52-01:19:52]

## 教学展开

1. **完成三条旋转链。** `CH1: S1 -> S2 -> S3`，`CH2: S2 -> S3 -> S1`，`CH3: S3 -> S1 -> S2`。Configuration service 保存 shard/object 到 chain 的 mapping。[01:09:52-01:10:27]
2. **推导 read scaling。** 每个 server 都是某条 chain 的 tail，不同 shards 的 reads 可在不同 tails 并行。若 read load 在 chains 上均匀，三个 tails 可提供约三倍 read throughput；老师强调这个结论限定于 reads 分散到不同 chains。[01:10:27-01:11:01]
3. **保持 per-chain linearizability。** 每个 shard 仍使用原先的 head-to-tail CR protocol，读写并没有在同一 object 的 replicas 间随意切换，因此 single-chain linearizability 直接沿用。老师将其与 ZooKeeper 任意 peer read 对比：这里获得 read scaling 时不必放弃该保证。[01:11:01-01:11:33; 01:13:19-01:13:36]
4. **Client 获取配置。** Paper 对 client path 没有讲得很明确，提到可能经 proxy；老师以 Lab 4 为参照，说 client 通常下载含 shard assignment 的 configuration。Configuration manager 还可考虑 network topology、chain hot spots，改变 shard 分配并 rebalance。[01:11:50-01:13:09]
5. **解释复用同一 servers 的收益。** 单链中 tail 的 read load 较高而 middle 可能有闲置 CPU；旋转角色让各 server 都成为某些 shards 的 tail，从而利用这些空闲资源，而不是为每个 chain role 再配一组独立 servers。[01:13:42-01:14:31]
6. **总结两种架构。** Approach 1（Lab 3）把 configuration 和 service operations 都交给 Raft；Approach 2 用 Raft/Paxos 构建 configuration server，再让 data plane 运行 CR primary-backup。[01:14:41-01:15:26]
7. **总结 Approach 2 的收益。** Data replicas 可获得 scalable read performance；大 state 可以使用更 specialized state copy/synchronization，而不受小 configuration service 的复制方式束缚。老师仍强调 Approach 1 也可行，Lab 3 与后续 Spanner 是例子。[01:15:40-01:17:04]
8. **正式授课结束，进入问答。** 老师说明 Raft reads 若全部送 leader 可由 leader 服务，但新 term 仍需通过一个 empty agreement/no-op 确认自己 up-to-date；若想把 reads 分散到 peers，则不能由 follower 独自判断最新状态，需要 majority-based machinery。[01:17:15-01:18:46]
9. **再次讨论加 tail。** 学生提出新 `S3` 在 copy 期间按需向 `S2` 取数据并读服务的理解；老师表示 paper 描述一种具体方法，但也提出更清晰的替代：在 `S3` 收完 remaining operations 前，`S2` 仍是 serving tail，`S3` 不处理 client operations。该问答跨到第 009 段继续。[01:18:48-01:19:52]

## 概念、符号与推导

- **Shard-to-chain map**：configuration service 决定 object/shard 使用哪条 ordered chain。[01:10:10-01:10:27]
- **Role rotation**：同一 server 在不同 chains 中分别担任 head、middle、tail，以摊平 read-serving load。[01:09:52-01:10:41]
- **Read-throughput 条件**：不同 chains 的 read load 大致均匀，且 tail 是瓶颈时，新增/分散 tails 才能带来接近线性的扩展。[01:10:41-01:11:01]
- **Consistency scope**：本段确认每条 chain 上的 object operations 保持 CR linearizability；跨 objects/chains 的总序问题在下一段被课堂明确列为未决。[01:13:19-01:13:36]
- **Control/data plane 分离**：configuration service 可用 consensus 保证小规模 metadata；data plane 用 specialized P/B protocol 处理大 state 与高吞吐。[01:14:41-01:16:32]
- 本段无数值公式推导；`3 tails -> 约 3x reads` 是在 uniform distribution 前提下的课堂定性例子。

## 例子与课堂提示

- 三条 chain 的 cyclic permutation 用于确保 `S1/S2/S3` 各自成为一次 tail，而不是允许同一 object 从任意 replica read。[01:09:52-01:10:59]
- Configuration manager 可感知 network layout、调整每条 chain 的 shard 数并 rebalance，是老师提出的原则性可能，不是本段给出的具体 balancing algorithm。[01:12:29-01:13:09]

- 易错点：多链不是让 `S1/S2/S3` 都能读取同一个 object；同一 object 仍映射到一条 chain，并从该 chain 的 tail 读。

## 本段掌握检查

1. **问：三台 servers 怎样形成三个 tails？**  
   **答：**为不同 shards 建立顺序轮换的 chains，使每台 server 在其中一条 chain 担任 tail。[01:09:52-01:10:41]

# 009. Tail 切换细化、拓扑替代与一致性边界

> 时间范围：`01:19:52-01:29:51`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

这一段是课后深入问答。老师用具体 operation numbers 细化 tail handoff，再讨论 tree topology、chain length/latency、per-shard consistency、跨 chain linearizability 的未决边界、update propagation invariant，以及 network partition 下 configuration version 的必要性。它没有引入新的主协议，而是在压力测试前述设计的假设与 scope。[01:19:52-01:29:51]

## 教学展开

1. **用 `100/101-110` 解释 tail handoff。** 假设 base copy 让 `S3` 拥有 operations 到 100，而 `S2` 又积累 101–110。`S3` 请求 remaining operations；`S2` 在交付它们的同时停止担当 serving tail。`S3` 在应用 101–110 之前不处理 client reads/commands，追平后才对外作为 tail。[01:19:52-01:21:21]
2. **讨论 tree 替代 chain。** 学生希望用 balanced tree 把 propagation latency 从线性降为对数，并从多个 leaves 读。老师警告多个 leaves 可能不同步：client 先从一个 leaf 看到新值，再从另一个 leaf 看到旧值会危险；他没有对学生的复杂方案作完整 correctness 判断。[01:21:27-01:23:15]
3. **Chain 通常较短。** Chain depth 由 failure rate/availability 目标约束，实践中可能是 3–5 servers，因此线性 propagation latency 有界。老师确认只有整条 chain 的所有 replicas 都失去时，数据服务才彻底无副本可用；单节点不可达仍会触发短暂停顿和重配置。[01:23:15-01:24:07]
4. **澄清多链中的 consistency scope。** 对映射到同一 chain 的 object，多个 clients 的 operations 保持 strong consistency/linearizability。对于跨 objects、跨 chains 是否有全局 real-time total order，老师明确犹豫，认为可能需要更多 machinery，不愿在课堂当场作结论；serializability/transactions 将在后续讲次讨论。[01:24:10-01:27:04]
5. **解释 update propagation invariant。** 对示例顺序 `S1 -> S2 -> S3`，`S3` 的 update history 始终是 `S2` 的 prefix，`S2` 又始终是 `S1` 的 prefix。这不是“完整一轮传播后”才成立，而是 reliable FIFO propagation 下始终成立。老师提醒 paper 定义中 `i/j` 的角色容易读反。[01:27:08-01:28:47]
6. **Network partition 与 configuration version。** 若 server 仍活着但被 partition，不能让旧/new topology 同时把 updates 送进同一 successor。老师推测 configurations 应编号，每个 operation 携带 version/epoch；server 拒绝 version 不匹配的 commands。本段末尾继续追问：如何阻止 stale client 向被移除的旧 tail 读取，答案在第 010 段。[01:28:50-01:29:51]

## 概念、符号与推导

- **Tail handoff barrier**：`S2` 确定要停止 serving tail并交付 suffix；`S3` 应用到该 suffix 末端后才能服务 client。[01:20:16-01:21:21]
- **Propagation latency**：linear chain 的 update latency 随 chain depth 增加；课堂只作线性/对数的定性比较，没有性能公式。[01:21:43-01:23:52]
- **Per-chain linearizability**：同一 chain 内，即使有多个 objects/clients，老师确认 CR protocol 提供 linearizability。[01:24:21-01:27:04]
- **Cross-chain order**：不同 chains 上 operations 是否组合成一个保留 real-time 的 total order，老师未下结论，不能从 per-chain guarantee 自动推出。[01:24:42-01:27:01]
- **Update propagation invariant**：沿 `S1 -> S2 -> S3`，后继 history 是前驱 history 的 prefix，即 `Hist(S3) ⪯ Hist(S2) ⪯ Hist(S1)`。[01:27:35-01:28:17]
- **Configuration version/epoch**：课堂推测用编号识别 stale topology；具体 protocol 未完整给出。[01:29:20-01:29:40]

## 例子与课堂提示

- `base=100`、`delta=101..110` 把“copy + catch-up + switch”拆成可观察 barrier，解决“updates 一直来，何时能切换”的疑问。[01:20:19-01:21:21]
- 多 leaves read 的反例服务于 consistency：不同 leaves 没有一个共同 tail linearization point，可能返回不同进度的 state。[01:22:43-01:23:15]
- `S3 prefix S2 prefix S1` 是老师对白板图的直接解释；`i/j` 记号本身来自 paper 问答，容易因方向定义看反。[01:27:35-01:28:47]
- 易错点：老师没有断言跨 chains 一定不 linearizable；他明确拒绝当场承诺，需要把该问题保留为待研究项。[01:24:42-01:27:04]

## 本段掌握检查

1. **问：`S3` 何时可以开始作为新 tail 服务？**  
   **答：**Base copy 完成且已应用旧 tail 交付的 remaining suffix 后。[01:20:16-01:21:21]
2. **问：从多个 tree leaves 读取的直接风险是什么？**  
   **答：**Leaves 可能进度不同，client 可先看到新值再看到旧值，破坏 linearizable observation。[01:22:43-01:23:15]
3. **问：课堂对跨 chains linearizability 作了什么结论？**  
   **答：**没有确定结论；老师认为可能需要额外 machinery，并把 transaction 类问题留到后续。[01:24:42-01:27:04]
4. **问：Update propagation invariant 在三节点链中怎样表达？**  
   **答：**`Hist(S3) ⪯ Hist(S2) ⪯ Hist(S1)`，后继只拥有前驱 history 的 prefix。[01:27:35-01:28:17]
5. **问：Partition 下为什么需要 configuration version？**  
   **答：**让 servers 能拒绝来自旧 topology 的 commands，避免旧/新链同时驱动同一 successor。[01:28:54-01:29:40]

- `[需回听 01:23:19]` 关于 mean time between failures 与 3–5 replicas 的口述较松散；只保留“chain 通常较短、长度由 availability 目标决定”的课堂判断。

# 010. 旧配置客户端、跨对象事务与 ZLock 回看

> 时间范围：`01:29:52-01:34:17`  
> 证据：本段 transcript；本段没有匹配到课堂讲义页面。

## 本段在整讲中的作用

最后一段继续追问 reconfiguration 的最难边界：即使 servers 带 configuration version，partitioned old tail 仍可能被 stale client 当作 read endpoint。老师先给出版本号与 retry 的直觉方案，随后承认 proxy routing 可能正是 paper 规避该问题的原因。接着课堂把跨对象原子性明确归入 transactions，并在结束前回到本讲开头的 ZooKeeper lock，澄清分布式持锁者故障后 persistent intermediate state 为何与单机 Go lock 不同。[01:29:52-01:34:17]

## 教学展开

1. **Client 携带 configuration version。** Client 从 configuration manager 下载 topology 时也取得 version；每个 operation 带该 version。若 client 访问已知旧配置的 server，server 可拒绝并要求 retry，client 再回 configuration service 刷新状态。[01:29:52-01:30:30]
2. **指出 stale old-tail 难题。** 若旧 tail `S3` 与 coordinator partition，它不知道自己已被移除；某个 stale client 也不知道 version 已升级，仍向 `S3` 读。与此同时新链 `S1 -> S2` 已接受 writes，于是 `S3` 可能返回 stale value。单靠 client/server 都持有同一个旧 version 无法发现错误。[01:30:32-01:30:56]
3. **老师保留结论。** 对上述场景，老师说这“probably”是 paper 让请求通过 proxy 的原因。课堂没有给出完整 proxy protocol 或形式 proof，因此只能记录该设计动机，不把它提升为已证明解决方案。[01:30:56-01:31:02]
4. **跨对象原子性属于 transactions。** 学生提出 `a=1` 与 `b=2` 应一起可见或一起不可见。老师回答课程尚未讨论，将在数周后把 transactions 作为大主题；本讲 CR 的单对象/单链讨论不能自动提供该保证。[01:31:07-01:31:51]
5. **回到 ZLock intermediate state。** 学生确认 slide 上关于 lock holder failure 后 intermediate state 可见的论述主要针对 ZLocks。失败 leader 留下的状态不会自动消失，后继 leader 可以做 cleanup。[01:31:55-01:32:43]
6. **与 Go locks 比较。** 老师讨论的是同一 machine 上 goroutines/threads 的 Go mutex：若 machine crash，所有本地 threads 一起消失，其他本地执行不会在锁消失后继续观察进程内 intermediate state。ZooKeeper client 则可能修改共享/持久状态后失效，其他 clients 继续运行并看到这些 changes。[01:32:47-01:33:55]
7. **最后的 goroutine 追问。** 学生问 goroutine 是否可能独自 die while holding a lock，而程序其他部分继续；老师的课堂回答是 goroutine crash 会导致 application crash。本笔记保留这一现场说法并标记需回听/核对，不把它推广为 Go 语言的一般故障语义。[01:33:57-01:34:17]

## 概念、符号与推导

- **Stale client**：仍持旧 topology/version 的 client。[01:29:52-01:30:30]
- **Old-tail read hazard**：old tail 与 coordinator 隔离、client 也持旧 version 时，双方 version 一致却共同落后于新配置，故旧 tail 仍可能返回 stale data。[01:30:32-01:30:56]
- **Proxy（课堂推测）**：请求经一个能遵守 current configuration 的中介路由；本段未说明 proxy 自身如何获得/验证最新配置。[01:30:56-01:31:02]
- **Cross-object transaction**：多个 pieces of state 要么一起可见、要么都不可见；老师把它明确留给后续 transactions 课程。[01:31:07-01:31:51]
- **Persistent intermediate state**：ZLock holder 在共享服务中已创建/修改的状态不会随其 session lock 删除而自动回滚。[01:32:24-01:33:55]
- 本段无公式推导。

## 例子与课堂提示

- `S3` 被新配置移除但与 coordinator partition、stale client 仍向它读，是 configuration-version 方案的反例，说明 reconfiguration 不只要约束 servers，还要控制 client routing。[01:30:32-01:30:56]
- `a=1, b=2` 一起可见的例子把 per-object linearizability 与 multi-object atomicity/transactions 分开。[01:31:26-01:31:49]
- ZLock holder 创建额外 ZooKeeper files 后失效的例子说明 lock deletion 只移除 ephemeral lock，不回滚所有 persistent side effects。[01:33:31-01:33:55]
- 易错点：版本号能拒绝“新 server 看到旧 request”，却未必让被 partition 的 old server 发现自己过期。

## 本段掌握检查

1. **问：正常的 stale-version retry 流程是什么？**  
   **答：**Operation 携带 configuration version；server 拒绝旧 version，client 回 configuration service 重新下载 topology。[01:29:58-01:30:30]
2. **问：为什么该办法仍挡不住 partitioned old-tail read？**  
   **答：**Old tail 与 stale client 都只知道同一个旧 version，二者无法从彼此发现新配置已产生。[01:30:32-01:30:56]
3. **问：课堂如何处理这个 old-tail 难题？**  
   **答：**老师推测这可能解释 paper 的 proxy path，但没有给出完整 protocol/proof。[01:30:56-01:31:02]
4. **问：`a=1` 与 `b=2` 必须一起可见属于什么问题？**  
   **答：**跨对象 transaction/atomicity，老师明确留到后续课程。[01:31:07-01:31:51]
5. **问：ZLock holder failure 后为什么可能留下可见中间状态？**  
   **答：**删除 ephemeral lock 不会回滚它已写入共享持久服务的其他状态，其他 clients 仍会继续执行并观察它们。[01:32:24-01:33:55]
