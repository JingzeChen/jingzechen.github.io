## 核心模型与不变量

```text
无法区分 crash / partition
  -> 两副本发生 split-brain 或停止服务的两难
  -> 全局 majority 才能作决定
  -> 任意两个 majorities 相交
  -> 前一轮已保存的信息进入后一轮 election
  -> 每 term 至多一个 leader
  -> leader 为 commands 建立 log order
  -> majority replication 后才 commit
  -> committed entries 才交给 state machine
  -> tentative tails 可暂时不同并被 leader repair
  -> client timeout/retry 由 application 去重收尾
```

### Majority 与 fault tolerance

- 对固定成员数 `N`，majority 至少为 `floor(N/2)+1`。分母是全部配置 servers，不是 live servers。[00:12:53-00:13:20]
- `N=2f+1` 时，最多 `f` 台不可达后还剩 `f+1` 台，仍是 majority；超过该数量时安全地停止 progress。[00:12:04-00:12:49]
- 两个 majorities 必相交。课堂先用 test-and-set 前后操作说明，再映射到“log majority 与下次 election majority 有共同 server”。[00:09:57-00:10:52]

### Replicated state machine 路径

```text
client request
  -> leader KV handler
  -> leader Raft log append
  -> AppendEntries to followers
  -> majority successfully stores entry
  -> leader advances committed frontier
  -> applyCh delivers entry to KV state machine
  -> leader replies to client
  -> later AppendEntries tells followers the commit frontier
  -> followers apply in order
```

[00:19:56-00:30:44] [课件: l-raft.txt p.1]

### Election safety 与 liveness

- heartbeat 是不带新 entries 的 AppendEntries；follower 每次收到 leader traffic 就 reset election timer。[00:41:47-00:43:13]
- candidate 提高 `currentTerm`、vote for itself，并必须取得 majority；每台 server 每 term 只能投一票。[00:43:18-00:43:51]
- majority intersection 加 one vote per term 推出同一 term 至多一个 leader。split vote 的结果是 no leader，不是 two leaders。[00:45:51-00:47:13]
- randomized election timeout 降低 simultaneous candidacy 的概率，但不保证第一次成功；失败后进入更高 term 重试。[00:47:13-00:49:19]
- vote 与 term 必须跨 crash 持久化，否则 restart 后可能在同一 term 改投另一 candidate。[00:52:25-00:53:57]

### Log basics 与 commit 边界

- 每条 entry 包含 application `command`、leader `term` 和位置 `index`；相同 `(index, term)` 不会对应不同 commands。[00:38:17-00:39:57]
- log 同时承担 retransmission、global order、persistence 和 tentative storage；state machine database 不能取代这些职责。[00:35:08-00:37:10]
- follower ACK 先表示本地 append；leader 取得 majority 后才知道 committed；follower 要在后续 leader message 中获知 commit 再 apply。[00:27:56-00:30:44]
- logs 不要求每时每刻 identical。未 committed tails 可以分歧；在稳定 leader 与通信条件下，logs 最终收敛。[00:37:13-00:37:57]
- committed entries 约束 future leader，tentative higher-term tail 不自动获得保留保证。[01:27:33-01:28:41]

## Failure scenarios 与设计取舍

- **server crash vs network partition：** timeout 无法区分；Raft 选择只有 majority partition 可继续，从而以可能停止服务换取 strong consistency。[00:05:48-00:12:03]
- **旧 leader 仍在线：** 它可能暂时自认为 leader，但较低 term 无法让较高 term majority 接受新 entries，收到 higher-term reply 后 step down。[00:44:04-00:45:51]
- **leader 在通知 commit 前 crash：** apply 可能延迟，系统先 election 与 repair；不能把短期停顿误判为 safety failure。[00:31:53-00:34:40]
- **timeout 选择：** 太短导致不必要 elections，随机范围太窄易 split vote，太长又增加 failover downtime。[00:49:51-00:52:03]
- **client 在 apply 后、reply 前失联：** client 必须 retry，application 必须检测 duplicate 并缓存 prior response。[01:30:23-01:36:13]
- **跨地域部署：** correctness 条件不变，但 majority RPC latency 增加。[00:25:54-00:26:17]
- **吞吐扩展：** 课堂把 key space 分成多个 shards，每个 shard 使用独立 Raft group，而不是让一个 group 拥有多个 leaders。[00:24:25-00:25:18]
- **协议简洁性：** batching、利用 commutative operations 等可优化性能，但增加 complexity；本讲 Raft 基本不依赖这些优化。[01:36:19-01:37:55]

## 易错点与待核对项

- majority 以全部 configured servers 为分母，candidate/leader 自己也计入。[00:12:53-00:14:21]
- timeout 只产生 suspicion，不证明 leader crash；unnecessary election 可能 slow but safe。[00:41:23-00:43:13]
- follower ACK 不表示 follower 已 commit/apply；leader 与 followers 获得 commit knowledge 的时间不同。[00:29:34-00:30:44]
- 同一 index 不同 term 可以暂时存在；这不违反“相同 `(index, term)` 对应相同 command”。[00:39:39-00:39:57] [01:00:22-01:00:40]
- last log term 不是 current term，log freshness 也不等于 candidate 已获全体 votes。[01:19:39-01:26:28]
- uncommitted entry 可被覆盖；committed entry 与 tentative tail 的保留保证不同。[01:13:51-01:15:18] [01:27:33-01:28:41]
- duplicate detection 属于 key/value service，不是让 Raft repair algorithm 去删除“重复 log 格子”。[01:30:23-01:36:13]

## 本段在整讲中的作用

# 第 2 段：quorum 交集与 replicated state machine 目标

> 时间范围：`00:09:57-00:19:55`
>
> 证据范围：本段课堂转录；本段 prompt 未匹配独立课件页，但 `l-raft.txt p.1` 含同讲的 majority、quorum 历史与 Raft replicated state machine 提纲，仅用于交叉定位老师实际讲到的内容。[课件: l-raft.txt p.1]

## 本段在整讲中的作用

本段完成上一段尚未说完的 majority 论证：任何两个多数派都有交集，所以前一轮决定可以经交集中的 server 进入后一轮；network partition 下至多一个分区能继续，没有 majority 时宁可停机。老师随后把容错能力概括为 `2f+1`，澄清 majority 是相对于全部配置 server、且会计入自己，再用 Paxos、View-Stamped Replication 和 Raft 的历史把这个思想放入 consensus protocol 脉络。最后，他从“为什么需要共识”转向“Raft 给应用提供什么”，开始搭建 Lab 3 的 replicated key/value state machine。[00:09:57-00:19:55] [课件: l-raft.txt p.1]

## 教学展开

1. **完成 test-and-set 的 overlap 推导。** 前一项操作已写入 `S1`、`S2`。第二个 client 若也要取得 majority，无论选择哪两台，都至少会碰到 `S1` 或 `S2`，因此能观察到前一项操作，不能再次把旧状态当成未设置。[00:09:57-00:10:04] [课件: l-raft.txt p.1]
2. **把同一结构映射到 Raft。** 当 leader 把 operation 放进多数 server 的 logs，下一 term 的 leader 也必须从多数 server 获得 votes；两个多数派交叠，至少一个参与投票的 server 看过上一位 leader 的 operation。老师把这称为构造可同时处理 partition、server failure 与 strong consistency 的基础积木。[00:10:22-00:11:10] [课件: l-raft.txt p.1]
3. **从 partition 角度重述 safety。** network partition 后至多一个分区拥有全体 server 的 majority，因此至多一边可以继续。如果网络碎成多个小分区、没有任何一边取得 majority，系统就不能处理 client operation，只能等待网络恢复到至少一边拥有 majority。[00:11:13-00:12:03]
4. **从三台推广到 `2f+1`。** 三台只能在一台不可达时保留 majority；若两台不可达便不能前进。要容忍 `f` 个 failure，需要 `2f+1` 台 server，使剩余 `f+1` 台仍构成 majority。老师依次给出 `f=1 -> 3`、`f=2 -> 5`、`f=3 -> 7`。[00:12:04-00:12:52] [课件: l-raft.txt p.1]
5. **澄清 majority 的分母。** majority 按系统全部 server 计算，包含 up 与 down 的成员，不是只对当前活着或当前可见的节点重新取半数。这一点来自课前问题，老师特意强调。[00:12:53-00:13:20] [课件: l-raft.txt p.1]
6. **回答偶数 server 的问题。** 四台 server 的 majority 是 3。偶数配置并非非法：若能联系 4 台中的 3 台就可继续；但老师借 7 减到 6 的例子指出，6 台仍需 4 票，不能因一台已 down 就把 majority 改成当前 5 台中的 3 票。[00:13:20-00:13:55]
7. **回答是否计算自身。** server 自身属于全体成员。candidate 会先 vote for itself；leader 把 entry append 到自己的 log 时，这一份也计入复制该 entry 的 server 数量。[00:13:58-00:14:29] [课件: l-raft.txt p.1]
8. **给出 quorum protocol 的历史定位。** 老师说这种 majority 思路常称 quorum。Paxos 与 View-Stamped Replication（VR）约在 1990 年前后出现，早期需求不足，长期没有广泛采用；近十五年自动化 fault-tolerant system 的需求上升后，这类协议才大量投入实际使用。[00:14:32-00:16:16] [课件: l-raft.txt p.1]
9. **说明为何课程选择 Raft。** Raft 论文约在 2014 年发表，较完整、清楚地覆盖构建 replicated state machine 所需的多个方面，因此被课程选作论文、Lab 与课堂主协议。[00:16:16-00:17:03]
10. **从最终用途反推 Raft 的职责。** 老师开始画 Lab 3：每台 replica 上层是相同的 key/value server 和状态，下层嵌入一个 Raft library/Go package。client 发出 `Put`/`Get`，上层把 operation 交给 Raft；Raft 把它追加到 log 并与其他 replica 的 Raft 实例通信。只要各 key/value server 以相同顺序执行相同 operations，就应得到相同 key/value state。[00:17:11-00:19:55] [课件: l-raft.txt p.1]

## 模型、不变量与推导

- **majority 大小：** 对固定成员数 `N`，课堂使用的 majority 是严格超过一半，即至少 `floor(N/2)+1` 台。老师通过 `N=3 -> 2`、`N=4 -> 3`、`N=6 -> 4` 的例子建立这一点。[00:08:38-00:09:05] [00:13:23-00:13:47]
- **quorum intersection：** 两个集合若都严格大于 `N/2`，就不可能互不相交；否则其总成员数会超过 `N`。课堂把交集用于让后续 election 接触到前一 leader 留下的信息。[00:09:57-00:10:52] [课件: l-raft.txt p.1]
- **故障容忍关系：** `N=2f+1` 时，最多 `f` 台不可达后仍有 `f+1` 台；`f+1` 是 `2f+1` 的 majority。超过 `f` 台不可达时，本段承诺的是 no progress，而不是降低门槛。[00:12:04-00:12:49]
- **partition safety/liveness 边界：** 至多一个 partition 能拥有 majority，这是 safety 的来源；可能没有任何 partition 拥有 majority，此时牺牲 availability，等待通信恢复。[00:11:13-00:12:03]
- **replicated state machine 模型：** 每个 replica 运行同一上层 state machine；Raft 的 log 为这些 state machines 提供共同的 command order。相同初始状态加相同 operation sequence，得到相同最终状态。[00:17:18-00:19:55]

- **网络被切成多个无 majority 分区** [00:11:35-00:12:03]：用于提醒 consensus 不是在所有 partition 形态下都保持 availability；安全停机是协议设计的一部分。
- **3/5/7 台 server** [00:12:24-00:12:52]：用于把抽象容错参数 `f` 变成具体部署规模。

- **Lab 3 key/value server** [00:17:18-00:19:55]：用于把 consensus 从协议术语落到应用结构。Raft 是每个 replica 内的 library，不是取代 key/value state machine 的业务层。

- **误解：majority 是当前活着的 server 中过半。** 分母是系统全部成员；down server 不投票，但仍影响门槛。[00:12:53-00:13:20]

# 第 3 段：一条 client command 的 replicate、commit 与 apply 路径

> 时间范围：`00:19:56-00:29:54`
>
> 证据范围：本段课堂转录；`l-raft.txt p.1` 中的 state machine replication 时间图、`applyCh` 与 client retry 提纲用于核对课堂流程。[课件: l-raft.txt p.1]

## 本段在整讲中的作用

上一段只画出“每个 replica 都有 key/value layer 和 Raft layer”的静态结构，本段把一条 command 沿时间展开：client 找 leader，leader 追加 log entry，用 AppendEntries 复制到 followers，收到 majority 后把 entry 视为 committed，再经 `applyCh` 交给 state machine，最后回复 client。老师接着逐个插入 failure、retry、重复请求、leader discovery、sharding 与跨地域延迟，说明 Raft 只解决 replicated order，client 与 application 仍有自己的职责。段尾以三节点时间线精确说明：leader 加自身只需再收到一个 follower 的确认即可形成 majority；此时 leader 能 apply，但 followers 还不知道该 entry 已 committed。[00:19:56-00:29:54] [课件: l-raft.txt p.1]

## 教学展开

1. **指定 leader 作为 client 入口。** 三个 replica 中一个是 leader。client 向 leader 的 key/value server 发请求；上层把 operation append 到 leader 的 Raft log。[00:19:56-00:20:24]
2. **leader 驱动 log replication。** leader 的 Raft 与其他 replica 的 Raft libraries 通信，followers 把同一 operation append 到各自 logs 并向 leader 回 ACK。老师顺带说 log 与部分其他 state 位于 disk，使 server failure/restart 后仍可从已有 log 继续。[00:20:24-00:21:00]
3. **从 replicated 转到 committed，再转到 applied。** entry 复制到足够 server 后被视为 committed；各 log entry 有 index，committed operations 必须按 index 顺序交给 key/value server。state machine 执行 operation、更新 table；leader 的上层服务再向 client 回复。[00:21:03-00:22:14] [课件: l-raft.txt p.1]
4. **插入 leader failure 场景。** 旧 leader crash 后，系统选出 new leader。client 因收不到回复而 timeout，转向新 leader 并 retry；新 leader 把 retry operation 再次送进 Raft，重复正常复制流程。[00:22:17-00:23:11]
5. **由 retry 推出 duplicate detection。** 第一次 operation 可能已经成功，只是 reply 在 leader crash 前没有送达；client 无法知道，于是 retry 会让同一逻辑 operation 第二次进入 log、第二次到达 key/value server。老师把去重责任放在 Lab 3 的 service layer，本讲暂不展开实现。[00:23:12-00:24:19] [课件: l-raft.txt p.1]
6. **回答 leader 能接多少 clients。** 协议没有固定 client 数限制，但单 leader 的处理能力会成为性能瓶颈。扩展办法是把 key space 分成 shards，每个 shard 使用独立 Raft group，client 把请求发给对应 shard；这是 Lab 4 的方向。[00:24:25-00:25:18]
7. **回答 client 如何找到 new leader。** 课堂假设 client 知道系统全部 servers。它尝试某个 server；若该 server 不是 leader，课堂口述为把 client 引向实际 leader。这里记录老师的高层 client behavior，不补写 Lab client 的具体轮询代码。[00:25:23-00:25:51]
8. **回答 server 地理位置是否受限。** Raft 原理上不要求 replicas 地理接近；但距离越远，复制 entry 并取得足够回复的 latency 越高。[00:25:54-00:26:17]
9. **回答何时执行 log entry。** 老师先用高层定义说：Raft 判断足够 replicas 已接收、operation 不再需要回退后，才把它交给 key/value server。随后他改用一条 leader/follower 时间线讲得更精确。[00:26:23-00:27:15]
10. **画出三节点时间线。** client command 先追加到 leader log；leader 向 `F1`、`F2` 发送新 entry。假设 `F1` 收到并 append 后回复 ACK，leader 加自身已有两份，构成三台中的 majority，因此可把 entry 标为 committed。[00:27:18-00:28:26]
11. **用 `applyCh` 连接 Raft 与 service。** Raft goroutine 一旦决定 entry committed，就把 operation 通过单个 Go channel `applyCh` 发送给 key/value server，由上层 apply。[00:28:26-00:29:02] [课件: l-raft.txt p.1]
12. **解释为何两份足以承受下一次 leader election。** leader 与 `F1` 已有 entry；即使发生 failure 并选新 leader，下一次 majority 必然与这两台中的至少一台相交。老师据此说 leader 可以安全 commit。段尾提醒：leader 已经知道 committed，followers 当前只知道自己是否保存了 entry，尚不知道 majority 是否形成。[00:29:02-00:29:54]

## 模型、不变量与推导

- **请求路径：** `client -> leader KV -> leader Raft log -> AppendEntries -> follower logs -> majority ACK -> leader commit -> applyCh -> KV apply -> client reply`。[00:20:13-00:22:14] [00:27:18-00:29:02]
- **commit 门槛：** 三台 server 中，leader 自己的 log 算一份；收到一个 follower 的成功 ACK 后共有两份，形成 majority。无需等待所有 followers。[00:27:56-00:29:19]
- **apply 顺序不变量：** committed entries 依 log index 顺序交给每个 key/value state machine；相同 order 是 replicas 构造相同 state 的前提。[00:21:18-00:21:40]
- **持久性前提：** 老师在 overview 中说 log 等 state 存于 disk，server 重启后仍可取得最后一段 log。本段未展开哪些字段必须持久化以及写盘时机。[00:20:46-00:21:00]
- **client retry 模型：** timeout 只表示 client 没收到 reply，不表示 operation 未执行；因此 client 必须 retry，而 service 必须识别 duplicate。Raft log 自身不在本段替 application 消除重复语义。[00:22:47-00:24:06]
- **leader knowledge 与 follower knowledge 分离：** follower 的 ACK 证明本地 append；只有 leader 汇总 ACK 后知道 majority。followers 要靠后续消息获知 commit，具体机制在下一段讲。[00:29:34-00:29:54]

## 例子与课堂提示

- **leader crash 后 client retry** [00:22:17-00:24:06]：用于区分 consensus safety 与 end-to-end exactly-once illusion。Raft 可保持 log order，仍不能让 client 从丢失 reply 中判断第一次是否执行。
- **多个 Raft groups 的 sharding** [00:24:25-00:25:18]：用于说明所有请求经过一个 leader 的吞吐限制可在应用架构层拆分，而不是让同一 Raft group 同时拥有多个 leader。
- **跨地域部署** [00:25:54-00:26:17]：用于展示 correctness 与 performance 的边界。协议不禁止远距离，但多数派往返时延会进入请求 latency。
- **只收到 `F1` ACK** [00:27:56-00:29:29]：用于强调 majority 包含 leader 本身；`F2` 尚未回复也不阻止 commit。
- **课堂实现提示 `applyCh`** [00:28:37-00:29:02]：Raft 不直接修改 key/value table，而是向 service 交付 committed command。

## 常见误解与辨析

- **误解：entry 必须复制到所有三台才 committed。** 时间线明确只用 leader + 一个 follower 的两份形成 majority。[00:27:56-00:29:19]
- **误解：follower 回复 ACK 就表示它知道 entry 已 committed。** ACK 只证明本地 append；leader 才知道收到多少回复，followers 此时不知道全局门槛是否满足。[00:29:34-00:29:54]
- **误解：client timeout 表示 operation 一定失败。** 第一次可能已 apply，只是 reply 丢失或 leader 在回复前 crash；retry 因而可能制造 duplicate。[00:23:12-00:23:40]
- **误解：Raft library 负责业务去重。** 老师把 duplicate detection 明确留给 Lab 3 的 key/value service。[00:23:40-00:24:06]
- **误解：扩展 client 数量就是给同一 group 增加多个 leader。** 课堂方案是按 shard 建多个独立 Raft groups，每组仍有自己的 leader。[00:24:41-00:25:18]

# 第 4 段：commit 通知、log 的四项职责与 entry 标识

> 时间范围：`00:29:54-00:39:52`
>
> 证据范围：本段课堂转录；`l-raft.txt p.1` 中的 commit piggyback、log purposes 与 log convergence 提纲用于核对课堂顺序。[课件: l-raft.txt p.1]

## 本段在整讲中的作用

本段接续“leader 已知 committed、followers 尚未知”的悬点，说明后续 AppendEntries 同时携带新 entries 与 commit information，followers 得知后才 apply。连续的学生问题把 failure timing 推到极端：majority 已保存、leader 已或未通知 followers 时 crash，会延迟执行，但不会迫使已稳定保存的 committed entry 消失。老师由这些问题转入“为什么 state machine 已有数据库还要 log”，依次给出 retransmission、global order、persistence、tentative storage 四项职责，最后定义一条 log entry 的 `command`、`term`、`index`，并提出 `(index, term)` 唯一确定 entry content 的课堂不变量。[00:29:54-00:39:52] [课件: l-raft.txt p.1]

## 教学展开

1. **解释 followers 如何得知 commit。** 下一次 client request 到来时，leader append 新 entry 并发送新的 AppendEntries。该 RPC 一方面携带新 log entry，另一方面告诉 followers 此前哪些 entries 已 committed。followers 收到这项 commit information 后，才把那些 entries 交给本地 key/value state machine。[00:29:54-00:30:44] [课件: l-raft.txt p.1]
2. **回答 majority 中一台随后 crash 的问题。** 学生确认 follower ACK 是否只表示 entry 已在 log，并追问形成微弱 majority 后其中一台 crash 会怎样。老师回答 log 属于必须写入 stable storage 的 state；term 等其他 state 也需要稳定保存。因此 crash/restart 后 server 仍能从 disk 找到 entry。[00:30:50-00:31:48]
3. **讨论 leader 在通知全部 followers 前 crash。** 若 leader 已取得足够复制但尚未告诉其他 followers apply，entry 至少仍在一个 follower log 中。老师预告后续 election rules 会使拥有该信息的 follower 推动 entry 复制、apply；直接后果可以是 execution 被 delay，而不是已达成的顺序被另一批 client operation 越过。[00:31:53-00:34:29]
4. **区分 safety 与暂时停顿。** 学生坚持问“会不会 delay”。老师明确回答会；leader failure 后 clients 暂时不能继续，系统先重新选举，再由新 leader 修复 logs。正确性不要求 failure 后零延迟。[00:33:38-00:34:40]
5. **预告 follower 落后时的回退补发。** 新 leader 先尝试从自己 log 末尾发送；若 follower 不认可该末尾，leader 会逐步往前回退并发送更早 entries，极端情况下可重放完整 log。本段只给高层动作，未讲 Figure 2 的参数与冲突处理细节。[00:34:40-00:35:08]
6. **提出“已有 KV state，为什么还要 log”。** 老师指出 key/value server 已保存当前 database，看似重复维护 log；接下来用四个职责回答。[00:35:08-00:35:29]
7. **职责一：retransmission。** AppendEntries message 可能丢失，leader 必须保留尚需发送或重发的 entries，才能把同一 command 再发给落后 follower。[00:35:29-00:35:56]
8. **职责二：order。** 所有 commands 必须在所有 replicas 以同一顺序交付。log 的 index sequence 为这种全局执行 order 提供直接表示。[00:36:00-00:36:18]
9. **职责三：persistence。** follower 甚至全部 servers 都可能 crash 后重启；持久 log 使它们能恢复已知 history，并相互 retransmit 以追上进度。[00:36:21-00:36:37]
10. **职责四：tentative entries。** follower 收到 entry 时并不知道它最终是否会 committed；在 leader 宣告 commit 之前，需要一个位置保存 tentative command，log 就承担这个角色。[00:36:42-00:37:10]
11. **说明 logs 的暂时不一致与最终收敛。** 运行期间某些 logs 可以更长或含不同尾部；若系统继续正常运行且停止加入新 client requests，leader 会把它们修复为 identical logs。相同 log order 使各 state machines 最终按同一顺序 apply。[00:37:13-00:37:57] [课件: l-raft.txt p.1]
12. **拆开一条 log entry。** 每个位置包含 application `command`，例如带参数的 `Put`/`Get`；Raft 对 command 语义基本不作解释，只把它交给 application。entry 还包含创建它时的 leader `term`，以及其位置 `index`。[00:38:04-00:39:39]
13. **提出 `(index, term)` 标识不变量。** 一个 term 最多只有一个 leader，因此同一 leader 在给定 index 处只能 append 一个具体 command。老师据此说相同 `index` 和 `term` 的两条 entries 不会有不同 commands；完整句跨到下一段开头结束。[00:39:39-00:39:52]

## 模型、不变量与推导

- **两阶段 knowledge flow：** follower ACK 表示“我已持久 append”；leader 汇总 majority 后更新自己的 committed frontier；随后 AppendEntries 携带该 frontier，followers 才更新本地 commit knowledge 并 apply。[00:29:54-00:30:44] [00:30:50-00:31:34]
- **stable log 前提：** ACK 对 crash tolerance 有意义，依赖 entry 已写入 stable storage；否则形成 majority 后立即 crash 仍可能全部遗失。课堂还点名 term 等 state 也需 stable，但未在本段枚举完整字段。[00:31:19-00:31:48]
- **log 四职责：** `retransmission + order + persistence + tentative storage`。KV database 表示已执行后的 state，不能替代尚未 committed 的 command history，也不能单独给出跨 replica 的统一 order。[00:35:08-00:37:10]
- **最终收敛条件：** logs 不是时刻 identical；在 leader 能持续通信且不再加入新 workload 的条件下，它们才被修复到一致。protocol safety 只允许稳定 entries apply，不要求每个瞬间长度相同。[00:37:13-00:37:57]
- **entry 结构：** `entry = (index, term, command)`；`term` 是 append 该 entry 的 leader term，`index` 是 log 中位置，`command` 是上层 state machine operation。[00:38:17-00:39:42]
- **课堂不变量：** `(index, term)` 相同意味着 `command` 相同。老师的依据是一个 term 内至多一个 leader，且该 leader 在一个 index 上产生唯一内容。[00:39:00-00:39:52]

## 例子与课堂提示

- **commit information piggyback 在下一次 AppendEntries** [00:30:01-00:30:44]：用于说明 follower 为什么不会仅凭本地收到 entry 就执行，也说明没有新 command 时 heartbeat 仍可承载控制信息这一方向；本段未展开 heartbeat 格式。
- **leader 在 commit 通知前 crash** [00:31:55-00:34:40]：用于区分“eventually apply”与“立即 apply”。failure 可以延迟 service，但只要重配置成功，日志中的稳定信息可由后继 leader 继续传播。
- **完整 log replay 的极端 follower** [00:34:40-00:35:08]：用于说明 retransmission 不是只重发最后一条；落后范围可能很大。
- **KV table 与 log 并存** [00:35:10-00:37:10]：用于区分 materialized state 与 ordered command history。两者看似重复，承担的 failure/recovery 职责不同。
- **`Put`/`Get` 作为 opaque command** [00:38:29-00:38:43]：Raft 关心其位置和复制状态，不在本段解释业务含义。

## 常见误解与辨析

- **误解：follower 收到 entry 后应立刻执行。** 它此时不知道是否形成 majority，只能先把 entry 作为 tentative 内容保存。[00:29:54-00:30:44] [00:36:42-00:37:10]
- **误解：leader crash 前没通知 followers，就说明 entry 必须丢弃。** 结果可能只是延迟；拥有 entry 的 server 仍可参与后续 election 与 log repair。具体能否保留还受后续 leader 与日志状态影响，课堂后半 Figure 7 会继续区分。[00:31:55-00:34:29]
- **误解：state machine database 已含最终值，所以 log 多余。** database 不保存 tentative command、统一 command order 或可供 follower 重发的完整 history。[00:35:10-00:37:10]
- **误解：所有 server logs 始终完全相同。** 老师明确允许暂时不同长度和不同尾部；目标是修复后收敛，同时只 apply stable entries。[00:37:13-00:37:57]
- **误解：term 是 entry 到达 follower 的时间。** 它记录 append 该 entry 的 leader term，不随 entry 后续复制而改成 follower 当前时间或当前角色。[00:38:43-00:39:19]

# 第 5 段：terms、heartbeats 与 randomized leader election

> 时间范围：`00:39:52-00:49:51`
>
> 证据范围：本段课堂转录；`l-raft.txt p.1` 的 leader election 提纲用于核对 terms、majority voting、heartbeats、split vote 与 randomized timeout。[课件: l-raft.txt p.1]

## 本段在整讲中的作用

本段先补完上一段的 `(index, term)` 唯一性理由，并确认 uncommitted tail 可能被覆盖。随后老师把 Raft 拆成两个主要问题：为每个 term 选 leader，以及在 leader changes/failures 后使 logs identical；本段先处理 Lab 2A 的 election。老师按正常故障、旧 leader 回归、同时 candidacy 三个场景依次增加机制：heartbeat/election timeout 触发选举，term 与 majority 排除旧 leader，one vote per term 保证 election safety，randomized timeout 缓解 split vote、推动 liveness。段尾开始讨论 timeout 太短的代价。[00:39:52-00:49:51] [课件: l-raft.txt p.1]

## 教学展开

1. **补完 entry 唯一性。** 一个 term 只有一个 leader 负责 append，因此同一 `index`、同一 `term` 不会出现两个不同 commands。学生随即问 uncommitted entries 是否会被覆盖，老师答“可能”，并承诺稍后详细讨论。[00:39:52-00:40:09]
2. **把协议分成两大任务。** 一是为特定 term elect leader，二是在 failures 和 leader changes 下让各 logs 变成 identical。老师先讲 election，说明它直接对应 Lab 2A。[00:40:13-00:41:06] [课件: l-raft.txt p.1]
3. **从稳定 term 10 开始。** 三节点当前有一位 term 10 leader、两位 term 10 followers。若 leader crash 或与网络隔离，followers 因收不到 heartbeat 而开始 election。[00:41:09-00:41:47]
4. **定义 heartbeat。** leader 周期性发送 AppendEntries。client workload 活跃时，正常 AppendEntries 已持续表明 leader 存活；没有新 commands 时，leader 发送不带新 log entries 的 AppendEntries 作为 heartbeat，并带上自己的 log 末尾信息供 follower 检查。[00:41:47-00:42:40]
5. **定义 election timeout。** follower 维护 timer，每收到 heartbeat 或 AppendEntries 就 reset。若在 timeout 内一直收不到，timer 到期，follower 开始 election。[00:42:41-00:43:18]
6. **把 follower 变成 candidate。** 假设第一个 follower 先 timeout：它把 local current term 从 10 增为 11，vote for itself，并向另一 follower 与失联的旧 leader 请求 votes。旧 leader 不回复，另一 follower 投票；candidate 拿到自己加另一台共两票，成为 term 11 leader。[00:43:18-00:44:03]
7. **处理旧 leader 仍存活的场景。** 若 term 10 leader 只是处于 partition，网络恢复后它仍可能收到 client request 并尝试 AppendEntries。term 11 followers 会拒绝旧 term RPC，回复自己的较高 term。旧 leader 看见 `11 > 10` 后 step down，转为 follower。[00:44:04-00:45:27]
8. **解释为何没有 split brain。** term 10 旧 leader 无法从 term 11 majority 接受新的 AppendEntries，因此不能让新 client operation 达到 commit 条件。老师把这归因于 majority rule 与 term numbers 的组合。[00:45:27-00:45:51] [课件: l-raft.txt p.1]
9. **构造 split vote。** 两个 followers 若几乎同时 timeout，会各自进入同一新 term、vote for itself，再互发 RequestVote。由于每台 server 每 term 只能投一票，两者都拒绝对方，最终各一票、无人取得 majority。[00:45:51-00:47:13]
10. **说明失败 election 如何重试。** 无 heartbeat 的状态持续，下一次 timeout 触发更高 term 的新 election。若每次都同步 timeout，split vote 可能无限重复，系统没有 forward progress。[00:47:13-00:47:47]
11. **用 randomness 打破对称。** 每次 reset election timer 时，follower 都从一个区间重新随机选择 timeout。老师引用论文的 `150-300 ms` 例子：通常一台先 timeout，并有机会在下一台 timeout 前完成 election；新 leader 的 heartbeats 随后压制其他 candidacy。偶尔仍可能 split，但持续重试最终应成功。[00:47:47-00:49:19] [课件: l-raft.txt p.1]
12. **开始讨论 timeout 选择压力。** timeout 不能太短；若比 heartbeat interval 还短或只丢一个 message 就触发 election，虽不一定破坏 safety，却会造成不必要 election。本段在这项 tradeoff 解释中途结束。[00:49:20-00:49:51]

## 模型、不变量与推导

- **角色转换主线：** `follower --election timeout--> candidate --majority votes--> leader`；较高 term 的消息可使旧 leader/candidate退回 follower。课堂在本段通过场景建立三种 roles，没有给独立状态表。[00:42:41-00:45:20]
- **term 不变量：** 每次新 election 使用更高 term；一个 term 至多一位 leader，也可能因 split vote 没有 leader。[00:43:18-00:43:56] [00:46:44-00:47:30] [课件: l-raft.txt p.1]
- **election safety 推导：** candidate 必须取得 majority；每台 server 每 term 只能投一票。两个不同 candidates 不可能在同一 term 各取得 majority，因为两个 majorities 必相交，而交集 server 不能投两票。[00:43:28-00:43:51] [00:46:44-00:47:11]
- **failure detector 模型：** election timeout 只根据一段时间未收到 AppendEntries 作怀疑，不证明 leader 已 crash。因此可能发生 unnecessary election；课堂结论是可能慢，但 term/majority 机制保持 safe。[00:41:23-00:43:13] [课件: l-raft.txt p.1]
- **旧 leader 限制：** 较低 term leader 可以暂时仍自认为 leader，但无法让较高 term majority 接受 entries；收到较高 term reply 后必须 step down。[00:44:04-00:45:36]
- **randomized liveness：** 随机 timeout 不消除单次 split vote，只降低多个 candidates 同时启动的概率；失败后提高 term 再试。[00:47:13-00:49:14]

## 例子与课堂提示

- **term 10 到 term 11** [00:41:09-00:44:03]：用于串起 heartbeat、timeout、self-vote、RequestVote 和 majority 成为 leader 的完整正常路径。
- **partition 中的旧 leader** [00:44:04-00:45:51]：用于说明“两个 server 都自称 leader”不等于两个都能 commit。决定性标准是能否让 majority 接受当前 term 的 work。
- **两个 follower 同时参选** [00:45:51-00:47:47]：用于区分 safety 与 liveness。one vote per term 防止双 leader，却可能导致无人当选。
- **论文的随机区间** [00:47:47-00:49:19]：用于说明 randomness 是 network protocol 中打破 symmetry 的常见方法；区间具体数值不是本段推导出的常量。
- **空 AppendEntries heartbeat** [00:41:47-00:42:40]：即使没有 client command，leader 仍需主动维持 followers 对当前 leadership 的认知。

## 常见误解与辨析

- **误解：timeout 就证明 leader 已死。** timeout 只触发 election；旧 leader 可能仍活在 minority partition。[00:41:23-00:43:13] [00:44:04-00:44:30]
- **误解：旧 leader 还活着就必然形成 split brain。** 它可以短暂保留主观角色，但较低 term 不能从较高 term majority 获得接受，因而不能 commit 新 operation。[00:44:33-00:45:51]
- **误解：split vote 违反 election safety。** split vote 的结果是没有 leader，不是两个 leaders；它损害 progress，不损害 one-leader-per-term。[00:46:23-00:47:13]
- **误解：random timeout 保证第一次 election 成功。** 课堂明确允许一两次不走运的 split votes，只说重试后成功概率提高。[00:48:38-00:49:14]
- **误解：heartbeat 是独立于 AppendEntries 的另一种 RPC。** 老师说 heartbeat 采用普通 AppendEntries 的形式，只是不带新的 log entries。[00:42:11-00:42:27]

1. **问：follower 何时开始 election？**

2. **问：同一 term 为什么至多一位 leader？**

## 教学展开

1. **解释 timeout 不能太短。** election 期间 service 不可用、clients blocked，因此应避免不必要 election。timeout 至少要覆盖若干 heartbeat/RPC 往返，让暂时丢包有重试机会，而不是丢一个 heartbeat 就换 term。[00:49:51-00:50:40]

# 第 10 段：commit 边界、application 去重与性能取舍问答

> 时间范围：`01:31:58-01:39:22`
>
> 证据范围：仅本段课堂转录；本段为正式授课后的延伸问答。`l-raft.txt p.1` 仅可交叉定位 client retry/`applyCh` 高层流程，不作为本段未口述机制的补充。[课件: l-raft.txt p.1]

## 本段在整讲中的作用

本段用连续问答回查本讲最容易混淆的三个边界。第一，leader 必须先得到 majority append responses 才能推进 committed frontier；followers 是否 apply 取决于后来收到 leader 的 commit information，leader crash 时未稳定的 tails 可能继续也可能消失。第二，Raft 不负责把 client timeout 变成 exactly-once：新 leader 未必知道原 client，client 要 retry，key/value service 用 duplicate table 记 request 与 response。第三，Raft 选择清晰的 ordered replication，而不是课堂上枚举的 batching、commutativity 等性能优化；网络仍会丢 reply，所以 end-to-end progress 依赖 client resend。最后一个 transcript segment 在 `01:39:22.400` 结束。[01:31:58-01:39:22]

## 教学展开

1. **补完 duplicate 的触发条件。** 学生确认只有 client 未收到 response 才会 retry；老师同意，并说明 Lab 3 会实现这类处理。[01:31:58-01:32:06]
2. **学生重述 commit notification。** 其理解是 leader 自己决定 commit 后，借下一条 client command 的 AppendEntries 告诉 followers 先前 entries committed。老师说协议高层上是这种间接传播，但随即纠正学生把“leader 单方面 commit”放得太早。[01:32:13-01:32:44]
3. **强调 commit 前必须有 majority append responses。** leader 先把 command 放入 logs；在没有取得 majority responses 前，不能把它交给 key/value state machine。收到足够 follower replies 后，leader 才提高 committed index 并 apply。[01:32:44-01:33:29]
4. **澄清 follower ACK 与 follower commit 不同。** 学生说是否要等所有 followers 各自 commit；老师纠正：followers 在知道 leader 已 commit 后才 commit/apply。它们先前回复的是本地 append，不是自己已知全局 committed。[01:33:30-01:33:48]
5. **讨论 leader 在传播 commit 前 crash。** 若 entries 只作为 tentative 内容留在部分 logs，之后是否 committed 取决于 new leader 与 log situation；老师把这对应到刚讨论的 Figure 7 分歧。[01:33:48-01:34:13]
6. **讨论“majority accepted 后 leader crash”。** 学生追问某 entry 已被 majority 接受，是否可由另一 leader commit。老师口述 “can, also may not”，随后转入 client identity 问题；由于 “accepted/committed” 在问答中用词混杂，这一判断保留为需回听，不用 paper-only rule 替换。[01:34:16-01:34:50]
7. **new leader 不知道原 client 时如何完成交互。** follower/new leader 可能后来 apply 旧 operation，却不会凭那条旧 log entry 向原 client 主动发送 reply；原 client 因超时会 retry，同一 operation 再次进入 Raft，新 leader 在这一次活动请求上返回结果。[01:34:50-01:35:41]
8. **key/value service 记录 last response。** 对 `Get` 等需要返回值的 operation，service 在执行时保存 response；duplicate detection table 不只记“见过 request”，还保存可重发的结果。看到 duplicate 后，server 返回此前 response，而不是再次改变 state。[01:35:48-01:36:13]
9. **转入 batching 性能问题。** 学生认为 leader 可积累多个 entries 再发送 AppendEntries，从而 implicit batching。老师先说 Raft 没有采用这项优化、加入优化会增加 complexity；学生说明自己的 Lab 实现因等待而自然合并多项，老师承认可以出现这种发送行为。[01:36:19-01:37:24]
10. **扩大到 Raft 的性能边界。** 老师说存在许多 Raft 未做、其他系统会做的 optimizations，例如利用某些 operations 可交换、顺序不重要的性质。Raft 基本不做这些优化；对特定 use case，这种简单性可能完全够用。[01:37:28-01:37:55]
11. **回答 request 是否可能永远不执行。** 学生担心 tentative entry lost 意味着 application 不可用。老师从网络现实回答：即使 server 正确执行，response 也可能丢失，所以 client 本来就必须 resend/retry；不能把一次无回复当成完成或永久失败的可靠证明。[01:37:59-01:38:49]
12. **闭合 retry 与 duplicate table。** entry committed、执行后 server 构造 reply；duplicate table 保存该 response。client retry 时，service 能返回同一结果，避免重复改变业务状态。[01:38:49-01:39:09]

## 模型、不变量与推导

- **leader commit/apply 门槛：** `local append + successful replication on a majority -> advance committed frontier -> deliver to state machine`。不能把 leader 本地 append 当成 commit。[01:32:44-01:33:29]
- **follower state progression：** `append tentative -> ACK local storage -> later learn leader commit -> apply in order`。ACK 与 commit knowledge 是两种不同事件。[01:33:30-01:33:48]
- **committed frontier 单调性（课堂口述）：** 老师提到一个只增加的 committed/applied index variable，在收到 majority responses 后推进；字幕对变量名不可靠，因此本笔记不把它静默定名为 Figure 2 中某一字段。[01:33:21-01:33:29]
- **client/application 协议：** client timeout 后 retry；service 用 request identity 查 duplicate table，并保存 previous response，以便对重复请求返回同一结果。[01:34:50-01:36:13]
- **layering：** Raft 负责复制 ordered commands 与交付 committed entries；识别 client、缓存 reply、消除 logical duplicates 属于 key/value service。[01:34:50-01:36:13]
- **性能取舍：** batching 或利用 commutative operations 可提高吞吐，但增加协议/实现 complexity。课堂把 Raft 描述为未采用大量此类 optimizations 的清晰基线。[01:36:19-01:37:55]
- **liveness 假设边界：** 网络可丢 request/reply，所以 client 必须 retry；本段没有给出保证“每个 request 最终执行”的时间上界或 fairness 条件。[01:37:59-01:39:09]

## 例子与课堂提示

- **leader 在 commit notification 前 crash** [01:32:13-01:34:13]：用于再次分离 majority replication、leader knowledge、follower knowledge 与 application execution。
- **旧 operation 后来由 follower apply，但无人主动回原 client** [01:34:50-01:35:41]：用于说明 log entry 不等于仍活跃的 RPC connection；client retry 才建立新的 reply path。
- **`Get` response 缓存** [01:35:48-01:36:13]：用于说明 duplicate table 不只适用于有副作用的 `Put`，还要保留读请求原先构造的 response。
- **学生实现中的 implicit batching** [01:36:19-01:37:24]：用于讨论实现可能合并发送，但老师没有把它提升为本讲 Raft protocol 必须机制。
- **commutative operations** [01:37:28-01:37:49]：用于说明更高性能系统可能放宽全序约束做优化；本讲不展开算法。

## 常见误解与辨析

- **误解：leader 本地 append 后就可以执行。** 它必须先收到足以证明 majority replication 的 responses，才推进 committed frontier并交给 KV。[01:32:44-01:33:29]
- **误解：followers 的 ACK 表示它们已经 commit/apply。** ACK 先表示本地保存；followers 等 leader 的 commit information 后才 apply。[01:33:30-01:33:48]
- **误解：new leader 会根据旧 log entry 自动找到原 client 并回复。** log 中的 operation 可被 apply，但原 RPC 可能已断；client retry 才让当前 leader有可回复的请求。[01:34:50-01:35:41]
- **误解：duplicate table 只需要一个 boolean。** 对需要返回值的 request，service 还要保存 prior response，重试时返回它。[01:35:48-01:36:13]
- **误解：Raft 追求所有可用性能优化。** 老师明确把简洁与完整描述放在前面，称其基本不做 batching/commutativity 等一系列优化；这可能适合某些 use cases。[01:36:19-01:37:55]
