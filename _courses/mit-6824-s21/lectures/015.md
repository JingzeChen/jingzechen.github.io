## 老师的教学主线

1. **先定边界再谈速度（00:00:00-00:09:57）**：FaRM 是单数据中心 research prototype，目标是降低 server CPU cost；Spanner 则承担跨地域同步复制与光速延迟。
2. **移除持久存储瓶颈（00:09:57-00:19:57）**：数据驻留 RAM；相关断电由 UPS 提供时间，把 memory image 刷到 SSD；OID、object header 和 transaction API 为 OCC 做准备。
3. **移除网络软件路径开销（00:20:01-00:39:58）**：kernel bypass 把 NIC queues 映射到用户态，RDMA 让 remote NIC 直接访问 RAM；per-pair logs/queues 支撑日志追加和 RPC。
4. **从硬件约束推出 OCC（00:39:58-00:49:48）**：传统锁协议要求 server code，one-sided read 不允许这种主动参与；FaRM execute 时无锁读并缓存写，commit 时再验证。

6. **用并发例子检查正常路径（01:09:52-01:19:50）**：两个 transaction 同时递增 `x` 时，一个成功，另一个依据 lock bit 或 version mismatch abort；老师明确这只是直觉，不是完整证明。

## 核心概念与依赖关系

```text
单数据中心 + 数据全部驻留 aggregate RAM
  -> UPS + SSD 构成课堂语境下的 NVRAM
  -> 正常事务不等待磁盘

kernel bypass + RDMA NIC
  -> 用户态直接操作 NIC queues
  -> one-sided read 不运行远端 CPU
  -> write RDMA 可追加远端 log / message queue

one-sided read 无法主动执行远端锁协议
  -> Execute 时无锁读取 object + version，写入只在 TC 本地 buffer
  -> Commit 时 LOCK 写集合
  -> VALIDATE 只读集合

LOCK + VALIDATE 全通过
  -> concurrency-control decision to commit
  -> COMMIT-BACKUP 把 write data 放入所有相关 backup logs
  -> COMMIT-PRIMARY 保存 transaction-level commit decision
  -> 至少一个 primary NIC ACK 后向 application 返回 success
```

关键对象 header 为一个 64-bit word：最高位是 lock bit，低 63 位是 version。写集合的接受条件和只读集合的验证条件都可概括为：

$$
lock=0 \land v_{current}=v_{read}.
$$

区别是 LOCK 随后原子设置 lock bit，需要 primary CPU 参与；VALIDATE 只用 one-sided RDMA 重读 header，不设置读锁。

## 关键推导、例子与结论边界

- **FaRM vs. Spanner**：性能差距首先来自目标差异。FaRM 不提供跨数据中心副本，不能用其吞吐数字否定 Spanner 的地理容灾设计。
- **相关断电**：多个 DRAM 副本不自动等于持久化。UPS-backed flush 只在电源故障路径写 SSD；独立机器 crash 仍依赖复制与 recovery。
- **RDMA ACK**：只证明 bytes 已写入 remote NVRAM log，不证明 remote application thread 已处理记录或 object memory 已更新。
- **两个 transaction 同时 `x=x+1`**：先锁者成功；后者若撞上持锁期看到 lock bit，若稍后到达则看到新 version，都会 abort。Retry 后重新读 `x=1` 才可能得到 2。
- **Read-only fast path**：一轮读取加一轮 validation，都是 one-sided RDMA；“two one-sided RDMAs”指两轮协议阶段，不代表读多个对象也永远只有两个 packet。
- **严格串行化边界**：若 $end(T1)<start(T2)$，必须按 T1 后 T2 排序；执行区间重叠时可以选择满足读写结果的任一 serial order。
- **本文件不声称完成 recovery proof**：老师在 Part 1 只说明记录顺序、故障后最终 cleanup，以及恢复必须保留已公开的 committed transaction；完整 recovery protocol 和第二个 validation 例子明确留到 Thursday 的 Part 2。

## 易错点与待核对项

1. 不要把 CM/ZooKeeper 的配置锁与 object header 的 transaction lock 混为一谈。
2. 不要把 OID 当作固定机器物理地址；它是 `region number + offset`，region 到副本的映射可改变。
3. 不要把 write RDMA 当作“远端事务逻辑已经执行”；远端 CPU 可能尚未 poll log。
4. 不要把 LOCK/VALIDATE 通过的 decision point 与最终向 application 返回 success 的 commit point 混为一谈。
5. 不要把 version number 当作 TrueTime；它是 per-object logical version。
6. 课堂开场口述约 1.4 亿 TATP transactions/s，官方 notes 另写约 1 亿 transactions/s；应按论文 Figure 7 的具体配置复核，不能强行合成一个数。
7. Test-and-set 与 compare-and-swap 的具体实现措辞在口述/notes 中不同；可靠要求是对 version + lock 的检查/更新必须原子。
8. 高吞吐依赖低冲突、数据可装入总 RAM、单数据中心、RDMA/NVRAM hardware 和较低层对象 API；并非无条件性能保证。

## 综合复习问答

1. **为什么 FaRM 的 1.4 亿 transactions/s 不能直接与 Spanner 的 10-100 ms 事务时延做同条件排名？**  
   因为 FaRM 优化单数据中心的 CPU/内存路径，Spanner 付出跨地域同步复制和地理容灾成本；workload、指标和系统目标都不同。

2. **为什么 $f+1$ 个 RAM 副本仍需要 UPS + SSD？**  
   多副本只能在至少一个副本存活时恢复；全数据中心断电是相关故障，所有 DRAM 可同时丢失，UPS 让软件有时间把内存镜像写入 SSD。

3. **Kernel bypass 和 one-sided RDMA 分别消除哪类参与？**  
   Kernel bypass 移除每个 packet 的 kernel/system-call 路径；one-sided RDMA 进一步避免 destination CPU/OS 运行请求处理代码。

4. **为什么 FaRM 不在首次 read 时加锁？**  
   远端加锁需要 server-side RPC/等待，破坏 one-sided read fast path。FaRM 先无锁读，commit 时用 version/lock 检查冲突。

5. **LOCK 与 VALIDATE 的对象范围和成本有什么不同？**  
   LOCK 用于 write set，要写 primary log、由 primary 原子加锁并回复；VALIDATE 用于只读对象，仅 one-sided 重读 header。

6. **发现 lock bit 已设置后，为什么不等待？**  
   当前 new value 已基于旧输入计算；持锁者即将改变对象，等待不会修复过期计算，因此必须 abort/retry。

7. **为什么 COMMIT-BACKUP 必须先于 COMMIT-PRIMARY？**  
   在公开 commit decision 或允许值可见前，所有 write data 必须已进入相关 primary/backup logs，才能在允许的副本故障后完成 committed transaction。

8. **NIC ACK 与 server ACK 的语义差别是什么？**  
   NIC ACK 证明 remote memory write 完成；它不证明 server application 已处理 log entry。FaRM 正是利用前者缩短关键路径。

9. **两个 transaction 都读到 `x=0, version=0` 时，第二个在哪里 abort？**  
   在 LOCK phase：若第一个仍持锁，看到 lock bit；若第一个已完成并解锁，看到 current version 不再是 0。

10. **什么 workload 最能发挥 OCC + RDMA，什么 workload 会伤害它？**  
    大量 read-only、短、低冲突 transaction 最受益；高 write/read conflict 和长事务会增加 abort/retry。

11. **Strict serializability 何时强制真实时间顺序？**  
    只有 T1 已完成后 T2 才开始时，T2 必须排在 T1 后；重叠 transactions 可按满足结果的顺序串行化。

12. **Part 1 对 recovery 讲到了哪里？**  
    讲了 UPS/NVRAM、主备日志记录顺序、commit evidence 和未完成事务最终清理的结论；完整 reconfiguration/recovery algorithm 留到 Part 2/论文。

# 001｜从 Spanner 到 FaRM：目标、系统边界与总体结构

> 时间范围：00:00:00-00:09:57  
> 证据范围：课堂 transcript；官方课堂讲义 `l-farm.txt`。本文件只整理 **MIT 6.824 Spring 2021 官方 Lecture 15 视频 Part 1** 的本时间段。

## 本段在整讲中的作用

老师先用上一讲的 Spanner 作为参照，解释为什么还要研究另一套“事务 + 复制 + 分片”（transactions + replication + sharding）系统。核心不是宣称 FaRM 全面优于 Spanner，而是先分清目标：Spanner 为跨地域容灾付出网络时延，FaRM 把所有副本限制在单个数据中心，研究怎样借助内存与 RDMA 把服务器 CPU 开销压到极低。本段随后建立 FaRM 的机器、region、primary/backup 和 transaction coordinator（TC）模型，为后面讲 NVRAM、RDMA 与 optimistic concurrency control（OCC）提供共同底图。

## 教学展开

1. **先给出研究问题和性能量级。** 老师把 FaRM 定位为 2015 年的 research paper，研究的是 high-performance transactions，而不是一套已经广泛部署的通用数据库。课堂口述给出的抓眼数字是：90 台机器在 TATP benchmark 上达到约 1.4 亿 transactions/s（00:00:32-00:00:45）。这个数字的作用是提出问题：这种数量级是怎样得到的？

2. **用 Spanner 校准比较口径。** 老师回忆上一讲：Spanner 某些事务大约需要 10-100 ms，因此单条串行执行流大致是每秒 10-100 个事务（00:01:27-00:01:46）。随即强调，两者不能只看数字排名：Spanner 做跨世界范围的同步复制，FaRM 全部运行在单个 data center；前者面向不能容忍整个数据中心失效的应用，后者面向类似单数据中心内存数据库的工作负载（00:01:49 起）。因此，Spanner 的主要约束是地理距离和网络时延，FaRM 的研究对象则是 server CPU time。

3. **说明共同点与差异。** 两者都要解决分片、复制和分布式事务，也都包含 two-phase commit（2PC）式协调；区别在于 FaRM 是为探索 RDMA 潜力而建的 prototype。官方讲义还给出 simple transaction 约 58 microseconds、90 台机器约 1 亿 transactions/s 的论文数字。它们与老师开场口述的约 1.4 亿 transactions/s 口径不同，应理解为不同图表或 benchmark 数字，不能混写成同一个测量结果。

4. **建立分片和复制布局。** 数据被切成多个 region，每个 region 有一个 primary 和至少一个 backup。不同 region 的 primary/backup 分散到不同机器；例如一台机器可以保存 region 1 的 primary，同时保存 region 2 的 backup。这样单机崩溃时，相关 region 仍有副本可接管。一般化地说，每个 region 有 $f+1$ 个副本时，系统希望容忍 $f$ 个副本故障，但前提是每个 region 至少还有一个副本存活。

5. **引入配置与事务角色。** Configuration Manager（CM）配合 ZooKeeper 维护 `region -> [primary, backups]` 的映射。事务应用与存储服务运行在同一批机器上；执行事务的 application code 同时扮演 2PC transaction coordinator（TC），跨多个 region 协调读写与提交。

6. **列出高性能所依赖的条件。** 老师最后把性能来源拆开：用 90 台机器分片扩展；全部数据必须装入 aggregate RAM，避免磁盘读；借助 non-volatile RAM（NVRAM）避免正常路径上的磁盘写；用 one-sided RDMA 直接访问远端内存；让用户态快速访问 NIC；再设计一套适合这些硬件条件的事务与复制协议。这里的结论是：FaRM 的高吞吐不是单一算法技巧，而是系统边界、硬件假设和协议共同作用的结果。

## 概念、符号与推导

- **FaRM**：面向单数据中心、以内存和 RDMA 为基础的分布式事务研究原型。
- **Region**：数据分片与复制的基本单位；本段先把它理解为分布在机器内存中的一段数据。
- **Primary / backup**：region 的主副本与备份副本。primary 负责正常操作，backup 为故障接管保留副本。
- **Configuration Manager（CM）**：与 ZooKeeper 配合，记录并管理每个 region 当前的 primary/backup 位置。
- **Transaction Coordinator（TC）**：由运行事务的 application code 承担，协调跨 region 的提交协议。
- **容错副本数**：课堂采用 $f+1$ replicas tolerate $f$ failures 的表达；其必要条件是同一 region 的 $f+1$ 个副本不能全部丢失。
- **时延到吞吐的粗略换算**：若一条执行流每个事务耗时 $10\text{-}100\,\mathrm{ms}$，则其数量级约为 $10\text{-}100$ transactions/s。老师用它帮助理解 Spanner 与 FaRM 的量级差距，不是对整个 Spanner 集群总吞吐的严格推导。
- 本段无更复杂的公式推导。

## 例子与课堂提示

- **Spanner 对照**：老师用跨地域复制与单数据中心复制说明“性能数字必须连同系统目标一起读”。这避免了把 FaRM 的高吞吐误解为在相同容灾语义下免费获得的提升。

- **一机多角色**：一台机器可以同时承载某 region 的 primary 和另一个 region 的 backup，但同一 region 的 primary/backup 需要分开，才能处理单机 kernel panic、设备故障等失败。

# 002｜NVRAM、对象布局与事务 API

> 时间范围：00:09:57-00:19:57  
> 证据范围：本段 transcript；本段 prompt 未对齐课件页。属于 **MIT 6.824 Spring 2021 官方 Lecture 15 视频 Part 1**。

## 本段在整讲中的作用

上一段建立了单数据中心内的 region 主备布局，本段先补上该布局面对的两个问题：谁记录 region 到副本的映射，以及全数据中心断电时 RAM 中的数据怎样保存。老师随后下沉到 object header、OID 和 transaction API，把硬件/复制假设连接到后面 OCC 所需的 version number 与 lock bit。结尾从“已移除稳定存储 I/O 瓶颈”过渡到“继续压低 CPU 和网络成本”。

## 教学展开

1. **完成 primary/backup 与配置管理说明。** 不同机器保存同一 region 的 primary 和 backup，可处理 kernel panic、设备故障等单机失败。Configuration Manager（CM）与 ZooKeeper 共同维护每个 region 到 primary/backups 的映射（00:09:57-00:11:05）。ZooKeeper 管的是配置与成员关系，不是后面每个对象的事务锁。

2. **提出相关故障（correlated failure）。** 主备复制能处理一台机器失效，却不能自动处理整个 data center 同时断电：DRAM 本身断电即失去内容，即使数据在多台机器 RAM 中也可能一起消失（00:11:10-00:11:34）。这说明“多副本”只有在故障不完全相关时才能替代持久介质。

3. **用 UPS + SSD 构造 NVRAM。** 每台机器/机架有 uninterruptible power supply（UPS）。全局断电时，电池让机器继续运行一小段时间；FaRM 停止事务处理，把 regions、transaction state 和 logs 的内存内容刷到 SSD，再关机。数据中心恢复后，从 SSD 载入 memory image（00:11:36-00:12:45）。正常事务路径不写 SSD，SSD 只处理这种相关断电。

4. **定义 region 与 OID。** Region 可视为约 2 GB 的 byte array，对象位于其中。Object identifier（OID）由 `region number + offset/address within region` 组成（00:13:03-00:13:49）。Region 可以搬到别的机器，因此 OID 不是某台机器固定的物理地址；CM 先把 region number 解析到当前副本，再在 region 内使用 offset。

5. **定义对象 header。** 每个对象有一个 64-bit metadata word：低 63 位是 version number，最高位是 lock bit（00:13:49-00:14:28）。Version number 将检测对象自事务读取后是否被修改；lock bit 将表示另一个事务是否正在提交对该对象的写入。

6. **展示简化 transaction API。** 应用先 begin transaction，以 OID 调用 read；在本地修改对象字段，再调用 write 登记更新，最后 `txCommit()`。一次事务可跨多个 region 操作多个对象，因此提交要采用类似 2PC 的跨分片协议。OCC 发现冲突时事务 abort，应用通常等待一段随机时间后 retry（00:14:34-00:16:15）。

7. **澄清“全局名字”而非“全局地址空间”。** 学生询问 OID 是否是机器地址。老师澄清：每台机器仍有自己的地址空间；对象具有全局 OID，region 可移动，OID 中保存 region number 与 offset。FaRM 的更根本设计是 in-memory database：DRAM 足够便宜，所有数据常驻内存，事务不必访问持久存储（00:16:30-00:18:22）。

8. **转入网络路径。** 到这里，正常读写已不访问 SSD，storage device 不再是瓶颈。下一目标是降低 CPU utilization 和网络开销，老师引出第一个技术 kernel bypass，并开始画用户态 FaRM、Windows OS 与 NIC driver 的关系（00:18:28-00:19:57）。

## 概念、符号与推导

- **相关故障（correlated failure）**：同一原因同时影响多个副本，例如整个数据中心断电。它破坏“机器故障彼此独立”的直觉。
- **NVRAM（non-volatile RAM）**：本课语境中不是 DRAM 天生不挥发，而是 UPS 提供关机窗口，软件把 RAM image 写入 SSD，从而在电源故障后恢复。
- **OID**：$\langle region\ number, offset\rangle$。Region number 经配置映射找到 primary/backups，offset 定位该 region 内对象。
- **Object header**：$64\text{-bit}=1\text{-bit lock flag}+63\text{-bit version}$。
- **事务接口链**：`begin -> read(oid) -> local modify -> write(oid, value) -> commit/abort`。
- 本段无公式推导；上述位宽和 OID 是数据结构定义。

## 例子与课堂提示

- **全数据中心断电**：用于说明把同一数据复制到多台 DRAM 仍不等于持久化；共同电源是 shared fate。
- **Region 搬迁**：用于纠正 OID 等于机器地址的误解。对象名字稳定，物理承载位置由配置映射变化。
- **对象加一**：老师用读对象、字段加一、write、commit 展示 API；这个简单例子稍后会成为两个并发事务争用同一对象的串行化测试。
- **随机退避后重试**：OCC 的 abort 是预期控制流，不是系统异常；但冲突越高，重试成本越大。

# 003｜Kernel Bypass 与 One-sided RDMA

> 时间范围：00:20:01-00:29:59  
> 证据范围：本段 transcript；本段 prompt 未对齐课件页。属于 **MIT 6.824 Spring 2021 官方 Lecture 15 视频 Part 1**。

## 本段在整讲中的作用

上一段已把磁盘从正常事务路径移除，本段处理剩余瓶颈中的网络和 CPU。老师先解释传统 OS/TCP 路径为何贵，再依次介绍 kernel bypass 与 RDMA，最终得到 FaRM 后续协议的关键原语：用户态直接驱动 NIC，以及不运行远端 CPU 代码就读取远端对象的 one-sided RDMA。

## 教学展开

1. **从传统路径的开销出发。** 通常 application 通过 system call 请求 kernel 发送 packet；路径经过 OS、TCP/network stack 和 NIC driver。进入内核、运行协议栈和处理中断都消耗 CPU，因此短消息 RPC 的瓶颈常不是线速，而是 per-packet CPU cost（00:20:01-00:20:48）。

2. **定义 kernel bypass。** OS 与支持该功能的 NIC 在 setup 时合作，把 NIC 的 send queue/receive queue 映射到 application address space。此后用户态进程可直接在队列中写 command/packet 或读取完成状态，不必为每个操作调用内核（00:20:48-00:21:42）。OS 没有彻底消失：它仍负责初始授权、映射与资源隔离。

3. **用 polling 代替 interrupt。** FaRM 还避免 packet arrival interrupt。用户态线程持续检查 receive queue 的 flag/entry；NIC 放入 packet 后改变相应状态，线程发现后处理。代价是占用一个 polling thread，因此 FaRM 的线程会在运行 application code 与 poll NIC 之间切换（00:21:46-00:22:47）。老师提到 DPDK 作为 kernel bypass 已相当标准化的例子。

4. **引入 RDMA。** Remote Direct Memory Access 要求两端 NIC 支持协议。发送方把带有 read/write instruction 和 remote address 的 RDMA packet 放入 send queue；目标 NIC 解析它，直接访问目标 RAM（00:23:17-00:25:49）。

5. **解释 one-sided RDMA read。** 以读取 region 中对象 `o` 为例，source application 指定目标地址；destination NIC 从 RAM 取值并封装 response，整个过程不 interrupt 目标 OS，也不在目标 CPU 上运行 application/server code。响应到达 source receive queue，source 的 polling thread 看到结果（00:25:54-00:26:53）。“One-sided”强调只有发起端软件主动参与。

6. **回答 polling 与 NIC 能力问题。** Receive queue 的内存状态指示 packet 是否到达，专用线程不断读取它。普通 NIC 不一定支持此模式；NIC 需要多个 send/receive queue，把某些 queue pair 分配给特定 application，同时还要实现 RDMA。队列数量有限，课堂举例约 16 或 32 个（00:27:02-00:29:04）。

7. **由 read 转向 write。** Write RDMA 与 read 类似：sender 指示目标地址和 bytes，destination NIC 直接写内存。老师在片段结尾预告 FaRM 主要把 write RDMA 用于两类远端结构，其中第一类是 transaction log，具体在下一段展开（00:29:07-00:29:59）。

## 概念、符号与推导

- **Kernel bypass**：数据平面在 setup 后由 user-level application 直接操作 NIC queues，避免逐包 system call 与 kernel network stack。
- **Polling**：CPU thread 主动反复读取 receive queue 状态；节省 interrupt/context transition，但持续占用 CPU 时间。
- **RDMA**：NIC 执行远端内存读写的网络机制。
- **One-sided RDMA read**：source software 发起，destination NIC 完成 RAM access，destination CPU/OS 不处理该请求。
- **Queue pair**：分配给 application 的 send/receive queues；是 kernel bypass 的有限硬件资源。
- 本段无公式推导。

## 例子与课堂提示

- **读取 region 中对象 `o`**：把抽象的 remote memory access 落到数据库对象，说明后面 `txRead(oid)` 为什么可以不调用目标 server code。
- **Polling flag 从 0 变 1**：帮助理解“没有 interrupt”并非 application 自动知道消息到达，而是线程主动观察共享队列状态。
- **DPDK**：说明 kernel bypass 并非 FaRM 独有，但 FaRM 将它与 RDMA、事务协议组合。
- **有限 queue 数量**：提醒 kernel bypass 依赖特定 NIC 资源，不能假定每个 OS process 都无限拥有独立队列。

**参考答案：**

# 004｜RDMA 日志、消息队列与事务协议矛盾

> 时间范围：00:30:00-00:39:58  
> 证据范围：本段 transcript；本段 prompt 未对齐课件页。属于 **MIT 6.824 Spring 2021 官方 Lecture 15 视频 Part 1**。

## 本段在整讲中的作用

本段把 RDMA 从硬件读写原语提升为 FaRM 的通信基础设施：write RDMA 追加 transaction log，也可向 message queue 投递 RPC。老师随后指出论文真正要解决的矛盾：传统 transaction/2PC 协议要求 server 主动检查锁、等待和验证，而 one-sided RDMA 的价值恰恰是绕开 server CPU。这个矛盾直接引出下一段的 OCC。

## 教学展开

1. **Write RDMA 追加远端 log。** 每个 sender-receiver pair 有独立 incoming log。Sender 知道该 log 的 begin/end，可用 write RDMA 把 LOCK、COMMIT 等 transaction records 写到指定位置；destination NIC 完成内存写入（00:30:00-00:30:40）。独立 log 避免多个 sender 争写同一 append position。

2. **Write RDMA 构造 message-based RPC。** 每对机器另有 message queue。Sender 用 write RDMA 把 request 写入 remote queue；destination thread 轮询队列，看到消息后运行 server-side operation，再用 write RDMA 把 response 放回 sender queue。相比普通 NIC 上的标准 RPC，这条路径绕过传统 kernel network stack（00:30:40-00:31:54）。

3. **说明连接建立和访问控制。** 学生担心 remote NIC 可写任意 application memory。老师回答：RDMA 操作前要 negotiation/setup，建立 connection-oriented、reliable、ordered channel；OS 与两端在 setup 时进行 security/access-control checks，限定允许访问的 memory region（00:31:56-00:32:53）。因此 fast path 无软件介入不等于没有保护边界。

4. **讨论全连接规模。** 每对机器需要连接，形成 $O(n^2)$ 个 RDMA connections；老师指出类似部署也可能有 $O(n^2)$ 个 TCP connections，因此这不是 RDMA 独有差异（00:32:53-00:33:12）。

5. **完成 server memory layout。** FaRM process 的 RAM 不只有 object regions，还包括 per-peer message queues 与 logs。NIC 与 memory subsystem 协作，并在 setup 时由 OS 建立硬件级访问关系；课堂指出 NIC 可原子读取/写入 cache line（00:33:18-00:34:41）。

6. **解释 write completion acknowledgement。** Write RDMA 把 network bytes 写到指定 remote address，remote CPU 不参与。Receiver NIC 可返回 hardware acknowledgment（ACK），证明该 write RDMA 已执行；这个 ACK 稍后将成为 commit protocol 判断记录已进入 NVRAM log 的关键证据（00:34:44-00:36:17）。ACK 不等价于 destination application 已处理 log entry。

7. **量化动机。** 老师给出 one-sided RDMA 约 5 microseconds 的 latency，并强调它远快于 disk I/O，足以带来极高操作率（00:36:25-00:37:17）。具体 packets/s 的口述有转写歧义，可靠结论是低微秒级远端访问。

8. **提出论文核心挑战。** 过去的 2PC/transaction protocols 要 server 取得锁、等待锁释放或运行 validation；这要求目标 CPU 执行代码。RDMA 本身不能替应用任意运行 server code。因此 FaRM 要重新组合 one-sided RDMA、write RDMA RPC 和有限 server participation，在保持事务语义的同时尽量减少远端 CPU 工作（00:37:19-00:39:58）。

## 概念、符号与推导

- **Per-pair incoming log**：每个 sender-receiver pair 独立的 NVRAM 日志区域，sender 可管理自己的 append offset。
- **Per-pair message queue**：用 write RDMA 投递请求/响应，receiver software 通过 polling 执行 RPC handler。
- **RDMA ACK**：receiver NIC 确认远端内存写已经完成；不表示 receiver application 已消费或应用该记录。
- **连接规模**：$n$ 台机器两两建立有向通信关系时，连接数量为 $O(n^2)$。
- **两类 RDMA 路径**：one-sided read 不运行 destination code；message-queue RPC 虽用 write RDMA 传输，仍要 destination thread 处理。
- 本段无其他公式推导。

## 例子与课堂提示

- **Log 与 message queue 分离**：前者保存事务证据，后者承载要求对端执行动作的 RPC；两者都在 RAM，却不能混同语义。
- **ACK 先于应用处理**：这是理解后续 COMMIT-BACKUP/COMMIT-PRIMARY 的关键。协议可只等 NIC ACK 来缩短 critical path，但恢复时必须能解释尚未被 server thread 应用的日志。
- **访问控制问题**：老师承认“NIC 直接碰内存”需要严格 setup；性能优化没有取消 OS 的隔离职责，只把它移出每次操作的 fast path。

## 本段掌握检查

1. 为什么每个 sender-receiver pair 使用独立 log？
2. FaRM 如何用 write RDMA 实现 RPC？
3. RDMA fast path 的访问权限在什么时候建立？
4. Hardware ACK 能证明什么，不能证明什么？
5. 为什么传统 2PC 不可直接全部替换成 one-sided RDMA？

**参考答案：**

1. Sender 可独立管理 append position，避免多个 sender 争用同一日志尾部。
2. 请求写入 remote message queue，目标 polling thread 处理，再把响应写回 source queue。
3. Connection setup/negotiation 时，由 OS、application 和 NIC 协作限定 memory region。
4. 能证明 remote memory write 已完成；不能证明 application 已读取并执行记录。
5. 锁检查、等待和 validation 等步骤需要运行 server-side code，而 one-sided RDMA 只读写内存。

## 教学展开

1. **从 RDMA 约束推出 OCC。** 如果 read 先取锁，server 必须运行代码，客户端还可能等待锁，这与 one-sided RDMA 不匹配。FaRM 因此允许 transaction 在不加锁的情况下读取并使用对象（00:40:02-00:41:23）。这是“optimistic”：先假定没有冲突。

2. **用 version number 延迟发现冲突。** `txRead` 同时返回 object 和 version。Coordinator 记住版本；commit 时重新 validation。若 version 自最初读取后增加，说明有其他 transaction 修改过对象，当前事务 abort；若一致，才可能继续 commit（00:41:24-00:42:48）。Abort 后通常随机等待再 retry。

3. **对比 optimistic 与 pessimistic。** OCC 是“先做，发现不允许再道歉并 abort”；pessimistic concurrency control 是“先申请许可/锁，再做操作”，成功拿锁后 commit 更有保证（00:43:08-00:44:02）。OCC 的收益是 read fast path 不改变 server state；代价是冲突到后期才暴露，已做工作可能浪费。

## 概念、符号与推导

- **Read set / write set**：本段未直接给出符号，但 Figure 4 区分“只读对象”和“将写对象”；前者随后 validation，后者进入 locking。

- **正确性目标**：strict serializability；本段只提出目标，尚未完成论证。

# 006｜LOCK 与 VALIDATE：写集合加锁、读集合复核

> 时间范围：00:49:57-00:59:54  
> 证据范围：本段 transcript；本段 prompt 未对齐课件页。属于 **MIT 6.824 Spring 2021 官方 Lecture 15 视频 Part 1**。

## 本段在整讲中的作用

上一段只列出 Figure 4 的阶段，本段逐步展开最关键的 concurrency-control 部分。老师先说明写集合怎样通过 log-driven RPC 在 primary 上取得对象锁，再解释为什么只读集合不走同样的昂贵路径，而用 one-sided RDMA 做 VALIDATE。至此，FaRM 把需要 server participation 的工作限制在写对象，把无锁远端读取的优势保留给读对象。

## 教学展开

1. **区分图中的两类箭头。** Execute phase 的虚线表示 one-sided RDMA read：对象直接从 remote memory 取回 TC 本地。Commit phase 的实线表示 write RDMA；LOCK 请求先作为 record 追加到每个相关 primary 的 incoming log（00:49:57-00:50:49）。

2. **构造 LOCK record。** 对每个待写对象，record 至少含 transaction id、OID、execute 时读到的 version number 和本地计算出的 new value。TC 用 write RDMA 把它追加到 P1/P2 的日志（00:50:49-00:51:40）。把 new value 一并记录，既传递锁请求，也为后面的提交/恢复留下更新内容。

3. **Primary 主动处理日志。** Primary 上的 thread poll incoming logs，看到 LOCK record 后查找对象 header。它必须同时检查：lock bit 是否为 0，以及当前 version 是否仍等于 record 中的 `v_read`；符合时用 atomic test-and-set / compare-and-swap 式操作设置 lock bit，再通过 coordinator 的 message queue 回复成功（00:51:43-00:53:19）。老师口述这一小段先突出 lock bit，结合前后文可确认 version check 也是 LOCK 成功条件。

4. **失败不等待，直接 abort。** 如果对象已锁，try-lock 失败，primary 回复“no”，TC abort 整个 transaction（00:53:26-00:54:05）。这不是 ZooKeeper lock：它是 object header 内的 in-memory transaction lock；ZooKeeper 只负责 region 配置（00:54:13-00:54:56）。

5. **解释为何不能等待锁。** Transaction 已基于旧 version 在本地计算 new value。发现对象被另一个 transaction 锁住，意味着它正要变化；即使等待锁释放，原来的计算输入也已不再可信，继续提交会破坏 serializability，所以必须 abort 并从新值重试（00:55:46-00:56:38）。

6. **定位写侧 serialization point。** 当 TC 成功取得所有待写对象的 locks 时，别的 transaction 不能同时修改这些对象。老师称其为 write part 的 serialization point（00:56:39-00:57:02）；但包含只读依赖的完整 transaction 还必须通过接下来的 validation，不能在这里就返回 commit。

7. **为只读对象选择更便宜的路径。** 若 read-only objects 也走 LOCK，需要 write RDMA request、primary CPU 处理和 write RDMA reply，等于一次完整 RPC。FaRM 改用 VALIDATE：TC 对每个“读但不写”的对象做一次 one-sided RDMA，重取 64-bit header，不需要 destination server code（00:57:07-00:58:47）。

8. **执行 validation。** TC 检查当前 lock bit 和 version：若已锁，说明并发 transaction 正在修改，abort；若 version 与最初读取不同，说明已经被修改，abort；只有未锁且版本相同才通过（00:58:52-00:59:35）。到所有 write locks 已拿到且所有 read-only objects 已验证时，完整 transaction 才有可接受的 serialization point，并准备进入复制/提交阶段。

## 概念、符号与推导

- **LOCK record**：`<txid, oid, v_read, new_value>`；经 write RDMA 进入 primary NVRAM log。
- **LOCK 成功条件**：$lock=0 \land v_{current}=v_{read}$，随后原子设置 $lock\leftarrow1$。
- **VALIDATE 成功条件**：对只读对象，$lock=0 \land v_{current}=v_{read}$。
- **写集合（write set）**：execute 中读过且准备写入的对象；在 primary 上主动加锁。
- **只读集合（read-only portion of read set）**：被事务读取但不修改的对象；只用 one-sided RDMA 重读 header。
- **Abort 传播**：任一 LOCK reply 为 no，或任一 VALIDATE 失败，整个 transaction abort；已取得的锁随后需要由 abort/恢复路径清理。
- **原子性要求**：lock check、version check 和 lock set 必须作为不可竞争的更新完成，否则两个 primary threads 可能都认为自己拿到同一对象锁。

## 例子与课堂提示

- **锁不是 ZooKeeper 锁**：老师专门纠正这一点。Configuration lock/membership 与 per-object transaction lock 的生命周期和作用完全不同。
- **为何 abort 而非 block**：关键不是追求低延迟，而是计算已经基于旧输入。等待只能获得锁，不能让旧计算自动变正确。
- **Primary 故障后的锁**：老师在 00:54:56 只预告 reconfiguration/recovery 最终会清理未完成 transaction；完整 recovery protocol 留给后续内容，本段不能据此补写状态机。
- **Validation 是无锁检查**：它不设置 read lock，因此快；正确性依赖它能看见并发 writer 的 lock bit 或更新后的 version。

# 007｜COMMIT-BACKUP、COMMIT-PRIMARY 与持久提交证据

> 时间范围：00:59:55-01:09:52  
> 证据范围：本段 transcript；本段 prompt 未对齐课件页。属于 **MIT 6.824 Spring 2021 官方 Lecture 15 视频 Part 1**。

## 本段在整讲中的作用

LOCK + VALIDATE 已决定 transaction 在并发控制上可以提交，但此时 new values 只存在 coordinator 与 primaries 的日志，backups 尚无副本。本段解释 Figure 4 后两步怎样把提交变成可容错事实，并严格区分三个时刻：通过验证并决定进入 commit、更新内容已覆盖所有 primary/backup logs、至少一个 primary log 中的 COMMIT-PRIMARY 获 NIC ACK 后 transaction 真正向 application 报成功。

## 教学展开

1. **从 validation 结果进入提交决定。** 所有 write locks 已取得、所有 read-only versions 已验证后，TC 决定“go commit”（00:59:55-01:00:34）。老师把这里称为 commit 开始/decision point；它还不是 application 可观察的最终 commit point，因为 fault tolerance 所需记录尚未完成。

2. **指出副本缺口。** 此前 LOCK 只联系待写对象的 primaries，没有联系 backups。若系统要用 $f+1$ replicas 容忍 $f$ failures，commit 后的写不能只留在 primary。课堂 Figure 4 示例是一主一备，因此目标是容忍一个相关 shard replica failure（01:00:44-01:01:17）。

3. **执行 COMMIT-BACKUP。** TC 向每个相关 backup 的 log 追加 COMMIT-BACKUP record，其中包含与 LOCK record 相应的 transaction id、OID、读取 version 和 new value。传输使用 write RDMA（01:01:17-01:02:10）。Backup CPU 此刻不必处理记录。

4. **只等待 NIC ACK。** Receiver NIC 完成远端日志写后返回 ACK。TC 收齐这些 ACK 时，知道每个待写对象的内容已经在其 primary log 和 backup log 中；即使 primary 或 backup 任一方失效，另一方仍有应用 write 的信息（01:02:10-01:03:09）。这里的“在 log 中”不等于 object memory 已更新。

5. **写 COMMIT-PRIMARY。** TC 接着向 primaries 的 logs 追加只需标识 transaction id 的 commit record。仍使用 write RDMA，不触发 interrupt，也不等待 primary application thread 执行；NIC ACK 表示 record 已安全进入 primary NVRAM log（01:03:14-01:04:23）。

6. **确定真实 commit point。** 只要一个 primary 的 NIC ACK 了 COMMIT-PRIMARY record，老师即把 transaction 视为 truly committed，TC 可向 application 返回 success（01:04:27-01:04:52）。其余日志处理可异步继续；至少一个 commit decision 证据与此前已复制的 new values 能在故障后推动完成。

7. **把 TRUNCATE 移出关键路径。** 后续需要缩短 logs，防止无限增长，但 truncate 可与后续 locking/validation 重叠，老师不在本讲详细讨论（01:04:57-01:05:16）。

8. **澄清 ACK、日志和执行的区别。** ACK 回到 coordinator NIC 的 receive queue；TC poll 到 ACK 后继续。Write RDMA 用于 log append 和 message queue。说“write RDMA 已 performed”只证明 bytes 已追加到 log，不证明 backup/primary thread 已读取记录或把 new value 安装到 object（01:05:24-01:07:04）。

9. **再次强调 64-bit 原子锁。** 学生担心多核同时把 lock bit 从 0 改 1。老师说明 version + lock 合在一个 64-bit word，primary 用 atomic test-and-set；同时竞争时一个赢、另一个输，这是协议的 crucial point（01:07:04-01:08:38）。本段末尾学生开始询问 validation 与 commit 之间并发事务插入的问题，回答延续到后续问答。

## 概念、符号与推导

- **Decision to commit**：LOCK/VALIDATE 全通过后，TC 不再因正常并发冲突选择 abort，但尚需写容错证据。
- **COMMIT-BACKUP record**：`<txid, oid, v_read, new_value>`，写入所有相关 backups 的 NVRAM logs。
- **COMMIT-PRIMARY record**：至少包含 `txid`，表示 TC 的 commit decision，写入 primary log。
- **Commit point**：课堂定义为至少一个 primary NIC ACK COMMIT-PRIMARY 后；此时 TC 可返回 success。
- **Hardware ACK 语义**：$ACK(write) \Rightarrow$ bytes 已到目标 NVRAM log；不推出 $object\ memory$ 已更新。
- **容错前提**：在 $f+1$ replica 配置下，协议要让每个 write 在所有相关副本日志中有内容，再公开 commit decision，从而在至多 $f$ 个副本失败后仍留有恢复证据。
- 本段无数值公式推导。

## 例子与课堂提示

- **一主一备**：老师用最简单配置说明为何 COMMIT-BACKUP 必须先于 COMMIT-PRIMARY。只有 primary log 有值时就宣布 commit，primary 随即失败会丢失 committed write。
- **“ACK 不等于 executed”**：这是本段最重要的语义边界。低延迟来自不等待 remote CPU，但恢复协议必须能消费持久日志并完成尚未应用的写。
- **一个 primary ACK 即返回**：这不是说只复制了一个对象；此前所有相关 primary/backup logs 已有 write data。此处只需保存 transaction-level commit decision 的证据。
- **故障恢复细节**：老师说稍后再详讲；part 1 本段只建立记录顺序与证据，不描述完整 recovery algorithm。

## 概念、符号与推导

- **并发递增事务**：$T_i: R(x=v);\ W(x=v+1);\ Commit$。

- **合法结果集合**：$x\in\{0,1,2\}$，但它必须与 success/abort 返回一致：两次 success 对应 2，一次 success 对应 1，零次 success 对应 0。

- **证明边界**：例子提供 serializability intuition，不构成所有可能 execution 的形式化证明。

## 教学展开

1. **完成 read-only fast path。** 纯读 transaction 初次读取对象时用 one-sided RDMA，commit validation 时再用 one-sided RDMA 读取 header；没有 writes、locks 或 log records。老师概括为只需“两轮 one-sided RDMAs”，这正是采用 OCC 的大收益（01:19:51-01:20:38）。若读取多个对象，“两轮”指 read round 与 validate round，不是整个 transaction 永远只有两个 packet。

2. **回答 RDMA 安全边界。** NIC 不能任意读写进程全部 memory。Connection setup 时 OS 与 application 配合，登记允许访问的 virtual memory addresses/regions；NIC 的 fast path 被限制在这些授权范围（01:20:41-01:21:25）。

3. **承认高冲突下 OCC 的代价。** Reads 虽快，但 write contention 或 read version 被频繁改动会让 transaction abort。FaRM 更适合触碰不同 records/objects 的低冲突 workloads；论文 TPC-C/TATP benchmarks 的冲突较少（01:21:26-01:22:39）。因此高吞吐数字依赖 workload，不是任意事务都能达到。

4. **澄清 log 并发写。** 不同 clients 不会覆盖同一个 append slot，因为系统为每个 sender-receiver pair 配置独立 log（01:22:46-01:23:14）。这里字幕把 `log` 听成 `lock` 的位置较多，但上下文是 remote log append 冲突。

9. **构造跨 shard 交错。** T1 写 shard 1/2、读 `z`；T2 在 T1 运行期间读写并 commit `z`。若 T2 完成后 T1 才 validation，T1 重读 `z` 会从 version 0 看到 version 1，于是 abort（01:27:01-01:29:07）。学生继续追问：若 T1 validation 先通过、T2 又在 T1 最终 commit 前完成，会不会漏检？老师的回答跨入下一节，并最终把重叠 transaction 的可重排性作为关键。

## 概念、符号与推导

- **Read-only fast path**：对 read set 执行一轮 one-sided reads，commit 前再执行一轮 one-sided validation；无 remote CPU、lock 或 log write。
- **OCC 适用性**：冲突概率越高，abort/retry 越多；transaction 越长，暴露于冲突的时间窗口通常越大。
- **Logical version**：按对象更新推进的序列信息，不是 physical time，也不是 global TrueTime。
- **Per-source ordering**：同一 sender 的 queue 内有序；不同 senders 间无全局消息顺序，协议正确性不能依赖它。
- **Locality**：把共同访问对象放在同一 primary，可把跨机器参与者数从多个降到更少；本段不提供具体优化公式。
- **跨 shard 例子**：若 T2 在 T1 validation 前把 `z` 从 $v_0$ 提升到 $v_1$，则 T1 的条件 $v_{now}=v_{read}$ 失败并 abort。

## 概念、符号与推导

- **Concurrent/overlapping transactions**：两个 transaction intervals 有重叠；strict serializability 允许在满足读写结果的前提下选择任一 serial order。

- **Serializability**：存在一个等价串行执行；不单独要求尊重真实时间中的非重叠先后。
- **Strict serializability**：serializability 加 real-time order，对不重叠 transactions 保留先后约束。
