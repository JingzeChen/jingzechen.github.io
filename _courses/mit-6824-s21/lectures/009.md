## 概览

本讲以两个问题组织 ZooKeeper。第一，replicated service 如何获得远高于串行 Lab 3-style `Put` 的 throughput：asynchronous/pipelined requests 与 batching 摊薄 network/disk cost，local replica reads 让 read capacity 随 server 数增长。代价是整体不再提供 full linearizability；ZooKeeper 保留 linearizable writes 与 FIFO client order，允许 read stale，但通过 `zxid` progress lower bound、read-your-own-writes 和 non-decreasing reads 阻止同一 session 倒退。

第二，怎样把 coordination 从每个 application 的临时逻辑变成通用 service。课堂从 GFS/MapReduce configuration、VM-FT test-and-set 与 master election 出发，说明普通 `Put`/`Get` 难以组合出 atomic conditional update，也不能自然表达 participant/session disappearance。ZooKeeper 用 znode tree、regular/ephemeral/sequential creation、watches 和 versioned `setData` 提供 building blocks；`ready` protocol 展示 configuration publication，counter 展示 optimistic mini-transaction/retry。

本讲的核心 tradeoff 是：full linearizability 最容易按 single machine 推理，但把所有 reads 纳入 ordered leader path 会限制 read scaling；ZooKeeper 放松 cross-client read freshness，以更复杂的 programmer discipline 换取高 read throughput。应用必须理解 write order、session read order、watch notification 与 restart，且在确实需要更强 freshness 时使用 `sync`。

## 学习主线

1. **先建立性能矛盾**：串行 durable write 粗算约 `200 Put/s`，论文图却约 `21K writes/s`，并显示 reads 随 replicas 扩展。
2. **再暴露 local-read correctness 问题**：任意 follower 可返回 stale value，同一 client 切换 replica 后甚至可能先读新、后读旧。
3. **精确定义替代 guarantee**：Lab 3 让 reads 也进入 Raft log 以达 linearizability；ZooKeeper 改为 linearizable writes 加 FIFO client order，reads 对应 non-decreasing write-log prefixes。
4. **让 weaker semantics 可编程**：session 携带 `zxid` progress floor；`ready` marker 与 watch 让 configuration reader 检测跨版本并 restart；`sync` 是需要更强 freshness 时的慢路径。
5. **把 coordination 编进 API**：ephemeral znode 表达 session-bound membership，sequential naming 提供顺序，versioned `setData` 用 conditional write/retry 避免 lost update，并可类推 test-and-set。
6. **保留 failure/performance tradeoff**：session failure detection 不是瞬时的；weak reads 增加应用复杂度；optimistic update 在 contention 下会 retry/backoff；更多 replicas 提高 read capacity却增加 write coordination cost。

## 关键模型

### Performance baseline 与 batching

课堂数量级估算为：

$$
T_{put}\approx 1\text{ ms RTT}+2\times2\text{ ms durable writes}=5\text{ ms},
$$

$$
throughput_{serial}\approx\frac{1}{0.005}=200\text{ Put/s}.
$$

ZooKeeper 的 busy-client benchmark 不是逐请求串行等待：clients 保持多个 outstanding operations，leader 把 requests pipeline/batch 到较少 network/disk writes，所以三副本纯 write throughput 可达到课堂口述的约 `21K ops/s`。reads 可在 replicas 本地完成，总 capacity 随 server 数增加；writes 则因 replication coordination 在更多 servers 时变慢。

### Linearizability 与 ZooKeeper ordering

课程的 full linearizability 判定要求：存在尊重 real-time precedence 的 total order，每个 read 返回该 order 中 preceding last write 的 value。Lab 3 的直接方法是让 `Put` 与 `Get` 都通过 current leader/Raft log。

ZooKeeper 对 writes 保留 total order。若一次 local read 位于 write-log prefix $W[1..k]$，同一 client 的 successive reads 满足：

$$
k_{i+1}\ge k_i.
$$

而且 client 自己先前 write 的位置必须包含在后续 read prefix 中。因此 read 可以漏掉 other clients 的 later writes，却不能 read before its own write，也不能在 session 中向更短 prefix 倒退。

### Configuration publication

Writer：

```text
delete(ready)
write(f1)
write(f2)
create(ready)
```

Reader 对 `ready` 设置 watch，再读取 `f1/f2`。若 reader 看到的是本轮末尾的新 `ready`，non-decreasing read order 保证后续 reads 已越过之前的 configuration writes。若 reader 看到旧 `ready` 后 update 开始，delete notification 会暴露 configuration boundary；notification 在读取中途到达时，client 丢弃 partial result 并 restart。

### Versioned conditional update

```text
while true:
    x, version = getData("count")
    if setData("count", x + 1, version):
        break
```

两个 clients 即使都读到同一 `(x,version)`，linearizable writes 也让两个 conditional sets 有确定先后；先执行者成功并推进 version，后执行者 mismatch 后 retry。stale read 不会直接覆盖 newer state。这一 pattern 可类推课堂提出的 test-and-set，但本讲没有给出完整 lock protocol。

## 本段在整讲中的作用

老师先把 ZooKeeper 放回课程主线：前几讲深入了 Raft 和代码，本讲开始转向更 conceptual 的 distributed-systems design；ZooKeeper 一方面与 Lab 3 的 replicated service 和 linearizability 相连，另一方面是一个仍被广泛使用的 coordination service。[00:00:18–00:01:18]

随后他给出全讲的两个问题。第一，ZooKeeper 为什么能比预期中的 Lab 3 吞吐更高：client operations 可以 asynchronous/pipelined，且系统不为所有操作提供同样强的 consistency，因此 read 可以分散到 replicas。[00:01:18–00:02:19] 第二，为什么要把 cluster membership、master identity 和 configuration state 外包给通用服务，而不是让每个 distributed application 重做一套。[00:02:20–00:03:19]

在提出目标后，老师只把 ZooKeeper 的底层 replication 抽象为一个 Raft-like replicated state machine，并明确本讲不展开 Zab 的协议细节。[00:03:41–00:07:22] 本段末尾开始为性能问题建立 baseline：三副本正常路径上的一次 `Put` 至少需要 leader 与 follower 的持久化写入及一次 round trip；具体数值推导在下一段完成。[00:07:28–00:10:00]

## 教学展开

### 1. 从 Raft 细节转向系统设计问题

- [00:00:18–00:00:55] 前几讲已经详细研究 Raft，本讲不再逐行钻协议，而是借 ZooKeeper 讨论 conceptual ideas，并回看 Lab 3 所追求的 linearizability。
- [00:00:55–00:01:18] ZooKeeper 不只是论文案例：它源自 Yahoo，后来成为 Apache open-source project，课堂强调它在实践中被广泛使用且仍然活跃。
- [00:01:18–00:02:19] “high performance”在这里首先是 throughput，即单位时间处理更多 operations，而不是承诺单个 operation 的低 latency。老师先预告两项原因：asynchronous client operations，以及允许 read 在任意 replica 执行的 consistency design。

### 2. 提出 coordination service 的动机

- [00:02:20–00:03:10] 很多 distributed applications 都要维护相似的 coordination metadata：cluster 中有哪些成员、谁是 master、每个 chunk 由哪些 server 保存、谁担当 primary。
- [00:02:37–00:03:07] 老师用 MapReduce 与 GFS 说明这些问题会反复出现。GFS 例子包括 master 跟踪 chunk servers 和 primary 等配置状态。
- [00:03:07–00:03:19] ZooKeeper 的定位是承接这类 configuration management，让应用开发者把精力留给自身的数据路径与业务逻辑。

### 3. 用熟悉的 replicated state machine 理解 ZooKeeper

- [00:03:41–00:05:07] client 向 ZooKeeper server 发起创建 znode 等请求；leader 把修改操作交给 Zab。课堂把 Zab 暂时类比成 Raft library：它建立 operation log，把有序操作交回 service，再由 service apply 并响应 client。
- [00:05:11–00:05:47] 这种类比只用于抽象其保证。老师说 Zab 实现方式不同，但高层上同样要在 failures 与 network partitions 下给操作排序，并避免 split brain。
- [00:05:52–00:06:29] Lab 2 主要实现 replication layer；Lab 3 则在 Raft 上实现 key/value service，数据结构是 key 到 value 的 map，接口是 `Put`/`Get`。
- [00:06:33–00:07:00] ZooKeeper 的 service state 不是平面 map，而是一棵 znode tree；但 deterministic operations 仍按同一顺序 apply 到各 replica，因此得到相同 state。
- [00:07:02–00:07:22] 本讲聚焦 ZooKeeper service semantics，不讲 Zab internals；老师要求把 Zab 当成与 Lab 2 已学内容作用相近的底层排序机制。

### 4. 为吞吐分析建立一次写入的正常路径

- [00:07:28–00:08:02] 老师问：若完成 Lab 3 后测量每秒通过多少 `Put`/`Get`，会得到怎样的 baseline？为排除干扰，先假设三台 server、无 crash、无 partition。
- [00:08:04–00:09:15] `Put` 到达 leader 后，leader 将其写入自己的 log，并几乎并行地向两个 followers 发 RPC；follower append 到 persistent log 后回复。获得 majority 后，leader apply `Put` 并回复 client。
- [00:09:16–00:10:00] 粗略成本至少包含 leader 到一个 follower 的 round trip，以及为了让 majority 拥有该 entry 而产生的 stable-storage writes。老师在这里尚未完成毫秒与 operations/second 的计算，下一段继续。

## 概念、符号与推导

### 两层系统模型

课堂模型可写成：

```text
client request
    -> ZooKeeper service / Lab 3 KV service
    -> Zab / Raft ordered log
    -> apply in the same order at replicas
    -> deterministic replicated state
```

这里的关键区分是：Zab/Raft 负责 replication 与 total ordering；ZooKeeper/KV layer 决定 state model、API 和可观察的 consistency semantics。[00:03:41–00:07:22]

### 三副本写入 baseline 的前提

本段只建立成本项，尚未给出最终公式：

1. 集群包含 one leader 与 two followers。
2. 只分析 normal case，不含 failure、retry 或 leader change。
3. entry 至少要到达 majority，leader 因而至少需要一个 follower 的确认。
4. leader 与响应的 follower 都要把 log entry 写入 persistent storage。
5. 至少存在一次 leader-follower round trip。

精确的课堂估算 `1 ms + 2 × 2 ms = 5 ms` 以及由此得到的 `200 Put/s` 出现在下一段，不提前归入本段。[00:09:26–00:10:00]

## 常见误解

- **误解：high performance 指每次请求 latency 一定更低。** 本讲此处明确把它定义为更高 throughput；后续 batching 甚至可能在等待凑批时改变 latency tradeoff。[00:01:22–00:01:56]
- **误解：ZooKeeper 完全没有 consistency guarantee。** 此处只是预告它“不提供强一致性的完整版本”；后续才精确定义 linearizable writes 与 FIFO client order，不能把预告简化成“无一致性”。
- **误解：Zab 就是 Raft。** 老师只说高层可按 similar guarantees 理解，并指出其 implementation quite different。[00:05:21–00:05:37]
- **误解：有了 ZooKeeper，应用就不需要自己的 replicated state。** 本段只说可把 coordination/configuration metadata 外包；没有声称 ZooKeeper 接管 GFS chunk data 或所有应用状态。

## 本段掌握检查

1. **问：本讲为什么同时连接 ZooKeeper、Lab 3 与 linearizability？**

## 概念、符号与推导

### 串行 baseline

$$
T_{put} \approx T_{RTT} + 2T_{disk}

          = 5\text{ ms}.
$$

若每次等待前一次完成，则：

$$
throughput \approx \frac{1}{0.005\text{ s}} = 200\text{ Put/s}.
$$

这是教学用数量级估算，不是对所有硬件、Raft implementation 或 ZooKeeper deployment 的普遍 benchmark。[00:10:21–00:11:35]

### Batching 的摊销模型

若一个 persistent write 包含 $B$ 个 operations，课堂直觉是每个 operation 分摊的 disk-write cost 从约一次降到约 $1/B$ 次。老师没有给 $B$ 的具体值，也没有在本段推导 latency；结论只针对 busy system 下的 aggregate throughput。[00:15:42–00:16:36]

### Read scaling 的前提

## 例子与课堂提示

- **`x: 0 → 1` 后任意 follower read**：服务于把性能优化转换为 correctness question。此时不得默认 follower 已收到或 apply 最新 entry。

# 003｜为什么任意副本读会产生 stale data 和“倒退”？

> 时间范围：`00:19:57–00:29:51`
>
> 证据范围：仅本段 transcript；本段 prompt 没有课件页。

## 本段在整讲中的作用

上一节为了 read scalability 刻意让 follower 不通信、直接返回 local state。本段先展示这种 naive design 的两种异常：一个 `Get` 可在 completed `Put` 后返回旧值；同一 client 的后一次 `Get` 甚至可比前一次看到更旧的 state。[00:19:57–00:23:04]

老师随后不凭直觉评价，而是重新给出 linearizability 的三个检查条件，再把两个 execution 逐一代入，证明它们都不满足 Lab 3 的 correctness goal。[00:23:13–00:29:51] 这样，性能优化与 correctness guarantee 的冲突被明确化，下一节才有理由比较“所有 reads 走 leader”和 ZooKeeper 的替代 semantics。

## 教学展开

### 1. 第一次 read 可以返回新值或旧值

- [00:19:57–00:20:14] `x` 初值为 `0`，系统正在处理 `Put(x,1)`。任意 follower 上的 local `Get(x)` 可能返回 `1`，也可能因该 follower 尚未赶上而返回 stale value `0`。
- [00:20:19–00:20:47] 老师把第一读固定为已经返回 `1`，再问没有其他 writes 时，第二次 read 能返回什么。

### 2. 第二次 read 仍可能“回到过去”

- [00:20:47–00:22:08] 直觉会认为只能是 `1`，但若 client 因短暂 disconnection/network partition 改连另一台 lagging follower，第二次 read 可以得到 `0`。
- [00:21:35–00:23:04] 老师先用五台 server 让现象更直观，随后确认三台同样可能：majority 由 leader 和一个 follower 组成，剩余 follower 仍可能没有该 write。
- [00:22:10–00:22:44] 因此 naive local reads 有两类问题：返回 stale data；在 successive reads 中先看到较新值、后看到较旧值，即 data appears to go backward in time。

### 3. 用 linearizability 精确替换“这样是否可以”的直觉争论

- [00:23:13–00:23:37] execution 是否“可以”取决于 correctness definition。课程前面使用的是 linearizability。
- [00:23:46–00:24:37] 第一项要求：即使 operations 并发，也能把所有 operations 安排进一个 total order，使系统看起来像 single machine。
- [00:24:42–00:25:05] 第二项要求：该 total order 与 real-time precedence 一致。如果 operation 1 已完成后 operation 2 才开始，则 order 中 1 必须在 2 前。
- [00:25:06–00:25:35] 第三项要求：read 返回 total order 中 preceding last write 的 value。这三项把“behaves like a single machine”变成可检查条件。

### 4. 检查 completed write 后的 stale read

- [00:25:37–00:26:36] execution 是 `Put(x,1)` 完成后，另一 client 才开始 `Get(x)`，但 read 返回 `0`。
- [00:26:40–00:27:46] real-time rule 迫使 `Put` 排在 `Get` 前；last-write rule 又要求 `Get` 返回 `1`。实际返回 `0`，因此没有合法 linearization。
- [00:27:50–00:28:04] single-machine intuition 同样说明问题：写入已完成，再读不应得到被覆盖的旧值。

### 5. 检查 successive reads 的 time travel

- [00:28:06–00:28:44] 第二个 execution 是一次 `Put(x,1)` 后，同一串观察先 `Get(x)→1`，再 `Get(x)→0`。
- [00:28:44–00:29:16] operations 的 real-time order 已确定，后一次 read 却没有返回 preceding last write 的 value，所以同样违反 linearizability。
- [00:29:16–00:29:51] 结论落回 Lab 3：若用这种 naive follower-local read implementation，测试中允许出现上述结果，就无法达到 `Put`/`Get` linearizability，因而不会通过目标测试。

## 概念、符号与推导

### Linearizability 的课堂判定模型

对 execution history $H$，要存在一个 operations 的 total order $L$，满足：

1. **Single total order**：每个 operation 在 $L$ 中占一个位置。
2. **Real-time precedence**：若 $op_1$ 的 response 早于 $op_2$ 的 invocation，则 $op_1 <_L op_2$。
3. **Legal read result**：每个 read 返回 $L$ 中排在它之前的最后一次 write 所写的值。

老师没有在本段讨论 overlapping concurrent operations 的全部可线性化选择；本段两个反例的 operations 都具有足够清楚的 real-time precedence，因此可直接判错。[00:23:46–00:25:35]

### 反例一

```text
Put(x, 1) completes
                    Get(x) starts -> 0
```

由 real time 得 `Put < Get`，由 last write 得 `Get(x)=1`，与 observed `0` 矛盾。

### 反例二

```text
Put(x, 1) -> Get(x) returns 1 -> Get(x) returns 0
```

没有 intervening write。第二次 `Get` 在 total order 中不能跳回 `Put(x,1)` 以前，故返回 `0` 不合法。

## 例子与课堂提示

- **五副本再回到三副本** [00:21:35–00:23:04]：用于说明问题不依赖“大集群”。只要某 follower 可落后于 committed majority，任意副本读就有风险。
- **client 不固定连接同一 peer** [00:21:47–00:22:08]：短暂网络故障或重连足以让 successive reads 落到进度不同的 replicas。
- **operation 的左右边界图** [00:25:53–00:26:12]：左边表示 invocation，右边表示 response，用来判断 real-time precedence，而不是只按 request 发出时间猜顺序。
- **single-machine intuition** [00:27:50–00:28:04]：是 linearizability 的辅助理解；正式判断仍用 total order、real time 和 last write 三项。

## 常见误解

- **误解：write 已经到达 majority，所有 replicas 就同时拥有它。** majority commitment 不要求每个 follower 已赶上；local read 可能落到不在该 majority 或尚未 apply 的 follower。
- **误解：stale read 只会发生在五副本。** 三副本也可由 leader+一个 follower 形成 majority，另一个 follower 仍 stale。[00:22:46–00:23:04]
- **误解：只要每个 replica 自己按 log 顺序 apply，client 就不会倒退。** client 切换到进度更慢的 replica 时，跨 replica 的观察仍可倒退。
- **误解：linearizability 只要求某个 total order。** total order 还必须尊重 non-overlapping operations 的 real-time precedence，并给出合法 read result。

# 004｜ZooKeeper 用什么 guarantees 换取 local-read scalability？

> 时间范围：`00:29:53–00:39:51`
>
> 证据范围：仅本段 transcript；本段 prompt 没有课件页。

## 本段在整讲中的作用

本段先给出 Lab 3 达到 linearizability 的直接方案：让 `Get` 也经过 leader/Raft log。这样容易建立尊重 real time 的 total order，却使所有 reads 再次汇聚到 leader，失去上一节追求的 read scaling。[00:29:53–00:33:50]

老师随后揭示 ZooKeeper 的核心 tradeoff：它不让整体 API 表现为一台 fully linearizable machine，而是组合 **linearizable writes** 与 **FIFO client order**。reads 可看到 write log 的某个 prefix、可 stale，但同一 client 的观察不能倒退，且要 read its own writes。[00:33:53–00:39:02] 末尾学生追问“linearizable writes 单独如何理解”，老师明确把答案延至下一块白板，因此本节不提前补答。[00:39:05–00:39:51]

## 教学展开

### 1. Lab 3 的直接解法：reads 也进入 ordered log

- [00:29:53–00:30:25] 若所有 operations 真正在一台 machine 上执行，自然容易线性化。replicated setting 中的直接对应是所有 reads 都发给当前 leader。
- [00:30:25–00:31:04] Lab 3 的 `Get` 会经过 Raft/log。即使 leader 随时间更换，Raft 仍提供 log total order；reads 在这个 ordered path 上返回 preceding last write 的 value。
- [00:31:04–00:31:39] replicated state machine 在 failures 和 network splits 下维持有序 log，各 peers 同序 apply，于是整体可被理解为 single machine。
- [00:31:43–00:32:31] 学生追问 real time。老师重申：若 operation 1 已完成，leader 已回复；之后才开始的 operation 2 必须在 log 中位于更后位置。
- [00:32:34–00:32:45] 课堂同时确认 Lab 3 client requests 在这里按 synchronous requests 理解。

### 2. 强保证的性能代价

- [00:32:46–00:33:07] Raft paper 有 read-only optimization，但老师指出即使该优化也需要某种 communication；此处不展开。
- [00:33:07–00:33:50] 若所有 reads 仍经 leader，read throughput 就不会随 server 数量线性增加。这个代价正好与 ZooKeeper graph 的表现冲突。

### 3. ZooKeeper 改变的是 correctness definition

- [00:33:53–00:34:28] 老师把这一点称为最重要的认识：ZooKeeper 不为整体操作提供前面定义的 full linearizability，某些结果可能不会在 single machine 上出现。
- [00:34:33–00:35:11] 第一项 guarantee 是 **linearizable writes**：所有修改 state 的 operations 都经 leader/log，在所有 peers 上以相同 total order apply。
- [00:35:19–00:36:09] 第二项是 **FIFO client order**：同一 client 可异步发多个 requests；ZooKeeper 按该 client 的发送次序执行/呈现这些 operations，不让后发 request 越过先发 request。

### 4. 读保证：read your own writes、prefix 与不倒退

- [00:36:24–00:37:09] 同一 client 的 read 必须至少看到自己此前 write 的结果，即 read your own writes；但不保证已经看到其他 clients 的所有 completed writes。
- [00:37:09–00:38:04] read 对应 write log 的某个 prefix。lagging follower 可以只拥有较短 prefix，所以返回 stale state；但不能乱序拼接 log entries，观察点必须是 prefix boundary。
- [00:38:07–00:38:39] 同一 client 的 successive reads 必须处于 non-decreasing prefixes：第二次可看到同一 prefix 或更长 prefix，不能看到更短 prefix。
- [00:38:44–00:39:02] 因而两个不同 clients 可能一新一旧；但同一 client 先新后旧的 time-travel history 永远不允许。
- [00:39:05–00:39:51] 学生指出 classic linearizability 通常同时涉及 reads/writes，询问“linearizable writes”如何独立成义。老师说 writes 的 total order 还会通过 rules 与 reads 建立关系，但完整说明留到下一段。

## 概念、符号与推导

### Lab 3-style fully ordered path

```text
Put/Get -> current leader -> Raft log -> ordered apply -> reply
```

这个模型把 reads 也放进全局 ordered path，便于满足 full linearizability，但 leader 成为 read-throughput bottleneck。[00:29:53–00:33:50]

### ZooKeeper 的 write order 与 read position

把 linearizable writes 形成的序列写为：

$$
W = (w_1, w_2, \ldots, w_n).
$$

一次 local read $r$ 可以在某个 prefix $W[1..k]$ 的 state 上执行。对同一 client 的 successive reads $r_i,r_{i+1}$，课堂要求：

$$
k_{i+1} \ge k_i.
$$

若该 client 自己先前的 write 位于 $w_j$，其后 read 还必须满足 $k \ge j$。因此系统允许 `stale relative to other clients`，但不允许 `read before own write` 或 `go backward`。[00:36:24–00:38:39]

### 性能与 guarantee 的对应关系

- all reads globally ordered through leader → 更接近 full linearizability，read capacity 不随 followers 直接增加；
- local reads at prefix positions → aggregate read capacity 可扩展，但可能 stale；
- FIFO client order/non-decreasing prefix → 在放松 freshness 后保留可编程的 session-local order。

## 例子与课堂提示

- **Lab 3 的 `Get` 也过 Raft** [00:30:20–00:31:39]：服务于展示最简单的强一致性实现及其 bottleneck。
- **leader 会变，但 log 仍 total ordered** [00:30:44–00:31:08]：用于纠正“所有请求必须永远经过同一物理机器”的误解。
- **lagging follower 只看到 prefix** [00:37:21–00:37:50]：用于精确表达 stale read 的合法边界，不是允许 replica 返回任意历史拼接。
- **不同 client 与同一 client 的区别** [00:38:44–00:39:02]：不同 clients 可观察到不同 freshness；同一 client 的 reads 受 FIFO/non-decreasing order 约束。

## 常见误解

- **误解：ZooKeeper reads 完全没有顺序。** reads 必须对应 write order 的某个 prefix，同一 client 的 prefix 不能缩短，并且要看到自己的先前 writes。
- **误解：linearizable writes 等于整个 ZooKeeper API linearizable。** 老师明确说 reads 不具备相同 freshness guarantee，所以整体可能出现 single machine 不会出现的结果。
- **误解：FIFO client order 只约束 writes。** 课堂把它用于同一 client 的 asynchronous operations，并具体推导 read-your-own-writes 与 successive reads 不倒退。
- **误解：让 reads 经过 leader 没有扩展性代价。** leader 必须处理全部 reads，总 read capacity 不能简单随 followers 增加。[00:33:20–00:33:34]

## 本段掌握检查

2. **问：该做法为什么不能复现 ZooKeeper 的 read scaling？**

3. **问：ZooKeeper 在本段给出的两项基本 ordering guarantees 是什么？**

# 005｜`zxid` 怎样让 local reads 可以 stale 却不能倒退？

> 时间范围：`00:39:52–00:49:50`
>
> 证据范围：仅本段 transcript；老师明确称实现解释为 “roughly best guess”，因此本节把 implementation intuition 与 observable guarantee 分开。

## 本段在整讲中的作用

上一节定义了 linearizable writes、FIFO client order、read-your-own-writes 和 non-decreasing read prefixes。本段尝试给出一幅实现直觉图：ZooKeeper client/session 携带一个 `zxid` lower bound；follower 若尚未 apply 到该位置，就延迟 read，达到后才回答。[00:39:52–00:42:57]

这个机制不强迫 follower 追到 global latest，因此仍允许漏掉其他 clients 已经提交的较新 writes；但它阻止同一 session 迁移到较慢 replica 后回到更短 prefix。[00:42:57–00:48:13] 段尾由机制转回 programmability：既然 full linearizability 更容易理解，ZooKeeper 的弱保证究竟够不够写出正确程序？老师先指出 `sync` 可获得更强 freshness，但为保留性能，下一节将先假设不用 `sync`。[00:48:16–00:49:50]

## 教学展开

### 1. 先声明证据边界：这是实现直觉，不是论文给出的完整 protocol

- [00:39:52–00:40:14] 老师说论文对具体实现并不十分 explicit，接下来的解释是 roughly best guess，目标是说明 guarantees 可能怎样实现。
- [00:40:15–00:40:48] client machine 上运行 ZooKeeper client library，类似 Lab 3 的 clerk。client 建立 session，并由 session 在连接与迁移中保存状态。

### 2. Write 经 leader 排序并产生 `zxid`

- [00:40:48–00:41:31] writes 最终进入 leader 的 ordered log。每个 write 位于一个 index，论文术语是 `zxid`；课堂建议先把它理解成 log index。
- [00:41:37–00:42:00] leader 在 write committed 后把相应 `zxid` 返回 client，session 因而知道自己的已确认进度。

### 3. Read 把最低可接受进度带给 follower

- [00:42:02–00:42:20] 为了性能，read 不必去 leader，可以发到 follower；request 带着 session 已知的 `zxid`。
- [00:42:25–00:42:57] 若 follower 的 committed/applied prefix 还没达到该 `zxid`，它不能立即用更旧 state 回答，而要等到看到该位置后再响应。
- [00:42:57–00:44:28] client 后续可能改连另一 follower。只要该 follower 至少达到 client 已知 `zxid`，它可以立即回答；它不需要包含其他 clients 更晚的 writes，因此结果可以相对 global latest 为 stale。
- [00:47:47–00:48:13] 学生问 client 是否指定“恰好读那个 index”。老师澄清 `zxid` 是 lower bound：reply state 至少覆盖到该位置，也可以更新；它不是要求精确停在该 prefix。

### 4. 课堂问答补清连接、commit 与 lower bound

- [00:44:39–00:45:16] session 通常可保持连接，但短暂 partition/disconnection 会让 client 切换 server；ZooKeeper 也可能做 load balancing。因此 guarantee 不能依赖永远 sticky 到同一 replica。
- [00:45:22–00:46:24] write request 可以先到 follower，但最终仍转给 leader 进入 ordered write path。
- [00:45:30–00:46:08] 对“leader 是否先达成 consensus 再返回 `zxid`”，老师在抽象协议细节后回答：应当在 entry committed 后才返回，否则只是 uncommitted entry。
- [00:46:26–00:47:16] follower 等待的不是仅仅在 log 中“看见”一个 uncommitted entry；它要达到 committed progress。反过来，client 能持有该 `zxid` 本身意味着对应 write 已 committed。
- [00:47:19–00:48:13] `zxid` 只防止 session 倒退，不保证把所有其他 clients 的 newer writes 一并纳入 read。

### 5. 从机制回到可编程性与 `sync`

- [00:48:16–00:49:30] full linearizability 像 single machine，`Put` 后 `Get` 的直觉简单；ZooKeeper programming model 不同，问题是这些精心挑选的 weaker rules 是否足够支持实际协调逻辑。
- [00:49:32–00:49:50] 老师准备分析 paper 的关键例子。先指出在 read 前发 `sync` 可使该 read 获得更强的 freshness/linearizability behavior，但每次都这样会失去性能；下一段因此暂时忽略 `sync`。

## 概念、符号与推导

### `zxid` 作为 session progress lower bound

设 client/session 已知的最高 write-log position 为 $z_c$，接收 read 的 server 已 committed/applied 到 $z_s$。课堂 sketch 的响应条件是：

$$
z_s \ge z_c.
$$

若 $z_s < z_c$，server wait；若 $z_s \ge z_c$，可在自己的 local state 上回答。它不需要等待到当前 global maximum $z_{latest}$，所以可能满足：

$$
z_c \le z_s < z_{latest}.
$$

这正是“session 不倒退但可 stale”的实现直觉。[00:42:02–00:44:34] [00:47:47–00:48:13]

### Client progress 的更新边界

老师最初以 “last write zxid” 讲解 request tag；随后用 “hasn't seen any new zxids” 和 lower-bound 语言说明 client 的已知进度会约束后续 reads。结合上一节 guarantee，应把它理解为 session 当前已观察到的 progress floor，而不是永远只记录自己最后一次 write。课堂没有给出字段名、wire format 或完整 failover algorithm。

### Guarantee 与 sketch 的区别

- **Guarantee**：同一 client 的 operation order、read-your-own-writes、successive reads 不后退。
- **Sketch**：client/session 携带 `zxid`，server 等到 committed prefix 达到 lower bound。
- **未展开**：Zab 如何编码 `zxid`、server 切换协议、duplicate handling 等内部细节。

## 例子与课堂提示

- **sticky session 被 network event 打断** [00:44:39–00:45:16]：服务于说明 read-order guarantee 必须跨 server migration 成立。

## 常见误解

- **误解：满足 client 的 `zxid` 就代表 read 是 global latest。** 其他 clients 的 later writes 可以缺失，结果仍合法 stale。

# 006｜`ready` 配置发布为什么需要 write order、read order 与 watch？

> 时间范围：`00:49:51–00:59:48`
>
> 证据范围：仅本段 transcript；本段 prompt 没有课件页。

## 本段在整讲中的作用

本段回答上一节的 programmability question：即使 read 可以 stale，ZooKeeper 的 ordered writes 与 non-decreasing client reads 仍能让应用可靠发布一组 configuration files。老师先分析 reader 已观察到“新 `ready`”的简单情况，再揭示 reader 可能在更新前看到“旧 `ready`”并跨越 configuration change 的危险。[00:49:51–00:57:41]

为阻止 old/new configuration 混读，应用把 `exists(ready)` 与 watch 结合。新 leader 删除 `ready` 时触发 notification；ZooKeeper 保证 notification 的观察顺序与触发它的 write/后续 writes 协调，使 client 能在混用新配置前收到事件并重启读取流程。[00:57:43–00:59:48] 事件到达的两种合法位置与 restart 行为在下一节完成。

## 教学展开

### 1. 为保留性能，先不依赖每次 `sync`

- [00:49:51–00:50:03] 在每次 read 前 `sync` 会把性能重新拉低。老师因此把问题设为：在不靠 `sync` 的情况下，能否利用 ZooKeeper guarantees 写出正确 configuration protocol。

### 2. Writer 用 `ready` 包围一批 configuration writes

- [00:50:04–00:50:47] 新 master/leader 要发布 replicated-state-machine membership、leader identity 等配置。它按 write order 执行：

```text
delete(ready)
write(f1)
write(f2)
create(ready)
```

- [00:51:02–00:51:47] reader 先做 `exists(ready)`；若结果为 true，再顺序读取 `f1`、`f2`。若不存在则等待，本轮先不讨论等待路径。

### 3. 若 `exists` 看到的是新 `create(ready)`，后续 reads 不会退回旧配置

- [00:51:55–00:52:49] 老师先明确假设：`exists(ready)` 立即返回 true，并且观察的是序列末尾的新 create；此时暂不讨论 notification。
- [00:53:00–00:54:06] 因为 writes 按 total order 执行，`write(f1)` 位于新 `create(ready)` 之前；`exists` 已观察到 create 对应的 `zxid`，同一 client 后续 `read(f1)` 不能回到更短 prefix，所以必须看到该轮 `write(f1)`。
- [00:54:10–00:55:32] 这满足配置发布的关键需求：reader 看到新 leader 的 `ready` 后，不会读取到该 leader 发布之前的旧 `f1`。`exists` 本身是 read，不是 write；论证依赖它观察到了哪一个 create。

### 4. 真正危险的 case：`exists` 看到旧 `ready`

- [00:55:33–00:56:04] 学生指出 `ready` 在新 leader 删除之前本来就可能存在。老师接受并切换到第二个 scenario。
- [00:56:04–00:57:15] reader 先对旧 `ready` 执行 `exists`，随后读取旧 `f1`；与此同时 leadership change/crash recovery 发生，新 primary 执行 delete、写新 `f1/f2`、再 create。
- [00:57:05–00:57:41] 若 reader 的 `read(f2)` 延迟到更新之后，它可能拿到新 `f2`，与旧 `f1` 组成 mixed configuration。这不是应用可接受的结果。

### 5. 用 watch 把 configuration boundary 变成可见事件

- [00:57:43–00:58:20] reader 实际应调用 `exists(ready, watch=true)`。当新 primary 删除 `ready` 时，watch 产生 notification。
- [00:58:35–00:59:24] 课堂给出的 ordering rule 是：由 `delete(ready)` 触发的 notification 必须在 client 能继续观察该 delete 之后的 writes/state 之前交付。于是事件要么在 reader 尚未进入相关读取前到达，要么整组旧读取先完成，不能静默夹在 old `f1` 与 new `f2` 之间而不通知。
- [00:59:24–00:59:48] 对规则实现的直觉是 notification 与触发 change 的 `zxid` 关联，并沿 client/session ordering 交付；下一节澄清 watch 不是 write operation 本身。

## 概念、符号与推导

### Configuration publication 的 write order

令：

$$
w_1=delete(ready),\quad
w_2=write(f1),\quad
w_3=write(f2),\quad
w_4=create(ready).
$$

linearizable writes 给出：

$$
w_1 < w_2 < w_3 < w_4.
$$

若 reader 的 `exists(ready)` 明确观察到 $w_4$，则该 session 后续 reads 的 prefix 不得短于 $w_4$，所以读取 `f1/f2` 时已包含 $w_2,w_3$。[00:50:04–00:54:06]

### 旧 `ready` 造成的 race

若 `exists` 观察的是上一轮 create，则它不能证明当前 configuration update 已完成。没有 watch 时，以下 interleaving 可能发生：

```text
reader: exists(old ready) -> read(old f1) ........ read(new f2)
writer:                         delete -> write f1 -> write f2 -> create
```

read prefixes 单调并不能防止从 old prefix 前进到 new prefix；它只防止倒退。因此还需要 watch 把 crossing boundary 暴露给 reader。

### Watch ordering 的课堂保证

本段把 guarantee 表述为：触发 watch 的 state change 与其 notification 带有相应 order/`zxid`；client 在观察该 change 之后的 state 前，会先收到 notification。课堂在下一节明确纠正“watch 像 write”的类比，故这里不把 notification 本身写成 log write。

## 例子与课堂提示

- **新 leader 发布 `f1/f2`** [00:50:14–00:50:47]：服务于说明 configuration 常由多个 znodes 组成，需要一个 readiness marker 定义发布边界。
- **`exists` 返回 true 的歧义** [00:52:42–00:55:45]：true 可能来自新 create，也可能来自尚未 delete 的旧 marker；正确推理必须说明观察的是哪一轮。
- **old `f1` + new `f2`** [00:56:04–00:57:41]：服务于说明 monotonic reads 本身不提供 multi-key snapshot；watch 用于检测跨配置版本。
- **不用 `sync` 的设定** [00:49:51–00:50:03]：服务于展示 weaker semantics 的实际价值，而不是否认 `sync` 在需要 freshness 时有用。

## 常见误解

- **误解：`exists(ready)==true` 总能证明本轮 update 完成。** 只有它观察到本轮末尾的新 create 才能这样推理；旧 ready 仍可能返回 true。
- **误解：FIFO/non-decreasing reads 自动提供跨多个 znodes 的 snapshot。** 它防止倒退，却允许 reader 从旧 prefix 前进到新 prefix，产生 old/new 混合。
- **误解：watch 通知直接携带完整新配置。** 本段只把它作为 change notification；client 仍需按 protocol 重新读取。
- **误解：watch 是一条 write。** 本段末尾只用类比解释 order；下一节老师明确说 watch 不是 write operation。

## 本段掌握检查

1. **问：writer 为什么按 `delete ready → write f1/f2 → create ready` 排序？**  
   **答：** `ready` 不存在表示配置正在改变，末尾 create 表示这一批 ordered writes 已发布。[00:50:04–00:50:47]

2. **问：若 `exists(ready)` 观察到新 create，为什么后续 `read(f1)` 不能返回旧值？**  
   **答：** create 排在该轮 `write(f1)` 后；同一 client 的后续 read 不能退到比已观察 create 更短的 write prefix。[00:53:00–00:54:06]

3. **问：为什么只检查 `ready` 仍可能混读配置？**  
   **答：** reader 可能在 delete 前看到旧 ready，先读旧 `f1`，再在 update 后读新 `f2`；prefix 虽前进却跨了 configuration boundary。[00:55:33–00:57:41]

4. **问：`watch=true` 在这个 protocol 中解决什么？**  
   **答：** 删除 ready 会触发 notification；ordering guarantee 让 reader 在消费 delete 后的新 state 前获知 boundary change，从而可丢弃部分结果并重启。[00:57:43–00:59:48]

5. **问：为什么课堂暂时不用 `sync`？**  
   **答：** 不是因为它无效，而是普遍使用会牺牲目标性能；这个例子要证明 weaker guarantees 加 watch 也能支持正确配置读取。[00:49:51–00:50:03]

- [需回听 00:53:36–00:54:02] `exists` 所观察 create 的具体 `zxid` 被字幕转成 “exists [id]”；笔记按随后明确的 total-order 解释整理。

# 007｜Watch 触发后为何要 restart，普通 KV 又为何不够做 coordination？

> 时间范围：`00:59:51–01:09:48`
>
> 证据范围：仅本段 transcript；本段 prompt 没有课件页。

## 本段在整讲中的作用

本段先完成 `ready`/watch 例子：notification 与触发它的 modification/`zxid` 有顺序关系，应用在读取中途收到通知时必须丢弃 partial result 并 restart。老师据此总结第一项 tradeoff：弱于 full linearizability 的 guarantees 增加 programmer burden，但经谨慎设计仍可正确使用，并带来 fault tolerance/scalability 下的性能收益。[00:59:51–01:03:43]

随后课程转入第二主题：coordination-service API。VM-FT 的 test-and-set 需要 exclusive winner 来避免 split brain，而只有 `Put`/`Get` 的 Lab 3 KV API 无法直接原子化“写入候选 master 后再验证”的组合操作；此外应用还需要知道 participant/session 何时消失。[01:03:48–01:08:17] 最后老师引入 znode tree、regular 与 ephemeral nodes，为下一节完整 API 与 versioned update 铺路。[01:08:17–01:09:48]

## 教学展开

### 1. 澄清 watch notification 的顺序，而不是把 watch 当 write

- [00:59:51–01:00:30] 由 `delete(ready)` 触发的 notification 必须在 client 观察后续 `write(f1)`、`write(f2)` 等新 state 之前交付；这是 ZooKeeper 必须提供的 ordering rule。
- [01:00:35–01:00:59] 如果 notification 在 reader 完成旧 `read(f1/f2)` 之后才到，旧读取整体位于 update 之前，不会混合，所以没有问题。
- [01:01:03–01:01:41] 学生追问 watch 是否“像 write”。老师纠正：watch 不是 write operation；它是 local watch/event，但与导致 modification 的适当 `zxid` 一起被有序观察。论文对具体实现略含糊，重要的是 guarantee 本身。

### 2. 中途收到通知就丢弃 partial read 并重来

- [01:01:52–01:02:15] 若 reader 已完成 `exists`、读了 `f1`，随后 notification 到达，应用必须 restart。
- [01:02:36–01:02:53] restart 包括丢弃之前读到的 `f1`，从 protocol 开头重新执行。这种 bail out and start over 是 ZooKeeper recipes 中反复出现的模式。
- [01:03:00–01:03:43] 老师总结：linearizability 最直观，但在 fault tolerance 与 scalability 下获取高性能更难。ZooKeeper 放松 consistency，增加了 programming difficulty；不过 guarantees 是为可用 recipes 精心选择的，不是任意放松。

### 3. 用 VM-FT test-and-set 定义 coordination 的原子性需求

- [01:03:48–01:04:51] VM fault-tolerance paper 中的 test-and-set 让两个 clients 竞争，恰好一个获胜并成为 primary，另一个失败；exclusive result 用来防止 split brain。
- [01:04:52–01:06:10] 老师问只有 `Put`/`Get` 的 Lab 3 是否能实现。naive code 是：

```text
Put("master", myIP)
if Get("master") == myIP:
    act as master
```

- [01:06:13–01:06:56] 这个组合没有 atomicity。两个 clients 的 `Put`/`Get` 可以交错，使双方分别在某一时刻读回自己的 IP，于是都认定自己是 master。
- [01:06:57–01:07:17] 单纯 `Put`/`Get` 很难直接表达 test-and-set。老师提到理论上可用 bakery algorithm 等复杂做法，但认为在这里不切实际；ZooKeeper 选择提供更合适的 primitive support。

### 4. Coordination 还需要 failure/session disappearance signal

- [01:07:31–01:08:17] 除原子条件更新外，应用需要发现 leader/participant 已经 down，才能触发 replacement。普通 KV interface 没有直接把 client failure 与某个 key 的生命周期绑定。
- [01:07:57–01:08:17] 因而 ZooKeeper design 要回答两个需求：如何得到所需 atomicity；如何让应用知道某个 node/session 消失。

### 5. 引入 znode tree 与 ephemeral lifecycle

- [01:08:17–01:09:06] ZooKeeper state 是 znode tree。应用可拥有自己的 subtree，例如 `/app1` 下的 children 表示 participating machines，名字可使用 IP/DNS 等身份信息。
- [01:09:06–01:09:20] regular znode 是正常持久的 replicated node，需要显式管理其创建/删除。
- [01:09:20–01:09:48] ephemeral znode 与创建它的 session 绑定。若 session 因 client 终止、heartbeat 缺失或网络问题被 ZooKeeper 判定结束，该 znode 会由系统自动删除；这为 membership/failure observation 提供基础。

## 概念、符号与推导

### Watch 的两类安全位置

对 reader 的一个读取 attempt 与 writer 的 configuration update，notification 有两类不会产生静默 mixed result 的位置：

1. 在 reader 消费 new-state reads 前到达：reader abort/restart；
2. 在 reader 完成整组 old-state reads 后到达：本轮结果整体位于 update 前。

危险位置“old `f1` 后、新 `f2` 前但没有通知”由 watch ordering rule 排除。[00:59:51–01:02:15]

### Naive master election 的 interleaving

```text
C1: Put(master, IP1)
                         C2: Put(master, IP2)
                         C2: Get(master) -> IP2  => master
C1: Put/Get 的另一合法交错中也可能读回 IP1 => master
```

老师的核心结论不是某一个固定四步 schedule，而是 `Put` 与 `Get` 是两个独立 operations，缺少 conditional atomic update，不能把“仅当未被竞争者改写时获胜”表达为单一步骤。[01:05:10–01:07:17]

### Ephemeral znode 的 failure model

ephemeral node 的删除以 **session expiration/termination** 为条件，不是 ZooKeeper 瞬间、完美地判断 process crash。课堂说在 heartbeat 不再到达等情况下，ZooKeeper“at some point”判定 session gone 再删除。[01:09:20–01:09:48]

## 例子与课堂提示

- **read `f1` 后收到 watch** [01:01:52–01:02:44]：服务于强调 partial data 不能继续使用，restart 必须覆盖已完成的 reads。
- **VM-FT test-and-set** [01:04:13–01:04:51]：服务于把 coordination correctness 具体化为 exclusive primary，失败结果是 split brain。
- **`Put(master,myIP)` + `Get`** [01:05:10–01:06:56]：服务于说明 linearizable individual operations 不等于 multi-operation sequence 原子。
- **`/app1/machine-*`** [01:08:35–01:09:06]：服务于说明 hierarchical namespace 如何组织 application membership metadata。
- **ephemeral node 随 session 消失** [01:09:20–01:09:48]：服务于 failure notification/lifecycle，而不是一般持久数据存储。

## 常见误解

- **误解：watch notification 到达后可以保留先前读到的 `f1`，只重读 `f2`。** 课堂要求整次 attempt restart，因为部分值可能属于旧配置。
- **误解：watch 本身是一条 linearizable write。** 老师明确否认；它是与 modification/`zxid` 有 ordering guarantee 的 notification。
- **误解：每个 `Put`/`Get` 都 linearizable，就能把两者组合成 test-and-set。** interleaving 发生在两个 operations 之间，组合缺少 atomicity。
- **误解：ephemeral znode 在机器断线瞬间删除。** 删除取决于 ZooKeeper 判定 session 终止/超时，存在 failure-detection delay。
- **误解：本段已经讲完 ZooKeeper lock recipe。** 本段只用 test-and-set 说明需求，并引出 API；具体 smarter lock 被留到下一次 lecture。

## 本段掌握检查

1. **问：watch 在配置读取中途触发时，client 为什么要完整 restart？**  
   **答：** 已读部分可能属于旧 configuration，而后续 state 可能已进入新 configuration；丢弃 partial result 才能避免混用。[01:01:52–01:02:53]

2. **问：为什么 `Put(master,myIP)` 后 `Get(master)` 不是 test-and-set？**  
   **答：** 两个独立 operations 之间可被另一 client 的 `Put/Get` 交错，缺少单一 conditional atomic decision，可能产生两个 masters。[01:05:10–01:06:56]

3. **问：coordination API 在本段被归纳为哪两个需求？**  
   **答：** 提供 conditional/atomic coordination 能力；让应用得知 participant/session 已消失。[01:07:31–01:08:17]

4. **问：ephemeral znode 怎样支持 membership 或 leader failure handling？**  
   **答：** node 与 session 绑定，session 被判定结束时自动删除；其他参与者可据此观察 membership/leadership marker 消失。[01:09:20–01:09:48]

5. **问：本段怎样概括 weaker consistency 的代价与收益？**  
   **答：** programmer 必须理解 order、watch 和 restart，复杂度更高；但精心选择的规则让正确 recipes 仍可实现，同时保留 fault-tolerant read scalability。[01:03:00–01:03:43]

# 008｜Znode API 怎样用 versioned update 提供 mini-transaction？

> 时间范围：`01:09:49–01:19:49`
>
> 证据范围：本段 transcript；`l-zookeeper.txt` 仅用于核对 API signature。课堂总结在 `01:19:10` 已结束，末尾 `01:19:42–01:19:49` 是课后提问开头。

## 本段在整讲中的作用

上一节已经引入 regular 与 ephemeral znodes。本段补上 sequential naming，列出 ZooKeeper API，并集中解释 versioned conditional update 如何填补普通 `Put`/`Get` 缺少的原子性。[01:09:49–01:11:47]

核心例子是 concurrent counter increment：`getData` 取得 `(value, version)`，`setData` 只在 version 仍匹配时写入；linearizable writes 保证两个竞争 writes 有先后，只有先执行者匹配成功，失败者回到循环重读重试。[01:11:50–01:16:32] 这不是把 read 与 write 变成 server-side transaction，而是以 compare-and-set-like conditional write 实现课堂所谓 mini-transaction/lock-free programming。

随后老师因时间停止新的细节，概括 ZooKeeper 的成功之处：carefully designed API 与 weaker read consistency 仍能承载关键 configuration service，同时换得高 throughput。[01:16:45–01:19:10] 锁的具体实现没有在本段展开，课后问答延续至下一节。

## 教学展开

### 1. Sequential znode 给同一 parent 下的 children 排序

- [01:09:49–01:10:28] sequential node 创建时，名称带有递增 sequence number。同一 parent 下的 children 可按编号排序；已有 `1,2,3` 时，新建者获得更高编号。
- 课堂口头把 regular、ephemeral、sequential 说成三类；`l-zookeeper.txt` 的 API 表达更准确地把 sequential 作为 `create` flag。此处保留讲授直觉，不将两种描述混为额外语义。

### 2. 按老师顺序列出 znode API

- [01:10:29–01:10:47] `create(path, data, flags)`：路径、数据和 node flags；课堂把 flags 对应到前述 regular/ephemeral/sequential choices。
- [01:10:48–01:10:58] `delete(path, version)`：老师纠正前一张图遗漏 version 的问题。
- [01:10:58–01:11:05] `exists(path, watch)`：检查 path 是否存在，并可设置 watch。
- [01:11:05–01:11:18] 老师口述 `getData` 时把第二参数说成 version；课堂讲义列为 `getData(path, watch)`，并在 counter 例子中明确返回 value 与 current version。笔记按讲义 signature 记录，不把口误扩展为新的 API。
- [01:11:19–01:11:25] `setData(path, data, version)`：以 expected version 条件更新 data。
- [01:11:26–01:11:37] `getChildren(path, watch)`：读取一个 znode 的 children，并可设置 watch。
- [01:11:39–01:11:47] `sync()`：当确实需要更强 read freshness 时使用；本讲没有在此重新推导其完整语义。

### 3. 用 versioned counter 建立 conditional update

- [01:11:50–01:12:59] increment pseudo-code 为：

```text
while true:
    x, v = getData("count")
    if setData("count", x + 1, v):
        break
```

- [01:13:04–01:13:40] `getData` 返回当前 value `x` 和 version `v`。`setData` 只有在 znode 当前 version 仍等于 expected `v` 时才执行，否则失败。
- [01:13:45–01:14:35] 两个 clients 并发读取时，都可能得到 `(x=0,v=0)`，并都尝试 `setData(count,1,0)`。
- [01:14:37–01:15:32] 两个 set operations 不会都成功。因为 writes linearizable，它们进入一个 total order；先执行者看到 version 仍为 `0`，把 value 改为 `1`，同时推进 version，并返回 success。
- [01:15:35–01:16:15] 后执行者发现 expected version `0` 已不匹配，write 失败，于是 loop 回去重新 read，再把 `1` 改为 `2`。最终两个 increments 都保留，结果为 `2` 而非 lost-update 后的 `1`。
- [01:16:24–01:16:32] 老师把这种 read/conditional-write/retry pattern 类比为 familiar lock-free programming，并说 ZooKeeper API 鼓励这种风格。

### 4. 课堂总结：弱 read consistency 与 carefully designed API 的组合

- [01:16:45–01:17:10] 老师因时间停止进一步内容，原想谈 locks 的部分延期；先总结本讲。
- [01:17:11–01:17:44] ZooKeeper 是 widely used、successful design；其区别之一是整体不提供 full linearizability，尤其 reads 可 stale。
- [01:17:44–01:18:31] 尽管 consistency 较弱，API 仍可用于关键 configuration service，如 primary identity 与 replica set。正确使用 API 能避免 split brain 等错误。
- [01:18:34–01:19:10] weaker guarantees 与 API discrimination 换来 high performance。老师预告后续课程还会看到通过放松 consistency 改善 performance，或在 network partition 下继续工作的设计取舍。
- [01:19:42–01:19:49] 课后学生开始追问前面的 test-and-set；答案进入第 9 节。

## 概念、符号与推导

### API 总表

| Operation | 本讲使用的关键语义 |
| --- | --- |
| `create(path, data, flags)` | 创建 znode；flags 选择 regular/ephemeral 及 sequential naming |
| `delete(path, version)` | expected version 匹配时删除 |
| `exists(path, watch)` | 检查存在性，并可注册 watch |
| `getData(path, watch)` | 返回 data/metadata，包括 version；可注册 watch |
| `setData(path, data, version)` | expected version 匹配时条件写入 |
| `getChildren(path, watch)` | 返回 children names，并可注册 watch |
| `sync()` | 为后续 read 建立更强的已传播 write 可见性边界 |

表中 signature 由课堂口述与 `l-zookeeper.txt` 交叉核对；未加入 paper-only API behavior。

### Versioned increment 的正确性链

两个 clients 都读到：

$$
(x,v)=(0,0).
$$

它们提交：

$$
setData(count,1,0).
$$

由于 writes 有 total order，设 $W_1<W_2$。$W_1$ 在 current version 为 `0` 时成功，并将 version 推进；$W_2$ 执行时 expected `0` 不匹配而失败。$W_2$ 的 client 重读后获得 `(1,1)`，再写 `2`，所以最终：

$$
count=2.
$$

这里依赖两项语义：writes 不能并列无序执行；version check 与该 write 原子判定。stale `getData` 不会破坏正确性，因为 stale version 会让 `setData` 失败并触发 retry。[01:13:04–01:16:15]

### 课堂所称 mini-transaction 的边界

`getData + setData(version)` 的整体不是不可被并发者插入的锁住区间；并发 change 可以发生，但会由 version mismatch 检出。它提供的是 optimistic conditional update 与 retry，不是 multi-znode atomic transaction。

## 例子与课堂提示

- **children 编号 `1,2,3`** [01:09:49–01:10:28]：服务于解释 sequential naming 可建立 contender/order 信息；本讲没有据此展开 lock queue algorithm。
- **纠正 `delete` 的 version 参数** [01:10:48–01:10:58]：服务于强调 conditional API，而不是无条件删除。
- **两个 clients 同读 `(0,0)`** [01:13:45–01:15:48]：服务于展示 stale/concurrent read 不会自动造成 lost update，关键在 conditional linearizable write。
- **最终 `2` 而不是 `1`** [01:15:54–01:16:15]：服务于验证 retry loop 保留两个 increments。
- **configuration service 总结** [01:17:44–01:18:31]：服务于回扣本讲动机；API 的价值在于用正确 recipe 管理 primary/replica metadata。

## 常见误解

- **误解：sequential 是与 regular/ephemeral 完全互斥的第三种 lifetime。** 课堂口语称“三类”，但 API 中 sequential 由 create flag 控制 naming；本讲没有声称它替代 lifetime semantics。

## 概念、符号与推导

### Versioned test-and-set 的课堂可证范围

本段只给出与 counter 相同的结构，不给具体 path/value protocol：

```text
read current value and version
attempt conditional set with expected version
if success: this write wins its place in the linearized write order
if failure: another write changed the version; re-read/retry if still needed
```

能推出的是：两个竞争者使用同一 expected version 时，不会都以该 version 成功。不能从本段推出完整 leader lifecycle、session expiry handling、fencing 或 lock release algorithm；老师没有讲这些步骤。[01:20:07–01:20:41]

### Contention tradeoff

令一次成功前发生 $r$ 次 version mismatch，则 client 至少进行了 $r+1$ 轮 conditional attempts。课堂只给定性关系：

- low/no contention → $r$ 接近 `0`；
- high contention → $r$ 增大，需要 backoff 避免立即重试加剧竞争。

本段没有 throughput equation、fairness guarantee 或 starvation proof。

### Lock topic 的严格边界

- **已讲**：ZooKeeper primitives 可支持 lock-free-style operation；naive lock 也会有 contention；存在 smarter design。
- **未讲**：simple lock acquire/release pseudo-code、ephemeral node 如何释放该具体 lock、sequential contenders 监视 predecessor、herd effect 的完整机制。
- **原因**：老师两次明确说原计划/希望下一次再讲。[01:20:19–01:20:27] [01:21:52–01:22:19]
