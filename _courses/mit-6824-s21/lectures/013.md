## 核心概念与依赖关系

```text
distributed transaction
  |
  +-- concurrency / interleaving
  |     -> Isolation
  |     -> serializability target
  |     -> concurrency control
  |          +-- pessimistic -> 2PL -> wait/deadlock -> abort/retry
  |          +-- optimistic  -> validate at commit -> abort/retry
  |
  +-- crash / partial execution
        -> Atomicity
        -> atomic commit
             -> 2PC coordinator decision
             -> participant/coordinator durable logs
             -> recovery/re-send
             -> prepared-state blocking
```

- **Consistency** 约束 application/database invariants，老师以 referential integrity 为例后明确不展开。[00:10:49-00:11:13]
- **Durability** 要求 committed transaction 在 stable storage 中跨 crash 保留；它支撑 2PC decision recovery，但不等同于 atomic commit 本身。[00:11:44-00:12:01]
- **2PL 与 2PC 是正交组件：** 前者约束 concurrent schedules，后者协调不同 participants 的 commit outcome。同一 transaction 可先用 2PL 保持 locks，再用 2PC 决定是否共同 install。[01:14:37-01:16:28]

## Serializability 与 concurrency-control 边界

### Outcome 定义

令 $Outcome(E)$ 同时包括 execution $E$ 的程序输出与 database changes。Concurrent execution $E_c$ serializable，当且仅当存在 transactions 的某个 serial order $S$：

$$
\exists S:\quad Outcome(E_c)=Outcome(S).
$$

[00:12:44-00:13:52]

课堂 transcript 采用 `x = 10, y = 10`，`T1: x -= 1; y += 1`：

| Serial order | Audit output | Final state |
| --- | --- | --- |
| `T1; T2` | `9,11` | `x = 9, y = 11` |
| `T2; T1` | `10,10` | `x = 9, y = 11` |

任何混合输出如 `10,11` 或 `9,10` 都不属于上述 outcomes，即使最终余额随后成为 `9,11`，整个 execution 仍不 serializable。[00:13:58-00:19:44]

> 材料差异：`l-2pc.txt` 将 transfer 方向写为 `x += 1, y -= 1`，故讲义合法值是 `11,9` 与 audit `10,10`。课堂 argument 相同，符号相反；本笔记按 transcript chronology 使用 `9,11`，不把两套数字混用。

### Pessimistic 与 optimistic

| 方法 | Conflict 前 | Commit 附近 | Conflict cost |
| --- | --- | --- | --- |
| Pessimistic | 使用前取得 locks | 保持到安全结束 | 等待；可能 deadlock 后 abort |
| Optimistic / OCC | 先执行，不长期预锁 | 验证 reads/writes 能否 serializable | 验证失败 abort + retry |

[00:20:22-00:22:29]

老师只预告 FaRM 将展示 OCC；本讲没有给 OCC validation algorithm，也没有量化 conflict threshold。数据库可以提供 weaker isolation 换 concurrency，但本讲固定分析 gold-standard serializability。[00:22:06-00:24:02]

## Two-Phase Locking

### 规则与必要性

对 transaction $T$、record $r$ 与对应 lock $L_r$：

1. $T$ 第一次 read/write $r$ 前必须持有 $L_r$。
2. $T$ 已取得的所有 locks 保持到 `commit` 或 `abort`。

```text
begin T
  acquire Lx -> use x
  acquire Ly -> use y
  ... keep Lx and Ly ...
commit/abort T
  release Lx, Ly
```

[00:24:15-00:25:58]

若 `T1` 更新 `x` 后立即释放 `Lx`，`T2` 可在 `T1` 更新 `y` 前读完整个 audit，看到 partial transfer；若 `T1` 随后 abort，`T2` 还可能使用一个从未成为 committed state 的 value。因此 release point 不能早于 transaction outcome。[00:26:47-00:29:57]

### Simple Locking、并发度与 deadlock

- **Simple/strict locking（本讲命名）：** Transaction 开始前声明并取得全部 locks，结束时释放；避免渐进 acquisition 的一类 deadlock，但过早锁住 late/conditional records。
- **2PL：** 随实际 execution 增量 acquire；rare branch 未执行时无需取得 branch-specific lock，允许其他 transactions 更久使用该 record。
- **代价：** `T1` 持 `Lx` 等 `Ly`、`T2'` 持 `Ly` 等 `Lx` 时形成循环等待。[00:30:22-00:32:04] [00:36:11-00:37:21] [00:46:20-00:46:39]

Wait-for graph 中，若 $T_i$ 等待 $T_j$ 持有的 lock，则加入：

$$
T_i \rightarrow T_j.
$$

本例同时有 $T_1 \rightarrow T_2'$ 与 $T_2' \rightarrow T_1$，cycle 表示 deadlock。System 可用 timeout 近似处理，或动态检测 cycle，再 abort 一名 victim、撤销其 tentative effects、释放 locks；client 选择是否 retry。[00:33:17-00:36:05]

## Two-Phase Commit

### 角色与 failure-free timeline

```text
client
  |
transaction coordinator (TC)
  | messages tagged with TID
  +-------------------+
  v                   v
participant A         participant B
record x + Lx + log   record y + Ly + log
```

```text
TC                         A                         B
 |---- tentative put x --->| acquire Lx; log x      |
 |---- tentative put y ---------------------------->| acquire Ly; log y
 |---- PREPARE(TID) ------>|                         |
 |---- PREPARE(TID) -------------------------------->|
 |<-------- YES -----------|                         |
 |<-------- YES -------------------------------------|
 | durable decision=COMMIT |                         |
 |---- COMMIT(TID) ------->| install x; release Lx  |
 |---- COMMIT(TID) --------------------------------->| install y; release Ly
 |<--------- ACK ----------|                         |
 |<--------- ACK ------------------------------------|
```

[00:47:59-00:53:29]

Basic decision rule：

$$
decision=COMMIT \iff \bigwedge_{p\in Participants} vote_p=YES.
$$

任一 NO 导致 ABORT；participant 在 PREPARE 前可 NO/abort，但回复 YES 后只是进入 prepared，不立即 install，也不能再 unilateral abort。[00:54:07-00:56:20]

### Durable ordering

Participant 在发 YES 前：

$$
durable(prepared,TID,tentative\ data) \prec send(YES,TID).
$$

Coordinator 在发任何 COMMIT 前：

$$
durable(COMMIT,TID) \prec send(COMMIT,TID).
$$

[00:56:42-01:01:16]

第一条让 participant crash/restart 后仍记得 promise、tentative update 与 lock obligation；第二条让 TC 只通知 `A` 后 crash，restart 仍会向 `B` 重发同一个 decision。Tail Q&A 进一步确认 participant 也必须记住 `NO/ABORT(TID)`，因为 NO message 可能丢失，recovery 后要向 TC 重发一致 vote。[01:18:24-01:21:12]

### Failure-state table

| Failure / message state | Safe action | 原因与边界 |
| --- | --- | --- |
| Participant 尚未 YES，不能完成 | 回复 NO / unilateral abort | TC 尚不能合法形成 COMMIT |
| TC 未收齐 YES，PREPARE 无回复 | Timeout 后 ABORT | 尚未发送任何合法 COMMIT，可让 locks 释放 |
| Participant YES 后 crash/restart | 恢复 prepared state、tentative data 与 lock，query/wait TC | Promise 跨 crash 保留 |
| TC durable COMMIT 后 crash | Restart/recovered replica 重发 COMMIT | 某 participant 可能已 install |
| Participant YES、decision message 未到 | 持锁 block，不能自行 commit/abort | 既可能另一方已 commit，也可能另一方 NO |
| ABORT/NO reply 丢失后 participant crash | 从 durable `NO(TID)` 重发 NO | 不能 restart 后忘记或改变 vote |

## Blocking、availability 与部署域

Prepared `B` 只知道自己已 YES，却不知道 `A` 与 TC 的状态：

```text
World 1: A=YES; TC durable COMMIT; A 已 commit; 给 B 的 COMMIT 延迟
World 2: A=NO 或 TC 未 COMMIT; outcome 应 abort
```

在 World 1 abort 错，在 World 2 commit 错；本地没有 safe decision，所以 `B` 只能 query/wait TC，并持续持有 `Ly`。任何需要 `y` 的其他 transaction 都因此阻塞。这是 basic 2PC 的 blocking property，不是简单加短 timeout 就能消除。[01:05:57-01:07:31]

### Raft 与 2PC

| 维度 | Raft | 2PC |
| --- | --- | --- |
| Services 的工作 | Replicas 做同一件事 | Participants 操作不同 data/角色 |
| Progress condition | 同一 group 的 majority | Transaction 涉及的全部 logical participants |
| 课堂目标 | Replication / high availability | Atomic operation across servers |

可用 Raft group 实现 TC，也可复制各 participant service，再在这些 logical services 之间运行 2PC。Raft 降低单 replica crash 引发的 unavailable interval，却不把 “所有 shards 都要同意” 改成 “任意多数 shards 同意”。[01:07:46-01:13:33]

### Deployment boundary

- Cross-organization travel/hotel booking 中，一方 failure 会使另一方等待，且 organizations 彼此不一定信任；老师以此解释 2PC 的 negative reputation。
- Single-organization sharded data center 有共同 administration 与 recovery control，2PC 在这里 widely used。
- 课堂没有给出 cross-organization replacement protocol，也没有展开 presumed-commit variation；不能以 external Chapter 9 内容填补。[01:16:31-01:19:45]

1. **把 ACID Atomic 当成 concurrent visibility。** 老师现场纠正：crash/recovery all-or-none 是 Atomic；transaction 间不见 intermediate results 是 Isolated。[00:09:58-00:11:40]

3. **混用 transcript 与 handout 的 transfer signs。** 前者是 `9,11`，后者是 `11,9`；结构相同、数字不可拼接。

# 第 1 段：从跨分片原子操作到事务接口与 ACID

> 时间范围：`00:00:01-00:09:58`
>
> 证据范围：本段 transcript；课堂讲义 `l-2pc.txt` p.1 中的 topics、sharded-data 问题、bank-transfer 例子、transaction API、abort 与 ACID 提纲。[课件: l-2pc.txt p.1]

## 本段在整讲中的作用

本段先说明这是一堂 transactions 教程，而不是对单一系统论文的分析；其目的，是为随后两篇默认读者已熟悉 transactions 的论文补齐背景。老师随即把整讲问题压缩为 **cross-machine atomic operations**：数据按 key 分散在不同 servers 时，怎样让一个 client 的多个操作面对 failures 与 concurrency 仍表现为一个整体。由这个问题依次引出 transaction boundary、`commit`、`abort`，并在段末开始用 ACID 命名所需保证。[00:00:01-00:09:58] [课件: l-2pc.txt p.1]

老师在开头特别区分两个容易混淆的术语：two-phase locking（2PL）与 two-phase commit（2PC）虽然都叫 “two-phase”，但解决的是不同问题；本段只预告它们，尚未进入协议步骤。[00:00:43-00:01:47]

## 教学展开

1. **先交代本讲为何采用 tutorial 形式。** 接下来的两篇论文包含很多内容，并假定学生知道 transactions，尤其是 2PL 与 2PC。因此本讲先建立概念工具，而不是研究某一个系统如何实现它们。[00:00:06-00:01:10]
2. **立即消除名称造成的误解。** 2PL 与 2PC 都常出现在 transaction systems 中，但二者本身“相当不相关”，不能因为都带 two-phase 就把机制或职责混为一谈。老师此时只给预警，没有定义各自阶段。[00:01:14-00:01:47]
3. **把目标具体化为跨机器操作。** 假设一个 sharded key/value service：`x` 在 `KV1`，`y` 在 `KV2`。Client 要从账户 `x` 转出 1 美元并向 `y` 转入 1 美元，即对不同 shards 发出 `add(x, -1)` 与 `add(y, +1)`。[00:01:50-00:03:35] [课件: l-2pc.txt p.1]
4. **从两类干扰说明“整体”意味着什么。** 面对 failure，如果一个 server 在完成自己的 update 后另一边失败，期望结果是两个操作都发生或都不发生；面对 concurrency，另一个 client 不应看到 `x` 已扣款而 `y` 尚未入账的 intermediate state。[00:03:35-00:04:36]
5. **引入数据库给出的传统方案：transactions。** Programmer 用 `begin_xaction` 标出开始，在其中执行多个 reads/writes，并用 `commit` 标出成功结束。系统负责让这组操作相对于 concurrency 与 failure 表现为一个整体。[00:04:48-00:06:06] [课件: l-2pc.txt p.1]
6. **增加第二个 transaction，为后面的 serializability 做准备。** `T1` 执行 transfer；`T2` 依次读取 `x`、`y` 并打印。引入 `T2` 的目的不是添加业务逻辑，而是让课堂随后能够枚举 concurrent schedule 的合法与非法 outcomes。[00:06:07-00:07:00]
7. **强调 transaction abstraction 对 programmer 的价值。** Programmer 只标出 begin/end，system 自动处理 locking 与 recovery；同一抽象既适用于 distributed shards，也适用于 single-machine 或 multicore database。[00:07:04-00:08:10]
8. **补齐 `abort` 接口。** 若 `T1` 发现余额不足，可以主动 `abort`；即便此前已经执行部分 `put`，这些 writes 也应全部取消。System 也能强制 abort，例如后文将看到的 deadlock handling；被 abort 的 transaction 之后可能 retry。[00:08:14-00:09:32] [课件: l-2pc.txt p.1]
9. **以 ACID 作为下一段入口。** 老师总结三个关键接口是 `begin_xaction`、`commit`、`abort`，然后说 transaction semantics 通常由 ACID 四个字母概括。本段到 `Atomic` 一词处结束，四项的准确区分留到下一段，不能把此前口语中的 broad “atomic” 直接当作最终定义。[00:09:32-00:09:58]

## 概念、符号与推导

### 本段系统模型

```text
client / transaction
        |                    |
  add(x, -1)           add(y, +1)
        |                    |
KV server 1             KV server 2
   owns x                  owns y
```

- **Sharding：** Records/keys 分布在多台 servers；本例固定 `x` 与 `y` 位于不同 shards，因此 transfer 不是单机上的一次 update。[00:02:26-00:02:56]
- **Cross-machine atomic operation：** 一次应用动作包含多个跨 shard operations；系统要隐藏 partial failure 与 concurrent observation，使应用不必自己处理每一种 interleaving。[00:02:02-00:04:58]
- **Transaction boundary：** `begin_xaction` 声明一组 operations 的开始；`commit` 请求让整组结果成立；`abort` 取消整组结果。课堂此处使用的是概念 API，不是在规定某个具体数据库的函数签名。[00:05:10-00:06:06] [00:08:14-00:09:32]
- **`T1`：** Transfer transaction，逻辑效果为 `x := x - 1`、`y := y + 1`。
- **`T2`：** Audit/inspection transaction，读取 `x` 与 `y` 后打印；它让并发执行是否暴露 intermediate result 成为可观察问题。[00:06:07-00:07:00]

### 保证需求的推导

```text
x、y 分属不同 servers
  -> 一个业务动作需要多次独立 RPC/update
  -> 任一 server/client 可能在中途失败，其他 transaction 也可能交错读取
  -> 应用可能看到或留下 partial result
  -> 用 transaction 把 operations 组成一个逻辑整体
  -> commit 使整体成立；abort 使此前 tentative work 整体不成立
```

本段无公式推导。这里建立的是问题与 abstraction 的因果链；ACID 各字母、serializability、2PL 和 2PC 的正式定义均尚未完成。

## 例子与课堂提示

- **跨银行/跨 shard transfer** [00:02:26-00:04:36]：服务于 failure 与 concurrency 两条问题线。只更新一边会丢钱或造钱；并发 reader 在两个 updates 之间读取，会看到暂态。
- **读取并打印两个余额的 `T2`** [00:06:07-00:07:00]：服务于后续“哪些 outcomes 合法”的判断。它把抽象的 isolation 问题变成具体输出。
- **余额不足时主动 abort** [00:08:27-00:09:08]：说明 abort 不只由 crash 触发，也可以是 application decision；已经执行到一半仍不能留下 partial writes。
- **Deadlock 时系统强制 abort** [00:09:10-00:09:27]：这是后文 concurrency control 的预告。本段没有讲 deadlock detection 算法，只说明 abort 可被 system 用来让另一个 transaction 继续。
- **课堂提示：不要混淆 2PL 与 2PC。** 从本讲标题容易把两者当作同一协议的两个版本；老师明确说它们处理不同问题，详细职责要随课堂顺序分别建立。[00:01:14-00:01:47]
- **课堂提示：本段的 “atomic” 是宽泛目标。** 老师多次用它概括“面对 failures 与 concurrency 的整体效果”，但下一段会当场纠正 ACID 中 Atomic 与 Isolated 的边界；复习时应采用纠正后的术语。[00:03:35-00:06:06] [00:09:42-00:09:58]

# 第 2 段：ACID 边界、serializability 定义与非法执行

> 时间范围：`00:09:58-00:19:58`
>
> 证据范围：仅本段 transcript。Section prompt 明确标记为 transcript-only；本段不虚构课件页码。

## 本段在整讲中的作用

上一段用 broad “atomic” 描述 transaction 对 failures 与 concurrency 的整体效果，本段一开始老师就亲自纠正这个混用：ACID 中 **Atomic** 专指面对 crash/recovery 时 all writes or none；多个 transactions 不观察彼此中间状态属于 **Isolated**。完成 ACID 快速定位后，老师把本讲缩到 `A + I` 两条主线，并先为 `I` 建立可检验的正确性标准 **serializability**。[00:09:58-00:13:52]

随后老师不靠抽象口号，而是用 transfer transaction `T1` 与 audit transaction `T2` 枚举两个合法 serial outcomes，再让学生逐个判断两种 concurrent interleavings。核心方法是：不问执行过程“看起来是否合理”，只问其数据库最终状态与输出能否由某个 serial order 同时产生。[00:13:58-00:19:58]

## 教学展开

1. **老师先说错，再明确纠正 Atomicity。** 他起初把“另一个 transaction 要么看到全部 puts，要么一个也看不到”称为 Atomic，随即在 `00:10:21` 明确说前述说法不对。纠正后的 Atomic 是 crash-recovery 属性：transaction 中途 crash 时，多项 writes 要么都到 stable storage/都可见，要么都不成立。[00:09:58-00:10:46]
2. **快速定位 Consistency。** `C` 指 transaction 应维持 database/application 的 invariants，老师以 referential integrity 为例；但他明确说今天基本不讨论这一项。因此不能把本讲后续的 protocol 当作自动证明任意业务 invariant 的机制。[00:10:49-00:11:13]
3. **把此前误放在 Atomic 下的内容归入 Isolation。** `I` 处理多个 concurrent transactions 的相互观察：一个 transaction 不应看到另一个 transaction 的 intermediate results。这里的 all-or-nothing 是“相对于另一 transaction 的可见性”，不是 crash 后 durable state 的 all-or-nothing。[00:11:15-00:11:40]
4. **说明 Durability。** `D` 表示一旦 transaction commits，其结果写入 stable storage；system crash/restart 后，latest committed transactions 仍被记录。[00:11:44-00:12:01]
5. **划定本讲范围并选择讲解顺序。** 老师将重点放在 `A` 与 `I`：先讲 `I` 的正确含义，再讲 `A`。这对应整讲后续的 concurrency control/2PL 与 atomic commit/2PC 两部分。[00:12:22-00:12:36]
6. **定义 serializability。** 多个 transactions 可以实际并发执行；若存在一个逐个执行的 serial order，使该 order 产生与实际 concurrent execution 相同的 outcome，则实际结果合法。Outcome 同时包括 database changes 与程序输出，不能只比较最终余额。[00:12:44-00:13:52]
7. **枚举 transfer/audit 的合法结果。** 课堂口述采用 `x = 10, y = 10`，`T1` 将 1 从 `x` 移到 `y`，所以最终余额为 `x = 9, y = 11`。若 `T1; T2`，audit 打印 `9,11`；若 `T2; T1`，audit 打印 `10,10`，随后数据库仍结束于 `9,11`。这两种结果都合法，其他组合不合法。[00:13:58-00:15:23]
8. **与 linearizability 比较。** 两者都要求结果仿佛来自某个 total/serial order；老师指出 linearizability 还约束 real-time order，而本段给出的 serializability 定义不要求按 wall-clock 先后排序。因此在本讲表述中，serializability 比 linearizability 稍弱，但仍给 programmer 一个“按某个串行顺序思考”的方便模型。[00:15:28-00:16:31]
9. **检查第一种非法 interleaving。** `T2` 先读到 transfer 前的 `x = 10`，`T1` 完成 transfer，`T2` 再读到 transfer 后的 `y = 11`，于是打印 `10,11`。该输出既不是 `T1; T2` 的 `9,11`，也不是 `T2; T1` 的 `10,10`，故不 serializable。[00:16:44-00:18:18]
10. **检查第二种非法 interleaving。** `T1` 先更新 `x`，`T2` 在 `y` 尚未更新前读取两者，再由 `T1` 更新 `y`。Audit 会观察 partial transfer；这个结果同样无法由两个 serial orders 中任一个产生，所以 transaction system 必须禁止该 schedule。[00:18:20-00:19:44]
11. **以 programmer model 收束。** Serializability 排除的正是那些迫使 programmer 推理任意 operation interleavings 的 executions；下一段由此转入如何实施这种禁止，即 concurrency control。[00:19:44-00:19:58]

## 概念、符号与推导

### ACID 在本讲中的边界

| 属性 | 老师在本段给出的含义 | 本讲处理程度 |
| --- | --- | --- |
| Atomic | 面对 crash/recovery，多项 writes 全部成立或全部不成立 | 后半讲用 atomic commit / 2PC 处理 |
| Consistent | Transaction 保持 application/database invariants，如 referential integrity | 明确不作为今天重点 |
| Isolated | Concurrent transactions 不观察彼此 intermediate results | 前半讲用 serializability / 2PL 处理 |
| Durable | Committed results 已在 stable storage，crash 后仍存在 | 作为恢复与 logging 的必要背景 |

[00:09:58-00:12:36]

### Serializability 判定

令 $Outcome(E)$ 同时包含 execution $E$ 的数据库 changes 与输出。Concurrent execution $E_c$ 合法，当且仅当存在 transactions 的某个 serial permutation $S$，满足：

$$
\exists S:\quad Outcome(E_c) = Outcome(S).
$$

这是对老师口头定义的符号化，不增加新的 protocol 条件。[00:12:44-00:13:52]

### 本段两个合法 serial outcomes

| Serial order | `T2` 的打印 | 最终 database state |
| --- | --- | --- |
| `T1; T2` | `9,11` | `x = 9, y = 11` |
| `T2; T1` | `10,10` | `x = 9, y = 11` |

[00:13:58-00:15:23]

因此，打印 `10,11` 或 `9,10` 都暴露了 transfer 的一半；即使最终 database 最后回到 `9,11`，output 已经使整个 outcome 无法匹配任一 serial order。[00:16:44-00:19:44]

## 例子与课堂提示

- **老师对 Atomic/Isolated 的现场纠正** [00:09:58-00:11:40]：这是本段最重要的术语证据。笔记采用纠正后的定义，不把老师 `00:10:21` 前的临时说法当成结论。
- **Referential integrity** [00:10:49-00:11:13]：仅用来说明 Consistency 是 application/database invariant；课堂没有展开 constraint checking 或实现机制。
- **Transfer + audit** [00:13:58-00:19:44]：这个例子服务于 isolation/serializability，而不是单独证明 durability。判断时必须同时比较 audit output 与最终 balances。
- **Serializability 与 linearizability** [00:15:28-00:16:31]：相似点是都寻找看似串行的 order；本讲强调的差异是前者没有 real-time requirement。不要由此补入课堂未讲的其他形式化历史条件。
- **课堂口述与 `l-2pc.txt` 的符号方向不同。** 本段 transcript 的 transfer 是 `x -= 1, y += 1`，合法结果为 `9,11`；讲义 p.1 写的是 `add(x, 1), add(y, -1)`，合法结果为 `11,9`。二者结构完全相同但方向相反。本段按口述 chronology 使用 `9,11`，不静默改成讲义数值。

# 第 3 段：concurrency control 两条路线与 two-phase locking

> 时间范围：`00:19:58-00:29:57`
>
> 证据范围：仅本段 transcript。Section prompt 明确标记为 transcript-only；本段不虚构课件页码。

## 本段在整讲中的作用

上一段用 serializability 指定了哪些 concurrent outcomes 合法，本段开始回答“系统怎样禁止非法 schedules”。老师先把 concurrency control 分成 pessimistic 与 optimistic 两类，再把当天范围收窄到 pessimistic 的 two-phase locking（2PL）。随后用两条规则定义课堂采用的 2PL，并通过一个 early-unlock 反例解释为什么 locks 必须一直持有到 commit/abort。[00:19:58-00:29:57]

本段同时建立了整讲的重要职责边界：2PL 负责 isolation/serializability；后续 2PC 将负责 failures 下的 atomic commit。二者可以在同一个 transaction system 中配合，但本段只讲前者。[00:19:58-00:24:02]

## 教学展开

1. **给“禁止非法执行”命名。** 为使实际并发结果仍然 serializable，系统必须排除某些 operation interleavings；完成这一工作的机制总称为 concurrency control。[00:19:58-00:20:08]
2. **先讲 pessimistic approach。** Transaction 在运行时先获得维持 serializability 所需的 locks，冲突 transaction 不能直接继续，只能等到相应 lock 可以安全释放。它把潜在冲突当作会发生，先请求 permission 再操作。[00:20:22-00:20:59] [00:22:34-00:22:53]
3. **再讲 optimistic approach。** Transaction 不先锁 records，而是先执行，到 commit point 再检查过去的 reads/writes 是否能对应一个 serializable execution；能则 commit，不能则 abort，通常再 retry。老师口述先说了一次 linearizable，随即改为 serializable，应以后者为准。[00:21:03-00:22:05]
4. **把 OCC 留给后续 FaRM。** 老师只预告接下来一到两周后的 FaRM 会展示 optimistic distributed transaction system；当天重点是 pessimistic concurrency control。[00:22:06-00:22:29]
5. **说明 isolation level 与 concurrency 的取舍。** 两大类内部都有很多方案；database 往往提供多个 isolation levels，让 programmer 用较弱保证换更高 concurrency。本讲不沿这条支线展开，而是坚持老师称作 gold standard 的 serializability。[00:23:05-00:24:02]
6. **引出 2PL 的每-record lock。** 每个 database record 有自己的 lock；在账户例子中即 `Lx` 与 `Ly`。老师此处为简化只用 lock-per-record 的思路，没有在本段引入 shared/read 与 exclusive/write lock 的区分。[00:24:02-00:24:34]
7. **给出第一条规则：use 前 acquire。** Transaction 在第一次 read/write 某 record 前必须先取得其 lock，transaction system 自动完成 acquisition，而非要求 application 在代码中显式 lock。[00:24:34-00:25:03]
8. **给出第二条规则：持有到终点。** 一旦取得 lock，transaction 在 commit 或 abort 前不得释放。`T1` 若先锁 `x` 再锁 `y`，同时开始的 `T2` 试图锁 `x` 时必须等待，直到 `T1` 完整结束。[00:25:03-00:25:58]
9. **与 simple/strict locking 比较。** Simple locking 要求 transaction 开始时一次取得将用到的全部 locks，并持有到结束；2PL 则随执行按需增量取得。这使 transaction 不必预先声明所有可能访问的 records，并可允许 simple locking 禁止的某些 concurrency patterns。[00:26:01-00:26:41]
10. **用 early release 反证第二条规则。** 假设 `T1` 更新 `x` 后立即释放 `Lx`，尚未更新 `y`；此时 `T2` 可锁住并读取 `x`、`y`，恰好插入 `T1` 两个 puts 之间，观察 partial transfer。上一段已证明这种 output 不 serializable。[00:26:47-00:29:09]
11. **推广到 lock-set intersection。** 当两个 transactions 的 lock sets 相交时，需要通过 lock 持有顺序建立一致 ordering；若在 commit 前释放，可能暴露 intermediate result，甚至让别人读到后来因 abort 消失的 tentative value。本段在这个结论即将说完处结束。[00:29:12-00:29:57]

## 概念、符号与推导

### 两类 concurrency control

| 路线 | 操作前 | Commit 时 | 冲突后果 |
| --- | --- | --- | --- |
| Pessimistic | 先 acquire 必要 locks | 按协议释放 locks | 等待；后段会出现 deadlock/abort |
| Optimistic / OCC | 不先锁，直接执行 | 验证结果能否 serializable | 验证失败则 abort，可能 retry |

[00:20:22-00:22:29]

老师在本段没有给出 conflict rate 与性能的定量公式，也没有展开 OCC validation algorithm；这些不能从常识补入。

### 本讲采用的 2PL 规则

对 transaction $T$ 与 record $r$：

1. $T$ 在第一次使用 $r$ 前必须持有 $L_r$。
2. $T$ 已取得的任何 $L_r$，都保持到 $T$ 的 `commit` 或 `abort`。

课堂执行形态可以写成：

```text
begin T
  acquire Lx -> use x
  acquire Ly -> use y
  ... keep Lx and Ly ...
commit/abort T
  release Lx, Ly
```

[00:24:15-00:25:58]

### 为什么 early unlock 破坏 serializability

```text
T1: acquire Lx; put(x); release Lx
T2: acquire Lx; get(x); acquire Ly; get(y); commit
T1: acquire Ly; put(y); commit
```

`T2` 读到 `T1` 更新后的 `x` 与更新前的 `y`。该 output 不等于 `T1; T2`，也不等于 `T2; T1`，所以无法映射到 serial order。[00:27:03-00:29:09]

此外，若 `T1` 暴露 `x` 后最终 abort，`T2` 已使用一个逻辑上从未 commit 的值；老师在段尾只简要指出这种风险，尚未展开 cascading abort。[00:29:39-00:29:57]

## 例子与课堂提示

- **“先请求 permission，还是先做后道歉”** [00:22:34-00:23:02]：老师用这句类比区分 pessimistic 与 optimistic；它说明时机差异，不是 protocol 的形式化定义。
- **FaRM 预告** [00:22:06-00:22:29]：服务于课程导航。今天不讲 OCC 内部 machinery，因此不能把后课内容倒灌到当前 chronology。

- **`T1` 先得 `Lx`，`T2` 等待** [00:25:20-00:25:58]：服务于 2PL 如何把 overlap 变成 transaction order。等待不是 failure，也不意味着 `T2` abort。
- **Early-release 反例** [00:27:03-00:29:09]：服务于第二条规则。问题不在于 lock 最终有没有释放，而在于 release 发生在 transaction outcome 确定之前。
- **课堂术语边界。** 老师把“开始前拿全部 locks”称为 simple locking/strict locking，把本段按需增量 acquire 的方案称为 2-phase locking。复习时应沿用本讲定义，不把外部教材对 strict 2PL 的命名反向覆盖课堂 chronology。

# 第 4 段：2PL deadlock、wait-for graph 与 simple locking 取舍

> 时间范围：`00:29:59-00:37:36`
>
> 证据范围：仅本段 transcript。Section prompt 明确标记为 transcript-only；本段不虚构课件页码。

## 本段在整讲中的作用

本段完成 2PL 的课堂主线。上一段证明 locks 必须持有到 transaction end，本段马上承认由此产生的代价：transactions 按需取得多个 locks 时可能形成 deadlock。老师先构造 `T1` 与反向访问的 `T2'`，再给出 timeout 与 wait-for graph 两类 detection 方法，并利用 transaction 自带的 `abort` 解除循环等待。最后，他把 2PL 与一次性预锁全部 records 的 simple/strict locking 对比，布置 breakout 问题：找出 2PL 能利用、simple locking 却禁止的 concurrency。[00:29:59-00:37:36]

这也是整讲 isolation/concurrency-control 部分的收束。`00:37:36-00:44:07` 是 breakout-room 与恢复课堂的间隔，当前 prompt 没有该区间的技术 transcript；下一段从 breakout 答案和 lock-mode Q&A 接回，再转入 2PC。[00:37:07-00:37:36]

## 教学展开

1. **承接 hold-to-end 结论并提出明显问题。** 因为 2PL 允许 transaction 随执行逐步 acquire locks，很多学生已经问到是否会 deadlock；老师明确回答“完全会”。[00:29:59-00:30:22]
2. **通过相反访问顺序构造 deadlock。** 保持 `T1` 先写 `x`、后写 `y`，把 audit 改成 `T2'`：先读 `y`、后读 `x`。于是 `T1` 先取得 `Lx`，`T2'` 先取得 `Ly`。[00:30:22-00:31:18]
3. **形成循环等待。** `T1` 接下来请求 `Ly`，但它由 `T2'` 持有，只能 wait；`T2'` 接下来请求 `Lx`，但它由 `T1` 持有，也只能 wait。二者都必须 hold 已得 lock 到 transaction end，又都无法继续到 end，deadlock 成立。[00:31:18-00:32:04]
4. **用 abort 解除 deadlock。** Transaction system 若能检测到该状态，就 abort 其中一个 transaction，释放其 locks，让另一个继续并 commit。被 abort 的 transaction 由 client/application 决定是否稍后 retry；retry 是可能策略，不是 system 保证一定成功。[00:32:09-00:32:37]
5. **指出 2PL 的局部 optimistic 味道。** 2PL 本身是 pessimistic locking，但按需取得 locks 并不保证执行途中永远无冲突；遇到 deadlock 后可以 abort/recover。老师只是用“有一点 optimistic flavor”描述这一点，并未把 2PL 重新分类为 OCC。[00:32:42-00:32:56]
6. **回答“怎样找到 deadlock”。** 第一种方法是 timeout：transaction 长时间无 forward progress 就 abort。老师说这种方法“不那么扎实”；第二种更系统的方法是动态构造 wait-for graph。[00:33:03-00:33:45]
7. **定义 wait-for graph。** Graph nodes 是 transactions；若 `T1` 请求的 lock 正由 `T2'` 持有，则添加 `T1 -> T2'`，表示前者等待后者。反向 lock conflict 添加 `T2' -> T1`。Graph 中出现 cycle 表示一组 transactions 互相等待，system 可选一个 victim abort。[00:33:45-00:35:03]
8. **沿 abort 后状态继续。** 若 abort `T2'`，system 确保其结果不可见并释放 `Ly`；`T1` 随后获得 `Ly`、完成 transfer。调用 `T2'` 的 client 收到 abort，再决定是否重跑。[00:35:13-00:36:05]
9. **回到 2PL 与 simple locking 的 homework question。** Simple/strict locking 要求 transaction 一开始声明并取得全部 locks；它不易因 acquisition order 形成这种 deadlock，但 programmer 必须预先声明 access set。2PL 原则上允许更多 concurrency，却可能需要 deadlock abort。[00:36:11-00:37:07]
10. **进入 breakout。** 老师要求学生构造一个 simple locking 排除、2PL 却能执行的并发例子，然后开始约五分钟 breakout rooms。本段在技术讨论暂停处结束。[00:37:07-00:37:36]

## 概念、符号与推导

### Deadlock schedule

```text
T1                                  T2'
acquire Lx                          acquire Ly
put(x)                              get(y)
request Ly -> wait for T2'          request Lx -> wait for T1
        \________________ cycle ________________/
```

成立条件来自本讲 2PL 规则：`T1` 等待 `Ly` 时不能先释放 `Lx`，`T2'` 等待 `Lx` 时也不能先释放 `Ly`。[00:30:22-00:32:04]

### Wait-for graph

令 transaction 为 vertex。若 $T_i$ 正等待一个由 $T_j$ 持有的 lock，则加入 directed edge：

$$
T_i \rightarrow T_j.
$$

本例为：

$$
T_1 \rightarrow T_2', \qquad T_2' \rightarrow T_1.
$$

存在 directed cycle，故发生 deadlock；abort cycle 中任一 transaction 并释放其 locks，可打破当前循环。[00:33:45-00:35:03]

### 两种 detection 方法

| 方法 | 课堂做法 | 边界 |
| --- | --- | --- |
| Timeout | 长时间无 progress 时挑一个 transaction abort | 老师称其不够系统；慢不必然等于 deadlock |
| Wait-for graph | 跟踪谁等待谁，cycle 时判定 deadlock | 需要 transaction system 动态维护依赖关系 |

[00:33:17-00:35:03]

本段无其他公式推导。老师没有规定 victim selection、distributed graph construction、timeout 长度或 retry backoff 算法。

## 例子与课堂提示

- **`T2` 改为 `T2'` 并反向读取** [00:30:22-00:32:04]：只改变 access order 就从普通等待变成 deadlock，说明 multiple-lock ordering 是关键，而不是 transfer 业务本身有错。
- **Abort `T2'`** [00:35:13-00:36:05]：服务于 transaction abstraction 的恢复能力。Abort 要同时撤销其 visible effects 与释放 locks；仅杀掉执行线程而保留 lock 不足以解除 deadlock。
- **2PL 的 “optimistic flavor”** [00:32:42-00:32:56]：只是说它允许先运行、遇到 deadlock 再 abort，不应与前一段“不加锁、commit 时 validation”的 OCC 混淆。
- **Simple locking 的 tradeoff** [00:36:11-00:37:07]：预先拿全 locks 避免渐进 acquisition 的循环等待，但要求事先知道完整 access set，并可能过早阻塞其他 transactions。
- **Breakout question** [00:37:07-00:37:36]：要求的是“2PL 比 simple locking 多出 concurrency 的具体情况”，不是要求证明 2PL 在所有 workloads 都更快。

   **答：** `T1` 持有 `Lx` 等 `Ly`，`T2'` 持有 `Ly` 等 `Lx`；二者互相等待，且 2PL 禁止它们提前释放已有 locks。[00:30:22-00:32:04]

# 第 5 段：从 lock Q&A 转入 two-phase commit 正常路径

> 时间范围：`00:44:07-00:54:07`
>

## 本段在整讲中的作用

本段先收回 breakout 的两个尾问题：exclusive-only 简化下 locks 与 commit/abort point 对齐，而 read/write locks 可能允许受限的 early read-lock release；2PL 相比 simple locking 的清晰例子，是 transaction 只有在某个少见条件成立时才访问额外 record，因此无需一开始就锁住它。随后老师明确结束第一主题并进入整讲第二主题 **two-phase commit（2PC）**，把关注点从 concurrency/serializability 切换到 crashes 下的 atomic commit。[00:44:07-00:46:54]

2PC 部分先只处理无 failure 的 straightforward path：coordinator 驱动 transfer，participants `A`、`B` 各管理自己的 shard record 与 lock，updates 暂存于 log；PREPARE 阶段收集 votes，decision 阶段发送 COMMIT 或 ABORT。本段完整讲完全体 YES 的 commit path，并在结尾开始引入 `B` 返回 NO 的 abort path。[00:47:27-00:54:07]

## 概念、符号与推导

### 角色与本地职责

```text
client
  |
  v
transaction coordinator (TC)
  | PREPARE/decision messages tagged TID
  +-------------------+
  v                   v
participant A         participant B
```

- **Coordinator/TC：** 推进 transaction、收集全部 votes、作出单一 commit/abort decision。[00:47:59-00:48:45]

### 无 failure 的 2PC timeline

```text
TC                         A                         B
 |---- tentative put x --->| acquire Lx; log x      |
 |---- tentative put y ---------------------------->| acquire Ly; log y
 |---- PREPARE(TID) ------>|                         |
 |---- PREPARE(TID) -------------------------------->|
 |<-------- YES -----------|                         |
 |<-------- YES -------------------------------------|
 | decision = COMMIT       |                         |
 |---- COMMIT(TID) ------->| install x; release Lx  |
 |---- COMMIT(TID) --------------------------------->| install y; release Ly
 |<--------- ACK ----------|                         |
 |<--------- ACK ------------------------------------|
```

[00:48:45-00:52:58]

决策规则在本段可写为：

$$
decision = COMMIT \iff \bigwedge_{p \in Participants} vote_p = YES.
$$

若任一 participant 不是 YES，则不能走本段的 commit path；ABORT 的完整路径在下一段展开。[00:51:27-00:54:07]

# 第 6 段：2PC votes、持久化恢复状态与 coordinator crash

> 时间范围：`00:54:07-01:04:06`
>
> 证据范围：仅本段 transcript。Section prompt 明确标记为 transcript-only；本段不虚构课件页码。

## 本段在整讲中的作用

上一段给出无 failure 的 all-YES commit path，本段先补全 NO vote 导致的 ABORT，再逐个插入 crashes，推导 2PC 为什么必须 logging/persist state。老师用两个对称问题建立恢复规则：participant `B` 在 YES 后 crash，必须记住自己的 prepared promise、tentative data 与 lock obligation；coordinator 在可能已向某 participant 发 COMMIT 后 crash，必须记住全局 COMMIT decision 并在恢复后继续通知。最后再对比尚未收到全部 YES 的情况：此时 commit decision 不可能已经成立，coordinator 可以 timeout/abort。[00:54:07-01:04:06]

本段的核心不是“crash 一律 abort”，而是 **能否安全单方面改变 decision 取决于 crash 前已持久化、已发送的状态**。尤其 participant 一旦回复 YES，就失去 unilateral abort 权利；否则另一 participant 可能已经依 coordinator 的 COMMIT 安装结果，破坏 atomicity。[00:55:02-01:02:08]

## 教学展开

1. **先完成 NO vote path。** Coordinator 收到 `A = YES, B = NO` 时，所有 participants 没有共同同意，所以不能 commit；它决定 abort，并向 `A`、`B` 发 ABORT，让两边终止 transaction。顶层 transaction 只有所有 participants 都同意才能 commit。[00:54:07-00:54:38]
2. **学生追问 YES 后能否反悔。** 老师明确回答不能：participant 在 PREPARE 前可以 unilateral abort；一旦回复 YES，就是 promise to be ready to commit，必须等 coordinator 的 decision，不能因后来想 abort 而退出。[00:55:02-00:55:41]
3. **把 deadlock 与 vote 时机对齐。** 若 participant 尚未取得 transaction 所需 locks，deadlock 应在 PREPARE/YES 前暴露并处理。能回复 YES 意味着它已经具备继续 commit 的本地条件并仍持有 locks，因此不能把 deadlock 当作 YES 后反悔的理由。[00:55:45-00:56:20]
4. **插入 participant-after-YES crash。** `B` 回复 YES 后立即 crash。课堂先否定“因此整个 transaction 必须 abort”：`B` 已作 promise，coordinator 可能在 crash 同时继续形成 COMMIT decision，故 `B` recovery 后仍必须能履约。[00:56:23-00:57:51]
5. **推导 participant persistent state。** `B` 必须在 stable storage 记住自己对该 TID 处于 prepared、对应 tentative update，以及仍须持有 `Ly`。Restart 时先查看是否有 in-progress distributed transaction，恢复 prepared/lock state，然后等 coordinator retry COMMIT；收到后 install `y` 并完成。[00:57:51-00:59:04]
6. **指出持久化成本。** 2PC 不仅有多轮 messages，participant 还必须写 stable storage。老师用约 1 ms 的 optimistic 写延迟粗略说明单条串行 durable path 会受约 1000 transactions/s 量级限制；这是课堂直觉估算，不是系统 benchmark。[00:59:06-00:59:45]
7. **插入 coordinator crash。** 假设 coordinator 收齐 PREPARE votes，可能已向 `A` 发 COMMIT，却在通知 `B` 前 crash。此时它必须在发出 COMMIT 前把 `COMMIT(TID)` 写入 stable storage；restart 后读取 decision，继续/重发，直到 `A` 与 `B` 都完成。[00:59:48-01:01:16]
8. **从 participant uncertainty 解释不能自行 abort。** `B` 只知道自己 YES、尚未收到 decision；它不知道 `A` 是否已经收到 COMMIT 并安装。若 `B` 自行 abort，可能形成 `A` commit、`B` abort 的 split outcome。因此必须等待 coordinator recovery 告知原 decision。[01:01:16-01:02:08]
9. **对比 PREPARE 没送达/没有 YES 的情况。** 若 coordinator 的 PREPARE 没有到达某 participant，也未取得该方 YES，则 global COMMIT 不可能形成；coordinator 可 unilateral abort，通知已知 participant 释放 locks。将来 participant 查询时，coordinator 没有 COMMIT record 就回答 abort。[01:02:13-01:03:30]
10. **以 recovery query 接到下一段。** 学生追问 ABORT message 丢失且 participant crash/restart 怎么办；老师开始回答 participant 知道 coordinator 身份，可主动 ping/query transaction outcome。本 prompt 在答案中间结束，下一段从 query 继续。[01:03:41-01:04:06]

## 概念、符号与推导

### Vote 后的状态边界

```text
before YES
  participant may say NO / abort unilaterally
       |
       | persist prepared state + tentative data, retain locks
       v
after YES (prepared)
  participant may neither commit nor abort unilaterally
  it must follow the coordinator's durable decision
```

[00:55:02-00:59:04]

### Participant durability rule

在发送 `YES(TID)` **之前**，participant 必须让 recovery 所需状态 durable：

$$
durable(prepared, TID, tentative\ update) \prec send(YES, TID).
$$

Lock ownership/obligation 必须跨 restart 恢复并保持到最终 COMMIT/ABORT，否则其他 transaction 可能在 decision 未定时访问同一 record。[00:57:51-00:59:18]

### Coordinator durability rule

在发送任何 `COMMIT(TID)` **之前**，coordinator 必须先持久化 decision：

$$
durable(COMMIT, TID) \prec send(COMMIT, TID).
$$

否则它可能只通知 `A` 后 crash，restart 却忘记 decision，无法让 `B` 与 `A` 收敛到相同 outcome。[01:00:07-01:02:08]

### 何时可安全 abort

| 已知状态 | Coordinator/participant 的安全动作 |
| --- | --- |
| Participant 尚未回复 YES | Participant 可 NO/abort |
| Coordinator 未收齐全部 YES，未作 COMMIT | Coordinator 可 timeout/abort |
| Participant 已回复 YES，decision 未知 | 不可自行 commit 或 abort；等待/query TC |
| Coordinator 已 durable COMMIT | Recovery 后必须继续发送 COMMIT |

[00:55:02-00:55:41] [01:00:42-01:03:30]

## 例子与课堂提示

- **Deadlock 必须在 YES 前解决** [00:55:45-00:56:20]：participant 若连必要 locks 都拿不到，就不应回复 prepared YES；YES 后用 deadlock 作理由退出会破坏 promise。
- **`B` YES 后 crash** [00:56:42-00:59:04]：服务于 participant log。Crash/restart 不会抹掉协议义务；“重新启动后再看 coordinator 消息”也不足，必须知道自己此前是 YES 还是 NO。
- **Coordinator 只通知 `A` 后 crash** [01:00:07-01:02:08]：服务于 durable global decision。Participant 的 uncertainty 正来自它不知道别的 participant 已看到什么。
- **PREPARE 丢失** [01:02:13-01:03:30]：服务于 abort-safe boundary。没有某 participant 的 YES，coordinator 就不可能已合法 COMMIT，因此可以放弃并释放 locks。
- **1 ms / 1000 tx/s 粗算** [00:59:18-00:59:45]：老师用它说明同步 stable-storage writes 很贵；没有说明 batching、parallelism 或 hardware 参数，不能把该数当作 2PC 普遍性能上限。

# 第 7 段：prepared blocking、Raft 高可用与 2PC 职责边界

> 时间范围：`01:04:07-01:14:06`
>
> 证据范围：仅本段 transcript。Section prompt 明确标记为 transcript-only；本段不虚构课件页码。

## 本段在整讲中的作用

本段从 participant recovery 主动询问 coordinator 接回，先澄清 locks 存在于各 shard owner，而非额外假设一个跨服务器 global lock。随后老师返回最棘手情形：participant 已 YES、coordinator 在 decision 传播期间失联。由于 participant 无法分辨另一个 participant 已 commit、已 NO，还是也在等待，它只能继续持锁并 **block**。这给出 basic 2PC 的 availability 代价。[01:04:07-01:07:31]

老师接着调用课程前半的 Raft：把 coordinator（也可把 participants）做成 replicated state machine，可让单机 crash 不必长期阻塞。但他用多数派与“相同工作/不同工作”两组差异强调：Raft 与 2PC 不是替代关系。Raft 复制同一 service 以获得 high availability；2PC 协调存放不同 data、承担不同角色的所有 participants 共同完成 atomic operation。[01:07:46-01:13:33]

## 教学展开

1. **完成上一段的 recovery query。** Prepared participant 若没有收到最终 message，可以联系已知 coordinator，询问该 TID 的 outcome，而不是凭 timeout 自己改 decision。[01:04:07-01:04:16]
2. **确认 lock 的持续区间。** 学生问 `B` 是否从把 `y` 写入 log 一直持有 `Ly`，直到将 `y` install；老师回答是。也就是说 PREPARE/decision message exchanges 期间 lock 仍被占用。[01:04:24-01:04:43]
3. **澄清 sharded lock placement。** 当前 setup 中每个 record 只在一个 shard server：`A` 管理自己所有 records 的 locks，`B` 管理自己的。课堂不是在假设 `y` 同时复制到多机后再运行某个 global distributed-lock protocol；replication 是后面 Raft composition 的另一层。[01:04:44-01:05:23]
4. **重返 coordinator-after-decision crash。** `A`、`B` 都 YES，coordinator 在 commit point 后 crash；`A` 可能已经收到 COMMIT，`B` 未收到。`B` 已 promise，不能 unilateral abort，也不能知道能否 commit。[01:05:27-01:06:38]
5. **推导 blocking。** `B` 唯一安全动作是 wait，并继续持有 `Ly`；所有需要 `y` 的其他 transactions 也只能等待，直到 coordinator 恢复并宣布或重申 durable decision。老师明确把这称为 2PC 不理想之处：协议可能 block 到某台 machine 回来。[01:06:38-01:07:31]
6. **问实践中怎样降低该风险。** 学生提出把 coordinator 做成 fault tolerant；老师让其具体化为使用 Raft replicated state machine 实现 coordinator。一个 replica crash 时，其他 replicas 可继续提供 decision state。[01:07:46-01:08:55]
7. **联系 Lab 4。** 老师说 Lab 4 的 shard movement/rebalancing 使用类似 2PC 的 scheme，master/coordinator 与 shard servers 又分别由 Raft groups 复制；并行运行多个 Raft groups，使单点 crash 不必让整体长时间停止。[01:09:01-01:10:23]

9. **给出根本职责差异。** Raft replicas 都做相同的事情，组成 replicated state machine，目标是 high availability；2PC participants 操作不同 data，例如 `A` 操作 `x`、`B` 操作 `y`，目标是跨 servers 的 all-or-none atomic operation。[01:11:50-01:13:08]

## 概念、符号与推导

### 为什么 prepared participant 必须 block

Participant `B` 已发送 YES、尚未收到 decision 时，至少存在两种与本地观察一致的世界：

```text
World 1: A = YES; TC durable COMMIT; A 已 commit; 给 B 的消息延迟
World 2: A = NO 或 TC 尚未 COMMIT; global outcome 应 abort
```

- `B` 在 World 1 自行 abort，会与 `A` 分裂。
- `B` 在 World 2 自行 commit，也会与 `A`/TC 分裂。

因此本地没有安全 decision，只能 query/wait TC，并保持 lock。这不是 timeout 参数没调好，而是现有信息不足。[01:05:57-01:07:31]

### Lock 与 data placement

```text
shard A: records including x + their locks
shard B: records including y + their locks
```

本讲 basic setup 是 single owner per sharded record。2PL 的 lock management 分布在 records 所在 servers；2PC coordinator 跨这些 owners 收集 votes。[01:04:44-01:05:23]

### Raft 与 2PC

| 维度 | Raft | 2PC |
| --- | --- | --- |
| Participants 做什么 | Replicas 执行同一 replicated state machine | Participants 对不同 data/角色执行不同部分 |
| Progress 条件 | 依赖 majority 可用 | Atomic commit 需要所有 involved participants 能 YES |
| 课堂目标 | High availability via replication | Atomic operation across servers |
| 二者关系 | 可复制 TC/participants | 在 replicated services 之间协调 commit |

[01:10:31-01:13:33]

组合架构可表示为：

```text
Raft group implementing TC
          |
          | 2PC
     +----+----+
     |         |
Raft group A  Raft group B
shard x       shard y
```

Raft 减少单 replica crash 导致的 unavailable interval，但 2PC 仍要得到每个 logical participant service 的同意；复制没有把 “all participants” 改成 “任意 majority of shards”。[01:08:20-01:13:33]

- **Shard-local locks** [01:04:44-01:05:23]：老师限定的是 sharding，不是 replication。不要看到 “distributed transactions” 就假设每个 record 本身已有多副本。

- **Majority vs every participant** [01:11:25-01:11:38]：用于区分 availability model。Raft 的 majority 是同一 state machine replicas 中的多数；2PC 的 all 是业务 transaction 涉及的所有不同 participants。
- **Google/Microsoft papers 预告** [01:13:44-01:14:06]：只说明后续 systems 将依赖今天的 2PL/2PC 背景，且第二篇用 optimistic transactions；本段没有讲论文机制或名称。

## 概念、符号与推导

### 2PL 与 2PC 的组合方式

```text
transaction execution / concurrency control
  participant A: acquire Lx, make tentative x update
  participant B: acquire Ly, make tentative y update
                 (2PL or another CC scheme)
                           |
                           v
atomic decision across participants
  PREPARE -> votes -> COMMIT/ABORT
                 (2PC)
```

- **2PL correctness target：** Concurrent record access 的 isolation/serializability；单机 multicore 与 distributed transaction 都可能需要。[01:14:37-01:15:16]
- **2PC correctness target：** 不同 participants 是否全部执行各自部分；本讲语境是 distributed atomic commit。[01:15:21-01:16:28]
- **Independence：** 2PC 在 commit agreement 前需要 transaction 已达到可 prepare 状态，但从 2PC 角度，前面用 2PL 还是 simple locking 并非其核心规则。[01:15:39-01:16:23]

### Participant recovery record

对每个 `TID`，participant recovery 至少必须区分课堂强调的状态：

| Durable local state | Recovery / query response |
| --- | --- |
| `YES/PREPARED(TID)` | 保持 promise，等待或查询 coordinator 的 COMMIT/ABORT |
| `NO/ABORT(TID)` | 不得后来假装 YES；coordinator 询问时重发 NO |

[01:18:24-01:21:12]

因此，收到未来的 `COMMIT(TID)` 不能替代本地 durable vote。若本地此前是 NO，则一个合法 basic 2PC coordinator 本不应形成 COMMIT；participant 必须保存证据以正确回答恢复查询，而不是无条件接受并“假设 prepared”。[01:18:46-01:20:45]

### 适用域的定性边界

```text
cross-organization participants
  -> independent failures + weak mutual trust + operational dependency
  -> blocking cost difficult to accept

single-organization sharded data center
  -> common administration and failure handling
  -> 2PC widely used for cross-shard transactions
```

[01:16:31-01:18:21]

本段无定量性能公式。老师没有给出跨组织替代 protocol，也没有展开 presumed-commit messages，故不从外部资料补充。

## 例子与课堂提示

- **Single multicore database** [01:14:57-01:15:16]：用于拆除“2PL 因为出现在 distributed-transactions lecture，所以只能跨服务器”的误解。它处理 concurrency，不以 network 为必要前提。
- **Initial puts 使用 2PL，随后运行 2PC** [01:15:39-01:16:28]：用于说明两者可组合。锁住 `x`、`y` 是隔离步骤；participants 对是否一起 commit 的 agreement 是另一层。
- **Travel + hotel booking** [01:16:42-01:18:08]：用于说明 2PC 不只从 sharding 中产生，也可描述不同 organizations 的共同 action；同时暴露 blocking 与 trust-domain 代价。

- **Presumed commit** [01:19:16-01:19:45]：老师仅承认一种 variation/optimization 存在，并明确没讲。本笔记不补它如何省 messages 或改变 logging，因为那会越过课堂证据。
