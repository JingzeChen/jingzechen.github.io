## 整讲主线

本讲服务于 6.824 labs 所需的两类基础设施。老师先建立 thread/goroutine 的执行模型，解释为什么 distributed programs 需要 I/O concurrency、multi-core parallelism 和 background activities；随后把代价归纳为 race、coordination 与 deadlock。Go 提供两种可互换但思维中心不同的组织方式：用 locks 保护 shared state，用 condition variables、channels 或 `WaitGroup` 完成等待和通知；老师不主张教条式二选一。

课堂用两个连续例子把这些原则落到 code。Vote collector 展示 shared counter race、`sync.Mutex`、`defer Unlock()`、loop-variable capture、busy waiting、`sync.Cond` 和 unbuffered channel 的 goroutine leak。Web crawler 再对比 serial recursion、Mutex + per-node `WaitGroup` 与 coordinator/workers + channel：前者通过 atomic check-and-mark 保证 URL fetch once，后者让 coordinator 独占 `fetched` map，同时保留 workers 的并行 network `Fetch`。

后半讲从 local procedure call 的外观引出 RPC。Stub/`Call()` 负责 marshalling、network request、server dispatch、waiting 与 unmarshalling；toy KV server 说明 RPC handlers 是 concurrent goroutines，因此 shared map 仍要 lock。最后的核心边界是 failure ambiguity：没有 reply 不等于 server 没有执行。At-least-once 用 retry 换取较少漏执行但可能 duplicate；at-most-once 过滤 duplicate 但允许执行 zero times；exactly-once 还需要 durable/fault-tolerant state。Go RPC library 不自动 resend 一次 `Call`，application 自行 retry 时仍须处理重复与失败。

## 课堂顺序中的关键提醒

- Goroutine 是 lightweight，但不是 free：stack memory 与创建 overhead 仍存在。
- 高级语言的一条 statement 不自动 atomic；`go ... -race` 应成为 labs 的默认检查。
- `cond.Wait()` 必须与 predicate loop 和 associated mutex 一起理解。
- Channel thread-safe 不代表使用 channel 的 protocol 不会 deadlock 或 leak。
- Single coordinator 可以串行管理 metadata，同时让 expensive workers 并行。
- `Call()` error 与 `reply.Err` 属于不同层次：前者是没有可靠拿到 RPC reply，后者是正常 reply 中的 service result。
- RPC 能隐藏 wire protocol，不能消除 distributed failure ambiguity。

5. **定义 thread/goroutine（00:05:45-00:07:37）**
   - thread 是 “thread of execution” 的简称；Go 称其为 goroutine，老师在一般语境中仍会说 thread。
   - `go run` 启动一个 operating-system process；Go runtime 位于该 process 内。
   - 启动时先有一个 main thread，之后可以用语言 primitive 创建更多 threads，让多个 execution streams 并行推进。
   - 单个 thread 仍像 sequential program 一样执行：拥有 program counter、自己的 stack 和一组 registers，按顺序执行 instruction、调用和返回 procedure，也可以递归。
   - 同一 process 内的 threads 共享 address space，因此一个 thread 写入的 memory location 可由另一个 thread 读取；这使它们能够交换信息。

6. **从 runtime 角度解释 thread 操作（00:07:37-00:09:10）**
   - 创建：Go 的 `go` keyword 启动新的 goroutine。
   - 退出：goroutine 所运行的 function 返回时，thread 隐式退出。
   - 停止：例如向 channel 写入而暂时没有 reader 时，goroutine 会 blocked；runtime 可停止它，把 processor 让给其他 runnable thread。
   - 恢复：条件具备后 runtime 再恢复该 thread。
   - 机械上，stop/resume 可理解为保存或重新装入 program counter、stack pointer 和 registers，使 processor 切换所执行的 thread。

7. **转入“为什么需要 threads”（00:09:19-00:10:00）**
   - 老师承认 parallel code 比 sequential code 更复杂，因此 threads 需要有明确收益才值得引入。
   - 对 6.824 而言，最主要的收益是表达 concurrency；本段只提出该问题，具体类型留到下一段。

## 概念、符号与推导

- **Thread / goroutine**：一条 execution stream；每条 stream 自身按顺序执行，但同一 process 中可以存在多条。
- **每线程状态**：program counter、stack、registers。老师用这些状态解释 runtime 如何暂停和恢复 thread。
- **共享状态**：threads 位于同一个 process address space，因而可读写共同 memory；本段只说明通信能力，尚未展开由此产生的 race。
- **Blocked**：thread 因等待某事件而暂时不能继续执行，例如 synchronous channel send 尚无 receiver；runtime 可让其他 thread 使用 processor。
- **生命周期关系**：function return 导致相应 goroutine 退出；学生反馈指出 main/function 过早结束会影响其他 goroutines，但本段尚未给出协调方案。
- **本段无公式推导**。老师使用的是执行状态和控制流程的概念分解，没有数学公式。

# 第二节：Concurrency 的收益与 Threads 的三类风险

- **时间范围**：00:10:01-00:19:58
- **证据范围**：本节 prompt 所附 transcript（材料模式：仅 transcript）
- **材料参照**：无对齐课件页；结论只取本节口述。

## 本段在整讲中的作用

上一节已建立 thread/goroutine 的执行模型，并在结尾提出“既然 parallel code 更复杂，为什么还要 threads”。本段先完整回答这个问题：I/O concurrency、multi-core parallelism 和周期性 background activity。随后老师转向代价，依次介绍 race condition、coordination 和 deadlock 三类挑战，并给出 Go 中对应的工具入口。片段结尾把解决并发问题的方法概括为两套思路：channels，以及 locks + condition variables；如何选择在下一节继续。

## 教学展开

1. **I/O concurrency（00:10:01-00:10:52）**
   - distributed application 中的 goroutine 可能发起 network call，然后 blocked 等待远端响应。
   - 等待期间不应让整个 process 停住；runtime 可以运行其他 goroutines。
   - 如果 client 要向多台 machines 大致并行地发送请求，可以为每个请求启动 goroutine，让连接与等待重叠发生。
   - 老师以 MapReduce 类应用为例，说明 I/O concurrency 是 6.824 特别关心的理由。

2. **Multi-core parallelism（00:10:52-00:11:30）**
   - 多个 cores 可以同时运行不同 goroutines，这是真正的 parallel execution。
   - key-value server 可以在不同 cores 上并行处理不同 keys 的 requests，从而提高 throughput。
   - 老师将 I/O concurrency 与 multi-core parallelism 称为两项主要理由。

3. **便利地表达周期性工作（00:11:30-00:12:13）**
   - labs 中常需要每秒或每 200 milliseconds 做一次事情。
   - 可以启动专用 goroutine：sleep 200 ms，执行任务，再 sleep。
   - 这类 background activity 并非只能用 threads 表达，但 threads 很方便。

4. **Goroutine 数量的权衡（00:12:13-00:12:44）**
   - Go 的使用思路是按需要创建 goroutines，把它们视为 lightweight。
   - 但它们不是 free：每个 goroutine 需要 stack memory，启动也有 performance overhead。
   - 老师在此没有给固定数量公式，而是鼓励按工作需要创建。

5. **挑战一：race condition（00:12:55-00:17:13）**
   - 两个 threads `T1`、`T2` 共享初值为 `0` 的变量 `n`，都执行 `n = n + 1`。
   - Go statement 不是不可分割的 atomic operation；编译后可分成 load、register increment、store。
   - 不利的 interleaving 是：两边都先 load 到各自的 `r0`，都从 `0` 加到 `1`，再各自 store `1`。
   - 结果 `n = 1`，但程序期望 `n = 2`，因此是 bug。
   - race 危险之处在于大多数运行“看起来正常”，只在特定时序下失败。
   - 两条处理路线：避免共享变量，用 channels 传值；或者用 locks 把一组 instructions 变成 atomic critical section。
   - Go 提供 race detector。老师建议 labs 默认使用 `-race`；它不能发现所有可能的 race，但很有效。

6. **挑战二：coordination（00:17:13-00:17:57）**
   - 一个 thread 常常必须等另一个 thread 完成某件事。
   - Go 的 channels 同时承担 communication 与 coordination。
   - condition variables 也是等待和唤醒工具，老师预告后面会进一步讲。

7. **挑战三：deadlock（00:17:57-00:19:08）**
   - 若 `T1` 等 `T2`，同时 `T2` 等 `T1`，双方都无法 progress，这就是老师所说的 deadly embrace。
   - 等待环可以由 locks 引起，也可由 communication 引起。
   - 最简单的 Go 例子：程序只有一个 thread，却向 unbuffered channel 发送；send 会等 receiver，但根本没有其他 thread 来 receive，于是 deadlock。
   - Go runtime 能识别“没有 thread 可以继续运行”的简单情形并报 runtime error；多 thread deadlock 会更复杂，labs 中很可能遇到。

8. **归纳为两套并发设计思路（00:19:08-00:19:58）**
   - 老师回顾上述挑战，把 Go 的常见方案概括为 channels，以及 locks + condition variables。
   - 本节在提出两套方案后结束，尚未给出取舍规则。

## 概念、符号与推导

- **I/O concurrency**：一个 goroutine 因 network I/O blocked 时，其他 goroutines 继续运行；目的是重叠等待时间。
- **Multi-core parallelism**：不同 goroutines 同时占用不同 processor cores；老师用 KV requests 的 throughput 说明收益。
- **Race condition**：多个 threads 并发访问 shared state，其中至少有更新，结果取决于执行 interleaving，并可能违反程序期望。
- **`n = n + 1` 的分解**：`load n -> r0`，`r0 <- r0 + 1`，`store r0 -> n`。两个 threads 的 load 都看到 `0` 时，会产生 lost update。
- **Atomic operation / critical section**：外部不能观察到中间 interleaving 的操作序列；本节只提出 locks 可提供这种保护，尚未给具体 API 用法。
- **Coordination**：thread 等待另一 thread 产生结果或达到状态；channels 和 condition variables 是候选 primitive。
- **Deadlock**：等待关系形成环，使相关 threads 都无法 progress。
- **结果关系**：本例实际结果 `1 != 2`，其中 `2` 是两个 increment 各生效一次的期望值。

## 例子与课堂提示

- **并行 network calls（00:10:09-00:10:49）**：为多台 remote machines 分别启动 goroutine，服务于 I/O latency 隐藏。
- **不同 keys 的 KV requests（00:11:18-00:11:27）**：在不同 cores 上处理，服务于 throughput 提升。
- **每 200 ms 的 background goroutine（00:11:44-00:12:08）**：服务于周期性任务的结构化表达。
- **Lost update（00:13:31-00:15:28）**：用 `T1`、`T2`、`n`、`r0` 的具体 interleaving 证明高级语言的一行赋值不自动 atomic。
- **“程序跑通”不能证明无 race（00:15:44-00:17:07）**：race 多数时候不显现，应用 `go ... -race` 主动检测。
- **单 goroutine channel send（00:18:23-00:18:53）**：服务于 synchronous communication 也会制造 deadlock 的警示。

# 第三节：Channels 与 Locks 的选型，以及 Vote Race 的第一轮修复

- **时间范围**：00:19:59-00:29:57
- **证据范围**：本节 prompt 所附 transcript（材料模式：仅 transcript）
- **材料参照**：无对齐课件页；vote 代码仅按屏幕口述记录，不补写未提供的源码。

## 本段在整讲中的作用

上一节把并发方案归纳为 channels 与 locks + condition variables。本段先给出非教条式选型原则，然后用一个与后续 Raft lab 相似的 vote collection 小程序，把抽象风险落实到 shared variables、race detector、`sync.Mutex`、critical section、`defer` 和 anonymous function 的 lexical/static scope。片段末尾开始讨论 loop variable `i` 的 capture 问题，修复方法留到下一节。

## 教学展开

1. **按问题选择并发风格（00:19:59-00:20:47）**
   - 若两个 threads 只需 communication、没有真正共享 memory，老师倾向 channels。
   - 若多个 threads 方便地共享 state，例如 key-value service 的 table，老师倾向 locks 与 condition variables。
   - 老师明确反对把某一方案教条化为永远更好；应选当前问题最方便、最自然的表达。

2. **为什么专门补讲 condition variables（00:20:47-00:21:11）**
   - Go tutorial 对 channels 讲得较多，提到 locks，却较少讲 condition variables。
   - 因此老师用一个很小的例子补足这一工具；本段先从无 condition variable 的版本开始。

3. **建立 vote collection 场景（00:21:11-00:22:17）**
   - `T1` 要从 remote machines 收集 votes，以判断是否达到 majority，进而决定能否 commit 某个 value。
   - 老师指出这类 primitive 稍后会出现在 Raft lab。
   - `T1` fork 出多个 worker threads，例如 `T2`；每个 worker 做昂贵的 remote operation 取得 vote，再向 `T1` 报告。

4. **第一版程序及其表面行为（00:22:17-00:24:14）**
   - 两个 shared variables 是 `count` 与 `finished`：前者累计 yes votes，后者统计已返回的 workers。
   - loop 启动 10 个 anonymous goroutines；每个调用 `requestVote`。该函数用 sleep 模拟 remote machine 上耗时且会 block 的工作。
   - 若返回 yes，则增加 `count`；每个 worker 结束时增加 `finished`。
   - 主流程依据 `count` 与 `finished` 判断赢或输。老师多次运行，输出有时 win、有时 lose，看上去能工作。
   - 老师随即追问：能产生结果是否等于程序正确？

5. **识别 race 并用 detector 证实（00:24:14-00:25:37）**
   - 学生指出多个 goroutines 都在修改 `count` 和 `finished`，存在 race condition。
   - 老师把“同一变量被不同 goroutines 访问或修改”视为立即需要审查的 red flag。
   - Go race detector 报出问题并给出相关 line numbers，证明“几次运行有输出”不足以证明正确。

6. **用 `sync.Mutex` 修复 shared state（00:25:37-00:27:43）**
   - 声明一个独立的 lock `mu`，由程序员约定它保护 `count` 和 `finished`。
   - 每次访问这些 shared variables 都必须放在 `Lock()` 与 `Unlock()` 之间。
   - worker 在 `requestVote` 返回后加锁，更新 vote count 和 finished，再解锁；这段是 critical section。
   - `defer mu.Unlock()` 会在当前 function/block 的退出路径上执行，减少遗漏 unlock 的风险，尤其适合存在多个 return paths 的代码。
   - 加锁后再运行 race detector，老师观察到 detector 不再报告该 race。

7. **Anonymous function 的 scope（00:27:43-00:29:04）**
   - anonymous function 内使用但未在内部声明的变量，会解析到外层 lexical/static scope 中的变量。
   - 因而它能访问外面的 `mu`、`count` 和 `finished`。
   - mutex 本身不会自动绑定某个 variable；它只是一个 lock object/name。由 programmer 维持“哪个 lock 保护哪些 data”的 convention。

8. **提出 loop variable capture 风险（00:29:04-00:29:57）**
   - 学生追问：若 goroutine 直接使用外层 loop variable `i` 会怎样。
   - goroutine 实际开始运行时，会读取 `i` 当时的值，而外层 loop 正在继续改变它。
   - 这通常不是程序员想要的“本次 iteration 的 `i`”；本节只提出问题，具体传参修复在下一节开头。

## 概念、符号与推导

- **选型原则**：communication-centered problem 倾向 channels；shared-state-centered problem 倾向 locks + condition variables。这是老师的经验判断，不是语言强制规则。
- **`count`**：已经获得的 yes votes 数量。
- **`finished`**：已经完成 `requestVote` 并报告的 worker 数量。
- **Critical section**：访问由 `mu` 保护的 `count`、`finished` 的代码区域；同一时刻只允许持锁者执行。
- **Lock-data convention**：`sync.Mutex` 与被保护变量在语言层面相互独立，正确性依赖所有访问者遵守同一约定。
- **`defer`**：把 `Unlock()` 安排在当前 function 返回时执行，覆盖多条 exit paths。
- **Lexical/static scope**：anonymous function 可以引用外层声明；它捕获的是外层 variable，而不是自动复制创建 goroutine 时的 value。
- **多数阈值的口述边界**：老师先说收集 majority，演示中又口述 `count < 5` 为失败、`count >= 5` 为胜利。对于 10 votes，这个边界与严格多数的通常含义并不一致，因此这里只记录原话，不替老师改写条件。
- **本段无公式推导**。只有计数条件和 shared-state invariants，没有数学证明。

## 例子与课堂提示

- **Raft vote collection（00:21:13-00:22:04）**：以 remote vote 为昂贵 operation，说明 worker goroutines 与 collector 之间既有并行也有 coordination。
- **Sleep 模拟 remote call（00:22:54-00:23:10）**：服务于“worker 会 block，适合并发发起”的直观模型。
- **输出正常但 detector 报 race（00:23:43-00:25:28）**：服务于“测试几次不能排除时序 bug”。
- **`defer mu.Unlock()`（00:26:24-00:27:00）**：服务于减少多 exit path 下忘记 unlock 的错误。
- **Mutex 不自动保护任何变量（00:28:45-00:29:04）**：提醒必须在设计和 code review 中明确 lock ownership/invariant。
- **Loop variable `i`（00:29:04-00:29:57）**：服务于区分 capture variable 与 capture value；修复留到下一节。

   **答：**没有 shared memory、重点是 threads 之间 communication 时倾向 channels；方便共享 state 时倾向 locks 与 condition variables，并按具体问题选择而非教条化。

2. **问：第一版 vote 程序为什么有 race？**  
   **答：**10 个 goroutines 并发访问和更新同一组 `count`、`finished` variables，而没有 synchronization。

# 第四节：Loop Capture、Condition Variables 与 Goroutine 生命周期

- **时间范围**：00:29:58-00:39:55
- **证据范围**：本节 prompt 所附 transcript（材料模式：仅 transcript）
- **材料参照**：无对齐课件页；本节不借用下一段的 `crawler.go` 内容。

## 本段在整讲中的作用

本段承接上一节末尾的 loop variable capture，先给出按值传参的修复，再通过 vote collector 的连续改写解决“如何等待”的问题：busy spinning 浪费 CPU，固定 `Sleep()` 又有 latency/period 选择困难，因此引出 `sync.Cond` 的 `Wait`、`Signal`、`Broadcast`。之后老师用 channel 重写同一程序，比较 shared-state 与 communication 两种风格，并指出 unbuffered channel 的阻塞语义可能造成 goroutine leak 或 main 过早退出。

## 教学展开

1. **修复 loop variable capture（00:29:58-00:30:22）**
   - 把 `i` 声明为 anonymous function 的 parameter，并在创建 goroutine 时把当前 `i` 作为 argument 传入。
   - argument 在创建 goroutine 的调用点求值，因此 worker 得到本次 loop iteration 的 value，而不是稍后读取持续变化的外层 variable。

2. **讨论被 closure 引用的 local variables 生命周期（00:30:24-00:32:21）**
   - 学生问：如果 `count`、`finished` 是 local variables，而外层 function 先退出，它们会不会被销毁。
   - 老师最初回答它们原则上在 stack 上，外层返回后可能消失，并一度同意可能 segmentation fault。
   - 随后老师立即撤回这一回答：只要另一个 thread 仍持有 reference，garbage collector 就不会删除 object；直到没有 thread 持有引用才回收。
   - 老师借此再次强调 garbage-collected language 对 shared-memory programming 的价值。
   - 另一种 capture 修复是 loop body 内写 `i := i` 创建新的 scoped variable；老师确认可行，但个人更喜欢显式传参。

3. **识别 busy waiting（00:32:41-00:33:11）**
   - 加锁版主 thread 的 loop 只是反复 lock、检查 `count`/`finished`、unlock，再立即重试。
   - 这种 spinning 一直占用 processor，却没有做有用工作。
   - 希望 waiting thread 可以让出 core，让其他 goroutines 运行，并在条件变化时再醒来。

4. **为什么固定 `Sleep()` 不理想（00:33:11-00:33:53）**
   - 一个直接办法是每轮 sleep 一段时间，再检查条件，能减少疯狂 spinning。
   - 但 sleep 多久没有自然答案：太久会延迟观察到 `count` 达标，太短仍会频繁唤醒。
   - 更理想的是状态达到关注点时，由更新者主动 wake waiting thread；这正是 condition variable 的用途。

5. **`sync.Cond` 的等待协议（00:33:53-00:35:04）**
   - 创建 condition variable，并把它与保护 `count`/`finished` 的 `mu` 关联。
   - main thread 先持有 `mu`，因为读取 shared state 本身必须受 lock 保护。
   - 条件尚不成立时调用 `cond.Wait()`。
   - `Wait()` 原子地释放 associated lock 并让调用 goroutine sleep，避免“检查后、睡眠前”错过通知。
   - `Wait()` 返回前会重新取得 lock，所以调用者醒来后可安全地再次检查 `count` 和 `finished`。
   - 老师展示的结构是 loop 中反复检查 predicate；被唤醒不等于 predicate 必然已满足。

6. **`Signal` 与 `Broadcast`（00:35:05-00:35:49）**
   - vote workers 仍先持锁更新 `count`/`finished`。
   - 更新后通过 condition variable 通知 waiter。
   - `Signal` 唤醒一个 waiter，`Broadcast` 唤醒所有 waiters；本例只有一个 waiter，两者都可使用。
   - 课堂实现每次增加 `finished` 都可能唤醒 main，让它重新检查成功或结束条件。

7. **同一 vote collector 的 channel 版本（00:36:11-00:37:21）**
   - main 创建 channel，并把它交给多个 request-vote goroutines。
   - 每个 worker 把 `requestVote` 的 Boolean result 写入 channel。
   - main 在 receive 处 block；收到结果后，若为 true 就增加 `count`，并增加 `finished`。
   - 这里无需 locks，因为只有 main goroutine 更新 `count` 与 `finished`；workers 只通过 thread-safe channel 发送 values。

8. **Buffered channel 的取舍（00:37:28-00:38:04）**
   - unbuffered channel 没有 receiver 时，sender 立即 blocked。
   - buffered channel 可暂存指定数量的 values，使 sender 在 buffer 未满时不必等同步 receiver。
   - 老师明确说自己在 6.824 labs 几乎不用 buffered channels，少数使用经历令他后悔；这是经验建议，不是语言限制。

9. **提前停止接收导致 goroutine leak（00:38:04-00:39:29）**
   - 若 main 在 `count` 达到 5 后停止 receive，其余 workers 仍可能尝试向 unbuffered channel send。
   - 没有 receiver 后，这些 senders 会永久 blocked。
   - 短程序里 main exit 会清理整个 process，看不出长期问题；long-running service 中这些 goroutines 会累积，形成 thread/goroutine leak。
   - 反方向也有风险：main 在 workers 完成前过早退出，工作就没有完成。老师将 thread management 总结为常见难点。

10. **Goroutine 不能被外部随意“杀掉”（00:39:29-00:39:55）**
    - 对“能否不退出 main 就 kill thread”的提问，老师给出的方向是通过某个 channel 发送“please exit”之类的 value。
    - 退出协议需要程序自行 coordination，而不是依赖这里展示的外部强杀 primitive。
    - 片段结束时，老师准备回到 condition variable 与 channel 在该问题上的差异。

## 概念、符号与推导

- **Capture by parameter**：`go func(i int) { ... }(i)` 在调用点把当前 value 传给 goroutine，避免 closure 读取后续变化的外层 `i`。
- **Busy waiting / spinning**：waiting thread 持续执行“lock-check-unlock”，消耗 CPU 却不推进业务状态。
- **Condition predicate**：本例中由 `count` 与 `finished` 表示的“可以决定结果”状态；必须在 associated mutex 保护下读取。
- **`cond.Wait()` invariant**：调用前持有 lock；内部原子 release + sleep；返回时再次持有 lock；返回后在 loop 中重查 predicate。
- **`Signal` / `Broadcast`**：分别唤醒一个/all waiters。通知只促使重查，不替代 predicate。
- **Unbuffered channel synchronization**：send 与 receive 必须 rendezvous；任一端缺席都会使另一端 blocked。
- **Goroutine leak**：goroutine 因永远无法完成的 send/receive 等待而长期存活；进程未退出时会占用资源。
- **本段无公式推导**。核心是等待协议和 happens-in-program-order 的控制流程。

- **老师对 segmentation fault 的自我纠正（00:30:24-00:32:17）**：服务于“被 goroutine 引用的 object 由 GC 保持存活”；应以纠正后的说法为课堂最终结论。

- **`Wait` 自动 release/reacquire lock（00:34:12-00:35:04）**：服务于在不 race 的前提下让出 CPU。

## 本段掌握检查

1. **问：为什么把 loop variable `i` 作为 anonymous function parameter 可以修复 capture 问题？**  
   **答：**创建 goroutine 时 argument 就按当前 value 求值，worker 不再稍后读取同一个持续变化的外层 `i`。

2. **问：`cond.Wait()` 对 associated mutex 做了什么？**

3. **问：为什么从 `cond.Wait()` 返回后仍应在 loop 中检查 predicate？**

# 第五节：Crawler 的 Serial、Mutex 与 Channel 结构

- **时间范围**：00:39:55-00:49:53
- **证据范围**：本节 prompt 所附 transcript + `crawler.go` p.1
- **材料参照**：`materials/crawler.go`；prompt 对齐页标记为 `[课件: crawler.go p.1]`。

## 本段在整讲中的作用

本段先完成上一节未说完的比较：`cond.Broadcast()` 不像 unbuffered channel send 那样等待 receiver，因此 vote worker 不会因无人等待而挂住。随后老师进入更真实的 crawler exercise，先明确 I/O concurrency、每个 URL 只 fetch 一次和正确结束三项目标，再用 serial recursion 作 baseline，依次讲 `ConcurrentMutex` 和 `ConcurrentChannel`。片段结束在 channel coordinator 的处理中段，worker 计数与并行性由下一节继续。

## 教学展开

1. **`Broadcast` 与 channel send 的阻塞差异（00:39:55-00:40:44）**
   - vote 程序达到决定条件后，main 可能继续离开等待逻辑，而剩余 workers 仍会更新状态。
   - worker 持 lock、更新、调用 `Broadcast`；即使当时没有 waiter，`Broadcast` 也不会 block。
   - 这与 unbuffered channel send 不同：无人 receive 时 send 会 block。
   - 因而在该特定 vote 程序中，condition-variable 版本不会留下卡在通知动作上的 workers。

2. **定义 web crawler（00:41:00-00:41:52）**
   - 从一个 URL 开始 fetch page，从 page 中取得更多 URLs，再递归 fetch。
   - webpages 与 links 形成 graph；URL 可能指回已经访问过的 page。
   - crawler 的正确性目标之一是同一 webpage 不访问两次。

3. **列出 crawler 的目标（00:41:52-00:42:42）**
   - **I/O concurrency**：`Fetch` 可能跨越很远、很慢的 network；等待一个 page 时应并发 fetch 其他 pages。
   - **Fetch once**：每个 URL 只 fetch 一次。老师把它称为 correctness/performance 相关目标。
   - **Parallel work**：如果有多个 cores，希望可利用它们并行工作。
   - 后续代码还必须知道何时所有 reachable work 都已结束。

4. **以 serial solution 建立 baseline（00:42:44-00:44:20；`crawler.go` p.1）**
   - `main` 调用 `Serial(startURL, fetcher, emptyMap)`。
   - `Serial` 先查 `fetched[url]`；已访问就 return，否则立即标记为 `true`。
   - 调用 `fetcher.Fetch(url)` 得到 links；失败就 return。
   - 对每个 child URL 递归调用 `Serial`，形成 sequential depth-first traversal。
   - shared-by-reference 的 `fetched` map 破除 graph cycles 并防止重复 fetch，但任一时刻只 fetch 一个 page，不能隐藏 network latency。
   - 三种实现输出大体相同，concurrent versions 的打印顺序偶尔不同，这是 execution order 不确定的外显结果。

5. **课堂 breakout discussion（00:44:20-00:45:29）**
   - 老师让学生分组分享自己的 concurrent crawler solution 和遇到的问题。
   - transcript 在发出任务后直接跳到返回课堂；实际讨论内容没有证据，因此笔记不补写学生方案。

6. **`ConcurrentMutex` 的 shared state（00:45:29-00:46:39；`crawler.go` p.1）**
   - `fetchState` 把 `sync.Mutex` 与 `fetched map[string]bool` 放在同一 struct 中，表达保护关系。
   - `map` 本身不是 thread-safe；因为多个 goroutines 会访问它，programmer 必须用 mutex 使访问安全。
   - 每次处理 URL 时先 `Lock()`，读取 `already := f.fetched[url]`，再把 `f.fetched[url] = true`，随后 `Unlock()`。
   - check 与 mark 必须在同一个 critical section 中；之后依据 local `already` 决定是否 return。
   - lock 只覆盖 map check/update，不覆盖耗时的 `Fetch`，因此多个 page fetches 仍可并发。

7. **每个 child URL 启动 goroutine（00:46:39-00:47:00；`crawler.go` p.1）**
   - 当前 page fetch 完成并返回 child URLs 后，为每个 child 创建 anonymous goroutine。
   - code 用 `go func(u string) { ... }(u)` 显式传入 URL，沿用上一节讲过的 loop capture 修复。
   - 每个 child goroutine 递归调用 `ConcurrentMutex(u, fetcher, f)`，共享同一个 `fetchState`。

8. **用 `sync.WaitGroup` 判断 subtree 完成（00:47:00-00:48:07；`crawler.go` p.1）**
   - 每次启动 child 前调用 `done.Add(1)`。
   - child 用 `defer done.Done()` 保证退出时平衡计数。
   - parent 调用 `done.Wait()`，直到它启动的所有 child goroutines 完成后再 return。
   - 每次 recursive invocation 都有自己的 local `WaitGroup`，由这些 waits 形成 goroutine tree 上的 completion propagation。
   - 老师指出 `WaitGroup` 可被理解为内部使用 condition variable 的便利 primitive。

9. **开始 `ConcurrentChannel`：coordinator/worker 组织（00:48:07-00:49:53；`crawler.go` p.1）**
   - 结构类似 MapReduce lab：一个 coordinator 管理任务，多个 workers 执行 fetch。
   - `ConcurrentChannel` 创建 `ch := make(chan []string)`。
   - 初始 URL 也通过 channel 交给 coordinator；因为 unbuffered send 在 coordinator 开始 receive 前会 block，代码专门启动 goroutine 发送 `[]string{url}`，避免初始化阶段 deadlock。
   - `coordinator` 是唯一访问 `fetched` map 的 goroutine，所以该 map 不需要 lock。
   - coordinator 用 `for urls := range ch` 持续 receive URL slices，对尚未 fetched 的 URL 启动 worker。
   - 本片段在 coordinator 处理流程中结束，`n` 的完整结束条件和 worker 回传在下一节继续。

## 概念、符号与推导

- **Web graph**：webpage 是 node，link 是 directed edge；multiple links 与 cycles 要求记录 visited set。
- **Serial invariant**：`fetched[url] = true` 在 `Fetch` 前完成，所以递归遇到 cycle 时能立即 return。
- **Mutex crawler invariant**：对任一 URL，检查 `fetched[url]` 与设置为 `true` 是同一 atomic critical section；只有第一个观察到 `already == false` 的 goroutine 继续 fetch。
- **Lock granularity**：mutex 只保护 shared map，不覆盖 network `Fetch`；若覆盖 I/O，会不必要地序列化 crawler。
- **WaitGroup accounting**：每个 launched child 对应一个 `Add(1)`，且退出对应一个 `Done()`；parent 的 `Wait()` 在计数归零后返回。
- **Channel ownership**：`fetched` 只由 coordinator 访问，以 ownership/serialization 代替 mutex。
- **Unbuffered bootstrap**：初始 send 必须与 receive 并发发生，因此材料用单独 goroutine 执行 `ch <- []string{url}`。
- **本段无公式推导**。核心是 graph traversal invariants 和 worker completion accounting。

## 例子与课堂提示

- **远端慢网页（00:42:03-00:42:19）**：服务于 crawler 必须并发 `Fetch`、network latency 比单纯顺序计算更关键。
- **三种实现输出顺序不同（00:43:19-00:43:40）**：服务于 concurrent scheduling 会改变 observable ordering，但不应改变 fetched set。
- **先 mark 后 fetch（`crawler.go` p.1）**：服务于阻断 cycles；即使 `Fetch` 返回 error，该 URL 也已被视为尝试过。
- **`go func(u string)`（00:46:47-00:47:00）**：服务于上一节 loop capture 的实际应用。
- **过早 termination（00:47:14-00:47:49）**：服务于 `WaitGroup` 不能省略；否则 main/parent 可能在 descendants 完成前 return。
- **初始 channel send 另起 goroutine（00:48:44-00:48:55）**：服务于 unbuffered channel 必须有并发 receiver 的规则。

## 本段掌握检查

1. **问：crawler 为什么必须维护 `fetched` set？**  
   **答：**web graph 有重复 links 和 cycles；set 既防止重复占用 network，也让 traversal 能在 cycle 上终止。

2. **问：`ConcurrentMutex` 为什么要把 check 与 mark 放在同一个 lock interval 内？**  
   **答：**若分开，两个 goroutines 可能都看到 `false` 并重复 fetch；同一 critical section 保证只有一个观察者获得 first-fetch 权利。

3. **问：为什么 mutex 不应覆盖 `Fetch`？**  
   **答：**`Fetch` 是慢 network operation；持锁等待会阻止其他 goroutines 检查 map 并并发 fetch，破坏 I/O concurrency。

4. **问：`WaitGroup` 如何让 recursive parent 知道何时可以 return？**  
   **答：**每启动一个 child 就 `Add(1)`，child 退出时 `Done()`，parent 的 `Wait()` 直到计数归零才返回。

5. **问：channel 版为何无需给 `fetched` map 加锁？**  
   **答：**只有 coordinator goroutine 读写该 map；workers 通过 channel 交付结果，不直接共享它。

# 第六节：Channel Crawler 收尾与 RPC/KV Client

- **时间范围**：00:49:54-00:59:52
- **证据范围**：本节 prompt 所附 transcript（材料模式：仅 transcript）
- **材料参照**：无对齐课件页；尽管口述开始展示 KV code，本节不借用下一节才对齐的 `kv.go` 页面补写。

## 本段在整讲中的作用

本段先完成 `ConcurrentChannel` 的控制逻辑，回答 unbuffered channel 是否会把 crawler 变回 sequential 的问题：channel handoff 一次一个，但昂贵的 `Fetch` 仍在多个 workers 中并行。随后老师切换到 labs 的另一项基础设施 RPC，从“让 remote call 尽量像 local procedure call”的目标出发，解释 client/server、stub、request/response、marshalling/unmarshalling，再进入 toy key-value service 的 Args/Reply 与 client-side `Call()`。片段结束时刚转向 server-side map。

## 教学展开

1. **Coordinator 过滤 URLs 并启动 workers（00:49:54-00:50:24）**
   - coordinator 收到 URL 后检查它是否已 fetched；已处理则不再启动工作。
   - 对尚未处理的 URL 创建 worker goroutine 执行 fetch。
   - `n` 记录 outstanding workers；只有 `n == 0` 时 coordinator 才 termination，防止仍有网页未完成就退出。

2. **Worker 回传 links（00:50:24-00:51:02）**
   - worker 调用 `Fetch`；不同 workers 的这些 calls 完全并行。
   - worker 从 page 得到 URLs 后，通过 channel 把这一组 URLs 交给 coordinator。
   - coordinator 的 range receive 获得结果、发现新 work，并相应维护 `n`。
   - 每个 worker 完成一次回传后 exit；coordinator 据此减少 outstanding count。

3. **Unbuffered channel 没有消除昂贵工作的并行性（00:51:13-00:52:09）**
   - 学生问：channel 同时只能交接一个 value，其他 sender 要排队，是否令程序 sequential。
   - 老师回答：被串行化的是向 coordinator 交付结果的短暂 handoff；多个 fetchers 仍可并行执行跨 Internet 的昂贵 `Fetch`。
   - 因而 coordinator 单线程维护 state 与 workers 并行 I/O 可以同时成立。

4. **定义 RPC 目标（00:52:14-00:54:38）**
   - RPC 是 Remote Procedure Call，是 labs 需要的另一项工具。
   - caller 在 RPC terminology 中称 client，callee 称 server。
   - 理想模型是 client 调用 `fn(x, y)`，server 上执行对应 implementation，例如计算 `x + y`，结果 `z` 再返回 client。
   - 虽然两段程序在不同 computers 上运行，RPC 希望调用方式尽量接近 ordinary local procedure call。
   - 老师同时预告两者存在 fundamental difference，稍后由 distributed failures 暴露。

5. **Client stub 构造 request（00:54:38-00:55:39）**
   - client application 调用本地 stub function。
   - stub 建立 message，其中包含要调用的 function、argument types 和 argument values 等。
   - stub 经 network 把 request 发给 server-side RPC machinery/stub。

6. **Server dispatch 与 response path（00:55:39-00:57:35）**
   - server 接收 bytes 后 unmarshal，把 byte representation 转回 typed values。
   - server-side stub/dispatcher 调用真正的 `fn` implementation。
   - function return 后，server 把 response value marshal 成 message 发回。
   - client stub 在 send request 后一直 waiting；收到 response 后 unmarshal，再像 local return 一样把 value 交给 client application。
   - 同一个 server-side stub 调用 implementation 并接收其 return，不需要另造一对返回 stub。
   - 老师说 stubs 一般自动生成；Go 示例随后用 generic `Call()` 展示接近这一结构的做法。

7. **Toy KV service 的 RPC interface（00:57:35-00:58:35）**
   - service 提供两个 remote procedures：`Put(key, value)` 和 `Get(key)`。
   - Go 的常见 convention 是为每个 operation 声明 argument struct 与 reply struct。
   - `PutArgs`/`PutReply` 描述 Put request/response；`GetArgs`/`GetReply` 描述 Get request/response。
   - 老师先指出 server 有两个对应 functions，但随即跳回 client side 解释 call path。

8. **Client-side `get`/`put` 与 generic `Call()`（00:58:35-00:59:37）**
   - client `get` 先连接 server，填充 argument object，并分配 reply object。
   - `client.Call(method, args, reply)` 可看作 generic stub，三个要素分别是 server method name、arguments、reply destination。
   - `Call()` marshal arguments，经 connection 发送 request，并 block 等 response。
   - response 到达后，`Call()` unmarshal 并填充 reply struct，然后 return 给 client code。
   - `put` 的组织方式相同。

9. **转向 server state（00:59:37-00:59:52）**
   - 老师指出 server 内部有普通 Go key-value map。
   - `KV` struct、registration、concurrent handlers 和 locking 从下一节继续。

## 概念、符号与推导

- **Coordinator/worker split**：coordinator 串行拥有 scheduling state 与 fetched set；workers 并行执行慢 `Fetch`。
- **Outstanding count `n`**：表示尚未完成并可能产生新 URLs 的 work；`n == 0` 是 coordinator 的 termination condition。
- **RPC roles**：client 是 caller；server 是 remote callee/handler 所在端。
- **Stub**：在 client side 把普通-looking call 转为 request message，并等待 reply；server side 解码、dispatch、编码 response。
- **Marshalling**：typed arguments/results -> wire bytes/message；**unmarshalling** 是反向转换。
- **RPC call shape**：`z = fn(x, y)` 的外观对应 `request(fn, x, y) -> server execution -> response(z)`。
- **Go `Call()` interface**：`Call(method, args, reply)`；return 前 reply destination 被填充。
- **本段无公式推导**。`x + y = z` 只是老师说明 remote execution/return 的 toy example，不是推导。

## 例子与课堂提示

- **Channel handoff 与 `Fetch` 的成本分离（00:51:35-00:52:09）**：服务于说明“一条 unbuffered channel”不等于“所有 worker work sequential”。
- **`fn(x, y) -> z`（00:53:08-00:54:24）**：服务于 local-call illusion；真正 execution 在 server，argument 与 result 跨 network。
- **Request/reply stubs（00:54:48-00:56:48）**：服务于隐藏 protocol details，让 application 不直接拼 network packets。
- **`Put`/`Get`（00:57:43-00:58:24）**：服务于把抽象 RPC 结构映射到 labs 中常见的 key-value interface。
- **`client.Call(method, args, reply)`（00:58:43-00:59:32）**：服务于说明 Go 使用 generic call API 指定 remote method、request object 和 response destination。
- **课堂预告（00:54:25-00:54:35）**：RPC 只能“看起来相似”，failures 会使它不同于 local procedure call；本节尚未展开失败语义。

# 第七节：KV Server、RPC Failure Semantics 与调用边界

- **时间范围**：00:59:55-01:07:06
- **证据范围**：本节 prompt 所附 transcript + `kv.go` p.1 + `l-rpc.txt` p.1
- **材料参照**：`materials/kv.go`、`materials/l-rpc.txt`；prompt 对齐页分别标记为 `[课件: kv.go p.1]` 与 `[课件: l-rpc.txt p.1]`。

## 本段在整讲中的作用

本段完成 toy KV service 的 server side：registration、TCP accept/dispatch、concurrent RPC handlers 与 mutex。老师随后把 RPC 的关键差异落到 failure semantics：timeout 后 client 不知道 request 是否执行，retry 可能重复，因此区分 at-least-once、at-most-once 和 exactly-once。结论是 RPC 可以隐藏 marshalling/protocol，却不能隐藏 distributed failure；Go RPC 的一次 `Call` 不自动 resend，失败后的 application retry 必须自行处理 ambiguity 与 duplication。

## 教学展开

1. **`KV` shared state（00:59:55-01:00:10；`kv.go` p.1）**
   - `KV` struct 包含 `mu sync.Mutex` 和 `data map[string]string`。
   - `data` 保存 `Put`/`Get` 操作的 key-value state；`mu` 保护该 shared map。

2. **创建并注册 RPC server（01:00:10-01:01:13；`kv.go` p.1）**
   - `server()` 分配 `KV` object，并初始化空 map。
   - `rpc.NewServer()` 创建 RPC server，`rpcs.Register(kv)` 把 `KV` object 的可导出 methods 注册给 dispatcher。
   - 老师强调只有 capitalized method names 被导出；Go 用首字母大写表示 public/exported，所以 `Get`、`Put` 可供 client 调用，小写 method 不会以同样方式暴露。

3. **TCP connection 与 dispatch（01:01:13-01:01:57；`kv.go` p.1）**
   - server 在 `:1234` 上 `net.Listen("tcp", ...)`，循环 `Accept()` incoming connections。
   - code 为每个 accepted connection 启动 `go rpcs.ServeConn(conn)`。
   - RPC library 从 connection 读取 message，根据注册表找到 object/method，unmarshal arguments，调用 handler，再 marshal reply 写回 connection。
   - `l-rpc.txt` 进一步说明 RPC library 为 request 创建 goroutine；因此 handlers 必须按 concurrent execution 设计。

4. **为什么 handlers 必须 lock（01:01:57-01:02:22；`kv.go` p.1）**
   - 多 clients 可同时发起 `Get` 与 `Put`，于是多个 goroutines 可能并发操作同一个 `data` map。
   - `Get`、`Put` 都先 `kv.mu.Lock()`，并 `defer kv.mu.Unlock()`。
   - 这使 map read/update 在 mutually exclusive critical section 中执行，避免 race 与 map 内部并发访问问题。

5. **`Get` 与 reply（01:02:22-01:03:09；`kv.go` p.1）**
   - `Get(args, reply)` 用 `args.Key` 查询 map。
   - key 存在时设置 `reply.Err = OK`、`reply.Value = val`；不存在时设置 `ErrNoKey` 和 empty string。
   - handler return 后 RPC library marshal reply，client side unmarshal 并返回 caller。
   - `Put` 在材料中把 `args.Value` 写入 `data[args.Key]` 并返回 `OK`；本段口述没有逐行再讲 `Put` body。

6. **口述转向 failure semantics（01:03:09-01:03:55）**
   - 场景是 client 发送 request，server crashes，client 最终 timeout。
   - client 只知道没有拿到 response，不知道 operation 是没发生，还是已发生但 response 未成功返回。
   - 这一 ambiguity 是 RPC 与 ordinary local procedure call 的根本差异来源。

7. **At-least-once（01:03:55-01:04:20）**
   - 老师描述的策略是 client timeout 后自动 retry，并继续尝试，以获得“至少执行一次”的目标。
   - 代价是同一个 operation 可能被 server 执行多次；`Put` 也可能重复。
   - 因此它不适用于很多 non-idempotent application operations。

8. **At-most-once（01:04:20-01:05:01）**
   - request 对应的 operation 执行 zero times 或 one time，不超过一次。
   - 常见实现是 server filtering duplicate requests。
   - 例如 network 暂时 partition，original 与 resend 后来都到达；server 必须识别 resend，不能重复运行 handler。
   - 老师指出后续 labs 会实际处理 duplicate suppression。

9. **Exactly-once 的目标与成本（01:05:01-01:05:40）**
   - ordinary sequential procedure call 的直觉是恰好执行一次，因此 exactly-once 最接近理想接口。
   - 老师说它很难安排，需要把相关 state 持久化到 disk，因而 expensive；实践中很少 RPC systems 提供 exactly-once。
   - 课程会在 Lab 3 构建“basically exactly-once”的系统。

10. **Go RPC 的实际边界（01:05:40-01:06:11；`l-rpc.txt` p.1）**
    - 老师把 Go RPC 的一次 call 描述为 at-most-once：request 通过 TCP connection 发送，RPC library 本身不自动 re-send，所以 server 对这次 call 不会因 library retry 看见 duplicate。
    - outcome 是 handler 可能执行 once，也可能 not at all；若 client 没拿到 reply，`Call()` 返回 error。
    - application 如果在 error 后自行 retry，就重新引入 duplicate execution 的可能；处理 duplicates 与 failed messages 是 application responsibility。

11. **总结 local call illusion 的边界（01:06:11-01:07:06）**
    - RPC 的目标是尽量像 procedure call，但不可能 identical。
    - failure/server crash 会暴露差异：local call 的控制流不包含同样的 remote execution ambiguity。
    - 老师结束正式 lecture，祝学生完成 Lab 1 顺利，并留下来回答额外问题。

12. **`l-rpc.txt` 的材料补充：本段口述未逐项展开**
    - **Binding**：Go RPC 由 `Dial` 的 server name/port 决定连接目标；大型系统可能使用 name/configuration server。
    - **可传输类型**：讲义列出 strings、arrays、objects、maps 等；pointer 表示复制其所指数据，channels/functions 不能直接跨 RPC 传递。
    - **两层错误**：`Call()` 的 return 表示是否得到 RPC reply；service-level failure 通常放在 `reply.Err`，如 `ErrNoKey`。
    - **Best effort retry 风险**：讲义用 `Put("k", 10)`、`Put("k", 20)` 展示 original/retry 的延迟重排可能破坏期望 final value。read-only 或 repeated execution 无副作用/idempotent 的 operation 更容易承受 retry。
    - **Duplicate detection sketch**：client 给 request 加 unique `XID`，resend 复用同一 `XID`；server 对 seen request 返回 cached old reply，而不重跑 handler。
    - **At-most-once 的额外 state tradeoff**：要避免 client ID/XID collision；server 要决定何时丢弃 old replies；original 尚在执行时要用 pending state 协调 duplicate；server crash/restart 后若 duplicate table 只在 memory 中会遗忘，可能需要写 disk 或 replicate。
    - **Exactly-once 的讲义组合**：unbounded retries + duplicate detection + fault-tolerant service。该组合只见于本节对齐讲义，老师在口述中只概括为 hard、需要 persistent state，并关联 Lab 3。

## 概念、符号与推导

- **RPC handler concurrency**：RPC library 可并发执行 requests；server object 的 shared mutable state 必须 synchronization。
- **Transport/RPC error**：`Call()` 未取得 reply；它不能告诉 application handler 是否已经执行。
- **Service-level error**：server 正常 reply，但业务结果失败，例如 `ErrNoKey`；它与“没收到 reply”不同。
- **At-least-once**：通过 retry 追求 operation 至少发生一次，但允许 duplicate execution。
- **At-most-once**：operation 发生 `0` 或 `1` 次；要么本次成功执行，要么 caller 只得到 failure/ambiguity，不由 RPC 自动保证最终成功。
- **Exactly-once**：最终既不漏执行也不重复执行；口述强调需要 durable state、实现昂贵。
- **XID duplicate suppression（讲义）**：同一 logical request 的 retries 使用同一 identifier；server 保存 `seen[xid]` 与 `old[xid]`。
- **Failure ambiguity**：no response 与 no execution 不是同一命题；request 丢失、server 执行后 crash、reply 丢失对 client 都可能表现为 timeout/error。
- **本段无公式推导**。`0/1/multiple executions` 是语义分类，不是概率或数学推导。

## 本段掌握检查

1. **问：为什么 toy KV server 的 `Get`/`Put` 必须使用同一个 mutex？**  
   **答：**RPC requests 可由多个 goroutines 并发执行，它们共享同一 `data` map；同一 mutex 使 map read/update mutually exclusive。

2. **问：client timeout 后为什么不能断言 operation 没执行？**  
   **答：**request 可能未到 server，也可能 handler 已执行但 server 在 reply 前 crash，或 reply 在 network 中丢失；这些都表现为 no response。

3. **问：at-least-once 与 at-most-once 的主要 tradeoff 是什么？**  
   **答：**at-least-once 通过 retries 减少漏执行但允许 duplicates；at-most-once 防止重复，却允许 operation 为 zero times，失败时 caller 仍有 ambiguity。

4. **问：讲义中的 XID 如何帮助 duplicate suppression？**  
   **答：**同一 logical request 的 retries 使用同一 XID；server 若已 seen，就返回 cached reply 而不重新执行 handler。

5. **问：为什么 Go RPC 的一次 `Call` 被称为简单的 at-most-once，而 application retry 仍要小心？**  
   **答：**library 不自动 resend 同一 request，所以该 call 不因 library 行为重复；但 error 不说明是否已执行，application 重新发起 call 可能让同一 logical operation 再执行。
