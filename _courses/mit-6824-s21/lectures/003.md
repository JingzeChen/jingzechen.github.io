## 老师的教学主线

1. **先建立设计张力**（`00:00:00-00:09:59`）：durable storage 简化 application recovery；high performance 需要 sharding，scale 带来 failures，fault tolerance 需要 replication，而 replica coordination 又影响 consistency/performance。随后用并发写 trace 引入 ideal consistency。材料核对仅限 `l-gfs.txt` p.1。
2. **用错误复制方案证明必须协调**（`00:10:01-00:20:00`）：两个 replicas 各自接收写、reads 任取副本，会让后续读取无稳定结果；GFS 因大规模工业实践、single master 与 relaxed consistency 成为案例。段末把目标接到 MapReduce。
3. **由 aggregate throughput 推到 architecture**（`00:20:00-00:29:57`）：历史单盘约 `30 MB/s`，聚合读超过 `10,000 MB/s`；GFS 用 `64 MB` chunks、master metadata 与 client-to-chunkserver direct data path 实现 parallel reads。
4. **把 master state 放进 failure/recovery 框架**（`00:29:58-00:39:53`）：namespace 与 version 进入 stable log/checkpoint；locations、primary 和 lease 可重建；client 查询并缓存 handle/list/version，再读取 nearest chunkserver。
5. **逐步执行 record append**（`00:39:53-00:49:52`）：master 建立带 lease 的 primary epoch并持久化 version；client pipeline data；primary 验证 lease、选择 offset、命令 secondaries；任一失败返回 error，client 从头 retry。
6. **观察 relaxed semantics 的应用后果**（`00:49:53-00:59:53`）：retry 可能产生 duplicate records，library 用 unique ID 去重、checksum 检错；cached version 与 stale secondary 可共同停在 `10`，即使活动组已升到 `11`，旧 client 仍能读旧数据。
7. **用 lease 收束 failure cases**（`00:59:53-01:06:17`）：reconfiguration 细节被老师明确标为推测；确定结论是 master 必须等 old lease 过期，old primary 到期后拒绝 writes，从而阻止 split brain。最后给出 all replicas or none visible 的 stronger-consistency 方向。

## 核心概念与依赖关系

```text
MapReduce large-data workload
  -> high aggregate throughput
  -> shard files into 64 MB chunks across chunkservers
  -> many servers and disks
  -> frequent failures
  -> replicate each chunk
  -> replicas may diverge
  -> need a primary to order mutations
  -> need version numbers to reject stale epochs
  -> need leases to bound primary authority
  -> need log/checkpoint to recover master durable state
  -> client caching and direct replica reads improve throughput
  -> stale metadata can expose stale replicas
  -> failed append + retry gives at-least-once / duplicates
  -> application library compensates with record IDs and checksums
```

关键依赖有三条：

1. 不先理解 `master` 只在 metadata/control path，就无法解释 direct chunkserver reads 为什么能扩展吞吐，也无法解释 client cache 为什么重要。
2. 不先区分 durable version 与 volatile locations，就无法判断 reboot 后为何不能取“当前 live replicas 的最大 version”。
3. 不先区分 data pipeline 与 mutation order，就容易误以为 bytes 到达 replicas 已等于 append committed，也看不到 partial success + retry 如何产生 duplicates。

## 关键协议与故障场景

### read

```text
client -> master: filename, offset
master -> client: chunk handle, chunkserver list, version
client caches metadata
client -> nearest chunkserver: read
chunkserver checks version and returns data
```

该路径优化 single-master load 与 network locality（`00:35:52-00:39:53`），但 cache 使 client 可能继续使用旧 list/version。

### record append

```text
master selects primary/secondaries -> grants lease -> increments version
client pipelines temporary data to all replicas
client sends append command to primary
primary checks version + lease -> selects offset -> writes locally
primary orders secondaries to write same offset
all acknowledge -> success; any failure -> error; client retries
```

该路径由 `00:41:37-00:49:46` 口述。primary 排列 mutation，network pipeline 只负责高效传播数据；二者不能混为一谈。

### stale read homework 场景

```text
C_old caches {S2, version 10}
S2 loses contact with master/active replica group
master establishes version 11 and C_new completes a write
C_old can still reach S2
C_old sends version 10; S2 has version 10; check passes
C_old reads stale data
```

这是课程 [MATERIALS.md](/courses/mit-6824-s21/materials/) 中 Lecture 3 Question 的课堂回答（`00:55:02-00:58:43`）。关键不是 version 完全无用，而是 client 与 stale replica 可以共享同一个旧 version。

### split-brain prevention

```text
master cannot reach old primary
  -> do not appoint new primary while old lease may still be valid
  -> wait for lease expiry
old primary at expiry
  -> reject new writes
master after expiry
  -> may appoint new primary
```

这一安全条件来自 `01:01:44-01:03:40`；本讲没有展开 clock-error model 或 lease duration。

## 易错点与待核对项

- replication 提供冗余，不自动提供 strong consistency；无协调 replicas 即使都不 crash 也可能状态不同。
- global 在本讲被解释为 applications 共享同一文件系统，不应擅自扩写为跨全球多地域部署。
- checkpoint 加速 recovery，不替代 log；chunkserver locations 可重建，但 namespace mapping 与 version 不能只取当前 live servers 的报告。
- client cache 减轻 master load，却也是 stale metadata 的必要条件之一；version check 不是绝对 stale-read barrier。
- checksum 检测 corrupted bytes，unique record ID 识别 duplicates；二者职责不同。

# 第 1 段：为什么分布式存储困难，以及理想一致性

- **时间范围**：`00:00:00-00:09:59`
- **课堂证据**：`transcript`（`00:00:00-00:09:57`）

## 本段在整讲中的作用

老师先给出全讲路线：从存储系统（storage system）的重要性出发，再进入 GFS 的主要设计，并把一致性（consistency）设为贯穿本讲的主线；稍后还会用讨论题继续检验一致性场景（`00:00:01-00:00:43`）。本段因此不是直接罗列 GFS 组件，而是在建立后续分析所需的问题链：高性能要求分片，规模带来持续故障，容错需要复制，而复制又让副本可能不一致（`00:02:56-00:06:51`）。

这条问题链与讲义一致：`l-gfs.txt` p.1 将课程主题概括为 parallel performance、fault tolerance、replication、consistency，并把“更强一致性通常牺牲性能”列为核心权衡。课堂在本段只展开到并发写与后续读的理想行为；GFS 的具体架构、读写协议和 lease 尚未开始。

## 教学展开

### 1. 先说明为什么课程反复讨论存储

老师把耐久的存储系统称为构建容错应用的关键 building block（`00:00:51-00:01:14`）。如果持久状态都交给存储后端，应用层就可以近似保持无状态（stateless）：应用自身只有 soft state，没有必须自行维护的 hard state；进程崩溃后可快速重启，再从分布式存储读取状态（`00:01:15-00:02:03`）。

随后用网站架构作例子：storage backend 保存状态，application middle tier 执行 JavaScript、Go 等应用逻辑，再向 Internet client 提供前端服务（`00:02:06-00:02:28`）。这种分层简化了应用，却把难题集中到存储系统本身：它必须高度容错，而容错存储并不容易设计（`00:02:38-00:02:51`）。

### 2. 从性能目标推导出复制与一致性难题

GFS 面向 MapReduce 类型应用，首先要求高性能（high performance）（`00:03:05-00:03:17`）。单台机器的磁盘与网卡吞吐有限，因此要把数据分片（shard）到多台服务器、多个磁盘和多张网卡上（`00:03:21-00:03:51`）。

规模扩大后，故障从例外变成常态。老师假设每台机器约一年故障一次，课堂据此估算一千台机器每天约有三台故障；他还把这与开课时自己的笔记本故障联系起来（`00:03:55-00:04:38`）。机器数继续扩展到一万或十万时，设计就必须默认会发生故障（`00:04:41-00:04:50`）。

存储容错的典型方法是复制（replication）：把数据复制到多个磁盘，使一个磁盘失败时其他磁盘仍可能保有数据（`00:05:01-00:05:13`）。但多个位置的数据可能不同步，于是出现潜在不一致（inconsistency）（`00:05:18-00:05:27`）。若希望复制系统表现得像未复制系统一样，就需要协调协议；协议会增加通信，甚至要求读写 durable storage，而持久化 I/O 较昂贵（`00:05:40-00:06:17`）。

老师最后把因果链收束为全课反复出现的设计张力（`00:06:20-00:06:51`）：

1. 高性能需要多服务器并行与数据分片。
2. 服务器越多，故障越频繁。
3. 容错通常依赖复制。
4. 复制使不同位置的数据可能失步。
5. 修复不一致需要协议，而协议可能降低性能。

### 3. 用单机模型引入理想一致性

老师把理想一致性（ideal consistency）先近似描述为“系统表现得像一个单一系统”（`00:06:56-00:07:29`）。实现这一目标有两个主要障碍：并发（concurrency）和故障（failure）（`00:07:31-00:07:47`）。本段先讨论并发；即使只有一台多处理器机器，多个客户端请求也可能在内部并行执行，因此仍需定义什么结果才算正确（`00:07:48-00:08:14`）。

### 4. 从读者视角定义并发 trace 的允许结果

老师构造四客户端场景：`C1` 写 `x=1`，`C2` 同时写 `x=2`；之后 `C3` 读取 `x`，再之后 `C4` 读取 `x`（`00:08:18-00:09:16`）。一致性规则通常从 reader 能观察到什么来表述（`00:08:35-00:08:54`）。

对于 `C3`，因为两次写并发发生，返回 `1` 或 `2` 都可以，不必预先规定两次写的具体顺序（`00:09:20-00:09:56`）。老师在本段末开始追问哪些值不应出现，回答跨入下一段（`00:09:57-00:10:06`）；完整结论将在第 2 段继续。

## 概念、符号与推导

### 核心概念

- **durable storage**：应用崩溃、重启后仍可依赖的持久状态来源（`00:01:15-00:02:03`）。
- **soft state / hard state**：本段中，应用可丢失并重建的是 soft state；必须持久保存的状态交给存储系统，属于 hard state（`00:01:43-00:02:03`）。
- **sharding**：把数据分散到多台服务器或多个磁盘，以叠加磁盘和网络吞吐（`00:03:21-00:03:51`）。
- **replication**：把同一数据保存在多个磁盘上，以承受部分故障（`00:05:01-00:05:13`）。
- **ideal consistency**：本段的工作定义是复制或并发系统在外部看来像一个单一系统（`00:05:40-00:05:48`、`00:07:10-00:07:29`）。`l-gfs.txt` p.1 进一步用“单服务器逐个执行操作，读反映先前写”核对这一目标。
- **trace**：按客户端操作及先后关系描述一次执行，再讨论哪些观察结果属于正确行为；术语在下一段 `00:10:45-00:10:58` 才被明确说出，本段只建立该例子。

### 课堂符号

```text
C1: W(x, 1)  ┐
              ├─ concurrent writes
C2: W(x, 2)  ┘
C3: R(x) -> 1 or 2
C4: R(x) -> ?    （结论在下一段完成）
```

这里的 `C1` 至 `C4` 是客户端（client），`W` 是写（write），`R` 是读（read）。这不是老师给出的形式化公式，而是对板书操作的结构化转写（`00:08:18-00:09:56`）。

### 口头数量估算

在“每台机器约一年故障一次”的简化假设下，一千台机器的期望故障数约为：

$$
\frac{1000}{365}\approx 2.7\approx 3\text{ 台/天}
$$

课堂只给出“约三台/天”的口头答案（`00:04:09-00:04:31`）；上式只是把该口头估算显式化，不代表更完整的故障概率模型。

除上述估算与操作 trace 外，本段无公式推导。

## 例子与课堂提示

- **网站分层**（`00:02:06-00:02:28`）：用于说明把 persistent state 集中到 storage backend 后，应用中间层可以更容易重启和替换。
- **课堂开头的笔记本故障**（`00:04:29-00:04:38`）：用于把“大规模系统持续发生机器故障”从抽象概率变成日常事件。
- **一千台机器、每台一年故障一次**（`00:04:09-00:04:31`）：用于说明 scale 会把低频单机故障放大为每天都要处理的系统事件。
- **`C1/C2` 并发写、`C3/C4` 后续读**（`00:08:18-00:09:57`）：用于从 reader 观察结果定义 consistency，而不是只说“副本应该一样”。

### 常见误解

- **误解：使用 replication 就自动得到强一致性。** 复制首先提供冗余，但副本可能失步；还需要协调协议（`00:05:18-00:06:17`）。
- **误解：并发写必须由规范预先指定谁先谁后。** 本例允许 `C3` 返回 `1` 或 `2`；关键是整个 trace 的后续观察必须符合一个可接受的单一顺序（`00:09:20-00:09:56`，后续约束见第 2 段）。
- **误解：应用无状态意味着系统没有持久状态。** 持久状态并未消失，而是被移到 storage backend（`00:01:15-00:02:14`）。
- **误解：更强一致性的成本只有几条网络消息。** 老师特别提醒协议还可能要求 durable storage I/O，而这通常昂贵（`00:05:51-00:06:17`）。

# 第 2 段：从理想 trace 到 GFS 这项案例研究

- **时间范围**：`00:10:01-00:20:00`
- **课堂证据**：`transcript`（本段无课件材料）
- **材料边界**：本段所有课堂断言仅来自上述时间窗；不引用 `l-gfs.txt` 或 GFS 论文补足细节。

## 本段在整讲中的作用

本段先完成上一段被切开的理想一致性例子，再用一个“最简单但错误”的双副本方案说明 replication 本身不能保证 consistency（`00:10:01-00:14:21`）。在这个问题框架建立后，老师才正式把 GFS 定位为全学期第一项综合案例：它同时暴露 performance、fault tolerance、replication 与 consistency 的冲突，并以大规模工业实践作出当时并不标准的取舍（`00:14:25-00:18:20`）。段末转向 MapReduce 工作流，开始说明 GFS 的性能目标从哪里来（`00:18:31-00:20:00`）。

## 教学展开

### 1. 完成四客户端的理想一致性例子

上一段末尾问 `C3` 不应读到什么。本段开头学生回答 `7`，老师确认：因为没有任何客户端写过 `7`，它不是合理结果；`C3` 应返回并发写入的 `1` 或 `2`（`00:10:01-00:10:10`）。

接着讨论较晚发生的 `C4` 读取。如果 `C3` 已经返回 `1`，`C4` 也应返回 `1`；若 `C3` 返回 `2`，`C4` 也应返回 `2`（`00:10:14-00:10:42`）。老师借此说明 consistency 可以通过执行轨迹（trace）来定义：列出操作的并发与先后关系，再判断某个观察结果是否正确（`00:10:45-00:10:58`）。在单机并发程序中，lock 是实现这类约束的标准技术之一（`00:11:00-00:11:15`）。

### 2. 构造一个没有协调协议的错误复制方案

老师回到理想一致性的第二个障碍 failure，并画出两个带磁盘的服务器 `S1`、`S2`（`00:11:21-00:11:40`）。为了证明“必须做某种协调”，他故意选择一个非常差的复制方案：每个写客户端自行向两个服务器写入，但双方不协调；读客户端可以任选一个 replica 读取（`00:11:44-00:12:57`）。

在 `C1` 写 `x=1`、`C2` 写 `x=2` 的场景中，`C3` 可能从任意副本读到 `1` 或 `2`；更晚的 `C4` 仍可能读到 `1` 或 `2`（`00:13:00-00:13:41`）。所以即便中间没有新写入，同一应用也可能第一次读到 `1`、下一次读到 `2`，这让应用逻辑难以推理（`00:13:42-00:14:01`）。问题的根源不是“使用了两台服务器”，而是 reader、writer 与 replicas 之间没有协议；后续课程会学习具有不同容错与一致性权衡的协议（`00:14:04-00:14:32`）。

### 3. 说明为什么选择 GFS 作为案例

GFS 把前述核心问题集中到一套真实设计中：它追求高性能，因此使用 replication 和 fault tolerance，同时又必须处理 consistency 的困难（`00:14:34-00:15:30`）。它也是成功投入使用的系统；老师提到后继系统 Colossus，以及受 GFS 启发、面向 MapReduce 类用途的 HDFS（`00:15:33-00:16:01`）。

老师强调，GFS 发表时，distribution、replication、fault tolerance 和 consistency 的基本概念并不新；新的挑战来自数千台机器的实际规模（`00:16:05-00:16:39`）。组合这些技术的方式也不标准，课堂突出两点：

1. 用一台 single master 负责系统中几乎所有协调，形成明显的单点风险（`00:16:43-00:17:17`）。
2. 接受可能出现的一致性异常，而不是以消除所有异常为首要目标（`00:17:21-00:17:47`）。

因此，GFS 的研究价值既来自大规模真实运行，也来自它在性能、故障与一致性之间采取的非传统组合；这些冲突至今仍是分布式存储的重复主题（`00:17:47-00:18:20`）。

### 4. 把性能目标接回 MapReduce

老师把 GFS 概括为“MapReduce 的文件系统”：目标是支撑许多 MapReduce jobs 并获得高性能（`00:18:31-00:19:02`）。他引用上一讲 MapReduce 图中的三个阶段：mapper 从 GFS 读输入、系统进行内部 shuffle、reducer 把结果写回 GFS（`00:19:14-00:19:43`）。一个作业的速度因而部分取决于大量 mappers 能以多快的速率并行读取 GFS；该性能图的数值讨论延续到下一段（`00:19:47-00:20:00`）。

## 概念、符号与推导

### 理想 trace 的完整约束

```text
C1: W(x, 1)  ┐
              ├─ concurrent
C2: W(x, 2)  ┘
C3: R(x) -> v
C4: R(x) -> v    （C4 在 C3 之后，期间没有新写）

允许：v = 1 或 v = 2
不允许：v = 7；或 C3 = 1 而 C4 = 2

write: client -> S1 and S2, no coordination

```

由于两个 replica 对并发写的最终状态可能不同，较晚的 reads 没有共同结果保证（`00:11:44-00:14:01`）。本段无公式推导。

### GFS 的课堂定位

- **single master**：一台机器承担主要协调；老师将其视为当时学术设计中不寻常的 single point of failure（`00:16:57-00:17:17`）。

- **scale as novelty**：基本机制已知，但数千台机器的实际规模带来此前系统未处理的挑战（`00:16:05-00:16:39`）。

## 例子与课堂提示

- **`7` 不是合理读结果**（`00:10:01-00:10:10`）：用于区分“并发允许多个合法顺序”和“系统可以返回任意值”。
- **同一应用连续两读变值**（`00:13:42-00:14:01`）：用于展示未协调 replicas 给应用程序员带来的直接困难。
- **Colossus 与 HDFS**（`00:15:33-00:16:01`）：用于说明 GFS 不是只存在于论文中的实验设计，而是有后继和影响的工业系统。

### 常见误解

- **误解：只要 `C3` 和 `C4` 各自读到某个写过的值就算一致。** 理想例子还要求没有新写时，后读不能任意改成另一个结果（`00:10:14-00:10:42`）。

- **误解：GFS 是追求所有场景下 strong consistency 的通用文件系统。** 本段把它定位为面向 MapReduce 性能目标、愿意接受部分 anomalies 的案例（`00:17:21-00:19:02`）。

# 第 3 段：从聚合吞吐目标到 GFS 总体架构

- **时间范围**：`00:20:00-00:29:57`
- **课堂证据**：`transcript`（本段无课件材料）

## 本段在整讲中的作用

上一段把 GFS 定位为 MapReduce 的文件系统，本段先用吞吐量数量级解释“高性能”究竟意味着什么，再列出 big、fast、global/shared、fault-tolerant 四类目标（`00:20:00-00:23:47`）。这些目标随后直接推导出架构分工：single master 回答元数据位置，clients 拿到位置后绕过 master 直接并行读取 chunkservers，从而让数据面吞吐随磁盘和机器数量扩展（`00:24:05-00:28:08`）。最后，老师从总体图收拢到 master 内存状态，为下一段讨论持久化与恢复作铺垫（`00:28:12-00:29:57`）。

## 教学展开

### 1. 先判断聚合读取数字是否真正“快”

多个 MapReduce jobs 的许多 mappers 会同时读取，甚至可能读取同一批文件；图中的输入曲线表示一个 job 的 mappers 从文件系统集体读取的 MB/s（`00:20:00-00:20:23`）。老师口述该曲线超过 `10,000 MB/s`，然后追问这个数字是否值得惊讶（`00:20:23-00:20:50`）。

判断必须结合当时硬件：老师说论文时代单盘吞吐大约是 `30 MB/s`，或至少在几十 MB/s 的量级，因此超过 `10,000 MB/s` 的聚合吞吐很可观（`00:21:08-00:21:29`）。真正的设计目标不是固定追求某个历史数字，而是让约一千台机器上的磁盘能够同时工作，使总吞吐接近“单盘吞吐 × 机器数”（`00:21:30-00:22:02`）。

### 2. 列出 GFS 服务对象与关键属性

老师首先强调 large data sets，例如把完整 Web crawl 存入分布式文件系统（`00:22:07-00:22:32`）。其次必须 fast；方法是 automatic sharding，把文件分布到多个磁盘，让多个 clients 并行读取（`00:22:35-00:22:50`）。

第三个属性是 global，老师随即把它解释为 shared：所有应用看到同一个文件系统。一个 MapReduce job 可以读取既有文件并产生新文件，后续 job 再复用这些结果，从而方便应用间共享（`00:22:52-00:23:23`）。第四个属性是 fault tolerant；大规模环境必然发生故障，GFS 希望尽可能自动恢复，但老师明确说它并非完全自动（`00:23:26-00:23:47`）。

### 3. 从应用接口进入总体设计

应用可能包含多个 map tasks 和 reduce tasks，并链接（link with）GFS client library。老师特别区分：这不是日常编辑、编译文件所用的 Linux file system，而是面向大型计算的 special-purpose file system（`00:24:05-00:24:47`）。

为让单个应用利用多机总吞吐，系统设置一个 master 保存“数据在哪里”的信息；client 只周期性联系 master 获取元数据（`00:24:54-00:25:19`）。例如 client 打开文件时，向 master 提供 filename；master 返回构成文件的 chunk handles，以及保存相关 chunks 的 chunkserver locations（`00:25:19-00:25:45`）。

### 4. 文件切成大 chunk，数据路径绕过 master

一个大文件由 `chunk 0`、`chunk 1`、`chunk 2` 等多个独立 chunk 组成，每个 chunk 大小为 `64 MB`（`00:25:51-00:26:12`）。若应用要读文件的第二个 `64 MB` 区间，master 返回 `chunk 1` 的 handle 和持有它的 servers（`00:26:12-00:26:29`）。不同应用或 task 可以同时索取同一文件的不同 chunks，并得到各自的 locations（`00:26:34-00:26:46`）。

获得 locations 后，GFS client 直接与 chunkservers 通信，数据不经过 master（`00:26:50-00:27:08`）。多个 map tasks 因而可以同时从不同 disks 读取；这个并行数据路径正是聚合高吞吐的来源（`00:27:10-00:27:46`）。chunkserver 本质上是一台带磁盘的 Linux 机器，每个 `64 MB` chunk 作为一个 Linux file 存在本地 Linux file system 中（`00:27:53-00:28:08`）。

### 5. 开始枚举 master state

老师把 master 称为 control center，并开始列出其状态（`00:28:12-00:28:29`）：

1. `filename -> array of chunk handles`（`00:28:32-00:28:49`）。
2. 大部分信息放在 memory 中，使单个 master 能快速响应许多 clients，减少单机 CPU、memory 与 network interface 成为瓶颈的风险（`00:28:49-00:29:14`）。
3. 每个 chunk handle 对应 version number 和保存副本的 chunkservers list（`00:29:14-00:29:35`）。
4. 这些服务器中一个被指定为 primary，其余是 secondaries；典型情况下一个 chunk 存在三台服务器上（`00:29:40-00:29:55`）。

lease time 从 `00:29:58` 开始讲，属于下一段。

## 概念、符号与推导

### 聚合吞吐关系

老师给出的设计直觉可以写成：

$$
\text{aggregate throughput}\approx
\text{single-disk throughput}\times\text{number of active disks}
$$

课堂口头例子为约一千台机器、每块磁盘约 `30 MB/s`（`00:21:08-00:21:52`）。因此理想数量级是：

$$
1000\times 30\ \text{MB/s}=30{,}000\ \text{MB/s}
$$

老师用乘法关系说明扩展目标，并没有声称实测值等于该理想上限；实测图只被口述为超过 `10,000 MB/s`。

```text
filename
  -> [chunk handle 0, chunk handle 1, chunk handle 2, ...]

chunk handle
  -> version number
  -> [chunkserver locations]
  -> one primary + secondaries
```

该结构整理自 `00:25:19-00:26:29` 与 `00:28:32-00:29:55`。本段尚未说明哪些字段必须持久化、locations 如何恢复，也尚未解释 primary 的 lease。

```text
metadata/control path: client <-> master
data path:             client <-> chunkserver
```

master 返回 handle 和 locations，实际文件数据由 chunkserver 直接送到 client（`00:24:54-00:27:08`）。

# 第 4 段：master 持久状态、恢复与读路径

- **时间范围**：`00:29:58-00:39:53`
- **课堂证据**：`transcript`（本段无课件材料）
- **材料边界**：只依据本时间窗区分 stable/volatile state 并整理读取步骤；未用论文或讲义补充恢复协议。

## 本段在整讲中的作用

上一段刚列出 master state，本段立即追问这些状态在 master crash 后怎样恢复（`00:29:58-00:35:46`）。老师通过 log、checkpoint 和逐字段问答建立关键边界：namespace 与 chunk version 必须持久化，chunkserver locations、当前 primary 和 lease 可在重启后重建。随后他进入两个基本操作中的 read，解释 master 只提供元数据、client 缓存后读取最近副本的完整路径（`00:35:52-00:39:53`）。这一段把 architecture 转化为 failure/recovery 与 performance 的具体机制，也埋下缓存导致 stale read 的伏笔。

## 教学展开

### 1. 补全 master state：primary 带 lease

每个 primary 都有关联的 lease，master 因而还维护 lease time（`00:29:58-00:30:02`）。本段此时只列出该字段，lease 如何避免两个 primary 同时工作要到第 7 段才展开。

### 2. 用 operation log 保证已确认的 namespace 变更可恢复

master 是控制中心。创建文件、改变 namespace、改变 filename 到 chunks 的映射等操作都先写入位于 stable storage 的 log（`00:30:06-00:30:42`）。顺序至关重要：master 先把变更写到 stable storage，再向 client 回复成功；若随后 crash/reboot，就能 replay log 重建内部状态（`00:30:49-00:31:11`）。

老师给出反例：若 master 先回复 client“文件已创建”，还没持久化就崩溃，重启后文件可能不存在，client 会观察到前后矛盾（`00:31:11-00:31:27`）。因此 write-before-reply 是这里的 consistency point。

### 3. 用 checkpoint 缩短恢复时间

从系统建立之初回放完整 log 会让唯一 master 长时间不可用（`00:31:31-00:31:41`）。所以 master 周期性把自身状态写成 checkpoint 保存到 stable storage；重启时加载最近 checkpoint，只 replay 其后的 log tail（`00:31:42-00:32:05`）。checkpoint 不替代 log，而是缩短恢复路径。

### 4. 逐项判断哪些 master state 必须持久化

老师先问 `filename -> chunk handles[]` 是否可以只放 memory。课堂结论是不能：文件创建及映射必须进入 log/stable storage，否则 crash 后会丢失已经创建的文件；重启时再由 log 恢复到内存（`00:32:08-00:33:25`）。

接着问 `chunk handle -> chunkservers list`。它可以是 volatile state，因为 master reboot 后会询问 chunkservers 各自持有哪些 chunks，再重建 locations；当前 primary/secondaries 和 lease time 也被课堂归入可重建状态（`00:33:26-00:34:02`）。

最后问 version number。它必须保存在 stable storage：如果整个系统停机后只有持有旧版本 `14` 的 chunkserver 先回来，而真正最新的服务器仍离线，master 必须知道 `14` 已经过期，不能把当前 live servers 中的最大版本误当作全局最新版本（`00:34:03-00:35:39`）。

### 5. 展开 read protocol

client 先把 `filename + offset` 发给 master，请求该位置对应的 chunk handle 和 chunkservers（`00:35:52-00:36:30`）。master 根据 filename 的 handles 数组定位目标 chunk，再返回 chunk handle、持有该 chunk 的服务器列表以及 version number；课堂示例为 handle `221`、三台机器、version `10`（`00:36:30-00:37:20`）。

client 缓存这组信息，然后从最近的 chunkserver 读取（`00:37:26-00:37:40`）。缓存减少重复访问 master，因为 single master 的 memory、CPU 与 network interface 都有限；太多 clients 每次读写都查询它会使其无法扩展（`00:37:51-00:38:36`）。选择最近副本则减少网络流量和跨数据中心网络拓扑的开销，提高大量 clients 并行读取时的 aggregate throughput（`00:38:42-00:39:22`）。

chunkserver 检查 version number；若版本可接受，就发送数据（`00:39:28-00:39:43`）。老师在 `00:39:53` 回答这样做是为了尽量避免读取 stale data，但马上提醒系统并不能完美杜绝 stale read；完整说明进入第 5、6 段。

## 概念、符号与推导

### master state 的课堂分类

| 状态 | stable storage? | 本段理由 |
|---|---:|---|
| `filename -> chunk handles[]` | 是 | 否则已确认的文件/映射会在 crash 后消失（`00:32:17-00:33:25`） |
| `chunk handle -> version number` | 是 | 必须识别先上线但已 stale 的 chunk replica（`00:34:03-00:35:39`） |
| `chunk handle -> chunkservers[]` | 否，可重建 | reboot 后询问 chunkservers（`00:33:26-00:33:51`） |
| current primary/secondaries | 否，可重建 | 课堂把它们与 locations 一并视为 volatile state（`00:33:49-00:34:02`） |
| lease time | 否，可重建 | 同上（`00:33:49-00:34:02`） |
| operation log / checkpoint | 是 | 用于 crash recovery（`00:30:24-00:32:05`） |

### 恢复顺序

```text
normal operation:
namespace change -> append log on stable storage -> reply to client

master restart:
load latest checkpoint -> replay log entries after checkpoint -> rebuild memory state
                         -> ask chunkservers to rebuild locations
```

这里是对 `00:30:24-00:33:51` 的顺序化整理。本段没有说明 checkpoint 的创建协议或 log 的副本方式，不应自行补足。

### read protocol

```text
1. client -> master: filename, offset
2. master: locate chunk handle
3. master -> client: handle, chunkserver list, version
4. client: cache metadata
5. client -> nearest chunkserver: read request
6. chunkserver: check version, return data if acceptable
```

步骤来自 `00:35:52-00:39:43`。本段无公式推导。

## 例子与课堂提示

- **先回复、后持久化的反例**（`00:31:11-00:31:27`）：用于证明 log 必须在 client success reply 之前落盘。
- **checkpoint + log tail**（`00:31:31-00:32:05`）：用于区分 correctness 所需的可恢复记录与 recovery speed 优化。
- **最新 replica 未上线、旧 version `14` 先上线**（`00:34:28-00:35:39`）：用于证明不能简单取所有 live chunkservers 报告的最大版本。
- **handle `221`、三台服务器、version `10`**（`00:37:09-00:37:20`）：用于具体化 master 的 read reply。
- **client cache 与 nearest replica**（`00:37:26-00:39:22`）：前者减轻 single master 负载，后者减轻网络负载；两者都服务吞吐，但缓存也为后续 stale metadata 场景创造条件。

### 常见误解

- **误解：有 checkpoint 后就不需要 log。** checkpoint 只提供较新的恢复起点，之后的操作仍要由 log tail 恢复（`00:31:31-00:32:05`）。
- **误解：master 的所有内存字段都必须逐项持久化。** chunkserver locations 可通过重启后询问 chunkservers 重建（`00:33:26-00:33:51`）。
- **误解：重启后取 live replicas 的最大 version 就一定正确。** 最新 replica 可能仍离线，所以 master 必须保有自己的持久版本上界（`00:35:01-00:35:39`）。
- **误解：client 每次读取都要经过 master。** client 缓存元数据并直接读取 chunkserver（`00:37:26-00:38:36`）。
- **误解：version check 可以彻底消除 stale reads。** 老师只说尽量减少，并明确预告不能做到完美（`00:39:28-00:40:03`）。

## 本段掌握检查

1. **问：为什么 master 要先写 log 再回复 client？**  
   **答：** 这样已确认的 namespace 变更在 crash/reboot 后可由 log 重放；反过来会出现 client 见过“成功”但文件重启后消失的异常（`00:30:49-00:31:27`）。

# 第 5 段：record append、primary 排序与失败重试

- **时间范围**：`00:39:53-00:49:52`
- **课堂证据**：`transcript`（本段无课件材料）
- **材料边界**：协议步骤按本时间窗的课堂口述记录；未从论文图 2 或 `l-gfs.txt` 补齐老师未讲的分支。

## 本段在整讲中的作用

上一段完成 read path，本段先承认 version check 只能尽量减少 stale reads，随后转入 write，重点分析 Google 工作负载常用的 record append（`00:39:53-00:41:35`）。老师把写入拆成两个阶段：先把数据通过网络 pipeline 送到所有 replicas，再由 primary 检查 lease、选择 offset、把 mutation 以同一位置下发给 secondaries（`00:41:37-00:48:21`）。段末加入 secondary failure 与 client retry，说明“返回 error”不等于“没有任何副本写入”，并引出下一段的 duplicate record 异常（`00:48:28-00:49:52`）。

## 教学展开

### 1. 从 read 的局限转到 append

chunkserver 检查 version number 是为了避免 stale data，但老师明确说只能尽量减少，不能完美杜绝（`00:39:53-00:40:10`）。read 相对直接，因此他转向更复杂的 write，并把注意力集中到 append（`00:40:11-00:40:27`）。

record append 对 MapReduce 类工作负载重要，因为计算往往产生新结果并追加，而不是回头修改先前输出。学生先举 mapper，老师纠正 mapper 中间结果写本地文件，不是写 GFS；reducer 把最终计算结果追加到 GFS 才是更合适的例子（`00:40:40-00:41:35`）。

### 2. client 先向 master 查询最后一个 chunk 的 replica group

client 联系 master 查找要写的 chunk；master 先经 `filename -> chunk handles` 找到 handle，再经 `handle -> servers` 找到持有该 chunk 的服务器（`00:41:37-00:42:14`）。

老师分成“已有 primary”和“没有 primary”两种情况，重点展开后者（`00:42:14-00:42:33`）。如果尚无 primary，master 从可用 chunkservers 中选一个作为 primary，其余作为 secondaries，并授予 primary 带到期时间的 lease（`00:42:33-00:43:04`）。

### 3. 建立新 primary 时更新并持久化 version

每次建立新 primary，master 增加 version number；老师把这描述为该 chunk 进入一个新的 epoch（`00:43:04-00:43:35`）。master 把新 version 和 replica-group 角色发给 primary/secondaries，replicas 把 version 写到 disk（`00:43:35-00:44:53`）。

version 不能只在 memory 中：chunkserver crash/reboot 后仍需证明自己持有哪个版本，否则 master 无法区分最新数据和 stale data（`00:44:00-00:44:53`）。课堂随后说明，master 等待 primary/secondaries 确认 version 已落盘、primary 已收到 lease，master 自己也把 version 写盘，然后才向 client 回复 primary、secondaries 与 version（`00:44:58-00:45:29`）。

### 4. 先 pipeline 数据，但暂不执行 mutation

client 把要写的数据先发给列表中网络上最近的 replica；该服务器一边接收，一边继续推给下一个，直到所有 replicas 都拿到数据（`00:45:32-00:46:17`）。这样 client 的外向 network interface 可以持续把数据注入 pipeline，而不是串行重复发送多份，目标是提高 throughput（`00:46:19-00:46:32`）。

此时数据只是暂存在 replicas 旁边，并未写入目标 chunk 的 stable storage；数据传输与 mutation control 被分开（`00:46:35-00:46:45`）。

### 5. primary 决定 offset 并统一 mutation 顺序

数据就绪后，client 向 primary 发送 append request（`00:46:48-00:46:56`）。primary 检查请求的 version 是否匹配，并检查 lease 是否仍有效；lease 过期后不能接受 mutation，因为外部可能已有另一个 primary（`00:46:56-00:47:26`）。

检查通过后，primary 选择 append offset，先把记录写到自己的 stable storage，再告诉每个 secondary 把之前收到的数据写到同一 offset。课堂示例为 offset `125`（`00:47:26-00:48:05`）。只有 primary 和所有 secondaries 都成功写盘，primary 才向 client 回复 append success（`00:48:12-00:48:21`）。

### 6. 任一 secondary 失败则 client 收到 error，并从头 retry

如果 primary 已在自己的 disk 写入，但某个 secondary crash、网络不可达或没有响应，primary 向 client 返回 error（`00:48:28-00:48:51`）。client library 通常重新发起同一个 append，希望临时故障消失；老师称这种重试带来 at-least-once 行为（`00:49:06-00:49:22`）。

重试时 primary 不保证选择原 offset，而会选择新的 offset（`00:49:31-00:49:46`）。因此同一 record 可能已经在部分 replicas 的旧位置出现，又在新位置成功写入；具体副本图在下一段继续（`00:49:46-00:49:52`）。

## 概念、符号与推导

### record append 控制流

```text
1. client -> master: locate target chunk
2. if no primary:
   a. master selects primary and secondaries
   b. master grants lease
   c. master increments version
   d. replicas persist version; master persists version
3. master -> client: primary, secondaries, version
4. client pipelines data through replicas (temporary data only)
5. client -> primary: append request
6. primary checks version and lease
7. primary selects offset and writes locally
8. primary -> secondaries: write same data at same offset
9. all acknowledge -> success; any failure -> error
10. client retries after error, potentially at a new offset
```

步骤严格整理自 `00:41:37-00:49:46`。课堂没有在本段形式化 success/error 的状态机，也没有给出 quorum 规则；这里的 success 条件是老师口述的“primary 与所有 secondaries 都成功”。

### 两条相互独立的顺序

- **data flow order**：client 从较近 replica 开始，通过 pipeline 传播 bytes，服务 network throughput（`00:45:32-00:46:32`）。
- **mutation order/location**：primary 选择 offset，再命令 secondaries 在同一 offset 写入，服务副本间操作排序（`00:46:48-00:48:05`）。

本段无公式推导。

## 例子与课堂提示

- **mapper 与 reducer 的纠正**（`00:41:02-00:41:33`）：mapper 中间输出写 local files；用 reducer 结果写回 GFS 来解释 append 更准确。
- **version 必须落盘**（`00:44:23-00:44:53`）：用于说明 reboot 后只保留 memory version 会让 stale replica 冒充最新副本。
- **network pipeline**（`00:45:44-00:46:29`）：用于说明为何不让 client 独立、串行地向每个 replica 发送完整数据。
- **offset `125`**（`00:47:51-00:48:05`）：用于强调 primary 不只转发请求，还决定所有 replicas 使用的具体位置。

### 常见误解

- **误解：把数据 pipeline 到 replica 就已经完成 append。** 数据先临时缓存，之后才由 primary 发起有序 mutation（`00:46:35-00:47:45`）。
- **误解：client 自己决定 record offset。** offset 由持有有效 lease 的 primary 选择，并发送给 secondaries（`00:47:10-00:48:05`）。
- **误解：primary 写成功就可以向 client 返回 success。** 本段课堂要求所有 secondaries 也成功；任一未响应都返回 error（`00:48:12-00:48:51`）。
- **误解：client 收到 error 说明记录肯定没有写入任何地方。** primary 可能已经落盘，部分 secondaries 也可能成功，只是没有完成全部 acknowledgments（`00:48:28-00:49:22`）。
- **误解：retry 会覆盖或复用原 offset。** 老师明确说重试会取新 offset，这为 duplicates 留下空间（`00:49:31-00:49:46`）。

# 第 6 段：重复记录、应用补偿与 stale read 场景

- **时间范围**：`00:49:53-00:59:53`
- **课堂证据**：`transcript`（本段无课件材料）
- **材料边界**：只使用本时间窗的课堂对话。学生提出而老师未明确确认的细节单独标注，不当作协议事实。

## 本段在整讲中的作用

上一段说明 append retry 会选择新 offset，本段先把后果画到 replicas 上：旧尝试可能只写入部分副本，新尝试又在所有副本写入，于是同一 record 重复出现（`00:49:53-00:50:16`）。老师随后从应用角度追问这种弱语义是否可接受，给出 library-level unique ID 去重与 checksum 检错的补偿方式（`00:50:21-00:53:22`），并补充系统的 trusted-internal 边界（`00:54:04-00:54:52`）。后半段转向 homework 的 stale-read 场景，说明 client caching 如何绕过 master 的最新版本知识（`00:55:02-00:59:53`）。

## 教学展开

### 1. retry 使 replicas 出现重复且不完全相同的内容

老师延续上一段的图：一次 append 在 primary 和某些 secondaries 上可能已经写到旧 offset，但另一个 secondary 没写成功；client retry 后，同一数据又在新 offset 成功写到全部三份 replicas（`00:49:53-00:50:15`）。因此 record 可以 duplicated，各 replica 在失败窗口内也可能有 hole 或额外片段（`00:50:15-00:50:16`）。

这种行为不同于普通本地文件系统。老师用编译器输出块重复和 email body 重复作类比：任意块重复会让程序文件损坏或邮件内容怪异，应用不能假装它没有影响（`00:50:21-00:51:24`）。

### 2. 用 word count 追问 weak append semantics 的应用后果

学生以 MapReduce word count 为例：若同一个 `a,1` record 因 retry 出现两次，而应用不做处理，最终计数会错误（`00:51:30-00:52:04`）。另一名学生提到 checksum 和 unique ID；老师确认关键做法是应用通过 library 读写 records，library 在写入时附加 ID，在读取时识别相同 ID 并跳过重复项（`00:52:07-00:52:59`）。

checksum 承担另一项职责：检测 record bytes 是否被破坏（garbled/corrupted）；它不是识别 duplicates 的主要依据，去重依赖 record ID（`00:52:59-00:53:19`）。这体现 GFS 的设计边界：文件系统允许某些 anomaly，再由了解其语义的 application/library 补偿。

### 3. 解释为什么不立即为单个失败副本停写并重配置

学生问，能否记住失败 replica，只等它补写成功，而不是让所有 replicas 重试（`00:53:23-00:53:31`）。老师说存在多种设计，并给出当前选择的一个理由：如果只是临时网络断开，重试可能很快成功，write 可以继续，而不必立即做 reconfiguration（`00:53:35-00:53:58`）。这是 availability/progress 与更整洁写入语义之间的权衡，而不是宣称只有一种正确方案。

### 4. 明确 trusted internal system 假设

课堂确认 servers、clients、master 和 Google 编写的软件都被信任；这不是带完整 permissions/access control 的通用 Linux file system，而是 Google 内部文件系统（`00:54:04-00:54:31`）。老师还指出，我们能了解内部系统细节，是因为 Google 选择发表论文描述它（`00:54:34-00:54:52`）。

### 5. 从 append 后的 read 进入 stale-data homework

老师总结 read/write 已讲完，接下来 consistency 问题就是“append 后 read 能观察到什么”，并让 breakout room 讨论 homework（`00:55:02-00:55:34`）。讨论回来后，学生质疑：既然 client 与 chunkserver 都有 version number，二者不匹配时拒绝读取，是否就不可能 stale read（`00:55:43-00:56:25`）。

### 6. 构造 client cache 与 replica-group 版本分叉

老师给出关键场景（`00:56:36-00:58:28`）：

1. client 缓存某 chunk 的 version `10` 和包含旧 secondary `S2` 的服务器信息（`00:56:43-00:57:27`）。
2. `S2` 对 master/当前 replica group 看起来 crash 或 network-disconnected，于是 master 建立新的 primary epoch，把活动组提升到 version `11`（`00:57:27-00:57:44`）。
3. 另一个 client 在 version `11` 活动组完成新 write，chunk 的最新内容已经前进（`00:57:44-00:58:02`）。
4. 旧 client 仍可能从另一条网络路径访问 `S2`。它携带缓存的 version `10`，而 `S2` 自己也还是 version `10`；version check 在双方看来匹配，所以 `S2` 返回旧数据（`00:58:02-00:58:28`）。

问题不在于 master 不知道 `S2` stale，而在于旧 client 没有重新询问 master；协议也没有把 version `11` 主动推送给已缓存 version `10` 的 client（`00:58:32-00:58:43`）。

### 7. 区分 version number 与 write serial number

老师澄清，master 维护的 version number 只在选择新 primary 时增加，不是每次 write 都增加；另有 serial number 用来排列 writes，两者不同（`00:58:50-00:59:18`）。primary 要等待哪些 secondaries，由 master 在授予 lease 时告诉它（`00:59:24-00:59:34`）。

本段结束在学生追问“授予 lease 时某个 secondary 已经 down，master 如何处理”的句子中间（`00:59:40-00:59:53`）；老师的回答属于第 7 段。

## 概念、符号与推导

### at-least-once append 的可见结果

```text
attempt 1 at offset a:
  primary:   record R
  secondary 1: record R
  secondary 2: missing/error

retry at offset b:
  primary:   record R
  secondary 1: record R
  secondary 2: record R

possible logical scan: R appears more than once
```

这是对 `00:49:53-00:50:16` 的抽象；课堂中具体服务器标签和板书数值听写不完整，所以不把某一副本的精确字节布局写成确定事实。

### library compensation

```text
write: application record -> library adds unique record ID
read:  library sees same ID again -> suppress duplicate
check: checksum -> detect corrupted bytes
```

去重与检错分工来自 `00:52:07-00:53:19`。本段没有说明 ID 生成算法、checksum 算法或 false-positive 处理。

### stale-read trace

```text
t0: C_old caches {servers: [..., S2], version: 10}
t1: S2 loses contact with master/active group
t2: master establishes new primary epoch, active version = 11
t3: C_new completes a write on version-11 replicas
t4: C_old can still reach S2 and sends cached version 10
t5: S2 has version 10, check matches, stale data is returned
```

关键是网络可达性不对称与 client cache：`master !-> S2` 不推出 `C_old !-> S2`（`00:57:27-00:58:28`）。本段无公式推导。

## 例子与课堂提示

- **编译器输出块或 email body 重复**（`00:50:55-00:51:16`）：用于证明 duplicates 对普通 byte-oriented file use 并不自然。
- **word count 的两个 `a,1`**（`00:51:30-00:52:04`）：用于展示不去重会直接改变计算结果。
- **ID 与 checksum 的分工**（`00:52:39-00:53:19`）：ID 识别同一逻辑 record；checksum 检测 bytes 损坏。
- **临时网络断连**（`00:53:35-00:53:58`）：用于解释 retry 方案为什么优先让 write 继续，而不立即 reconfigure。
- **cached version `10` 对 stale `S2`**（`00:56:36-00:58:43`）：用于回答 course `MATERIALS.md` 中 Lecture 3 的 homework，即怎样让 client 在 GFS 读到 stale data。

### 常见误解

- **误解：checksum 可以自动去重。** checksum 检测数据是否被破坏，unique record ID 才用于识别 duplicate（`00:52:39-00:53:19`）。
- **误解：GFS 向应用隐藏所有 weak consistency。** application/library 必须了解并补偿 duplicate-record semantics（`00:52:37-00:53:19`）。

### 1. 对 failed secondary 的重配置只给出带保留的课堂设想

上一段的问题是：master 授予 lease 时若某个 secondary 已 down，是否只更新活着的 replicas 并把旧副本排除。老师回答，论文对 recovery/reconfiguration 的具体工作方式 “a little bit” 不清楚（`00:59:53-01:00:07`）。

他随后以 “I imagine” 提出可能流程：primary/replica group 通过 heartbeats 发现 `S2` dead；现有 primary 的 lease 到期后，master 建立新的 primary 与 secondary 集合，若没有额外 chunkserver，组里甚至可能暂时只有 `S1`（`01:00:07-01:00:38`）。这段是课堂推测，不应写成 GFS 的已证实 recovery algorithm。

### 2. 明确分析 consistency 的方法：枚举 failure cases

老师肯定学生持续追问边界条件，因为 consistency 分析正是要考虑所有可能 failures，并论证每一种是否会导致 inconsistency（`01:00:44-01:01:05`）。这把本讲前面的具体问答抽象成可复用方法：不要只验证正常路径，也要追问 crash、message loss 和 partition 下的角色、版本与可见性。

### 3. 构造 master-primary network partition

老师画出 master、primary `S2` 和 secondary `S1`，假设 master 向 primary 发送 heartbeat messages 却收不到回复，即二者间发生 network partition（`01:01:05-01:01:53`）。关键问题是：master 什么时候能任命 new primary？

答案是必须等待 `S2` 的 lease expired（`01:01:53-01:02:12`）。若 lease 尚未到期就选新 primary，旧 primary 可能仍能服务另一侧 clients，于是同一 chunk 同时有 `P1`、`P2`；不同 clients 向不同 primary 写入，会产生混乱顺序甚至 lost writes，无法再解释为一个 primary 逐个排序的操作历史（`01:02:12-01:03:04`）。

### 4. lease 如何阻止 split brain

老师把同时存在两个有效 primary 的状态称为 split-brain syndrome（`01:03:04-01:03:13`）。规避规则是：master 在确认旧 lease 已绝对过期前不任命 new primary；即便旧 primary 仍存活、master 无法访问它、某些 clients 却仍可访问它，旧 primary 在 lease 到期后也必须拒绝新的 write messages（`01:03:13-01:03:40`）。

lease 因而不是用来复制数据，而是给 primary 的排序权限设置时间边界。master 的等待和旧 primary 的自我停止共同保证不会有两个同时有效的写入排序者。

### 5. 给出更强一致性的方向，而非完整协议

临近结束，老师问怎样得到 strong consistency 或至少 stronger consistency，并强调有很多可能方案，后续课程会继续学习（`01:03:43-01:04:18`）。他指出一个反复出现的问题：不应让某些 replicas 的 update 已对 clients 可见、另一些仍未 update；更强方向是让 primary/secondaries 全部更新后再一起暴露，或者都不暴露（`01:04:26-01:04:50`）。

这是设计原则而非完整 protocol。老师说 Labs 2、3 会构建具有更强 properties、能处理这些 consistency scenarios 的系统（`01:04:53-01:05:06`）。Google 也为不同 application domain 构建更强一致性的其他存储系统；课堂举 Spanner 为例，它提供更强 consistency 甚至 transactions（`01:05:12-01:05:40`）。

最后回到 workload fit：GFS 专门面向 MapReduce jobs，而不同应用域可以承担不同成本来换取更强语义（`01:05:41-01:05:51`）。老师把本讲定位为 consistency 入门；这些问题会贯穿剩余学期（`01:05:52-01:06:17`）。

## 概念、符号与推导

### lease 的安全条件

```text
old primary lease valid:
  master MUST NOT appoint a new primary

old primary lease expired:
  old primary MUST reject new writes
  master MAY appoint a new primary
```

该条件整理自 `01:01:53-01:03:40`。它依赖双方对 lease expiry 的执行；本时间窗没有讨论时钟误差模型或 lease duration。

### partition 场景

```text
clients A <-> old primary S2    master !<-> S2
                         master <-> candidate new primary

危险：旧 lease 未过期时选新 primary
结果：两个有效写入排序者 -> split brain

规避：master 等待旧 lease 过期；S2 到期后停止接受 writes
```

### stronger-consistency 方向

```text
undesired visibility:
  some replicas updated and visible, others not updated

stronger direction:
  all participating replicas become visible together, or none do
```

这只是 `01:04:26-01:04:50` 的课堂设计方向，不是 atomic commit 的完整算法。本段无公式推导。

## 例子与课堂提示

- **老师对 heartbeat/reconfiguration 的保留语气**（`00:59:58-01:00:38`）：用于训练区分“paper 明确机制”和“课堂合理猜测”。
- **master 到不了 primary，但 clients 仍能到**（`01:01:05-01:03:40`）：用于说明 failure detection 不能仅凭无回复就立刻重授角色。
- **两个 primary 导致 bizarre ordering/lost writes**（`01:02:12-01:03:04`）：用于解释 split brain 为什么破坏 consistency。
- **all updated or none visible**（`01:04:26-01:04:50`）：用于连接 GFS anomaly 与后续 stronger protocol 的设计目标。
- **GFS 对 MapReduce、Spanner 对另一应用域**（`01:05:12-01:05:51`）：用于说明 consistency 选择要与 workload 和接口目标一起评价。

### 常见误解

- **误解：master 一次 heartbeat 收不到回复就能立即选新 primary。** 旧 primary 可能仍服务其他 clients；master 必须等待 lease expiry（`01:01:44-01:03:21`）。
- **误解：lease 过期只影响 master 的记录。** old primary 自己也必须在到期后停止接受 writes，否则等待规则不能阻止 split brain（`01:03:21-01:03:33`）。
- **误解：本段给出了 secondary replacement 的确定算法。** 老师明确说论文细节不清，并以 “I imagine” 描述可能流程（`00:59:58-01:00:38`）。
- **误解：强一致性只需让 writes 最终都到达。** 老师强调更新何时对 client 可见也关键；部分 replicas 先可见会暴露不一致（`01:04:26-01:04:50`）。
- **误解：GFS 的 relaxed semantics 对所有应用都合适。** 课堂把它与 MapReduce workload 绑定，并用 Spanner 说明其他应用域会选择更强 guarantees（`01:05:12-01:05:51`）。
