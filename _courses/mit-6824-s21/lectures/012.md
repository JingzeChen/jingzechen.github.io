## 分布式文件系统架构

```text
users / ordinary Unix applications
                 |
        standard system calls
                 |
+------------------------------------------+
| workstation                              |
| Frangipani file-system code              |
| inode/directory logic + write-back cache |
+------------------------------------------+
                 |
       network + lock protocol
          /               \
distributed lock service   Petal virtual disk service
lock owner + leases        shared block read/write storage
          \               /
       metadata, data blocks, per-WS logs
```

- **Frangipani workstation/server：** 运行完整 file-system logic 并缓存 directories、inodes、file content。增加 workstation 同时增加 workload 与 CPU capacity，这是课堂扩展性论点的核心。[00:04:06-00:06:51]
- **Petal：** 对 Frangipani 暴露共享 virtual disk/block interface；课堂开头只概述其内部多机、block replication 与 Paxos。完整 Petal striping、recovery/performance 细节虽在讲义中存在，但没有按本讲 transcript 展开，故不冒充课堂内容。[00:04:59-00:05:44]
- **Distributed lock service：** 记录每个 inode-named lock 的 owner，使用 leases 限制失联 owner 的权利期限；service 本身 fault-tolerant/Paxos-based。[00:21:36-00:22:28]
- **Shared Petal logs：** 每个 Frangipani workstation/server 有独立 log，但 log 位于共享 Petal，使另一 workstation 能在 crash 后执行 recovery。[00:46:51-00:47:42] [00:59:55-01:00:49]

## 核心协议与不变量

### 1. Cache coherence handoff

```text
cache only while holding lock
  -> old owner receives revoke
  -> finish current atomic operation
  -> force log and flush dirty state to Petal
  -> release lock to LS
  -> LS grants new owner
  -> new owner reads current state from Petal
```

该顺序使跨 workstation read 看到 last owner 的 write。Sticky `idle` lock 把无争用重复访问留在本地；它不是向 LS 归还 ownership。[00:23:26-00:30:24]

### 2. Locks 的双重职责

- **Reveal writes for coherence：** handoff 前 flush，next owner 从 Petal 读到最新值。
- **Conceal partial operations for atomicity：** create/rename 等 system call 持有所需 locks 到所有内部 metadata modifications 完成，pending revoke 不切开 operation。[00:33:39-00:38:43]

### 3. Write-ahead order

$$
durable(log(op)) \prec install(metadata(op)) \prec release(locks(op)).
$$

`log-before-install` 让 partial metadata write 可 redo；`install-before-release` 让下一 owner 不会在 home blocks 尚未更新时进入。[00:41:28-00:49:41]

### 4. Recovery replay rule

对 log update $u$ 及其目标 metadata block：

$$
replay(u) \iff v_{log}(u) > v_{Petal}(block).
$$

`<` 表示已有 newer update，`=` 表示该 update 已安装，二者均跳过；只有 `>` 表示 log 中仍有尚未安装的 update。[01:13:53-01:16:29]

### 5. Crash recovery ordering

```text
old owner unreachable
  -> wait until its lease expires
  -> surviving workstation runs recovery daemon
  -> read crashed owner's shared Petal log
  -> stop at first incomplete/checksum-failing record
  -> replay complete records whose versions are still newer
  -> report recovery complete
  -> lock server may grant locks to another workstation
```

[00:58:01-01:03:40] [01:13:15-01:17:29]

## Crash 情形与保证边界

| Crash point | 可观察结果 | 课堂保证 |
| --- | --- | --- |
| recent changes 仍只在 workstation cache | Recent operations 可全丢 | Petal 没有 partial metadata install，内部结构一致 |
| force log 中途 | Petal 只有 complete-record prefix，末条可能 torn | Checksum 使 recovery 停在 torn record 前；durable prefix 可 replay |
| log durable、metadata 未安装 | Operation 尚未反映到 home blocks | Recovery daemon 从 log redo |
| metadata 部分安装 | 部分 inode/directory blocks 已更新 | WAL 补齐同一 operation 的其余 metadata changes |
| user content blocks 写入中 | None/some/all recent blocks 可能落盘 | 不保证 whole-file data atomicity；metadata structure 仍受保护 |
| owner 与 LS partition、仍可达 Petal | 旧 owner 可能继续写 | LS 等 lease expiry 后才 recovery/reassign |
| stale write 延迟超过 lease margin | 新 owner 写完后旧 write 才到 Petal | 当前分层可能 break consistency；老师提出 Petal timestamp/freshness support 方向，但未给完整 protocol |

## 扩展性与取舍

- **适合的 common case：** trusted lab 内用户多操作自己的 files；sticky lock + write-back cache 让大多数 operations 无 RPC/无 Petal traffic。[00:07:11-00:10:34]
- **计算扩展：** 新增 workstation 也新增 file-system CPU，不把所有 pathname/inode/security computation 压在单一传统 server。[00:05:45-00:06:51] [00:14:22-00:16:10]
- **共享写热点差：** 两台 workstations 频繁修改同一 file 会产生 revoke/flush/grant 与 cache bouncing；协议性能依赖低 contention workload。[00:31:17-00:32:12]
- **细粒度 lock 取舍：** per-inode locks 提高无冲突 concurrency，但 multi-lock operations 需要 fixed order 处理 deadlock。[00:36:49-00:38:21]
- **Metadata-only logging：** 保住全局 file-system structures，同时避免 user data 先 log 再 home-write 的近似 $2D$ 写放大；代价是应用必须自己处理 data atomicity。[00:50:52-00:55:31]
- **多独立 logs：** 避免单日志成为明显集中点并便于 distributed recovery，但同一 object 的 updates 散落不同 logs，必须用 locks + per-block versions 防止 stale replay。[01:03:47-01:17:29]
- **分层简洁与跨层缺口：** Petal/Frangipani 独立让 block layer 可复用，但 Petal 若不知道 Frangipani lease/freshness，就难以 fence late old writes，只能依赖 margin 或扩展接口。[01:26:37-01:27:43]
- **性能证据边界：** 老师只概括论文图显示 workload capacity 随 workstations 增长；课堂没有逐项讲 Figure 5-7、Table 3 或讲义中的 MB/s 数字。[01:19:02-01:19:40]

## 课堂 Q&A 与复习

1. **Read lock release 是否也必须写 Petal？** 老师没有在此给精确规则，而是暂时忽略 read/write distinction、只讲 exclusive locks；不能由简化推断 clean read cache 需要 write-back。[00:30:30-00:31:09]
2. **File 在 cache 中但 lock “released” 是否矛盾？** 不矛盾。课堂前半所谓 release 常是 local `busy -> idle`；sticky lock 仍由 workstation 持有，LS ownership 未变。[00:32:15-00:32:49]
3. **Revoke 在 busy 时到达怎么办？** 等 operation 完成；local release 发现 pending revoke 后才 force/flush/LS release，因而 revoke 不切开 atomic operation。[00:32:55-00:36:36]
4. **为什么 file content 不进 log？** 避免大 data 两次写入；代价是 crash 后可能留下任意 recent-block subset，application 用 temp file + atomic rename 建立更高层保证。[00:50:52-00:55:31]
5. **为什么等待 lease expiry？** 无响应可能是 partition；old owner 仍可访问 Petal。Expiry 后它才按协议无权继续使用 lock。[00:58:01-00:59:55]
6. **为什么 crash during log force 只恢复 prefix 也可以？** 每个完整 record 对应一个 atomic operation；丢 suffix 是 durability loss，不是 partial-operation inconsistency。[01:01:37-01:03:40] [01:22:20-01:23:45]
7. **旧 delete 为什么不覆盖 newer create？** Recovery 比较每项 update 的 version 与 Petal current version；旧 10 小于新 11，跳过。[01:12:22-01:17:29]
8. **一条多-update record 如何判完整？** Paper/课堂线索包括 checksum；老师还介绍单-sector/commit-record 一般方案，但明确不确定 Frangipani 的精确选择。[00:45:09-00:46:10] [01:20:09-01:21:18]
9. **Lease 过期是否完全 fencing 已发出的旧 writes？** 不一定。若 stale write 在 margin 外延迟到达 Petal，仍可能覆盖新 owner；老师指出 Petal-side timestamp/freshness check 会更有帮助。[01:26:04-01:27:43]


# 第 2 段：从 write-back 与 strong consistency 到三类挑战

> 时间范围：`00:10:01-00:19:58`
>
> 证据范围：本段 prompt 明确为 transcript-only；不引用课堂讲义页码，不用讲义后续答案替代老师在本段提出的问题。

## 本段在整讲中的作用

本段承接上一段的 workload 选择，把“workstation 本地 cache”具体化为 write-back cache，并立即加入一个看似冲突的目标：即使数据多数时间私用，只要发生共享，另一个 workstation 就应看到最新修改，也就是 strong consistency/coherence。老师先借 GFS 和 ZooKeeper 说明“file-system API 与 workload 决定系统机制”，再回答 client-side file-system code 为什么能扩展，最后从 write-back 设计系统性推出三类问题：cache coherence、atomicity、crash recovery。后续各段将按这个顺序逐一处理。[00:10:01-00:19:58]

## 教学展开

1. **完成 write-back 的动机。** 研究者通常操作自己的 private files，所以把数据留在 workstation cache 后，read/write 可以不产生网络流量。Frangipani 不采用每次修改都写 Petal 的 write-through，而让 operation 先停留在 cache，之后再回写 Petal。[00:10:01-00:10:34]
2. **加入 strong consistency 目标。** 私有访问是 common case，但发生共享时，后一个 workstation 的 read 必须看到另一个 workstation 已做的 changes。老师把这个要求称为 strong consistency，也使用 coherence 一词。[00:10:38-00:11:29]
3. **用 GFS 对照 workload 驱动的设计。** GFS 面向 MapReduce：文件大、常顺序读取，通常不适合在 client cache 完整数据；它只缓存 chunk-server location 等 metadata，而不缓存 file data，因此不需要同类 data-cache coherence。GFS 也不是让 `vi`、`gcc` 等普通 Unix applications 透明运行的完整 POSIX/Unix file system；Frangipani 则要让应用看起来像在使用单一普通文件系统。[00:11:42-00:13:33]
4. **再用 ZooKeeper 扩大对照。** ZooKeeper 也有 file-system-like interface，但用途是 coordination service，不适合保存大文件。老师由此得出方法论：不能只按“都有文件和路径”比较系统，必须先看目标 application/workload。[00:13:33-00:14:16]
5. **课堂问答重述 scalability。** 学生问 client-side server code 为什么更可扩展。老师先把传统架构简化为很多 clients 对一个 file server：所有 open、security checks 和 read/write processing 都在该 server，clients 增多会集中施压。Frangipani 则让每台 workstation 执行自己的 file-system operations，支持的 workload 因而可随 workstation 数增加。[00:14:22-00:15:30]
6. **澄清传统系统也可分区，但仍有热点。** AFS 可以把不同 volumes 放在不同 file servers；可是一个 volume 的全部数据仍由一个 server 管理，该 volume 负载很高时仍形成 bottleneck。该回答限定了 Frangipani 扩展性论点：不是传统系统绝不能横向拆分，而是计算/数据管理粒度会形成集中热点。[00:15:31-00:16:10]
7. **由 write-back 场景提出 coherence。** `WS1` cache 并修改 file `f`，结果稍后才写 Petal；若 `WS2` 随后 `cat f`，Unix 用户预期它看到 last write。让跨 workstation read 看到该 write，就是 cache coherence/cache consistency 问题。[00:16:27-00:18:28]
8. **由并发目录更新提出 atomicity。** `WS1` 在 directory `d` 创建 `f`，`WS2` 同时在 `d` 创建 `g`；结果必须同时保留两个 entries，而不能一方用自己的 cached directory state 覆盖另一方。老师把防止错误 interleaving 的要求称为 atomicity。[00:18:33-00:19:29]
9. **由复杂操作中途故障提出 crash recovery。** workstation 可能在执行一个包含多步修改的 file-system operation 时 crash；系统必须有恢复方案。本段只提出第三类问题，下一段继续解释 create 的多步结构及“正确恢复”的最低含义。[00:19:32-00:19:58]

## 概念、符号与推导

- **write-back cache：** operation 先更新 workstation cache，不立即更新 Petal；稍后在协议规定的时机 flush。优点是 common case 减少 network/storage traffic，代价是 Petal 暂时不是最新值的唯一来源。[00:10:01-00:10:34]
- **strong consistency / coherence：** 在本段的操作性表述中，一个 workstation 写完后，另一个 workstation 的后续 read 应看到该 change。老师将 coherence 与 cache consistency 作为近义词使用。[00:10:38-00:11:18] [00:18:03-00:18:28]
- **workload-to-design：** GFS 的大文件、顺序处理、MapReduce workload 不需要 data caching；Frangipani 的普通 Unix applications、private-file locality 与偶尔共享则同时需要 cache 和 coherence。[00:11:42-00:13:53]
- **atomicity 问题：** 多个 workstation 对同一 directory 的 modifications 不能从各自旧副本独立写回并互相覆盖，也不能让复杂 operation 的中间状态成为其他 workstation 可观察结果。[00:18:33-00:19:29]
- **三类挑战之间的来源关系：**

```text
write-back + shared access -> stale read -> cache coherence
decentralized concurrent updates -> lost/interleaved update -> atomicity
multi-step operation + workstation crash -> partial state -> crash recovery
```

# 第 3 段：lock server、sticky lock 与 coherence timeline

> 时间范围：`00:20:02-00:30:01`
>
> 证据范围：本段 prompt 明确为 transcript-only；协议图按老师口述重建，不把讲义中的后续 atomicity/recovery 内容提前并入。

## 本段在整讲中的作用

老师先用 create operation 的多个 metadata steps 完成上一段对 crash recovery challenge 的说明，然后按既定顺序正式解决第一类问题：cache coherence。核心做法不是让 Petal 主动追踪所有 caches，而是加入 distributed lock service，并规定 workstation 只有持锁才能 cache；lock transfer 前旧 owner 必须把 dirty state 写回 Petal。老师从 lock-server table、workstation busy/idle table 和四种 messages 起步，再用 `WS1` 修改 `f`、`WS2` 读取 `f` 的完整 timeline 推导 strong consistency。下一段从该 timeline 的结论出发讨论 contention、local release 与 atomicity。[00:20:02-00:30:01]

## 教学展开

1. **先把 crash-recovery challenge 说具体。** 在 directory `d` 创建文件不止一个 write：修改 directory、allocate inode、initialize inode、把 inode number 写入 directory。若 workstation 在任意两步之间 crash，最低恢复目标是 internal file-system structures 保持一致，例如不能留下目录不可达的 lost inode。[00:20:02-00:20:45]
2. **宣布逐一处理三类问题，先从 coherence 开始。** 老师把 cache coherence 与 cache consistency 并列，并引入 lock server 作为关键组件。[00:20:46-00:21:39]
3. **定义 lock-server ownership table。** Lock server 为每个 file，实际按其 inode number，记录当前 lock owner，例如 `f -> WS1`。Lock service 本身是 fault-tolerant distributed service，课堂把它类比为支持 acquire/release 的 ZooKeeper，并说明 Frangipani 使用 Paxos-based implementation。[00:21:39-00:22:35]
4. **定义 workstation 本地 lock state。** Workstation 为所持 locks 维护 table。`busy` 表示 Frangipani code 正在操作对应 file；`idle` 表示暂时不用，但 lock 仍留在该 workstation。老师称后者为 sticky lock：若本机稍后再次访问，就不需重新从 Petal load cache，也不必重新与 lock server 完成一次 ownership transfer。[00:22:41-00:24:06]
5. **给出 coherence 的首要规则。** Workstation 要 cache 一个 file，必须先 acquire 其 lock。课堂为简化先只讨论 exclusive lock；论文还有 read/write locks，允许多个 workstation 以 read-only mode cache，这是重要优化但不改变主协议逻辑。[00:24:09-00:25:13]
6. **界定目标为单文件系统行为。** 虽然系统分布式，返回结果应与单一 file system 相同，外部无法从行为区分。老师把目标联系到 linearizable file-system operations，但用 “I believe” 表述，因此笔记保留其课堂判断语气，而不扩写形式证明。[00:25:14-00:25:55]
7. **列出四类协议消息。** `request`、`grant`、`revoke`、`release` 在 workstations 与 lock server 之间流动。初始无人持有 `f` 时，`WS1 -> LS: request(f)`；LS 检查 table、登记 `WS1` 为 owner，再 `LS -> WS1: grant(f)`。[00:25:56-00:27:09]

## 概念、符号与推导

### 状态与命名

- Lock 按 file/directory 标识，实际名称是 inode number；lock server 不需要理解 file-system semantics，只维护 lock name 到 owner 的映射。[00:21:46-00:22:07]
- `busy`/`idle` 是 workstation 内部使用状态，不等于 LS 看到的“持有/未持有”。从 `busy -> idle` 是 local release；向 LS 发 `release` 才是真正归还 ownership。[00:23:06-00:24:03] [00:27:33-00:27:49]
- Sticky lock 将无争用时的重复访问优化为本地操作；外部 request 到来时才触发 revoke/flush/release。[00:23:26-00:24:06]

### Coherence protocol

```text
WS1                  Lock Server                    WS2
 | request(f) ---------->|                           |
 |<----------- grant(f)  |                           |
 | read f from Petal     |                           |
 | modify/cache f        |                           |
 | busy -> idle          |<------------- request(f) |
 |<---------- revoke(f)  |                           |
 | flush dirty f to Petal|                           |
 | release(f) ---------->|                           |
 |                       | grant(f) ---------------->|
 |                       |              read latest f from Petal
```

关键顺序为：

```text
old owner flush complete
  -> old owner release
  -> lock server grant new owner
  -> new owner read from Petal
```

因此新 owner 的 Petal read 不会越过旧 owner 尚未公开的 dirty writes。[00:28:43-00:30:01]

本段无公式推导。

# 第 4 段：coherence 的代价与 locks 提供的 atomicity

> 时间范围：`00:30:01-00:39:58`
>
> 证据范围：本段 prompt 明确为 transcript-only；per-inode locks、fixed ordering 与 create timeline 均按课堂口述记录。

## 本段在整讲中的作用

本段先闭合上一段的 coherence proof：新 owner 获 lock 前，旧 owner 必须把 state flush 到 Petal，因此 read 能看到 latest changes。老师随后用多个学生问题暴露该协议的性能边界和容易混淆的两层“release”，并顺势进入第二类挑战 atomicity。关键转折是：同一套 locks 不仅决定 cache 何时对下一 workstation 可见，还把一个多步 file-system system call 包在持锁区间内，使其他 workstation 看不到 partial result。段末再指出 locks 只能保证无 crash 时的 atomicity；workstation 在中途 crash 仍需 write-ahead logging。[00:30:01-00:39:58]

## 教学展开

1. **完成 coherence 结论。** `WS2` 获 grant 后读 Petal，保证看到 `WS1` 的 latest changes，因为 `WS1` 必须在 release lock 前完成 flush。Strong consistency 因而与 lock management 的 transfer order 绑定。[00:30:01-00:30:24]
2. **暂时搁置 read-lock 细节。** Chat 问释放 read lock 为什么也要 write Petal。老师重申本讲先只考虑 exclusive locks；read/write distinction 是重要优化，却不改变主要 design。这里不能推导为“干净 read cache 也必须写回”。[00:30:30-00:31:09]
3. **指出共享写热点的性能问题。** 两台 workstations 反复修改同一 file 会让 cache/lock 来回 bounce，每次 handoff 都触发 flush 与 transfer，因此效率很低。该设计依赖 workload assumption：engineers 多数处理 private copies，偶尔共享，而不是持续敲打同一 shared file。[00:31:17-00:32:12]
4. **澄清 local release 与 server release。** 学生问 lock 已释放时是否还能 cache。老师说明先前所谓 release 多指 local `busy -> idle`；sticky lock 仍在 `WS1`，LS 也仍记录 `WS1` 为 owner。只有处理 revoke、flush 后发送 `release` message 才归还 LS。[00:32:15-00:32:49]
5. **处理 busy 时到达的 revoke。** 若 `WS2` request 在 `WS1` 的 lock 为 busy 时到达，request 不被拒绝，而是等待。`WS1` 完成本地 file-system operation、调用 local release，看到 pending revoke 后才 flush state 并把 lock 归还。[00:32:55-00:33:38]
6. **借等待规则引出 atomicity。** 一个 application `create` system call 内部包括 allocate inode、initialize/write inode、update directory entry 等多个 modifications。为了不让其他 workstation 看到 intermediate result，Frangipani 在 operation 开始前 acquire 所需 locks，在整个 operation 完成后才 local release。[00:33:39-00:35:41]
7. **说明 revoke 不能切开 operation。** Revoke 若在 create 中途到达，只会登记为 pending；直到 Frangipani local code 完成 operation 并 release，才 flush cache、回复 LS。由此 lock handoff 发生在 operation boundary，其他 workstation 无法在 inode 已初始化而 directory 尚未更新时进入。[00:35:42-00:36:36]
8. **从 create 推出 multiple locks。** 创建 `d/f` 要改 file inode 与 directory inode，因此技术上持有至少两个相关 locks。老师强调 directory 本身也是特定格式的 file，lock 粒度基本是 per inode；先 acquire directory `d` 的 lock，再 acquire 为 `f` 分配的 inode lock。[00:36:49-00:37:50]
9. **处理 deadlock 风险。** 一旦 operation acquire multiple locks，不同 workstations 若顺序不同就可能 deadlock。Frangipani 对 locks 建立 fixed order，所有人按同一顺序 acquire；老师记忆中可能按 inode number 排序，但用了 “I think”，应保留不确定性。[00:37:52-00:38:21]
10. **划定 locks 的 failure boundary。** 没有 crash 时，持锁到 operation 结束可以保证 atomicity。可是若 `WS1` 在 allocate inode 后、update directory 前 crash，仍可能只把 operation 的一部分带到 Petal；这把课堂带入第三类问题 crash recovery 和仔细的 Petal-update protocol。[00:38:29-00:39:58]

## 概念、符号与推导

### Locks 的两项职责

1. **Cache coherence：** 旧 owner flush 后才 release，新 owner grant 后再从 Petal read，因此 writes 在 handoff 时被“revealed”。[00:30:01-00:30:24]
2. **Operation atomicity：** operation 完成前 lock 保持 busy，pending revoke 不会穿过 operation；partial metadata changes 被“concealed”。[00:33:39-00:36:36]

### 两层 release

```text
local release:  busy -> idle
                lock ownership 仍在 workstation
                cached data 仍可继续使用

LS release:     pending revoke + operation complete
                -> flush dirty state to Petal
                -> send release(lock) to lock server
                -> ownership 可转给另一 workstation
```

### Create 的 atomic lock interval

```text
acquire lock(d)
acquire lock(new inode for f)
    allocate inode
    initialize inode
    add (f -> inode number) to directory d
local release all locks
if revoke pending: flush -> LS release
```

固定 lock order 用于消除 circular wait。课堂没有形式化证明或给出完整 ordering table。

本段无公式推导。

## 例子与课堂提示

- **cache bouncing** [00:31:17-00:31:54]：用于揭示 coherence 不是免费午餐；频繁写共享会把 local-cache fast path 变成持续 flush/handoff。
- **独立代码副本** [00:32:03-00:32:12]：老师用类似各自 checkout、最后写回的工作方式说明 Frangipani 的目标并非多人逐写同一 file。
- **busy 时的 revoke** [00:32:55-00:33:38]：既是协议 corner case，也是转向 atomicity 的桥梁；等待 operation boundary 保证不暴露中间态。
- **create `f`** [00:34:03-00:37:50]：用于说明一个 system call 不等于一个 disk write，且同一 operation 可能需要 directory 与 file 两把 locks。
- **per-inode granularity** [00:37:15-00:37:50]：相对 coarse global lock 提供更多 concurrency，但带来 multiple-lock acquisition 和 deadlock-order complexity。

# 第 5 段：write-ahead logging 与 flush-before-release

> 时间范围：`00:39:59-00:49:56`
>
> 证据范围：本段 prompt 明确为 transcript-only。课堂对 log record 字段的描述带有论文未完全明确的限制；本笔记不把讲义中的 guess-work 或论文细节升级为确定事实。

## 本段在整讲中的作用

本段进入第三类挑战 crash recovery。老师先把普通 virtual disk 分成 log area 与 file-system area，用 create operation 的两个 metadata writes 解释为什么直接安装 updates 会在 crash window 留下 inconsistent structure；随后建立 write-ahead logging 的核心顺序：先完整记录 operation 的所有 changes，再安装它们。最后把 WAL 嵌回 coherence protocol，形成 `force log -> send updated blocks -> release lock`。这为下一段逐个分析 crash point、metadata/data 边界以及 leases/recovery daemon 奠定基础。[00:39:59-00:49:56]

## 教学展开

1. **命名 write-ahead logging。** 老师把它称为常见技术，学生可能已在 6.033 见过，之后的 transaction papers 也会反复使用。课堂此处讨论的是 Frangipani 在更新共享 Petal 上 file-system state 时使用的 log-before-install protocol。[00:39:59-00:40:50]
2. **建立简化磁盘布局。** 把 virtual disk 想成很长的 block array，一部分保留给 log，一部分保存 file system 的 inodes、data blocks 等。真实 Frangipani 有 per-server log，但老师暂时先画成单一 log，稍后再回到 many logs 的特殊问题。[00:40:51-00:41:27]
3. **给出 WAL 第一条规则。** Workstation 要把 cached state 写入 Petal 时，不先直接改 file-system blocks，而先把该 operation 的 update description 写到 log。对 create 而言，description 覆盖 inode allocation/initialization 与 directory change 所需的 block modifications。[00:41:28-00:42:42]
4. **再执行 install update。** Log 完整持久化后，workstation 才把 changes 安装到实际 file-system blocks。这样如果 install 过程中 crash，recovery daemon 可以从 log 重做尚未完成的 updates，最终把结构带到一致状态。[00:42:43-00:44:03]
5. **通过反例解释为何不能直接写。** Create 需要 inode-block write 与 directory-block write；两次 disk writes 不是一个 atomic action。若第一笔完成、第二笔未完成就 crash，会留下 allocated-but-unreachable inode。全盘 scan 或许可找回，但代价很高；先记录两项 change 则可在恢复时补齐。[00:44:04-00:45:08]
6. **追问 log record 自身如何 atomic。** 学生指出第一步“写 log”也可能中途 crash。老师说 paper 没有百分之百讲清，但提到每个 log record 有 checksum；recovery 读 record 后重算 checksum，只有完整 record 才采用。[00:45:09-00:45:39]
7. **补充一种通用替代方案，但不冒充 Frangipani 实现。** 老师说明还可先写多个 blocks，再写一个单-sector commit record，假定 512-byte sector write atomic；commit record 不存在就不执行该 operation。该段是一般 WAL 说明，不是老师确认论文采用的唯一方案。[00:45:40-00:46:10]
8. **区分 crash-before-flush 与 crash-during-flush。** Workstation 在 log/cache 尚未写 Petal 前 crash，recent data 会丢失，但共享 Petal 中没有 partial visible state；真正危险的是已经开始把一个 multi-block operation flush 到 Petal却未完成。[00:46:11-00:46:44]
9. **引入 per-server logs。** 老师口述一度出现 “lock per server”，随后上下文明确讨论的是每个 Frangipani server/workstation 一个 log。这种安排不寻常，会在恢复单个 log 时遇到其他 workstation 后来 updates 的问题，后文用 version numbers 解决。[00:46:51-00:47:42]
10. **描述课堂版 log record。** 每条 record 有 sequence number，用连续编号判断 log end；record 内有 updates array。每项 update 包含要修改的 block number、version number 和 new bytes。Create `f` 的例子含两项：inode block update 与 directory data block update。[00:47:43-00:49:04]
11. **把 WAL 放回 revoke path。** 收到 revoke 时，workstation 先 force its log to Petal；完成后把 updated blocks 发到 Petal；最后 release lock。没有 crash 时它等价于前面 coherence timeline，真正需要逐项分析的是这些步骤之间 crash。[00:49:05-00:49:56]

## 概念、符号与推导

### WAL 顺序不变量

```text
operation executes in local cache
  -> append complete operation description to local log
  -> force log to shared Petal storage
  -> install metadata updates into Petal file-system area
  -> release locks to lock server
```

核心约束可写成：

$$
durable(log(op)) \prec install(op) \prec release(locks(op)).
$$

这里 $\prec$ 表示协议规定的 happens-before 顺序，不是课堂给出的数值公式。第一条边保证 partial install 可重做；第二条边保证 lock 转给下一 workstation 前，Petal state 已按 operation 更新。[00:41:28-00:43:23] [00:49:05-00:49:41]

### 课堂描述的 record 结构

```text
log record
  sequence number
  updates[]
    block number
    version number
    changed address/range and new bytes
  integrity evidence such as checksum
```

- Sequence number 帮助识别连续 log records/end。[00:47:43-00:48:03]
- Update 描述 file-system block 应变成什么，而不是只写高级 `create(f)` 名称。[00:42:08-00:42:40]
- Version number 在本段先出现，理由留到 many-log recovery 段落。[00:48:17-00:48:36]
- Checksum 用于识别 torn/incomplete record；老师同时承认 paper 在精确 atomic-record mechanism 上不够明确。[00:45:09-00:46:07]

## 例子与课堂提示

- **长 block array** [00:40:51-00:41:27]：用于暂时忽略 Petal replication 等细节，只关注 log area 与 home/file-system area 的顺序。
- **allocated inode 但 directory 未更新** [00:44:21-00:44:56]：说明 crash consistency 保护 internal structures，不只是“某个用户最后几字节是否保存”。
- **checksum vs commit record** [00:45:09-00:46:07]：前者是课堂从 paper 提到的线索，后者是老师给出的通用替代做法；二者证据等级不能混同。
- **crash before any Petal flush** [00:46:11-00:46:44]：recent update 可丢，但没有 partial shared state；提示 durability 与 consistency 是不同保证。
- **create record 的 two updates** [00:48:38-00:49:04]：用于说明一个 atomic file-system operation 可对应多项 block-level changes，而这些 changes 应在同一 complete log record 中描述。

## 本段掌握检查

1. **问：WAL 为什么要求 log 先于 home blocks？**

# 第 6 段：metadata logging、user data 边界与 lease

> 时间范围：`00:49:57-00:59:55`
>
> 证据范围：本段 prompt 明确为 transcript-only；对 data-block flush 相对 step 2 的精确并行顺序，老师使用推测语气，笔记不升级为协议保证。

## 本段在整讲中的作用

本段从 WAL 的 record 细节转向“它究竟保证什么”。学生对 `new bytes` 和大块 data 的追问使老师明确划定 logging boundary：Frangipani log 只保护 inode、directory 等 file-system metadata，application file content 直接写 Petal，不获得整文件 atomicity。老师由此讨论数据丢失/partial write、应用用 temporary file + atomic rename 自救，以及不记录大数据带来的性能收益。随后开始按 crash point 做 case analysis，并用 lease 解决“LS 以为 owner crash，但它可能只是与 LS partition、仍能写 Petal”的危险，为下一段的 recovery daemon 铺路。[00:49:57-00:59:55]

## 教学展开

1. **澄清 `new bytes`。** Log update 不是只记“改 inode”这类抽象动作，而是记录 metadata block 的哪些 byte ranges 变成哪些 values，例如 bytes 0-5、12 或 10-20 的新值。若 operation 影响多个 blocks，就为每个 block 记录 update。[00:49:57-00:50:52]
2. **划定 log 只覆盖 metadata。** Application 写入 file content 时，大量 data blocks 不经过 log；在 flush 时直接送 Petal。经过 log 的是 metadata changes，如 inodes、directories 和描述文件结构的信息。[00:50:52-00:51:57]
3. **推导不记录 user data 的后果。** 若一个 file 有 10 blocks，crash 可能使 Petal 保存 none、some 或 all recent writes，不能保证 10 blocks 作为整体 atomic apply。老师把它称为可能 inconsistent 的 application data state，但与 file-system metadata structure consistency 区分开。[00:52:00-00:52:48]
4. **把 data atomicity 责任交回 application。** 若应用需要整份内容原子替换，应自行安排。老师给出的典型 Unix pattern 是先完整写 temporary file，再做 atomic rename 到目标文件名；Frangipani 复用普通 Unix file system 的语义，不额外承诺 whole-file write atomicity。[00:52:58-00:54:25]
5. **解释性能取舍。** 若 1 GB user data 也经过 WAL，就要先写 1 GB log、再写 1 GB home data，约产生两倍写流量。Metadata 相对小，值得为 internal consistency 付出 logging cost；大 user data 直接写可避免显著吞吐损失。[00:54:32-00:55:31]
6. **再次强调 metadata atomicity。** Create 更新 inode block 与 directory block，二者必须一起完成或可由 recovery 补齐，否则内部结构损坏会影响所有用户。Data blocks 则可能与 metadata install 同阶段发往 Petal；老师对此用了 “I think/probably”，没有给出严格并行调度规则。[00:55:16-00:56:02]
7. **开始 crash-case enumeration：log 前 crash。** Workstation 在任何 log 内容写 Petal 前 crash，recent operations 直接 lost；这是可接受的 durability loss，因为 Petal 中没有它们的 partial metadata install。[00:56:14-00:57:25]
8. **转向 log 已写后的恢复。** 若 log 已在 Petal，另一个 workstation 之后需要 crashed owner 的 lock，LS 会先要求原 owner 归还。它不响应时，LS 不能马上重分配，而要等待 lock lease expires。[00:57:27-00:58:36]
9. **用 network partition 解释等待 lease。** 无响应并不证明 `WS1` crash；它可能只与 LS 隔离，却仍可访问 Petal。若 LS 立即让 `WS2` recover/持锁，两个 workstations 可能并发写同一 blocks。Lease expiry 后，遵守协议的旧 owner 不再允许使用 lock，因此 LS 才能确定它不会继续写。[00:58:37-00:59:55]

## 概念、符号与推导

### 保证边界

| 数据类别 | 是否写 Frangipani log | Crash 后本讲保证 |
| --- | --- | --- |
| inode、directory 等 metadata | 是 | 可恢复到 internal file-system structures 一致 |
| application file-content blocks | 否，直接写 Petal | recent writes 可全部、部分或完全未落盘 |

[00:50:52-00:55:31]

### 写放大取舍

若把大小为 $D$ 的 user data 也先写 log 再写 home location，课堂估算写流量约为：

$$
D_{log}+D_{home}\approx 2D.
$$

这不是 paper benchmark 公式，而是老师用 1 GB file 解释 metadata-only logging 的定性性能理由。[00:54:32-00:55:09]

### Lease 作为 fencing 条件

```text
LS cannot reach WS1
  != proof that WS1 is dead
WS1 may still reach Petal
  -> immediate reassignment risks two writers
wait until lease expiry
  -> protocol forbids WS1 from further lock use
  -> recovery/reassignment may begin
```

Lease 在这里解决的是 stale owner 的写权限期限，不是保存未落盘 user data。[00:58:01-00:59:55]

## 例子与课堂提示

- **bytes 0-5 / 10-20** [00:50:07-00:50:35]：用于说明 log 是 byte-level/block-level update description，不只是 method-call trace。
- **10-block file** [00:52:25-00:52:48]：说明 application data 可能落盘任意 subset；不能因 metadata 使用 WAL 就推断所有 user writes atomic。
- **temporary file + atomic rename** [00:53:34-00:54:25]：展示 end-to-end responsibility；file system 提供原子 metadata operation，application 用它组合更高层的 safe replacement。
- **1 GB 写两遍** [00:54:54-00:55:09]：直观说明不 logging data 的性能收益和 write amplification。
- **partitioned old owner** [00:58:37-00:59:55]：lease 的核心反例。机器可能没有 crash，不能仅靠 timeout/revoke failure 把它的 locks 给别人。

## 本段掌握检查

1. **问：Frangipani log 记录 application file content 吗？**  
   **答：** 不记录；它记录 inode、directory 等 metadata updates，content blocks 直接写 Petal。[00:50:52-00:51:57]
2. **问：10-block file 在 crash 后可能处于哪些状态？**  
   **答：** Recent writes 可能一个都没有、只落一部分或全部落盘，不保证 whole-file atomicity。[00:52:25-00:52:48]
3. **问：应用如何在普通 Unix/Frangipani 语义上实现文件原子替换？**  
   **答：** 先写完整 temporary file，再用 atomic rename 替换目标名称。[00:53:34-00:54:25]
4. **问：为什么只 log metadata？**  
   **答：** Metadata 小且 internal consistency 必须保护；大 user data 若先 log 再 home-write 会近似双倍写流量，显著损害性能。[00:54:32-00:55:31]
5. **问：LS 为什么必须等 lease expires 后才能恢复旧 owner？**  
   **答：** 无响应可能是 partition，旧 owner 仍可写 Petal；lease expiry 才使其按协议失去写权限，避免两个 writers。[00:58:01-00:59:55]

- [需回听 00:50:38-00:50:52] 学生将 block 大小说成 512 bytes；课堂随后只确认“每个受影响 block 有 record/update”，不据此断言 Frangipani/Petal 所有层的统一 block size。

# 第 7 段：recovery daemon、完整前缀与 many-log 难题

> 时间范围：`00:59:55-01:06:17`
>
> 证据范围：本段 prompt 明确为 transcript-only；`01:06:17-01:12:22` 是 breakout-room/无本段技术 transcript 的间隔，答案留到下一 section。

## 本段在整讲中的作用

上一段用 lease expiry 建立了 recovery 可以安全开始的时刻；本段接着说明谁来恢复、恢复什么、何时才能重分配 lock。老师随后处理“写 log 本身中途 crash”：checksum 让 recovery 只接受完整 records，因此可能恢复 operation sequence 的一个完整 prefix，而不会执行半条 atomic operation。最后，他提出全讲最棘手的 many-log 问题：`WS1` 的旧 delete 已被 `WS2` 的 later create 超越，`WS3` 若只 replay `WS1` log 会不会撤销新状态？课堂在此进入 breakout，version-number 答案必须等下一段。[00:59:55-01:06:17]

## 教学展开

1. **指定 surviving workstation 运行 recovery daemon。** Lease expiry 后，LS 让一个仍存活的 workstation 执行 recovery daemon。Daemon 是不持续服务前台请求、负责 house-keeping 的 server process；它读取 crashed `WS1` 放在 Petal 的 log，并把其中 operations 应用到 file-system state。[00:59:55-01:00:49]
2. **恢复完成后才重分配 lock。** Recovery daemon 通知完成后，LS 才能把旧 owner 的 lock grant 给另一 workstation。这把 `recover before reassign` 接到前面的 `wait for lease expiry`，共同防止恢复与新 writes 并发。[01:00:49-01:00:58]
3. **问答再次划定 recovery guarantee。** 学生确认：log 已写后 crash，metadata 可恢复一致，但 user data 不保证完成。老师明确同意，WAL 的保证是 internal file-system data structures；如果它们损坏，影响可能扩散到所有用户。[01:00:59-01:01:36]
4. **分析 crash during log force。** 若 workstation 正在把多个 records 写 Petal时 crash，Petal 可能只保存 log 的 prefix。每条 record 有 checksum；recovery 遇到 checksum 不匹配的 torn record 就停止，不使用该 record。[01:01:37-01:02:46]
5. **得到“完整 operation prefix”。** 例如 create `f`、create `g` records 完整，create `h` record incomplete；recovery 只执行前两项。最后若干 operations 丢失虽然不理想，但可接受，因为 crash 再早一点本来可能丢掉全部 recent operations；关键是每条被 replay 的 atomic file-system operation 都完整。[01:02:47-01:03:40]
6. **提出 per-workstation logs 的新问题。** 每个 workstation 有自己的 log。`WS1` 先 delete `d/f`，其 update 在 log 1；之后 `WS2` create `d/f`，其 update 在 log 2。随后 `WS1` crash，`WS3` 负责 recovery log 1。[01:03:47-01:05:14]
7. **构造错误 replay 后果。** 如果 `WS3` 无条件 replay log 1 的旧 delete，就会覆盖/撤销 `WS2` 已经写入 Petal 的 later create。Recovery daemon 又只看 crashed workstation 的 log，不会先把所有 logs 合并排序，因此必须有额外机制判断 old record 是否已被更新状态超越。[01:05:15-01:05:30]
8. **把问题交给 breakout room。** 老师让学生讨论约五分钟：如何防止 stale delete replay，以及 Frangipani/Petal 其他问题。当前 section 到 `01:06:17` 只提出问题，没有给正式答案；下一 section 从 `01:12:22` 回来后用 version numbers 解决。[01:05:30-01:06:17]

## 概念、符号与推导

### Recovery ordering

```text
request for lock held by unreachable WS1
  -> revoke fails
  -> wait for WS1 lease expiry
  -> choose surviving workstation WS3
  -> WS3 reads WS1 log from Petal
  -> replay eligible complete records
  -> WS3 reports recovery complete
  -> LS may grant recovered locks
```

[00:59:55-01:00:58]

### 完整前缀性质

设 `r1, r2, ..., rn` 是 workstation memory log 中按顺序生成的 atomic-operation records。Crash during force 可能让 Petal 保留：

$$
r_1,r_2,\ldots,r_k,\text{torn}(r_{k+1}).
$$

Checksum 检查使 recovery 只接受 $r_1\ldots r_k$，不接受 torn record。课堂结论是“丢 suffix 可接受，执行半条 operation 不可接受”。[01:02:14-01:03:34]

### Many-log stale replay 问题

```text
WS1 log: delete(d/f) ---- old operation ---- WS1 crashes
WS2 log:          create(d/f) ---- newer operation
WS3 recovery: replay WS1 log only ?
```

仅凭 sequence number 不能解决，因为各 workstation logs 独立。需要比较 log update 与 Petal metadata block 的版本；该 rule 在本段尚未讲出。

## 例子与课堂提示

- **daemon 的 house-keeping 类比** [01:00:25-01:00:49]：用于解释术语，而不是引入新故障模型。
- **`f`、`g` 完整，`h` 不完整** [01:02:47-01:03:21]：用于区分 record atomicity 与整批 log atomicity。系统接受一批 operations 的 prefix，不要求整批全有或全无。
- **delete 后 recreate 同名 `d/f`** [01:04:19-01:05:30]：这是 Lecture 12 Paper Question 的课堂版本，检验多个独立 logs 如何避免旧 operation 撤销 later update。
- **breakout 作为 chronology 边界** [01:05:30-01:06:17]：本段只记录问题陈述；不能把下一段的 version-number solution 倒填成老师在 breakout 前已讲出的答案。

## 本段掌握检查

1. **问：谁执行 crashed workstation 的 recovery，log 为什么必须在 Petal？**  
   **答：** 另一个 surviving workstation 的 recovery daemon 执行；共享 Petal 让它能读取 crashed `WS1` 的 log。[00:59:55-01:00:49]
2. **问：LS 何时可以重新 grant 旧 locks？**  
   **答：** 旧 lease 已过期，且 recovery daemon 已完成 log replay 并报告完成之后。[00:59:55-01:00:58]
3. **问：crash during log force 时如何避免 replay 半条 operation？**  
   **答：** Recovery 检查 record checksum；遇到 incomplete/torn record 就停止，只 replay 前面的完整 records。[01:01:37-01:03:09]
4. **问：为什么只恢复 operations 的 prefix 是可接受的？**  
   **答：** Crash 本可发生得更早而丢失更多 recent operations；接受 durable complete prefix 保留结构一致性，代价只是丢 suffix。[01:03:10-01:03:40]
5. **问：`delete(d/f)`、later `create(d/f)` 场景的核心风险是什么？**  
   **答：** Recovery 若只看旧 `WS1` log 并无条件 replay delete，会撤销 `WS2` 的 newer create；下一段需用版本机制判断 stale record。[01:03:47-01:05:30]

# 第 8 段：version-number recovery 与全讲收束

> 时间范围：`01:12:22-01:22:20`
>
> 证据范围：本段 prompt 明确为 transcript-only；性能只记录老师在课堂实际说出的“随 workstation 数扩展”结论，不从讲义补入未口述的 Figure/Table 数值。

## 本段在整讲中的作用

Breakout 后，老师解决 Lecture 12 的核心 Paper Question：每个 metadata update 携带与目标 block/inode 关联的 version number，recovery 只在 log version 高于 Petal current version 时 replay，因此旧 `delete` 不会覆盖 later `create`。随后他从具体机制退回整讲主题，强调真正值得记住的是 coherence、distributed locks/leases、distributed recovery 以及三者交互，并用工作负载随 workstation 数增长的图概括扩展性目标。正式结束后，学生继续追问 exclusive-cache 简化、log-record atomicity 和 prefix replay，为下一 section 的尾部复述建立上下文。[01:12:22-01:22:20]

## 教学展开

1. **重新陈述 stale-replay 场景。** `WS1` 的 log 有 delete `d/f`，`WS2` 后来 create `d/f` 并写自己的 log，`WS1` crash 后 `WS3` 只 recover log 1。若 replay old delete，就会破坏 later create。[01:12:22-01:13:08]
2. **学生提出 version numbers。** Locking 已经使相冲突 operations 有顺序；metadata block 在 Petal 保存当前 version，log update 也保存它准备安装的 version。Recovery daemon 不能盲目重复 old operation，而要比较二者。[01:13:15-01:13:51]
3. **用 10/11 具体化顺序。** `WS1` delete 更新 directory/metadata 的版本为 10；`WS2` later create 在读取 current version 后写 version 11。Lock protocol 确保这些冲突 updates 被 totally ordered，所以 later operation 能基于前一个 current version 生成 `+1`。[01:13:53-01:15:11]
4. **给出 replay rule。** 只有 log record 中 update version 高于 Petal metadata block current version 时，recovery 才 replay。例中 old delete 的 10 小于 current 11，所以跳过；老师补充 equal 也不需 replay，因为该 version 已经安装。[01:15:12-01:16:00]
5. **澄清 version 的粒度。** Version 与被修改的具体 inode/metadata block 绑定，不是 workstation log 的单一全局 counter。Record 的 updates array 中，每一项分别带 block number、version number、new bytes；目录与 file inode 可各有自己的 version。[01:16:02-01:17:29]
6. **从机制退回论文价值。** 老师说系统本身未成为主流，但 ideas 重要：cache coherence/cache consistency；distributed locking，包括 grant/request/revoke、lock server、leases；distributed recovery，即一台 workstation crash、另一台的 daemon 恢复它。最有趣的是三者互相依赖。[01:17:32-01:18:59]
7. **连接后续课程。** 之后更复杂的 transaction systems 还会出现这些主题；Frangipani 帮学生先建立 vocabulary 和 interaction model。[01:18:35-01:18:59]
8. **简述扩展性证据。** 论文年代久远，绝对 performance numbers 难直接比较；但图表显示 file-system workload capacity 随 workstation 数增加，这正是 client-side computation 希望达到的目标。老师没有在本段口述 small/big-file figures 的具体坐标和 MB/s。[01:19:02-01:19:40]
9. **正式结束后回答 cache-copy 问题。** 学生问 coherence protocol 是否意味着同一 file 不会 cache 在两处，老师在本讲 exclusive-lock 简化下回答 yes。应结合前面 shared read locks 的优化理解：多个 read-only caches 是真实设计可有的情况。[01:19:42-01:20:09]
10. **再次讨论 record atomicity。** 一条 record 有多个 updates；老师重申 paper 在精确实现上略模糊，可能 record fits in one atomic 512-byte sector，也可能读多个 sectors 后用 checksum 验证 complete。老师明确说不确定具体采用哪种。[01:20:09-01:21:18]
11. **学生要求重讲 log prefix。** 学生回到 crash midway through writing log 的场景；老师开始列举一个 workstation 连续 create `f`、create `g`、delete `f` 等 operations，每个 operation 对应一条 record。完整解释延续到下一 section。[01:21:22-01:22:20]

## 概念、符号与推导

### Version replay rule

对 log 中某项 update $u$，令 $v_{log}(u)$ 为它携带的 target version，$v_{petal}(block)$ 为 Petal 当前 metadata block version。课堂规则是：

$$
replay(u) \iff v_{log}(u) > v_{petal}(block).
$$

- $v_{log}<v_{petal}$：有 newer update，old record stale，跳过。
- $v_{log}=v_{petal}$：该 update 已安装，不需重复。
- $v_{log}>v_{petal}$：该 update 尚未安装，可 replay。

[01:14:38-01:16:00]

### 为什么 `+1` 有意义

```text
acquire lock for metadata object
  -> observe current object/block version v
  -> prepare update with version v+1
  -> WAL + install
  -> release lock
```

Locking 使同一 object 的 conflicting operations 串行，后一个 writer 才能建立在 current version 上；version comparison 又让 recovery 识别 operation 是否已被同一或 newer update 覆盖。[01:13:22-01:16:29]

### 三个机制的交互

```text
locks order conflicting operations
  -> versions encode that order at metadata blocks
WAL makes an operation redoable after partial install
leases stop an unreachable old owner from writing forever
recovery daemon replays only complete, still-newer updates
  -> LS can safely transfer locks
```

## 概念、符号与推导

### Prefix durability，不是 batch atomicity

```text
records in WS memory: r1 r2 r3 r4 r5
force interrupted:    r1 r2 r3 [torn r4]
recovery accepts:     r1 r2 r3
recovery rejects:              r4 r5
```

只要 `r1-r3` 每条都对应完整 atomic file-system operation，接受这个 prefix 不会制造 partial metadata operation。系统牺牲 recent-operation durability，保留 internal consistency。[01:22:20-01:23:45]

### Lease 与 delayed write race

```text
WS1 lease expires
  -> LS/recovery lets WS2 acquire lock
  -> WS2 writes new state to Petal
  -> WS1's previously issued old write arrives late
  -> old bytes may overwrite WS2's new bytes
  -> consistency breaks
```

### 分层 tradeoff

- **独立 Petal interface 的好处：** 上下层可分别设计，Frangipani 只依赖 block storage abstraction。[01:26:37-01:26:49]
- **缺点：** Petal 不理解 Frangipani lock lease/fencing state，就难以拒绝过期 owner 的 stale writes。[01:26:49-01:27:11]
- **老师提出的支持：** write 携带可供 Petal 判断 freshness 的 timestamp。课堂没有给出完整 timestamp protocol、clock assumption 或 proof；不能静默补成成熟方案。[01:26:49-01:27:11]

本段无数值公式推导；margin 的具体大小和时钟误差条件均未在课堂给出。
